# M4.1 additional items

Two fixes found on 2026-10-21 from GitHub's runner after M4.1 was archived, decided by Dickson the same day. Each is one step under `REVIEW.md`. Evidence for both is in the artifacts of runs 39613639083 (commit eff11a35) and the `ci` job of the run on 4304016c; the logs read from them are quoted below where they matter.

## A failed ancestor hop is reported as ancestors unknown, not as the desktop root

Decided (Dickson, 2026-10-21): the remote-operations ancestor walk reports a hop that fails from an element below the root as ancestors unknown, the way an out-of-time walk is reported, instead of as a complete walk that reached the root.

What happens today. In `crates/verbatim-uia-rops/src/focus.rs`, `focus_ancestry_classic` (near lines 849 to 864) treats any failed hop to the parent other than a timeout as having reached the desktop root, and a parent that is the root the same way. A focus whose element is gone before its first hop, such as File Explorer's "Working on it..." placeholder during a slow folder load, therefore comes back as a complete walk with zero ancestors. The listener (`crates/verbatim-outpost/src/focus_read.rs`, about lines 1043 to 1054) turns a walk that was not out of time into a known, empty chain; the outpost's `uia_chain_onward` (`crates/verbatim-outpost/src/outpost/read.rs`, about lines 352 to 364) returns the empty chain without continuing through MSAA because the walk was complete; the worker reports `ancestors_unknown: false` with no ancestors; and Core's reducer (`crates/verbatim-core/src/reduce.rs`, lines 707 to 715 and 791) stores the placeholder as the focus with no containers. The next focus in the same window, the folder's first item, then finds nothing of its chain in the stored one (`entered_ancestors`, lines 2139 to 2174, matching by node id and by role and name both fail against a chain holding only the placeholder), so every container counts as entered and the window's client pane is spoken as the window's title. In run 39613639083 the Enter step of `explorer_folder_window` spoke "Working on it...", "Inner - File Explorer", "Items View list", "delta not selected 1 of 1"; the title is the one File Explorer set after Enter, and the window kept its node (number 10) across the retitle, so matching by node would have kept it silent. The listener's lines for the placeholder: `UIA focus ancestors read path="classic" read=0 met_known=None depth_limited=false out_of_time=false window=Some(197444)`, then the outpost's `focus reported role=StaticText name=Some("Working on it...") ... ancestors_unknown=false` and `the focus's own element looked for by its path found=false`. The same shape failed run 39573264801; the roadmap's entry on that run guesses a role-and-name mismatch after the retitle, which is wrong and is to be replaced.

What NVDA does (pinned 732d1ce2, read from source, no capture): the placeholder's failed parent read falls back to the window hierarchy (`nvda/source/NVDAObjects/UIA/__init__.py` lines 2142 to 2145; `nvda/source/NVDAObjects/window/__init__.py` lines 287 to 293), so NVDA never stores an empty chain for a focus inside a window; the item's chain then meets the old one at the window (`nvda/source/api.py` lines 111 to 143) and only the ancestors past the meeting point are spoken (`nvda/source/eventHandler.py` line 418). NVDA says the placeholder, "Items View list", the item, with no title.

The change. The walk reports a failed hop from a non-root element as unknown (reuse `out_of_time`'s outcome or add one that `focused` in `focus_read.rs` turns into `ancestors: None`); the listener and the outpost then take the existing unknown path, and Core keeps the previous chain, matches the window by node and enters only the new list. No reducer change. Whether the failed hop in the run was an error or a parent returned as the root could not be told from the logs, since both log `read=0`; make the two cases distinguishable in the log while there. One mockapp test in `remote_ops.rs` of a focus whose parent hop fails, next to the existing `a_focus_whose_walk_times_out_is_reported_with_its_containers_unknown`. Correct `docs/parity/focus-events.md`, "A focus whose element is gone before its read" (its Verbatim paragraph names the listener's classic read failing or its budget as what leaves the ancestors unknown; add the failed hop, now also unknown), and replace the roadmap's follow-up on run 39573264801 with the real cause and its fix. Related scenarios: `explorer_folder_window` (its placeholder is accepted at either place in each step, so a local pass does not prove the fix; the mockapp test does), and the `explorer_` scenarios.

## The unit-test job warms the speech platform before the tests

Decided (Dickson, 2026-10-21): the `ci` job in `.github/workflows/ci.yml` activates the Windows speech synthesizer once, in a PowerShell step before `cargo xtask ci`, as environment preparation like the step that closes the runner image's paging-file message box. Verbatim and its hang bound are unchanged.

What happens today. The runner's first activation of the Windows speech platform in a fresh session takes longer than ten seconds. The hosting tests in `crates/verbatim-synth-host/tests/hosting.rs` run in parallel threads under `cargo test --workspace`, five of them each start their own OneCore host, and the four that start first all wait on that one activation and are given up on at `HANG_TIMEOUT` (`crates/verbatim-synth-hosted/src/lib.rs` line 78, ten seconds) with "the synthesizer host sent nothing for 10s". The host's log from the `ci` job's `verbatim-ci-logs-X64` artifact on 4304016c (uploaded on failure since that commit, `target/debug/logs/<test pid>/synth-onecore.log`) shows four hosts logging "synthesizer host starting" and "creating the speech synthesizer" at 14:27:46.7 and nothing after; the next host, started at 14:27:56.9 after the timeouts, logged "enumerating voices" 2.3 seconds later and was ready; every host after it was ready in about 50 milliseconds. The ARM64 job passed in the same run. The same failure hit runs 39603654902 and 4304016c's run on 2026-10-21 and the run the roadmap recorded before 2026-10-15.

The change. A step named for what it does runs a short PowerShell that creates a `Windows.Media.SpeechSynthesis.SpeechSynthesizer` (WinRT from PowerShell: load the type with `[Windows.Media.SpeechSynthesis.SpeechSynthesizer, Windows.Media, ContentType=WindowsRuntime]`, construct it, read its voice, dispose it) and prints how long the activation took, so the job log shows the cold cost. Add the same step to `ci-arm64` only if it is shown to need it; it has not failed this way. Update the roadmap's OneCore item to say the cause is known and the job warms the platform, keeping the log upload for anything else.

Separate product question, not in this item, for a roadmap line: what Verbatim does for a user whose first OneCore activation after logon takes longer than the ten-second hang bound.
