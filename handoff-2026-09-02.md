## Purpose of the next several sessions

Dickson is returning to the project after six weeks and does not understand
most of the code, which was written in a rush over six days in July 2026.
The next sessions have two linked goals: make the existing runtime
trustworthy, and make its behavior understandable to Dickson. Pair reading
with small repairs, but establish the intended behavior before choosing
an implementation.

The work is a bounded correctness review of Core-outpost communication,
process recovery, and speech delivery, supported by repairs to the test
harness. Preserve the main architectural boundaries: the pure reducer,
per-application outposts, the dedicated focus listener, and separate
synthesis and audio rendering. Simplify ownership and control flow within
and between those boundaries.

The audit findings remain useful evidence; their proposed implementations
are starting hypotheses, not commitments. Correctness and understandability
come first. Introduce types where they clarify established rules and make
them harder to violate; typestate conversion is not a separate objective.

## Decisions made on 2026-09-02

These are decisions of record for the work ahead. Decisions 2, 3, 5, 7,
and 8 are already reflected in `docs/architecture.md` (D3, D4, D14 to
D16, and section 14); the rest are process decisions that belong here.

1. No restart. The repository is kept and the problem areas are fixed in
   place. The reasoning is in `audit-2026-09-02.md` under "What this means
   for the restart question".

2. Development model. Dickson now develops on a Proxmox host with two Windows
   VMs: a primary VM where he works with Claude and runs cargo, and a
   secondary VM that runs Verbatim and NVDA. Builds are deployed from the
   primary into the secondary and the end-to-end suite runs against the
   secondary. Contributors without Proxmox must still be able to develop on
   one machine and test in a Hyper-V VM as today. Video captures that
   demonstrate Verbatim must keep working.

3. Guest transport. Standard tools, not bespoke protocol additions. OpenSSH
   Server on the guest, installed and key-provisioned by the existing
   harness script, carries file copies (scp) and remote commands (ssh) on
   both Hyper-V and Proxmox. The in-guest agent keeps only what SSH cannot
   do: launch processes in the interactive session, report session facts,
   and tunnel the control-plane named pipe. Hypervisor backends handle
   lifecycle and snapshots only. A proposal to add a chunked put-file
   request to the agent protocol was withdrawn.

4. NVDA as reference, not as a test oracle in CI. A small packaged NVDA
   add-on hooks the pre-speech-queued extension point, records one entry
   per speech sequence with a timestamp, flattened to text the way NVDA's
   own test spy does, and serves them over TCP using the framing the agent
   already speaks. Keystrokes come from real OS input through the agent, so
   NVDA is driven the same way Verbatim is. The transcript is a research
   instrument used interactively: Claude drives NVDA on the secondary VM,
   captures what it says for a scenario, and uses that to decide what
   Verbatim should do and to write Verbatim's own end-to-end assertions by
   hand. Where Verbatim legitimately behaves differently, that is decided
   case by case when the test is written and recorded in `docs/parity.md`.
   Verbatim's tests never compare against an NVDA transcript directly, and
   NVDA is never installed or run in continuous integration. No fork of
   NVDA, and NVDA's Robot Framework spy is not reused directly. Normally
   NVDA and Verbatim run separately. The exception is NVDA reading
   Verbatim's own GUI, which Dickson wants as the source of expected
   readings for the menu and settings dialog and as the before-and-after
   check for the GUI port: for that, Verbatim runs with the test-audio
   setting so it is silent, the two readers get different modifier keys
   (Verbatim's share-modifier setting exists for a second reader hooked
   behind it), and keys are injected through the agent's real OS input so
   NVDA sees them as keyboard presses.

5. GUI. wxDragon is removed entirely. The wxWidgets part becomes a minimal
   C++ layer compiled from the GUI crate's build script through cxx, linking
   static wxWidgets per architecture. Rust keeps `main` and all logic, so
   `cargo xtask ci`, the ARM64 cross-build, deploy, and the end-to-end suite
   stay cargo-driven. `d:\source\loadstone` is the pattern reference for the
   cxx bridge, the typed page models, the callbacks class, and the
   wxAccessible subclass, but not for the build shape, since loadstone has
   C++ owning `main`, no ARM64 build, and no CI. The static wxWidgets build
   recipe for both architectures already exists in wxdragon-sys's build
   script in the cargo registry and should be adapted, not rewritten. The
   alternative of keeping wxDragon with a C++ shim was raised and rejected;
   do not raise it again.

6. Order of work, revised 2026-09-05: learn the vocabulary and map
   ownership; repair harness integrity; review speech delivery; review and
   simplify Core-outpost coordination; verify the boundaries and consolidate
   understanding; then resume the Proxmox backend, NVDA transcript tool,
   GUI port, and M4 work. The phases below define completion criteria rather
   than calendar estimates. NVDA transcripts inform later behavior work;
   communication and recovery correctness do not wait for that tool.

7. Checkpoint restores are deliberate, never automatic. In July the test
   verb restored the golden checkpoint on every run unless `--no-restore`
   was passed, and that was a major source of slowness in the interactive
   loop. Nothing is installed into the guest (deploy copies files and
   hash-skips unchanged ones), so a restore buys nothing on an ordinary run.
   The default flips: `cargo xtask vm test` does not restore; a restore
   happens only through the `restore` verb or an explicit opt-in flag on
   `test`, and the same rule applies to the Proxmox backend's snapshot
   rollback. The cold-start loop under "Carried forward from July" is the
   one place a fresh restore per run is the point, and it asks for it
   explicitly.

8. Architecture decisions D14 (attention model), D15 (split latency
   budget), and D16 (recording audio from Verbatim's own rendering) were
   ratified on 2026-09-02 and written into `docs/architecture.md`, along
   with rewritten D3 and D4 and a rewritten section 14. eSpeak NG moves
   from M8 to the opening work of M4. `architecture-review-2026-09-02.md`
   holds the reasoning behind each.

## Reference points for the work ahead

Facts gathered on 2026-09-02 that the next session would otherwise have to
rediscover.

The NVDA transcript add-on, from reading `nvda/tests/system`:

- NVDA's own spy is a scratchpad global plugin plus a replacement synth
  driver (`tests/system/libraries/SystemTestSpy/speechSpyGlobalPlugin.py`
  and `speechSpySynthDriver.py`), served over XML-RPC on port 8270 for
  Robot Framework. It is not reused: it silences NVDA and carries a
  transport Verbatim does not want.
- The public hook to use instead is `speech.extensions.pre_speechQueued`
  in `nvda/source/speech/extensions.py`, which fires with the fully
  processed sequence and leaves the real voice speaking. NVDA's own Remote
  Access feature uses the same hook, which is the proof it is stable API.
- Flatten a sequence the way the spy does (`_getJoinedBaseStringsFromCommands`):
  keep only string items, join, strip. That makes the transcript lexically
  comparable to Verbatim's speech frames from day one.
- Settling: the spy waits for the speech index to advance and then one
  second of quiet (`SPEECH_HAS_FINISHED_SECONDS`), polling no faster than
  10 ms so NVDA's core is not starved. Keep the same rule.
- Do not inject keys through NVDA's `inputCore` as the spy does; it skips
  NVDA's own keyboard hook. Inject real OS input through the agent, which
  today has no input request: `SendKeys` lives in Verbatim's control
  plane, so the agent needs a small `SendInput` request added, reusing
  `verbatim-control`'s parser and key table.
- Ship it as a packaged `.nvda-addon` so it works against an installed
  NVDA without the scratchpad setting. Pin the NVDA version in the guest.
- NVDA's `nvda.log` with the `speechManager` debug category logs every
  queued sequence as a Python `repr`; a zero-code fallback if the add-on
  is ever unavailable.

The harness backend, from reading `xtask/src/vm`:

- Everything runs through the fourteen-method `Host` trait in `host.rs`;
  `HyperVHost` (about 220 lines) is the only implementation and there is
  no fake for tests. After the D3 change the trait shrinks to lifecycle
  (exists, start, stop, snapshot, restore, delete, address), and a fake
  implementation should arrive with the Proxmox one.
- Guest file transfer today is `Copy-VMFile` (host to guest only) and
  base64 over PowerShell Direct for reading back, which buffers a whole
  recording in memory several times over. Both go away with SSH: scp in
  both directions, ssh for the commands `run_in_guest` issues today (the
  audio-device pin, ffprobe, RDP enablement).
- `renew_guest_dhcp` exists only because Hyper-V's Default Switch changes
  its subnet on host reboot; it is a no-op elsewhere. Guest address
  discovery reads the Hyper-V adapter; on Proxmox use a configured address
  or hostname from `.env`.
- The agent's TCP port (44001), the stderr log path, and the agent client
  are each duplicated between crates; fold them when touching the harness.
- Backend selection is hardcoded (`let host = host::HyperVHost;` in
  `mod.rs`); it becomes a `.env` key alongside the guest credentials.

## Working agreements

These apply to every session and are the ones the memory notes carried.

- Dickson is a screen reader user. No ASCII diagrams, box drawings, arrow
  chains, or symbol shorthand anywhere he reads: code comments, commit
  messages, documentation, or chat. Prose and lists over pipe tables.
- NVDA parity means NVDA with simple review mode off. Focus-ancestry
  filtering is a separate rule and stays.
- Fix causes, not symptoms. No retries that paper over flakes, no
  documented flakiness, no interim mitigations when the real fix can be
  pulled forward.
- No infrastructure for hypothetical hardware or speculative conditions.
- One shared clipboard-copy helper owns the spoken confirmation; every
  copying gesture routes through it.
- When infrastructure is needed, name the standard tool before proposing
  something bespoke.
- End every implementation task with a plain-prose walkthrough of the
  change, and keep changes readable in size.
- Commits are unsigned, single-line imperative subject, and stay on local
  `main` until Dickson asks to push. `cargo xtask ci` before every commit.
- Behaviour changes are verified live before they are committed.
- Reviews are read-only unless implementation or verification commands
  have been authorized. State the scope of those commands before running
  them. A documentation edit does not authorize compilation or tests.
- Before changing a subsystem, explain its current behavior in plain prose:
  who owns its state, what messages cross its boundary, what ordering it
  guarantees, and what happens on overload, timeout, cancellation, failure,
  and restart. Distinguish implemented guarantees from intended ones.
- Agree on intended behavior before choosing its representation. Prefer
  fewer independent mechanisms and fewer places that must remember the
  same correctness rule. Explicit enums and owning resource wrappers are
  useful where they clarify ownership; more elaborate typestate and
  capability tokens are secondary to correctness and understandability.
- Keep changes independently reviewable. End each phase with a walkthrough
  of the resulting behavior, supporting verification, and remaining
  limitations. Retain useful type safety without unrelated type conversions.

## Additional findings from the second review, 2026-09-05

These are the five additional findings discussed with Dickson and included
in the revised plan. They come from targeted code inspection; their
triggering scenarios have not been reproduced live. Numbers in this section
are independent of the original audit's item numbers.

1. Outpost incarnation is missing from the reducer's source identity. A
   restarted outpost resets its snapshot counter, while the reducer retains
   the previous counter for the application PID. New events can consequently
   be rejected as stale until the counter catches up. Ordinary events and
   replies also lack the generation checks used for heartbeat and lifecycle
   handling. See `verbatim-core/src/state.rs`, `verbatim-app/src/main.rs`,
   and `verbatim-outpost/src/supervisor.rs` under `crates/`.
   Acceptance: a replacement's first event is accepted, obsolete incarnation
   messages are rejected, and replacement retires the previous incarnation's
   version history, focus and navigator state, and pending requests.

2. Query deadlines expire the wait, not the work. Queued jobs can expire
   before starting and still execute later; the pool counts these as
   abandoned workers. Running fire-and-forget jobs retain permission to
   publish after expiry. See `crates/verbatim-outpost/src/query_pool.rs`
   and the worker-published events and replies in `runtime.rs`.
   Acceptance: distinguish queued from running work, prevent expired queued
   jobs from starting, suppress accepted results from expired running jobs,
   and produce exactly one terminal outcome for each accepted request.
   An activation already issued to another application cannot be undone;
   distinguish that uncertainty from expiry before execution.

3. Speech completion is not reliable evidence of completed playback. The
   manager reports completion after an audio-drain error, the WASAPI drain
   path can return success after a wait failure, and paced tests accept a
   completion belonging to any utterance. See
   `crates/verbatim-speech/src/manager.rs`,
   `crates/verbatim-audio/src/wasapi.rs`, and
   `crates/verbatim-e2e/src/speech.rs`.
   Acceptance: completion, cancellation, and failure are distinct outcomes
   carrying the utterance's identity. Failure or cancellation never reports
   successful completion; pacing waits for the matched utterance's outcome.

4. Protocol framing loses partial messages on read timeout. The JSON-line
   reader discards its temporary buffer when a read times out after
   consuming part of a frame. Retrying then starts in the middle of that
   frame. See `crates/verbatim-control/src/protocol.rs` and `client.rs`,
   and the timeout setup in `crates/verbatim-e2e/src/agent_client.rs`.
   Acceptance: an incomplete frame survives timeouts and is decoded exactly
   once, followed correctly by the next frame. Preserve decoder state, or
   decode continuously and apply assertion deadlines to complete messages.

5. Tree-dump replies are not correlated with pending requests. A delayed
   reply to a timed-out request can satisfy a newer request, potentially
   for another application. See `incoming_input` and `request_dump_tree`
   in `crates/verbatim-app/src/main.rs`.
   Acceptance: match delivery and cleanup to request identity and outpost
   incarnation. An old reply or timeout cleanup may never satisfy or clear
   a newer request.

## Correctness and simplification plan, paired with reading

These phases replace the original seven reading steps. Audit item numbers
refer to `audit-2026-09-02.md`; references to additional findings refer to
the five findings above. Read and repair in small increments. Completion
criteria replace the original hour and day estimates, and the outpost work

### Phase 1: learn the vocabulary and map ownership

Read `docs/architecture.md` before proposing design changes, then
`docs/glossary.md` and `crates/verbatim-model/src/` in the order `lib.rs`,
`tree.rs`, `event.rs`, `speech.rs`, `gesture.rs`. Hold in mind that the
reducer uses normalized node identities and emits structured utterances;
`Input` and `Effect` are its interface with the world.

Read `docs/walkthroughs.md`, `crates/verbatim-core/src/reduce.rs` and
`state.rs`, then skim `tests/reduce.rs` by test name. Understand version
staleness, focus timestamp ordering and its window and ancestor exceptions,
and identical-focus suppression. Distinguish the reducer's ordering rules
from the app's current foreground PID gate.

Use `crates/verbatim-app/src/main.rs` as the composition map. Trace one
focus announcement, one navigation request, one outpost restart, and one
interrupted utterance. Consult the outpost and speech crate guides, then
the relevant functions, to explain who owns each state transition and what
happens on failure. Record missing guarantees rather than explaining the
intended architecture as though the code already implements it.

Small reducer repairs can accompany this reading: establish the intended
priority for late window announcements (audit item 16), and the behavior
when a focused object disappears (item 15). Decide whether an independently
positioned, still-valid navigator survives before choosing a representation.
Do not require focus and navigator to become one enum. Retirement of a whole
outpost incarnation, including pending fetches, belongs to phase 4.

Completion: Dickson can explain the four paths and their state owners,
including the known gaps. Any behavior repaired here has a focused
regression case and the verification required by the working agreements.

### Phase 2: make the harness trustworthy

Read `docs/tooling.md`, `docs/crates/verbatim-e2e.md`,
`crates/verbatim-e2e/src/scenario.rs`, `speech.rs`, and `agent_client.rs`,
`crates/verbatim-control/src/protocol.rs` and `client.rs`,
`xtask/src/vm/test.rs`, `deploy.rs`, and `recording.rs`, and
`crates/verbatim-agent/src/tunnel.rs`.

Repair artifact freshness, deploy recovery, recording attribution, tunnel
teardown, and the environment-mutating test (audit items 9, 10, 12, 11,
and 20). Flip the restore default per decision 7: restore is opt-in, and
the old `--no-restore` flag and warning go away.

Repair partial-frame preservation (additional finding 4). Add deterministic
coverage that delivers part of a frame, a timeout, its remainder, and a
second frame. Both frames must be decoded exactly once. Timeouts must not
silently discard bytes already consumed by the decoder.

Repair pacing's discarded speech frames (audit item 8) together with its
utterance correlation (additional finding 3). Preserve speech encountered
while waiting and do not let an unrelated completion release the wait.
Distinguish assertions about speech being queued from assertions about
playback completing; cancellation, failure, and timeout are not successful
playback. Complete the producer side of this contract in phase 3.

Completion: old artifacts, unrelated completions, and partial frames cannot
masquerade as successful observations. Run the suite against the available
interactive test VM when authorized, restoring deliberately when needed.
Until phase 3 supplies truthful playback outcomes, passing a queued-speech
assertion remains evidence of queuing only.

### Phase 3: review and simplify speech delivery

Read `crates/verbatim-speech/src/manager.rs`, `theme.rs`, `driver.rs`, and
`events.rs`, then `crates/verbatim-audio/src/wasapi.rs` and
`crates/verbatim-synth-onecore/src/lib.rs`. Review the queue, synthesizer,
and sink as one system while preserving their separate responsibilities.

Define each utterance's lifecycle and identify the owners of cancellation
and terminal outcomes. Explain what queued, started, completed, cancelled,
and failed mean, including cancellation before synthesis and during audio
rendering. Define when the sink has actually completed playback.

Repair format negotiation and failed-stream recovery, including resource
cleanup (audit items 3 and 4). Include default-device changes, interruption,
and discard of buffered audio in the review. Review OneCore's polling,
cancellation responsiveness, and repeated voice enumeration (item 17).
Choose the simpler interface or state representation after these behaviors
are clear; a typestate stream is an option, not a required design.

Implement additional finding 3: carry utterance identity through synthesis,
rendering, and the terminal outcome. Successful completion requires a
successful drain. Propagate drain errors and render wait failures as
failures, and report cancellation separately. Complete phase 2's correlated
pacing against these outcomes.

Completion: a controllable sink verifies successful drain, failed drain,
and interruption, with one terminal outcome per utterance and pacing
waiting for the correct one. Verify actual playback, interruption, and
device recovery live. Explain remaining cancellation limits explicitly.

### Phase 4: review and simplify Core-outpost coordination

Read architecture sections 1 and 4 and decisions D9 and D13, then
`docs/crates/verbatim-outpost.md`. Read the outpost code in this order:
`protocol.rs`, `query_pool.rs`, `arbitration.rs`, `listener.rs`,
`supervisor.rs`, and `runtime.rs`. Revisit the app's incoming-message and
request handling and the reducer's version history and pending fetches.
The correctness boundary spans these crates, not just the outpost crate.

Establish the contracts first, then implement separate, reviewable increments:

1. Give lifecycle decisions one owner, with explicit spawning, readiness,
   retirement, and replacement behavior. Other threads report facts to that
   owner. Close the competing-spawn window (audit item 14); keep blocking
   process creation outside the lifecycle decision loop and shared locks.

2. Carry incarnation identity through events, requests, replies, and reducer
   cleanup (additional finding 1). Retire state owned by the old incarnation
   and reject its delayed messages, including messages already queued for
   delivery. A replacement's first event must be accepted regardless of its
   predecessor's snapshot counter. Preserve snapshot ordering within each
   incarnation by assigning versions in outbound serialization order
   (audit item 5).

3. Remove blocking writes from shared-lock and coordination paths (audit
   item 1), including listener heartbeat writes. A dedicated writer with a
   bounded channel is a candidate. Specify overload policy by message kind:
   coalesce replaceable focus facts while preserving the newest fact;
   explicitly fail requests that cannot be accepted; keep heartbeat and
   lifecycle delivery from depending on unbounded ordinary work. Do not
   apply a blanket drop-on-full rule to all commands.

4. Unify request scheduling, correlation, expiry, and terminal outcomes
   (additional finding 2). Distinguish queued work from running work, discard
   expired queued jobs before execution, and revoke publication rights when
   running work expires. Track abandoned running workers by identity;
   returning abandoned workers retire and reduce the count (audit item 2).
   State the uncertainty of an activation already issued to another app;
   expiry cannot undo its side effect.

5. Move fetch, navigation, activation, ancestry, and dump handling off the
   command loop using that shared request contract (audit item 6). Each
   accepted request receives one terminal outcome, including explicit
   timeout or retirement failure. Moving sends into worker closures alone
   does not meet this requirement: expired workers must not publish accepted
   replies or events.

6. Correlate tree-dump replies and timeout cleanup in the app (additional
   finding 5). Store request identity and incarnation with the pending
   sender. An old reply may neither satisfy nor clear a newer request, and
   timeout cleanup may remove only its own request.

7. Converge on one announcement implementation. Drain queued facts in
   observation order (audit item 13), bound event-driven concurrency
   (item 18), and retire the legacy poll once the listener-based path covers
   startup and recovery (item 22). Startup and recovery reconciliation use
   the same acquisition and announcement machinery. Move the duplicated
   MSAA window snapshot into verbatim-ia2 (item 23). Clarify arbitration
   verdicts and remove the obsolete resolver (item 25).

Keep the listener's never-block rule explicit and review its call paths.
Capability tokens are optional aids after ownership is clear, not a blanket
conversion requirement.

Completion: hanging, restarting, overloading, or receiving obsolete results
from one outpost cannot corrupt current state or prevent another application
from being read. Add deterministic cases for restart after a high snapshot
version, obsolete messages after replacement, expiry before and during
execution, returning abandoned workers, and an old tree-dump reply arriving
after a newer request starts. Use barriers or controlled channels to establish
ordering. Recreate the missing focus-churn scenario and follow with live
integration checks in phase 5.

Read `crates/verbatim-uia/src/client.rs`, `map.rs`, and `registry.rs`, then
`crates/verbatim-ia2/src/acquire.rs` and `hook.rs`. Review registry lifetime
and pruning (audit item 19), cache assumptions, and COM resource ownership.
Use owning resource wrappers where they remove manual ownership hazards,
including SAFEARRAY handoff. A cached-element wrapper or named MSAA address
can help if it clarifies the contract; broad newtype conversions are not
required. Preserve valid live identities when choosing registry eviction.

Finish the app and control-server reading, then
`crates/verbatim-input/src/state.rs`. Correct the stale multi-press and
other affected comments and guides (audit item 26). Review mockapp's missing
selection fidelity (item 21) when establishing backend verification.
Add the planned shared interactive-session probe to Verbatim's startup so
non-interactive launches receive a clear diagnosis, as the agent already
provides. Review the remaining audit findings and record each disposition;
do not lose lower-priority items during the broader correctness work.

Completion: Dickson can explain the resulting ownership, ordering, recovery,
and speech behavior. The five additional findings have explicit regression

### Phase 6: resume feature work from the stabilized baseline

Continue with the agreed Proxmox transport, NVDA research tool, GUI port,
and M4 work. Use NVDA transcripts to investigate the deferred real-app
scenarios and document intentional differences. Preserve the architectural
decisions, while treating attention behavior and latency feasibility as
questions requiring evidence rather than assuming the proposed mechanisms
have already proved them.

For attention, define global focus ordering, startup behavior, and events
arriving while attention updates are in flight before removing the PID
gate. For latency, introduce the stage ledger before optimizing; define
workloads, cold and warm conditions, cancellation accounting, measurement
points, and acceptance thresholds. Timestamp types and stage enums may
clarify these rules once established; they are not the goal themselves.

  it with the integrated runtime in phase 5.
- The three deferred scenarios (Explorer folder window, Settings-app
  toggle, Start-menu search results) have by-hand recipes in
  `docs/roadmap-done.md` and no automation. The Explorer scenario's source
  was never committed. One lesson from writing it survives only here: on
  the guest, poll for a precondition (a folder existing, say) by launching a
  checker whose captured output is read back through the agent, never by
  reading a fast process's exit code. The checker exits in milliseconds,
  its process object is gone before the agent's status poll opens it, and
  the agent then reports an exit with no code, indistinguishable from
  failure.
- One end-to-end flake remains unexplained: speech frames verifiably queued
  and written into the control pipe never crossed the agent's tunnel relay,
  and teardown's pipe disconnect discarded the unread data into a clean end
  of stream. It did not recur in eight clean runs. Logging was added to
  attribute any recurrence to a layer (the subscribe log line, each
  connection writer's frame total at close, the tunnel's per-direction byte
  totals). Do not chase it speculatively; audit item 11 is a candidate
  cause and should be fixed first.
- One unchased one-off: an MSAA value-change announcement (a rate slider
  reading "79") was missed once in eight suite runs under load.
- The announce poll's retry budget (ten attempts across about five seconds)
  was set without consulting Dickson; any further policy change there
  should be raised with him. Phase 4 retires the poll once startup and
  recovery are covered by the shared announcement machinery.
- The UIA element cache clears wholesale at 2,048 entries, a stopgap
  awaiting a real eviction policy (audit item 19).
