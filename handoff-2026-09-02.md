## Decisions made on 2026-09-02

These are decisions of record for the work ahead. Decisions 2, 3, 5, 7,
and 8 are already reflected in `docs/architecture.md` (D3, D4, D14 to
D16, and section 14); the rest are process decisions that belong here.

1. No restart. The repository is kept and the problem areas are fixed in
   place. The reasoning is in `audit-2026-09-02.md` under "What this means
   for the restart question".

2. Development model. Dickson now develops on a Proxmox host with two Windows
   VMs: a primary VM where he works with Claude and runs cargo, and a
   secondary VM that runs Verbatim and NVDA. Builds are deployed from the
   primary into the secondary and the end-to-end suite runs against the
   secondary. Contributors without Proxmox must still be able to develop on
   one machine and test in a Hyper-V VM as today. Video captures that
   demonstrate Verbatim must keep working.

3. Guest transport. Standard tools, not bespoke protocol additions. OpenSSH
   Server on the guest, installed and key-provisioned by the existing
   harness script, carries file copies (scp) and remote commands (ssh) on
   both Hyper-V and Proxmox. The in-guest agent keeps only what SSH cannot
   do: launch processes in the interactive session, report session facts,
   and tunnel the control-plane named pipe. Hypervisor backends handle
   lifecycle and snapshots only. A proposal to add a chunked put-file
   request to the agent protocol was withdrawn.

4. NVDA as reference, not as a test oracle in CI. A small packaged NVDA
   add-on hooks the pre-speech-queued extension point, records one entry
   per speech sequence with a timestamp, flattened to text the way NVDA's
   own test spy does, and serves them over TCP using the framing the agent
   already speaks. Keystrokes come from real OS input through the agent, so
   NVDA is driven the same way Verbatim is. The transcript is a research
   instrument used interactively: Claude drives NVDA on the secondary VM,
   captures what it says for a scenario, and uses that to decide what
   Verbatim should do and to write Verbatim's own end-to-end assertions by
   hand. Where Verbatim legitimately behaves differently, that is decided
   case by case when the test is written and recorded in `docs/parity.md`.
   Verbatim's tests never compare against an NVDA transcript directly, and
   NVDA is never installed or run in continuous integration. No fork of
   NVDA, and NVDA's Robot Framework spy is not reused directly. Normally
   NVDA and Verbatim run separately. The exception is NVDA reading
   Verbatim's own GUI, which Dickson wants as the source of expected
   readings for the menu and settings dialog and as the before-and-after
   check for the GUI port: for that, Verbatim runs with the test-audio
   setting so it is silent, the two readers get different modifier keys
   (Verbatim's share-modifier setting exists for a second reader hooked
   behind it), and keys are injected through the agent's real OS input so
   NVDA sees them as keyboard presses.

5. GUI. wxDragon is removed entirely. The wxWidgets part becomes a minimal
   C++ layer compiled from the GUI crate's build script through cxx, linking
   static wxWidgets per architecture. Rust keeps `main` and all logic, so
   `cargo xtask ci`, the ARM64 cross-build, deploy, and the end-to-end suite
   stay cargo-driven. `d:\source\loadstone` is the pattern reference for the
   cxx bridge, the typed page models, the callbacks class, and the
   wxAccessible subclass, but not for the build shape, since loadstone has
   C++ owning `main`, no ARM64 build, and no CI. The static wxWidgets build
   recipe for both architectures already exists in wxdragon-sys's build
   script in the cargo registry and should be adapted, not rewritten. The
   alternative of keeping wxDragon with a C++ shim was raised and rejected;
   do not raise it again.

6. Order of work: harness fixes, audio fixes, outpost concurrency, then the
   Proxmox backend, the NVDA transcript tool, the GUI port, and finally the outpost
   re-review with NVDA transcripts in hand. The first three items exist so
   the later ones stand on trustworthy ground.

7. Checkpoint restores are deliberate, never automatic. In July the test
   verb restored the golden checkpoint on every run unless `--no-restore`
   was passed, and that was a major source of slowness in the interactive
   loop. Nothing is installed into the guest (deploy copies files and
   hash-skips unchanged ones), so a restore buys nothing on an ordinary run.
   The default flips: `cargo xtask vm test` does not restore; a restore
   happens only through the `restore` verb or an explicit opt-in flag on
   `test`, and the same rule applies to the Proxmox backend's snapshot
   rollback. The cold-start loop under "Carried forward from July" is the
   one place a fresh restore per run is the point, and it asks for it
   explicitly.

8. Architecture decisions D14 (attention model), D15 (split latency
   budget), and D16 (recording audio from Verbatim's own rendering) were
   ratified on 2026-09-02 and written into `docs/architecture.md`, along
   with rewritten D3 and D4 and a rewritten section 14. eSpeak NG moves
   from M8 to the opening work of M4. `architecture-review-2026-09-02.md`
   holds the reasoning behind each.

## Reference points for the work ahead

Facts gathered on 2026-09-02 that the next session would otherwise have to
rediscover.

The NVDA transcript add-on, from reading `nvda/tests/system`:

- NVDA's own spy is a scratchpad global plugin plus a replacement synth
  driver (`tests/system/libraries/SystemTestSpy/speechSpyGlobalPlugin.py`
  and `speechSpySynthDriver.py`), served over XML-RPC on port 8270 for
  Robot Framework. It is not reused: it silences NVDA and carries a
  transport Verbatim does not want.
- The public hook to use instead is `speech.extensions.pre_speechQueued`
  in `nvda/source/speech/extensions.py`, which fires with the fully
  processed sequence and leaves the real voice speaking. NVDA's own Remote
  Access feature uses the same hook, which is the proof it is stable API.
- Flatten a sequence the way the spy does (`_getJoinedBaseStringsFromCommands`):
  keep only string items, join, strip. That makes the transcript lexically
  comparable to Verbatim's speech frames from day one.
- Settling: the spy waits for the speech index to advance and then one
  second of quiet (`SPEECH_HAS_FINISHED_SECONDS`), polling no faster than
  10 ms so NVDA's core is not starved. Keep the same rule.
- Do not inject keys through NVDA's `inputCore` as the spy does; it skips
  NVDA's own keyboard hook. Inject real OS input through the agent, which
  today has no input request: `SendKeys` lives in Verbatim's control
  plane, so the agent needs a small `SendInput` request added, reusing
  `verbatim-control`'s parser and key table.
- Ship it as a packaged `.nvda-addon` so it works against an installed
  NVDA without the scratchpad setting. Pin the NVDA version in the guest.
- NVDA's `nvda.log` with the `speechManager` debug category logs every
  queued sequence as a Python `repr`; a zero-code fallback if the add-on
  is ever unavailable.

The harness backend, from reading `xtask/src/vm`:

- Everything runs through the fourteen-method `Host` trait in `host.rs`;
  `HyperVHost` (about 220 lines) is the only implementation and there is
  no fake for tests. After the D3 change the trait shrinks to lifecycle
  (exists, start, stop, snapshot, restore, delete, address), and a fake
  implementation should arrive with the Proxmox one.
- Guest file transfer today is `Copy-VMFile` (host to guest only) and
  base64 over PowerShell Direct for reading back, which buffers a whole
  recording in memory several times over. Both go away with SSH: scp in
  both directions, ssh for the commands `run_in_guest` issues today (the
  audio-device pin, ffprobe, RDP enablement).
- `renew_guest_dhcp` exists only because Hyper-V's Default Switch changes
  its subnet on host reboot; it is a no-op elsewhere. Guest address
  discovery reads the Hyper-V adapter; on Proxmox use a configured address
  or hostname from `.env`.
- The agent's TCP port (44001), the stderr log path, and the agent client
  are each duplicated between crates; fold them when touching the harness.
- Backend selection is hardcoded (`let host = host::HyperVHost;` in
  `mod.rs`); it becomes a `.env` key alongside the guest credentials.

The GUI port, from comparing `crates/verbatim-gui` with loadstone:

- Survives in Rust unchanged: `plan.rs` (pure, ten tests),
  `hidden_frame.rs`, `foreground.rs` except its one wx handle conversion,
  `shell_items.rs` except two call-after lines, and `tray_list::click`.
- Rewritten in C++: `dialog.rs`, `list_dialog.rs`,
  `tray_list::build_shell_list_dialog`, and the widget half of `lib.rs`
  (init, show menu, open settings, shutdown, the close functions).
- Extract before porting, so the port cannot reintroduce the current bugs:
  the keyboard-shortcut routing table as a pure function (Enter on Cancel
  currently commits), the dialog lifecycle rules as one state machine, the
  category model's selection logic, the Speech panel's rebuild decision,
  and a real sender behind `GuiHandle` instead of a process-global queue.
- From loadstone (`d:\source\loadstone`): the cxx bridge shape (typed page
  models pulled by C++, a pure-virtual `UiCallbacks` class implemented on
  the C++ side, `CallAfter` marshalling with an alive flag), the
  `DescribedAccessible` subclass of `wxAccessible` that supplies accessible
  descriptions without breaking names, and the rule that narrow C++
  literals stay ASCII with all Rust text crossing as UTF-8. Not from
  loadstone: C++ owning `main`, CMake at the top, or the hand-built
  wxWidgets prefix.
- The static wxWidgets build for x64 and ARM64 is in the wxdragon-sys
  0.9.17 build script in the cargo registry: it downloads the pinned
  3.3.2 source and builds it through CMake, with the ARM64 cross-compile
  handled. Adapt it.

## Working agreements

These apply to every session and are the ones the memory notes carried.

- Dickson is a screen reader user. No ASCII diagrams, box drawings, arrow
  chains, or symbol shorthand anywhere he reads: code comments, commit
  messages, documentation, or chat. Prose and lists over pipe tables.
- NVDA parity means NVDA with simple review mode off. Focus-ancestry
  filtering is a separate rule and stays.
- Fix causes, not symptoms. No retries that paper over flakes, no
  documented flakiness, no interim mitigations when the real fix can be
  pulled forward.
- No infrastructure for hypothetical hardware or speculative conditions.
- One shared clipboard-copy helper owns the spoken confirmation; every
  copying gesture routes through it.
- When infrastructure is needed, name the standard tool before proposing
  something bespoke.
- End every implementation task with a plain-prose walkthrough of the
  change, and keep changes readable in size.
- Commits are unsigned, single-line imperative subject, and stay on local
  `main` until Dickson asks to push. `cargo xtask ci` before every commit.
- Behaviour changes are verified live before they are committed.
- Make invalid states unrepresentable. Dickson wants the compiler carrying
  as much of the correctness burden as it can, prompted by the July
  crashes. Where the audit found runtime discipline standing in for types
  (COM elements whose cache contract is a doc comment on an `unsafe fn`,
  raw `SAFEARRAY` ownership, an outpost's ready state as a bool beside a
  queue, thread roles enforced by comments), prefer newtypes, typestate,
  and capability tokens over conventions when touching that code. The
  specific sites are woven into the reading steps below, each in the step
  where its code is open.

## Reading order, paired with fixes

Each step names what to read, what to hold in mind while reading, and the
change to make in the same sitting so the reading sticks. Audit item numbers
refer to `audit-2026-09-02.md`. Times are rough and assume Claude is doing
the reading aloud and Dickson is following the structure rather than every
line.

### Step 1: the vocabulary (an hour, no fix)

Read `docs/glossary.md`, then `crates/verbatim-model/src/` in the order
`lib.rs`, `tree.rs`, `event.rs`, `speech.rs`, `gesture.rs`. This is 1,160
lines and every other crate speaks only these types. Hold in mind: the
reducer never sees backend identifiers, only `NodeId`; utterances are
sequences of typed spans, never strings, until the presentation theme; and
`Input` and `Effect` are the whole interface between the pure reducer and
the world.

### Step 2: the reducer (two hours, two small fixes)

Read `docs/walkthroughs.md` first, then `crates/verbatim-core/src/reduce.rs`
and `state.rs`, then skim `tests/reduce.rs` by test name to see what
behaviour is pinned. Hold in mind the three ordering rules: version
staleness per source, last-observation-wins on focus timestamps with the
window and ancestor carve-out, and identical-focus suppression. Fix audit
item 16 (late window spoken at Interrupt priority) and add a reducer test.
Fix audit item 15 (navigator left on a dead node) by making focus and
navigator one enum instead of two independent options, so a navigator
cannot outlive its focus; that enum is also where D14's attention record
lives, so shape it with the attention model in mind.

### Step 3: the harness, by fixing it (a day)

Read `docs/tooling.md` and `docs/crates/verbatim-e2e.md`, then
`crates/verbatim-e2e/src/scenario.rs` and `speech.rs`, `xtask/src/vm/test.rs`,
`deploy.rs`, and `recording.rs`, and `crates/verbatim-agent/src/tunnel.rs`.
Fix audit items 9, 10, 12, 8, 11, and 20 in that order, and flip the
restore default per decision 7 (`restore_golden_unless_skipped` in
`xtask/src/vm/test.rs` becomes opt-in, and the `--no-restore` flag and its
warning go away). Run the suite against the Hyper-V VM until it is green,
restoring only when a run has left the guest in a state worth discarding. This step is
first because every later step is verified with this harness, and today it
can report a pass for a scenario that never ran.

### Step 4: the speech and audio path (a day)

Read `crates/verbatim-speech/src/manager.rs`, `theme.rs`, and `driver.rs`,
then `crates/verbatim-audio/src/wasapi.rs`, then
`crates/verbatim-synth-onecore/src/lib.rs`. Hold in mind the two-thread
shape (queue thread owns lanes, synth thread owns driver and sink) and the
cooperative cancel flag. Fix audit items 3 (stream never rebuilt after a
device error, plus the leaked event handle) and 4 (format read before
synthesis) together, by making the synth-to-sink stream a typestate:
starting a stream with a declared format returns a handle whose only
methods are push and finish, an error consumes the handle, and the driver
declares the format with real data in hand. The `begun` and
`first_written` flags in the pipeline sink and the `running` flag and
reusable `stream` in the WASAPI sink disappear into it, and both defects
become unwritable rather than fixed. Item 17's polling sleeps can be
replaced in the same sitting.

### Step 5: the outpost, by fixing its concurrency (two to three days)

This is the crate that most needs to be understood and most needs to
change. Read `docs/architecture.md` sections 1 and 4 and decisions D9 and
D13, then `docs/crates/verbatim-outpost.md`, then the code in this order:
`protocol.rs`, `query_pool.rs`, `arbitration.rs`, `listener.rs`,
`supervisor.rs`, and finally `runtime.rs`. Keep the audit open. Then make one
change set:

- Give each running outpost its own writer thread fed by a bounded channel,
  so no pipe write ever happens under the outposts lock (item 1). While
  there, make the outpost's ready state a lifecycle enum (spawning with
  its queued facts, ready with its writer) rather than a bool beside a
  queue, and move the generation into the handle the supervisor's map is
  keyed by, so a stale message is a lookup miss rather than a comparison
  every path has to remember.
- Make snapshot versions mintable only by the outbound writer thread: the
  emit path produces an unversioned event type and the writer is the one
  place that turns it into a versioned wire message (item 5, by
  construction).
- Reply to dump, ancestor, navigate, activate, and navigation fetches from
  the pool worker instead of blocking the command loop (item 6).
- Make the pool's parked accounting track abandoned workers by identity and
  retire them when they return, so the count can go down (item 2).
- Turn thread roles into capability tokens: blocking backend calls take
  `&mut Worker`, which already exists, and the listener receives a context
  that exposes cached reads only, so its never-block rule is checked by
  the compiler.
- Make the arbitration verdict a three-variant enum (UIA, MSAA, unknown)
  instead of `Option<bool>`, and delete the dead `resolve_with` and
  `Resolution` (item 25).
- Drain queued facts in observation order (item 13), close the respawn
  window (item 14), and bound the per-event thread spawns (item 18).
- Delete the pre-D13 announce poll once the D13 lane covers the startup
  target (item 22), and move the window snapshot into verbatim-ia2
  (item 23).

Verify with the full suite on fresh restores and the cold-start loop (see
"Carried forward from July"). Update the crate guide's description of
parking to match the new code.

### Step 6: the backends (half a day, one fix)

Read `crates/verbatim-uia/src/client.rs`, `map.rs`, and `registry.rs`, then
`crates/verbatim-ia2/src/acquire.rs` and `hook.rs`. Hold in mind that every
UIA read is from a cache request built with the element, and that MSAA has
no such thing, so every MSAA property is a cross-process call. Add pruning
to both node-id registries (item 19). Then put the two crates' invariants
into types: a `CachedElement` newtype for a UIA element known to be built
with the base cache request, so `snapshot_from_cached_element` and its
siblings become safe functions and the contract leaves the doc comments;
an owning `SafeArray` wrapper that is consumed into the variant it is
handed to, so the July double free cannot be written again; and newtypes
for window handles, object ids, and child ids with a named MSAA address
struct in place of the three-integer tuple. The last touches outpost call
sites too; do it here because these crates define the vocabulary, and let
the compiler find the call sites.

### Step 7: the shell and the rest (half a day, no fix beyond comments)

Read `crates/verbatim-app/src/main.rs` top to bottom as the map of how the
threads connect, then `crates/verbatim-control/src/server.rs` and
`crates/verbatim-input/src/state.rs`. Correct the stale multi-press
comments in `main.rs` and the app guide (item 26). Add an
interactive-session check to Verbatim's startup: the agent already refuses
to run when its window station is not visible (its `session` module), but
`verbatim.exe` has no such check and, launched from SSH, WinRM, or a
service, would start with a keyboard hook that never fires and outposts
that see no events, and say nothing about why. Move the session probe into
a shared place and have Verbatim log and refuse in the same way.

After step 7 the runtime is known well enough to start the Proxmox backend,
the NVDA add-on, the M4 opening work, and the GUI port. Two type-level
items belong to those later pieces rather than to a reading step: the D15
stage ledger should introduce a timestamp newtype for epoch milliseconds
and a stage enum, so a stage cannot be recorded twice or out of order and
an `Instant` cannot be mixed with a wall-clock value; and the GUI port
should generate Fluent message ids as constants from the `.ftl` file, so a
mistyped descriptor label fails to compile instead of speaking the id, and
give the GUI handle a real sender instead of a process-global queue. The
GUI crate is deliberately not on this list: read
`crates/verbatim-gui/src/plan.rs` and `shell_items.rs` when the port
starts, since those survive it, and treat the rest as a specification to be
reimplemented rather than code to be learned. Not worth typing more
strictly: the reducer's clone-per-step state, the control-plane handler
bag, and the config value types; types there would cost more readability
than they save.

## Carried forward from July

Facts from the deleted July notes that the code and docs do not record.

- The cold-start loop is the reproducer for announce races: repeated runs of
  `cargo xtask vm test --scenario start_menu` and the same for
  `m1_exit_regression`, each on a fresh golden restore, until eight
  consecutive runs are clean. A menu-lag measurement worth keeping: on the
  July VM, Verbatim+V to hearing "Context menu" was about 110 to 190 ms
  warm.
- A rapid-focus-churn stress scenario was written in July and never
  committed; it is not in the tree. Recreate it during step 5.
- The three deferred scenarios (Explorer folder window, Settings-app
  toggle, Start-menu search results) have by-hand recipes in
  `docs/roadmap-done.md` and no automation. The Explorer scenario's source
  was never committed. One lesson from writing it survives only here: on
  the guest, poll for a precondition (a folder existing, say) by launching a
  checker whose captured output is read back through the agent, never by
  reading a fast process's exit code. The checker exits in milliseconds,
  its process object is gone before the agent's status poll opens it, and
  the agent then reports an exit with no code, indistinguishable from
  failure.
- One end-to-end flake remains unexplained: speech frames verifiably queued
  and written into the control pipe never crossed the agent's tunnel relay,
  and teardown's pipe disconnect discarded the unread data into a clean end
  of stream. It did not recur in eight clean runs. Logging was added to
  attribute any recurrence to a layer (the subscribe log line, each
  connection writer's frame total at close, the tunnel's per-direction byte
  totals). Do not chase it speculatively; audit item 11 is a candidate
  cause and should be fixed first.
- One unchased one-off: an MSAA value-change announcement (a rate slider
  reading "79") was missed once in eight suite runs under load.
- The announce poll's retry budget (ten attempts across about five seconds)
  was set without consulting Dickson; any further policy change there
  should be raised with him. Step 5 deletes the poll, which makes this moot.
- The UIA element cache clears wholesale at 2,048 entries, a stopgap
  awaiting a real eviction policy (audit item 19).
