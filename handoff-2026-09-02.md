## Purpose of the next several sessions

Dickson is returning to the project after six weeks and does not understand
most of the code, which was written in a rush over six days in July 2026.
The next sessions have two linked goals: make the existing runtime
trustworthy, and make its behavior understandable to Dickson. Pair reading
with small repairs, but establish the intended behavior before choosing
an implementation.

The work is a bounded correctness review of Core-outpost communication,
process recovery, and speech delivery, supported by repairs to the test
harness. Preserve the main architectural boundaries: the pure reducer,
per-application outposts, the dedicated focus listener, and separate
synthesis and audio rendering. Simplify ownership and control flow within
and between those boundaries.

The audit findings remain useful evidence; their proposed implementations
are starting hypotheses, not commitments. Correctness and understandability
come first. Introduce types where they clarify established rules and make
them harder to violate; typestate conversion is not a separate objective.

- Root cause: the outpost abandoned a focus read after 1.5 seconds (an

  returned. Notepad starting up took about 3 seconds to answer, and the

## Decisions made on 2026-09-02

These are decisions of record for the work ahead. Decisions 2, 3, 5, 7,
and 8 are already reflected in `docs/architecture.md` (D3, D4, D14 to
D16, and section 14); the rest are process decisions that belong here.

1. No restart. The repository is kept and the problem areas are fixed in
   place. The reasoning is in `audit-2026-09-02.md` under "What this means
   for the restart question".

2. Development model, revised 2026-10-01. Dickson no longer uses the
   Hyper-V setup. He develops in a single Windows VM on Proxmox, which runs
   Claude and cargo, and the end-to-end suite runs locally on that same VM
   (the runner-direct mode in `docs/tooling.md`: a local agent and
   `cargo test -p verbatim-e2e`). The earlier plan of a second VM for
   Verbatim and NVDA, with builds deployed into it, is dropped, and so is
   the Proxmox backend for `cargo xtask vm`. The Hyper-V harness stays in
   the repository as the documented option for contributors and is still
   maintained, but it cannot be run live from Dickson's VM. A local run
   takes over the VM's desktop and speaks through its audio, so it is
   started only with Dickson's agreement, and NVDA must not be reacting to
   the injected keys while it runs. Video captures that demonstrate
   Verbatim must keep working; today only the Hyper-V path records, so
   recording on the local VM is a follow-up, not phase 2 work.
   D3 and section 14 of `docs/architecture.md` were amended to match.

3. Guest transport. Standard tools, not bespoke protocol additions. OpenSSH
   Server on the guest, installed and key-provisioned by the existing
   harness script, carries file copies (scp) and remote commands (ssh) on
   both Hyper-V and Proxmox. The in-guest agent keeps only what SSH cannot
   do: launch processes in the interactive session, report session facts,
   and tunnel the control-plane named pipe. Hypervisor backends handle
   lifecycle and snapshots only. A proposal to add a chunked put-file
   request to the agent protocol was withdrawn.

4. NVDA as reference, not as a test oracle in CI. A small packaged NVDA
   add-on hooks the pre-speech-queued extension point, records one entry
   per speech sequence with a timestamp, flattened to text the way NVDA's
   own test spy does, and serves them over TCP using the framing the agent
   already speaks. Keystrokes come from real OS input through the agent, so
   NVDA is driven the same way Verbatim is. The transcript is a research
   instrument used interactively: Claude drives NVDA on the development VM,
   captures what it says for a scenario, and uses that to decide what
   Verbatim should do and to write Verbatim's own end-to-end assertions by
   hand. Where Verbatim legitimately behaves differently, that is decided
   case by case when the test is written and recorded in `docs/parity.md`.
   Verbatim's tests never compare against an NVDA transcript directly, and
   NVDA is never installed or run in continuous integration. No fork of
   NVDA, and NVDA's Robot Framework spy is not reused directly. Normally
   NVDA and Verbatim run separately. The exception is NVDA reading
   Verbatim's own GUI, which Dickson wants as the source of expected
   readings for the menu and settings dialog and as the before-and-after
   check for the GUI port: for that, Verbatim runs with the test-audio
   setting so it is silent, the two readers get different modifier keys
   (Verbatim's share-modifier setting exists for a second reader hooked
   behind it), and keys are injected through the agent's real OS input so
   NVDA sees them as keyboard presses.

5. GUI. wxDragon is removed entirely. The wxWidgets part becomes a minimal
   C++ layer compiled from the GUI crate's build script through cxx, linking
   static wxWidgets per architecture. Rust keeps `main` and all logic, so
   `cargo xtask ci`, the ARM64 cross-build, deploy, and the end-to-end suite
   stay cargo-driven. `d:\source\loadstone` is the pattern reference for the
   cxx bridge, the typed page models, the callbacks class, and the
   wxAccessible subclass, but not for the build shape, since loadstone has
   C++ owning `main`, no ARM64 build, and no CI. The static wxWidgets build
   recipe for both architectures already exists in wxdragon-sys's build
   script in the cargo registry and should be adapted, not rewritten. The
   alternative of keeping wxDragon with a C++ shim was raised and rejected;
   do not raise it again.

6. Order of work, revised 2026-09-05 and again 2026-10-01: learn the
   vocabulary and map ownership; repair harness integrity; redesign the
   outposts and Core's coordination with them (`outpost-redesign.md`);
   review speech delivery; verify the boundaries and consolidate
   understanding; then resume the NVDA transcript tool, GUI port, and M4
   work. The phases below define completion criteria rather
   than calendar estimates. NVDA transcripts inform later behavior work;
   communication and recovery correctness do not wait for that tool.

7. Checkpoint restores are deliberate, never automatic. In July the test
   verb restored the golden checkpoint on every run unless `--no-restore`
   was passed, and that was a major source of slowness in the interactive
   loop. Nothing is installed into the guest (deploy copies files and
   hash-skips unchanged ones), so a restore buys nothing on an ordinary run.
   The default flips: `cargo xtask vm test` does not restore; a restore
   happens only through the `restore` verb or an explicit opt-in flag on
   `test`, and the same rule applies to any future backend's snapshot
   rollback. The cold-start loop under "Carried forward from July" is the
   one place a fresh restore per run is the point, and it asks for it
   explicitly. Implemented 2026-10-01 (1fb53c0): the opt-in flag is
   `--restore`, and `--no-restore` no longer exists.

8. Architecture decisions D14 (attention model), D15 (split latency
   budget), and D16 (recording audio from Verbatim's own rendering) were
   ratified on 2026-09-02 and written into `docs/architecture.md`, along
   with rewritten D3 and D4 and a rewritten section 14. eSpeak NG moves
   from M8 to the opening work of M4. `architecture-review-2026-09-02.md`
   holds the reasoning behind each.

9. Performance target and how thresholds are set (2026-09-16). Verbatim
   aims to be within a factor of two of what the hardware and the OS
   allow on every user-visible operation. Wall time is what the user
   experiences and is the number asserted. A threshold is never chosen by
   hand or tuned until runs pass; it is derived. For each operation, a
   floor model states the minimum count of each primitive: a
   cross-process UIA call, an MSAA property read, a WM_GETOBJECT probe, a
   pipe hop, a channel hop, one audio engine period, and synth time to
   first sample. The cost of each primitive is measured in the same run
   against the scenario's own target application, so a loaded host moves
   both sides of the comparison together and a breach means Verbatim's
   own overhead grew. The assertion is that the median over repetitions
   stays under twice the modelled floor, with the worst case reported.
   Round-trip counts per trace are asserted exactly in mockapp
   integration tests, because a count cannot flake. D15's 10 ms figures
   stand as the expected outcome of this model with eSpeak NG and
   IAudioClient3, and are checked against the model rather than the
   other way round.

10. Outpost redesign (2026-10-01). Reading the reducer and outposts in
    phase 1 showed that their correctness rests on eight independent
    ordering and staleness mechanisms, and that repairing them one at a
    time would not make the system understandable. The outposts, focus
    listener, supervisor, the app's outpost handling, and the matching
    reducer changes are redesigned instead, following NVDA's intake model:
    outposts only listen and answer queries, the supervisor manages
    processes and routes messages, and the reducer decides what to speak
    and what to accept. Snapshot versions and the focus timestamp check
    are removed; node ids are stamped with their outpost incarnation; each
    outpost has one worker; and the D14 attention model is pulled forward
    from M4, with event acceptance classified by the reducer rather than
    the outposts (an amendment to D14). The full design, the review that
    tested it, and the seven implementation steps are in
    `outpost-redesign.md`. The harness repairs come first so that each
    step can be verified live as it is built.

## Reference points for the work ahead

Facts gathered on 2026-09-02 that the next session would otherwise have to

The NVDA transcript add-on, from reading `nvda/tests/system`:

- NVDA's own spy is a scratchpad global plugin plus a replacement synth
  driver (`tests/system/libraries/SystemTestSpy/speechSpyGlobalPlugin.py`
  and `speechSpySynthDriver.py`), served over XML-RPC on port 8270 for
  Robot Framework. It is not reused: it silences NVDA and carries a
  transport Verbatim does not want.
- The public hook to use instead is `speech.extensions.pre_speechQueued`
  in `nvda/source/speech/extensions.py`, which fires with the fully
  processed sequence and leaves the real voice speaking. NVDA's own Remote
  Access feature uses the same hook, which is the proof it is stable API.
- Flatten a sequence the way the spy does (`_getJoinedBaseStringsFromCommands`):
  keep only string items, join, strip. That makes the transcript lexically
  comparable to Verbatim's speech frames from day one.
- Settling: the spy waits for the speech index to advance and then one
  second of quiet (`SPEECH_HAS_FINISHED_SECONDS`), polling no faster than

The hot path, from reading the outpost, UIA, speech, and audio code on
2026-09-16 (decision 9 is the target these facts are measured against):

- The floor for a UIA focus change on a responsive application is two
  cross-process round trips: one `focused_element` call carrying the base
  cache request, and one remote operation returning the ancestor chain
  and the selected child. Event to first audio sample is roughly 6 ms
  with eSpeak NG at the device's minimum engine period, so the target is
  about 12 ms. The July warm menu-lag figure of 110 to 190 ms and M3's
  100 ms menu-open figure are the baseline the ratio starts from.
- Today's UIA focus fact for a non-window element (a list item, a menu
  item) costs roughly 15 to 25 round trips cold, in `runtime.rs` under
  `crates/verbatim-outpost/src`. The causes, largest first: the per-hop
  ancestor walk in `Uia::ancestor_chain`, one round trip per parent up to
  64; `resolve_uia_element`'s runtime-id search, which enumerates the
  target's top-level windows and runs a subtree `FindFirst` in each
  instead of one `focused_element` call compared against the fact's
  runtime id; the element being resolved twice, once in
  `uia_fact_window` and again in `focus_enrichment_query`; the
  arbitration verdict cached for only 500 ms (`CACHE_TTL` in
  `arbitration.rs`), so Win32 controls, each its own window, re-probe
  with a `WM_GETOBJECT` send on nearly every focus change; and two or
  three calls for the selected child.
- MSAA ancestor snapshots in `verbatim-ia2`'s `acquire.rs` read six
  properties per hop where the presentability filter needs role and name.
- OneCore (`crates/verbatim-synth-onecore`) enumerates every installed
  voice and calls `SetVoice` on every utterance, waits on synthesis and
  stream loading with 1 ms sleeps that are subject to timer granularity,
  and never cancels the WinRT operation when an interrupt arrives, so a
  new utterance waits for the old synthesis to finish. The WASAPI sink
  waits one engine period on the render event before the first write of
  every utterance although `begin` has just reset the buffer.
- Verbatim's own process hops are not the cost: listener to Core to app
  outpost to Core is under a millisecond in total, as D15 states. The
  JSON-line framing is not a cost at today's message sizes either; it
  will be for browse-mode buffers in M6, and `write_message` and
  `read_message` are already the seam for a bulk path then.

## Additional findings from the second review, 2026-09-05

These are the five additional findings discussed with Dickson and included
in the revised plan. They come from targeted code inspection; their
triggering scenarios have not been reproduced live. Numbers in this section
are independent of the original audit's item numbers. Findings 1, 2, and 5
are resolved by the outpost redesign (`outpost-redesign.md`); finding 3
belongs to phase 4 and finding 4 to phase 2.

1. Outpost incarnation is missing from the reducer's source identity. A
   restarted outpost resets its snapshot counter, while the reducer retains
   the previous counter for the application PID. New events can consequently
   be rejected as stale until the counter catches up. Ordinary events and
   replies also lack the generation checks used for heartbeat and lifecycle
   handling. See `verbatim-core/src/state.rs`, `verbatim-app/src/main.rs`,
   and `verbatim-outpost/src/supervisor.rs` under `crates/`.
   Acceptance: a replacement's first event is accepted, obsolete incarnation
   messages are rejected, and replacement retires the previous incarnation's
   version history, focus and navigator state, and pending requests.

2. Query deadlines expire the wait, not the work. Queued jobs can expire
   before starting and still execute later; the pool counts these as
   abandoned workers. Running fire-and-forget jobs retain permission to
   publish after expiry. See `crates/verbatim-outpost/src/query_pool.rs`
   and the worker-published events and replies in `runtime.rs`.
   Acceptance: distinguish queued from running work, prevent expired queued
   jobs from starting, suppress accepted results from expired running jobs,
   and produce exactly one terminal outcome for each accepted request.
   An activation already issued to another application cannot be undone;
   distinguish that uncertainty from expiry before execution.

3. Speech completion is not reliable evidence of completed playback. The
   manager reports completion after an audio-drain error, the WASAPI drain
   path can return success after a wait failure, and paced tests accept a
   completion belonging to any utterance. See
   `crates/verbatim-speech/src/manager.rs`,
   `crates/verbatim-audio-wasapi/src/lib.rs`, and
   `crates/verbatim-e2e/src/speech.rs`.
   Acceptance: completion, cancellation, and failure are distinct outcomes
   carrying the utterance's identity. Failure or cancellation never reports
   successful completion; pacing waits for the matched utterance's outcome.
   Status 2026-10-01: the harness half is done (d47a94d). Pacing waits for
   the matched utterance's own completion and records "played" or
   "playback not confirmed"; the producer half, distinct cancellation and
   failure outcomes, remains for phase 4.

4. Protocol framing loses partial messages on read timeout. The JSON-line
   reader discards its temporary buffer when a read times out after
   consuming part of a frame. Retrying then starts in the middle of that
   frame. See `crates/verbatim-control/src/protocol.rs` and `client.rs`,
   and the timeout setup in `crates/verbatim-e2e/src/agent_client.rs`.
   Acceptance: an incomplete frame survives timeouts and is decoded exactly
   once, followed correctly by the next frame. Preserve decoder state, or
   decode continuously and apply assertion deadlines to complete messages.
   Status 2026-10-01: done (5561746), by preserving decoder state in a
   `MessageReader` the timeout-bearing clients read through.

5. Tree-dump replies are not correlated with pending requests. A delayed
   reply to a timed-out request can satisfy a newer request, potentially
   for another application. See `incoming_input` and `request_dump_tree`
   in `crates/verbatim-app/src/main.rs`.
   Acceptance: match delivery and cleanup to request identity and outpost
   incarnation. An old reply or timeout cleanup may never satisfy or clear
   a newer request.

The attention model and the removal of the PID gate are part of phase 3

every threshold by the derived model of decision 9, never by hand.
Concretely: write the operation ledger in `docs/` stating the minimum

The ledger has a Core row too, with a different primitive: bytes
allocated and copied per reduce step. The invariant is that a step's
allocation and copying are proportional to the input and the effects,
never to the size of the state. Today `reduce` clones the whole state per
input, which costs a few microseconds because the state is small; once
the text model (M4) and the virtual buffer (M6) live in the state, that
shape would copy a document per caret move. Decide the representation
when the text model is designed, before either structure lands: large
parts shared behind `Arc` with the state passed by value so mutation
happens in place, a rope for text, a persistent map for the node map, or
in-place mutation, which keeps determinism since replay needs only no I/O
and no clocks. Enforce the invariant with a counting allocator behind the
`verbatim-core` unit tests, asserting that a focus event, a caret move,
and a terminal line allocate the same byte count against a ten-node
state and a hundred-thousand-node state; a byte count never flakes, so it
runs in `cargo xtask ci`. Two shell-side items on the reducer thread go

## Carried forward from July

Facts from the deleted July notes that the code and docs do not record.

- The cold-start loop is the reproducer for announce races: repeated runs of
  `cargo xtask vm test --restore --scenario start_menu` and the same for
  `m1_exit_regression`, each on a fresh golden restore, until eight
  consecutive runs are clean. With the suite now run locally rather than
  in a Hyper-V VM (decision 2), how to get an equivalent cold start
  without a golden restore is decided in phase 5. A menu-lag measurement worth keeping: on the
  July VM, Verbatim+V to hearing "Context menu" was about 110 to 190 ms
  warm. It is the pre-model baseline for decision 9's ratio, roughly ten
  times the modelled floor.
- A rapid-focus-churn stress scenario was written in July and never
  committed; it is not in the tree. Recreate it during phase 3 and verify
  it with the integrated runtime there and again in phase 5.
- The three deferred scenarios (Explorer folder window, Settings-app
  toggle, Start-menu search results) have by-hand recipes in
  `docs/roadmap-done.md` and no automation. The Explorer scenario's source
  was never committed. One lesson from writing it survives only here: on
  the guest, poll for a precondition (a folder existing, say) by launching a
  checker whose captured output is read back through the agent, never by
  reading a fast process's exit code. The checker exits in milliseconds,
  its process object is gone before the agent's status poll opens it, and
  the agent then reports an exit with no code, indistinguishable from
  failure.
- One end-to-end flake remains unexplained: speech frames verifiably queued
  and written into the control pipe never crossed the agent's tunnel relay,
  and teardown's pipe disconnect discarded the unread data into a clean end
  of stream. It did not recur in eight clean runs. Logging was added to
  attribute any recurrence to a layer (the subscribe log line, each
  connection writer's frame total at close, the tunnel's per-direction byte
  totals). Do not chase it speculatively; audit item 11 is a candidate
  cause and should be fixed first. Item 11 was fixed on 2026-10-01
  (fba0fef), and the tunnel's close line now also says why each direction
  ended, telling a closed pipe from a stop and from an error; if the flake
  recurs, read that line first.
- One unchased one-off: an MSAA value-change announcement (a rate slider
  reading "79") was missed once in eight suite runs under load.
- The announce poll's retry budget (ten attempts across about five seconds)
  was set without consulting Dickson; any further policy change there
  should be raised with him. Phase 3 removes the poll entirely; startup and
  recovery use a single focus-now query instead.
- The UIA element cache clears wholesale at 2,048 entries, a stopgap
  awaiting a real eviction policy (audit item 19). Phase 3 replaces it with
  held nodes: the outpost keeps exactly the elements Core still refers to.
