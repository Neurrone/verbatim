# Decision records

Each record here keeps the decisions behind one part of Verbatim: the problem, the options weighed and why each was taken or rejected, each decision with its date and who took it, and the limits accepted. How that part works today is explained in [the design pages](../../explanation/design/readme.md), and its mechanism is in [the crate guides](../crates/readme.md).

Records are numbered in the order they are recorded; a later record can rest on an earlier one, never the reverse. A decision taken while Dickson was away is marked "pending Dickson's acceptance" until he accepts it. [The architecture](../../explanation/architecture.md) remains the index of every decision of record and links to the record that holds each one.

- [ADR 0001: Focus](0001-focus.md) — which process reads each focus, how a focus keeps its order, how Verbatim waits for a slow or hung application, how an earlier ancestry is reused safely, and what Verbatim+Tab reports.
- [ADR 0002: No screen reader per outpost](0002-no-screen-reader-per-outpost.md) — why keys, focus and what depends on them are judged in Core and not in each application's outpost, and what an outpost keeps for Core between requests.
- [ADR 0003: Readers tell, Core asks](0003-readers-tell-core-asks.md) — why the listener and the outposts tell Core of each event and read only when Core asks, how Core orders events, keys and commands in one queue, and how only Core stops waiting for a frozen window.
- [ADR 0004: One definition of focus validity, decided in Core](0004-focus-validity.md) — why every focus candidate, MSAA and UI Automation, is judged by one definition in Core at its turn and while something waits behind it, why the readers only report facts, how a caret key confirms a stale MSAA focus, and the identity check that says an item's split focus once.
- [ADR 0005: Calls that reach another application](0005-calls-that-reach-another-application.md) — why a busy application's neighbours are not held by it: nothing read above the process boundary, the listener's hooks before its registration, no search for a gone node, every call whose target the system picks checked for its process, and the collisions left as stated limits.
- [ADR 0006: One owner for every fact](0006-one-owner-per-fact.md) — why every fact has one owner, one thread or one state machine run by one thread: pure reducers with calls as effects, one answer per request, messages of declared kinds, nodes released by message position, no back-channel, no state lent across a call, one minter for input, and who may block on whom.
