# Ownership: one owner for every fact

Every fact in Verbatim has one owner: one thread, or one state machine run by one thread. Every other component learns the fact from one-way reports or from a view the owner gives it, and none judges a copy of it. This page explains who owns what and how each rule is held; why, the options weighed and the limits are in [ADR 0006](../../reference/adr/0006-one-owner-per-fact.md), and the mechanisms are in the crate guides each section links. The rules each planned milestone follows are in [the milestone rules](https://github.com/Neurrone/verbatim/blob/main/docs/design/ownership-milestone-rules.md).

## Who owns what

- Core owns every word, every rule and every fact across applications: the focus, attention, the foreground, the order of events, keys and commands, text and terminals ([ADR 0003](../../reference/adr/0003-readers-tell-core-asks.md); [verbatim-core](../../reference/crates/verbatim-core.md)).
- The listener owns the desktop-wide registrations and hooks. It tells Core of each event and reads only when Core asks, judging nothing but NVDA's local drops ([the architecture](../architecture.md), "Where the rules run (D14)"; [verbatim-listener](../../reference/crates/verbatim-listener.md)).
- An outpost owns its application's objects: the node registries, text objects, anchors and the caret tells' elements, in its object store, and the calls into its application, which it makes for Core's requests on one worker ([verbatim-outpost](../../reference/crates/verbatim-outpost.md), "Inside an outpost").
- The supervisor owns each outpost generation's life ([verbatim-supervisor](../../reference/crates/verbatim-supervisor.md)); Core's record of it is Core's ([verbatim-core](../../reference/crates/verbatim-core.md), "The outpost generation record").
- The keyboard hook's thread owns the key number ([verbatim-input-windows](../../reference/crates/verbatim-input-windows.md)).
- The saver thread owns `settings.toml`, the synthesizer's thread its settings' values, and the audio thread the mixer ([verbatim-app](../../reference/crates/verbatim-app.md), [verbatim-speech](../../reference/crates/verbatim-speech.md), [verbatim-audio](../../reference/crates/verbatim-audio.md)).

## The rules

- **One owner per fact.** A fact has one writer; its fields are private to the owner's module, with one mutating function, so Rust's privacy holds the rule. A monitor, one module whose every operation runs under its own private lock, never held across a call, never exposing its guard and never running a caller's code, counts as one owner: the outpost's object store is one.
- **Pure reducers, with calls as effects.** Core's reducer, the outpost's (`verbatim-outpost-logic`) and the listener's logic (`verbatim-listener-logic`) take inputs and return effects, with no clock, no call and no blocking; a thread around each, its shell, runs the effects and keeps the time. Their orderings are tested by replaying inputs. The ownership check in `cargo xtask ci` (`xtask/src/ownership.rs`) reads the outpost's reducer and the listener's schedule against an allow-list of what each may name, and its determinism rule holds every crate on a reducer's path, Core's included.
- **Every request has exactly one answer.** Core's request table gives each request to a reader one ending: its answer, or why Core stopped waiting ([verbatim-core](../../reference/crates/verbatim-core.md), "Core's requests"). Within a process a `Responder` answers on drop and lives only in a thread's shell.
- **Messages are of declared kinds.** The wire types in `verbatim_model::protocol` are split by role and direction, so a message a receiver may not take cannot be decoded, and every dispatch is an exhaustive match ([verbatim-model](../../reference/crates/verbatim-model.md)). No message carries Core's state for a reader to judge against.
- **Nodes are released by message position.** A message naming nodes is built from a `Recorded` only the object store makes, which records the position of the message that carried each node; the store frees a node only between programs, when Core's `NodesHeld` acknowledges a later position and does not name it.
- **A fact carries the version of the state it depends on.** Every node id carries its outpost generation, so an id from a replaced outpost names nothing of its successor; a program carries its worker generation, so an abandoned worker's late result is discarded.
- **No state lent across a call into an application.** An outpost's workers run whole call programs on copies and never see the reducer's state; the store's API returns owned clones, never a guard or a closure, so no lock is held across a call.
- **One route and one minter for input.** Every user input enters Core by one route and carries the key number the hook's thread gave it, in the order the hook handles keys; a test's gestures are pressed as keys. Core puts the number of the key that caused it on every `Speak`, and only the reducer's thread holds the `SpeakToken` that speaks ([verbatim-core](../../reference/crates/verbatim-core.md), "Key numbers").
- **Lifecycles as typestates.** A lifecycle is an enum whose transitions consume the old state, such as the supervisor's generation, whose lifecycle messages carry a `Sealed` only the supervisor makes.
- **Who may block on whom.** Core never blocks on a reader, nor a reader on Core. The ownership check's hook rule keeps the hook's modules from taking a lock, waiting, logging, doing I/O or taking work from another thread; its audio rule keeps the audio thread's pass from locking, waiting, allocating or logging, with an allocation-counting test beside it.

## Output: one saver, one audio owner

One saver thread owns `settings.toml`, with one writer per section that posts and never waits; the saver writes the newest of each section per batch. The synthesizer's thread alone writes its settings' values, reads each back from the driver after a change, and saves what the driver has. The audio thread owns the mixer with no lock: each producer has a bounded single-producer lane, cancel is a generation and pause a flag, and records leaving the audio thread go through a ring to a delivery thread that runs listeners, logs and frees. Wakes are plain events.

## The outpost's store and reducer

The outpost's reducer holds every remembered fact its rules read, with no Windows type; producers only append to its mailbox, and its shell waits on the mailbox's alarm, a high-resolution timer set to the earliest timer, so no other thread keeps the outpost's time. The text facts no rule reads are the object store's. The reducer applies a program's results only while its request is live ([verbatim-outpost-logic](../../reference/crates/verbatim-outpost-logic.md)).
