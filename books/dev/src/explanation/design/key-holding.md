# Holding caret keys as NVDA does

Status: adopted and built (Dickson, 2026-10-22), the one mechanism for caret keys in text fields and terminals. This document keeps the problem, the choices and their reasons, the costs and the limitations. The mechanism is described in the crate guides: the hook in `books/dev/src/reference/crates/verbatim-input-windows.md` ("Holding caret keys"), the caret table in `books/dev/src/reference/crates/verbatim-input.md`, Core's stroke line and caret key entry in `books/dev/src/reference/crates/verbatim-core.md`, the shell's sending of strokes in `books/dev/src/reference/crates/verbatim-app.md`, and the starting read and the watch in `books/dev/src/reference/crates/verbatim-outpost.md`. NVDA's behaviour for each key, with its source, is in `docs/parity/text.md`, and Core's mechanism in `books/dev/src/reference/crates/verbatim-core.md`, "The caret key on the event queue".

Terms used here:

- A held key is a caret-table key that the keyboard hook swallows and Verbatim sends to the application again once it has read the caret, as NVDA's caret scripts do.
- The starting read is that read of the caret, made by the focus's outpost (the per-application process that reads it through UIA or MSAA) at the key's turn in Core's event queue, before the key is passed on. Its answer mints the starting point, a position the outpost holds behind an id Core names.
- The watch is Core's request that the outpost check the caret against the starting point until the key's effect shows or its bound passes, then make one final read and answer once.
- A key's effect is misjudged when its answer is read from a caret that does not follow from the key: read before the application handled the key, or compared with a caret older than the one the key started from.

## The problem

Without holding, a caret key reaches the application at once, and Verbatim judges its effect from a caret it reads afterwards. When the application has not yet handled the key, or has not yet reported the key before it, the answer is read from the wrong caret: select then copy followed at once by Right Arrow was misjudged in every round in the Windows Forms text box and Notepad (30 of 30 each), and Shift+Right followed at once by Right in 56 of 60 rounds ("How often a key's effect was misjudged"). These cases share one cause, which per-case fixes had treated one at a time. NVDA avoids it by holding the key: its caret script reads the caret, sends the key, and waits for the caret to move from that read.

## Decisions

- Holding is Verbatim's one mechanism for caret keys, replacing the per-case fixes of the caret problems that share one cause, at the cost measured below: up to about 3 ms more from key to first sound at the median, and 8 to 13 wake-ups and 0.7 to 1.5 ms of processor time per held key in a debug build (Dickson, 2026-10-22).
- Keys that are not held never overtake a held key (Dickson, 2026-10-22): see "Keys behind a held key". This goes one step beyond NVDA, which has the same race: there a typed character pressed while a held Backspace's caret is read reaches the application first, so "ab", Backspace, "c" typed fast leaves "ab", the "c" deleted instead of the "b".
- Nothing is held while an elevated window is in front, a temporary guard until Verbatim has uiAccess (Dickson, 2026-10-22): see "Elevated windows".
- The foreground changing between a key's press and its pass-on is an accepted limitation, too small a window to matter in practice (Dickson, 2026-10-22).
- A held key is released to the application 150 ms after its press whatever waits ahead of it in Core's event queue, and a key so released says nothing (Dickson, 2026-11-13; [ADR 0003](../../reference/adr/0003-readers-tell-core-asks.md), "Keys and commands"), so a stuck or slow read never holds the user's typing.
- A caret key takes its starting read at its own turn, with no wait for the effect of the key ahead, as NVDA's next script reads the caret as soon as the one ahead returns (Dickson, 2026-11-16).
- The lock keys are never held back behind a held key (Dickson, 2026-10-26): see "Keys behind a held key".
- Enter and the numpad's Enter are held in a text field other than a terminal, as NVDA's new-line script holds them, reading the caret before sending the key; in a terminal, where NVDA binds no new-line script, they pass as typed text (Dickson, 2026-11-19): see "The hook" and "Core".
- In the console host the watch checks the caret every 5 ms, where NVDA checks every 10 ms, because the console host raises its caret events only on its blink timer (Dickson, 2026-10-26): see "The console host's caret poll".
- In a UI Automation text field other than a terminal, a caret or text-change event of the watched node within 60 ms of the key's pass counts as the key's effect, as NVDA's caret scripts take it (Dickson, 2026-11-16).

## The design

### The hook

The keys held are Verbatim's caret table (`verbatim_input::caret_bindings`): the arrows and their Control forms, Home, End, Page Up and Down, Control+Home and Control+End, Backspace and Delete alone and with Control or Shift, Alt with Up and Down Arrow, and Enter and the numpad's Enter, which are held only while the focus is a text field other than a terminal and no input method or keyboard text service composes in the window in front, and otherwise pass as the carriage return they type (Dickson, 2026-11-19), since NVDA's focus during a composition is the composition, which has no new-line script. The selection keys, the Shift forms of the moves and Control+A (`verbatim_input::selection_bindings`), are observed and pass at once, deferred only behind a held key as every key is: NVDA binds them only in controls that do not report their own selection changes, none of which Verbatim reads (`docs/parity/text.md`, "Selecting with Shift"). Typed characters, the clearing keys, cut and paste and every other key are not held, as NVDA binds no script to them.

The keyboard decision machine decides which keys are held, from a permit the hook gathers from Core's view of the window in front, which the reducer's thread publishes after every input and the hook reads with one lock-free load, so the hook never waits. Keys are held while the view says the focus has text, or a role that may have it, and the press names the focus record it was bound to. A key held for a focus that turns out to have no text is passed on at once by Core and says nothing. A held key's release is swallowed too, so the application never sees a release without its press; once a later press of the key has reached the application, its release is delivered, so no key is left down (`books/dev/src/reference/crates/verbatim-input.md`).

### Keys behind a held key

While any key held back has not yet reached the application, the machine defers every later key transition it would pass, typed characters, Enter, clearing keys, modifiers and releases included, so that nothing overtakes the held key; a later caret key is held in its own turn. A deferred key is never read: the hook reports each deferred transition to Core, which appends it to its stroke line behind the held stroke, and Core sends a held stroke with every deferred transition behind it up to the next unsent held stroke, in one `SendInput`, which Windows never interleaves with other input.

Verbatim's own commands never reach the application, so the hook reports them at once, and they join Core's event queue in line with the keys, as NVDA runs scripts in the order queued. A key or command joining the queue behind a caret key marks that key silent: a key not yet at its turn is sent with no read, and a key whose watch is out has it withdrawn and says nothing, as NVDA's caret script stops waiting and says nothing once another script is queued (`nvda/source/editableText.py` 94 to 95 and 166 to 167). The guard for elevated windows and the lock keys are the exceptions to the deferral. Caps Lock, Num Lock and Scroll Lock pass at once, because Verbatim announces a lock key's new state from Windows' own state 30 ms after the press, which a deferred key would not yet have changed, and Windows turns a numpad key into an arrow or a digit by Num Lock's state before the hook sees it, so numpad 4 pressed behind a deferred Num Lock would arrive as Left Arrow. The consequence is in "Limitations".

### Elevated windows

Verbatim runs without the uiAccess privilege, and Windows drops input it sends to a window of higher integrity without an error, so a key held for such a window would be lost. While the foreground window's process has higher integrity than Verbatim's, or its integrity cannot be read, the hook therefore holds and defers nothing. The focus listener reads each foreground window's integrity, and Core publishes whether keys may be held there in a lock-free view the hook applies only while the window it names is still in front (architecture section 5; `books/dev/src/reference/crates/verbatim-input-windows.md`, "Holding caret keys"). This is a temporary guard, removed when uiAccess is built (`docs/roadmap.md`, M8.7). The live case is not checked, since no elevated window can be opened without a UAC prompt.

### Core

A caret key joins Core's event queue and waits there, behind every event, key and command that arrived before it, as NVDA's caret scripts wait in its queue. At its turn:

- A key the hook did not hold, or one its 150 ms timer already released, says nothing and asks nothing.
- A key marked silent by a later key or command is sent with no read and says nothing.
- A key whose node has no text or is no longer held is sent at once and says nothing. A key whose node is no longer the committed focus, because a focus was executed between its press and its turn, still runs on the node it was bound to at its press, as NVDA's script bound at the press runs on the earlier object.
- Any other key asks its starting read of its node, naming the key's unit and where it is read: at the caret, or for Backspace and Control+Backspace around the character before the caret, the text they would delete, as NVDA's Backspace scripts read it. On the answer Core keeps what it found (the unit, the line, the selection, the text Backspace would delete), sends the stroke, and sends the watch: the starting point, the key's effect test, the poll interval, whether the node's UI Automation events may end the watch, the bound, and what the final read reads.

Core speaks by NVDA's caret scripts from the watch's answer. With the key's effect, a movement key and Delete say the unit at the caret, Backspace and Control+Backspace the text they deleted, a sentence key the line, and Enter the new line's text from its start up to the caret, nothing where that is blank, and where it is empty only the formatting at the caret's character, as NVDA's new-line script (`docs/parity/text.md`, "Enter in a text field"). At the bound, movement keys and Delete say the unit at the caret, and Backspace and Enter say nothing. After its words a key applies the character it typed to the word being typed, as NVDA's typed-character event runs after the script: Backspace's drops the word's last character, and Enter's carriage return, taken as reaching the field only when the watch saw the caret move, ends the word and speaks it; an Enter that moved nothing keeps the word for the focus change that follows to forget, as a dialog's manager takes Enter before the field receives a character (Dickson, 2026-11-19; `docs/parity/input.md`, "Typed-character echo"). A key dropped at a desktop switch applies nothing, since it never reached the application. A focus that counts as pending withdraws the watch and the key says nothing, except Backspace and Control+Backspace, which say the text they delete before the focus, as NVDA's `_backspaceScriptHelper` does. Whether a focus counts is judged by the one definition of a candidate's validity; an MSAA focus whose focused state no read has shown, raised before the key's 100 ms bound, withdraws the watch and is confirmed by a read of its facts alone, naming its own window, then judged again, as NVDA's wait pumps its events and queues only a focus that has the focused state; one not focused lets the watch run the rest of the bound. A confirmation the foreground, a hang or its due time stops ends the key saying nothing, Backspace included, as a stopped watch does. In a terminal the key says nothing for itself, and its final read goes to the terminal's reading rules (`books/dev/src/explanation/design/terminal-model.md`, "Keys").

A key is never lost while Verbatim runs: a starting read that fails or that Core stops waiting for sends the key at once, and the key's 150 ms release sends it whatever its turn. Selection keys are not held: their effect is said by the caret event the application raises, whose read Core compares with the selection it last spoke from (`docs/parity/text.md`, "A selection no key made").

No branch on the application but NVDA's. NVDA's one branch is whether a control's caret events are trusted (`caretMovementDetectionUsesEvents`, false for terminals): with it, NVDA takes a caret or text-change event within 60 ms of the key as its effect, without it, it polls the caret. Verbatim takes the same branch in UI Automation text fields, where such an event brings a check forward and counts only if the caret is no longer where it was when the key was pressed (Dickson, 2026-11-17), because Notepad raised a key's event about 7 ms late, inside the next key's watch; in a classic edit control and MSAA text, whose caret events reach the listener rather than the outpost, the watch polls the caret, as it does in terminals.

### The outpost

The starting read is one remote-operations round trip through UIA where the window's provider runs them, the classic UIA reads otherwise, and the edit control's messages for a classic edit control. In a focused terminal it is a full read of the terminal, so the reading rules compare the key's effect with the screen just before the key (`books/dev/src/explanation/design/terminal-model.md`, "Keys").

The watch is a request in the outpost's table of waiting requests. It checks the caret at once and then about every 10 ms, every 5 ms in the console host, comparing it with the starting point; on the first check that shows the key's effect, or at the bound, it makes one final read and answers once. The bound is NVDA's 100 ms from the pass, multiplied by 3 in Windows Terminal; NVDA's 1.5 for an older console host applies only where a user forces UI Automation onto it, a setting Verbatim does not have. Through UI Automation the check that shows the effect goes on to read the final read's fields in the same program, so a key found by a check costs one round trip. Its poll and bound share one high-resolution waitable timer, because at Windows' default 15.6 ms resolution a 5 or 10 ms poll would miss most reads.

Remote operations audit (CLAUDE.md): each check and the final read are one round trip through UIA each, and both programs stay under 10,000 executed instructions.

### The console host's caret poll

The console host raises its caret events only on its cursor's 530 ms blink timer, one tick covering every move since the last, and nothing earlier follows a caret move: no text change, console update, property change or focus change (`experiments/the-console-host-raises-its-caret-events-on-its-blink-timer/`, 120 Left and Right Arrow presses each in cmd and Windows PowerShell). The caret's signals came 257 to 278 ms after the key at the median and at most 540, while the cursor itself had moved at the median within 1 ms and at most 54 ms after the key. NVDA does not use caret events in consoles (`_get_caretMovementDetectionUsesEvents` returns false, `nvda/source/NVDAObjects/behaviors.py` 527 to 530) and polls the caret every 10 ms until its timeout (`nvda/source/editableText.py` 70 and 150 to 160); Verbatim polls every 5 ms there, a Verbatim-only interval (Dickson, 2026-10-26). A key whose caret moves later than the bound is still spoken: the next read of the terminal finds the move, and the reading rules say what moved.

Costs, per caret key the first check finds unmoved: one more check every 5 ms to the bound, each a program on the outpost's worker; a key that moves nothing, such as Left Arrow at the start of the line, pays all 20.

### The shell

The shell keeps no line of held keys: it sends the strokes Core names, with `SendInput`, pressing before a stroke the gesture's Shift, Control or Alt that Windows does not have down and releasing them after, as NVDA's `KeyboardInputGesture.send` does. Since every transition after a held key is deferred behind it, the modifiers are as they were when it was pressed. Verbatim is not idle while any stroke waits in Core's line, since that key has not reached its application.

At exit, once the hook is gone, the strokes still in line are dropped, since they would reach the application after keys pressed since, but none is left down: Core names each key whose last transition in line is a release, a held stroke counting as one, and the shell releases those Windows has down because a press of them reached the application first. Without this, Shift pressed before a held Down Arrow and released behind it would stay down in Windows after Verbatim exits, since the hook swallowed its release; and so would a key whose first press passed and whose auto-repeat was held, since the hook swallows a held press's release.

## Costs

Measured on debug builds with the read before each key that the starting read is, before the watch replaced the outpost's earlier evidence reads.

- Latency added per held key, from the hook's press to the re-sent key's injection (minimum, P50, P95, P99, maximum, in ms): text box 0.9, 1.4, 4.9, 12.4, 44.3 (1,305 keys); Notepad 1.5, 2.0, 9.0, 12.7, 44.8 (1,305); console host 1.2, 1.6, 3.9, 5.7, 12.7 (396); Windows Terminal 1.3, 1.9, 3.6, 32.7, 62.8 (396).
- Enter, held (2026-11-19, debug, the three held Enters of `notepad_caret_keys` and `text_box_caret_keys`, from the flight recorder): press to the starting read's answer, after which the key is passed, 1.4 to 2.2 ms; press to the application's first event 2.7 to 3.5 ms, once 13.5 ms. Three presses only; a larger count needs a measure scenario that presses Enter.
- Key to first sound, three runs of each build: the P50 cost of holding is -0.2 to 1.3 ms in the text box, 1.9 to 3.0 ms in Notepad (UIA's round trip), 0.1 to 0.9 ms in the console host and 0.6 to 1.5 ms in Windows Terminal. The P95 and above are set by the audio's period and move by about as much between runs of one build as between the builds.
- Calls: one round trip through UIA per held key, or the edit control's window messages for a classic edit control (1 UIA call remotely, 8 classically, 5 window messages, pinned by `starting_reads_cost_exactly`), on top of the watch's checks.
- Wake-ups and processor time (`cargo xtask trace scenario`, debug build, info logging): in the console host's window holding added 6 percent of wake-ups and 3 percent of processor time, in Windows Terminal's 7 and 4 percent. The reducer thread took 36 and 44 percent more wake-ups, the outpost's worker 24 and 15 percent more, and the hook thread 20 and 10 percent more, from the injected press and release: roughly 8 to 13 wake-ups and 0.7 to 1.5 ms of processor time per held key. The text field traces are not compared, since their fixed windows caught different stretches of the workload in the two builds.

## A key held with auto-repeat

A key held with auto-repeat is held press by press. Each repeat is sent at its turn, after its starting read, or by its own 150 ms release, whichever is first, and a repeat with another behind it is marked silent, so only the last repeat can speak. `measure_held_repeat_text_box` measures how long after the release the last repeat reaches the application: three times, Control+End in the Windows Forms text box, then Right Arrow, which moves nothing there, held about a second as Windows' default auto-repeat sends it.

## How often a key's effect was misjudged

Measured with three runs of ten rounds of each case, the build before holding against the build with it.

- Select then copy followed at once by Right: the review copy's first press (Verbatim+F10) selects "line", and Right follows at once. NVDA (captured on 2026-10-22, alpha-58022, the pinned build) says the character after the selection, then the selection's end: "a", "N unselected". Without holding, 30 of 30 misjudged in the text box (the answer read before the edit control handled Right, saying "l") and 30 of 30 in Notepad (saying "space" with the selection still there); "line unselected" was never said. With holding, 0 of 60, each saying "space", then "line unselected", as NVDA does. `text_box_review_cursor` and `notepad_review_cursor` end with this step.
- A selection reported after the next key: Shift+Right and Right pressed in one batch from the start of "line 01". Selection keys are not held; Shift+Right says its selection through its caret event's read and Right says its character. Tests pace keys at least 30 ms apart, since keys sent in one batch are faster than any person types.
- Bursts of ten Down Arrows 30 ms apart: 0 misjudged in either build, since each answer came within the 30 ms before the next key, so these bursts never made a key wait behind another's read.
- A say-all caret move the application refuses: the console host is the one application found that refuses it (its cursor stays put when UI Automation selects a position). Right Arrow after say-all has moved Core's caret onto a wrapped command's second row was misjudged in neither build (0 of 30 each); with holding it cannot arise, since each key's starting read gives the caret it is judged from. No scenario step covers it, since say-all in the console host reads the command's second row repeatedly (a separate fault, not traced), so its speech has no stable expectation.

## Limitations

- A caret key released by its 150 ms timer says nothing. In an application whose caret reads take longer than 150 ms, the last line of a burst may not be spoken: with reads of about 180 ms and Down Arrow pressed three times 60 ms apart, none is spoken, where NVDA speaks the last line (derived, no capture; [ADR 0003](../../reference/adr/0003-readers-tell-core-asks.md), "Limits accepted").
- A stalled Core thread delays caret keys, and every key deferred behind one, by up to their 150 ms release. If Verbatim exits while keys are held, those keys and the transitions deferred behind them are lost, though no key is left down ("The shell").
- The foreground changing between a key's press and its pass-on sends the key, and the keys deferred behind it, to the new foreground window, as NVDA's would; accepted (Dickson, 2026-10-22). If the new window is elevated, Windows drops them.
- A key auto-repeating is held press by press, so the application receives separate presses rather than repeats.
- Verbatim's own commands pressed behind a caret key mark it silent and run at their turn, at once, so a reading command may read the line before the key's move, as NVDA's capture does.
- In a classic edit control and MSAA text the watch polls where NVDA takes the caret event, so a key whose caret event comes with no move says the unit at the caret at the bound, where NVDA would say it at once.
- The lock keys pass at once while keys are held back, so a letter typed before Caps Lock and deferred behind a held key reaches the application after Caps Lock and is typed in the other case; a numpad key pressed behind a held key and before Num Lock likewise arrives as Windows translated it when it was pressed.
- The hook's hold decision: the permit is gathered before the machine decides, so the window in front is read for keys that end neither held nor deferred; and when the permit falls to `None` after the window in front changes while a deferred press or a mask waits in line, a release passes at once, ahead of that press or mask: a key's release can reach the application before the shell sends its press, leaving the key down in Windows, and a modifier's release before the mask, so the modifier can act alone, as Alt opening a menu.
- The cost figures are from debug builds, as the measuring guide's key workloads are, and the text field traces are not comparable; a trace over a fixed number of keys would settle their cost.
