# UI Automation

UI Automation (UIA) is Microsoft's current accessibility API, and the only one still being developed. This file gives a model of how UIA is built in the three places it runs: the client process, the provider process, and the channel between them. With the model, a reader can work out what happens in a situation, such as a busy application, a stuck call, several threads or an event flood, without memorising separate rules. NVDA's use of UIA is in [The UIA client](https://github.com/Neurrone/verbatim/blob/main/docs/nvda/uia.md) and [UIA remote operations](https://github.com/Neurrone/verbatim/blob/main/docs/nvda/uia-remote-ops.md); Verbatim's choices are in [Architecture](../architecture.md).

## How to read this

Most of UIA's internals are not documented. Every claim about them here is marked in one of four ways:

- Documented: the claim links a Microsoft Learn page.
- Measured: the claim links the readme of the experiment that observed it, with a debugger, a trace or timings, or of the UIA fact that reproduces it (`uia-facts/readme.md` is their index). The experiments ran on one x64 machine, a QEMU virtual machine under Proxmox with 12 virtual processors and 16 GB of memory, running Windows 11 Pro 25H2, build 26200, whose display adapter has no 3D acceleration, so the Desktop Window Manager composes on the processor, and their readmes give each setup and figure.
- From source: the claim names a framework's published source, read on 2026-11-02 (the repositories are under "References").
- Inferred: the claim says so, and names what it rests on.

What has not been observed is under "Not known", not stated as fact. This matters because an inference made earlier, that `FindAll` walks the tree from the client, turned out to be wrong when the requests were counted.

Terms: an STA is a single-threaded COM apartment, whose objects are called only on its one thread, through its message loop; the MTA is the multithreaded apartment, whose objects any of its threads may call ([Processes, threads and apartments](https://learn.microsoft.com/en-us/windows/win32/com/processes--threads--and-apartments); [COM](com.md)). mockapp is Verbatim's test application (`crates/mockapp`), which can serve a UIA provider, an MSAA object or neither, count the provider calls it receives, and hold a provider call or stall its window thread on command. A client object is one `CUIAutomation8` instance; the measurements are of that class.

The function names, such as `OverlappedIOManager::IoThreadProc`, are from Microsoft's public symbols as a debugger showed them in `UIAutomationCore.dll`. They name code, not a contract, and any Windows build can change them.

## Elements, properties and patterns

- Tree: elements form one tree rooted at the desktop. There are three standard filtered views: raw (every element), control (elements that are controls) and content (what a document reader wants). A client walks a view with `IUIAutomationTreeWalker`, or searches with `FindFirst` and `FindAll` and a condition ([UI Automation Fundamentals][learn-fundamentals]).
- Identity: an element is identified by its runtime id, an array of integers that two references to the same element share while it lives; `CompareElements` compares by it.
- Properties are read by numeric id (`UIA_NamePropertyId`, `UIA_ControlTypePropertyId`, `UIA_BoundingRectanglePropertyId` and so on), with `GetCurrentPropertyValue` returning a `VARIANT`, and typed getters for the common ones.
- Patterns express what an element can do: `Invoke`, `Toggle`, `Value`, `RangeValue`, `SelectionItem`, `ExpandCollapse`, `ScrollItem`, `Window`, `LegacyIAccessible` (the element's MSAA view), and `Text` with `TextRange`, a text model with endpoints, movement by unit (character, word, line, paragraph, page), formatting attributes and embedded objects. Terminals and modern document applications are read through the text pattern.
- Caching: a cache request names properties and patterns in advance; an operation that returns elements (a search, a walk step, `BuildUpdatedCache`, an event) fetches them with the elements, and `Cached*` reads then make no call ([Caching for clients][learn-caching]). A remote operation goes further: a small program the client sends into the provider process, run there against the provider, with its results returned at once ([CoreAutomationRemoteOperation][learn-rops]; [UIA remote operations](https://github.com/Neurrone/verbatim/blob/main/docs/nvda/uia-remote-ops.md)).
- Events: a client registers handlers for focus changes, automation events by id (window opened, invoked, notification and others), property changes for a list of properties, structure changes, text edits and active text position changes, each with a cache request whose properties arrive with the event's sender ([UI Automation Fundamentals][learn-fundamentals]). That cache is not sent with the event: the client fetches it from the application with requests of its own before calling the handler (see "Events into the client").

## The parts

A UIA call passes through four parts:

1. The client side of UIA: `UIAutomationCore.dll` in the client process. The client's objects (`IUIAutomation`, `IUIAutomationElement`) are local objects of this library. A call on an element that needs the application becomes a request on UIA's channel. The calling thread waits for the reply in `ChannelBasedClientConnection::WaitForResponse`, on `WaitOnAddress`, with no COM or RPC frame on its stack (measured: [CoCancelCall and UIA][cancel]).
2. The channel: a named pipe, `\\.\PIPE\UIA_PIPE_<provider process id>_<hex>`. The client's calling thread creates it inside its first connection to the process, and the provider process's I/O thread opens it. Requests, replies, element releases and events all pass on it. ALPC calls seen in both processes during a connection were theme services and COM's RPC binding, not UIA's channel (measured: [parallel calls][pc], "The transport").
3. The provider side of UIA: `UIAutomationCore.dll` loaded in the application. One thread of it, the I/O thread, reads every request and makes the provider call (measured: [parallel calls][pc], "UIA's I/O thread"; described under "Inside the provider process").
4. The provider: the application's own objects, `IRawElementProviderSimple` with the fragment interfaces for structure and `IRawElementProviderFragmentRoot` at the window, which raise events with `UiaRaiseAutomationEvent` and related functions ([UI Automation Fundamentals][learn-fundamentals]). A window with no provider of its own is read through a proxy built in the client (see "Making a connection").

Why `CoCancelCall` has no effect: it cancels a COM call outstanding on a thread ([CoCancelCall][learn-cocancelcall]). A UIA client call is not a COM call, so the cancel finds nothing: all 5,614 cancels over 203 trials answered `RPC_E_NO_CONTEXT` and changed nothing, for property reads, text calls, `FindAll`, remote operations and new connections, with cancellation enabled or not (measured: [CoCancelCall and UIA][cancel]).

Verbatim is also a provider, for its own GUI windows, which is why the provider side appears in this repository at all.

## Making a connection

A connection is how a client first reaches a window's provider, as `ElementFromHandle`, `ElementFromPoint`, `GetFocusedElement` or a walk into another window do. This section describes `CUIAutomation8`; the older `CUIAutomation` sends its messages with other flags and timeouts and can wait until the window answers (measured: [hung window][hung], its trace of the older class).

- The client sends the window `WM_GETOBJECT` with the object id `UiaRootObjectId`. The window's procedure answers by calling `UiaReturnRawElementProvider` with its provider, which returns "the key for the client process to connect to the server process" ([UiaReturnRawElementProvider][learn-returnraw]; [WM_GETOBJECT][learn-getobject]).
- In UIA's focus tracking, UIA sends it with `SendMessageTimeoutW`, flags `SMTO_ABORTIFHUNG | SMTO_ERRORONEXIT` and the connection timeout, from `HwndUtils::SendWmGetObject` (measured: [hung window, 2026-11-01][hung2], the breakpoint trace of the focus tracking's calls). That a connection by `ElementFromHandle` sends it the same way is inferred, since the trace covered only focus tracking and registration. `ElementFromHandle` sent two `WM_GETOBJECT`s and five requests into mockapp (measured: [parallel calls][pc], "Requests per client operation").
- Inside the first connection, the client's thread waited on two named events, `UIA_CONNECT_EVENT_<pid>_<hex>` and `UIA_NOBODY_THERE_EVENT_<pid>_<hex>`, then created the pipe and waited in `ConnectNamedPipe`; the provider's I/O thread opened it (measured: [parallel calls][pc], "The transport").
- When `WM_GETOBJECT` finds no provider of the window's own, UIA sends a second message, registered as `UiaServerConnection_HookMessage` (its number is assigned when first registered, so it differs between boots), with flags 0 and the connection timeout, and builds a proxy in the client process: Win32 proxies for standard controls, or the MSAA proxy over the window's `IAccessible` (measured: [hung window, 2026-11-01][hung2], the breakpoint trace of a focus registration). An element's provider description names the proxy.
- The connection timeout, default two seconds, is how long UIA waits "for a provider to respond to a client request for an automation element" ([ConnectionTimeout][learn-connectiontimeout]). A new connection to a stuck application failed with `UIA_E_TIMEOUT` after 2.0 to 2.2 seconds, to any of its windows, even one on an idle UI thread (measured: [parallel calls][pc]). The value is one setting for the whole client process: the last value any client object sets applies to every client object's calls (measured: [the connection timeout][timeout-scope]).
- A pending connection, one whose `WM_GETOBJECT` waits in a busy window's message queue, held the other calls of its own client process until it timed out, but held no other process's calls (measured: [parallel calls][pc], "Abandoning a stuck call"; [the collision experiments][collide], the pending connection without a queued operation).

What UIA answers in the client, without the application (measured: [parallel calls][pc] unless named):

- `Cached*` reads: no request.
- `GetRuntimeId` after the first read of an element (a search re-reads its start element's runtime id when the element was fetched 600 ms or more before, and not at 300 ms: measured, [UIA answers some calls in the client][compare]), and `CompareElements` of elements whose runtime ids it has read: no request ([CompareElements][compare]: none in either application, with one of them stalled).
- The parent of a top-level element, the desktop: no request.
- Elements under a window's title bar, and the other parts UIA's own proxies build: answered by those proxies in the client.
- `GetFocusedElement` does not go to an application of the client's choosing: its requests go to the process that has the focus, 6 into mockapp when it was in front and 5 into another process otherwise.

## Inside the provider process: the one request reader

The provider side of UIA has one I/O thread per process, which reads every request from every client (measured: [parallel calls][pc], "UIA's I/O thread" and "Where the waiting happens", in mockapp, a synthetic provider, Notepad, File Explorer, VS Code and Windows Terminal):

- What creates it: the application's first `UiaReturnRawElementProvider`, on the UI thread that received the first client's `WM_GETOBJECT`. Before that no thread of the process starts in `UIAutomationCore`, even with the library loaded. It starts in `OverlappedIOManager::StaticIoThreadProc`.
- One per process: after 30 connections from 5 client processes in all, one of them with 8 threads, to 8 windows on 2 UI threads, there was still exactly one, and its processor time grew with every client's calls.
- One request at a time: it takes a request, makes the provider call, writes the response, and only then takes the next. A request sent 950 ms earlier waited until the response before it was written.
- In order: requests are taken first in, first out, across all windows, UI threads and client processes. A request into an idle UI thread waited behind one into a busy thread that came before it.
- Releases: each element a client releases is a request of its own, sent at once by the releasing thread with no reply; the provider side delivers them in batches (`ReleaseCollection::DispatchReleases`), through the same thread and, for a provider on its UI thread, as a cross-apartment call into it. In the three snapshots taken while a UI thread was suspended, and in the one taken during a pending connection, the I/O thread was delivering releases; in a trace of a held name read it was in that read's own call, and in AccessKit during an `Invoke` it was sending `WM_GETOBJECT`.
- Events do not pass through it: the thread that raises an event writes it to the pipe itself (see "Events into the client").

Every effect of one slow call follows from this one thread. Provider work of two calls never overlapped in any application. While one call is in the provider, every other call into that process waits, from any client thread or process, to any window, element or UI thread of it, remote operations included. A call into another process is not affected.

Windows Terminal had one other thread started in `UIAutomationCore`, at `NavigationHelperProxyOneCore::s_CoreUIThreadProc`, whose work was not examined.

## Where the provider call runs

`ProviderOptions_UseComThreading` means that "STA-based provider implementations will be called back on their own STA thread" ([ProviderOptions][learn-provideroptions]). What the I/O thread does in each case (measured: [parallel calls][pc], "UIA's I/O thread", "Why several threads speed up cheap calls", "AccessKit"):

- With `UseComThreading` and a provider on a UI thread: the I/O thread makes a cross-apartment COM call (`ComInvoker::CallTarget`, `combase!MTAThreadDispatchCrossApartmentCall`), COM's window procedure dispatches it on the UI thread, and the I/O thread waits. It reads no other request meanwhile. So once a call is queued on a busy UI thread, every call into the process waits, the calls into its other UI threads included; a busy UI thread with no call queued on it held nothing else, and calls into the process's other UI thread answered in 0.4 to 1.2 ms (measured: [parallel calls][pc], "MSAA calls while a UIA call is stuck"; [the collision experiments][collide], the control with an idle second UI thread). A provider that waits while dispatching COM calls (`CoWaitForMultipleHandles`) held the others exactly as a sleeping one did.
- Without it: the I/O thread calls the provider itself. A busy UI thread then delays no read, but a slow provider call still holds every call into the process. Some requests still need the UI thread: in AccessKit, an `Invoke` into a busy window waited for it, with the I/O thread's stack in `HwndUtils::SendWmGetObject` under `GetNodeFromProviderEntryPoint`, so the I/O thread was held meanwhile. A new connection to the busy window failed at the connection timeout; the other calls of the same client process waited until then, while another process's read into the same window answered in 3.0 ms, so that connection was not seen holding the I/O thread. Whether a new connection's work ever runs on the I/O thread is not known.
- For a provider on its UI thread, the I/O thread and the UI thread, working in turn, take about half of each call's time; the client's threads take the rest. That serial share is why two client threads already keep such a provider busy, and why parallel client threads gained at most about 2 times on cheap calls and 1.0 to 1.5 times on calls whose cost is in the provider.

By framework:

- Windows Forms, Qt, Chromium (and so Edge and Electron), WinUI 3, Firefox, JavaFX and Flutter declare `UseComThreading` with the provider on an STA UI thread (from source). Measured, the real applications of these kinds (Notepad on WinUI 3, Edge, VS Code, Firefox, Windows Forms) behaved as STA providers: every call waited on a suspended UI thread, and Chromium served the browser's window and its page on the browser's UI thread.
- WPF and Avalonia do not declare `UseComThreading`; each provider method is sent to the UI thread's dispatcher and the calling thread waits, with a three-minute timeout in WPF and none in Avalonia (from source). So the I/O thread waits on the UI thread as for an STA provider. Measured for WPF on .NET Framework 4.8: it held like the others.
- The console host does not declare `UseComThreading`, and each method takes the console's lock, which also serialises console output (from source; not measured: the parallel-calls experiment did not open a console host, since this machine's default terminal hands an ordinary console to Windows Terminal, though running `conhost.exe` directly opens one, as the console host experiments did).
- Windows Terminal: its text provider declares only `ServerSideProvider` (from source), but its calls arrive through system XAML's automation peer, and they ran on the XAML UI thread: in a trace, 391 of the UI thread's 847 samples were in its `GetText`, and none of the I/O thread's. With that thread suspended, its text calls waited (measured). System XAML's source is not published.
- AccessKit declares `ServerSideProvider` alone, with agile objects, and reads its tree under a reader-writer lock so that reads could run in parallel (from source). Its calls ran on the I/O thread, never two at once, and a busy UI thread held none of its reads, but an `Invoke` waited for the UI thread and a new connection to its window failed at the connection timeout, and a slow action handler held every call into the process (measured). Its parallel-safe design cannot be exercised through UIA, because the one I/O thread never makes two provider calls at once.

## What one request is

Requests per client operation, counted on both sides with a debugger on mockapp, whose providers declare `UseComThreading` (measured: [parallel calls][pc], "Requests per client operation" and "One call's requests"). The I/O thread read every request the client sent. Another provider can make UIA send other requests.

- A `Current` property read: 1 request.
- A cached read: none. `GetRuntimeId`: 1 the first time, then none.
- A walker step (first child, next sibling): 2, the navigation and the release of the element passed over; with a cache request 4. A step to a parent that is a window's root: 4 to 6, with a `WM_GETOBJECT`.
- `FindFirst` of a node three levels down: 7, one of them a single `Find` request that held all 338 of the walk's provider calls. With a cache request: 9.
- `FindAll` of a 31-element subtree: 34 requests without a cache request, 1 `Find` and 30 releases among them; with one, 84, adding 24 `BulkFetch`es, one per found element mockapp serves (the rest are UIA's own proxies). On mockapp's 102-node tree, 315.
- `BuildUpdatedCache` of six properties: 2 (one `BulkFetch` and a release); with subtree scope, one `BulkFetch` for the whole subtree.
- `ElementFromHandle`: 5, with 2 `WM_GETOBJECT`s. `ElementFromPoint` then two reads: 9. `GetFocusedElement`: 6 into mockapp with the focus, 5 into another process otherwise.
- `GetCurrentPattern`: 2, the pattern and its release. Text: `DocumentRange` 2; `GetText`, `Move` and `ExpandToEnclosingUnit` on a held range 1 each.
- `Toggle` on a held pattern: 12, with a `SetFocus` before it; on the synthetic provider an `Invoke` was 2, and on AccessKit an `Invoke` was a `SetFocus` request, then the `Invoke`.
- Adding an automation or property event handler on one element, subtree scope: 2; removing it: 2. `AddFocusChangedEventHandler`: 27 requests, most to other processes, and on the registering thread it delivered a focus event for the element then focused.
- A remote operation: 1 request.
- Releasing elements: one request per element the provider serves, none for UIA's own proxies; dropping 30 elements held from a `FindAll` sent 23.

So a search is not walked from the client step by step. The client first reads the start element's runtime id, if it has not kept it (`GetRuntimeId` from `ElementFinder::Find`), and tests the condition on the start element itself, a `GetPropertyValues` request from `FindingVisitor::Enter` under `UiaNodeTraverser::Traverse` (measured: [CoCancelCall and UIA][cancel], its stacks; [parallel calls][pc], "A search's timeouts"). Its own proxies for the start element's window then navigate with window messages to that window: `CB_GETCOMBOBOXINFO` from `HwndProxy::Navigate`, and from oleacc a `WM_GETOBJECT` for object id -5 under `MsaaNonClientProxyRoot::Navigate` (measured: the same section). It then sends one `Find` request (`FindingVisitor::CallRemoteAndMergeState`); inside it the provider side walks the provider's tree, for an STA provider on the UI thread in one cross-apartment call (`RemoteUiaNodeStub::Incoming_Find`). On mockapp's 24-node tree that one request held 81 of the 83 navigations (measured: [parallel calls][pc], "One call's requests").

A remote operation is one request whose length is the program's. UIA stops a program after exactly 10,000 executed instructions with `InstructionLimitExceeded` (measured: `the_instruction_limit_is_measured` in `crates/mockapp/tests/instruction_limit.rs`, [The instruction limit](../../reference/performance.md)). Within that limit one operation held an application for 2.6 ms in Firefox and 228 ms in WPF, reading a bounding rectangle 1,500 times (measured: [parallel calls][pc]).

## Timeouts and cancelling

- The transaction timeout, default 20 seconds, is how long UIA waits "for a provider to respond to a client request for information about an automation element" ([TransactionTimeout][learn-transactiontimeout]). Like the connection timeout it is one value per client process, the last set winning (measured: [the connection timeout][timeout-scope]).
- Each call's wait starts at its own start. A call queued 200 ms behind a stuck one failed 2,198 ms after its own start under a 2-second timeout, not when the first did (measured: [parallel calls][pc], "Timeouts").
- How the client waits: the timeout less 200 ms, as a count of waits that each last about 110 ms, then one of 205 ms. So a 2-second timeout fails after about 2.2 seconds, 5 seconds after 5.5, and the 20-second default after 22.1 (measured, a context-switch trace: [parallel calls][pc], "Timeouts"). With the system timer at 1 ms the wait is the same, 2.2 seconds at 2 seconds, so the extra tenth is not the timer's tick (measured: [a call waits its timeout from its own start][own-start]). Under an invasive debugger the client waits the whole timeout at once, so these figures come from runs without one.
- The provider side never learns of the timeout. Its I/O thread stays in the provider call until the call returns, and then delivers the requests of calls that have already failed: after a hold, the provider answered the failed call's read and the read of the call queued behind it (measured: [parallel calls][pc], "Timeouts").
- Nothing cancels a call. `CoCancelCall` finds no COM call (see "The parts"). Abandoning a call, leaving its thread to wait and making later calls on new threads, only ends the client's wait for it: every later call into the stuck process waited for the release or failed on its own timeout, on any thread, and the first answer after the release came within 2 ms either way (measured: [parallel calls][pc], "Abandoning a stuck call").
- An operation made of several requests and messages waits for each of them in turn, each on its own bound, and the client re-sends nothing. A search's waits, in order (measured: [parallel calls][pc], "A search's timeouts", with no debugger attached):
  - the start element's runtime id, if read again: its failure ends the search;
  - the condition's test on the start element: its failure is passed over;
  - `CB_GETCOMBOBOXINFO` to the window, bounded by the transaction timeout;
  - oleacc's `WM_GETOBJECT`, bounded by the connection timeout in force when the start element was fetched, not the value set for the call;
  - the `Find` request, which with connection recovery on was sent only when the waits before it had ended 3.1 seconds or more after the search began.

  So in the experiment called E-TT, with mockapp holding the condition's test and the transaction timeout at 1 second, a `FindFirstBuildCache` failed after 13.2 seconds: 1,085 ms for the test, 1,010 for `CB_GETCOMBOBOXINFO`, 10,013 for `WM_GETOBJECT`, since the connection timeout was 10 seconds when the root was fetched, and 1,075 for the `Find` queued behind the held call. After the release the provider ran the whole walk, 53 provider calls, for a client that had failed 3 seconds before. Queued behind another client's held name read, a `FindFirst` failed after one timeout, 1,083 to 1,106 ms, because its first request was the root's runtime id. With mockapp's window thread stalled, both timeouts at T set before the fetch, and recovery on, it waited the first three bounds and failed without sending the `Find` at 100, 200 and 500 ms, and sent and waited for it at 1,000 ms, 4,207 ms in all.
- A registration that times out reports success, after the connection timeout, whatever the transaction timeout ([A registration that times out reports success](../../reference/uia-bugs.md#a-registration-that-times-out-reports-success)).

## Calls from the client

- A call runs on the thread that makes it and blocks it until the reply. The calling thread writes its request to the pipe itself (`ReadWriteChannelInfo::BlockingWrite` under `ChannelBasedClientConnection::DoCallWithReturn`); one I/O thread of the client process reads every reply and wakes the caller (`ChannelBasedClientConnection::SetResponseInfo`) (measured: [parallel calls][pc], "UIA's I/O thread").
- Calling threads: in snapshots of 8 calling threads, 39 of 40 stacks were waiting for their replies and none for a lock (measured: [parallel calls][pc], "Threads of one client against client processes"). One client object shared by all threads made no difference against one per thread.
- Apartments: Microsoft says to make UIA calls from a thread in the multithreaded apartment that owns no windows, and to add and remove event handlers on one non-UI thread, since adding or removing from several threads at once "can result" in unexpected behaviour ([Understanding Threading Issues][learn-threading]). An element cannot be used in another process: its marshaled form fails to unmarshal there (measured: [elements cannot be passed][elements]).

## Events into the client

- An event goes from the provider process on the same pipe as the replies, written by the thread that raised it, the application's UI thread here, not by the I/O thread; with no handler registered for it, nothing was sent (measured: [parallel calls][pc], "Events and releases").
- The client's threads: the first registration, or the element lookup before it, starts UIA's WinEvent thread (`WinEventManager::ThreadProc`), its I/O thread and a `NavigationHelperProxyOneCore` thread. The I/O thread reads each event and queues it to a work-item thread (`WorkItemQueue`), which it creates when the first event arrives (measured: [hung window, 2026-11-01][hung2], the thread-creation trace of a name-change registration).
- The worker: the event work of a client process ran on one work-item thread at a time, in order (measured: [hung window][hung], its thread dumps during a hold). Two client objects in one process shared it: an event registered on one client object waited behind the other client object's focus tracking, with the second object on the same thread or a thread of its own (measured: [hung window][hung], the client variants). That every client object of a process shares one worker, however many there are, is inferred. Before calling the handler the worker fetches the event's cache request from the application with requests of its own, 8 for one selection event (measured: [parallel calls][pc], "Events and releases"). So another client's call stuck in that application would hold this fetch, and with it every later event of the client process (inferred); whether the transaction timeout bounds the fetch is not known. The worker also runs UIA's focus tracking: for each focus WinEvent (`EVENT_OBJECT_FOCUS`) in a process holding any focus registration, it sends the named window `WM_GETOBJECT` and, when that finds no provider, the connection message, each waiting up to the connection timeout, while every other event of the process waits behind it (measured: [hung window][hung]; [hung window, 2026-11-01][hung2]). Four events in a row ran on four different thread ids (measured: [parallel calls][pc], "Events and releases"), so the thread is not kept between events; that it ends when its queue is empty is inferred.
- The open and show route: focus for a newly opened or shown window, such as a menu's popup, is raised on a thread-pool thread (`ClientEventManager::OpenShowWinEventCallbackThreadProc`) and is not held by the worker. One menu opening delivered many focus events to the handler by this route (measured: [hung window, 2026-11-01][hung2], the breakpoint traces of a menu opened during a hold).
- Focus events can be registered only desktop-wide: "Focus-changed events are system-wide; you cannot set a narrower scope" ([AddFocusChangedEventHandler][learn-addfocus]), and `AddAutomationEventHandler` for the focus event on one window is refused with `E_INVALIDARG` and the message "Focus events must be registered using IUIAutomation::AddFocusChangedEventHandler" (measured: [focus events cannot be limited][scope]). Two undocumented routes are accepted, the focus event in an event handler group on a window and the core API's `UiaAddEvent` on a window's node; each delivered that window's provider-raised focus and no other application's, and neither delivered any focus of a window UIA proxies (measured: [focus events cannot be limited][scope]).
- What a registration costs the application: each process with a focus registration on a window added about 47 to 49 provider calls per focus event on the application's UI thread, most of them navigation and options (measured: [focus events cannot be limited][scope], the provider calls counted per focus event).
- Selective registration is registering the busy events (text changes, caret and text selection changes, property changes) only on the focused element and moving them at each focus change, while events that can come from anywhere, such as notifications, selection and window opened, stay desktop-wide. What it saves: busy events from other elements and applications never reach the client's one worker, so their flood cannot fill its queue, and no provider work is spent raising them to this client (inferred from the worker and the per-registration cost above). What it costs: adding and removing a subtree registration on an element were 2 requests each into its application, made on the registering thread (measured: [parallel calls][pc]); against an application that does not answer, the registration returns success after the connection timeout (measured: [registration that times out][registration]); events raised between the focus change and the new registration are not heard (measured: the same, its `between` arm).
- Lost events: at about 10,000 events a second from one application, the worker delivered the first 83 to 110 and then no event to any handler of the process for at least 90 seconds, using a processor core throughout; at 2,000 to 5,000 a second some of another application's events were never delivered. The exception at 10,000 a second: text changed events with coalescing on kept being delivered, 2,529 and 2,641 of 30,000 (measured: [flood][flood]). Whether UIA drops events when the client's handler itself is slow was not observed; NVDA's record says it does (see the case study).
- With two or more processes each holding a desktop-wide focus handler, every process after the first received proxied focus events up to 0.7 to 2.7 seconds late; the cause is not known ([Desktop-wide focus handlers in a second process deliver late](../../reference/uia-bugs.md#desktop-wide-focus-handlers-in-a-second-process-deliver-late)).
- Before Windows 10 version 1809, one application that answered slowly reportedly stopped UIA events for every application in a client; Microsoft added event coalescing and connection recovery in `IUIAutomation6` then ([IUIAutomation6][learn-uia6]). The stall itself is NVDA's record, not observed here.
- Microsoft says a handler "is always called on a non-UI thread" and that UIA calls in it are safe ([Understanding Threading Issues][learn-threading]). The handler runs on the worker (measured), so whatever it waits for delays every later event that worker delivers (inferred).

## MSAA beside UIA

Measured: [parallel calls][pc], "Why MSAA slowed with more threads" and "MSAA calls while a UIA call is stuck".

- For a window with no `IAccessible` of its own, `AccessibleObjectFromWindow` gives oleacc's proxy in the client, and its `accName` sends `WM_GETTEXTLENGTH` and `WM_GETTEXT` to the window, answered on its UI thread: no COM call and no UIA request. A provider's own `IAccessible`, and UIA's MSAA bridge over a UIA provider, are COM calls answered on the window's UI thread.
- Neither goes through UIA's I/O thread. With a UIA call stuck in a provider off the UI thread, MSAA calls into the same process answered in 1.2 to 2.6 ms while UIA calls waited. An MSAA call waits only for the thread that answers it, and into a busy UI thread it waited as long as the thread was busy: no bound was observed, and [NVDA #20169](https://github.com/nvaccess/nvda/issues/20169) reports a freeze of about 65 seconds in `AccessibleObjectFromEvent` for windows entangled with a hung UIA application.
- Sent messages slow down with more sending threads: oleacc's name read, and a bare cross-thread `SendMessage`, ran at 0.52 to 0.78 times the single thread's rate with more threads, even when each thread sent to a window on a UI thread of its own. That the contention is in the window manager, which every sent message passes through, is inferred, since a user-mode debugger cannot see the kernel.

## Predicting outcomes

Each case follows from the sections above; the figures are measured, in [parallel calls][pc] unless named.

- Two client threads making cheap calls into one STA application: at most about 2 times one thread, since the I/O thread and the UI thread are already busy all the time. With costly calls, about 1.0.
- A slow call A, then a cheap call B into the same application from another thread or process: B waits for A's remaining provider time. Beside one 222 ms `GetText` in Edge, B took 220 ms against 0.2 ms alone.
- A `FindAll` with a cache request beside a cheap call B: B gets in between the `FindAll`'s many requests, so its median rose only to 0.4 ms, but B can wait for the whole `Find` request, up to 696 ms beside Edge's 20,000-element page.
- A stuck UI thread with a call queued on it: every call into the process waits, to any window, from any client; new connections fail after 2.0 to 2.2 seconds; waiting calls fail after 22.1 seconds with the default timeout. Calls into other processes are unaffected.
- A provider off the UI thread with a busy UI thread: reads answer at once, but a new connection to the busy window fails at the connection timeout, and an `Invoke` waits for the UI thread, holding the I/O thread meanwhile.
- Abandoning a stuck call against keeping one thread: the same answers at nearly the same times. On new threads later calls start sooner and each fails on its own timeout; on one thread they start once the stuck call fails.
- A new connection while another process's remote operation is queued in the application: it answers wrongly with no error, the window proxy after about 2 seconds or "no provider" after about 3 ([A new connection fails while another process's remote operation is queued](../../reference/uia-bugs.md#a-new-connection-fails-while-another-processs-remote-operation-is-queued); [the collision experiments][collide]). A plain read queued there is only delayed.
- An MSAA call while a UIA call is stuck: it answers if the thread that serves it is free, since it does not pass through UIA's I/O thread.
- Two applications: independent; one stuck application delays no call into another (File Explorer windows in two processes, 1 to 10 ms).
- An event flood of name changes, or of text changes with coalescing off, from one application at about 10,000 a second: every handler in the client process stops, the other applications' included; text changes with coalescing on kept being delivered; a client process holding no registration in the flooding application is unaffected (measured: [flood][flood]).
- A slow query inside an event handler: it runs on the worker, so every later event the worker delivers waits behind it (inferred).
- A focus WinEvent naming a window that does not answer, in a process with a focus registration: that process's UIA events wait about twice the connection timeout, 3.8 to 4.2 seconds at the default, or one timeout once Windows has marked the window hung. Focus in a newly opened or shown window, such as a menu, is still delivered on time by the open and show route; focus moving within an existing window, name changes and notifications are held. MSAA WinEvent hooks and explicit reads on other threads are not held (measured: [hung window][hung]; [hung window, 2026-11-01][hung2]).
- Selective registration under a flood from an unfocused application: its busy events were never registered, so they do not reach the worker (inferred). A flood of desktop-wide events, such as notifications, still fills it.

## Case study: NVDA

NVDA's UIA client (`nvda/source/UIAHandler/__init__.py`) has these threads: an MTA thread that creates the client object, registers every handler and runs queued registration work; the core thread, an STA, which makes most UIA calls ([NVDA #20654](https://github.com/nvaccess/nvda/issues/20654)); UIA's own worker, which calls NVDA's handlers; and, with enhanced event processing, a native handler that stores events for the core thread ([The UIA client](https://github.com/Neurrone/verbatim/blob/main/docs/nvda/uia.md)). Its watchdog recovers a frozen core thread with `CoCancelCall` and, for a few calls, runs them on a thread it can abandon (`watchdog.cancellableExecute`). Each issue below is explained from the model.

- [NVDA #20654](https://github.com/nvaccess/nvda/issues/20654): one `buildUpdatedCache` against a slow provider froze NVDA for about 5 seconds, and about 90 `CoCancelCall`s over 4.5 seconds did not end it. The cancels find no COM call. Against a window that did not pump messages the call took 19.8 seconds, about the transaction timeout; with both timeouts at 500 ms it failed in 0.509 seconds, and reading the fifteen state properties one at a time, as NVDA's fallback would, took 7.555 seconds in all, since each request waits its own timeout from its own start. The consistent 5 seconds is not explained by the model.
- [NVDA #20169](https://github.com/nvaccess/nvda/issues/20169) and [NVDA #20170](https://github.com/nvaccess/nvda/pull/20170): `UiaHasServerSideProvider` on a hung application blocked the core thread, and the watchdog could not cancel it; the fix runs it on a thread that is abandoned. The probe is a window message and a connection, not a COM call, so neither cancel reaches it; it does not respect the client's timeouts (NVDA's own note in [NVDA #6533](https://github.com/nvaccess/nvda/issues/6533)), and it answered "no provider" after about 3 seconds in this repository's [collision experiments][collide]. The issue also says a hung UIA application "jams the shared UIA client", so that Windows 11's Alt+Tab switcher cannot be read. The model gives two ways this can happen in one process: the core thread itself waiting in a call into the hung application, and a focus WinEvent naming the hung window holding every UIA event of the process; calls into the switcher's own process are not held. Which one the report met is not established.
- [NVDA #6533](https://github.com/nvaccess/nvda/issues/6533): NVDA never sets the timeouts, so a call into a stuck application holds the calling thread about 22 seconds and a new connection about 2.
- [NVDA #7345](https://github.com/nvaccess/nvda/issues/7345) and [NVDA #8539](https://github.com/nvaccess/nvda/pull/8539): UIA stalled in NVDA, and Microsoft bug 12608330 recorded Narrator becoming "unresponsive in all apps when a single app is continually slow to respond". NVDA stopped UIA's MSAA proxy from mapping WinEvents to property changes, which its comment says can make the client library unresponsive when an application has a slow message pump ([NVDA #7345](https://github.com/nvaccess/nvda/issues/7345)), and turned on event coalescing and connection recovery ([NVDA #8539](https://github.com/nvaccess/nvda/pull/8539)). Both fit the shared worker of a client process: anything the worker waits on, a cache fetch or a WinEvent's proxy work, holds every event behind it (inferred).
- [NVDA #11002](https://github.com/nvaccess/nvda/issues/11002), [NVDA #14888](https://github.com/nvaccess/nvda/pull/14888), [NVDA #15850](https://github.com/nvaccess/nvda/issues/15850) and [NVDA #17602](https://github.com/nvaccess/nvda/issues/17602): floods of console output or busy web pages stopped NVDA's UIA, at times until a restart. NVDA is one process holding registrations for every application, so a flood fills the worker that delivers all of them (one worker per process inferred). [NVDA #14888](https://github.com/nvaccess/nvda/pull/14888) made NVDA's handler return at once so that, in its words, UIA "should never feel the need to kill off events".
- [NVDA #20608](https://github.com/nvaccess/nvda/pull/20608) counted 34 to 63 cross-process calls for one focus change in File Explorer and Settings and cut them with cache requests. Each `Current` read and each release is a request, a turn of the application's I/O thread, and for an STA provider a cross-apartment call into its UI thread.
- [NVDA #20168](https://github.com/nvaccess/nvda/pull/20168) drops events from an application Windows reports hung, read with `IsHungAppWindow` on the sender's cached window handle, which makes no call into the application. Windows marks a window hung after about 5 seconds ([IsHungAppWindow][learn-ishung]), so events before that still reach the handlers.
- Selective registration: NVDA registers range value and the two drag-and-drop effect properties, and the global events, desktop-wide, and registers every other property change, the caret's text selection changes and, for some window classes, text changes on the focused element and its ancestors, moving them on each focus change from its MTA thread after checking with `GetFocusedElement` that the element still has the focus (`nvda/source/UIAHandler/__init__.py`, lines 241 to 289 and 592 to 755). Each move is requests into the focused application, and the check is a call into whichever process has the focus.

## What a client should take from this

- One thread per application is enough for calls into it. More threads gain at most about 2 times on cheap calls and nothing on costly ones.
- A call into an application waits for whatever that application's I/O thread is doing for any client, so a client cannot bound its calls by being careful with its own: it can only bound its own wait, with the timeouts or a thread it can abandon, and abandoning frees nothing in the application.
- Checks that must answer while an application is stuck, such as which window is in front and whether it is hung, must not depend on that application: window messages to it, a UIA connection, and `GetFocusedElement`, which goes to the process with the focus, all do.
- A remote operation helps when it replaces many requests, each of which is a turn of the I/O thread and possibly a cross-apartment call. A long one holds every other client's calls into the application for its whole length, so keep each one short and well under the instruction limit.
- A client process's events share one worker, as far as observed. Keep handlers short, register busy events only where they are needed, and hold registrations that must survive another application's flood in a different process.

Verbatim's own choices from this model are in [Architecture](../architecture.md); they are not restated here.

## Not known

- Why connection recovery makes a search skip its `Find` request when the waits before it end by 2.78 seconds, and send it when they end at about 3.1 seconds or later.
- Why a new connection to a stuck application fails with `UIA_E_TIMEOUT`, while one made during another process's queued remote operation returns the window proxy with no error; the mechanism of that collision inside UIA was not observed.
- Why a pending connection holds the other calls of its own client process, and which releases held the I/O thread in that case.
- Whether a provider process ever gets a second I/O thread, for example after every client disconnects; and whether a client process has more than one, since a thread-creation trace of a focus registration showed two created.
- Whether the client's work-item thread is one per process for any number of client objects (two were seen sharing it), and whether it ends when its queue is empty.
- Whether the transaction timeout bounds the worker's fetch of an event's cache, and so how long another client's stuck call into an application can hold a client's events.
- Whether `GetFocusedElement` fails during another process's queued remote operation: it failed in an earlier experiment that was not kept and succeeded in 3 of 3 later; a process's own lookups during its own queued operation were not exposed ([the collision experiments][collide]).
- Whether a new connection's work runs on the provider's I/O thread.
- How long an MSAA call into a busy UI thread can wait.
- Whether UIA drops events when the client's handler is slow, and whether coalescing dropped the events lost at 2,000 to 5,000 a second.
- That the flood's worker work grows with the square of the backlog is inferred from function names and processor time, not shown.
- Where `AddFocusChangedEventHandler`'s requests to other processes went, and what `GetFocusedElement` and a top-level element's next sibling reached in other processes.
- Whether connection recovery changes any of the call results; the parallel calls experiment ran without it (it did not change the focus-tracking hold).
- Why two or more processes with desktop-wide focus handlers receive proxied focus late.
- NVDA's consistent 5-second freeze in [NVDA #20654](https://github.com/nvaccess/nvda/issues/20654), and its 19.8-second call where this machine's client waited 22.1 seconds for the same default.
- The client-wide event stall before Windows 10 version 1809, known only from NVDA's record.
- The work of the `NavigationHelperProxyOneCore` thread.
- The console host, Qt, .NET 8 WPF and Windows Forms, and Java applications were not measured.
