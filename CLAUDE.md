# CLAUDE.md

## What this repository is

Verbatim: a screen reader for Windows 11 (x64 and ARM64), written in Rust.

- `books/dev/src/explanation/architecture.md` — decisions of record, read this before proposing any design or implementation work.
- `docs/roadmap.md` — the milestones ahead, completed milestones are archived in `docs/roadmap-done.md`.
- `books/` — the documentation published to GitHub Pages, one mdBook per book, each arranged after Diataxis (tutorials, how-to guides, reference, explanation): `books/dev/` the Development guide, `books/extensions/` the Extensions guide, `books/user/` the User guide. A page joins its book's `SUMMARY.md`, and names anything outside its book, an agent-only document included, by its full GitHub address, because the site carries nothing else (`cargo xtask docs` checks both).
- `docs/` — the working documents only agents read, never published: the roadmap, the design records of work not yet built, the parity ledger, `docs/nvda/` and the flaky-test list. `docs/readme.md` is the index of both, with reading paths; `books/dev/src/reference/glossary.md` defines Verbatim's invented vocabulary.
- `books/dev/src/reference/crates/` — the reviewer's guide to the implemented crates, one file per crate (`books/dev/src/reference/crates/readme.md` is the index): what each does, its public API, and how the intricate parts work. Keep the file for a crate current when its public API changes.
- `books/dev/src/how-to/readme.md` — how to actually drive this project, with the interactive-session rule and an index of the guides beside it in `books/dev/src/how-to/`: setup, `verbatim-inspect` against a running instance, `mockapp`, measuring, the end-to-end suite, NVDA captures, and the traps that cost us time (`troubleshooting.md`).
- `books/dev/src/reference/testing.md` — the testing standard every test must meet: one fixed target and code path, exact assertions, waits only for evidence, and no hidden failures. Read it before writing or changing any test, and check every test change against it.
- `books/dev/src/reference/test-coverage.md` — every gesture and user-facing feature, with the tests that cover it at each level and the gaps still open. Update its row when adding or removing a gesture, a user-facing feature or a test.

`nvda/` is the NVDA screen reader vendored as a git submodule **for reference only** (IA2 IDL under `nvda/include/ia2`, app modules under `nvda/source/appModules`, design docs under `nvda/projectDocs`). Never modify anything under `nvda/`; Verbatim is informed by NVDA but not constrained by its architecture.

## Writing conventions

All documentation, comments, and commit messages in this repo must read well with a screen reader, in both rendered and source form:

- No ASCII-art diagrams, box drawings, or arrow chains.
- Documents describe the present. When a mechanism changes, replace its description rather than appending a dated note or keeping the old text beside the new; history lives in git and the commit messages. A decision of record states the decision as it stands, dated when it was made, with no amended-on line. A rule that exists because something went wrong keeps one sentence of why, not the narrative. A superseded design record is archived or deleted, never kept in place with a banner.
- Design documents state the current model, its rules each with a brief reason, its limitations, and the important performance figures such as latency and memory; evidence lives in `experiments/` and history in git, so that a document stays short enough to be read whole. Once its work is built, a design document becomes two: an explanation of how it works today in `books/dev/src/explanation/design/`, with no alternatives or history, and a numbered decision record in `books/dev/src/reference/adr/` with the problem, the options weighed and why each was taken or rejected, the decision with its date, and its limits; the mechanism's details stay in the crate guide (Dickson, 2026-11-07).
- Each rule, mechanism and figure is written in one place, and other documents point at it: a behaviour in its explanation page, NVDA's behaviour and the ruled differences in its parity entry, a decision and its limits in its ADR, a mechanism in its crate guide, and a figure a test pins in that test, which `books/dev/src/reference/performance.md` names rather than copies; a cost goes in that ledger only when it is on the event or speech path or was measured to be slow. Because the dialog wait's ending rule is written in nine places, one behaviour changed 11 to 16 documents, and four ledger figures drifted from the tests that pin them (Dickson, 2026-11-20).
- Reports define any invented term on first use or avoid it, lead with the required decisions

## Decisions Dickson owns

Dickson takes the decisions in these areas himself; every other decision is Claude's, made with its reason recorded where the decision lives and checked by the adversarial review, because splitting each decision between Dickson and Claude spread the responsibility without adding judgment (2026-11-01).

- The process and thread layout: which work runs in which process and on which thread (D9, D13).
- Architecture and high-level design
- Trust boundaries and accepted risks: which code is trusted, what is sandboxed, what extensions and native add-ons may do and how users approve them, and the posture for UIAccess and secure screens. The mechanisms that enforce them are the session's.
- What users hear: every deliberate difference from NVDA's speech, and every spoken behaviour NVDA has no answer for. Matching NVDA's captured speech needs no decision where it is practical: it needs no new state, rule or mechanism and keeps the build within its budget. Where matching would need one or pass the budget, the difference goes to Dickson for approval when it arises, with NVDA's capture, the sequence and what matching would cost, and the build stops on that behaviour alone until he answers, because matching NVDA one sequence at a time in an architecture that is not NVDA's added a mechanism per fix (Dickson, 2026-11-20).
- Performance budgets: latency, idle wake-ups and processor time, memory, and how long silence is tolerated while an application hangs. How a budget is met is the session's.
- Public contracts: the extension API, the settings file format, the control and Remote protocols, and anything else people outside the project will depend on.
- Major dependencies and licensing: adopting or replacing a runtime, toolkit or engine, and the tier rules under NVDA provenance.
- Scope and order: what each milestone includes and which comes next.
- The working process: this file and `REVIEW.md`.

A decision outside these areas is delegated to Claude, but the user should still be told about it in case it needs to be overridden.

## Standing rules

These hold for every session and every subagent; a brief, `REVIEW.md` and the `port` skill point here rather than restating them.

- Fix root causes, never hiding a race or failure with a retry, a sleep, skipped cleanup, self-termination or a mechanism added for that one failure; a workaround needs evidence that the proper fix is not enough, and is documented as one, because the outpost code once became a pile of mechanisms each added for one live failure and had to be redesigned (Dickson, 2026-11-20).
- Verify every claim about NVDA's behaviour, in a design, a code comment or a decision put to Dickson, from the pinned source under `nvda/` or a live capture; a design's adversarial review checks each one and a wrong one blocks approval, and a decision put to Dickson gives one concrete sequence with the exact speech under each option, because the November rebuild carried three wrong claims about NVDA from its designs into code (Dickson, 2026-11-17 and 2026-11-20).
- Take spoken expectations only from NVDA captures made before the expectation is written, at the pinned build (a series stops when the capture header's build differs from `git -C nvda rev-parse HEAD`), and what an application raises, and in what order, only from a `verbatim-event-record` recording of the real application, against which each stand-in for it (mockapp, a scenario's fixture) is tested, a difference fixed or recorded as deliberate, because 52 fixes in one month came from an application's behaviour learned after building. Each capture and recording that a test or document cites is committed beside what cites it, and a check compares each expectation with its capture, because on 2026-11-20 only 4 of 105 scenarios cited a capture that still existed (Dickson, 2026-11-20).
- Confirm a design before building on it, and build nothing that depends on an open study or decision. The design states the exact speech in each sequence, its edge cases and where each part runs; NVDA's lines for the behaviour and a budget of product lines within 1.3 times NVDA's (Dickson's stated target), or three times for a behaviour that crosses a process boundary, with test lines within the product budget, and for a behaviour NVDA lacks the budget ruled with it; a table of any state it adds, saying what each rule does in each state; and, where it replaces code, everything that code does and says, mapped to new code and a test or to a ruling of Dickson's that retires it, because the November rebuild silently lost the formatting reads and two ruled differences (Dickson, 2026-11-17 and 2026-11-20).
- Each design gets one adversarial review by a subagent before implementation, and each completed build one implementation review, as `REVIEW.md` says, never one per commit. A review asks first what the change adds to shared machinery (a kind of request, reply or waiting request, a queue hook, a state, a document) and whether each addition can go, and only then breaks it with code-level sequences, one for each state-table cell it doubts, because on 2026-10-21 reviewing every commit produced contradictory findings and sixteen rounds on one area, and the dialog wait's three design rounds each met a new way for the wait to end with more state (Dickson, 2026-11-20).
- A build stops and goes to Dickson, saying whether the design is at fault, and builds nothing more in that mechanism until he answers, at the third fix commit in one mechanism after its implementation review (a gap a generated test finds in an approved design, or between a model and its prototype, counts as one), when its design still has must-fixes after three review rounds, or when its lines pass its design's budget, because the rule as a judgement did not fire for the gap record, which took seven more fixes (Dickson, 2026-11-10), and the dialog wait reached 1,560 product and 2,190 test lines for a behaviour that needs 100 to 165 (Dickson, 2026-11-20).
- A proposal, brief or design that would change a decision of record (a D-decision, an ADR, a dated decision in a design, a roadmap entry) quotes it, names the fact that has changed since or is not made, and says how it fits each planned milestone it touches, because proposals that ignored recorded decisions and planned work each cost a review and a reversal (Dickson, 2026-11-10). Adding a kind of request, reply, text operation or waiting request is such a change to ADR 0003 ("A new command adds no kind of request"), so the build stops and brings Dickson the generic operation it lacks, because 23 such kinds were added that each serve one behaviour (Dickson, 2026-11-20).
- Follow `books/dev/src/reference/testing.md`, testing each behaviour once, at the cheapest level that runs the real code in the order the real processes send, most often a recording of the real application replayed through Core (`cargo xtask replay`) against the captured speech, with a further level only for what that one cannot reach, and never through a copy or stand-in of Verbatim's own code, because Core's tests fed the foreground report before the foreground event, the reverse of the listener's order, and every one passed while new windows went unspoken (Dickson, 2026-11-17), and 121 mockapp tests ran a copy of the listener's check that two mutations of the real one pass (Dickson, 2026-11-20).
- A generated test is written only where a specific ordering across a hand-off is at risk (Dickson, 2026-11-10), against a much simpler reference model written from NVDA's rules and Dickson's recorded decisions, never from the design's or the code's rules and calling none of the code under test, by an agent other than the builder, committed before the implementation and shown failing on known defects, and never edited by the builder, as `testing.md` sets out, because generated tests of whole lifecycles found too little for their size, and models written by their builders were bent to the code (Dickson, 2026-11-20).
- Plan multi-step work as a few large builds, each grouping steps that touch the same code; before each, ask Dickson in one batch only the questions in his areas, state-table cells among them, and decide the rest with the reason recorded, matching NVDA where NVDA has an answer; a defect a review finds in the mechanism being built is fixed in that build, because on 2026-10-30 a cycle per step and questions asked one at a time took more than twelve hours for half of one design (Dickson, 2026-11-20).
- One build that adds or changes state is in flight at a time, pushed only when the logic of its design's state tables is covered by tests. A second builder may run beside it only on work that changes no state, each in its own target directory, because more exhausts the machine's disk and memory, and state changes built side by side were corrected against each other (Dickson, 2026-11-10).
- Builders run targeted tests while working and `cargo xtask ci` once at the end, again only when a rebase brought in code, because the dialog build ran it twelve times, seven failing. A brief points at documents rather than restating them, quotes the ADR decisions and limits the work must honour, which the parent checks before sending, and asks for a report of the outcome, the commits and the decisions; Sonnet does mechanical work such as triage and capture runs, Opus designs, builds and reviews, because the dialog build's reviewer, not told that Dickson had approved an ADR limit, reported its attribution to him as a must-fix (Dickson, 2026-11-20).
- A subagent whose brief cannot work, would be left partly undone, or would need anything beyond it stops and reports at once instead of improvising, and the parent never commits such a choice for later acceptance, because improvised choices committed as "pending" each cost a review and often a reversal. The session does not end a turn while work in scope remains, because such a turn idles until Dickson reads it; a question in his areas stops the build it arose in, nothing in that mechanism is built on a provisional answer and no ruling is written as his before he gives it, because on 2026-11-09 a build continued on provisional rulings and one question was decided six times (Dickson, 2026-11-10 and 2026-11-20).
- Run locally only the one to three end-to-end scenarios whose code path a change touches, through `cargo xtask e2e`, never a family by prefix or the full suite, and none whose failure `docs/flaky-tests.md` records: 3 runs each at a build's end, 1 to check a fix, 10 of a failed scenario to judge its fix (or `gh workflow run ci.yml -f scenario=<name> -f repeat=<n>`), at most 20 in a measurement, because a local batch of 42 scenarios on 2026-11-19 took an hour repeating what GitHub runs from the push anyway. Builder subagents end at unit tests and `cargo xtask ci`, and the parent runs the scenarios, one batch at a time from one background script, because agents that waited on the desktop with a large context spent hours polling and fought over it (Dickson, 2026-11-20).
- Push after each finished build once its review's fixes are in and `cargo xtask ci` and its scenarios pass locally, carry on while GitHub runs, and read every push's finished run, triaging each failure before the next push, because on 2026-11-19 five pushes went out over a unit test failing on GitHub that no one read. Before rerunning a failure or calling it interference, a flake or environmental, match it to `docs/flaky-tests.md`, read its artifacts and name the process or code responsible, because on 2026-10-30 two failures called interference were a unit test's stray console window and a real defect (Dickson, 2026-11-20).
- Judge every change on wake-ups, calls into other processes (a sequence of UIA calls batched into one remote operation where that saves round trips), locks, measured processor time and work that grows with the application, as well as latency, raise none on the event or speech path unless that is its purpose, and treat an allocation, a copy or a local call as no cost to design around unless a measurement shows it matters, except where `books/dev/src/explanation/design/ownership.md` forbids it (Dickson, 2026-11-04), because the dialog wait's first build woke the listener's event thread on every cancel until its review caught it. Measure wake-ups and processor time at each milestone's end, and inside a build only when it adds a thread, a timer or a message on the event or speech path, because three builds' measurements showed no change beyond the spread between runs (Dickson, 2026-11-10 and 2026-11-20).
- Studies, reviews, design drafts, run logs and measurement records stay in the session's scratchpad. Apart from the captures and recordings tests cite, something enters `experiments/` only as the cited evidence for a decision still in force, and only the part cited; a new file there or in `docs/design/` is proposed to Dickson before it is committed; and once its work is built, what nothing cites is deleted, because `experiments/` came to hold 1.1 MB that nothing cites and four built design files stayed the home of live rules (Dickson, 2026-11-20).
- Clean up: stop the processes you started, remove merged worktrees with their target directories, delete large traces once read, and release held keys, because on 2026-10-29 kept worktree targets filled the C: drive and leftovers break the next run (Dickson, 2026-11-20).
- Estimate time from measured durations, such as a scenario's run time in its log, because a guessed hour was twenty minutes.
- A new standing rule replaces or merges an existing one and names its incident in one clause, and other documents point at a rule rather than restate it; at each milestone's end, the rules that can name no defect they prevented are proposed to Dickson for removal, because each incident added a rule as each failure added a mechanism (Dickson, 2026-11-10), and on 2026-11-20 15 of 32 rules named no incident and restated copies contradicted them (Dickson, 2026-11-20).

## Design principles

Every design brief and review checks these; the ownership refactor (`books/dev/src/explanation/design/ownership.md`) records the history behind them.

- A decision is made by a process that sees, in order, every fact it depends on. A design lists each decision made outside Core with those facts and who sees them. A reader deciding from its own last read, where the fact is Core's or another reader's, is guessing: a guess that can only cost calls is allowed and marked as one; a guess that can change what is spoken is not built, and Core never corrects a reader by asking it again, because the readers' ancestry cache needed Core's check, a live re-read and an ordered queue (Dickson, 2026-11-10).
- One owner and one representation per fact: logic is a pure reducer with calls as its effects, and no process or thread judges a copy of another's state; inside one reducer, a lifecycle is one explicit state value, a type whose variants carry the data valid in them, never a combination of flags, optional fields, stamps and lookups in other records. A design that adds a lock, a shared flag, a second writer or a copied fact says why the hand-off cannot be removed instead, because copied state judged in two places caused the focus pipeline rework's fix rounds.
- Make invalid states unrepresentable, and parse rather than validate: a state that must not occur has no way of being written, in a reducer's state as in a message between processes, and input is turned once, at the boundary, into a type that can hold only what is valid, so that no later code checks it again (Dickson, 2026-11-09).
- Write no concurrency by hand: no raw pointers in posted messages, custom lock-free structures, or flags with fences; where a hand-off stays, use plain events, channels or locks, or a well-tested crate checked from its source, because each hand-written hand-off grew its own races, and the hook's went through four designs before it was deleted.
- Count the lifecycle states a design adds (re-dispatch, slots, holds, waiter tables, refused results) and have its review ask whether each can be removed, because the outpost reducer removed its races but its added bookkeeping produced all eight of its later defects. The design lists the waiting states, messages, timers and lifecycles held in two places that it adds and removes; a change made to save calls, wake-ups or time that adds any of them needs a measurement showing a budget missed without it (Dickson, 2026-11-10).
- A wake is decided by reading the state when the decision is made, never by assuming the other thread's state, because a push that skipped its wake when the lane looked busy lost wakes.
- A waiter on an event two conditions share checks its own condition again, and no test assumes only one setter, because the mixer's room test failed on GitHub's runner for that reason.
- A COM object is released only on a thread allowed to block, never on one that must stay responsive, because a release can call into a slow application.
- A loop never times a wake it will not act on, because the outpost's reducer spun at full processor time on a past wake.
- Every request and waiter has exactly one answer path, including after abandonment and re-dispatch, best a token whose drop answers it, because the settle waiters were lost twice that way.
- State about an owner (an outpost generation, an application's process, a terminal, a reading thread's application) lives in that owner's record, so its ending drops it; every stage of a lifecycle emits its ending, including stages before the peer exists; and a check against an ended owner's ids is tested.
- Where a fact can be both committed and in flight (applied and waiting, held, pending), the design names the two versions as separate facts, after NVDA's own split where it has one (its focus object and its last queued focus), and every rule says which version it judges.

## NVDA provenance

The crates fall into three kinds, each listed in `xtask/src/tiers.rs`, where a new crate is classed. The platform-neutral crates, which are `verbatim-model`, `verbatim-core`, `verbatim-speech`, `verbatim-config`, `verbatim-i18n`, `verbatim-input`, `verbatim-audio`, `verbatim-text`, and `verbatim-ext-api`, contain only original code, so that tier's licensing does not depend on NVDA's. Implement their behavior from the parity ledger under `docs/parity/` and the prose under `docs/nvda/`, never by translating NVDA source, and cite those docs in comments rather than NVDA file paths, function names, or line numbers. They never depend on a GPL-tier crate or on the Windows bindings; the hook thread and the WASAPI sink live in `verbatim-input-windows` and `verbatim-audio-wasapi` for that reason, and `cargo xtask ci` fails if the rule is broken. NVDA's spoken vocabulary, messages, and key layouts are deliberately matched for user familiarity and are fine to use; NVDA's non-English translations are never imported.

The logic crates, `verbatim-reader-rules`, `verbatim-outpost-logic` and `verbatim-listener-logic`, are in the GPL tier and may hold ported behaviour, but depend on no Windows crate and not on the Windows bindings, so their logic builds and is tested on any host. The Windows-specific crates are GPL like NVDA and may port NVDA code freely. A role's crates (`verbatim-outpost` with `verbatim-outpost-logic`, `verbatim-listener` with `verbatim-listener-logic`, and `verbatim-supervisor`) depend on no other role's. Ported code never moves from a GPL-tier crate into a platform-neutral one, and NVDA-core behavior destined for the reducer, such as browse mode, review modes, or symbol processing, is written from the parity docs rather than ported.

## Coding Standards

We use Rust 2024 edition.

Arm64 is a first-class target. Builds and tests always use the host's own architecture (no command names a target), so ARM64 is built and tested on an ARM64 machine, which GitHub Actions provides (the `ci-arm64` job); this machine is x64. Two stated exceptions, since neither builds a binary or runs a test: a check-only `cargo check` or `cargo clippy` with `--target x86_64-unknown-linux-gnu` on this machine, to check a crate's Linux build, and the tier check's `cargo metadata` with no platform filter, which reads every target's graph so its answer does not depend on the host.

Use Clippy with the pedantic lint group from the start. Public Rust APIs should have doc comments so the workspace can be browsed with Rustdoc.

Code reaches no fallback that could only be a logic bug: a miss is removed by construction, or passed up as an error, never defaulted silently.

We are using GitHub actions for CI.

## Commands

`cargo xtask ci` is the standard check, and exactly what GitHub Actions runs for a change to anything but Markdown files, `docs/` and `books/` (a documentation-only change runs only `cargo xtask docs` there): the tier check (every workspace member is classed in `xtask/src/tiers.rs`, and the graph keeps the tiers' rules under NVDA provenance, for every target, over normal and build edges), a check that the generated `crates/workspace-hack` crate is current (it needs `cargo install cargo-hakari --locked`; after adding a package or changing a third-party dependency, run `cargo hakari generate` and `cargo hakari manage-deps`, as `books/dev/src/how-to/setup.md` explains), a check that every document's links and backticked repository paths resolve (`cargo xtask docs`), rustfmt, clippy (pedantic via workspace lints, warnings denied), and unit tests, all for the host's architecture and into `target/debug`, the same output the end-to-end suite uses. On a Linux host it runs the tier check, the scans and the documentation check, then Clippy and unit tests for the crates listed in `LINUX_CRATES` (`xtask/src/main.rs`); GitHub Actions runs it there as the `ci-linux` job on `ubuntu-latest`, and the documentation-only check also runs on Linux. On Linux xtask has only `ci`, `docs`, `replay`, `e2e-plan` (which sizes the end-to-end groups in the `plan` job) and `coverage` (which merges a coverage run's levels in the `coverage` job); every other command is Windows-only.

`cargo xtask park` moves this Remote Desktop session onto the console, unlocked, so a local end-to-end run works with no RDP client connected. It needs a one-time, elevated `vm\scripts\Register-VerbatimParkTask.ps1`, and disconnects any connected RDP client, so run it only when Dickson is away or has agreed.

The end-to-end suite runs against this machine, or another one through `--endpoint` (`books/dev/src/explanation/architecture.md`, section 14), by pointing it at a locally running `verbatim-agent`. It launches a real Verbatim and injects real keystrokes, so it takes over the desktop while it runs and does nothing useful on a locked one; `books/dev/src/how-to/e2e.md` has the details. Run scenarios locally with `cargo xtask e2e <scenario>... --runs <n>`, which builds and starts the agent, runs each scenario and ends the agent (`books/dev/src/how-to/e2e.md`); the standing rules say which scenarios, and GitHub's run from the push is the wider check.

The `port` skill (`/port <scope>`, in `.claude/skills/port/`) is the protocol for porting an NVDA behavior or subsystem; its `references/` folder holds the brief template every subagent brief is written from.

The GUI's wxWidgets is built from source by `verbatim-gui`'s build script the first time anything builds that crate: it downloads the pinned release, builds static libraries with CMake (Ninja on x64), and keeps them in `target/wxwidgets`, or under `VERBATIM_WX_DIR` when that is set, so later builds reuse them. Nothing has to be set up by hand beyond CMake and the Visual Studio C++ tools.

Work on main, with no pull requests or feature branches unless asked, so that every session and subagent builds on the same history. When a scenario is added, removed or changes length, run `cargo xtask e2e-durations` once its GitHub run finishes and commit the table.
