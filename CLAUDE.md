# CLAUDE.md

## What this repository is

Verbatim: a screen reader for Windows 11 (x64 and ARM64), written in Rust.

- `books/dev/src/explanation/architecture.md` — decisions of record, read this before proposing any design or implementation work.
- `docs/roadmap.md` — the milestones ahead, completed milestones are archived in `docs/roadmap-done.md`.
- `books/` — the documentation published to GitHub Pages, one mdBook per book, each arranged after Diataxis (tutorials, how-to guides, reference, explanation): `books/dev/` the Development guide, `books/extensions/` the Extensions guide, `books/user/` the User guide. A page joins its book's `SUMMARY.md`, and names anything outside its book, an agent-only document included, by its full GitHub address, because the site carries nothing else (`cargo xtask docs` checks both).
- `docs/` — the working documents only agents read, never published: the roadmap, the design records of work not yet built, the parity ledger, `docs/nvda/` and the flaky-test list. `docs/readme.md` is the index of both, with reading paths; `books/dev/src/reference/glossary.md` defines Verbatim's invented vocabulary.
- `books/dev/src/reference/crates/` — the reviewer's guide to the implemented crates, one file per crate (`books/dev/src/reference/crates/readme.md` is the index): what each does, its public API, and how the intricate parts work. Keep the file for a crate current when its public API changes.
- `books/dev/src/how-to/readme.md` — how to actually drive this project, with the interactive-session rule and an index of the guides beside it in `books/dev/src/how-to/`: setup, `verbatim-inspect` against a running instance, `mockapp`, measuring, the end-to-end suite, NVDA captures, and the traps that cost us time (`troubleshooting.md`). `books/dev/src/how-to/vm.md` covers every `cargo xtask vm` verb and rebuilding the golden image.
- `books/dev/src/reference/testing.md` — the testing standard every test must meet: one fixed target and code path, exact assertions, waits only for evidence, and no hidden failures. Read it before writing or changing any test, and check every test change against it.
- `books/dev/src/reference/test-coverage.md` — every gesture and user-facing feature, with the tests that cover it at each level and the gaps still open.

`nvda/` is the NVDA screen reader vendored as a git submodule **for reference only** (IA2 IDL under `nvda/include/ia2`, app modules under `nvda/source/appModules`, design docs under `nvda/projectDocs`). Never modify anything under `nvda/`; Verbatim is informed by NVDA but not constrained by its architecture.

## Writing conventions

All documentation, comments, and commit messages in this repo must read well with a screen reader, in both rendered and source form:

- No ASCII-art diagrams, box drawings, or arrow chains.
- Documents describe the present. When a mechanism changes, replace its description rather than appending a dated note or keeping the old text beside the new; history lives in git and the commit messages. A decision of record keeps its date and an amended-on line, but one current statement. A rule that exists because something went wrong keeps one sentence of why, not the narrative. A superseded design record is archived or deleted, never kept in place with a banner.
- Design documents state the current model, its rules each with a brief reason, its limitations, and the important performance figures such as latency and memory; evidence lives in `experiments/` and history in git, so that a document stays short enough to be read whole. Once its work is built, a design document becomes two: an explanation of how it works today in `books/dev/src/explanation/design/`, with no alternatives or history, and a numbered decision record in `books/dev/src/reference/adr/` with the problem, the options weighed and why each was taken or rejected, the decision with its date, and its limits; the mechanism's details stay in the crate guide (Dickson, 2026-11-07).
- Reports define any invented term on first use or avoid it, lead with the required decisions

## Decisions Dickson owns

Dickson takes the decisions in these areas himself; every other decision is Claude's, made with its reason recorded where the decision lives and checked by the adversarial review, because splitting each decision between Dickson and Claude spread the responsibility without adding judgment (2026-11-01).

- The process and thread layout: which work runs in which process and on which thread (D9, D13).
- Architecture and high-level design
- Trust boundaries and accepted risks: which code is trusted, what is sandboxed, what extensions and native add-ons may do and how users approve them, and the posture for UIAccess and secure screens. The mechanisms that enforce them are the session's.
- What users hear: every deliberate difference from NVDA's speech, and every spoken behaviour NVDA has no answer for. Matching NVDA's captured speech needs no decision.
- Performance budgets: latency, idle wake-ups and processor time, memory, and how long silence is tolerated while an application hangs. How a budget is met is the session's.
- Public contracts: the extension API, the settings file format, the control and Remote protocols, and anything else people outside the project will depend on.
- Major dependencies and licensing: adopting or replacing a runtime, toolkit or engine, and the tier rules under NVDA provenance.
- Scope and order: what each milestone includes and which comes next.
- The working process: this file and `REVIEW.md`.

A decision outside these areas is delegated to Claude, but the user should still be told about it in case it needs to be overridden.

## Standing rules

These hold for every session and every subagent; a subagent brief points here rather than restating them.

- Fix root causes, never adding retries, sleeps, skipped cleanup, or self-termination to hide a race or failure; a workaround needs evidence that the proper fix is not enough, and is documented as one.
- Verify every claim about NVDA's behavior from the pinned source under `nvda/` or a live capture, and take spoken expectations only from captures
- A decision put to Dickson cites the pinned NVDA source for every claim about NVDA, and gives one concrete sequence with the exact speech under each option.
- The NVDA submodule pin must equal the installed NVDA build used for captures: the capture header prints the build, so compare it with `git -C nvda rev-parse HEAD` before a capture series and stop when they differ, because expectations come from captures and ported code from the pinned source, and both must describe the same NVDA.
- If a mechanism being implemented has 3 or more rounds of bug fixes, the design is likely flawed and continuing risks adding patches on top of workarounds. Pause and reassess whether to continue or if a redesign is required. Count the gaps a generated test finds in an approved design, or between a model and its prototype before approval, as fix rounds. When a build passes twice its estimate, stop and report to Dickson with options.
- Follow `books/dev/src/reference/testing.md` (one fixed target and code path, exact assertions, waits only for evidence, no branching on the environment, no alternative expectations, no substring matches), because a test that accepts two outcomes proves neither.
- When adding or removing a gesture, a user-facing feature or a test, update its row in `books/dev/src/reference/test-coverage.md`.
- Run the end-to-end scenarios related to a change, and the full suite only for wide-ranging changes or when asked, because the full suite takes a long time and takes over the desktop. Related scenarios are the few, usually one to three, whose code path the change touches, never a whole family by prefix; run each 3 times at the end of a build, once to check a fix within it, 10 times only for a scenario that failed, to judge its fix, and at most 20 in a measurement, because a family-wide batch of 77 scenarios took 45 minutes a run. Leave out a scenario whose failure `docs/flaky-tests.md` already records, and match a new failure to its entries before rerunning it or running a baseline.
- Before calling an end-to-end failure interference, a flake or environmental, read its artifacts and name the process or code responsible, because on 2026-10-30 two failures called interference were a unit test's stray console window and a real defect.
- Work on main, with no pull requests or feature branches unless asked, so that every session and subagent builds on the same history.
- Push after each finished build, once `cargo xtask ci` and its related scenarios pass locally, and check the GitHub run.
- Confirm a design before building on it, including all edge cases, where each part runs and the exact speech expected; while a design study or decision is open, build nothing that depends on it. Every design gets one adversarial review by a subagent before implementation, which breaks it with code-level sequences.
- A design that adds or changes state includes a table of its states and the rules that read them, each cell saying what the rule does in that state; the adversarial review checks every cell and derives a sequence for each it doubts. The table is written before any generated test's model; every cell the ADR does not decide goes to Dickson in one batch, and modelling starts only after he answers.
- A generated test is written only where a specific ordering across a hand-off is at risk (Dickson, 2026-11-10), because generated tests of whole lifecycles found too little for their size. It compares the mechanism after every step with a much simpler reference model, written from NVDA's rules (through the parity docs) and Dickson's recorded decisions and limits, never from the design's or the code's own rules, by an agent other than the builder, and committed with its world before the implementation. The world generates what real applications send and uses none of the code's rules, the model has no exemptions or skipped comparisons, and its commit shows it failing on known defects. It runs against a prototype before the build is approved, and every seed must pass. The builder never edits it: a disagreement the builder believes is the model's fault stops the build for a decision, and a later change to the model is its own commit, reviewed on its own, or checked by the parent on its diff when it is a few lines. The model's author changes nothing beyond its brief; a rule it believes is needed stops the work for a decision, as a builder's does. A generated test covers interactions whose combinations matter; a single rule or fixed sequence gets a hand-written test, and the review weighs the model's size against the code it tests. Because models written by their builders were bent to the code.
- Review each completed step, not each commit, as `REVIEW.md` says, because on 2026-10-21 reviewing every commit with no stopping rule produced contradictory findings and sixteen rounds on one area.
- Plan multi-step work as a few large builds, each grouping steps that touch the same code, with one design document and one implementation review, rather than a full cycle per small step; ask in one batch before building it, each of the build's open questions ("Decisions Dickson owns"), and decide the rest, matching NVDA where NVDA has an answer, with the reason recorded; defects a review finds in the mechanism being built are fixed in that build, not deferred as follow-ups. Because on 2026-10-30 a cycle per step (build, ci, review, fix, re-review, ten-run scenario batches) and questions asked one at a time took more than twelve hours for half of one design.
- Builders run targeted tests while working and `cargo xtask ci` once at the end, again only when a rebase brought in code; use Sonnet for mechanical work (failure triage, nits commits, ledger updates, capture runs) and Opus for designs, builds and reviews; keep briefs short by pointing at documents, and ask for reports capped at the outcome, the commit and the decisions, because restated briefs and long reports cost tokens on every hand-off.
- Use UIA remote operations wherever a sequence of UIA calls would benefit, and audit this whenever UIA code changes, because each separate call is a cross-process round trip.
- Judge every change on wake-ups, calls into other processes, locks, measured processor time and work that grows with the application (a document, a history, a tree) as well as latency, and raise none on the event or speech path unless that is the change's purpose, because a latency figure alone hides a cost paid on every event; an allocation, a copy or a local call is not a cost to design around or to record unless a measurement shows it matters, because code shaped to avoid one adds complexity for nothing, except where `books/dev/src/explanation/design/ownership.md` forbids it (no lock on the hook thread, no allocation on the audio thread). Record a cost in `books/dev/src/reference/performance.md` only when it is on the event or speech path or was measured to be slow; a command's own calls are pinned by a call-count test, not written in the ledger (Dickson, 2026-11-04).
- Clean up: stop the processes you started, remove merged worktrees, delete large traces once read, and release held keys, because leftovers break the next run and fill the disk.
- Studies, reviews, design drafts, run logs and measurement records are kept in the session's scratchpad, not the repository. Something enters `experiments/` only when a lasting document cites it as the evidence for a decision still in force, and only the part it cites; a new file in `experiments/` or `docs/design/` is proposed to Dickson before it is committed. When the work it served is finished, what nothing cites is deleted.
- Do not stop while work in scope remains; record a question for Dickson and continue with everything it does not block, because a turn that ends on a question idles until he reads it.
- Keep ported NVDA code in the GPL-tier crates, the logic crates and the Windows-specific ones, and write the platform-neutral crates from the parity docs (see "NVDA provenance"), so that the platform-neutral tier's licensing does not depend on NVDA's.
- At most two subagents build at once on Dickson's machine, each in its own target directory, because more exhausts its disk and memory.
- Every brief for a design, model or build quotes the ADR decisions and limits it must honour, and the parent checks the brief against them before sending it.
- A subagent that finds its brief's design cannot work, that would leave any part of its brief undone, or that wants to do anything beyond its brief, stops and reports at once instead of improvising, and the parent never commits such a choice for later acceptance, because improvised choices committed as "pending" each cost a review and often a reversal.
- Builder subagents end at unit tests and `cargo xtask ci`; the parent runs the end-to-end scenarios, one batch at a time from one background script, because agents that waited on the desktop with a large context spent hours polling and fought over it.
- Measure each build's wake-ups and processor time before and after, inside the build, because a build's cost found later is paid on every event meanwhile.
- Estimate time from measured durations, such as a scenario's run time in its log, because a guessed hour was twenty minutes.
- When adding, removing or changing the length of an end-to-end scenario, run `cargo xtask e2e-durations` once its GitHub run finishes. Commit the table.

## Design principles

Every design brief and review checks these; the ownership refactor (`books/dev/src/explanation/design/ownership.md`) records the history behind them.

- One owner and one representation per fact: logic is a pure reducer with calls as its effects, and no process or thread judges a copy of another's state; inside one reducer, a lifecycle is one explicit state value, a type whose variants carry the data valid in them, never a combination of flags, optional fields, stamps and lookups in other records. A design that adds a lock, a shared flag, a second writer or a copied fact says why the hand-off cannot be removed instead, because copied state judged in two places caused the focus pipeline rework's fix rounds.
- Make invalid states unrepresentable, and parse rather than validate: a state that must not occur has no way of being written, in a reducer's state as in a message between processes, and input is turned once, at the boundary, into a type that can hold only what is valid, so that no later code checks it again (Dickson, 2026-11-09).
- Write no concurrency by hand: no raw pointers in posted messages, custom lock-free structures, or flags with fences; where a hand-off stays, use plain events, channels or locks, or a well-tested crate checked from its source, because each hand-written hand-off grew its own races, and the hook's went through four designs before it was deleted.
- Count the lifecycle states a design adds (re-dispatch, slots, holds, waiter tables, refused results) and have its review ask whether each can be removed, because the outpost reducer removed its races but its added bookkeeping produced all eight of its later defects.
- A wake is decided by reading the state when the decision is made, never by assuming the other thread's state, because a push that skipped its wake when the lane looked busy lost wakes.
- A waiter on an event two conditions share checks its own condition again, and no test assumes only one setter, because the mixer's room test failed on GitHub's runner for that reason.
- A COM object is released only on a thread allowed to block, never on one that must stay responsive, because a release can call into a slow application.
- A loop never times a wake it will not act on, because the outpost's reducer spun at full processor time on a past wake.
- Every request and waiter has exactly one answer path, including after abandonment and re-dispatch, best a token whose drop answers it, because the settle waiters were lost twice that way.
- State about an owner (an outpost generation, an application's process, a terminal, a reading thread's application) lives in that owner's record, so its ending drops it; every stage of a lifecycle emits its ending, including stages before the peer exists; and a check against an ended owner's ids is tested.
- Where a fact can be both committed and in flight (applied and waiting, held, pending), the design names the two versions as separate facts, after NVDA's own split where it has one (its focus object and its last queued focus), and every rule says which version it judges.

## NVDA provenance

The crates fall into three kinds, each listed in `xtask/src/tiers.rs`, where a new crate is classed. The platform-neutral crates, which are `verbatim-model`, `verbatim-core`, `verbatim-speech`, `verbatim-config`, `verbatim-i18n`, `verbatim-input`, `verbatim-audio`, `verbatim-text`, and `verbatim-ext-api`, contain only original code, so that tier's licensing does not depend on NVDA's. Implement their behavior from the parity ledger under `docs/parity/` and the prose under `docs/nvda/`, never by translating NVDA source, and cite those docs in comments rather than NVDA file paths, function names, or line numbers. They never depend on a GPL-tier crate or on the Windows bindings; the hook thread and the WASAPI sink live in `verbatim-input-windows` and `verbatim-audio-wasapi` for that reason, and `cargo xtask ci` fails if the rule is broken. NVDA's spoken vocabulary, messages, and key layouts are deliberately matched for user familiarity and are fine to use; NVDA's non-English translations are never imported.

The logic crates, `verbatim-reader-rules`, `verbatim-outpost-logic` and `verbatim-listener-logic`, are in the GPL tier and may hold ported behaviour, but depend on no Windows crate and not on the Windows bindings, so their logic builds and is tested on any host. The Windows-specific crates are GPL like NVDA and may port NVDA code freely. A role's crates (`verbatim-outpost` with `verbatim-outpost-logic`, `verbatim-listener` with `verbatim-listener-logic`, and `verbatim-supervisor`) depend on no other role's. Ported code never moves from a GPL-tier crate into a platform-neutral one, and NVDA-core behavior destined for the reducer, such as browse mode, review modes, or symbol processing, is written from the parity docs rather than ported.

## Coding Standards

We use Rust 2024 edition.

Arm64 is a first-class target. Builds and tests always use the host's own architecture (no command names a target), so ARM64 is built and tested on an ARM64 machine, which GitHub Actions provides (the `ci-arm64` job); this machine is x64. Two stated exceptions, since neither builds a binary or runs a test: a check-only `cargo check` or `cargo clippy` with `--target x86_64-unknown-linux-gnu` on this machine, to check a crate's Linux build, and the tier check's `cargo metadata` with no platform filter, which reads every target's graph so its answer does not depend on the host.

Use Clippy with the pedantic lint group from the start. Public Rust APIs should have doc comments so the workspace can be browsed with Rustdoc.

Code reaches no fallback that could only be a logic bug: a miss is removed by construction, or passed up as an error, never defaulted silently.

We are using GitHub actions for CI.

## Commands

`cargo xtask ci` is the standard check, and exactly what GitHub Actions runs for a change to anything but Markdown files, `docs/` and `books/` (a documentation-only change runs only `cargo xtask docs` there): the tier check (every workspace member is classed in `xtask/src/tiers.rs`, and the graph keeps the tiers' rules under NVDA provenance, for every target, over normal and build edges), a check that the generated `crates/workspace-hack` crate is current (it needs `cargo install cargo-hakari --locked`; after adding a package or changing a third-party dependency, run `cargo hakari generate` and `cargo hakari manage-deps`, as `books/dev/src/how-to/setup.md` explains), a check that every document's links and backticked repository paths resolve (`cargo xtask docs`), rustfmt, clippy (pedantic via workspace lints, warnings denied), and unit tests, all for the host's architecture and into `target/debug`, the same output the end-to-end suite uses. On a Linux host it runs the tier check, the scans and the documentation check, then Clippy and unit tests for the crates listed in `LINUX_CRATES` (`xtask/src/main.rs`); GitHub Actions runs it there as the `ci-linux` job on `ubuntu-latest`, and the documentation-only check also runs on Linux. On Linux xtask has only `ci`, `docs`, `replay`, `e2e-plan` (which sizes the end-to-end groups in the `plan` job) and `coverage` (which merges a coverage run's levels in the `coverage` job); every other command is Windows-only.

`cargo xtask vm <cmd>` drives the Hyper-V harness: `create` (Packer-built golden image, imported, deployed to, checkpointed), `start`, `stop`, `restart`, `restore`, `deploy`, `test` (the end-to-end suite against the VM), `logs`, and `delete`. Guest credentials come from a `.env` at the repo root, which is never committed. See `books/dev/src/how-to/vm.md`.

`cargo xtask park` moves this Remote Desktop session onto the console, unlocked, so a local end-to-end run works with no RDP client connected. It needs a one-time, elevated `vm\scripts\Register-VerbatimParkTask.ps1`, and disconnects any connected RDP client, so run it only when Dickson is away or has agreed.

The end-to-end suite also runs without a VM, against this machine, by pointing it at a locally running `verbatim-agent`. It launches a real Verbatim and injects real keystrokes, so it takes over the desktop while it runs and does nothing useful on a locked one; `books/dev/src/how-to/e2e.md` has the details. Build and start the agent with `cargo build -p verbatim-agent` and `target\debug\verbatim-agent.exe --bind-address 127.0.0.1 --port 44001`, set `$env:VERBATIM_E2E_ENDPOINT = '127.0.0.1:44001'`, then run one scenario with `cargo test -p verbatim-e2e --test e2e -- --ignored --exact <name> --test-threads=1`, or the full suite with `cargo test -p verbatim-e2e --no-fail-fast -- --ignored --skip demo_ --skip measure_ --test-threads=1`.

The full suite takes a long time, so don't run it by default. For a change, run the few scenarios that exercise the changed code path, such as `conhost_typing` for a change to typed-character echo in a console; a family by prefix (all `windows_terminal_` and `conhost_` scenarios) only for a change every scenario of it sees. Keep full runs for wide-ranging changes, such as changes to the harness, to how outposts start and stop, or to behaviour every scenario sees.

The `port` skill (`/port <scope>`, in `.claude/skills/port/`) is the protocol for porting an NVDA behavior or subsystem; its `references/` folder holds the brief template every subagent brief is written from.

The GUI's wxWidgets is built from source by `verbatim-gui`'s build script the first time anything builds that crate: it downloads the pinned release, builds static libraries with CMake (Ninja on x64), and keeps them in `target/wxwidgets`, or under `VERBATIM_WX_DIR` when that is set, so later builds reuse them. Nothing has to be set up by hand beyond CMake and the Visual Studio C++ tools.
