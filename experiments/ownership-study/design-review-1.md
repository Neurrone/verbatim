# Adversarial review of docs/design/ownership.md: 9 Important

1. Core, title rule: it picks "the chain's entry carrying top_level_client or the top below the desktop" and compares with the top-level handle of the last focus taken. Popup menus (#32768), combo lists (ComboLBox) and Windows Forms ToolStripDropDowns are top-level windows of their own. Shift+F10 then Escape in the Windows Forms text box: the record holds the menu's handle, the edit's top is the form, so the form's title is spoken on every menu or list close (today silent: is_presentable_container Pane => top_level_client, false via accParent). A named popup (Windows Forms dropdown) is spoken on entry although is_presentable_container silences Menu "as in NVDA". When the reader omitted the window (verbatim-uia/src/client.rs ~1135 crosses non-presentable UIA ancestors) the "top below the desktop" is an inner container. The rule must name the window's own entry (handle == top_level) and say what happens with popups and owned windows, with tests for return from an owned popup and a named popup menu.

2. The outposts, followed focus: "Core refuses only for a reason across applications" is false. reduce_focus_changed (reduce.rs ~938) refuses a foreground report for the window that already holds the focus, within one application. Core holds f in W; the outpost reports F(W) with no focus after (foreground back from a popup that took no focus); Core refuses; the outpost's newest report and followed focus is W's window node; Space toggles f; f's state change is targeted against W, never read, nothing spoken (today Held is f, spoken). List this refusal and correct it, or redefine the followed focus.

3. The listener: removing HeldElements leaves NVDA's menu-opening comparison without a subject. judge_before_reading (focus_read.rs ~1765-1800) compares a MenuOpened sender with held_elements.held(); a failed comparison drops the event (COMPARISON_FAILED). Specify what it compares with.

4. Message kinds, configuration: the design says a receiver can tell a judgement made under an older generation but not what it does. The backend override changes for X; the listener on gen 1 skips an MSAA focus by the class table, its drop names gen 1; the outpost on gen 2 cannot re-judge (the UIA element cannot leave the listener, the event was never read); the only correction would be a focus-now query, unstated. "Applied between two events" is undefined for the listener's concurrent reading threads (a read started under gen 1 can end after gen 2). M5's "outpost's rules apply to its recovery reads under the same generation" requires keeping older tables, not designed. Undefined whether anything (the gap record) waits on a drop judged under an older generation.

5. Merging only for kinds that declare it: the stated test cannot hold for kept merges. The listener's Waiting removes the older fact of a key (MSAA focus events per thread) and pushes the newer to the back: A1, B1, A2 becomes B1, A2, reordered, A1 never reduced, so "reducing the merged message equals reducing both in order" is false. Waiting also enforces ForwardingEnded and idle-answer rules, so "every queue states only its bound" is wrong. Define the equivalence (for example what Core concludes after cuts) and name the exemptions.

6. The outpost's reducer, workers and call programs: node id minting and identity contradict publication at the bound and the walk's stop. Today the walk interns objects as it reads; bound.rs FocusProgress holds NodeSnapshots with ids and the watchdog builds the chain from them. The design says results carry objects in, the reducer mints ids, workers never see reducer state; but at the bound the reducer must publish ancestors whose objects are still in a stuck worker's hands, with no ids; and the walk's stop at a container of the previous chain, by NVDA's MSAA equality, needs identity decided mid-walk, while the call program stops only "at these windows". Either identity runs in the worker or walks run to the top (more calls, breaking pinned call_counts). This is the four-round area (c47d57ae, 6dbcca25, 2bd69a85, 8a087fe7) and must be specified.

7. Workers and call programs, console caret poll: misdescribed. Today (caret_poll.rs, 463f2ef9) each 5 ms read is an intake wake (Item::Wake), interleaved with other entries, ending on a check its own or one an event makes, up to BOUND 50 ms. As one call program looping on the worker's wait, the worker cannot see the events that end it; it runs to 50 ms while the next key's caret read or a terminal read waits behind it (conhost 30 ms autorepeat delays every key). Each tick as a reducer timer adds 2 wake-ups per 5 ms; a stop signal from reducer to worker is an unnamed mechanism. Specify.

8. One route for user input: fencing the lock key's announcement departs from NVDA without a capture. NVDA's reportExtra calls core.callLater(30, _reportToggleKey) then ui.message (nvda/source/keyboardHandler.py 740-750): a key pressed within 30 ms cancels first and "caps lock on" is still heard afterwards. The design calls today's identical behaviour a bf4fbedb defect and adds a test silencing it; bf4fbedb's reason does not apply to a delayed message.

9. Enforcement claims that Rust or the named check cannot deliver as written: Rust cannot restrict construction of an enum variant to a module (needs a private-field token); children's Ready/Ended are built outside the owner; with M4.4's fold-in the enums are in a platform-neutral crate where a token constructor cannot be private to a module in verbatim-outpost. The CallToken borrow rule works only if every application call, including Release of a clone taken under the guard, goes through wrappers taking &mut CallToken; raw windows-rs methods take &self and no wrappers are named. A responder answering in Drop held in a pure reducer's state sends a message inside a transition, breaking purity and replay, and the textual ownership check (locks, threads, Instant::now) does not catch channels or helpers in other modules.

## Nits
- MSAA repeats and foreground changes read in full (about 20 calls) have no stated cost; REVIEW.md requires the ledger to state it.
- The first KEY_ORIGINS sequence (hook removed past LowLevelHooksTimeout by a scan of 1,024 entries) is implausible; the real risks are priority inversion and the lock-key miss.
- "Kept: the menu opening's pending focus" is listed under Core but lives in the listener (Readers::focus_pending).
- "One node per window handle" is undefined (window object vs client object of one handle, UIA host element vs MSAA client) and sits in the messages build although identity belongs to the reducer build, so identity code changes twice.
- M6.1's cancel bound to the call's ticket needs the canceller to hold the ticket lock across CoGetCancelObject and Cancel, and the worker to call CoEnableCallCancellation.
- GetKeyState moves from the router thread to the reducer's shell; thread input state differs, so check on the new thread or use GetAsyncKeyState.
- The router's behind_toggles ordering of handled-input marks and idle waiters is not carried into the input build.
- The supervisor's lagging copy of attention is kept without saying whether it is ordered or keyed.
- The stale rule's known limit (foreground report stamped at confirmation) gives no frequency or evidence.
- The title rule's speech "as a foreground focus" must not move attention; unstated.
