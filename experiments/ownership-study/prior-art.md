# Prior art for choosing change targets without Core's verdict

A read-only study, made on 2026-10-30 against main at 6f0d5ecd, of how other systems coordinate ownership of state across threads and processes, judged against the candidate rule in [the one judge build](../../docs/design/ownership.md): an outpost reads changes for every node of its unreleased reports, a node being released only when Core's `NodesHeld` acknowledges a later message position and does not list it. Nothing was built or run. Claims about Verbatim's code name the file they were read from; claims about other systems cite their sources, and anything not confirmed from a primary source is marked.

Terms: the release set is the set of nodes an outpost has not yet released. A carry is a message to Core that names a node. The superset rule is the candidate itself: the release set is always a superset of what Core holds, so a lag costs extra reads, never a missed change.

## What this study concludes

- The candidate is the standard pattern. Retaining a reference until the receiver acknowledges a message position later than the last message that carried it is how Java RMI's distributed garbage collector protects references in transit, how Birrell's network objects order dirty and clean calls, how game servers keep unacknowledged inputs, and how Wayland's `ack_configure` consumes configure serials. Every one of them is safe under the same three conditions, which Verbatim must hold too: positions only increase, every carry records its position (a node copied into a message without being recorded breaks it), and an acknowledgement reflects every message up to its position. Verdict: confirmed, with those three conditions as the rule's preconditions.
- No system studied has a simpler design for Verbatim's situation. Systems that avoid the problem do so in one of two ways that Verbatim cannot use. Chromium's renderer owns the DOM, so it sends every change of its whole tree and never needs to choose targets. NVDA and Orca run the verdict and the change filter on one thread, in one queue, so the filter is never behind the verdict. Verbatim's reads are cross-process calls into an application it does not own, and its verdict lives in another process, so the cheapest correct choice is a bounded superset, which is the candidate.
- The release lag is not one hop once `CoreFocus` is gone. `NodesHeld` is never written on its own: Core's shell leaves it in the writer's slot, and it rides on the next command written to that outpost, a request or the relay's ping within 3 seconds (`crates/verbatim-outpost/src/supervisor/writer.rs`, `leave_held`; `crates/verbatim-app/src/main.rs`, the `leave_nodes_held` call; `docs/design/communication.md`, step 11). Today `CoreFocus` is that next command on every judged focus. Without it, the old line stays in the release set for up to 3 seconds, not one round trip as the design's "Manageability" section says. Correctness holds (lag only adds reads), but the cost and the design's figure change. DCOM and RMI can piggyback their acknowledgements on slow pings because their only cost of lag is memory; Verbatim's cost is calls into the application, so the build should either write `NodesHeld` on its own after a judged focus changes the held set (the write `CoreFocus` costs today) or state the 3 second bound and its cost.
- Change delivery in UI Automation is itself a subscription, so the rule covers only half of the problem by itself. UIA property changes reach an outpost only through the event handler group on one element, as in NVDA's selective registration, so "read changes for every unreleased node" means nothing for a UIA node that has no group. The design already puts this to Dickson (removing the group on release rather than on the next focus). Prior art agrees with the design's recommendation: UIA documents event registration with a cache request as the way changes are seen, and Orca's history shows that whatever a screen reader does not subscribe to, it silently misses.
- Stale-request rejection by stamp, as X11 focus timestamps, Wayland serials, LSP document versions and Chromium's reset token do it, belongs in the authority, and the requester never needs the authority's state to make it work. That confirms Core's stale rule and the model's ban on the back-channel. Chromium's reset token adds one lesson Verbatim already follows: a stream that has gone out of sync is answered by a versioned reset, and a peer that needs too many resets is killed, the counterpart of an outpost's incarnation in every node id and kill-and-replace.

## Sequences that defeat the rule, or its preconditions

None defeats the rule for MSAA changes while its preconditions hold. These sequences break a precondition or fall outside the rule:

- A spliced ancestor. A walk that meets a known line copies its ancestors' snapshots without looking them up, so the report carrying them does not record their position (`docs/design/focus-pipeline-rework-remaining.md`, "A spliced ancestor released by `NodesHeld`"). An older acknowledgement then frees an ancestor that Core takes with the newer report, and its state changes are never read. This defect already exists, but the one judge build makes the rule depend on it more, and widens it: the design lets the walk stop at "every unreleased report's line", not only Core's line, so there are more lines to splice from. The fix, recording every spliced entry as carried and splicing only from entries still registered, is scheduled for the outpost's reducer build, after the one judge build. It should be a precondition of the one judge build, or built in it.
- UIA changes outside the one followed group. This is the shared-window case the design names, and any other case where Core holds a node that is not the newest report's: its UIA property changes are not delivered at all. The open question on removing the group at release answers it.
- A change between the read and the subscription. A UIA change raised after the listener read the focus and before the outpost adds the group is never delivered. NVDA has the same window, since it adds the group from its MTA thread after `event_gainFocus` (`nvda/source/NVDAObjects/UIA/__init__.py`, `event_gainFocus`; `nvda/source/UIAHandler/__init__.py`, `addLocalEventHandlerGroupToElement`). Verbatim's window is longer, since the read is in the listener and the group is added by the outpost after the fact is routed. This is a parity limit, not a defect of the rule, but worth measuring.
- Identity. The rule targets node ids, so it is only as good as the mapping from an event's element to a node. Two nodes for one element (defect A, one node per window) or a reused UIA runtime id kept under the old node (the keep-id fix) make a change resolve to a node Core does not hold, or the right node to the wrong element. Both are already scheduled in the focus pipeline rework; they are preconditions here too.
- The batch limiter. The limiter exempts only the newest focus's events from the 10-per-thread limit, as NVDA's `alwaysAllowedObjects` exempts only `lastQueuedFocusObject` (`crates/verbatim-outpost/src/outpost/intake.rs`, `admit`; `nvda/source/IAccessibleHandler/__init__.py`). In a flood, a change of an older unreleased node that Core still holds can be dropped. NVDA does the same for its own last queued focus, so this is parity and needs no change, but it is a case where the release set is not what decides.
- A replaced outpost. Core can hold nodes of an incarnation that no longer runs; nothing reads their changes until a new focus report arrives. This is the kill-and-replace boundary, not the rule.

The set should be defined as every node in the outpost's object store that is not released, minted and queued nodes included, not only nodes already written. Today a node is recorded when its message is queued and is not released while a message carrying it waits (`crates/verbatim-outpost/src/outpost/outbound.rs`, `take_releasable`, `report.waiting == 0`), which already gives that; the design's wording ("every node it sent") should match it.

## Chromium's accessibility across renderer processes

Mechanism. Each frame's renderer builds an accessibility tree and sends it to the browser process as atomic tree updates. The renderer's `AXTreeSerializer` keeps a mirror of the tree the client (the browser) has been sent, `ClientTreeNode` with an id, parent and children, and sends only what differs, so "it will never send an invalid update and the client tree will not break" ([ax_tree_serializer.h](https://chromium.googlesource.com/chromium/src/+/main/ui/accessibility/ax_tree_serializer.h)). On reparenting it finds the lowest common ancestor and resends its subtree. Each serialization is a Mojo call whose reply tells the renderer it may send more: "The browser will respond by invoking the callback specified by the renderer ... in order to notify the renderer that it can send additional updates" ([render_accessibility.mojom](https://chromium.googlesource.com/chromium/src/+/5ca86f30aacc0d858e71f7a32beedeee505d4e22/content/common/render_accessibility.mojom)). Focus across frames is the browser's alone: "only the browser is the source of truth when it comes to which window has focus"; each tree reports its own focused node, and any focus change in any tree, or of the focused window or frame, makes the browser recompute global focus by descending from the focused window through focused frames and fire a platform event only if the result differs from the last one computed ([How Chrome Accessibility Works, part 3](https://chromium.googlesource.com/chromium/src/+/main/docs/accessibility/browser/how_a11y_works_3.md)). That document names the race directly: focus events from two windows in different processes "could arrive at the browser process in either order".

The problem it solves: keeping a tree consistent across a process boundary without the browser telling the renderer anything about its own state, and deciding global focus where all the facts meet.

Failure modes. When the mirror and the real client tree disagree (duplicate ids, a bad parent link), the serializer resets: "This condition leads to performance problems. It will also reset virtual buffers, causing users to lose their place." The browser can also ask for a reset: "Tell the renderer to reset and send a new accessibility tree from scratch because the browser is out of sync. It passes a sequential reset token. This should be rare, and if we need to reset the same renderer too many times we just kill it. After sending a reset, the browser ignores incoming accessibility IPCs until it receives one with the matching reset token" (render_accessibility.mojom). On a new document the renderer stops expecting the old document's acknowledgement and invalidates its pending callbacks ([render_accessibility_impl.cc](https://chromium.googlesource.com/chromium/src/+/lkgr-android-internal/content/renderer/accessibility/render_accessibility_impl.cc), `DidCommitProvisionalLoad`). The serializer still carries an open bug where no common ancestor is found (crbug 442619489, in the header's TODO). I did not find a Chromium bug about lost changes from targeting, because Chromium does not target: it serializes every dirty node. The browser ignores a bundle with a stale reset token, or one for a frame that has since navigated, without counting it; the only trace is a verbose-level debug log, "Ignoring obsolete accessibility data." (`RenderFrameHostImpl::HandleAXEvents` in [render_frame_host_impl.cc](https://chromium.googlesource.com/chromium/src/+/main/content/browser/renderer_host/render_frame_host_impl.cc), read 2026-10-30).

Verdict for Verbatim:

- Confirms the split of global focus: per-process reports, one global judge, nothing sent back for a reader to judge against.
- Does not offer a simpler targeting rule. Chromium needs none, because reading its own DOM is cheap and in-process; Verbatim's reads are calls into an application. The candidate is the bounded version of Chromium's "send everything".
- Its serializer is the mirror image of the release protocol: the renderer keeps a model of what the browser has; the outpost keeps a model of what Core may hold. Chromium's protection against a wrong model is a versioned reset and a kill after too many; Verbatim's is the incarnation in every node id and kill-and-replace. Chromium found that a model which can be wrong needs a reset path; the release set has one for free, since a superset that is too large costs only reads.

## Distributed reference counting and leases

Java RMI's distributed garbage collector. A client that unmarshals a remote reference makes a `dirty` call; when it holds none, a `clean` call. Both carry a sequence number that "is used to detect and discard late calls to the garbage collector" and "should always increase for each subsequent call"; a failed dirty call must be followed by a "strong" clean so that the sequence number is remembered; references are leased and expire unless renewed ([java.rmi.dgc.DGC](https://docs.oracle.com/en/java/javase/21/docs/api/java.rmi/java/rmi/dgc/DGC.html)). References in transit are protected separately: the sender holds strong references to every remote object in a call's arguments or result until the receiver acknowledges, by a transport-level `DGCAck` carrying the result's id, or by the start of the response for arguments, or until `sun.rmi.dgc.ackTimeout`, 5 minutes by default ([DGCAckHandler.java, JDK 8](https://code.yawk.at/java/8/sun/rmi/transport/DGCAckHandler.java)).

Birrell, Evers, Nelson, Owicki and Wobber's network objects use the same dirty and clean calls with sequence numbers, so that a clean overtaken by a later dirty is ignored: "a sequence number is attached to each clean or dirty call", and "an incoming operation will be performed only if its sequence number exceeds this value; otherwise it has no effect" ([Distributed garbage collection for network objects, DEC SRC Research Report 116, 1993](https://web.archive.org/web/2020/https://www.hpl.hp.com/techreports/Compaq-DEC/SRC-RR-116.pdf), section 2).

DCOM keeps a remote object alive while its client pings it: a client's object exporter pings a set of object ids (a ping set, changed by deltas in `ComplexPing`), and the server reclaims an object whose pings stop ([MS-DCOM 3.2.6.1, Pinging](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dcom/8abedee5-e226-43e7-bb7c-34d0ac6a3c38)). The specification requires the ping period to be at most 2 minutes and suggests exactly 2 minutes, and requires the ping set timer to be at least three times the ping period and suggests exactly three times ([MS-DCOM 3.1.2.2, Timers](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-dcom/ce2c5aa4-30d7-4411-b0ff-9efe7909920e)).

The problem they solve: freeing an object exactly when no peer can still name it, when references cross in messages that the holder has not yet seen.

Failure modes: a late clean freeing a reference a later dirty re-acquired (answered by sequence numbers); a reference freed while in transit (answered by holding until acknowledged); a peer that dies without cleaning (answered by leases and pings, at the cost of holding objects for minutes).

Verdict for Verbatim: confirms the release rule exactly. `DGCAck` is the message position: a node in transit is held until Core acknowledges a position after the message that carried it, and the per-node recorded position is the sequence number that makes a late acknowledgement harmless, provided every carry updates it (the splice precondition above). Verbatim does not need leases, since the supervisor sees a process exit directly. The one difference that matters: RMI and DCOM acknowledge slowly because a held object costs memory only. A node held in Verbatim's release set costs reads of its changes while its window is in front, so the acknowledgement's latency is part of the rule's cost, which is why the ping-only delivery of `NodesHeld` after `CoreFocus` is removed is a real change.

## X11 focus timestamps and Wayland serials

X11: `SetInputFocus` "has no effect if the specified time is earlier than the current last-focus-change time or is later than the current X server time" ([XSetInputFocus](https://tronche.com/gui/x/xlib/input/XSetInputFocus.html)); a client that passes `CurrentTime` defeats the check, which is why the ICCCM forbids it: "Note that clients must not use CurrentTime in the time field" ([ICCCM section 4.1.7](https://tronche.com/gui/x/icccm/sec-4.html)).

Wayland: the compositor sends `xdg_surface.configure` with a serial; the client answers `ack_configure`, which "consumes the serial number sent with the request" and every earlier configure's, and "If the client receives multiple configure events before it can respond to one, it only has to ack the last configure event"; acknowledging a serial never sent is a protocol error ([xdg-shell](https://wayland.app/protocols/xdg-shell)). A popup grab must name the serial of the user input that caused it, or the popup is dismissed.

The problem: rejecting a request made on a view of the world the authority has moved past, without the requester holding the authority's state.

Failure modes: a stamp the requester invents (X11's `CurrentTime`) passes every check; stamps from two clocks cannot be compared.

Verdict for Verbatim: confirms Core's stale rule on observation stamps and the model's version rule, and `ack_configure` confirms the shape of `NodesHeld`: the newer acknowledgement replaces every older one, as Core's writer slot keeps only the newest list. Nothing here helps an outpost choose targets; these systems reject stale requests at the authority and never ask the requester to predict a verdict.

## Other screen readers and UI Automation itself

NVDA runs in one process with one main queue. Event handlers judge a change against the focus at the moment they run, on the thread that also set the focus: `event_valueChange` and `event_nameChange` speak only `if self is api.getFocusObject()`, and `event_stateChange` also for a focus ancestor (`nvda/source/NVDAObjects/__init__.py`). So NVDA's filter is never behind its verdict, which is the "view ordered with what it judges" the model allows within one process. For UIA it registers property changes on the focused element only, adding the group in `event_gainFocus` after checking from its MTA thread that the element still has the focus, and removing it in `event_loseFocus` (`nvda/source/NVDAObjects/UIA/__init__.py`; `nvda/source/UIAHandler/__init__.py`, `addLocalEventHandlerGroupToElement` and `removeLocalEventHandlerGroupFromElement`); range values and drag-and-drop effects stay global (`globalEventHandlerGroupUIAPropertyIds`). Its MSAA limiter exempts the last queued focus object's events from the per-thread limit. Verdict: NVDA's model cannot be copied across Verbatim's process split, and its UIA group follows NVDA's own focus, not a verdict made elsewhere; removing the group at release, as the design asks, is the faithful translation, since NVDA removes the group exactly when its own judged focus leaves the element.

Orca receives every application's AT-SPI events in one process and keeps libatspi's client-side cache there; Orca's maintainer explained that the cache lives in Orca's process and that stale data comes from applications that do not emit the events the cache depends on, or from cache bugs, and that restarting Orca clears it ([orca-list, May 2011](https://lists.gnome.org/archives/orca-list/2011-May/msg00033.html)). The earlier Python AT-SPI cache had the same defect and moved to deleting a cached value when a change is detected ([GNOME bug 334924](https://bugzilla.gnome.org/show_bug.cgi?id=334924)). Today's Orca clears the AT-SPI cache for an object explicitly and keeps a record of objects known to be dead, with workarounds for toolkits' broken trees naming Mozilla bug 1879750 and QTBUG-130116 ([ax_object.py](https://gitlab.gnome.org/GNOME/orca/-/raw/main/src/orca/ax_object.py), `clear_cache`, `object_is_known_dead`). Verdict: a cache kept by a reader goes stale exactly where the source's events are missing, so reading fresh on each event, as Verbatim's outposts do, is right; the only cached fact the design keeps, `states_read`, is the outpost's own and updated only by its own reads.

UI Automation's own caching: "The cache is valid only as long as nothing changes in the UI. Your application is responsible for retrieving a new snapshot of the cache, typically, in response to events", and an event subscribed with a cache request delivers its sender with a new snapshot ([Caching UI Automation Properties](https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-cachingforclients)). Verdict: UIA delivers changes only to registrations, so for UIA the rule must govern registrations, not only reads (the second lesson above).

JAWS, Narrator and VoiceOver: I found no public description of how they choose which objects' changes to watch or how they coordinate across processes. JAWS and Narrator are closed; Narrator is a UIA client like any other, so it is bound by the same registration model.

## Other leads

- Game netcode, the authoritative server with client prediction. The client numbers its inputs and keeps every input the server has not yet acknowledged; each server state names the last input it processed, and the client discards inputs up to it and replays the rest ([Gabriel Gambetta, Client-Side Prediction and Server Reconciliation](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html)). Quake III's server likewise sends each client a delta against the last snapshot that client acknowledged. Verdict: the same "keep everything not yet acknowledged" rule, and a warning in the other direction: prediction (acting on a guess of the server's verdict and correcting later) works there only because the client can redraw; speech cannot be unsaid, which is why Verbatim's earlier attempts to predict Core's verdict failed and the superset is right.
- LSP document versions. Each change increments the document's version ("The version number of a document will increase after each change"), and a versioned edit lets the client "check the text document version before an edit is applied"; the specification leaves a mismatch's handling to the client, and stale requests are cancelled or answered with `ContentModified` ([LSP 3.17](https://microsoft.github.io/language-server-protocol/specifications/lsp/3.17/specification/)). Verdict: the version rule of the model, for configuration in M5; nothing for change targets.
- Xi editor. Its author's retrospective: "adding async made everything more complicated, in some cases considerably so", with "races between editing actions and word wrap updates", and "I now firmly believe that the process separation between front-end and core was not a good idea" ([xi retrospective](https://raphlinus.github.io/xi/2020/06/27/xi-retrospective.html)). Verdict: supports keeping as few facts shared across processes as possible, as the model does; Verbatim's split is forced by UIA (`docs/design/ownership.md`), Xi's was chosen.
- Actor systems, Elm and Redux, deterministic replay, VS Code's extension host and Servo's constellation are covered in `architecture-study.md`, section 3, and are reflected in the model's pure reducers and typed messages; they say nothing more about change targets and are not repeated here. Compositors other than Wayland's serials added nothing.

## Standard terms

Each Verbatim mechanism, the standard name for it, what that name means, how Verbatim's mechanism matches or differs, and the source that defines or uses the term. Every citation in this section was read in its primary source.

### The release protocol (`NodesHeld`)

- Reference listing. A distributed garbage collector in which the owner of an object keeps the set of processes holding references to it, not a count. Birrell's network objects are "a generalization of reference counting; it maintains a set of identifiers for processes with references to an object" (Birrell, Evers, Nelson, Owicki and Wobber, "Distributed Garbage Collection for Network Objects", DEC SRC Research Report 116, 15 December 1993, [bitsavers copy](https://ftp.mirrorservice.org/sites/www.bitsavers.org/pdf/dec/tech_reports/SRC-RR-116.pdf)). The name is from Moreau, Dickman and Jones, "Birrell's Distributed Reference Listing Revisited" (ACM TOPLAS 27(6), 2005, [Kent repository](https://kar.kent.ac.uk/14235)), whose abstract calls Java RMI's collector, which uses it, "arguably the most widely used distributed garbage collector". Verbatim matches most closely the variant where the holder sends the list. In Shapiro's SSP chains, "spaces exchange idempotent live messages that list the set of stubs that are still reachable; the receiver deletes the scions corresponding to stubs that are not listed in the live message", and "race conditions are avoided by timestamping all messages and data structures, and ignoring messages that are inconsistent with the data structures" (Shapiro, Plainfossé, Ferreira and Amsaleg, "Some Key Issues in the Design of Distributed Garbage Collection and References", 1994, [PDF](https://perso.lip6.fr/Marc.Shapiro/papers/key-issues-GC_utpdcs94.pdf)). `NodesHeld` is that live message: Core, the holder, lists every node it still holds, and the outpost, the owner, frees what is not listed. It differs in being sent when the list changes rather than periodically, and its timestamp is the acknowledged message position.
- The in-transit reference problem. A reference inside a message not yet received is held by nobody, so a collector looking only at holders would free it. Shapiro's paper names it ("it would appear that x is unreachable although a reference to it is in transit"). Birrell's protects it by keeping the sender in the object's dirty set "until an acknowledgment from Q indicates that the reference has been received", as Java RMI does with `DGCAck` (cited above). Verbatim's rule that a node is freed only when an acknowledgement of a later position omits it is this protection, with Core's acknowledged position standing for the receiver's acknowledgement.
- Cumulative acknowledgement. One acknowledgement covers every message up to a position: in TCP, "The acknowledgment mechanism employed is cumulative so that an acknowledgment of sequence number X indicates that all octets up to but not including X have been received" ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html), section 3.4). `NodesHeld`'s acknowledged position is cumulative in the same way, which is why a newer list may replace one not yet sent.

### The outpost reading changes for a superset of what Core may hold

- Conservative approximation. A collector may keep more than is live, never less: "Because a conservative overestimate of the reachable set is safe, the distributed GC problem is easier than the general consistency problem. Inconsistencies are permissable as long as they are on the conservative side" (Shapiro and others, 1994, above). The candidate rule is a conservative overestimate of Core's focus line: a node released late costs reads, never a missed change. It is the same reasoning applied to change targets instead of memory.

### The generation

Verbatim's term for both the outpost's incarnation and the worker generation is the generation. The literature calls it:

- An epoch, or in Raft a term. "Terms act as a logical clock in Raft, and they allow servers to detect obsolete information such as stale leaders. Each server stores a current term number, which increases monotonically over time", and "If a server receives a request with a stale term number, it rejects the request" (Ongaro and Ousterhout, "In Search of an Understandable Consensus Algorithm (Extended Version)", [PDF](https://raft.github.io/raft.pdf), section 5.1). The generation in every node id and on every worker result plays this part: what an older generation made is recognised and discarded.
- A fencing token: "a number that increases" each time a lock is granted, with the storage service rejecting a write that carries a lower token than one it has already processed (Martin Kleppmann, [How to do distributed locking](https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html), 2016). This fits the worker generation most precisely: an abandoned worker is the paused lock holder of Kleppmann's example, and the commit's check that the committing generation is in charge is the storage service's check.

### The stale rule by observation stamp

- Timestamp-based rejection at the authority. X11's `SetInputFocus` "has no effect if the specified time is earlier than the current last-focus-change time or is later than the current X server time" ([XSetInputFocus](https://tronche.com/gui/x/xlib/input/XSetInputFocus.html)); Wayland's configure serials (cited above) apply the idea to configuration. Core's stale rule matches X11's: a focus observed before the newest focus Core applied is refused. It differs in the stamp's origin: X11 clients pass a time the server issued, while Verbatim's stamps are the readers' observation times on the machine's one clock.

### One owner per fact

- The single writer principle: "The Single Writer Principle is that for any item of data, or resource, that item of data should be owned by a single execution context for all mutations" (Martin Thompson, [Single Writer Principle](https://mechanical-sympathy.blogspot.com/2011/09/single-writer-principle.html), 22 September 2011). This is Verbatim's rule for threads; Verbatim applies it across processes too, where the other parties learn the fact from one-way reports.
- The actor model: "all of the modes of behavior can be defined in terms of one kind of behavior: sending messages to actors" (Hewitt, Bishop and Steiger, "A Universal Modular ACTOR Formalism for Artificial Intelligence", IJCAI 1973, [PDF](https://www.ijcai.org/Proceedings/73/Papers/027B.pdf)); in Erlang, "Threads of execution in Erlang share no data, that is why they are called processes" ([Concurrent Programming](https://www.erlang.org/doc/system/conc_prog.html)). Core, the outposts and the listener are actors in this sense. The model's allowance for a monitor inside one process is not actor-style; it is Hoare's monitor.
- The monitor: "Such a collection of associated data and procedures is known as a monitor" (C. A. R. Hoare, "Monitors: An Operating System Structuring Concept", Communications of the ACM 17(10), 1974). The model's monitor is Hoare's, with two added rules: its lock is never held across a call, and no caller's code runs under it.

### Pure reducers, with calls as effects

- Functional core, imperative shell: pure functions make the decisions, and "This functional core is surrounded by a shell of imperative code" that does the I/O "based on values produced by the functional core" (Gary Bernhardt, [Functional Core, Imperative Shell](https://www.destroyallsoftware.com/screencasts/catalog/functional-core-imperative-shell), 12 July 2012). The reducer is the core; its thread is the shell that carries out the effects.
- The Elm architecture: `update : Msg -> Model -> (Model, Cmd Msg)`, producing the new model and "a command of what we want Elm to do" ([An Elm guide, HTTP](https://guide.elm-lang.org/effects/http.html)). Verbatim's `step(input) -> effects` is this signature, with calls into applications, timers and messages as its commands.
- Sans-I/O protocol design: an implementation "defined entirely in terms of synchronous functions returning synchronous results", with "no code that does any form of network I/O or any form of asynchronous flow control", as h11 and hyper-h2 are ([Writing I/O-Free Protocol Implementations](https://sans-io.readthedocs.io/how-to-sans-io.html)). The read scheduler's `Schedule::step`, with no clock, thread or lock, is sans-I/O in this sense.

### Queries with exactly one answer, and responders whose `Drop` answers

- RAII: "Rust enforces RAII (Resource Acquisition Is Initialization), so whenever an object goes out of scope, its destructor is called and its owned resources are freed" ([Rust by Example, RAII](https://doc.rust-lang.org/rust-by-example/scope/raii.html)). A responder's `Drop` answering "gone" is RAII applied to an obligation to answer instead of to memory.
- The one-shot channel's dropped sender: "If the sender is dropped without sending, the receiver will fail with `error::RecvError`" ([tokio::sync::oneshot](https://docs.rs/tokio/latest/tokio/sync/oneshot/index.html)). This is the in-process responder exactly, except that Verbatim's sends a typed "gone" answer instead of an error. Across processes no destructor runs in a killed peer, so the request table's deadline gives the answer.
- Dropped: "guaranteed completion" is not a standard name; no primary source defines it.

### Lifecycles as typestates

- The typestate pattern. Typestate was introduced by Robert E. Strom and Shaula Yemini, "Typestate: A Programming Language Concept for Enhancing Software Reliability", IEEE Transactions on Software Engineering 12(1), 1986 ([DBLP](https://vldb.org/dblp/db/indices/a-tree/y/Yemini:Shaula.html)). In Rust it "describes the encoding of information about the current state of an object into the type of that object", and a transition taking `self` by value "consumes the original" state so that it "can not be reused" ([The Embedded Rust Book, Typestate Programming](https://docs.rust-embedded.org/book/static-guarantees/typestate-programming.html)). Verbatim's rule, an enum whose transitions consume the old state, has the consuming half but checks the state by `match` at run time; it is a typestate in the full sense only where each state is its own type, so each lifecycle's documentation should say which form it uses.

### `Merge`

- Coalescing: Windows combines queued messages of a named kind, "multiple WM_PAINT messages for the same window are combined into a single WM_PAINT message, consolidating all invalid parts of the client area into a single area" ([About Messages and Message Queues](https://learn.microsoft.com/en-us/windows/win32/winmsg/about-messages-and-message-queues)). `Merge` is coalescing declared per message kind, as Windows does it only for named kinds. NVDA's limiter, which Verbatim keeps, also coalesces, replacing a waiting event of the same object and kind (`nvda/source/IAccessibleHandler/orderedWinEventLimiter.py`).
- Dropped: market-data "conflation" fits the idea, but only vendor forums and blogs describe it, not a primary specification.

### The back-channel problem

- Time of check to time of use (TOCTOU): "The product checks the state of a resource before using that resource, but the resource's state can change between the check and the use in a way that invalidates the results of the check" ([CWE-367](https://cwe.mitre.org/data/definitions/367.html)). A reader skipping a read against its copy of Core's focus checks Core's state and acts on it after it can have changed; the repeat hole is that window. It differs from the classic case in that the copy is already old when checked, which is why the model removes the check rather than narrowing the window.
- Dropped: "decisions on a stale replica" describes it but is not a term defined in a primary source.

### Who may block on whom

- Priority inversion. Lampson and Redell: P1 enters a monitor and is preempted by P2, which is preempted by P3; "P3 tries to enter the monitor, and waits for the lock. P2 runs again, and can effectively prevent P3 from running, contrary to the purpose of the priorities" ("Experience with Processes and Monitors in Mesa", Communications of the ACM 23(2), 1980, [Lampson's page](https://bwlampson.site/23-ProcessesInMesa/WebPage.html)). The keyboard hook taking `KEY_ORIGINS` is this case, and the cost for a hook is specific: "If the hook procedure times out, the system passes the message to the next hook. However, on Windows 7 and later, the hook is silently removed without being called" ([LowLevelKeyboardProc](https://learn.microsoft.com/en-us/windows/win32/winmsg/lowlevelkeyboardproc)).
- Lock ordering: deadlock is avoided when every process takes its semaphores "in the order of increasing number" (Dijkstra, [EWD625](https://www.cs.utexas.edu/~EWD/transcriptions/EWD06xx/EWD625.html), "Two starvation-free solutions of a general exclusion problem"). The model's nesting of the commit's locks inside the watch lock is a lock order. Its rule that Core never blocks on a reader, nor a reader on Core, is stronger: there is no wait between them at all, so no order is needed.
