# Experiments: a new connection fails while another process's remote operation is queued

These experiments establish the fault recorded in `docs/uia-bugs.md` under [A new connection fails while another process's remote operation is queued](../../docs/uia-bugs.md#a-new-connection-fails-while-another-processs-remote-operation-is-queued). They ran on Dickson's x64 machine (Windows 11, build 26200), `e1` to `e32` on 2026-10-17 and `e33` to `e36` on 2026-10-18, in debug builds, with no other UIA client running. The account the per-application lock was designed from is `docs/design/focus-pipeline.md`, sections 20.1 and 20.8; this readme holds every experiment's setup and numbers.

Terms, beyond those defined at the top of `docs/uia-bugs.md`:

- The collide tool is a scratch crate, `collide`, with three roles: a server, S, a hidden window whose own UIA provider names its element "uia-provider"; clients, each a separate process with its own UIA client object, which take commands on standard input; and an orchestrator, `collide run <script>`, which starts the processes, sends them the script's commands, and prints every process's timestamped lines.
- L is the client that plays the listener: it sets UIA up in S with a first remote operation, then sends the operation under test. B is the client that makes the call under test. M, C and the others are further clients.
- A busy period is S's UI thread spinning without pumping messages (`busy <ms>`), so that L's operation waits in S. A stall in `e33` onward does the same by other means (the orchestrator's `stall` step).
- A collision is a call that answers wrongly because of the fault: `UiaHasServerSideProvider` answering false after about 3 seconds, or a lookup by handle returning UIA's window proxy, whose element is named by the window's title ("collide", or "collide-console") instead of "uia-provider", after about 2 seconds.

The client commands the scripts use: `init` creates the client object; `probe` is `UiaHasServerSideProvider`; `efh` is `ElementFromHandle`; `efhbc` is `ElementFromHandleBuildCache`; `rop` is a remote operation on the client's element of S; `ropname` is a remote operation that reads the element's name; `name` is a plain `CurrentName` read; `walk` is a raw-view tree walk; `events` registers event handlers; `getfocus` is `GetFocusedElement`; `async` sends a command without waiting for its answer. `parent`, `normalize`, `firstchild`, `children`, `cachechildren` and `descendants` are the walks of `e22` to `e26b`; `e33` onward adds the commands its section lists.

## The common procedure

Every experiment from `e1` to `e31` but `e21` and `e22` follows `e1`. S starts; L creates its client, looks S's window up (`efh`) and runs a first remote operation, which sets UIA up in S; B starts and creates its client, and has connected to nothing. S's UI thread is then busy for 40 ms (1,000 ms where said); L sends a remote operation, which waits for the busy thread; 5 ms later B makes the call under test. `base.txt` and `base2.txt` are the shared head of the scripts, without the step under test.

`e1` to `e21` were each run once; their `.out` files hold one run. `e22` onward were run three times each by `run-e23-e29.sh`, the runs appended to one `.out` file under "=== run N" lines, so "6 of 6" for an experiment with two variants means 2 variants times 3 runs.

## Results, e1 to e22

- `e1`, the fault: B's probe, sent 5 ms after L's operation into busy S, answered false after 3,047 ms. S's log shows S answered every `WM_GETOBJECT` it received with `0x10000` once the busy period ended, 40 ms in.
- `e2`, the control for `e1` with no operation: B's probe answered true after 36 ms, at the end of the busy period.
- `e4`: B's probe sent first and L's operation 5 ms after it: false after 3,045 ms. (`e31` repeats this with both kinds of connection.)
- `e5`, which of L's calls opens the window: with L's call a plain name read (`e5-name`), B's probe answered true after 36 ms; a tree walk (`e5-walk`), true after 36 ms; a name read with no first remote operation in S at all (`e5-name-nosetup`), true after 36 ms; a remote operation that reads the name (`e5-ropname`), false after 3,037 ms.
- `e9`: B probed S once, answered true in 7.8 ms, and probed again during L's queued operation: false after 3,035 ms. A client's earlier connection does not protect its later ones.
- `e10`: B held an element of S (`efh` before the busy period) and read its name during L's queued operation: "uia-provider" after 36 ms, delayed to the end of the busy period and correct (`e10-held-element`). `e10.out` is a first attempt whose script omitted B's `init`, so B never answered and the run timed out; it holds no result.
- `e11`: B's `ElementFromHandleBuildCache` during L's queued operation returned the window proxy, named "collide", after 2,049 ms.
- `e12`: L's own probe and `ElementFromHandleBuildCache` during its own queued operation: true after 36 ms, and "uia-provider" in 1.1 ms. A process's own operation does not expose its own lookups.
- `e14`: L's operation held inside a provider callback during its evaluation (S's `armprov` command, with S's UI thread pumping sent messages): B's probe answered true in 28 ms. Once evaluation has begun, connections are not exposed.
- `e16`: S has a second UI thread, idle; B probed that thread's window while L's operation waited for the busy main thread: false after 3,026 ms. The whole process is exposed.
- `e17`: L registered event handlers in place of the operation: B's probe answered true after 36.5 ms. Event registrations do not open the window.
- `e18`: two new connections and no operation: M's probe, sent first, and B's, 5 ms later, both answered true (41 and 37 ms). (The orchestrator then timed out waiting for M's line, which the earlier wait had consumed; the results are unaffected.)
- `e20`: S shown, so it can have the system focus, and B's `GetFocusedElement` during L's queued operation: "uia-provider" after 37.8 ms. `docs/uia-bugs.md` calls `GetFocusedElement` unsettled because an earlier experiment, not kept, saw it fail.
- `e21`, a sweep with nothing busy: L's operation into a settled S, then B's probe 0 to 2 ms later, 36 trials at 12 delays. B's probe answered false after 2,999.8 to 3,013.9 ms in 6 of 36: at 0 ms once, 0.1 ms twice, 0.2 ms twice and 1.0 ms once; every other probe answered true in 0.9 to 6.7 ms. The window exists without a busy UI thread, briefly.
- `e22`, the baseline for the walks with nothing busy: from B's element of S's child window, the parent and the normalized element reached S's provider in 1.1 and 1.5 ms; from S's main window, the first child, a walk, the children, a cache of the children and the descendants reached the child's provider in 1.3 to 6.4 ms.

Numbers `e3`, `e6` to `e8`, `e13`, `e15` and `e19` were not used for any kept script or output, and no document cites them.

## Results, e23 to e32

These ran on 2026-10-17 with the tool extended by `collide-tool-crossings.patch`. A window's own provider names its element "uia-provider"; the window proxy names it by the window's title.

- `e23`, upward within one process: B holds the element of S's child window and walks to its parent, S's main window (`GetParentElementBuildCache`, `e23-up-same-parent`), or normalizes to it (`NormalizeElementBuildCache` with a walker that excludes the child's own window, `e23-up-same-normalize`). Not exposed: 6 of 6 reached the provider, after the busy period (about 37 ms).
- `e24`, upward into another process: B holds the element of process T's child window, parented under S's main window as Settings' content is under `ApplicationFrameHost`'s frame, and walks or normalizes up into S. Exposed: 6 of 6 returned the window proxy after about 2,045 ms. The same when B had already connected to S's main window and held its element (`e24b`, 6 of 6), and when L's operation went into another top-level window of S (`e24c`, 3 of 3).
- `e25` and `e26`, downward: B holds a window's element and asks for its first child (`GetFirstChildElementBuildCache`), its children or descendants (`FindAllBuildCache`), or builds a cache scoped to its children (`BuildUpdatedCache`), reaching a child window's provider in S: in the same process (`e25`, four variants), from a parent window of another process (`e26`, three variants), and with L's operation into that child window itself (`e26b`, two variants). Not exposed: 27 of 27 reached the provider, after the busy period.
- `e27`, two remote operations: B's operation into S while L's waits, each reading the element's name inside the operation, with B's first operation into S (`e27-two-rops-firstrop`) and with one it had run before (`e27-two-rops-rops`). 6 of 6 pairs both read "uia-provider", B's ending within a millisecond of L's.
- `e28`, an idle UI thread: S has a second UI thread, idle; L's operation waits for S's main thread, busy 1,000 ms; B, holding the element of the second thread's window (with a connection and an operation of its own there before), runs a remote operation reading the name (`ropname`), reads the name, or probes it. All 9 were delayed to the end of the busy period, about 997 ms, and then answered correctly. The control without L's operation (`e28c`) answered all 9 in under 1.1 ms. A probe of the idle thread's window from a client with no connection there before (`e28d`) answered false after about 3,015 ms, 3 of 3.
- `e29`, MSAA: B's first MSAA call into S, `AccessibleObjectFromWindow` (`msaa`) or `AccessibleObjectFromEvent` (`msaaevent`) and then the name, through UIA's bridge to S's provider (`e29-msaa-bridge-*`) and, with S answering only UIA's own object id, through the system's standard proxy (`e29-msaa-oleacc-*`). All 12 answered correctly ("uia-provider" through the bridge, the window's title through the proxy) at the end of the busy period.
- `e30`, a pending connection and no operation: B's probe or `ElementFromHandleBuildCache` of the busy main window waiting, and a third client's remote operation reading the name, or its plain name read, on the idle thread. The third client answered in about 1 ms and 0.3 ms, 12 of 12, and B's connection then answered correctly. A pending connection holds no other client's call.
- `e31`, the order: B's probe or `ElementFromHandleBuildCache` sent first and waiting for S's busy thread, L's operation 5 ms after it. B's call failed in 6 of 6: the probe answered false after 3,049 to 3,055 ms, and the lookup returned the window proxy after 2,045 to 2,050 ms.
- `e32`, warming a client process's UIA start: 20 fresh client processes of each kind, interleaved (`e32-warm-up.txt`; `e32-summary.py` prints `e32-warm-up-summary.txt`). Cold, a process that only created its client: its first probe of S's window took 7.8 to 13.5 ms (median 8.6), and the lookup after it 0.8 to 1.8 ms. Warmed on a hidden window of its own: the first probe of S took 1.2 to 1.7 ms (median 1.4), the warm-up's own probe 6.8 to 10.8 ms (median 7.6). Warmed on a window of another process: 0.9 to 1.1 ms (median 1.0). This is section 20.10's measurement; it concerns cost, not the fault.

## Results, e33 to e36

Run on 2026-10-18 to decide whether a listener with no remote operations could replace the per-application lock: each experiment tests a call such a listener would use. In every trial L has set UIA up in the application with one remote operation, then sends a second while the application's UI thread is stalled for 300 ms; B (and C in `e34`), each a new process, makes the call under test 5 ms later. Each control trial omits L's operation. `gen-e33-e36.py` writes the scripts, `run-e33-e36.sh` runs them (6 trials each, 2 for controls), `e35b-run.ps1` runs `e35b` with a fresh console per trial, and `e33-e36-summary.py` prints `e33-e36-summary.txt`. The provider description, which the tool reads on every element found, tells the application's own provider (main provider collide.exe or conhost.exe) from the window proxy (main provider the MSAA proxy in uiautomationcore.dll); each trial records the target's owner process, and L's operation finished at the end of the stall in every trial with an operation.

- Positive control, `e33-root-efhbc`: B's `ElementFromHandleBuildCache` on S returned the proxy after 2,300 to 2,337 ms in 6 of 6; in the 2 controls it returned S's own element in 297 ms.
- `e33`, the walk down from the desktop root to S's top-level window: B got S's own element in all 24 trials, 6 each for the raw-view sibling walk (`rootwalk`), the control-view sibling walk (`rootwalkcv`), `FindFirst` on the root's children by window handle (`rootfind`) and `FindAll` on the root's children (`rootfindall`). Each took 297 ms, the step that reached S waiting for its stall, or 312 to 316 ms for `FindAll`; the 8 controls were the same. Reads afterwards took 0.5 to 2 ms and gave "uia-provider". The desktop had only 5 top-level windows (S, the activation watermark, the taskbar, Program Manager and Windows Terminal), so this says little about the cost on a busy desktop.
- `e34`, the raw probe: B's `SendMessageTimeoutW(WM_GETOBJECT, 0, UiaRootObjectId)` to S answered `0x10000` in 291 to 295 ms, once S pumped, in 6 of 6. C's `UiaHasServerSideProvider` on the same window, sent at the same moment, answered false after 3,296 to 3,308 ms in 6 of 6. In the 2 controls both answered yes in about 296 ms. For N, a window with no UIA provider, the raw probe gave 0 and `UiaHasServerSideProvider` false, both in under 1 ms, in all 8 trials.
- `e35`, a console: the window is conhost's and its client cmd.exe, so the stall suspends conhost's window thread, found by enumerating conhost's threads. B held the text area and walked up with the raw-view walker's `GetParent`: it reached the console window's own element ("Microsoft Console Host Window", conhost.exe) in one step in 6 of 6, in 299 to 313 ms, and in the 2 controls. The positive control did not collide in conhost: B's `ElementFromHandleBuildCache` returned conhost's own element in 296 to 297 ms in 6 of 6.
- `e35b`: both repeated on a fresh console for each trial, so that L's operation was the first in conhost: 5 trials each, with the same result.
- `e35c`: S's UI thread suspended in place of its busy loop, the way `e35` stalls conhost: the collision reproduced in 5 of 5, the proxy after 2,300 to 2,309 ms. So the method of stalling is not why conhost differs.
- `e36`, the listener's own application: B held S's top-level element and the element of S's child window found under it, then walked up from the child: it reached S's own top-level element in one step in 6 of 6 (300 to 302 ms) and in the 2 controls, as in `e23`.

## Launches of real applications

The fault as Verbatim met it, in end-to-end runs on 2026-10-16 and 2026-10-17 (`scripts/lc-run.ps1` runs one scenario repeatedly, optionally under a trace, and keeps each run's logs):

- `notepad/`: `notepad_typed_words` runs before the spare outposts (`runs-pre-spares-5eae1b65.txt`, at 5eae1b65: 1 failure in 15) and after them (`runs-main-untraced.txt`, 1 in 15; `runs-main-traced.txt`, 0 in 20). In each failure the first focus was read through MSAA and spoken "edit multi line" in place of "Text editor document" (`main-collided-run/test-failure.txt`, with that run's listener and outpost logs, and `pre-spares-collided-run/`). `timing-np*.txt` give, for each run, the outpost's probe of `RichEditD2DPT` and the listener's remote operation, relative to each other.
- `runs-wt-section20-traced.txt`: 14 traced `windows_terminal_commands` runs, 1 failure.
- `wt-launch-slow/`, that failure: the outpost's probe of the terminal's `InputSite` window waited 3,008 ms in `ChannelBasedClientConnectionManager::CreateLowBoxChannelBasedClientConnection` inside `UiaHasServerSideProvider` and answered no (`outpost-probe-3s-wait.txt`), while the listener's focus read waited for the terminal's busy UI thread (`wt-ui-thread-15608-phases.txt`, `wt-ui-and-io-threads-16.784-16.795.txt`); the terminal's focus was spoken "pane" (`test-failure.txt`). `outpost-worker-client-init-and-wm-getobject.txt` is the outpost worker's first UIA client start, which section 20.10 cites.
- `wt-launch-fast/`: a launch without the fault, for comparison: the terminal's UI thread phases and the outpost worker's timeline.
- `section20-build-scratch-logging.patch`: the scratch logging these runs used, against 3782ee8d.
- `scripts/`: `blk.py`, `phases.py` and `tl.py` condense the trace reader's blocked-wait and timeline reports, and `overlap.py` times the listener's first remote operation against the outpost's first UIA call from the debug logs.

The traces themselves (ETL files) are not kept; the text above was extracted from them.

## Established and inferred

Established, on this machine: any remote operation queued in an application, from its arrival until evaluation begins, makes another process's new connection by handle to any window of that application, and its walk up into a window of that application from another process, answer wrongly with no error; it happens in either order, from clients that connected before, and briefly even with an idle UI thread (`e21`). Calls on held elements, walks down, walks up within a process, another remote operation, MSAA, the raw `WM_GETOBJECT` and the operating process's own lookups are not exposed. conhost did not show it (`e35`, `e35b`).

Inferred, not shown: the mechanism inside UIA, and why conhost differs.

## Rerunning

In a scratch worktree, apply `collide-tool-e33.patch` to 32948a4d (or an earlier patch to the commit named above), then `cargo build -p collide`, then `collide run collide/<script>.txt` from this folder. `run-e23-e29.sh` and `run-e33-e36.sh` run a list of scripts three times each; change their `exe=` line to the built `collide.exe`. Every process runs hidden on the current desktop; nothing takes the foreground or injects keys, except `e20`'s shown server. The launches need a running `verbatim-agent` and take over the desktop (`docs/tooling/e2e.md`); `lc-run.ps1`'s output folder was a session's scratch folder and is redacted to `<scratch folder>`.
