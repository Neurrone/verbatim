# Experiments: a registration that times out reports success

These experiments establish the fault recorded in `docs/uia-bugs.md` under [A registration that times out reports success](../../docs/uia-bugs.md#a-registration-that-times-out-reports-success), and the limitation [A timeout bounds each provider call, not an operation](../../docs/uia-bugs.md#a-timeout-bounds-each-provider-call-not-an-operation); both rest on E-TT, so they share this folder. E-TT ran on 2026-10-10 on Dickson's x64 machine (Windows 11, build 26200), in a debug build, once. Its code is `e_tt` and `e_tt_transactions` in [`../mockapp-experiments-2026-10-10/experiments.rs`](../mockapp-experiments-2026-10-10/readme.md); e57, which asks whether such a registration delivers events afterwards, ran on 2026-10-18 on the same machine, in a debug build, 180 trials; its code, scripts and outputs are in [`e57/`](e57/). e58, which asks what reaches the application and the process's other registrations during that registration's silence, and whether it can be removed then, ran on 2026-10-18 on the same machine, in a debug build, 30 trials; its code, scripts and outputs are in [`e58/`](e58/).

Terms: the transaction timeout is `IUIAutomation2::TransactionTimeout`, which bounds a call on an element already obtained (a transaction), as the connection timeout bounds obtaining one. A hold is mockapp's `hold` command, which makes the provider's next call of a named kind wait, inside mockapp's process, until released.

## E-TT: what a 1-second transaction timeout bounds

In a mockapp test process, against mockapp's server-side provider with the `small.json` fixture, on a desktop of its own: the transaction timeout set to 1 second, the element fetched before the hold, and then each call below made while mockapp was held:

- `CurrentName`: failed with `UIA_E_TIMEOUT` after 1,095 ms.
- `CurrentHasKeyboardFocus`: failed with `UIA_E_TIMEOUT` after 1,092 ms.
- `AddEventHandlerGroup` on the window, held in `FragmentRoot`: returned success after 1,089 ms, though the provider never answered. Whether that registration delivers anything afterwards was not tested.
- `FindFirst` over the window's descendants: failed with `UIA_E_TIMEOUT` after 13,208 ms. A search that makes many provider calls waits a full timeout for each one that the still-held thread does not answer.
- `GetFocusedElement` could not be aimed at mockapp, since nothing has the system focus on a test's own desktop; it answered the desktop at once.

The related E3 (`e3_hold_never_released`), the same file: a held `HasKeyboardFocus` read, never released, returned `UIA_E_TIMEOUT` after 22,111 ms with the default transaction timeout and after 1,092 ms with it at 1 second.

Established: the transaction timeout bounds single reads, and remote operations, which are one transaction each (`a_stalled_provider_holds_execute_until_the_transaction_timeout` in `crates/mockapp/tests/remote_ops.rs`); it does not bound an operation made of many calls; and a registration whose provider timed out reports success.

Whether a registration that timed out delivers events afterwards is e57's question, below.

## e57: when a registration that timed out starts to deliver

Terms: the stall is mockapp's `stall-until-release posted`, which keeps its window thread from taking any message until the test sends `release`; the stall's end is the moment the test has `release`'s acknowledgement. The registration's return is the moment the registering client's `AddEventHandlerGroup` call returned. The gap is the time after the stall's end in which a registration that timed out hears nothing.

Setup, one trial per test process (`e57_trial` in [`e57/e57.rs`](e57/e57.rs)): a mockapp on the UIA backend with the `small.json` fixture, on the test's own desktop. The registering client sets the connection and transaction timeouts, fetches mockapp's window element before the stall, and, once mockapp says `stall started`, registers an event handler group holding UIA's focus event (`UIA_AutomationFocusChangedEventId`, subtree scope, with the name cached) on the window. The call returns success after the connection timeout (532 to 551 ms at 500, 2,190 to 2,226 ms at 2,000, 5,514 to 5,541 ms at 5,000), while the stall still holds. The test releases the stall a set time after the return (200 ms unless stated), then raises focus events at set offsets from the stall's end. Before each one it renames a focusable node `ev<n>`, so that the handler, which reads the sender's cached name, names the event it heard. It then listens for 2 to 4 seconds after the last raise. The registering client runs either on a thread of the test process (in-process below) or in a second process, the test binary started again (second process below). The control registers with no stall.

Results:

- Every event raised in the gap was lost: none was ever delivered, in any trial, though the trials listened 2 to 4 seconds past the last raise and events raised after the gap arrived within 1 to 11 ms of being raised.
- The gap ends about 2 seconds after the registration's return, whatever the connection or transaction timeout, and not at a fixed time after the stall's end. With the stall released 200 ms after the return and a focus event every 50 ms from the stall's end, the events up to 1,750 ms after the stall's end were lost and those from 1,800 ms were heard, in all 30 trials: 5 in-process and 5 in a second process at each connection timeout of 500, 2,000 and 5,000 ms (transaction timeout 5,000 ms). The same held with the connection timeout at 2,000 ms and the transaction timeout at 500 or 20,000 ms, 3 trials each, in-process and in a second process (12 trials).
- In 10-ms steps (connection timeout 2,000 ms, 3 trials in-process and 3 in a second process), the last event lost was raised 1,780 to 1,791 ms after the stall's end and the first heard 1,790 to 1,800 ms after it: 1,981 to 2,001 ms after the registration's return.
- Released later, the gap moved with the return, not the stall: released 1,000 ms after the return, events were heard from 1,000 ms after the stall's end (the last lost at 950); released 1,700 ms after it, from 300 ms (the last lost at 250); released 3,000 ms after it, the event raised as the stall ended was heard. 3 trials of each, in-process and in a second process (18 trials).
- A stall that outlasted the return by more than 2 seconds left no gap, whatever its length: the event raised as the stall ended was heard after a stall of 4,000 or 10,000 ms past the return with the connection timeout at 500 ms, and of 6,000 ms past it at 2,000 ms (8 trials, in-process).
- The next event does not start delivery: a single event raised 1,500 ms after the stall's end was never heard, and one raised at 2,000 ms was, 5 trials each in-process and in a second process (20 trials); with events at 1,000 and 2,500 ms, the first was lost and the second heard, without the first, 5 trials each (10 trials).
- In-process and second-process registrations behaved alike in every condition.
- Control: with no stall, the registration returned in 3 ms and every event was heard within a few milliseconds of being raised (6 trials).
- No message was sent to the stalled window thread during the registration in 4 trials of the stall without `posted` (`out/x_sends_hold3000.out`); with `posted`, mockapp reported a message posted to it in every stalled trial. In 1 of 40 runs of an earlier form of the reproduction test beside the rest of the folder, which expected the posted message, a message was sent to the thread first.

Established: a registration that timed out reports success and starts to deliver about 2 seconds after its call returned, or when the stall ends if that is later; the interval follows neither timeout nor the next event. Events raised in the gap are lost, not delivered late. Once delivery starts, no later event was lost. A registration in the test process and one in a second process behave alike.

Whether the 2 seconds is UIA's default connection timeout, used where the process's setting is not, was not tested. e58, below, shows that the end of the gap is not a second attempt reaching the application.

No test reproduces the loss: nothing marks the end of the gap, so a test cannot tell an event lost in it from one delivered late (`docs/uia-bugs.md` says why).

The outputs are in [`e57/out/`](e57/out/), one line per trial; the 66 exploratory trials that found the conditions are in [`e57/out/explore/`](e57/out/explore/) and agree with them. The first version of the summary script misread the exploratory stream trials as hearing nothing; the corrected [`e57/onset.py`](e57/onset.py) summarises each line: the registration's time, the events lost and heard, any event heard more than 50 ms after it was raised, any heard twice, and any lost after the first one heard.

## e58: what happens during the gap, and removing the registration

Terms as in e57; the gap is the time after the stall's end in which a registration that timed out hears nothing. The backlog is what the stalled thread took within 20 ms of its release, the messages and calls that had waited for it.

Setup, one trial per test process (`e58_trial` in [`e58/e58.rs`](e58/e58.rs)), with the stall `stall-until-release quiet`, which takes no message at all, the connection timeout 2,000 ms and the transaction timeout 5,000 ms in each registering process, and the stall released 200 ms after the registration returned. The registration is a group holding UIA's focus event, with the name cached, registered on mockapp's window by a client on a thread of the test process. Each focus event is raised on a node renamed `ev<n>` first, so the handler names the event it heard. In the `silent` and `onset` cases, mockapp counts registrations (`--count-registrations`), so its root provider is told of each registration and its removal (`IRawElementProviderAdviseEvents`), and a patch to mockapp ([`e58/mockapp-log.patch`](e58/mockapp-log.patch), [`e58/e58_log.rs`](e58/e58_log.rs)) logs, from the release on, with the time: each advise, each provider call, each message another thread sent to the window thread, and each posted message the thread took. Five trials of each case.

- `silent`: no event raised; the log read for 6,000 ms after the release.
- `onset`: as `silent`, with a focus event raised every 100 ms from the release to 3,000 ms after it.
- `scope`: two mockapps. Before the stall, the test process registers a group on the first window (A) and one on the second window (C), both on its main thread's client, and a second process, the test binary started again, registers one on the first window (D). During the stall, a client on another thread of the test process registers the timed-out group on the first window (B). After the release, focus events are raised on the first window every 100 ms from 0 to 3,000 ms and on the second every 100 ms from 50 to 2,950 ms.
- `remove`: the timed-out group is removed (`IUIAutomation6::RemoveEventHandlerGroup`) 500 ms after the release, in the gap; the test then drops its own references to the group and the handler, and waits up to 15 seconds for the handler object to be freed, which its destructor reports. Focus events are raised at 1,000 and 4,000 ms after the release.
- `remove-late`: as `remove`, removed 3,000 ms after the release, after the gap.
- `remove-nostall`: the control, as `remove` with no stall.

Results:

- One advise, at the release. In all 10 `silent` and `onset` trials the provider was advised of the focus event once (`AdviseEventAdded`), within a millisecond of the release, in the backlog with the calls that made it (`FragmentRoot`, `GetEmbeddedFragmentRoots`, `ProviderOptions`): the registering call's own request, which had waited for the stalled thread. No second advise came in any trial.
- With no event raised, nothing reaches the application after the stall's end. In the 5 `silent` trials, the log held nothing after the backlog: no advise, provider call, sent message or posted message for the 6,000 ms after the release. In the 5 `onset` trials, the registration still began to deliver about 2 seconds after its call returned: the events raised up to 1,700 to 1,703 ms after the release were lost, and those from 1,801 to 1,803 ms on were heard, each within 1 ms of being raised. The events raised in the gap reached the application's UIA side: from the one raised at 100 ms on, the log held provider calls, messages other threads sent the window thread (`WM_GETOBJECT` among them) and posted messages after each raise, 1,086 to 1,088 items between the backlog and the first delivery. The events raised in the gap were lost, which is observed; that they are lost in the registering client is inferred, not observed: nothing on the client's receiving side was watched, and state kept per client process in the application's UIA side would fit the same results.
- The gap affects every registration in the process on that window. In all 5 `scope` trials, A, registered before the stall on another client object, and which had heard a focus event raised before the stall, lost the same events as B, the last raised 1,701 to 1,703 ms after the release, and heard the same from 1,801 to 1,804 ms on. D, on the same window in the second process, heard all 31 events, and C, on the second window in the test process, all 30, each within 2 ms.
- Removal in the gap fails, and the handler is not freed. In all 5 `remove` trials, `RemoveEventHandlerGroup` returned `UIA_E_TIMEOUT` (0x80131505) in under 1 ms, and the handler object had not been freed 15 seconds after the removal. The registration stayed live: the event raised at 1,000 ms, in the gap, was lost, and the one at 4,000 ms was heard. In all 5 `remove-late` trials and all 5 `remove-nostall` trials, the removal succeeded in under 1 ms, the handler was freed within 1 ms, and neither event was heard.

Established: a registration that timed out against a stalled window is made once, when the stall ends, by its own waiting request, and no second advise follows; with no event raised, nothing more reaches the application after the stall's end, while delivery begins about 2 seconds after the call returned. Events raised in the gap are lost; where they are lost is inferred, as above. The gap silences every registration the process has on that window, including those made before the stall on other client objects, and no registration on another window or in another process. During the gap, removing the registration fails at once with `UIA_E_TIMEOUT` and leaves it in place, its handler not freed 15 seconds later, and it delivers once the gap ends; removed after the gap, at the one time tried, 3 seconds after the stall's end, it is removed at once.

The outputs are in [`e58/out/`](e58/out/), one line per trial, named after the case; [`e58/summarise.py`](e58/summarise.py) summarises each line: for each handler, the events lost and heard and the slowest delivery, and for the removal cases, the removal's result and the handler's release.

## Rerunning

E-TT: as [the mockapp experiments' folder](../mockapp-experiments-2026-10-10/readme.md) says, `cargo test -p mockapp --test experiments -- e_tt --nocapture` in a worktree at b0a1989. E-TT's registration and its read are tests now, in `crates/mockapp/tests/uia_bugs/` (`docs/uia-bugs.md` names them).

e57: in a worktree at e04bdd8a, the commit that recorded it, since the stall e57 used is not in mockapp on main. In that worktree, copy `e57/e57.rs` into `crates/mockapp/tests/uia_bugs/`, and add to that folder's `main.rs` the line `mod e57;`, the helper dispatch `if let Ok(window) = std::env::var(e57::REGISTRAR) { e57::registrar_process(&window); }` beside the others, and the entry `("e57_trial", e57::e57_trial)` in the test list. Add to `MockApp` in `crates/mockapp/tests/common/mod.rs` a method `pub fn line_within(&self, timeout: Duration) -> Option<String>` returning `self.lines.recv_timeout(timeout).ok()`. Build with `cargo test -p mockapp --test uia_bugs --no-run`, set `EXE` to the binary it names, and run `e57/run.sh` from the `e57` folder with the settings `e57.rs` documents, for example `E57_CTO=2000 E57_WHERE=out E57_RAISES=$(seq -s, 0 50 2500) ./run.sh 5 m_out_cto2000`. `E57_HOLD_AFTER` sets the time from the return to the release, in ms, and `E57_POSTED=0` stalls without `posted`.

e58: in a worktree at 64557420, the commit it ran on, run `python e58/apply.py <worktree> e58` from this folder: it adds the logging patch to mockapp (the change `e58/mockapp-log.patch` shows), `line_within` to `MockApp` in `crates/mockapp/tests/common/mod.rs`, and `e58.rs` to `crates/mockapp/tests/uia_bugs/` with its entries in that folder's `main.rs`. Build with `cargo test -p mockapp --test uia_bugs --no-run`, set `EXE` to the binary it names, and run `e58/run.sh` from the `e58` folder with the case in `E58_CASE`, and `E58_LOG=1` for `silent` and `onset` only, since the other cases read mockapp's acknowledgements without the log: for example `E58_LOG=1 E58_CASE=silent ./run.sh 5 silent` and `E58_CASE=scope ./run.sh 5 scope`.
