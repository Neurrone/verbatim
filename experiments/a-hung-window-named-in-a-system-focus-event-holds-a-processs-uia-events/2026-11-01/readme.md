# Experiments of 2026-11-01 and 2026-11-02: the hold's calls, threads and exceptions

This series, run on Dickson's x64 machine (Windows 11, build 26200) on the evening of 2026-11-01 and past midnight, established which calls UIA's focus tracking makes, which threads a UIA client process runs, which focus events escape the hold, how a hold looks on a real desktop where Windows marks a window hung, that a slow provider holds as a hung window does, and that Verbatim's running listener is held like any client. It serves the entry [A hung window named in a system focus event holds a process's UIA events](../../../docs/uia-bugs.md#a-hung-window-named-in-a-system-focus-event-holds-a-processs-uia-events). Unlike `h1` to `h6`, most of it ran on the user's desktop, an unlocked Remote Desktop session, with real keys where named.

Terms used here, besides those of [the folder's readme](../readme.md):

- `focusproto` is the tool of `h1` to `h6` with one addition, the `vbmap` flag, which removes from the client's proxy factory mapping the same WinEvent entries Verbatim's `verbatim_uia::proxy::ignore_win_events` removes (`focusproto/vbmap.patch`). Verbatim's client settings are `cto=2000,tto=5000,coalesce=1,recovery=1`.
- `evprobe` is the event probe kept with [the flood fault's experiments](../../a-flood-of-uia-events-from-one-application-stops-all-of-a-processs-uia-events/readme.md); its handlers only copy two cached properties and queue them. `q1` and `q3` used it, through `eventthread/evc.py` in that folder.
- TV is mockapp's comctl32 tree view (MSAA backend); B is a UIA mockapp that renames `btn1` or raises a notification 200 ms after the trigger; D is the client under test with a desktop focus handler and B's name changes; the hold is B's event's arrival minus its raise.
- hung-msaa is a TV mockapp started at 20:52 and kept running all evening under Verbatim, driven by `hung-msaa.cmd`; it had been stalled 66 times before `states`.

## The calls (`calls_reg`, `calls_focus`)

- `calls_focus` (`threads/focus2.py`, `threads/focus.cdb`, output `threads/run_focus2.txt`): cdb attached to a running D (connection timeout 2,000 ms) with breakpoints on `RegisterWindowMessageW` and `SendMessageTimeoutW`; TV stalled 7 s and a focus WinEvent named its tree view. On D's `WorkItemQueue` thread UIA's focus tracking (`WinEventTracker::CallbackWorkItem::DoWork`, `FocusTracker::HandleFocusChange`, `GetFocusedElementFromWinEvent`, `ClientProxyManager::GetCompleteProxyNode`) made two calls to the tree view. First, through `ProviderEntryPoint::GetNativeUiaNode`, `ConnectUsingHwnd` and `HwndUtils::SendWmGetObject`: `SendMessageTimeoutW(hwnd, WM_GETOBJECT, wParam, lParam 0xffffffffffffffe7 (UiaRootObjectId), flags 0x22 (SMTO_ABORTIFHUNG | SMTO_ERRORONEXIT), 2000)`. Second, through `ClientProxyManager::InternalGetProxyProvider`, `UiaNodeFactory::InProcProxyFromHwnd`, `ProviderEntryPoint::GetProxyUiaNode`, `ConnectUsingHwnd` and `PerformOperationOnHwndThread`: `SendMessageTimeoutW(hwnd, 0xC1AA, 0, lParam, flags 0, 2000)`. The script resolved 0xC1AA with `GetClipboardFormatNameW`; that output was not kept, but `calls_reg` shows the name.
- `calls_reg` (`threads/focus.py`, output `threads/run_focus.txt`): the same breakpoints from D's start, under cdb. Registering the desktop focus handler (`ClientEventManager::RegisterHandler`, `EventManager::AddEventRecord`, `AssociateWithRecord`, `DoCalldowns`, `TryGetClientChannelConnection`) made the same pair of calls to top-level windows: `RegisterWindowMessageW("UiaServerConnection_HookMessage")` from `PerformOperationOnHwndThreadImpl`, then that message, 0xC1AA, with flags 0 and 2,000 ms. Each window got the `WM_GETOBJECT`; the second call followed for seven windows and not for three others (0x40220, 0x303e2, 0x604c4), so it is made only on the proxy path, after the native path finds no provider of the window's own. The number is assigned by Windows when the message is first registered and is not fixed: `h2_base` on 2026-10-18 saw 0xC199.

## The threads (`threads_name`, `threads_desk`)

`threads/run2.py` started D under cdb with `threads/trace.cdb`, which logs each thread created and the stack of the call that created it.

- `threads_name` (`threads/run_name.txt`): D registered for B's name changes, then B renamed `btn1`. The registration started three of UIA's threads: `NavigationHelperProxyOneCore::s_CoreUIThreadProc` and the I/O thread `OverlappedIOManager::StaticIoThreadProc`, both from the `ElementFromHandle` that precedes the registration, and `WinEventManager::ThreadProc` from `AddPropertyChangedEventHandlerNativeArray` (`WinEventManager::Init`). No `WorkItemQueue` thread existed until the name change arrived: the I/O thread created it (`OverlappedIOManager::IoThreadProc`, `LocalEventCallbackStub::OnMessage`, `WorkItemQueue::AddItem`, `CreateThread`), and the handler ran on it.
- `threads_desk` (`threads/run_desk.txt`): the same with a desktop focus handler (`focusproto.exe client D to=2000 desk:base`, the trace's command line; the script's variant for it was not kept). `AddFocusChangedEventHandler` started the same three kinds, two I/O threads among them; the focus event it delivered during registration ran on the registering thread, and no `WorkItemQueue` thread was created in the trace.

## The focus that escapes (`route1`, `route2`, `both`, `altf`)

- `route1` and `route2` (`threads/focusthr.py`, `threads/focusthr.cdb`; outputs `threads/focusthr.txt` and `threads/focusthr2.txt`, the script having been renamed between them): D with Verbatim's client settings and `vbmap`, attached by cdb with breakpoints on D's focus and name handlers, `FocusTracker::HandleFocusChange` and `SendMessageTimeoutW`. Notepad in front; TV stalled 9 s; a focus WinEvent named its tree view; 0.2 s later B renamed `btn1`; 0.6 s after that Alt+F opened Notepad's File menu, and 0.8 s later Down moved within it.
  - The worker thread entered focus tracking at 05.420 (`route1`) and 44.662 (`route2`), made the 0xC1AA call about 2.3 s later, and was free at 09.740 and 48.975, about 4.3 s in all.
  - While it was held, the menu's focus events reached D's focus handler on a thread-pool thread, through `ClientEventManager::OpenShowWinEventCallbackThreadProc`, `EventManager::AssociateWithRecord`, `RaiseLocalEvent`: 64 handler calls between 06.350 and 07.273 in `route1` (Alt+F was pressed at 06.222), 54 between 45.602 and 46.113 in `route2`.
  - B's name change and the focus events after Down were delivered on the worker thread only once it was free (16 and 18 focus handler calls, through `WorkItemQueue`).
- `both` (`both.py`, results in `both.out`, copied from the session's output): Verbatim's running listener, Notepad in front on the unlocked desktop. TV stalled 9 s, a focus WinEvent named its tree view, B raised a UIA notification 200 ms later, and Alt+F was pressed 0.6 s after that. In each of 3 runs the listener logged B's notification 3,815 to 3,829 ms after it was raised and Notepad's menu focus 26 to 112 ms after the key. Two earlier sets of runs of the same script, at 00:58, are not counted: the desktop had locked and the key reached no window.
- `altf` (`series.py`, its key log `series.keys.log`, and `altf_report.py`, whose output is `altf_report.out`; the speech log it read was not kept): Verbatim running, hung-msaa stalled, a focus WinEvent naming its tree view, then Alt+F in Notepad 1.0 and 2.5 s into the hold and again 6 s in as a control. In the 6 runs between 23:41 and 23:47 in which Notepad was in front (`altf` runs 2 and 3, `altf_bg`), each Alt+F was spoken 126 to 170 ms after the key, in the hold as after it. These runs timed only focus events, which take the open or show route above, so they showed no hold. Not counted: `altf` run 1, in which the Alt+Tab to Notepad failed, and the set at 23:49, in which even the control was silent.

## Verbatim's listener (`states`)

`states.py`, results in `states.out` (copied from the session's output): the running listener, timed by B's UIA notification in its log, and a fresh stand-in D with Verbatim's client settings and `vbmap`, timed by B's name change. TV stalled 9 s and a focus WinEvent named its tree view. Against a new hidden TV, the listener 3,804 to 3,827 ms and the stand-in 3,806 to 3,821 ms; against a new shown TV focused once under Verbatim, the listener 3,807 to 3,822 ms and the stand-in 3,811 to 3,819 ms; against hung-msaa, the listener 7,821 to 7,834 ms, three runs. Why hung-msaa held twice as long is not known. The desktop was found locked at 00:58, just after these runs, and when the lock began is not known, so they may have run on a locked desktop; `both` confirms the listener's hold on the unlocked desktop.

## The hold on a real desktop (`h7`, `ghost`)

- `h7_*` (`h7.py`, one output each; `proto.py` and `keys.py` are its helpers): TV shown on the user's desktop, D with the connection timeout at 2,000 ms, B's rename 200 ms after the trigger; `hung_at_trigger` is `IsHungAppWindow` on TV at that moment.
  - Not yet marked hung, a focus WinEvent naming TV's tree view: `h7_fresh` (at 0 ms, 3,991 and 4,166 ms), `h7_synth_fg` (at 100 ms, TV in front before the stall, 3,980 and 4,139 ms), `h7_synth_bg` (at 100 ms, Notepad in front, 3,987 to 4,151 ms).
  - Marked hung, the same WinEvent 6.5 s into a 15-second stall: `h7_hung`, 1,803 to 1,981 ms, three runs.
  - Real Alt+Tab instead of a synthetic WinEvent: away from TV, which was in front and marked hung (`h7_alttab`, 1 to 2 ms, five runs); back to TV, marked hung (`h7_alttab_to`, 1 to 2 ms) or not yet (`h7_alttab_to_early`, at 2 s, 1 ms). No hold; why the switch to TV raised no WinEvent naming it is not established.
  - TV raising its own focus from inside its stall (`stall 15000 100 focus drafts`): `h7_selfbusy`, 1 to 2 ms.
  - Not kept: four runs with client flags that were not recorded (`vb_*`), which held about 2.0 s in six runs and about 4.0 s in two, without the window marked hung.
- `ghost` (`batch1.out`, from `series.py hung`, with hung-msaa in front and stalled 16 s): 6.5 s into each stall `IsHungAppWindow` answered 1 in every run, and from the fourth run on the foreground window was of class `Ghost`, Windows' stand-in for a hung window. `ishung.py` polls the same once a second; its output was not kept. With `h7_alttab_to_early`, not marked at 2 s, this places the marking between 2 and 6.5 s, which fits the 5 seconds Microsoft documents for `IsHungAppWindow`.

## A slow provider, and a name-change WinEvent (`q3`, `q1`)

Both use `evprobe` with Verbatim's client settings: D with a desktop focus handler and B's name changes, and D0 with B's name changes alone. U is a UIA mockapp and M an MSAA one, both on `small.json`; `slow <ms>` makes every provider call that much late while the window keeps answering messages.

- `q3` (`eventthread/q3.py`, outputs `eventthread/q3_r1.out` to `q3_r3.out` with their logs): U or M slow, then a synthetic focus WinEvent naming the window (`*_we`) or the application's own focus (`*_focus`, `focus btn1` or `focus slider1`). With the WinEvent, D held B's name change 3,807 and 4,818 ms (`slow_uia_we`, 3,000 ms per call), 4,966 and 6,817 ms (`slow_msaa_we`, 3,000 ms), and 3,800 to 3,968 ms (both at 1,000 ms); D0 got it in 1 to 3 ms throughout; the control with U answering at once (`ctl_uia_we`) 2 to 3 ms. The application's own focus held D in some runs and not others: `slow_msaa_focus` 3 ms, 1,803, 3, 3,807, 1,983 and 1,815 ms; `slow_uia_focus` 2, 3, 2 and 3,827 ms.
- `q3`'s stacks (`eventthread/q1stacks.py`, logs `eventthread/q1stacks_*.log`, dumps in `eventthread/stacks/`, a non-invasive cdb attach that pauses D): 1 s into a `q3_slow_uia_we` hold D's `WorkItemQueue` thread was in `HwndUtils::SendWmGetObject` under `FocusTracker::HandleFocusChange`, the same path as `calls_focus`; `*_target_1s` dumps the application instead.
- `q1` (`eventthread/q1.py`, outputs `eventthread/q1_run1.out` to `q1_run4.out` with their logs): D with a desktop-wide name-change registration and a cache request (`deskprop:base`) in place of the focus handler; a name-change WinEvent naming TV's stalled tree view (`stall_tree`) or a stalled M's window (`stall_win`), or a slow M renaming its own client (`slow_msaa`). B's name change arrived in 2 to 3 ms in every case, and in D0 in 2 ms.

## Rerunning

`focusproto` builds as the folder's readme says, after applying `focusproto/vbmap.patch` to its `main.rs`; this series built it standalone (`focusproto/Cargo.toml.txt`, with its own `[workspace]` table) and the scripts expect it at `fp/target/debug/focusproto.exe` beside them, with `mockapp` built in the repository's `target/debug`. `evprobe` builds as its folder says. The scripts that press keys (`h7.py`, `series.py`, `both.py`, `focusthr.py`) and those that time the listener (`states.py`, `both.py`, which read a running Verbatim's `listener.log` at a path to edit) need an unlocked desktop with a Notepad window titled `notes.txt` and take it over while they run; cdb's path is in each script. Run them with `python -I` from a folder holding `proto.py` and `keys.py`.
