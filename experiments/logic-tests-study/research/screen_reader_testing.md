# How screen readers and assistive technology projects test their software

Researched 2026-10-31. The primary sources were the current NVDA source (`nvaccess/nvda` master at commit 0041ab65, dated 2026-10-30, cloned from GitHub), the current Orca source (GNOME GitLab main, last commit 2026-10-30, cloned), W3C specifications and meeting minutes, Bocoup's blog, and Chromium, Mozilla, Google and Android documentation. Note that the local `nvda/` submodule in this repository was empty in this checkout, so NVDA facts come from a fresh clone of master and not from the pinned revision.

## NVDA: unit tests, system tests, speech assertions, flakiness and strategy discussions

### Takeaway
NVDA tests in two layers: Python unit tests that mock heavily, including a hand-built interaction harness for the speech manager, and a small Robot Framework system-test suite. The system tests have nine robot files covering Chrome, VS Code, settings, installer, startup and symbols. They capture speech through a spy synth and global plugin, call speech "finished" after 1 second of silence, and match by substring. Fixed sleeps are documented as workarounds for dialogs dropping keys, and flaky tests are tagged out with `excluded_from_build`. No property-based, fuzz, simulation or formal-methods testing appears in the tree.

### Cited Findings
- Unit tests live in `tests/unit`, with about 70 modules and packages. Examples are `test_speechManager`, `test_UIARemoteOps`, `test_NVDAObjects_UIA.py`, `test_orderedWinEventLimiter.py`, `test_speechSayAll.py`, `test_browseModeSentenceDispatch.py`, `test_appModules` and `test_braille` — [nvaccess/nvda tests/unit](https://github.com/nvaccess/nvda/tree/master/tests/unit)
- `tests/unit/test_speechManager/speechManagerTestHarness.py` is a deterministic interaction harness. It mocks the synth's `speak` and `cancel` and lets a test drive `indexReached`, `doneSpeaking` and `pumpAll` (pumping the queue handler) by hand. Expectations are expressed as `ExpectedIndex` and `ExpectedProsody` objects, with `expect_synthCancel` and `assertExpectedStateNowMet`. This is the closest thing in NVDA to a simulated, deterministically scheduled component test — [speechManagerTestHarness.py](https://github.com/nvaccess/nvda/blob/master/tests/unit/test_speechManager/speechManagerTestHarness.py)
- A grep of NVDA's `tests/` tree found no use of `hypothesis` or any other property-based testing library (checked 2026-10-31) — [nvaccess/nvda tests](https://github.com/nvaccess/nvda/tree/master/tests)
- System tests use Robot Framework through `runsystemtests.bat --include <TAG>`. Robot starts NVDA as a new process with a sandbox profile that is overwritten for each test (`-c`). A `SystemTestSpy` package installs a global plugin, `speechSpyGlobalPlugin`, which runs a Robot Remote Server, plus a spy synth driver. The readme tells authors to behave like a user and "wait for the speech to confirm that an expected dialog is open before taking the next action". Flaky tests are disabled with the `excluded_from_build` tag, with an example comment of "Excluded due to intermittent failure". Chrome tests warn that no previous Chrome instance may be open — [tests/system/readme.md](https://github.com/nvaccess/nvda/blob/master/tests/system/readme.md)
- The robot suites present on 2026-10-30 are NVDAInstaller, NVDASettings, browseableMessageTests, chromeTests, l10nTests, startupShutdownNVDA, symbolPronunciationTests and vscodeTests. `chromeTests.py` holds 51 `test_` functions. Support libraries are ChromeLib, NotepadLib, VSCodeLib, WindowsLib, NvdaLib and AssertsLib. The NVDASettings suite is force-tagged `excluded_from_build` and used only for settings diffs — [tests/system/robot](https://github.com/nvaccess/nvda/tree/master/tests/system/robot)
- Speech-finished detection in the spy uses timing. `SPEECH_HAS_FINISHED_SECONDS: float = 1.0`, and `_hasSpeechFinished` returns true once speech has started and more than 1.0 s has passed since the last utterance. Waits are bounded by `giveUpAfterSeconds` (often 10 s, capped by the Robot keyword timeout). Speech search is a substring match: `any(speech in x for x in baseStrings)` — [speechSpyGlobalPlugin.py](https://github.com/nvaccess/nvda/blob/master/tests/system/libraries/SystemTestSpy/speechSpyGlobalPlugin.py)
- The libraries contain fixed sleeps with comments admitting the cause. `startupShutdownNVDA.py` and `NVDAInstaller.py` contain `sleep(1)` with the comment "the dialog is not always receiving the enter keypress, wait a little longer for it". `WindowsLib.py` has "# Hack: using 'sleep' is error-prone." followed by `sleep(3)`. `_chromeArgs.py` passes `--browser-test` with the comment "Enable browser test mode, helps reduce flakey tests" — [tests/system/libraries](https://github.com/nvaccess/nvda/tree/master/tests/system/libraries)
- PR #10553, "System tests with HTML samples", was opened 2019-11-27 and merged 2020-04-14 for 2020.2. It moved test logic from Robot syntax into Python because Robot-only tests were hard to read with a screen reader and hard to write, since speech output contained Robot's argument separators. It also added Chrome HTML-sample tests. Early commits fixed AppVeyor problems, including "allowing variation in the number of tab presses needed to reach the start marker". A known issue was that Chrome was not closed at the end of a test — [PR #10553](https://github.com/nvaccess/nvda/pull/10553)
- PR #11776, "Fix system tests", fixed a locking bug in the spy, where a new lock was created for each critical section, and made the speech start index declarable. It also handled focus sometimes landing on the document or URL bar when Chrome tests start — [commit cb156d20 via semanticdiff](https://app.semanticdiff.com/gh/nvaccess/nvda/commit/cb156d2056649e1e7b4fb17b611e82e9341ac879)
- The original request for an automated system-testing framework was issue #708, filed in 2010 and now closed — [issue #708](https://github.com/nvaccess/nvda/issues/708)

### Inferences
- NVDA's end-to-end coverage is narrow, mostly Chrome browse mode. Its approach to speech assertions uses a 1-second quiet period and substring matching, both of which Verbatim's `docs/testing.md` forbids. NVDA's own sleeps show the cost of not having an evidence-based wait for dialog readiness.
- The speech-manager harness is a useful pattern: a component with real asynchrony (synth callbacks, index reached, cancel) tested by manually stepping its event sources against a mocked synth.

### Gaps
- I could not list NVDA issues labelled about intermittent system-test failures, because the GitHub search API was not available in this session and web search found no single tracking issue. NVDA's current CI provider for system tests (AppVeyor historically, possibly GitHub Actions now) was not confirmed from primary sources here.

## Orca (GNOME): history of the regression harness, what replaced it and why

### Takeaway
Orca's old harness replayed recorded keystrokes, later Macaroon scripts, and compared speech and braille with expected output. It was renamed `test-historical` on 2024-06-28 because the tests "have always been quite flakey and are largely unmaintained", then deleted on 2025-07-25. A new pytest-based integration suite replaced it, with 444 files and over 1,500 test cases. The new suite runs a real Orca with a no-audio speech server and asserts speech and braille. It waits by output quiescence gated on an `IsIdleForTesting` D-Bus call into Orca, and since 2026-10-01 it retries assertion failures once on CI. Many commits in 2026 are flake fixes, and some of them fixed real timing bugs in Orca itself.

### Cited Findings
- The early harness ran keystrokes against a specific application and compared Orca's speech and braille with expected output — [Linux Foundation AT-SPI test wiki](https://wiki.linuxfoundation.org/accessibility/atk/at-spi/reference/tests). A 2006 release announced a "new and improved regression test harness" — [LWN](https://lwn.net/Articles/203197/)
- Macaroon is a desktop macro tool with a Python-based script format, used heavily for Orca regression testing. The post says it produced "a huge collection of scripts that play back reliably and fairly quickly" — [blog.monotonous.org, 2007-10-18](https://blog.monotonous.org/2007/10/18/making-freedom-accessible). A 2014 commit by Joanmarie Diggs rewrote Calc, slider and progress-bar tests on `macaroon.playback` — [GNOME commits-list 2014-07](https://mail.gnome.org/archives/commits-list/2014-July/msg02292.html)
- Orca git history shows regular "New test case" and "Updated tests" commits through 2015 to 2018 (last 2018-11-23). On 2024-02-15 and 2024-02-19 came "Remove some extremely old and unmaintained tests" and "Eliminate some old, unmaintained tests". Commit 940ba79a4 on 2024-06-28, "test -> test-historical", has the message "These tests have always been quite flakey and are largely unmaintained. We're in the process of creating new tests, so let's start fresh." Commit 88af0b04f on 2025-07-25, "Remove the old test harness and keystrokes files", says "We're migrating to pytest, and the old harness was unmaintained." The first new pytest tests landed the same day (da5917249, "Create pytest tests") — [GNOME/orca git](https://gitlab.gnome.org/GNOME/orca)
- On 2026-10-30, `tests/` held 444 files: 90 unit tests, 192 integration-test files, 36 test apps (GTK3 and GTK4 widgets, terminals, browsers, Atril), 112 web pages, and a 5-file harness (`dummy_speech_server.py`, `keyboard.py`, `orca_session.py`, `sandbox.py`) — [GNOME/orca tests](https://gitlab.gnome.org/GNOME/orca/-/tree/main/tests)
- The README makes several points. "Prefer integration tests for new coverage", and unit tests only "for behavior that cannot be adequately tested through integration tests". Tests simulate keys (`tap_key()`, `press_chord()`) and check speech and braille. For bug fixes the instruction is to "confirm that the test fails without the fix and passes with it". The suite has "over 275 Meson test runs containing over 1,500 test cases", split into the suites core, document, gtk3, gtk4, gtk3-terminal, gtk4-terminal, chromium and gecko, and web tests run in both browsers. "A full local run can take around 90 minutes". CI runs the suites in parallel containers. The suites need Xvfb, a private D-Bus session and AT-SPI. Orca must not already be running, because each test launches its own Orca and the harness deliberately does not kill a running one. Fedora and openSUSE are supported, and other distros pass "modulo flakes" — [tests/README.md](https://gitlab.gnome.org/GNOME/orca/-/blob/main/tests/README.md)
- Waiting in the harness: `helpers.py` drains output "until the output stream goes quiet". Quiescence is 0.1 s for prompt output and is "idle-gated", while app-delayed output uses 0.5 s with `idle_aware=False`, with an overall timeout of 2.0 s by default. `orca_session.py` exposes `is_idle()`, which calls `EventManager.IsIdleForTesting` over D-Bus with an RPC secret, and this is implemented in `src/orca/event_manager.py`. Startup readiness polls a D-Bus `GetVersion` for up to 45 s, and `ORCA_TEST_TIMEOUT_SCALE` scales the waits. Meson gives each test a default timeout of 120 s — [Orca tests/integration_tests](https://gitlab.gnome.org/GNOME/orca/-/tree/main/tests/integration_tests)
- `tests/integration_retry.py` "Runs integration tests with one CI-only retry for assertion failures". Only assertion failures are retried, and setup errors or xfails block the retry. It comes from commit 125cb93b9 of 2026-10-01, "Integration Tests: Retry flakes once on CI", followed by "Capture debug log on retry of flakes/failures in CI". The retry runner has its own unit test (`test_integration_retry.py`) — [GNOME/orca git](https://gitlab.gnome.org/GNOME/orca)
- Commits about flakes in 2026 include "Fix some flakiness related to say all" (07-25), "related to terminal output" (07-25), "braille update in web form" (07-25), "Handle VTE-timing-triggered flake" (09-30), "flakiness related to object destruction" (10-01), "browser test flakiness" (10-12), "Enable MathCAT on CI; add diagnostics for some flakes" (10-29), and "Text Selection: Fix a timing issue leading to missing speech" (10-29, a product fix). Several commits update the "known failures" lists (for example 2026-10-27) — [GNOME/orca git log for tests](https://gitlab.gnome.org/GNOME/orca/-/commits/main/tests)
- No property-based testing library appears in Orca's `pyproject.toml`, which lists only pytest tooling — [pyproject.toml](https://gitlab.gnome.org/GNOME/orca/-/blob/main/pyproject.toml)
- In January 2024, Sam Thursfield proposed testing Orca in GNOME OS openQA by capturing audio and checking for "Screen reader on". The obstacles were interruption by "29 push button" from a focused calendar, whose date changes daily, and dependence on speech rate — [GNOME Discourse, 2024-01-03](https://discourse.gnome.org/t/testing-orca-screen-reader-in-openqa-help-wanted/18809)

### Inferences
- Orca dropped recorded-keystroke replay because of flakiness and maintenance cost. It replaced replay with code-written tests that wait on an idle query exposed by the screen reader itself. This is an internal readiness signal similar in spirit to waiting for evidence. Even so, it still combines that signal with quiet-period timeouts and a CI retry, and flake fixes continue at a rate of several a month.
- Orca shows flake hunting paying off: at least one 2026 flake turned out to be a real speech-loss timing bug in Orca.

### Gaps
- I did not find a public design write-up or mailing-list post by Joanmarie Diggs explaining the 2025 pytest rewrite beyond the commit messages. I did not confirm when `IsIdleForTesting` was introduced, because the history search timed out.

## JAWS, Narrator, VoiceOver, TalkBack, ChromeVox, Fusion, Dolphin, and the browser accessibility suites

### Takeaway
There is almost nothing public on how JAWS, Fusion, Dolphin, Narrator, VoiceOver or TalkBack test the screen reader itself. One old patent describes a scheme for recording screen reader output and replaying it for regression comparison. ChromeVox is open source and tested in Chromium `browser_tests` with a `MockFeedback` that asserts speech and braille. Chromium and Firefox test the accessibility tree that screen readers read, with golden-file tree and event dumps per platform API. Chrome has published a coverage-guided fuzzer that drives its UI through the accessibility tree.

### Cited Findings
- A US patent, US6889337B1, "Method and system for screen reader regression testing", describes recording test input together with the screen reader's output for later comparison on each release — [Google Patents](https://patents.google.com/patent/US6889337). The assignee and date were not verified here.
- ChromeVox: a 2015 change added a `mockFeedback` class that handles speech and braille and supersedes `MockTts`. Another change forced ChromeVox Next on in its tests because mixed Classic and Next feedback was causing flakiness — [codereview.chromium.org/1295213003](https://codereview.chromium.org/1295213003/). The developer doc runs these tests as `browser_tests` with a filter like `*ChromeVox*E2E*` — [ChromeVox for developers](https://chromium.googlesource.com/chromium/src/+/lkgr/docs/accessibility/os/chromevox.md). A later commit notes a background test that passed only because of extra speech, tied to a known issue — [commit 9d08020](https://chromium.googlesource.com/chromium/src/+/9d08020d3b500caf8dd775978e79902e8651b565)
- Chromium dump-accessibility tests compare output with exact per-platform expectation files (`-expected-win.txt`, `-uia-win.txt`, `-auralinux.txt`, `-mac.txt`, `-android.txt`, `-blink.txt`). They use platform-prefixed attribute filters (`@WIN-ALLOW:`, `-DENY`), `@WAIT-FOR:` and `@EXECUTE-AND-WAIT-FOR:` for timing, and `#<skip` to disable a test. A missing expectation file means the test passes, and "most tests don't have expectations on all platforms". Rebaselining uses `--generate-accessibility-test-expectations` or `rebase_dump_accessibility_tree_tests.py`. Events tests call `go()` and record events until a sentinel event — [content/test/data/accessibility/readme.md](https://chromium.googlesource.com/chromium/src/+/main/content/test/data/accessibility/readme.md)
- Chrome security fuzzing: in an October 2024 post, Google describes a coverage-guided, in-process fuzzer that interacts with Chrome UI controls through the accessibility tree. Selecting controls by ordinal was fragile as the UI changed, so the fuzzer mixes name-based and ordinal mutators, and selecting by name alone was far less effective. It had found "a couple" of potential bugs in accessibility code by then — [Google Security Blog, 2024-10](https://security.googleblog.com/2024/10/using-chromes-accessibility-apis-to.html?m=1)
- Firefox: browser tests use `addAccessibleTask`. This runs the same test across document configurations (top-level remote, parent process, in-process and out-of-process iframes) and waits for the accessibility tree to be built. The `atk` and `windows` directories are "an older, legacy test suite which only supports testing LocalAccessible in a single process". `caching_granularity` tests check cache domains — [Firefox a11y Guidelines for New Contributors](https://firefox-source-docs.mozilla.org/accessible/GuidelinesForNewContributors.html); [searchfox caching_granularity](https://searchfox.org/firefox-main/source/accessible/tests/browser/caching_granularity/browser_name_and_description_domain.js)
- Android: Google's Accessibility Test Framework (ATF) runs lint-style checks during Espresso tests through `AccessibilityChecks.enable()`, optionally from the root view, with `setSuppressingResultMatcher()` for known issues. It checks apps, not TalkBack — [Android Espresso accessibility checking](https://developer.android.com/training/testing/espresso/accessibility-checking)
- Guidepup offers a single API to drive real VoiceOver on macOS and NVDA on Windows, and `@guidepup/virtual-screen-reader`, a simulator for unit tests that its authors say "should not replace but augment" real screen reader testing — [guidepup](https://github.com/guidepup/guidepup); [virtual-screen-reader](https://github.com/guidepup/virtual-screen-reader/)

### Inferences
- The browser suites are the most mature published practice. They use exact golden dumps per platform API, explicit waits on content, and tooling to rebaseline. The gap they accept is that expectations can be missing on some platforms. A screen reader could apply the same golden-file style to its own normalized model of an application or to its speech sequences.

### Gaps
- I found nothing public on internal test practice for JAWS, Fusion or ZoomText (Freedom Scientific / Vispero), Dolphin, Narrator, VoiceOver or TalkBack's own test suites. Job postings and talks were not found in the searches run. Apple's XCUITest `performAccessibilityAudit` (2023) exists for app auditing but was not fetched here. Dolphin: nothing found.

## Cross-implementation work: ARIA-AT and AT Driver

### Takeaway
ARIA-AT (W3C Community Group, with Bocoup and others) collects screen reader responses to scripted web interactions and judges them against assertions. Human verdicts are reused when a bot's captured output equals a previously judged output. This is in effect a recorded-output differential check. AT Driver is the WebSocket protocol for it, and its spec admits that captured output cannot be tied to a specific command and that it does not define when speech has finished. The reported problems are unprompted speech, interruptions the bot hears but humans do not, an unreliable VoiceOver capture, mobile restrictions, and doubt about detecting regressions.

### Cited Findings
- AT Driver is a W3C Editor's Draft (5 September 2026, Browser Testing and Tools WG; editor Mike Pennisi of Bocoup). It runs over WebSocket and JSON with CDDL, modeled on WebDriver BiDi. Its modules are `session`, `settings` and `interaction`. The `interaction.userIntent` `pressKeys` command simulates keys, and the `interaction.capturedOutput` event carries text sent to speech or braille. The spec says `userIntent` returns only a generic success that "cannot be reliably tied to the AT's responses", that events may arrive before the command result, and that settings changes may not be verifiable. It recommends that AT Driver be disabled in public builds and limited to loopback — [AT Driver spec](https://w3c.github.io/at-driver/)
- The explainer gives the motivation: keys sent through WebDriver stay inside the browser, and WebDriver cannot read speech. Implementations are the NVDA add-on from Prime Access Consulting (`nvda-at-automation`), Bocoup's macOS AT Driver server, and a partial "Generic Driver" — [w3c/aria-at-automation](https://github.com/w3c/aria-at-automation); [w3c/at-driver](https://github.com/w3c/at-driver)
- Capture method: the NVDA plug-in uses Python plus a Go server. For VoiceOver, Bocoup built a macOS TTS voice that forwards text instead of audio, because AppleScript was not expressive enough. "The VoiceOver capture method is unreliable", with causes still under investigation. Mobile restrictions push toward speech-to-text or OCR — [Bocoup, "Smuggling words", 2025-03-17](https://bocoup.com/blog/smuggling-words)
- Verdict reuse: when a bot's output matches output a human previously judged, the system assigns the same verdicts. Testers found bot-run plans handed to them ambiguous about which assertions had been judged automatically — [aria-at-app issue #1045](https://github.com/w3c/aria-at-app/issues/1045); [public-aria-at, Feb 2025](https://lists.w3.org/Archives/Public/public-aria-at/2025Feb/0001.html)
- From the meeting of 2025-09-08:
  - "The bot recorded double speech but most human users couldn't detect the duplication" (Matt King).
  - AT Driver "is ignorant of those interruptions" (Mike Pennisi).
  - "Both JAWS and NVDA aren't technically capable of linking utterances with specific user interactions".
  - "AT-driver might not be able to detect product regressions" (Matt King).
  - The runner waits 1 s after navigation and 5 s after each key press.
  - A proposal was to treat a gap of under 50 ms between utterances as a sign of interruption.
  - Next steps were timestamps on speech events and priority levels.

  — [W3C ARIA-AT IRC, 2025-09-08](https://www.w3.org/2025/09/08-aria-at-irc)
- Bocoup said it had begun talking with JAWS implementers about their own AT Driver implementation — [search summary of W3C/Bocoup sources](https://bocoup.com/blog/interoperability-testing-for-assistive-technologies-and-the-web-platform); not independently confirmed

### Inferences
- ARIA-AT confirms that black-box speech capture without a link to the cause of each utterance is the core difficulty. A screen reader that records which input or event caused each utterance (Verbatim owns its reducer) can make assertions ARIA-AT cannot. Its verdict reuse amounts to golden-output regression with human triage. The double-speech finding shows that raw synth input differs from what users hear once interruption is applied.

### Gaps
- I found no published pass-rate or flakiness figures for the ARIA-AT bots, and could not fetch the 2024 automation-launch post (HTTP 403).

## Research papers on testing screen readers or assistive technology

### Takeaway
I found no peer-reviewed paper on testing the internals of a screen reader. What exists is the 2005 patent, technical disclosures on comparing screen reader output with baselines (including with AI validation), a German practitioner talk on scaling accessibility regression tests, and app-side accessibility research.

### Cited Findings
- US6889337B1 records screen reader output for comparison across releases — [Google Patents](https://patents.google.com/patent/US6889337)
- Technical Disclosure Commons hosts a disclosure proposing AI validation of screen reader output against a recorded baseline, and an October 2024 disclosure on diff-based regression testing of UI changes that break screen reader behavior (Miller, Wang, Sennadj). Only the abstracts were seen — [tdcommons 10415](https://www.tdcommons.org/dpubs_series/10415); [tdcommons 7422](https://www.tdcommons.org/dpubs_series/7422)
- GI TAV 52 talk (Scherer, 2025), on scaling automated accessibility regression tests, in German — [PDF](https://fg-tav.gi.de/fileadmin/FG/TAV/52.TAV/TAV52_Scherer_A11YRegrTestsSkalierung.pdf)

### Inferences
- No project I found uses property-based testing, formal methods, deterministic simulation or differential testing against another screen reader for the screen reader itself. The nearest are Chrome's accessibility-tree fuzzer (browser side), NVDA's hand-stepped speech-manager harness, ARIA-AT's comparison against recorded output, and Guidepup's virtual screen reader (simulation for web authors).

### Gaps
- I did not search ACM DL or ASSETS proceedings directly. There may be academic work on mobile accessibility-service testing, for example of Android apps with TalkBack, that was not surfaced.
