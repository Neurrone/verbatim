# Rust crates and approaches for verifying correctness, judged for Verbatim

Context for the writer: Verbatim is std threads plus Windows I/O completion ports, no async runtime, blocking COM and UI Automation calls in Windows-bound shells, and logic in pure reducers joined across processes by pipes. Release and download figures below come from the crates.io API, queried on 2026-10-31 (field `updated_at`, which tracks the latest publish; "recent" means downloads in the last 90 days). In-repo check: the workspace already depends on `proptest` (one Cargo.toml), used by `crates/verbatim-term-sim/src/oracle.rs`, `crates/verbatim-term-sim/tests/oracle.rs` and `crates/verbatim-text/tests/terminal_oracle.rs`; no loom, shuttle, insta, fuzz or Kani use was found.

## Generated testing: proptest, proptest-state-machine, quickcheck, bolero, arbitrary with cargo-fuzz, Hegel

### Takeaway
proptest plus proptest-state-machine is the mature, actively maintained choice and fits pure reducers directly (std only, no runtime, runs under plain `cargo test` on Windows); it is already in the workspace. Hegel (Hypothesis engine for Rust, from Antithesis-employed Hypothesis developers) is the new and fast-moving alternative but is beta; bolero and cargo-fuzz are for coverage-guided fuzzing and are a poor fit for Windows CI.

### Cited Findings
- proptest 1.12.0 and proptest-state-machine 0.9.0, both published 2026-10-10; proptest has about 229 million total downloads (67 million in 90 days), proptest-state-machine about 3.8 million — [crates.io proptest](https://crates.io/crates/proptest), [crates.io proptest-state-machine](https://crates.io/crates/proptest-state-machine) (API queried 2026-10-31).
- proptest-state-machine "provides state machine based testing support for proptest"; the `prop_state_machine!` macro takes a header saying whether transitions run sequentially or concurrently, but "only sequential is supported", a range of how many transitions to generate, and a type implementing `StateMachineTest`; detail on `ReferenceStateMachine`, preconditions and shrinking is in the Proptest Book's "State Machine testing" chapter — [docs.rs proptest-state-machine](https://docs.rs/proptest-state-machine/latest/proptest_state_machine/).
- quickcheck 1.1.0, published 2026-02-10, about 77 million downloads — [crates.io quickcheck](https://crates.io/crates/quickcheck).
- bolero 0.13.7, published 2026-10-03, about 6.3 million downloads — [crates.io bolero](https://crates.io/crates/bolero).
- bolero is "a front-end framework for fuzzing and property testing in Rust" with corpus replay, input shrinking, stable Rust support, structured testing, a unified interface and Miri support; repository topics list afl, honggfuzz and libfuzzer; the `cargo-bolero` install notes are Linux only (Debian packages `binutils-dev`, `libunwind-dev`) — [bolero README](https://github.com/camshaft/bolero), [bolero book](https://camshaft.github.io/bolero/).
- arbitrary 1.5.0 (2026-10-06, about 189 million downloads), cargo-fuzz 0.13.2 (2026-06-09), libfuzzer-sys 0.4.13 (2026-06-04), afl 0.18.2 (2026-05-11), Trail of Bits test-fuzz 8.1.1 (2026-08-02) — [crates.io arbitrary](https://crates.io/crates/arbitrary), [cargo-fuzz](https://crates.io/crates/cargo-fuzz), [libfuzzer-sys](https://crates.io/crates/libfuzzer-sys), [afl](https://crates.io/crates/afl), [test-fuzz](https://crates.io/crates/test-fuzz).
- Hegel is "property-based testing, based on Hypothesis": a native engine (libhegel, C ABI, shipped as prebuilt libraries and the `hegeltest-c` crate) does generation, shrinking and bookkeeping, with thin frontends for Rust (`hegeltest`), Python, TypeScript, C++, Java and OCaml; it "is in beta" and keeps a compatibility page of what may still change; MIT licence — [hegeldev/hegel](https://github.com/hegeldev/hegel).
- Hegel is "developed in part by Hypothesis developers as part of their work at Antithesis" — [hegel.dev](https://hegel.dev/).
- The Rust crate is `hegeltest` 0.51.0, published 2026-10-29, about 1.4 million total downloads, 1.2 million of them in the last 90 days; the older standalone `hegel-rust` repository is archived and moved into the monorepo under `frontends/rust/` — [crates.io hegeltest](https://crates.io/crates/hegeltest), [hegel-rust (archived)](https://github.com/hegeldev/hegel-rust). Note: the crate named `hegel` on crates.io is an unrelated 2022 crate with about 3,000 downloads — [crates.io hegel](https://crates.io/crates/hegel).

### Inferences
- A reducer (state plus input gives new state plus effects) is the ideal shape for proptest-state-machine: the reference model is a simplified reducer, the system under test is the real reducer, and effects are compared exactly, which meets the repo's exact-assertion rule. Because it is sequential only, it tests the reducer, not the threads around it; that is the correct split for this architecture (concurrency left to shuttle or loom on the thin hand-off layer).
- proptest shrinks via value trees and stores failing seeds in `proptest-regressions` files, which gives reproducibility in CI; the CLAUDE.md principle "A pure state machine with many lifecycle paths gets generated invariant tests" is already met with this tool at no new dependency cost.
- Hegel's Hypothesis-style integrated shrinking usually yields smaller counterexamples than proptest for structured data, but at 0.x with a beta label and a 0.51 version churn it carries API-break risk; whether its prebuilt libhegel ships for Windows ARM64 (a first-class target here) was not verified.
- cargo-fuzz and libFuzzer are coverage-guided and best for parsers (for example pipe-protocol frame decoding, terminal escape parsing, config parsing); MSVC supports `-fsanitize=fuzzer`, but most Rust fuzz tooling and docs assume Linux, so running fuzzing on a Linux CI job against the platform-neutral crates is the practical route. bolero is attractive because one harness runs as a property test under `cargo test` and as a fuzz target.

### Gaps
- Not confirmed: Hegel's stateful-testing API, its Windows and ARM64 support, and whether the Rust frontend needs anything beyond the native library; the fetched pages did not say.
- bolero's Kani engine, Windows support and state-machine helpers were not documented on the pages fetched.
- No independent comparison of shrinking quality between proptest, quickcheck and Hegel was found in this session.

## Simulation and concurrency: madsim, turmoil, shuttle, loom

### Takeaway
madsim and turmoil are async, tokio-shaped deterministic simulators and do not fit a std-threads, IOCP, no-async design. shuttle (AWS, randomized, scales) and loom (Tokio, exhaustive, small models) work with std threads but only for code written against their replacement types; neither can see Windows kernel objects, IOCP, COM or real pipes, so they apply only to the hand-off layer once it is expressed with std or crate primitives.

### Cited Findings
- shuttle 0.9.9, published 2026-10-29, about 7 million downloads — [crates.io shuttle](https://crates.io/crates/shuttle).
- shuttle "controls how each thread in a program is scheduled" and runs threads in random order, reproducing failures deterministically; it implements randomized techniques including PCT, a scheduler with probabilistic bug-finding guarantees; it is "inspired by Loom" but trades soundness for scalability: "a passing Shuttle test does not prove the code is correct"; drop-in `shuttle::thread` and `shuttle::sync` replace std, with wrappers for `std::sync`, `std::collections`, tokio and rand; Apache-2.0, about 1,100 stars — [awslabs/shuttle](https://github.com/awslabs/shuttle).
- loom 0.7.2 was published 2024-04-23 (no release for about two and a half years) yet has about 76 million downloads, 19 million in the last 90 days — [crates.io loom](https://crates.io/crates/loom).
- loom explores every interleaving by default; interleavings grow exponentially with thread count; it caps threads (`MAX_THREADS`), offers `LOOM_MAX_PREEMPTIONS` with a bound of 2 or 3 said to catch most bugs; it cannot model every `Relaxed` reordering; it only sees operations through its replacement types, and every library in the stack must also support loom; tests must be fully deterministic with random numbers and system calls mocked; its scheduler is unfair so spin loops need `yield_now`; code switches types via `#[cfg(loom)]` and runs with `RUSTFLAGS="--cfg loom"` — [loom docs](https://docs.rs/loom/latest/loom/).
- madsim 0.2.34, published 2025-10-11 — [crates.io madsim](https://crates.io/crates/madsim). madsim disallows spawning system threads by default, warning it "may cause the test to be non-deterministic" (opt in with `MADSIM_ALLOW_SYSTEM_THREAD`); its runtime runs the future on the current thread — [madsim builder source](https://docs.rs/crate/madsim/latest/source/src/sim/runtime/builder.rs), [madsim runtime source](https://docs.rs/crate/madsim/latest/source/src/sim/runtime/mod.rs). madsim intercepts libc functions such as `gettimeofday`, `clock_gettime` and `getrandom` for simulated time and randomness — [RisingWave blog](https://risingwave.com/blog/deterministic-simulation-a-new-era-of-distributed-system-testing/).
- turmoil 0.7.2, published 2026-04-24 — [crates.io turmoil](https://crates.io/crates/turmoil). turmoil is "a family of crates for deterministic simulation testing of distributed systems", runs "multiple concurrent hosts within a single thread", simulates network latency, drops and partitions, and offers drop-in replacements for `tokio::net` and `tokio::fs` plus simulated filesystem torn writes and io_uring — [tokio-rs/turmoil](https://github.com/tokio-rs/turmoil).

### Inferences
- madsim: needs async code on its runtime and libc interception, which is Linux-libc specific; no fit for blocking Win32 and COM calls. turmoil: built around tokio's networking and filesystem types and a single-thread host model; no fit without rewriting the pipe layer as tokio.
- The more useful idea from these tools is architectural, not the crate: Verbatim's pure reducers already allow deterministic simulation without a framework, by driving several reducers in one test thread and routing their effects as each other's inputs through an in-memory pipe model, with a seeded scheduler choosing delivery order, drops and process restarts. That is a hand-rolled turmoil-style simulator over reducers, which sidesteps the async requirement.
- shuttle is the better fit of the two concurrency checkers for this codebase: it scales to real-size tests, is actively released (October 2026), and accepts std-thread code once `std::sync` and `std::thread` are aliased through a `cfg` module. Kernel waits (`WaitForSingleObject`, `GetQueuedCompletionStatus`) are invisible to it, so the IOCP and COM layer must sit behind a trait with a channel-based fake in tests. loom is right only for very small hand-off kernels (for example a single slot or wake protocol), and its lack of releases since April 2024 is a maintenance risk, though Tokio still uses it.
- Both tools reinforce the CLAUDE.md rule "Write no concurrency by hand": the less hand-written hand-off there is, the less needs loom or shuttle.

### Gaps
- No source fetched lists shuttle's unsupported std primitives (for example `Condvar` variants, `thread::park` timeouts, `std::sync::mpsc` select-like patterns) or its notable users beyond AWS authorship.
- Whether loom or shuttle compile and run on Windows ARM64 was not checked; both are pure Rust, so it is likely but unverified.

## Model checking and verification: Kani, stateright, TLA+, P, Creusot, Prusti, Verus

### Takeaway
Kani is the most practical proof tool for a small Rust team, for bounded proofs of pure, sequential functions (reducer transitions, parsers, index arithmetic), but it does not model concurrency and runs only on Linux and macOS, so it would run on a Linux CI job against the platform-neutral crates. P is the closest conceptual fit (communicating state machines, used for the Windows 8 USB stack, at AWS, with PObserve checking production logs against specs) but is a separate model, not the Rust code. stateright checks Rust actor code itself; Verus, Creusot and Prusti are research-grade deductive verifiers with high annotation cost.

### Cited Findings
- kani-verifier 0.68.0, published 2026-09-16 — [crates.io kani-verifier](https://crates.io/crates/kani-verifier).
- Kani: concurrency is "currently out of scope"; it warns and compiles concurrent code as sequential; data races and `await` are unsupported; inline assembly is unsupported (global assembly aborts); panic stack unwinding is unsupported — [Kani Rust feature support](https://model-checking.github.io/kani/rust-feature-support.html).
- Kani's published platforms for 0.66.0 are aarch64-apple-darwin, aarch64-unknown-linux-gnu and x86_64-unknown-linux-gnu; install instructions say Linux or Mac — [docs.rs kani-verifier](https://docs.rs/crate/kani-verifier/latest/source), [model-checking/kani](https://github.com/model-checking/kani).
- stateright 0.31.0, published 2025-07-27, about 15 million downloads — [crates.io stateright](https://crates.io/crates/stateright). stateright is "a model checker for implementing distributed systems": an actor library with an embedded model checker, a browser explorer UI, and a runtime that runs the same actor code on a real network; it checks "always" invariants, "sometimes" reachability and experimental "eventually" liveness, offers symmetry reduction, lossy and duplicating network models, and linearizability and sequential-consistency testers; MIT, about 1,900 stars — [stateright/stateright](https://github.com/stateright/stateright).
- P is a state-machine language for modelling distributed systems; P-Checker explores interleavings of messages and failures and produces reproducible error traces; PEx does exhaustive checking and PVerifier formal proofs; AWS teams use P for S3, EBS, DynamoDB, MemoryDB, Aurora, EC2 and IoT; PObserve "validate[s] that your production system conforms to its formal P specifications" by checking service logs against P monitors; CI badges cover Windows, Ubuntu and macOS, distributed via NuGet — [P documentation](https://p-org.github.io/P/).
- The PLDI 2013 paper (Desai, Gupta, Jackson, Qadeer, Rajamani, Zufferey) says P was used to implement and verify the core of the Windows 8 USB device driver stack, producing a driver more reliable and faster than its predecessor; P programs are interacting state machines with deferred events and the checker ensures no unhandled events — [Microsoft Research publication](https://www.microsoft.com/en-us/research/publication/p-safe-asynchronous-event-driven-programming/), [paper PDF](https://microsoft.com/en-us/research/wp-content/uploads/2016/02/pldi212_desai.pdf).
- Verus "currently supports a subset of Rust"; "Features may be broken and/or missing, and the documentation is still incomplete"; about 3,500 stars, 230 open issues; installed from its own INSTALL.md, not crates.io (the `verus` crate is a 0.0.0 placeholder from 2024) — [verus-lang/verus](https://github.com/verus-lang/verus), [crates.io verus](https://crates.io/crates/verus).
- creusot-contracts 0.8.0 (2025-12-09, about 16,500 downloads) and prusti-contracts 0.3.3 (2026-10-29, about 25,000 downloads) — [crates.io creusot-contracts](https://crates.io/crates/creusot-contracts), [crates.io prusti-contracts](https://crates.io/crates/prusti-contracts).

### Inferences
- Kani fits the platform-neutral reducers well because they are sequential pure functions: a harness can prove, for all states and inputs within a bound, that an invariant holds after one transition (an inductive-style check that proptest can only sample). The Windows crates cannot be checked (Windows bindings, COM, no Windows host).
- P's model of machines exchanging events with deferral matches the outpost and pipe topology closely, and PObserve's idea of checking real logs against a spec maps onto a flight recorder of reducer inputs; the cost is maintaining a second model in another language (needs .NET) that can drift from the Rust.
- TLA+ (not researched this session beyond its reputation) has the same drift cost as P; stateright avoids drift but requires writing the system as its actors, which Verbatim's reducers could be adapted to since they are already message-driven.
- Verus, Creusot and Prusti need extensive specifications and a pinned toolchain; for a small team they are suitable at most for one tiny critical kernel, not routine use.

### Gaps
- No Kani experience reports on Windows via WSL were found; running it under WSL or a Linux CI job is assumed workable but unverified.
- No 2026 data on TLA+ tooling or on PObserve availability outside AWS was gathered.
- Notable production users of stateright, Verus, Creusot and Prusti were not confirmed in this session.

## Test quality and oracles: cargo-mutants, insta, differential testing against NVDA, record and replay, parser fuzzing

### Takeaway
cargo-mutants is mature and cheap to adopt for the platform-neutral crates, and it measures whether the existing exact-assertion tests actually catch defects; insta is compatible with an exact-assertion rule because a snapshot is an exact full-value comparison, provided snapshots are reviewed. The strongest oracle available is differential: replay recorded inputs through the reducers and compare spoken output with the existing NVDA speech captures, which is cheaper and more deterministic than driving real applications.

### Cited Findings
- cargo-mutants 27.1.0, published 2026-06-02, about 820,000 downloads; companion `mutants` attribute crate 0.0.4 (2026-01-15) — [crates.io cargo-mutants](https://crates.io/crates/cargo-mutants), [crates.io mutants](https://crates.io/crates/mutants).
- cargo-mutants finds places where bugs could be inserted without any test failing — [mutants.rs](https://mutants.rs/).
- cargo-mutants limitations: it helps only if the test suite is hermetic, flaky or externally dependent tests give wrong conclusions; it counts only in-tree tests run by `cargo test`; it supports cargo and `cargo test`, not Bazel or Nextest; it is type-blind on the AST and produces some unviable mutants; it reads `RUSTFLAGS` but ignores flags set in `.cargo/config.toml`; it does not understand `#[cfg(...)]`, so functions for other platforms are reported as missed; command-line and output formats may change between releases — [cargo-mutants limitations](https://mutants.rs/limitations.html). Note: this page's statement that Nextest is unsupported may be dated; it was reported as fetched and not cross-checked against the release notes.
- insta 1.49.0, published 2026-10-03, about 121 million downloads — [crates.io insta](https://crates.io/crates/insta).

### Inferences
- cargo-mutants suits the reducers: they are pure and hermetic, so each surviving mutant names a real untested decision. Its cost is one incremental build plus a test run per mutant, so running it on changed code only (its diff mode) in a periodic job is the cheap pattern; the cfg-blindness matters for the Windows crates, which is a further reason to aim it at the platform-neutral tier.
- Under "assertions must be exact", insta is acceptable because a snapshot compares the entire value byte for byte (stronger than a field check), but snapshot updates must be reviewed like code, and redactions or glob matchers would violate the rule and should not be used. Inline snapshots keep the expected speech beside the test, which reads well with a screen reader.
- Differential testing against NVDA: the team's recorded NVDA speech captures are already the spoken-expectation oracle mandated by CLAUDE.md. Recording the accessibility events and focus or caret facts that preceded each capture, then replaying them through the reducer and comparing utterances exactly, moves most end-to-end checks into unit tests that run in milliseconds. Differences are either Verbatim defects or recorded intentional deviations.
- Record and replay: a flight recorder of reducer inputs (serialized with serde) turns every field failure and every end-to-end run into a deterministic regression test, and doubles as a seed corpus for proptest or bolero and as the log a PObserve-style monitor would check. Its requirement is that all nondeterminism (time, IDs, ordering across pipes) enters the reducer as input, which the reducer design already implies.
- Coverage-guided fuzzing (cargo-fuzz or bolero with `arbitrary`) pays off on byte-level parsers: pipe framing, terminal output and escape sequences (the `verbatim-term-sim` oracle already present is a natural differential target), and configuration files; run on Linux CI against platform-neutral crates.

### Gaps
- No practitioner write-up comparing these tools specifically for desktop or accessibility software was found.
- cargo-mutants run-time figures (per-mutant cost on a workspace this size) and its current Nextest status were not verified; measure on the repo before planning CI.
- Whether the existing NVDA captures record enough input context (events and object facts, not only speech) to support replay was not examined; that determines how much differential testing is possible without new captures.
