# Model the reducers, simulate the pipes, shrink end-to-end

Verbatim's architecture already does the most expensive work that projects with successful simulation testing had to do: its logic is pure reducers that take messages and return effects, so it can be tested deterministically without any runtime, framework or code changes. Four approaches are viable and much cheaper than end-to-end scenarios. The first is **state-machine property tests of each reducer against a much simpler reference model**, with proptest and proptest-state-machine, which the workspace already depends on. The second is **a hand-written, single-threaded simulator that joins several reducers through in-memory pipes**, with a seeded scheduler that reorders, delays, fails and restarts. The third is **replaying recorded inputs through the reducers and comparing the speech exactly with the NVDA captures**. The fourth is **cargo-mutants on the platform-neutral crates**, to measure whether those tests actually catch defects. Other projects' experience points to one main mistake to avoid: checking only invariants after each step, which caught 38% of injected bugs in John Hughes's experiment, against 100% for comparison with a model. That matters because Verbatim's design principle asks for "generated invariant tests". The other mistakes were nondeterminism leaking into "deterministic" runs, fault models missing the fault that mattered, random tests making CI unreliable, and logic escaping into code the simulator never runs. The deterministic simulation frameworks built for async Rust (madsim, turmoil) do not fit std threads, I/O completion ports and blocking COM calls. Shuttle fits the small hand-off layer, and Kani fits bounded proofs of single transitions on a Linux job. No screen reader, open or closed, publishes any testing beyond example tests, mocked component tests and end-to-end speech capture. That leaves Verbatim no screen-reader precedent to copy, and it is also the strongest argument for the reducer-level approach.

## Decisions to take, in order of return on effort

The table ranks the approaches by what each costs Verbatim and what it buys. "Platform-neutral tier" means the crates the CLAUDE.md file lists as free of Windows bindings.

| Rank | Approach | Verdict | Where it runs | Main cost | Main risk |
|---|---|---|---|---|---|
| 1 | proptest-state-machine on each reducer, compared with a simpler reference model and exact postconditions, not only invariants | Adopt now | Every `cargo xtask ci`, fixed seed and case count | Writing the reference model and generators that produce valid operations | The model duplicates the reducer, or the generator never reaches lifecycle states |
| 2 | Record and replay: serialize reducer inputs during end-to-end runs and NVDA capture sessions, replay them, and compare utterances exactly | Adopt now | Unit tests, milliseconds each | A flight recorder and a stable input format; unverified whether existing captures hold enough input context, so new captures may be needed | Recordings are more orderly than real applications |
| 3 | A hand-written multi-reducer simulator: reducers in one thread, in-memory pipes, a seeded scheduler injecting reorder, delay, failure, application exit and process restart | Adopt as the next build | Fixed seeds in CI, plus a separate deep-search job | Fault model and coverage counters | Logic left in the Windows shells goes untested |
| 4 | cargo-mutants on the platform-neutral crates, limited to changed code | Adopt as a periodic job | Windows or Linux, diff mode | One build plus a test run per mutant, not yet measured on this workspace | Noise from unviable mutants and from `#[cfg]` code |
| 5 | Shuttle for the thin hand-off layer once it is written with `std::sync` and `std::thread` behind a cfg alias | Adopt where a hand-off remains | Unit tests | Aliasing primitives, a channel-based fake for IOCP and COM | Kernel waits are invisible to it |
| 6 | Kani bounded proofs of single reducer transitions and of parsers | Optional pilot | Linux CI job only | Harness per property, Linux or macOS host | Concurrency out of scope |
| 7 | Coverage-guided fuzzing of byte parsers (pipe framing, terminal escapes, configuration) with cargo-fuzz or bolero | Optional | Linux CI job | Harness per parser | Low value on non-parser logic |
| 8 | P, TLA+, Verus, Creusot, Prusti, madsim, turmoil, Antithesis | Do not adopt | None | A second model to maintain, async rewrites, or no Windows support | Drift, or tooling that cannot host the system |

Three rules should accompany the tools, because each one prevents a failure another project reported. Generated tests in CI run with a **fixed seed and a fixed case count**, so that each run takes one code path, as `docs/testing.md` requires. Deeper randomized searches run as a separate, deliberate job, and every failure they find is added to the fixed corpus. Each generated suite reports **how often each operation kind and each interesting state was reached**, because an invariant never violated in a state never reached proves nothing. And the design principle "a pure state machine with many lifecycle paths gets generated invariant tests" should be amended to require **a reference model or postconditions alongside the invariants**, for the reason given in the next section.

## Comparison with a model caught every injected bug; invariants alone caught 38%

The strongest quantified evidence for generated testing comes from Quviq's Erlang QuickCheck work. Klarna had seen database corruption every other month and later weekly, and Ericsson's maintainer had spent six weeks hunting the bug. A stateful model of **under 100 lines, against more than 6,000 lines of implementation**, found several race bugs, the corrupting ones after about 10 minutes of testing each, each provoked with at most one record and five or six API calls, and each fixed within a day ([Hughes 2016](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf)). One minimal case needed an open, close, open sequence that "was initially hard to believe" was necessary, a reminder that lifecycle bugs hide behind specific short prefixes that a generator must be able to produce often. At Volvo, 20,000 lines of models tested a million lines of AUTOSAR C from six suppliers and found more than 200 problems. The models were "an order of magnitude smaller" than the conventional suites they replaced "but tests more" ([Hughes 2016](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf)).

The finding that matters most for Verbatim's design principle comes from Hughes's "How to Specify It!", in which eight bugs were injected into a binary search tree and four styles of property were measured against them. **Invariant properties caught 38%, postconditions 79%, metamorphic properties 90%, and comparison with a model 100%**, and Hughes concludes that model-based properties "may offer the best return on investment" ([InfoQ summary](https://www.infoq.com/news/2020/02/property-based-testing-guide); [paper record](https://research.chalmers.se/en/publication/517894)). The outpost reducer's history, as CLAUDE.md records it, points the same way: all eight of its later defects were in lifecycle bookkeeping, which is exactly the behavior a model comparison checks step by step. A reducer test should therefore check three things after every generated step: the exact effects returned, compared with what the reference model predicts; the observable state against the model; and the invariants. This also meets the exact-assertion rule naturally.

Amazon's S3 ShardStore shows the pattern working in Rust at industrial scale. More than 40,000 lines of Rust were checked against one executable reference model per component, such as a hash table standing in for an LSM tree. The checks prevented **16 issues from reaching production**, and engineers who were not formal-methods experts extended the models ([Bornholt et al., SOSP 2021](https://www.amazon.science/publications/using-lightweight-formal-methods-to-validate-a-key-value-storage-node-in-amazon-s3)). Two of its choices transfer directly, according to Murat Demirbas's secondary summary. The team abandoned plans to write the models in Alloy, SPIN or Python and wrote them in Rust instead, because of maintenance cost. And it reused the models as mocks in unit tests, so that they could not fall out of date ([Demirbas](https://muratbuffalo.blogspot.com/2021/10/using-lightweight-formal-methods-to.html)). Its hardest bug needed three coincidences at once, which uniform generation would almost never produce, so the generators were biased toward corner cases and failures were injected.

Dropbox's sync engine gives the clearest picture of the two layers Verbatim needs. CanopyCheck tested the pure planner alone, with no I/O, and "caught an enormous number of bugs" early. Trinity, a custom executor with mocked filesystem, server and timer, covered concurrency; a separate real-server suite ran about 100 times slower ([Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). CanopyCheck also shows how to build a useful generator. It generated one tree and perturbed it into the other two, because independent random trees would never exercise delete, edit or move. It shuffled each batch to check that order did not matter, and it added invariants that prevent trivial passes, such as one that rules out deleting everything. Verbatim's generators should likewise derive each next operation from the current model state, for example by moving focus to an element that exists or by closing an outpost that is open.

## Simulate the pipes by hand, because the frameworks assume async

Deterministic simulation testing means running the real logic in one thread against a simulated network, disk, clock and randomness, with every choice drawn from one seeded generator so that any failing seed replays exactly. FoundationDB, the model for the technique, says the codebase "was built from the ground up to make this testing approach possible". All of its code is deterministic, multithreaded concurrency is avoided, and the production network, disk and clock are "a simple shim" ([FoundationDB SIGMOD 2021](https://www.foundationdb.org/files/fdb-paper.pdf)). Verbatim's reducers already have that shape: their inputs are messages, their outputs are effects, and time enters as input. Polar Signals' Rust design is the closest match. It used explicit state machines joined by a message bus rather than madsim, so failures are injected in one place, and it found one data-loss bug and one data-duplication bug ([Polar Signals, DST in Rust](https://www.polarsignals.com/blog/posts/2025/07/08/dst-rust)).

The Rust frameworks do not fit. madsim runs futures on its own runtime and intercepts libc calls such as `clock_gettime` and `getrandom`. Its users swap tokio, tonic and other crates for patched forks, and it refuses system threads by default ([madsim docs](https://docs.rs/crate/madsim/latest); [RisingWave part 1](https://risingwave.com/blog/deterministic-simulation-a-new-era-of-distributed-system-testing/)). turmoil replaces `tokio::net` and `tokio::fs` and runs hosts within one thread ([tokio-rs/turmoil](https://github.com/tokio-rs/turmoil)). Neither can see a blocking COM call, an I/O completion port or a named pipe. Antithesis, which needs no code restructuring, runs Linux containers on a bhyve-derived hypervisor ([Antithesis](https://antithesis.com/blog/deterministic_hypervisor/)); one team rejected it because "the pricing just didn't work for us" ([Polar Signals Go](https://www.polarsignals.com/blog/posts/2024/05/28/mostly-dst-in-go)). The practical design is therefore a small simulator in the test crate. It holds several real reducers and an in-memory model of each pipe, plus a scheduler with one seeded random stream per simulated process. The scheduler chooses which pending message to deliver next and whether to delay it, fail it, or kill and restart a process.

Two FoundationDB devices are worth copying almost verbatim. **BUGGIFY** injects unusual but contract-respecting behavior, such as an error from an operation that usually succeeds, a delay in one that is usually fast, or an odd value for a tuning parameter, so that "specific performance tuning values do not accidentally become necessary for correctness". For Verbatim, the equivalents are the outpost settle windows and the coalescing intervals. **Conditional coverage counters**, such as `TEST( buffer.is_full() )`, report how many runs reached a condition, and a count of zero tells the team to add a fault or workload ([FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)). The same paper warns that fault distributions must be tuned "to avoid driving the system into a small state-space caused by an excessive fault rate", and TigerBeetle bounds its faults so that its simulated cluster stays live ([tigerbeetle issue 696](https://github.com/tigerbeetle/tigerbeetle/issues/696)).

The simulator does not replace the end-to-end suite, and the evidence is explicit about this. FoundationDB says simulation cannot test "first-party code not implemented in Flow", and that "several bugs have resulted from the true operating system contract being weaker than it was believed to be" ([FoundationDB paper](https://www.foundationdb.org/files/fdb-paper.pdf)). Dropbox lists real OS interleavings, fsync placement and mock drift as things its simulator could not catch ([Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)). For Verbatim, the untested remainder is the Windows shells and the real applications behind UI Automation. The end-to-end suite remains the check on that remainder; what changes is that it no longer has to be the main check on reducer logic.

## What did not work elsewhere, and the guard for each

Across the property-testing and simulation reports, the same failures recur. Each has a cheap guard.

| What went wrong | Who reported it | Guard for Verbatim |
|---|---|---|
| Invariant-only or crash-only properties passed wrong code | Hughes ([InfoQ](https://www.infoq.com/news/2020/02/property-based-testing-guide)); Hypothesis users ([HATRA 2022](https://harrisongoldste.in/papers/hatra2022.pdf)) | Compare effects with a reference model; add postconditions |
| The model was a second implementation, brittle and slow to maintain | Hypothesis users ([HATRA 2022](https://harrisongoldste.in/papers/hatra2022.pdf)) | Keep the model far simpler than the reducer, as a list stands in for a database |
| Many failures were bugs in the model, not the code | Hughes ([2016](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf)); TigerBeetle false positives ([February 2025](https://tigerbeetle.com/newsletters/2025-03-05-february-in-tigerland)); etcd's checker flaw ([etcd](https://etcd.io/blog/2025/autonomus_testing_with_antithesis/)) | Validate the model with many sequential runs before adding faults; treat the oracle as code under review |
| Generators missed rare states; rejection sampling was too slow | Hypothesis users ([HATRA 2022](https://harrisongoldste.in/papers/hatra2022.pdf)); ShardStore ([Demirbas](https://muratbuffalo.blogspot.com/2021/10/using-lightweight-formal-methods-to.html)) | Build valid operations from model state; bias toward lifecycle operations; coverage counters |
| Shrinking found the same bug every run, or stalled on stateful sequences | Volvo ([Hughes 2016](https://www.cs.tufts.edu/~nr/cs257/archive/john-hughes/quviq-testing.pdf)); [Hypothesis #1857](https://github.com/HypothesisWorks/hypothesis/issues/1857); [proptest-stateful](https://docs.rs/proptest-stateful/latest/proptest_stateful/) | Fix a found bug before searching further; preconditions that hold under shrinking |
| Random discovery made CI "a bit like Russian roulette" | Hypothesis users ([HATRA 2022](https://harrisongoldste.in/papers/hatra2022.pdf)) | Fixed seed and case count in CI; separate deep-search job |
| "Deterministic" runs diverged through hash-map seeding, library clocks and entropy | S2 ([blog](https://s2.dev/blog/dst)); Dropbox; Polar Signals Go | Deterministic hashing in reducers; a meta-test that runs a seed twice and compares the full trace byte for byte |
| The simulator tested only the faults it was given | TigerBeetle missed a swap-induced memory fault ([December 2024](https://tigerbeetle.com/newsletters/2024-12-23-december-in-tigerland)) | An explicit fault list for the COM answer channel: slow, failed, out of order, re-entrant, application exits |
| Logic leaked from the state machines into the untested driver under deadline | Polar Signals ([Rust](https://www.polarsignals.com/blog/posts/2025/07/08/dst-rust)) | Shell decisions such as timeouts, retries and coalescing belong in reducers; review checks for this |
| Seeds broke on any code change, and could not be minimized | Dropbox Trinity ([Dropbox](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)) | One random stream per simulated process; store failures as input sequences, not only seeds |
| Simulation time outgrew the CI budget; unit-level simulation found mostly test bugs | RisingWave ([part 2](https://www.risingwave.com/blog/applying-deterministic-simulation-the-risingwave-story-part-2-of-2)) | Set a time budget per CI job; spend simulation on cross-process sequences, not single units |
| Managers would not fund someone to maintain the tests | Hypothesis users ([HATRA 2022](https://harrisongoldste.in/papers/hatra2022.pdf)) | Reuse reference models as test fakes, as ShardStore did, so they stay current |

Two more cautions come from the measured outcomes. A clean run proves less than it seems: Aiven ran about 2,200 logical hours under Antithesis, found nothing in its own code, and concluded that "a passing test can be the most suspicious type of test" ([Aiven](https://aiven.io/blog/deterministic-simulation-testing-in-diskless-apache-kafka)). Mutation testing answers that doubt, but only when filtered. At Google, about 85% of reported mutants were initially judged unproductive. With one mutant per changed line, suppression of "arid" code such as logging, and results shown in code review, **82% of the mutants developers rated were productive**, and the median changelist got 7 mutants instead of 820 ([Petrović et al., TSE 2021](https://ar5iv.labs.arxiv.org/html/2102.11378)). Running cargo-mutants in diff mode on the platform-neutral crates is the equivalent. Its documentation warns that it needs a hermetic test suite and does not understand `#[cfg]`, which is a further reason to point it at the reducers rather than the Windows crates ([cargo-mutants limitations](https://mutants.rs/limitations.html)).

No figure in any of these sources gives bugs found per engineer-week, or the share of production bugs a simulation would have caught. The evidence is case counts and qualitative judgments, consistent across independent teams but not a cost model.

| P language | No fit as a routine tool | A good conceptual match (machines exchanging deferred events; it verified the Windows 8 USB stack), but it is a second model in another language ([P docs](https://p-org.github.io/P/); [PLDI 2013](https://www.microsoft.com/en-us/research/publication/p-safe-asynchronous-event-driven-programming/)) |

Shuttle and loom cannot see `WaitForSingleObject`, `GetQueuedCompletionStatus`, COM apartments or real pipes. They can test a hand-off only after it is expressed with `std::sync` and `std::thread` behind a cfg alias, with the IOCP and COM boundary behind a trait whose test fake is a channel. This fits the CLAUDE.md rule against hand-written concurrency: each hand-off that remains becomes a small Shuttle target, and each one removed needs no checker. One idea from P is worth borrowing without the language. PObserve checks production logs against a specification ([P docs](https://p-org.github.io/P/)); Verbatim's recorded reducer inputs, replayed with the reference model's assertions enabled, do the same job against field traces.

## Other screen readers stop at mocks and end-to-end speech capture

Every screen reader with public sources uses example tests, mocked component tests and end-to-end speech capture, and nothing else. **NVDA** has about 70 Python unit-test modules and a small Robot Framework system suite whose largest file, the Chrome tests, holds 51 test functions ([nvaccess/nvda tests](https://github.com/nvaccess/nvda/tree/master/tests/unit); [tests/system/robot](https://github.com/nvaccess/nvda/tree/master/tests/system/robot)). Its speech spy declares speech finished after 1.0 second of silence and matches by substring ([speechSpyGlobalPlugin.py](https://github.com/nvaccess/nvda/blob/master/tests/system/libraries/SystemTestSpy/speechSpyGlobalPlugin.py)). Fixed sleeps carry comments such as "Hack: using 'sleep' is error-prone", and flaky tests are tagged `excluded_from_build` ([tests/system](https://github.com/nvaccess/nvda/blob/master/tests/system/readme.md)). Its one notable component harness steps the speech manager by hand against a mocked synth, driving index-reached and done-speaking callbacks deterministically ([speechManagerTestHarness.py](https://github.com/nvaccess/nvda/blob/master/tests/unit/test_speechManager/speechManagerTestHarness.py)). That is the nearest relative of a reducer test in any screen reader. No property-based library appears in the tree. These facts come from NVDA master at commit 0041ab65, because the local `nvda/` submodule was empty in the research checkout; they are not from the pinned revision.

**Orca** is the cautionary history. Its recorded-keystroke harness was renamed `test-historical` in June 2024 with the message "These tests have always been quite flakey and are largely unmaintained", and deleted in July 2025 ([GNOME/orca](https://gitlab.gnome.org/GNOME/orca)). The pytest replacement has more than 1,500 cases, takes about 90 minutes locally, and waits on an `IsIdleForTesting` D-Bus query into Orca itself ([tests/README.md](https://gitlab.gnome.org/GNOME/orca/-/blob/main/tests/README.md)). It still combines that query with quiet-period timeouts. Since 2026-10-01 it has retried assertion failures once on CI, and flake fixes arrive several times a month; at least one, "Fix a timing issue leading to missing speech", was a real product bug ([Orca test commits](https://gitlab.gnome.org/GNOME/orca/-/commits/main/tests)). The idle query is a good idea. The retry and the quiet periods are what Verbatim's standing rules forbid.

**ChromeVox** tests run in Chromium `browser_tests` with a `MockFeedback` class that asserts speech and braille ([ChromeVox for developers](https://chromium.googlesource.com/chromium/src/+/lkgr/docs/accessibility/os/chromevox.md)). **JAWS, Narrator, VoiceOver and TalkBack** publish nothing about testing the screen reader itself; the only public trace is a patent on recording screen reader output for regression comparison ([US6889337B1](https://patents.google.com/patent/US6889337)). The more mature published practice sits on the browser side. Chromium compares accessibility trees and events with exact golden files for each platform API, including UIA ([Chromium accessibility tests](https://chromium.googlesource.com/chromium/src/+/main/content/test/data/accessibility/readme.md)). Google built a coverage-guided fuzzer that drives Chrome through its accessibility tree, and found that selecting controls by name alone was far less effective than mixing name and ordinal mutators ([Google Security Blog](https://security.googleblog.com/2024/10/using-chromes-accessibility-apis-to.html?m=1)).

**ARIA-AT** and its AT Driver protocol show the limits of black-box speech capture. The specification concedes that a command's result "cannot be reliably tied to the AT's responses", and that the protocol does not define when speech has finished ([AT Driver](https://w3c.github.io/at-driver/)). Its participants recorded that "both JAWS and NVDA aren't technically capable of linking utterances with specific user interactions", that the bot heard double speech most humans could not detect, and that AT Driver "might not be able to detect product regressions" ([W3C ARIA-AT minutes, 2025-09-08](https://www.w3.org/2025/09/08-aria-at-irc)). Verbatim owns its reducer, so it can attribute every utterance to the input that caused it. That attribution is what makes the exact replay comparison in this report's second recommendation possible, and none of these projects has it.

## Conclusion

The research changes where Verbatim's end-to-end suite earns its cost. Every project that went beyond example tests learned that a deterministic core is the prerequisite, and that the real environment still has to be tested separately. FoundationDB and Dropbox designed for this from the start, and Polar Signals paid for it in cognitive overhead and in logic that leaked into its untested driver. Verbatim already has the core, so the end-to-end scenarios can shrink to checking what only Windows and real applications do: whether the shells fetch the right facts and whether UIA behaves as the fault model assumes. Every field or end-to-end failure that the simulator cannot reproduce should be treated, as FoundationDB treats production bugs, as a gap in the simulator's fidelity to close before the fix.

The less obvious implication is that the hardest part is the specification, not the tooling. Hughes calls the need for a specification "the real weakness of property-based testing", and the outpost reducer's eight defects were in bookkeeping that no hand-written test covered. Each new reducer should therefore ship with its reference model, which is a short, obviously correct description of what it should do, written before or with the code and reused as the fake in other crates' tests. Its effectiveness should then be measured by mutation rather than assumed from a green run. No screen reader has published anything like this, so Verbatim would be first to do so, and could test its own logic more thoroughly than the projects it learns from.
