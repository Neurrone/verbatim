# Second review of the design "Failure paths and locks"

Three Important findings.

Reviewed: the revised section "Failure paths and locks (a build of its own)" of `docs/design/logic-foundations.md` (working tree, 2026-10-31), against origin/main d62e7740 as checked out in `verbatim-wt-split`. Code paths and lines below are d62e7740's; design lines are those of `docs/design/logic-foundations.md`. This review judges only whether each of the first review's eleven Important findings (`failure-paths-design-review.md`) is fixed by a mechanism that works.

## The first review's findings

- The hook's post can be refused: not fixed. The fix is a timed retry with no evidence behind it, and it does not reach its own goal (first finding below).
- The relay mailbox loses "the owner has gone": fixed. The `closed` mark set under the queue's lock when the `Inbox` drops makes `send` fail and drops a queued `Shutdown`'s reply sender, so `Supervisor::shutdown` returns either way.
- The watched read's facts need a key per read: fixed. Each read keeps its own `WatchedRead`, so a late `learn` of an abandoned read touches only its own facts and finds its claim set.
- The readers'-lock acquisitions per read: fixed. The reading thread no longer takes the readers' lock; it takes its own read's lock at most twice, and the lock order is always the readers' lock, then a read's, never the reverse, so it cannot deadlock.
- Ending the outpost when its replacement worker cannot start: the recommended rule answers every program exactly once, and trying the start again at each dispatch is not a retry hiding a failure, since each failed start is logged at error and its program answered as failed. But the rule makes a branch that releases application objects on the shell's thread a steady state (second finding below).
- Arming by count: fixed. Each selector names the one call: the second focus handler's add and the first's removal by index, the old element's removal by runtime id, `OwnerEvent::Shutdown` after the queue is shown empty, `ListenerReady` of which a run has one, generation 0's two starts, and generation 1's one.
- Executables keeping both feature variants: fixed. Through `cargo xtask ci` nothing in `target/debug` carries a point: no dev-dependency turns the feature on, the fault tests are `required-features` targets the ordinary steps skip, and points behind `cfg(test)` exist only in a crate's own unit-test binary. A hand-run `cargo test -p mockapp --features faults` without `--target-dir` would relink `target/debug/mockapp.exe` with the feature's dependencies; the suite's own `cargo build` relinks it without them, and only a build staged through `VERBATIM_E2E_VERBATIM_EXE` would keep it (a nit).
- `cargo xtask ci` not building the shipped configuration: fixed by the same arrangement.
- The lock check's panic caught: the abort fixes it, but the abort's output does not name the check or the lock (third finding below).
- Calls the check does not see: fixed by checking agile references, bounded waits and the store's `Removed`, with the rest stated as a limitation (design line 919). A `Vec<Agile<Kept>>` dropped under a `Lock`, the first review's example, falls under that limitation.
- The record lost on out-of-order drops: fixed. Each guard empties only its own slot, and `MutexGuard` cannot move to another thread, so the record is right whatever the order.

## Important findings

### The hook's refused commands are retried by a 50 ms timer, without evidence, and it does not reach its goal

Design lines 840 to 844. Defect: the fix keeps refused commands and retries them every 50 ms from a new thread timer. No evidence is given that the refusal is transient or that a later post succeeds, so this is the retry the standing rules forbid, and it does not guarantee delivery either.

What refuses the post (`crates/verbatim-process/src/port_queue.rs` lines 150 to 175): a completion port has no capacity, so there is no full port. The port cannot be closed under a poster either, because the handle lives in `Shared`, held by every `Poster`'s `Arc`. A queue whose `PortQueue` has gone fails before any post (`open` is false, `is_open` says so), and that refusal is already handled correctly by dropping, since the reducer has gone. That leaves `PostQueuedCompletionStatus` failing on a live handle, which the code's own comment (line 147) puts down to a system out of memory. Verbatim cannot prevent that refusal. The same `send` first allocates the item's box (line 158), and Rust aborts the process when that allocation fails. So the case the timer serves is a narrow one: the kernel refuses the packet while the process's own heap still allocates, and the kernel recovers within one tick. The design gives no evidence that this case happens or that it clears.

Counterexamples:

- The refusal persists: key 1's commands are refused and kept, and the timer is set. Every 50 ms the hook thread wakes and posts again, is refused again, and keeps the commands. Each further key joins the thread-local queue, which grows without bound. That is 20 wake-ups a second for as long as the condition lasts, and the queue's push is itself an allocation under the condition the design blames for the refusal.
- `SetTimer` fails: it returns 0 under resource exhaustion, and the design does not say what happens then. The last key's kept commands then have no carrier until another key, which is exactly the case the timer was added for ("the last key may have nothing behind it").
- The other port on the same thread is not covered: `speech_effect` calls `SpeechControl::cancel_through` (`crates/verbatim-speech/src/manager.rs` line 224), which posts to the speech queue's port and drops a refused cancel with `let _ =`. Under the same refusal, the reducer's `SpeechCancelled` is kept and retried while the speech queue's cancel is lost, so the old speech goes on although the reducer believes it was cancelled. The rule is applied to one of the hook's two ports.

The hook thread today takes no message and has no timer (`crates/verbatim-input-windows/src/hook.rs` lines 154 to 172). The fix adds a third callback, a timer, `WM_TIMER` handling and two lifecycle states, all for a condition with no evidence.

Root-cause treatment: the refusal cannot be prevented, so it should be made visible rather than retried on a clock. Keep the in-order rule without the timer: commands refused while the poster is open are kept and posted ahead of the next key's commands on the hook thread, the same carrier the relay's `Outbox` uses (its next send). Apply the same rule to the speech queue's posts. State as a limitation that the last key's commands wait for the next key while the system refuses posts. A harness waiting on that key is already answered: `IdleLine::wait` (`crates/verbatim-app/src/harness.rs` lines 172 to 195) fails at its timeout with an error naming the input and what is outstanding, so nothing waits for ever. If Dickson prefers no kept state at all, the alternative is to drop the command and count the drop in a counter the reducer logs, accepting that a key's effect is lost. Either way the timer, the third callback and the message-loop change go.

### Under the recommended rule, a dispatch with no worker releases application objects on the shell's thread

Design line 845, against `crates/verbatim-outpost/src/outpost/shell.rs` lines 802 to 830. Defect: `dispatch` moves the shell's `Garbage` into the `Job` before it knows a worker exists, and when there is none it drops the job, and with it the garbage, on the shell's own thread. The worker is the place that release is meant to happen ("releasing one can call into the application, so it is done here, under the program's deadline", `worker.rs` lines 363 to 366). Today that branch is reached only after a worker has ended. The recommended rule makes it the steady state of an outpost whose worker cannot start.

Counterexample: worker generation 0 hangs in the application's provider. The reducer abandons it, and generation 1's start fails. The next event's program reaches `dispatch` with garbage that holds `Agile<Kept>` elements and the store's `Removed` objects of that same application, since the abandonment's `Unfollow` and `ForgetRanges` effects fill it. `dispatch` tries the start once and fails, then drops the `Job`. The release goes into the hung application on `verbatim-reducer`, the thread that must stay responsive, against the design principle that a COM object is released only on a thread allowed to block. The shell then takes nothing more. The I/O thread goes on answering pings, so the supervisor sees a live outpost, and no program of this outpost is answered again, which is the failure the rule exists to prevent. The lock check does not catch this, because no `Lock` is held. The fix: when no worker can be had, `dispatch` puts the garbage back into `self.garbage` (or never takes it) and drops only the program, so the next worker that starts drops it. The design should also say the dispatch's start passes `warm` as `Shell::start` would.

### The abort does not print which check fired or which lock was held

Design lines 887 and 888. Defect: the check panics "with a payload of its own type", and the design relies on the panic hook having "already printed the message". But Rust's default hook prints a payload only when it is a `&str` or a `String`; for any other type it prints `Box<dyn Any>`. The app's hook (`crates/verbatim-app/src/flight_dump.rs` lines 151 to 172) chains to that default.

Evidence: a program that calls `std::panic::panic_any(Check { what: "lock held at x.rs:1" })` prints `thread 'main' panicked at p.rs:2:13:` then `Box<dyn Any>` (rustc 1.99, run for this review).

Counterexample: a worker's program takes `store`'s `Lock` and counts a UIA call. The check panics with its typed payload, and the hook writes the panic site and `Box<dyn Any>` to the outpost's stderr log. The worker's `catch_unwind` sees the check's payload and aborts. The end-to-end suite records an outpost crash, `0xC0000409`, with no word of what was called or which lock was held, so the abort hides which check fired. A backtrace appears only when `RUST_BACKTRACE` is set. The design's own test, which checks that standard error names the lock's location, would fail as the design specifies it. The fix: the check writes its message, naming `what` and every location, to standard error and the log before it panics, or the abort branch formats the payload before calling `abort`.

## Nits

- Design line 886: a ninth lock panics with an ordinary payload, so inside a worker's program it is caught and becomes a program answered as panicked, which is the outcome the abort exists to prevent. It should raise the check's payload. Nine distinct outpost locks held at once is very unlikely, so this is not Important.
- Design line 886: the slot record is a thread-local, and a `Lock` guard dropped during thread-local destruction would panic in `LocalKey::with`. The record should be reached with `try_with`.
- Design line 833: the new `verbatim-faults` crate must depend on `workspace-hack` like every package (`xtask/src/main.rs` lines 344 to 349, `hakari manage-deps --dry-run`), so it does not have "no dependencies".
- Design line 833, the cost question for Dickson: `target/faults` starts empty, so its first build compiles every third-party crate again, `windows` included, in each worktree. Here `target/debug` holds 1.3 GB, 858 MB of it in `deps`. Since only `mockapp.exe` among the executables would be relinked by a fault build in `target/debug`, and the suite relinks it on its next build, the cheaper option to put to Dickson is the fault step in `target/debug` with its feature-variant libraries cached beside the others, at the cost of `mockapp.exe` relinking when the fault step and an ordinary build alternate.
- Design line 845: the design names no command for running one fault test by hand. A builder's targeted `cargo test -p mockapp --features faults` without `--target-dir target/faults` writes into `target/debug`. An `xtask` verb or a stated command would prevent that.
