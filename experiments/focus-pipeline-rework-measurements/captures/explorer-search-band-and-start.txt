The outposts' debug logs are Verbatim's logs\16092 folder; the File Explorer folder window's outpost was outpost-spare-5.log (target_pid 3332). The outpost's debug lines give each MSAA focus's window handle and, on the window's first probe, its class (the "arbitration probed" line); winevent-hook.ps1 (this folder), an out-of-context hook for EVENT_OBJECT_FOCUS on every process, recorded each MSAA focus with its window's class as well, and window-ancestry.ps1 (this folder) read the search box window's ancestors while it existed. Times are microseconds since the Unix epoch.

What it shows. Control+E in a folder window (a scratch folder, ReworkSearch, opened with --launch-without-foreground and brought forward with --front) raises an MSAA focus on OBJID_CLIENT of an InputSiteWindowClass window, whose parent is a Microsoft.UI.Content.DesktopChildSiteBridge child of the CabinetWClass frame: on this 25H2 build the search box is a WinUI island, and no window of class "Search Box" or "UniversalSearchBand" exists in the folder window at all (its 25 child windows are listed below), so NVDA's SearchBoxClient rule has no window to match. That MSAA focus came 16 ms before the search box's UIA focus here, not after it, and the outpost dropped it ("MSAA focus dropped: UIA owns the window"). Verbatim said " Search ReworkSearch edit" and "blank". From the desktop (shown with Windows+D) and from Notepad, the Windows key, Windows+X and Tab raised no MSAA focus in any window of class Start: the Windows key focuses SearchHost's "Search" window (class Windows.UI.Core.CoreWindow), and Windows+X and Tab focus the taskbar's Windows.UI.Input.InputSite.WindowClass window (Shell_TrayWnd's XAML island), with the desktop's FolderView between. So neither NVDA rule, SearchBoxClient nor StartButton, has a window to apply to on this build by these routes.
