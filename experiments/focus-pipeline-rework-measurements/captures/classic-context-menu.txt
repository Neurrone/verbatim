A classic Win32 context menu

Taken on 2026-10-30 on Windows 11 build 26200 (x64), NVDA alpha-58022,732d1ce2 (the pin) in session 1, started from a scratch configuration with eSpeak NG, default symbol and verbosity levels, the update check off and the transcript add-on, through cargo xtask nvda capture. context-menu.ps1 (this folder) ran under Windows PowerShell 5.1: a Windows Forms form holding a "Notes" text box with the text "hello" and a ContextMenu (the classic Win32 menu, not a ContextMenuStrip) of three items, "First item", "Second item" and "Third item". menu-hook.ps1 (this folder), one thread holding two out-of-context hooks scoped to the form's process, one for events 0x0003 to 0x0007 and one for EVENT_OBJECT_FOCUS, recorded each event with the time in microseconds since the Unix epoch (GetSystemTimePreciseAsFileTime) and the event's own millisecond stamp.

What it shows. Each of three Shift+F10 presses raised EVENT_SYSTEM_MENUSTART on the text box and then EVENT_SYSTEM_MENUPOPUPSTART on the #32768 popup, 3.4, 3.0 and 5.3 ms later, and no focus event at all: Windows highlights no item when this menu opens from the keyboard. The first focus came only with Down Arrow, on child 1 of the popup, 8.0 seconds after its popup start. NVDA said "Context menu" for each opening, the popup alone, and "First item f" for Down Arrow. So NVDA does not say only the menu's first item here, and the case the delayed pump changes, a batch that begins with a popup start and holds the item's focus within 10 ms, does not occur: the popup start is alone, and NVDA speaks the menu from it. By the design's rule (difference 17, step 14 builds the pump only if NVDA says the item alone here), the delayed pump is not built. Escape closed the menu with EVENT_SYSTEM_MENUPOPUPEND and EVENT_SYSTEM_MENUEND within 0.1 ms of each other, preceded by a focus on the popup's child 0 only when an item had been focused, and with no focus event for the text box, yet NVDA said "Notes edit selected hello" each time.
