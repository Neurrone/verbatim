# A hung window named in a system focus event holds a process's UIA events

## Fact

In a process holding any UIA focus registration, a desktop-wide focus handler or a focus event in an event handler group scoped to one window, even another application's, a focus `WinEvent` naming a window that does not answer UIA in time holds that process's UIA event delivery: UIA's focus tracking, on the process's one event worker, sends the window `WM_GETOBJECT` and then, finding no provider, `UiaServerConnection_HookMessage`, each waiting the connection timeout, while every other event waits behind it (`books/dev/src/reference/uia-bugs.md`, the fault of that name). What bounds the hold and who meets it:

- The hold is twice the connection timeout per focus `WinEvent`, or until the window answers if sooner: timed from the focus `WinEvent`, as the program times it, 1,010 to 1,019 ms at 500 ms and 4,017 to 4,026 ms at the default 2,000 ms (the originals timed it from B's change, raised 200 ms after the `WinEvent`: 812 ms and 3,806 to 3,821 ms). Once Windows has marked the window hung, between 2 and 6.5 seconds into a stall on a real desktop, it is one connection timeout in mockapp's tree view, 2 to 2.6 seconds in the provider program's window, and up to two waits for a focus `WinEvent` raised around the moment Windows marks the window. A window that answers messages but whose provider is slow holds the same way. Each focus `WinEvent` naming the window pays the full wait again, and each client object holding a focus registration runs its own focus tracking on the same worker. An application raising its own focus while its provider is slow held in some runs and not in others.
- Not held: a name-change `WinEvent` for the hung window; a process with no focus registration; a hung application no focus `WinEvent` names; explicit reads on other threads of the held process; its MSAA `WinEvent` hooks; Alt+Tab away from the hung window or back to it; and focus for a newly opened or shown window, raised by UIA's open-and-show route on a thread-pool thread.
- No client setting tested removes it: not the transaction timeout, a separate client object for focus on the same thread or one of its own, a single-threaded apartment, connection recovery or coalescing, a group-scoped registration, or removing the focus `WinEvent`s from the proxy factory mapping. Emptying the mapping halves it. The older `CUIAutomation` coclass's second call waits until the window answers, and its timeouts cannot be set.
- A focus change in a window that stays busy past both of UIA's waits is dropped, never delivered; a stall shorter than both depends on the application.
- Verbatim's listener is held like any client.

## What Verbatim relies on

Outposts holding no focus registration, so that a hang holds only the listener (`books/dev/src/explanation/design/focus-pipeline.md`, section 12.3; the module comment of `crates/verbatim-listener/src/listener.rs`); D9's amended reason; the 2-second `CONNECTION_TIMEOUT`; the listener dropping a focus in a hung window (`window_is_hung` in `crates/verbatim-listener/src/focus_read.rs`), which rests on `IsHungAppWindow`'s mark. If a process with no focus registration began to be held, every outpost's events would stop during any hang; if the hold lengthened, the listener's silence would exceed what was accepted. Verbatim uses `CUIAutomation8` only, so the older coclass's wait affects nothing.

## Method

The default run checks only what Verbatim relies on: `calls` and `listener-mapping`. Every other case runs only when named with `--case`, its claims kept here and in the documents: `who`, `until-answer`, `repeat`, `quiet`, `mapping`, `slow` and `own-focus`, and the desktop cases, `shown` and `desk-wide`. Three facts of the same entry have programs of their own, sharing this scene through support's `uia_facts_support::hung`: [a process with no UIA focus registration is not held](../a-process-with-no-uia-focus-registration-is-not-held-by-a-hung-window/readme.md) (the outpost stand-in), [a focus change in a window busy past both of UIA's waits is dropped](../a-focus-change-in-a-window-busy-past-both-of-uias-waits-is-dropped/readme.md) (`h6`), and [focus for a newly opened or shown window is not held](../focus-for-a-newly-opened-or-shown-window-is-not-held/readme.md) (the open-and-show route, on the desktop).

The kept CI test, `a_provider_held_raising_its_event_holds_only_its_own_events` in `crates/mockapp/tests/uia_bugs/a_hung_window_named_in_a_system_focus_event_holds_a_processs_uia_events.rs`, covers E-delivery: a server-side provider held while raising its own event holds only its own events. The program covers the hold, which needs a window that names the messages it is sent.

The scene: provider program P1 holds T, a plain Win32 window on UI thread 0, the window made to hang; A, a UIA window on thread 1; and M, a window with its own `IAccessible` on thread 2. Provider program P2 holds B. A stall is a UI thread busy, taking no message and logging each sent message that reaches it. Where a case measures a hold, the stall lasts until the program releases it: once the client has heard B's change, or once the hold has passed its band's top and 300 ms more, so a hold that lasts until T answers still shows as out of band; the case about how long a stall lasts, `until-answer`, and the desktop cases use stalls of a set length. The focus `WinEvent` naming T is raised from P1's control thread. Each client is a listening process of its own (`uia_facts_support::listen`): its timeouts are 2,000 and 20,000 ms, UIA's defaults, unless named, and it registers for B's name changes beside whatever its case names. Every trial has new providers and new clients, and every case but the desktop cases runs on a desktop of the program's own, as the originals ran, so that no input or real focus reaches its clients. A hold is the time from the focus `WinEvent` to the client hearing B's name change, raised 200 ms after it. A delivery counts as not held within 100 ms of its raise: the originals measured 0 to 3 ms, and a hold is at least one connection timeout, 250 ms or more. The stalls are deliberate, since the fact is about a timed stall.

- `calls`: a client with a desktop focus handler at UIA's default 2,000 ms connection timeout, the hold Verbatim's listener meets; T held until the client hears B's change. Judged: the hold, a band from two connection timeouts; the sent messages that reach T, 2; the second one connection timeout after the first, a band. The messages' names and flags are read under the debugger ([the threads guide](../uias-client-threads-and-focus-tracking-calls/readme.md)), since reading a sent message from a busy thread would answer it.
- `listener-mapping`: Verbatim's mapping against a hidden T (`states`' stand-in) at a 250 ms connection timeout, T held until it hears B's change, a band from two waits.
- `who`, run only when named: thirteen clients, each in a trial of its own with T held until it hears B's change, and each judged on its own, at connection timeouts of 250 and 500 ms where the originals ran at 500 to 2,000 ms, since what each shows is the hold's relation to the timeout: connection timeouts of 250 and 500 ms; a 100 ms transaction timeout; a single-threaded apartment; a focus group on B, and on A in place of the desktop handler; focus on a second client object on the same thread or a thread of its own, and the name registration on a thread of its own; two client objects each with a desktop handler (four waits), two handlers on one object (two waits); the mapping emptied (one wait), the focus `WinEvent`s removed from it (two waits); and the listener stand-in, held, with MSAA focus and foreground hooks and a read on another thread, in trials of its own as [the outpost stand-in](../a-process-with-no-uia-focus-registration-is-not-held-by-a-hung-window/readme.md)'s. The older `CUIAutomation` coclass's client object is judged for its missing `IUIAutomation2`; its wait to the window's answer, which needs a stall past its fixed 5 s first wait, is read under the debugger in the threads guide (`h2_cui`).
- `until-answer`, run only when named: T stalled 1.5 s at a 1,000 ms connection timeout, shorter than two waits: held until T answers.
- `repeat`, run only when named: three focus `WinEvent`s at once at a 250 ms connection timeout, T held: a band from six waits.
- `quiet`, run only when named: T held with no `WinEvent`, then a name-change `WinEvent` naming it: not held.
- `mapping`, run only when named: the class names of a new client object's proxy factory mapping entries that map the focus `WinEvent`.
- `slow`, run only when named: U, a UIA window whose every provider call takes 300 ms while it keeps answering messages, named by a focus `WinEvent`, at a 500 ms connection timeout: B's name change, raised 200 ms after the `WinEvent`, held at least one connection timeout from its raise; a client with no focus registration, not held.
- `own-focus`, run only when named: a window whose every provider call takes 1.5 s raising its own focus, at a 1,000 ms connection timeout, 4 times as a UIA provider and 6 times as an MSAA window, as `q3` ran at 3 s and 2,000 ms: a rate of trials whose B name change is held more than 500 ms. The trial does not wait for the raise's own slow calls.
- No case checks Alt+Tab back to the hung T; `h7_alttab_to_early` and `h7_alttab_to` record it.
- On the unlocked desktop, run only when named: `shown` (three trials, as `h7` ran its three, each with one change of B, since a sender's name is read when the worker takes its event; in each T is brought to the front and a baseline change of B heard by both clients first, as `h7` did: a client and Verbatim's stand-in held from a `WinEvent` at once, and when Windows first marks T hung; a `WinEvent` 6.5 s in, once marked; and B then T in front and Alt+Tab away from T 6.5 s in, landing on B or T's ghost window, a landing on T or on another application's window making the case inconclusive. The `WinEvent` once marked is raised as soon as Windows marks T, at 6.5 s into the stall as `h7_hung` raised it, and at 8.5 s, each in a trial of its own, D alone; the 6.5 s hold is judged against the provider program's own first desktop runs, 2,541 to 2,589 ms, where mockapp's tree view held one wait (`h7_hung`); the hold as soon as Windows marks T is judged to be at least one wait and at most two, as 12 runs found it one or the other; the 8.5 s hold is new); and `desk-wide` (T and B shown, so that a desktop-wide name registration hears B: E-hung-proxy's name change at a desktop-wide registration during a hold, at its 10 s connection timeout and 15 s stall, watched 25 s, and `q1`'s name-change `WinEvent`).

## Client settings

Neither connection recovery nor event coalescing changes these outcomes (checked on 2026-11-06 by running every case run without the desktop by default and once each with `--recovery`, `--coalescing` and both). Verbatim's client has both on: `target\debug\a-hung-window-named-in-a-system-focus-event-holds-a-processs-uia-events.exe --recovery --coalescing --case listener-mapping` runs the `states` stand-in with Verbatim's settings.

## How to rerun

`uia-facts/build.ps1`, then `target\debug\a-hung-window-named-in-a-system-focus-event-holds-a-processs-uia-events.exe`, which runs `calls` and `listener-mapping`, what Verbatim relies on, and takes over nothing. The other cases that need no desktop run when named, for example `--case who --case until-answer --case repeat --case quiet --case mapping --case slow --case own-focus`. The desktop cases run only when named, `--case shown --case desk-wide`; they need the unlocked desktop and take it over: they show windows and press Alt+Tab. Under `--pause` each trial prints its process ids and waits for Enter. The test: `cargo test -p mockapp --test uia_bugs -- --exact a_provider_held_raising_its_event_holds_only_its_own_events`.
