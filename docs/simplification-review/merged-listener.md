### L1. Progress bars as Core's requests (Question for Dickson)

Both reviewers count the bar path at about 1,320 to 1,390 product and 1,650 to 1,750 test lines, within a tenth of each other; my sum of the whole bar files and bar parts is about 1,370, against NVDA's 58 (about 24x). A proposes that Core ask for a bar as it asks for anything; B asks only whether the memo and the bar deadline should stay. Laid out for the owner below, under "Questions"; no recommendation.

What the listener's bar path judges today, from the code, against what ADR 0003 says only Core judges:

1. Acceptance. Classic: `reads_value_change` (`listener/configuration.rs` 104 to 112) calls `verbatim_core::accepts(EventKind::ValueChange, Some(facts), false)` on the tell's facts while background bars are not reported; UIA: `admits_bar` (120 to 129) does the same on facts it reads. ADR 0003, "Acceptance judged in Core": "The listener judges nothing with these facts, except, while background progress bars are not reported, whether to read a value change's classic bar, and a UI Automation bar change after its nearest window, with Core's own function on facts it reads for that purpose (Dickson, 2026-11-19)." A ruled exception.
2. The window's backend. Classic: `window_judged` (`listener.rs` 1827 to 1851: `class_verdict`, `raw_probe`, `listener_provider`), kept per application in `value_change.rs`'s `Verdicts`; UIA: `percent_of_bar` (1553 to 1563), `provider.is_some_and(served_only_by_uia_proxies)`. ADR 0003, "What Verbatim keeps beyond NVDA": "the progress path's own backend verdict". A ruled exception; the two listener paths disagreeing with each other is the misc fixes' recorded defect (L14).
3. Whether an object is a bar: a listed class (`is_progress_bar_class` on the normalised class, `listener.rs` 1637 to 1639) and a role memo (`BarMemo`, `value_change.rs` 99 to 125). A listed class's hidden window is dropped (`classic_value_change`, logic `focus.rs` 71 to 72: `visible.then_some(ClassicBarRead::Listed)`), where NVDA's `ProgressBar.event_valueChange` passes an invisible bar on as an ordinary value change (`behaviors.py` 47 to 53). The design's hook table (2026-11-09) gives the memo; ADR 0003's "Core holds every rule" does not name it.
4. A flood limit that guesses the focus. `limit_bars` (logic `schedule.rs` 1044 to 1079) keeps the newest `EVENTS_PER_THREAD` per thread of waiting bar jobs and caps them at `BARS_PER_APPLICATION` 64, always keeping `waiter.focused`, which is `knowledge.is_focused(object)`, set by every MSAA focus `WinEvent` (`listener.rs` 1880, `focus_moved`). ADR 0003, "Flood limiters and the merge": "The listener's limiter makes no guess about the focus: it merges only waiting events with the same object, kind and raising thread ... caps are added at the listener only if the measurement misses its budget." NVDA exempts `eventHandler.lastQueuedFocusObject` (`IAccessibleHandler/__init__.py` 1025 to 1031), a focus that passed acceptance, and counts every event kind of a thread together (`orderedWinEventLimiter.py` 92 to 110), not bar jobs alone.
5. A deadline of its own. `BAR_READ_DEADLINE` 1 second (logic `focus.rs` 85), `BAR_READS_ABANDONED_LIMIT` 2 (92), `tick` and `abandon_bar_read` (`schedule.rs` 854, 888). ADR 0003, "A frozen window": "The readers keep no deadline of their own and no rule of their own for the user having moved on."

The decision of record. ADR 0003 (`books/dev/src/reference/adr/0003-readers-tell-core-asks.md` 129 to 131), "Progress bars (Dickson, 2026-11-14)": "The approved progress-bar design stands as the one place a reader reads unasked: the listener reads a bar's role, percentage and place and reports facts, and Core judges them. Core's requests go ahead of bar reads on a reading thread. Reason: a bar's beep costs no request and no round trip; a UI Automation bar's value usually comes with its event, an MSAA bar's read runs on the application's reading thread, where a hung application stalls only that thread, and progress facts are handled at once in Core, outside the event queue." Rejected option (216): "Progress bars as ordinary requests, Core asking the listener to read a bar when told of its change. Rejected: under the fallback that filters change events to the foreground's processes, a background bar's change never reaches Core, so it would go unheard." `docs/design/progress-bars.md` 3: "Status: approved by Dickson on 2026-11-09", and its decision (132 to 137): "The listener owns every progress bar: its hook takes value changes always, for classic bars foreground and background, and its UIA group takes range values. An outpost reports no progress bars, and keeps its value-change handling for text. One owner, because an outpost for the foreground and the listener for the background would each have to judge whether a bar is its own against the foreground, and a foreground change could report a bar twice or not at all."

Which facts have changed since, and which have not:

- Changed, but known when the ADR's decision was made: the fallback named as the rejection's reason was not built. `docs/design/readers-tell-core-asks.md` 473: "Decided (Dickson, 2026-11-14): the added cost is accepted and the foreground filter is not built, for now; the listener's limiter merges only; the progress-bar path is kept, as ADR 0003 now gives its reason without the filter." So every value change is told to Core today ("The tell is kept either way", `books/dev/src/reference/crates/verbatim-listener.md` 181 to 182), and line 216's stated reason no longer holds, but Dickson kept the path the same day knowing it. Not a new fact.
- Changed since 2026-11-14: the bar path now needs Core's acceptance rule and Core's setting inside the listener (ccdb2a7a, 2026-11-19, "Skip reading a background value change while background bars are not reported": 52 files, 1,867 insertions, 16 Markdown files; `CoreToListener::Configuration`, a launch argument, a monitor, the `Told` value threaded out of the foreground hold, a 228-line supervisor test). This is Dickson's own ruling of that date; it is new cost on the bar path.
- Not changed: the bar limits, the deadline and the abandon count date from b842c487 and dd625bda (2026-11-09), before the ADR; the two native judges' disagreement was recorded in the roadmap by a2e8c521 (2026-11-10), before the ADR; the focus guess (`focus_moved`) dates from 3616b7b6 (2026-10-06). The ADR's stated reasons still hold of the code: a bar's beep makes no request to Core, a UIA bar's percentage comes from the event's cache (`bar_percent`, `listener.rs` 1544 to 1551), an MSAA bar's read runs on the application's reading thread, and progress facts are handled at once outside the event queue.

The cost of the rejected shape, from ADR 0003's own rules: a value-change tell joins Core's event queue, and "Only the front entry may have a request out" (59), so a bar read asked at the tell's turn holds the front, and every key behind it, for one listener round trip (a reading thread's read is about 0.65 ms, `docs/design/readers-tell-core-asks.md` 476), and for a slow but not hung application until the request's due time of 11 seconds or its live hang check. Today a bar read waits on the application's reading thread behind Core's requests and holds no key. Removed by A's estimate: about 1,300 product lines (the bar files, the configuration channel and its launch argument, the bar job kinds, limits, deadline, alarm and watchdog, `window_judged`, `NewestPerThread`), about 250 added in Core and the listener's MSAA read (`read_msaa`, `asked.rs` 403 to 414, reads only the name today); tests about 1,700 out and 300 in; outside the area, `crates/verbatim-supervisor/tests/listener_configuration.rs` (228) and the protocol message.

Speech, from the scenarios: a background classic bar's change with `report_background_progress_bars` off says nothing, and with it on plays "sound: progress" (`crates/verbatim-e2e/src/scenarios/background_progress_bar.rs` 94, 98, 112, 117; `background_progress_bar_off`). Both shapes are meant to give the same; only the time of the tone moves, by one round trip. A bar in an old console with an incomplete provider, which `value_change.rs` 7 to 13 records as a limit of the listener's judge, would follow Core's backend verdict instead: needs a capture.

### L2. The pending foreground held twice; the timer sends the tell before the report (Defect)

Verified quotations: logic `foreground.rs` 79 to 82, "The newest foreground event's window, when it was not in front as the event was handled: sent once a later event finds it in front, and replaced by a newer foreground event. `pending: Option<Front>`"; logic `tell.rs` 160 to 169, `struct Hold<T> { window: isize, until_us: u64, held: Vec<T> }`, "The window awaited."; listener `tells.rs` 304 to 308, `fn fired(&self) { let mut state = self.state.lock()...; let placed = state.hold.fired(self.front(), now_us()); let _ = self.apply(&state, placed, &SystemReads, None); }`. The watch lives on the WinEvent thread (`listener.rs` 754, `Rc::new(RefCell::new(ForegroundWatch::default()))`); the hold under the `Tells` lock, its timer a threadpool timer (`listener.rs` 303 to 432, ten `unsafe` blocks, four `unsafe impl`s, an `unsafe extern "system" fn` and `owner: *const T`; A's "five unsafe blocks" is wrong). `on_win_event`'s doc (`listener.rs` 1038 to 1041): "so that the hold releases a foreground tell on an event only when the watch has reported its window." `FOREGROUND_HOLD_US` is 20,000 (logic `tell.rs` 34).

Sequence, traced:
1. A foreground `WinEvent` for window W arrives while `GetForegroundWindow` names the previous window. `watch_win_event` calls `ForegroundWatch::foreground(front, false)`: `pending = Some(W)`, nothing reported. `tell_win_event` calls `ForegroundHold::foreground`: the hold awaits W, the tell is held, the timer armed for 20 ms.
2. No `WinEvent` arrives within 20 ms (a UI Automation focus does not count: it passes the hold, `ForegroundHold::passing`, and never reaches `watch_win_event`, which only `on_win_event` calls).
3. The threadpool timer fires: `ForegroundHold::fired` finds `front == hold.window` and sends W's foreground tell (`Sent::Tell`). The watch still holds W pending; nothing on this thread can reach it.
4. W's `ListenerToCore::Foreground` goes only when a later `WinEvent` of any kind finds W in front (`event_seen`). If that later event is a foreground event for another window not yet in front, `pending` is replaced and W is never reported.

What Core does with the tell: the supervisor forwards a `Tell` to Core's event queue and a `Foreground` report to Core's inbox (`crates/verbatim-supervisor/src/owner.rs` 734 to 762). The inbox sets the foreground record on arrival (`crates/verbatim-core/src/event_queue/inbox.rs` 592 to 597, `shared.state.queue.foreground = Some(foreground)`). The tell is judged at its turn: `focus/validity.rs` 800 to 804, `if tell.kind == EventKind::Foreground { if view.in_front != Some(ids.window) { return Ok(Settled::Refused(Reason::NotInFront)); }`, with `view.in_front` from `cx.foreground()` (648). So the tell is refused as `NotInFront` whenever its turn comes before the report reaches the inbox, and accepted when Core's queue happens to be busy long enough for the report to arrive first: the outcome depends on timing. Until the report arrives, the keyboard hook's view of the foreground, attention and the foreground record (the `ForegroundMarker`, `crates/verbatim-core/src/entries.rs` 140 to 151) stay on the old window.

The recorded defect, `docs/parity/focus-events.md` 362 to 365: "A hold that ends by its timer with the window in front sends the foreground tell before the watch has reported it, so Core refuses it: a limit until the hold and the watch keep the pending window in one place." The trace matches it, and adds two things the record does not say: the refusal depends on Core's queue timing, and a second foreground event can lose W's report altogether. A hold that ends by its time with W still not in front sends the tell and Core refuses it, which matches NVDA, whose deferral gives up after `MAX_FOREGROUND_DEFERS` (`internalWinEventHandler.py` 30, 233 to 263) and whose `processForegroundWinEvent` drops a window that is not `GetForegroundWindow` (`IAccessibleHandler/__init__.py` 834 to 840). NVDA's deferral counts core pumps, not 20 ms. No test covers the timer path: the hold's own `fired` tests (logic `tell.rs` 487 to 532) do not involve the watch, and the three ordering tests (`listener.rs` 3236, 3271, 3329) all release on an event.

Fix, two shapes. B's: the hold owns the one pending window and every release, by event or timer, emits the report first; this keeps the threadpool timer, but the watch's `sent` also unhooks the console events (`hook_consoles(false)`), which must happen on the WinEvent thread, so that part needs a hand-back. A's: the timer becomes a thread timer on the WinEvent thread's message loop (`crates/verbatim-ia2/src/event_thread.rs` 311 to 385 pumps `GetMessageW` and `DispatchMessageW`), and `PoolTimer`, `Timed`, `TimerHandle` and `set_timer` go; this moves work between threads, which is Dickson's area (thread layout), see Questions. Either removes `ForegroundWatch::pending`, `has_pending` and `event_seen` (about 60 lines) and adds one test of the timer path (about 40). Speech: changes only in the sequence above, towards NVDA; what is lost today needs a capture.

### L3. The listener's merge of waiting tells (Planned phase: M6.1)

`listener.rs` 276 to 299, `Waiting::merged`: "Queues the tell `message` behind everything waiting, replacing any waiting tell merged by the same `key`, but never across the idle barrier's answer". `TellKey` (`tells.rs` 35 to 42) is "its object, kind and raising thread, NVDA's limiter's key". B's sequence is right about the code: Core's `merge_away` stops at a focus-kind item (`crates/verbatim-core/src/event_queue/limiter.rs` 231 to 234, "a focus tell merges a waiting one of its element, but nothing merges past one"), and the listener's does not, so whether a value change before a focus survives depends on whether a pipe write was in flight. But B's implied standard is wrong: NVDA's own limiter merges across a focus within one pump (`orderedWinEventLimiter.py` 59 to 79: focus events go to `_focusEventCache`, and a generic event replaces its key in `_genericEventCache` whatever came between), so the listener's reach is NVDA's within a pump and Core's is narrower. UI Automation tells never merge: each carries a fresh token (`checking.rs` 522, `ElementToken(self.tokens.fetch_add(1, ...))`), so `Reported::withdrawn` (logic `kept.rs` 171) is reachable only by a tell that carries a token, and none does that can share a key; grep `withdrawn(` over `crates/`, `xtask/`, `uia-facts/`: 2 hits, the call (`listener.rs` 292) and the definition, no test. The decision of record is ADR 0003 135, "it merges only waiting events with the same object, kind and raising thread"; A's changed fact ("No tell waited long enough to be merged", `docs/design/readers-tell-core-asks.md` 469) was measured the same day Dickson reaffirmed "the listener's limiter merges only" (473), so it is not new. M6.1 rewrites this queue: "Queues an application can fill have no count limit: the listener's and the outposts' queues merge by key only" and "Waiting UI Automation tells are coalesced in transit ... The matching place is the check thread's queue" (`docs/roadmap.md`, M6.1). About 50 product and 30 test lines (`waiting_tells_merge_by_object_kind_and_thread`, `tells.rs` 877).

A behaviour is cheap when it is a rule over facts the event already carries, and expensive when a fact must reach a reader that does not own it, or when a new call must be threaded through the check's step machine. Shared mechanisms the reviewers propose, merged: decisions kept in Core with readers acting only when asked, which removes the configuration channel (L1, a question); one definition of each rule both roles apply, in `verbatim-reader-rules` (L4, the numbering; L14, the native judge); one state per fact on one thread (L2, L7, L11); the delivery-time check as straight-line code over a calls trait, so a new call is one line (L5); one shared configuration message for every reader, so a reader's next setting is a field (B); and crate guides that name the code rather than restate it, since ccdb2a7a's documents each needed the same edit (L16).
