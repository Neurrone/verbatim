# Setup and builds

How to get a fresh clone building: the submodules, CMake and wxWidgets, cargo-hakari and the workspace-hack crate, what `cargo xtask ci` scans, the documentation check, and the build's disk use.

## First-time setup

eSpeak NG, Verbatim's default synthesizer, is built from source that
lives in a git submodule, so a fresh clone must fetch it before anything
builds:

```
git submodule update --init third_party/espeak-ng
```

A new git worktree lacks the `third_party/espeak-ng` submodule, so run
`git -C <worktree> submodule update --init third_party/espeak-ng` before
building there.

The `nvda` submodule is reference material and stays optional; the
command above fetches only eSpeak NG. Building eSpeak NG also needs CMake
on `PATH` (Visual Studio's own copy, or a standalone install); the
`cmake` crate drives eSpeak NG's CMake build with Visual Studio's
generator. The first build of `verbatim-gui` (and so of `verbatim-app`)
also builds static wxWidgets 3.3.3 for the GUI: it downloads the release's
source archive, checks its hash, and builds wxWidgets' base and core
libraries with CMake, using Ninja on x64 when it is on `PATH`. That takes
about a minute and a half on the development machine and happens once per
architecture: the result is kept in `target/wxwidgets`, or under
`VERBATIM_WX_DIR` when that is set, and reused by every later build
(`docs/crates/verbatim-gui.md` has the details). GitHub Actions fetches the
eSpeak NG submodule in every job and caches the wxWidgets build.

`cargo xtask ci` also needs `cargo-hakari`, which checks the workspace-hack
crate described next:

```
cargo install cargo-hakari --locked
```

### The workspace-hack crate

Cargo decides each dependency's features from the packages one command
selects, so commands that select different packages (the whole workspace
in `cargo xtask ci`, four binaries for every end-to-end scenario, one crate
for a quick `cargo test -p`) used to build `syn` with different features.
Each of those gave the `windows` crate, and everything built on it, a new
identity, so `target\debug` held a full build per combination, and cargo
never deletes the ones a newer build replaces: it reached 36 GB. Cargo's
own fix, `resolver.feature-unification = "workspace"`, is still unstable.

`crates/workspace-hack` is the standard workaround: generated by
`cargo-hakari`, it depends on every third-party crate with the union of the
features the workspace uses, and every package depends on it, so every
command builds each dependency the same way. The `windows-rs` crates are
left out of it (`.config/hakari.toml`), because the platform-neutral crates
depend on it too and must never pull in the Windows bindings; the root
`Cargo.toml` asks for `windows-core` and `windows-future` exactly as
`windows` does, so they cannot split either. Every crate, the workspace's
own included, is also built with line tables only, not full debug info:
backtraces keep file and line, and the build is a fraction of the size.
Set `CARGO_PROFILE_DEV_DEBUG=full` for a build to step through in a
debugger.

After adding a package or changing a third-party dependency or its
features, run:

```
cargo hakari generate
cargo hakari manage-deps
```

`cargo xtask ci` fails until the crate is up to date.

### What cargo xtask ci runs

`cargo xtask ci` is the standard check and exactly what GitHub Actions
runs, in its `ci`, `ci-arm64` and `ci-linux` jobs. On Windows its steps are
the platform-neutral dependency check, the scans below, the documentation
check, the workspace-hack check above, rustfmt, and pedantic clippy with
warnings denied and unit tests for the whole workspace, all for the host's
own architecture into `target/debug`; no build names a target, so an ARM64
machine checks ARM64. On Linux, where the `ci-linux` job runs it on
`ubuntu-latest`, it runs the dependency check, the scans and the
documentation check, then clippy and unit tests only for the crates in
`LINUX_CRATES` (`xtask/src/main.rs`): the platform-neutral tier and xtask.
rustfmt and the workspace-hack checks run only on Windows, since they read
source and metadata the same way on every host. On Linux xtask builds only
its portable part, so `ci` and `docs` are its only commands there; the
documentation-only `docs` job runs on Linux for that reason, as it builds
less. To check xtask's Linux build from this machine, which has no Linux
C compiler, run a check-only build, which produces no binary:
`cargo clippy -p xtask --all-targets --target x86_64-unknown-linux-gnu
--target-dir <scratch> -- -D warnings` after `rustup target add
x86_64-unknown-linux-gnu`; crates that reach `verbatim-text` cannot be
checked this way, because its `zstd-sys` needs a Linux C toolchain, so
GitHub's `ci-linux` run is their check.

The dependency check inspects the `cargo tree --target all` of each crate the
`CLAUDE.md` NVDA provenance section lists as platform-neutral (every
target's graph, so a dependency gated on `cfg(windows)` counts on Linux
too), and fails
naming every one that pulls in the `windows` or `windows-core` bindings by
any path, or reaches `windows-sys` through a workspace crate that names it
directly; `windows-sys` beneath third-party libraries and the
workspace-hack crate is allowed, since those libraries are cross-platform.

Before it builds anything, `cargo xtask ci` also scans the sources with
checks of its own, each failing the run with the file and line of every
finding:

- Waits in test code (`xtask/src/waits.rs`): a fixed sleep or a retry
  counter anywhere in test code fails it, and the sleeps left in
  production code are listed for review (`docs/testing.md`, "Waits are
  for evidence").
- UIA cached reads through shapes (`xtask/src/shapes.rs`): every cached
  read of a UIA element goes through a shape
  (`docs/design/uia-shapes.md`, section 3.5, item 7). A raw cached read
  (an identifier starting `GetCached`, or a `.Cached` getter such as
  `.CachedName(`) fails it anywhere but `verbatim-uia`'s shape module and
  the cached-children read in its `client.rs`; a raw cache refill
  (`build_updated_cache` or `BuildUpdatedCache`) fails it outside
  `verbatim-uia`; and `.claim(`, which wraps a remote program's element
  as a shape, fails it outside `verbatim-uia-rops`. Comments and strings
  are not scanned, and tests are scanned like everything else: a test
  reads an element through a shape, declaring one in the shape module if
  none holds what it reads.
- Pure owners' names (`xtask/src/ownership.rs`): a module whose
  transitions are replayed in tests, the listener's read scheduler
  (`crates/verbatim-outpost/src/read_schedule.rs`), may `use` only its
  allow-list (`std::collections`, `std::time::Duration`, `verbatim_model`
  and the listener's data types), and fails on any name of a thread, a
  lock, an atomic, an `Arc`, a channel, a clock read, the file system,
  I/O, the environment, processes, the network, the Windows bindings, or
  `unsafe`, imported or written in full. Comments and strings are not
  scanned; it reads text, so its replay tests are the real check.
- Documents' links and paths (`xtask/src/docs.rs`): the documentation
  check below.

`cargo xtask warm-speech` activates the Windows speech platform once and prints how long that took and the default voice's name, failing if the activation fails; CI's two unit-test jobs run it before `cargo xtask ci`, because a fresh runner's first activation outlasts the synthesizer host's ten-second hang bound.

### The documentation check

`cargo xtask docs` (`xtask/src/docs.rs`) checks every Markdown file of
the repository except those under `nvda/`, `third_party/`, `.git/`,
the worktrees in .claude/worktrees, a top-level directory whose name starts with
`target`, and `experiments/` (which records code as it was when each
experiment ran). Fenced code blocks are not read.
It prints each violation as the file, line, and what is wrong, and
fails if there is any:

- Every relative Markdown link resolves to an existing file or directory,
  relative to the linking file. Links to `http:`, `https:`, and `mailto:`
  addresses and bare anchors are not checked.
- Every backticked repository path exists relative to the repository
  root: a code span starting with one of the folders crates, docs, xtask,
  vm, experiments, tools, sounds, videos, extensions, or .claude and a
  slash, with no spaces (a span with spaces is a command) and none of
  the characters star, question mark, angle brackets, braces, or vertical
  bar (a glob or a placeholder), read without a trailing anchor, line, or
  line range. A path that deliberately names something not there yet is
  followed directly by a space and the word planned in parentheses, as in
  `crates/verbatim-braille` (planned), which exempts that span alone and
  tells the reader why it is absent.
- `docs/readme.md` links every Markdown file under `docs/`, directly or
  through one of the indexes it links: `docs/crates/readme.md`,
  `docs/parity/readme.md`, `docs/nvda/readme.md`,
  `docs/explainers/readme.md`, and `docs/tooling/readme.md`.

Names are compared with their letter case, as GitHub compares them.

### Build disk use

Most of a debug build is debug information (PDBs) and incremental
compilation state, and every test binary carries its own PDB holding
everything it links. Two choices keep that down. Every crate is built
with line tables only (above). The end-to-end suite is one test binary,
`crates/verbatim-e2e/tests/e2e.rs`, rather than one per scenario, since
each one linked the whole harness. Add a scenario to that file, never as
a file of its own under `tests/`.

On x64, a clean build of everything `cargo xtask ci` and the suite
build (`cargo build --workspace --all-targets` and
`cargo test -p verbatim-e2e --no-run`) is about 4.1 GB, 1.4 GB of it PDBs
and 1.2 GB incremental state; full debug info and a test binary per
scenario made it 9.6 GB.

Several worktrees building at once (for example, parallel agents) each
build into their own `target` directory; do not point them at one shared
`CARGO_TARGET_DIR`. On a shared one, workspace crates from different
checkouts overwrite each other's output, every switch between checkouts
recompiles them all, and the suite stages Verbatim from the worktree's own
`target\debug`, not the shared one. Share only wxWidgets, by setting
`VERBATIM_WX_DIR` to one directory for all of them. A worktree's build is
used for one piece of work, so build it with `CARGO_INCREMENTAL=0`, which
leaves out the incremental state (about half of a worktree's target
directory, 2.7 of 5.4 GB measured on 2026-10-29), and delete its target
directory when the worktree is removed: on 2026-10-29 four kept worktree
target directories and the main one filled the development machine's disk. A worktree whose path
is deep (such as one under `.claude\worktrees`) also needs
`CMAKE_GENERATOR=Ninja`, since MSBuild's tracking files in eSpeak NG's
CMake build exceed the path length limit there. On a 16 GB machine, build
with `-j 4`, and never build while end-to-end scenarios run: a build
alongside a run once ran memory out and the run was killed.
A second worktree's build needs about 5.5 GB once `cargo xtask ci` has
run in it.
