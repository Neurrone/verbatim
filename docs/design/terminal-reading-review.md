Status: review of `docs/design/terminal-reading.md`, 2026-10-11; the roadmap lists its corrections, folded in when the terminal redesign is built.

Reviewed 2026-10-11 against main at 1063480 (step A1 merged), `nvda/source`, and Microsoft's terminal source at github.com/microsoft/terminal main, commit 7d06b26f (fetched today into the scratchpad's `ms-terminal` folder, reference only). Nothing was built or run. The installed builds are conhost.exe 10.0.26100.1 and Windows Terminal 1.24.12741.0. Which commit of Microsoft's source each build contains is not known, so every claim below about Microsoft's code is "verified in main's source, unverified in the installed build" unless it says otherwise.

## 1. The atomic-read claim

The claim holds in source, for both terminals, with three corrections to what it implies.

Evidence:

- `src/types/UiaTextRangeBase.cpp` lines 944 to 966: `GetText` calls `_pData->LockConsole()` (951), installs a scope guard that unlocks (952 to 954), calls `_getTextValue` (957), and only then releases the lock with `Unlock.reset()` (958), before `SysAllocString`. `_getTextValue` (976 to 1006) takes no lock of its own; it copies the range with `TextBuffer::GetPlainText` while the caller holds the lock. The whole copy is therefore made under one hold of the lock.
- The same class serves both terminals. In the console host, `RenderData::LockConsole` (`src/host/renderData.cpp` 90 to 94) takes the global console lock, `gci.LockConsole()`, which every console API write also holds. In Windows Terminal, `Terminal::LockConsole` (`src/cascadia/TerminalCore/terminalrenderdata.cpp` 207 to 210) takes the terminal's `_readWriteLock`, which output processing also holds. Windows Terminal's XAML wrapper forwards `GetText` straight to the same provider (`src/cascadia/TerminalControl/XamlUiaTextRange.cpp` 190 to 195).
- Every other range method takes the lock separately for its own call, for example `MoveEndpointByRange` at 1126 to 1150 and `CompareEndpoints` at 210 to 240. That supports the design's point that calls are not atomic with each other.

Corrections:

- One `GetText` is atomic with respect to the terminal's own writes: one console API call in the console host, one chunk of output in Windows Terminal. It is not atomic with respect to the program's logical writes. A line the program writes in two calls, or that ConPTY delivers in two chunks, can end a snapshot half written. Measurement 1's refutation test must allow a partial last line and look only for gaps or torn lines in the middle.
- `GetText` copies whatever is at the range's row coordinates at the moment of the call (the `CopyRequest` at 993 uses `_start` and `_end`). That is the design's "ranges are row coordinates" point. It means a kept range in a full history silently reads newer text. The design handles this by content, which is correct.
- The copy keeps padding: the `CopyRequest` passes `trimTrailingWhitespace` false, line breaks true, and `formatWrappedRows` false (`src/buffer/out/textBuffer.hpp` 199 to 228). So a wrapped line does come back whole, which confirms the design's logical-lines claim from source. It also means that in the console host every written row costs its full width, whatever was written to it.

## 2. NVDA claims, checked against nvda/source

Confirmed as written: `behaviors.py` 420 to 424, 446 to 453, 455 to 466, 468 to 505, 491 to 495, 519 to 530, 559 to 570, 572 to 619; `diffHandler.py` 25 to 51 and 112 to 113; `winConsoleUIA.py` 361 to 448 and 463 to 476; `UIAHandler/__init__.py` 145 to 147 and 778 to 798; `UIAHandler/utils.py` 337 to 347; `NVDAObjects/UIA/__init__.py` 511 to 512 and 1452 to 1474; `configSpec.py` 317, 320 and 364; `editableText.py` 70 to 192 and 387 to 413; `inputCore.py` 583 to 605 and 642 to 648; `keyboardHandler.py` 178 to 202, 326 to 355 and 729 to 738; `winConsole.py` 23 and 43 to 46; `winConsoleHandler.py` 83 to 89 and 154 to 173.

Corrections:

- Coalescing. Section 2, "Events used", says the `threading.Event` "is all the coalescing there is for UIA consoles". That is wrong. NVDA enables UIA's own event coalescing (`UIAHandler/__init__.py` 539, `CoalesceEvents = CoalesceEventsOptions_Enabled`). It also routes events through its C++ rate limiter, which merges events by element and event kind before Python sees them (`nvdaHelper/local/UIAEventLimiter/rateLimitedEventHandler.cpp` 33 to 60, flushed at 65 onward). The design itself cites "#14888 coalescing in C++" under the known weaknesses, so the document contradicts itself.
- Difflib's partial-line rule (section 2, "The diff"). The design says a line that replaces a deleted line speaks only the changed span when fewer than 15 characters changed. In fact the rule applies only to a "+" line that immediately follows a "-" line in `ndiff`'s output (`diffHandler.py` 77, `prevLine`), so only the first of several inserted lines is paired. When the two lines differ in length, the "changed span" runs from the first difference to the end of the line (93 to 95), not to the last difference. `ndiff` is not a plain longest-common-subsequence diff: it uses `SequenceMatcher` and pairs similar lines with "?" hint lines, which NVDA skips (65 to 67). So "This is NVDA's line diff" describes NVDA's model only loosely, which is acceptable because Verbatim writes its own diff, but the sentence should say so.
- Backspace. Section 1 says NVDA "speaks the character or word before the caret". It does so only if the caret moved within the timeout; otherwise it says nothing (`editableText.py` 313 to 315). The design's line 153, "it then speaks the unit at the caret whether or not the caret moved", is true of the movement scripts (`_caretMovementScriptHelper`, 181 to 192) and of Delete (329 to 342), but not of Backspace.
- Windows Terminal's text info. Section 2 says FORMATTED consoles and Windows Terminal both use "the plain `UIATextInfo`". Windows Terminal's diff class uses `_WinTerminalUIATextInfo` (`winConsoleUIA.py` 450 to 460 and 472). That class only changes the mouse unit, so the whole-buffer reading is the same.
- Notifications. Section 1 describes ignoring "activity id `TerminalTextOutput`". NVDA blocks every UIA notification from both terminal classes under diffing, whatever the activity id (`winConsoleUIA.py` 431 to 440 and 474 to 476). Verbatim's narrower filter is Verbatim's own choice, so the citation should not present it as NVDA's.
- The flood cap's reversion. Section 2 gives the reason as "a newer batch cancelled the older one". `docs/nvda/editable-text-and-terminals.md` 213 to 217 gives the reason as "users could not read the skipped output". One of the two needs correcting.
- Typed-character dispatch. Add that `_reportNewLines` also clears the characters still queued when it reports new lines (`behaviors.py` 567 to 569), so characters typed between a text change and its report are never echoed.
- The cancel. NVDA queues its cancel on the same `eventQueue` as `_reportNewLines`. Lines queued before the key are therefore cut off, but lines from a read that finishes after the key are still spoken (`inputCore.py` 595 to 605 against `behaviors.py` 497 to 502). The requirement "nothing read before the key is spoken after it" is Verbatim's (Dickson, 2026-10-07), and NVDA guarantees it only partly.

## 3. Claims about Verbatim's current code (main, after A1)

Confirmed: every symbol listed for removal exists. `Memory`'s fields `top_row`, `next_row`, `scrolled`, `unwritten` and `rows` are at `crates/verbatim-outpost/src/terminal.rs` 48 to 86. `trusted` is at 487, `footer_below` at 499, `screen_at` at 549, `Found::Unsettled` at 241, and the `Owed` and `ReplyUnsettled` states at `terminal/reading.rs` 20 to 26 and 47. `SEARCH_MATCHES = 20` is at `verbatim-uia-rops/src/terminal.rs` 55. `CARET_HISTORY` is at `verbatim-core/src/state.rs` 187, `REMEMBERED_CARETS` at `text/mod.rs` 60, `CARET_WATCH_BOUND` (10 seconds) at `outpost/text_reads.rs` 55, and `key_owns_line` at `verbatim-core/src/terminal.rs` 136. The file lengths of 1,007 and 1,133 lines are correct.

Corrections:

- The line numbers in worker.rs are stale after A1. `wrapped_removal` is now at 1186 to 1227, called from 900 and 975, and `terminal_event` starts at 1239.
- The summary says the current code "reads only the visible screen". It also reads up to `head_wanted` rows that scrolled by unread (`ScreenText::head`, terminal.rs 166 and 331). Extra 2 says this, but the summary should too.
- The coalescing invariant in "When to read" is presented as new, but it exists today. `terminal_output` (worker.rs 1389 to 1400) drops a change event observed before the last read began (`read_started_ms`, set at `text_reads.rs` 474 to 475). That rule is conservative under millisecond rounding. What the design adds is only the removal of `Owed`.
- A defect the design should fix explicitly, which it currently fixes only implicitly. The caret read with a terminal's text is emitted with the change event's observation time (`terminal_event`, worker.rs 1324 to 1332, `observed_at_ms`), not with the read's time. Core's `caret_before` (`editing.rs` 205 to 233) picks the caret before a key by `observed_at_ms < pressed_at_ms`. Suppose a read begins after a key but was triggered by an event observed before it. Its caret, which may already show the key's effect, is then taken as the caret before the key. This plausibly explains the roughly one-in-four failure of `conhost_typing` step 5, and it is the exact thing the design's "read end time" field is for. As a pre-existing bug, it should be reported as a follow-up, not fixed outside step 9.
- The clock. `pressed_at_us` (`verbatim-input-windows/src/lib.rs` 479 and 485, `unix_us()`), the outpost's `now_us` (`protocol.rs` 53) and Core's `now_ms` are all `SystemTime`: shared across processes, but a wall clock that a time adjustment can move. The design compares times across processes, so it should name the clock. One option is to keep `SystemTime` and accept the risk around a time adjustment. The other is to change to `QueryPerformanceCounter`, which is consistent across processes on Windows 11. Either way the times should be kept in microseconds: millisecond truncation makes "ended before the press" undecidable for a read that ends in the same millisecond.

## 4. Key attribution in Core and stage A2

The design's mechanism agrees with A2 in what it needs, but its wording and step 2 of its order of work contradict A2:

- The design asks Core to take "its two input channels in time order (each message stamped when queued ...)". A2 decides the opposite, and the focus design gives the reasons (`docs/design/focus-pipeline.md` section 4.1): one channel in arrival order, with no ordering by observation time and no reorder buffer. Step 2 of the design's order of work, "Time-ordered intake in Core's reducer", is therefore superseded and should be deleted, and section 3's sentence rewritten to say arrival order.
- Arrival order already gives the property the design wants, for the keys that matter. The hook sends `KeyReport::Observed`, `Passed` and `Typed` straight into the reducer's command channel (`verbatim-app/src/main.rs` 361 to 433, `reports_tx = command_tx`), from inside the hook procedure and before `CallNextHookEx` (`lib.rs` 477 to 503 against 548). After A2 that channel is the single channel, so the report is queued before the application can receive the key, and any read showing the key's effect is queued after it. This holds only for keys reported by the hook directly. Gestures routed through the router thread (`Routed::Gesture`) take an extra hop and are not ordered this way, which the design does not need.
- What the design needs from timestamps, given that A2 stamps outpost messages at receipt. Receipt time must not be used for attribution. A read whose snapshot was taken before the key can reach Core after the key, which is the design's own "in the pipe" case, and a receipt stamp would wrongly make it the key's. Each terminal fact must therefore carry the outpost's own times as payload: when the read's remote operation began and when it ended, on the same clock as the hook's `pressed_at_us`. The design's rules then become:
  - a fact from a read that ended before the press describes the state before the key;
  - a fact from a read that began after the press may show the key's effect;
  - a read that spans the press is decided by content.
  Core processes messages in arrival order and uses these times only to classify; nothing waits on them. The same applies to `cut_at_ms` (`verbatim-core/src/terminal.rs` 254), which today compares against the event's observation time.
- Typed characters carry no press time (`KeyReport::Typed { trace_id, text }`). The design matches them by content only, which works with arrival order. Giving `Typed` a press time would let the same "read ended before the press" rule reject a coincidental gain from a read taken before the key, such as a program printing "y" just as "y" is typed. This is recommended, not required.

## 5. Performance

Read size:

- The document's end is fixed by source, which settles measurement 2's question in principle. `get_DocumentRange` (`src/types/ScreenInfoUiaProviderBase.cpp` 321 to 332) expands to the document unit. That unit ends at `_getDocumentEnd` (`UiaTextRangeBase.cpp` 1341 to 1347): one row below the lower of the last non-space character and the cursor. It is computed within `_getOptimizedBufferSize` (1325 to 1334), which is the whole buffer in the console host (`renderData.cpp` 38 to 43) and the bottom of the mutable view in Windows Terminal (`terminalrenderdata.cpp` 16 to 22). So the document ends at the last written row or the cursor's row in both terminals, and rows below it are never in a document range. Open question 2's answer, the document's end, follows; the measurement only confirms it on the installed builds. A footer that the console host redraws lower is non-space, so it is inside the document.
- The bound on one snapshot is the rows from the kept range to the document's end. A cleared range of rows inside that span still costs its padding. In the console host each row costs its full width plus a line break, so 9,001 rows at 120 columns is about 1.1 million UTF-16 code units, about 2.2 MB, against Windows Terminal's 610,244 characters at 5,000 lines. The design's statement that "trailing blank rows are trimmed after reading, so the padding cost is bounded by one screen" applies only to the "visible end plus one screen" option. With the document's end there are no trailing blank rows to read, but padding inside written rows is unbounded, and the design should say so.
- `GetLastNonSpaceCharacter` scans backward from the buffer's bottom, under the lock, on every document-range request. In the console host that is up to 9,001 rows on a new console. This is cheap but not free, and it belongs in measurement 3.

The diff window:

- For the normal read the bound is correct and linear. Only the snapshot's first lines, up to the old screen's length plus one screen, are aligned, and the rest is appended. For a 2,000-line flood read in one snapshot with a 30-row screen, at most 61 lines are aligned against 30.
- For the whole-document fallback, the window as written does not apply, because the old screen can lie anywhere in up to 9,001 lines. The design must state that fallback's alignment and its bound. One proposal: find the old screen's last non-blank lines by content, scanning from the end of the snapshot backward, with each candidate checked against the whole old screen. The work is then bounded by document lines times old-screen lines, about 270,000 line comparisons in the worst case. When identical lines tie, the match nearest the end wins, which gives the smallest, and so honest, "more than N".

Reading the whole buffer once:

- Per read, yes: the kept-range snapshot finds no overlap, then one whole-document `GetText` follows, and there is no loop. The design should state explicitly that the whole-document read is never repeated within one read, even when it also fails to find the old screen. That failure is the overflow verdict.
- Per flood, no. While reading is held with a full history, every group's read after more than a screen has scrolled takes the fallback, so there is one whole-buffer read per group (about every 30 spoken lines). At about 6 ms per 610 KB this is acceptable, but the design's "cheaper than NVDA in the usual case" should not be read as "once per flood".
- Lock hold time is the real cost. The terminal's writer waits for the whole copy, so measurement 3 must measure how much the writer slows down, not only how long the read takes.

The proposed work-bound test. `docs/testing.md` line 33 requires exact counts, not bounds, so the test asserts exact numbers that the design defines:

- Make the diff return its work alongside its output, for example `Work { aligned_new: usize, aligned_old: usize, compared: usize }`. `compared` counts line equality tests.
- Flood case, a unit test in the platform-neutral crate. The old screen is 30 distinct lines ending with a prompt. The snapshot is those 30 lines with the prompt grown by the command, followed by 2,000 numbered lines and a new prompt. Assert the exact output: 2,001 appended lines, the change of the prompt line, and no skipped count from the diff itself, since the flood policy cuts later. Assert `aligned_new == 61` and `aligned_old == 30`, and assert `compared` equal to the exact number the chosen algorithm performs on this input, computed once from the algorithm's definition and written down beside the test. Any growth in that number changes the assertion and fails the test.
- Overflow case. The old screen is 30 lines. The first snapshot is 30 rows of newer text with no overlap. The second, whole-document snapshot is 9,001 rows that do not contain the old screen. Assert the output exactly: `Skipped::MoreThan(9001 - 30)` less the lines spoken, followed by the newest lines. Assert `compared` exactly, and that it is no more than 9,001 times 30 by construction. In mockapp, under step 4 (`crates/mockapp/tests/terminal.rs` already asserts `CallCounts`), assert exactly two `GetText` calls, the second on the document range, and exactly one `GetText` on the next read when nothing changed.
- Identical-line variant of the overflow case, with 9,001 identical rows: assert `Skipped::Uncounted`, as open question 7 decided.

## 6. Gaps and contradictions

- Missing text-change events. The design says that when the terminal raises no further events nothing is read, and treats that as the terminal's defect. Main's console host source makes this a likely and specific case. `raiseAccessibilityEventsOnExit` (`src/host/_stream.cpp` 33 to 79) raises `RegionChanged`, and through it UIA's text-changed event and `EVENT_CONSOLE_UPDATE_REGION`, only when the cursor's coordinates differ before and after a write. With a full history the buffer rotates under a cursor that stays on the bottom row. A write that ends at the same cell it started from, such as a whole line and its line break, therefore raises no text change. For VT output, the rotation's own notification is a no-op in the console host (`src/host/outputStream.cpp` 445 to 447, `NotifyBufferRotation`). This is a hypothesis for measurement 5's "events stop mid-write in 2 of 14 runs": the runs were 12,000-line writes, which fill the history. If the installed build has this code, then extra 12's WinEvents do not help either, because they are gated by the same cursor test. In that case the evidence rule must be rethought with Dickson, for example by treating the caret's text-selection event as evidence. The events were rewritten and debounced in microsoft/terminal #19344 (merged 2025-09-22), so whether build 26100's conhost has this code must be measured.
- Switch evidence for the alternate screen. The bounds checks in `CompareEndpoints` (`UiaTextRangeBase.cpp` 236 to 240), `MoveEndpointByRange` (1145 to 1146) and `_getTextValue` (991) return `E_FAIL` only when an endpoint lies outside the active buffer. The alternate buffer is one screen tall. A main-buffer range whose row is inside the alternate buffer's height therefore reads the alternate buffer silently. That happens when the main screen has less than one screen of history, not only "no history yet" as extra 6 says. The same code serves Windows Terminal, so measurement 4 should expect the same behaviour there. The design's second piece of evidence (no history above the screen while the memory had it) covers the rest.
- The overflow rule in extra 3 ("first line differs from the first line last seen") is always true while a full history rotates, so it adds nothing beyond "old screen not found in a document that has history". Say that directly.
- Extra 12's cost omits Microsoft's warning that registering for console WinEvents "will significantly impact performance of all command-line applications running on a system at the same time" (learn.microsoft.com, "Console WinEvents"). The console host checks `IsWinEventHookInstalled` (`src/host/AccessibilityNotifier.cpp` 248 and 279), so any registration costs every console.
- The ten-second bound on a caret key's watch (open question 10, decided to drop) also lives in the outpost's `CARET_WATCH_BOUND` and `wake` (worker.rs 1063 to 1076). Step 6 should list it for removal.
- Identical lines with a full history are invisible between any two reads, not only when the history overflows. If more than a screen of identical lines scrolls between reads, the snapshot from the kept row matches the old screen exactly. Open question 7's wording ("also overflows") understates this, and the limitation should be documented as "with a full history".

## 7. Measurements, in order, and how to run each

All are scratch probes, uncommitted, in an interactive session (locally with `cargo xtask park` when Dickson agrees, or in the VM). Each is a scratch Rust binary in the scratchpad that links `verbatim-uia` and `verbatim-uia-rops`, plus a PowerShell writer script.

0. Builds (no desktop needed): record the conhost.exe and WindowsTerminal versions. This was already done: 10.0.26100.1 and 1.24.12741.0. It decides whether Microsoft's main-branch notifier code applies; results 5 and 6 decide it in practice.
1. Atomicity, which gates open question 1. The writer prints `seq checksum padding` lines in one `Write` per 50 lines. The probe loops for 30 seconds: document range, `GetText(-1)`, then checks that each snapshot is consecutive with no interior torn line (the last line may be partial). Run in both terminals.
2. Document end. With the probe, compare the document range's end row with the cursor's row and the last non-blank row: on a new console, after 10 lines, with a footer drawn below the cursor, and with the history full.
3. Cost and lock hold. A snapshot from a kept range to the end at 30, 1,000 and 9,000 lines, and a whole-document read at 9,001 lines in both terminals: the probe's wall time, and the writer's lines per second with the probe reading continuously against without it.
4. The alternate screen. Keep a main-buffer range at row 5 and at row 5,000, open `less` or a script using `ESC[?1049h`, and call `GetText`, `CompareEndpoints` and `MoveEndpointByRange` on each range. Also record whether `cls` and `Clear-Host` clear the history in each terminal.
5. Missing events. A scratch listener subscribes to UIA text-changed events on the console host's text area and hooks the four console WinEvents for the conhost process, logging each with a timestamp. Run three writes:
   - with the history not full, single lines written one `Write` each;
   - the same after the history is filled with 9,100 lines;
   - the 12,000-line flood from `conhost_scrollback_overflow`.
   Run each with UIA event coalescing on and off, and once with NVDA running alone, as the design asks. The second write tests the cursor-gating hypothesis directly.
6. Stage C's scroll-count question, only if Dickson still wants live confirmation after section 8 below: the same listener logs `EVENT_CONSOLE_UPDATE_SCROLL` with its idObject and idChild while 12,000 identical lines are written. Run it twice, once by a VT-mode PowerShell `Write-Output` and once by a legacy WriteConsole without VT (for example `cmd /c type` of a file), and compare the summed idChild with the lines discarded.

The behavioural scenarios in step 5 of the design's order (flood, footer, overflow, full-screen, pager, lists) come after these, as the design says.

## 8. Can EVENT_CONSOLE_UPDATE_SCROLL count a flood of identical lines?

Not reliably. The recommendation is not to build on it.

- Microsoft's documentation ("Console WinEvents", learn.microsoft.com/en-us/windows/console/console-winevents) says only: "The console has scrolled. The idObject parameter is the horizontal distance the console has scrolled. The idChild parameter is the vertical distance the console has scrolled." It does not say whether this counts buffer rotation or view movement, and the page opens by discouraging these events in favour of UIA and warning of their system-wide cost.
- Main's source answers the question:
  - The vertical distance is the sum of buffer scrolls (`ScrollBuffer`, `src/host/AccessibilityNotifier.cpp` 246 to 274) and view scrolls (`ScrollViewport`, 277 to 289) over a debounce interval, raised once per timer callback (526 to 536). Microsoft's own comment at 252 to 254 says this design makes the information "completely useless".
  - The only buffer-scroll caller found is the legacy, non-VT write path, one `ScrollBuffer(-1)` per line that rotates the buffer (`src/host/_stream.cpp` 125 to 140).
  - The VT line-feed path rotates the buffer and calls `NotifyBufferRotation(1)` (`src/terminal/adapter/adaptDispatch.cpp` 2491), which the console host implements as a no-op (`src/host/outputStream.cpp` 445 to 447). PowerShell's output, which is in VT mode, would therefore raise no rotation count at all.
  - Windows Terminal raises no console WinEvents.
- The design's open question 7 should stand: an identical-line flood with a full history is uncounted. Stage C's question can be closed with this evidence, recorded as provisional pending measurement 6 on the installed build.
