# The focus pipeline with the outposts reading: an alternative design

Status: proposed on 2026-10-29 as an alternative to the agreed design ("The design" in [the focus pipeline rework](focus-pipeline-rework.md), as of commit c8045284), for Dickson's decision. Nothing here is to be built until the experiment at the end has run and Dickson has decided between the two. Where this document is silent, the agreed design holds.

In this version the focus listener makes no call into any application. For a UIA focus it sends the application's outpost a notice holding only what UI Automation cached with the event, and the outpost finds the element itself, judges NVDA's checks on it and reads it, in one place and in its application's order. The same approach was the design of record from 2026-10-01 to 2026-10-11 and was replaced by the listener reading (option (b) of [the focus pipeline](focus-pipeline.md), section 2.2). The history comes first, because it decides most of what follows.

## Terms

- A notice: the message the listener's UIA callback sends an outpost for a focus, a menu opening, a selection or a notification. It carries what the event's cache holds (runtime id, name, control type, class, framework, automation id, process, the element's own window handle or 0, the cached keyboard focus) with the event's stamp, and no element. It takes the place of today's marker and of the listener's read.
- Acquiring: the outpost getting an element of its own for a notice, by `ElementFromHandleBuildCache` on the sender's own window when the sender is a window, otherwise by `GetFocusedElementBuildCache`.
- A match: the acquired element's runtime id equals the notice's. A mismatch is any other answer.
- The focus window: the keyboard focus window of the foreground thread, read locally with `GetGUIThreadInfo`, as the outposts' focus-now read takes it today (`window::focus_window` in the outpost).
- A kept read, current, a plain window, a read request, the bound of a walk, the gap and the hand-over: as in the agreed design's terms.

## The history: the outpost reading, 2026-10-01 to 2026-10-11

The outpost redesign of 2026-10-01 (its record was deleted on 2026-10-28 in 44196cd0; git keeps it) had the listener forward each UIA focus as a fact from the event's cache, and the outpost resolve it "with one `focused_element` call, compared against the fact's runtime id. A mismatch means focus has already moved and the newer fact will arrive; the stale one is dropped." That is the shape asked for here, without a remote operation. Over the next ten days it was patched where it failed, and on 2026-10-11 it was replaced by the listener reading each focus from its sender (a4fcbcf1, whose message lists what went: "the focused element read for a focus event, the moved-on rules, 8be2223's Control+Tab rule, the name-and-position search"). The phase 6 record of that work (deleted in 6947275a), its section "The listener reads each UIA focus", gives the reason: the outpost "judged the focus when its worker reached it, often after the focus had moved on, and patched the cases with the moved-on rules and the name-and-position search."

Each problem met, with its evidence, and whether this version avoids it:

- A starting application's stand-in. Windows 11 Notepad, still starting, answered `GetFocusedElement` with a nameless edit read through UIA's window proxy, carrying the document's runtime id; the outpost took it as the focus, read no text pattern and spoke the whole document as its value (phase 6 record, "Notepad at launch and the outposts' loose ends", 2026-10-08; 0d791a13, a80986a2). It first forced the redesign's own revision, that a mismatch within the application reports the focus from the fact instead of dropping it. This version: partly avoided. The proxy rule (`docs/design/listener-without-connections.md`, section 5) now refuses an element served only by UIA's proxies, so a stand-in is never taken; and a sender that is a window, as Notepad's text area is, is acquired from its own handle, as 0d791a13 already did. But a refused or wrong answer leaves the notice with no element, and nothing is spoken until the next event, where the listener today reads the sender itself. The experiment counts it at Notepad's launch.
- Judging after the focus has moved on. Control+Tab in Windows Terminal raises focus on the tab and then the terminal; by the time the outpost handled the tab, the terminal had the focus and the tab was dropped, where NVDA speaks it and culls it (2818fd4f; phase 6 record, "Control+Tab announces the tab"). The fix reported a moved-on focus as its event said, which needed its element found elsewhere, and grew three rules: a container that had passed the focus to its content was dropped (5076b5aa, File Explorer's pane said before its list in 1 of 10 runs), the tab Control+Tab leaves was dropped once it lost its selection (8be22232), and File Explorer's late focus on its list's container was dropped expecting the item's own event, which never came, so nothing was said (phase 6 record, "A foreground event before its window is in front", 2026-10-10). This version: the cause is not avoided, since the outpost still judges when its worker reaches the notice; the patches are. A mismatch reports the element the outpost found, which is where the focus is now (the outpost's rule, below), so nothing is searched for, no moved-on rule exists, and a focus whose own event never comes is still spoken. What is lost is NVDA's speech of a focus that has already moved on when the outpost reaches it: it is not spoken at all, where NVDA speaks and culls it. How often that happens, against the listener's read today, is the experiment's first measurement.
- Elements in no tree. Windows Terminal raises its tabs' focus from elements that are not in its tree (the event named runtime id 17 while the tree's tabs had 9 and 10; phase 6 record, "Control+Tab announces the tab"), so the search by runtime id failed and the search by name and position found the tree's tab, whose ancestors made Verbatim say "tab control" before "list" (2818fd4f; `docs/design/focus-pipeline.md`, sections 2.1 and 12.5). This version: not known. There is no search; whatever `GetFocusedElement` answers during the tab's focus is read with its own ancestors. If it answers the event's own element, the result is today's; if it answers the tree's tab, the tab is read with "tab control" above it; if it answers the terminal, only the terminal is said. The experiment records which.
- A runtime id naming a destroyed element. File Explorer gave a new element a destroyed one's runtime id, and the outpost mapped it to the old node, so Core stayed silent (c67806c5; `docs/uia-bugs.md`, "File Explorer reuses a destroyed element's runtime ID"). This version: avoided by the same mechanism c67806c5 built, which was the outpost's: before a runtime id that names a node is reused, the kept element's keyboard focus is read live, and a node is reissued when it has lost it or is gone.
- States read too early. The outpost built the focus from the event's cache, read before File Explorer selected the item, so Verbatim said "Inner not selected" and then "selected" (36d93f3b). This version: avoided; the acquired element's cache is filled when the outpost handles the notice, which is when NVDA's main thread reads a focus's states.
- A focus reported from its event alone. When no element was found in time, the focus was reported from the fact, its element read again up to three times (f34c1fcd, b4f84d01), and its subscriptions listened nowhere until the window-wide follow (dd9114f1). This version: avoided by construction, since nothing is reported without an acquired element and nothing is retried; the price is the silence of the stand-in and timeout cases above.
- A windowless focus judged by its application. A windowless UIA focus the outpost could not find was reported with no window, so Core judged it by application and could speak a focus from an application already left; the listener was made to send the focus window from `GetGUIThreadInfo` (a842bf9, D13 amended 2026-10-05). This version: avoided; every report's window is the nearest window of the element the outpost read, and the outpost's local checks before acquiring use the focus window.
- The cost of reading the focused element again. On 2026-10-05 a UIA focus read made three cross-process calls, the first "fetching the live focused element again (2 to 4 ms in File Explorer, up to 10 ms in the Start menu; NVDA gets the element with its event)" (the deleted handoff of 2026-09-02, "Latency investigation, shelved 2026-10-05"). This version: not avoided; the fetch returns for every focus whose sender is not a window. Against it, the listener's five calls per focus go (costs, below).
- A call that lands in another application. `GetFocusedElement` connects to whatever window has the focus, so an outpost whose call landed in another, held application waited on it (E5, `docs/design/focus-pipeline.md`, section 11; `experiments/mockapp-experiments-2026-10-10/`, `e5_focus_read_in_held_application`), and whether it collides with another process's queued remote operation is recorded as unsettled ("failed in an earlier experiment and succeeded in 3 of 3 of the latest", `docs/uia-bugs.md`, "A new connection fails while another process's remote operation is queued"). This version: not avoided, narrowed. The outpost checks the focus window's provider process locally before the call and the answer's process after it, so it reads nothing of another application; but a focus that moves to another application between the check and the call still makes one connection there. The experiment counts the answers from another process.
- A connection into a window the application is still building. An outpost's connection by handle to a new File Explorer window, made after its probe, held the worker 2,003 to 2,516 ms in 1 to 6 of the 10 new windows of each `measure_focus_explorer` run; without it every first item was queued 62 to 323 ms after its event (`docs/design/listener-without-connections.md`, risk 11; `docs/roadmap-done.md`). Today the listener reads a new window's first focus from the held sender, with no connection, and the outpost's own lookup comes after the report for a focus without text. This version: not avoided, and it is the largest measured risk: every UIA focus whose sender is not a window makes a connection before it is reported.
- A focus behind reads of other objects. The first focus in a new File Explorer window waited 2,589.6 ms behind reads of other objects' events planned into the same batch (42d9caaf), fixed by putting a focus first in its batch. This version: partly. The intake's rule stays, but a call already under way cannot be overtaken, and the read itself now waits for the worker, where today it runs on the listener's reading thread while the worker is busy.
- The cross-outpost ordering race. Notepad's outpost delivered a focus observed before Verbatim's menu opened after the menu's own focus, and the stale rule by observation time was restored (84767402, 11616bd0, 2026-10-02). It does not depend on who reads; Core's stale rule carries over unchanged.
- The Notepad foreground race. Windows raised Notepad's foreground event about 130 ms before the window came in front, and the desktop list's focus raised meanwhile was spoken (9d82a415, b1917eed, 9e250d2). It does not depend on who reads; the acceptance test against the real foreground window before the read carries over, made once, by the outpost.
- One console window reported by two outposts (ece62cdf; phase 6 record, "Console windows as one application"). Routing by provider process carries over; a notice goes to the process the sender's cached process id names, which for a console's text area is the console host.
- Two processes calling into one application for one event, the objection to option (a) (`docs/design/focus-pipeline.md`, section 2.1). Avoided: the listener makes no call.
- The listener's read under the no-connection rule. A read of several calls on held elements, where one remote operation had been one transaction, needed a budget, a deadline and six commits on judging out of time in one day (30d808b2, 52b64765, fa255063, 9e517cad, c1b36869, e46d4183, 2026-10-20), woke the reading thread about 2,000 more times in 7 seconds of Notepad's menu bar (decision 12 of the listener design), sends a parent window across the process boundary the messages of decision 13, and needed a bound on threads spawned against a hung application (71126b8d). Avoided: none of it exists in the listener. The outpost's read is one remote operation, which the transaction timeout bounds as a whole.
- Two verdicts for one window. The listener's probe and the outpost's can judge one window differently (the agreed design, "The verdicts"). Avoided: only the outpost judges a window's backend for a UIA focus.
- UIA's late delivery and gone senders. UIA delivers a new process's focus events late or never, and sometimes after their senders are gone (`docs/uia-bugs.md`, "A new process's focus events reach the desktop-wide handler late or not at all"; the listener design, risks 2 and 13). Gone senders: avoided, since the outpost reads where the focus is and needs nothing from the sender. Never delivered: not avoided; the gap stays.
- Windows Terminal's second runtime identity. Its terminal's focus is sometimes raised from a second identity, which `CompareElements` says differs, so "terminal" was said twice (`docs/design/focus-pipeline.md`, section 16.8; `docs/uia-bugs.md`; `experiments/windows-terminal-raises-focus-from-a-second-runtime-identity/`). This version: probably avoided, unproven. If `GetFocusedElement` answers the usual identity while the second identity's notice is handled, the notice is a mismatch whose found element is the kept read, a repeat Core drops, and nothing more is said; that would also make the Windows Terminal module's twin rule (`docs/design/windows-terminal-twin-focus.md`) unnecessary. The identity judge measures it.
- The stale-focus race between the two routes. A change the outpost's own subscriptions receive before the focus's message reaches the outpost is handled before the focus (`docs/design/focus-pipeline.md`, section 13). Not avoided and not worsened: the notice travels the marker's route at the marker's time.
- The marker's patches. The marker news for the gap (3d99e52c, 8c4d5df4) goes with the marker. The reorder of the old focus's state changes ahead of a focus inside it (05fe1594, 4d442eb5) stays, since it answers the two routes' arrival order, which is unchanged.
- The first focus of a new application read while its outpost starts. Today the listener reads it while the marker starts a spare, which saves up to about 30 ms (`docs/design/focus-pipeline.md`, sections 12.6 and 19.1). Not avoided: the read waits for the outpost's `Ready`, under 12 ms with a spare.

## The constraints that still hold

Every constraint of the agreed design holds, and this version is built from them in the same way:

- A UIA element cannot leave the process that received its event (`docs/uia-bugs.md`, "Elements cannot be passed to another process"). So the outpost cannot have the sender; it finds an element of its own, which is this version's whole risk.
- A UIA focus registration is desktop-wide, and one in every outpost would cost 47 to 90 provider calls each per focus change (E-cost). So one listener still receives every UIA focus.
- A hung window named in a focus `WinEvent` holds every UIA event of a process with a focus registration. So the listener stays a process of its own, holding the registration and nothing whose stall would be heard. With no reads it holds even less.
- A thread blocked in a cross-process call cannot be cancelled (D9). The outpost's worker, watchdog and abandonment carry every read now.
- UIA delivers a new process's focus events late or never; decision 11 recovers them.
- `WinEvent`s and UIA callbacks have no common order.
- A console window's owner is the console's client while the console host serves it.
- Two Verbatim processes connecting to one application collide inside UIA. Only the application's own outpost connects to it, which this version keeps except for the narrowed case of `GetFocusedElement` above.
- NVDA parity for everything spoken, from captures and the pinned source.
- Verbatim's hidden frame is never announced.

## The design

### Per process

- The listener holds the UIA focus registration and its global group, in NVDA's order (`docs/design/focus-pipeline.md`, section 16.8), the global `WinEvent` hooks with the desktop switch, the gap's records, the applications whose outposts have their hooks in with each one's forwarding tick, and the time of the newest change of top-level window among the focus and foreground events it observed. Its UIA callback makes no call into any application. It drops an event received before its subscriptions are installed, an event of an ignored process, and an event whose sender is a window `IsHungAppWindow` names (the cached handle, a local call); it applies M5's window and event rules from the event's cache; and it sends the application a notice, numbered and stamped. A notice carries one bit more: whether the listener observed a focus or foreground event in another top-level window since this application's previous notice, so the outpost knows whether its kept read is current. It keeps no element, no reading thread, no watchdog and no verdict. It sends notices, forwarded `WinEvent`s until an outpost's hook is in, forwarding's end, focus-missing, menu and switcher ends, the foreground window for the keyboard hook, and the desktop switch.
- An outpost holds what the agreed design gives it, and in addition is the only reader of its application's UIA focus. For a focus notice it makes NVDA's checks before a read (below), acquires its element, reads it in one remote operation and reports it, or sends a repeat unread, all in its intake's order. It keeps one kept read for both backends: the UIA element it read last, with its runtime id and chain, or the MSAA address. For a menu opening, a selection or a notification it finds the sender as described below. It answers Core's read requests in its queue's order.
- The app is as in the agreed design: it decides nothing about a focus, reads only Windows' own state and relays notices with the marker's priority.
- Core is as in the agreed design: the only judge of what depends on the state it holds, making no call.

### How an outpost handles a focus notice

In the intake's order, as one entry:

1. Local checks, no call into the application. The window judged is the sender's own window when the notice has one, otherwise the focus window. If that window is not served by this application (`served_by`), the focus has left the application and the notice is dropped, as NVDA drops a sender whose keyboard focus reads false. If it is gone, a ghost or hung, the notice is dropped, as NVDA's hung check drops it. If the outpost's verdict for it is MSAA, the notice is dropped, as NVDA's native check drops it, and the outpost's own `WinEvent` copy carries the focus. Then NVDA's acceptance test against the real foreground window, Verbatim's hidden frame, and the console window's own element (its class and handle in the cache).
2. The repeat test, one call. When the notice's runtime id is the kept read's and the kept read is current (no foreground change from the outpost's hook since it was read and the notice's bit clear), the kept element's `CurrentHasKeyboardFocus` is read; true, and the outpost sends Core the repeat unread, as the agreed design's repeats do.
3. Acquiring, one call and one connection. A sender that is a window is acquired by its own handle, a connection to the application's own window. Any other by `GetFocusedElementBuildCache`. The answer is discarded when its process (the cached process id, or the provider process for a console window) is not this application, or when the proxy rule refuses it; then nothing is reported for the notice, and the next event or the gap speaks.
4. Matching, no call. A match is the sender's own element: the focus NVDA would read. A mismatch means the sender no longer has the keyboard focus, or is one Windows Terminal raises from outside its tree or from a second identity. NVDA would drop the sender; this version reports the found element instead, as the focus where it is now, unless it is the kept read and current, which is a repeat sent unread. Notices of the application waiting in the intake older than the one the found element matches are dropped as moved on, so a burst read late costs one read, not one per event.
5. The read, one remote operation on the acquired element: its cache refreshed, its keyboard focus, a list's or tab control's selected item, its raw-view ancestors with their window handles up to the first known ancestor, the desktop's root or the process boundary, and its nearest window (`verbatim_uia_rops::focus_ancestry`, the focus-now read's program today). Above the process boundary the chain continues through MSAA, as today. If the nearest window differs from the window judged in step 1, its acceptance test is made again on it.
6. The report, with a chain complete to the desktop, M5's node rules and hooks applied at emission as the agreed design places them. The element is kept, followed by the focus-following group at once, and its caret read for a text focus. There is no search for the outpost's own copy, because it is the copy.

So a steady focus costs two calls and one connection; a repeat costs one call; a focus in a window the outpost judges MSAA, in a hung window or outside the application costs none.

### NVDA's checks before a read, and where each is made

NVDA's focus handler (`nvda/source/UIAHandler/__init__.py`, 874 to 958), in its order, and this version's place for each:

- Events before initialisation are ignored (877 to 881): the listener, as today.
- The hung window, from the sender's cached handle (882 to 885; `UIAHandler/utils.py` 415 to 459): the listener, for a sender that is a window; the outpost again, on the window it judges, in step 1, which also covers windowless senders.
- `isNativeUIAElement` (887 to 899; its body 1516 to 1575, the nearest window from `getNearestWindowHandle`, 1383 to 1460, a live `NormalizeElementBuildCache`): the outpost, in step 1, on the sender's own window or the focus window, by its own verdict. The nearest window is not read before the acquisition, since only the sender has it; the focus window stands in for it, and step 5 checks the real one. A windowless sender whose nearest window differs from the focus window, both of the application, is judged on the focus window first; the experiment counts how often they differ.
- The duplicate test against the last queued focus (902 to 920: `compareElements` and the last element's live `currentHasKeyboardFocus`): the outpost, in step 2, by runtime id and the kept element's live keyboard focus, which is the evidence c67806c5 built for reused runtime ids; then Core, as decided.
- The acceptance test on the nearest window (921 to 927, `shouldAcceptEvent`): the outpost, in steps 1 and 5.
- Making the object (928 to 942): the outpost's mapping; M5's overlay rules and modules apply at emission.
- `shouldAllowUIAFocusEvent` (943 to 948; `NVDAObjects/UIA/__init__.py` 1632 to 1637, the sender's live `currentHasKeyboardFocus`): replaced by the match in step 4, made on the element that has the focus rather than on the sender. A match is the sender having the focus; a mismatch is a sender without it, except for elements in no tree and second identities, which NVDA reads on the sender and this version cannot.
- Queueing the focus (958): the report.

### The decisions of the agreed design

Each, carried over, changed or gone:

- Core the only judge, making no call; the listener and the outposts making every accessibility call: carries over, stricter, since the listener makes none.
- Repeats judged in Core, one mechanism, an unread fact and a read request to the reader that sent it: carries over with one reader per application, the outpost, for UIA, MSAA and foreground repeats alike. The listener's kept read and its currency stamp go; the stamp becomes the notice's bit.
- Currency of a kept read: changes. The outpost's kept read is current while its hook has delivered no foreground change since it was read and the notice's bit is clear.
- The gap in the listener, focus-missing at its one-second bound, and the outpost's read of a focus UIA did not deliver: carries over, simpler. Since every focus notice makes the outpost read its application's focus as it is, a notice of the application observed after the copy, or within 100 ms before it, answers the copy when the callback sees it; the listener waits for no read and keeps no drop classes. Whether the gap stays is still the agreed design's open item.
- The marker holding later events until the listener's read: goes. The notice is the entry itself, so nothing waits for a second message.
- The hand-over's hold: carries over unchanged.
- One time unit, every observation stamped in microseconds, and a report made for a request stamped by the event it answers: carries over.
- The window-name rule and the plain-window fallback: carry over, met by the outpost alone. A walk's bound is met by the outpost's watchdog under the generation claim. A read stuck in its remote operation is published at the bound from the acquired element's cache and plain windows from the window step 1 judged. A read stuck in acquiring has no element and nothing NVDA's checks have passed, so it is left to the handling deadline. That is a regression against the agreed design, whose listener holds the sender from the start: the Windows Terminal launch says its window at 500 ms only if the outpost acquired its terminal by then. Publishing from the notice's cache instead is possible, as a deliberate difference, and is a question for Dickson.
- A window named by `InternalGetWindowText` when its read has not answered within the bound: carries over.
- Core's foreground record and its single foreground test, with NVDA's two foreground tests in Core: carry over. The listener's acceptance test before a read goes; the outpost's in step 1 is the one test.
- Core joining chains where they meet, by node id or by window handle: carries over.
- The verdicts: change. Only the outpost judges a window's backend for a UIA focus; the listener makes no probe, sends no verdict drop, and the outpost has nothing of the listener's to read after or drop. The agreed design's deliberate difference of two raw probes per focus change in an MSAA window goes.
- A UIA menu opening read in order and judged in Core: carries over in Core; the read changes (below).
- The followed focus, refusal notices, no departure notice, change and selection targeting before the read: carry over.
- Hooks in, `HookInstalled` and `HookRemoved`: carry over; `HookRemoved` no longer ends a reading thread, since there is none.
- The millisecond field leaving the wire, and the deliberate differences on a dialog's text, the virtual desktop's rename and Excel: carry over.
- The stale rule's same-top-level exception: still open, as in the agreed design.
- Room for M5 (`docs/design/extensions.md`): carries over. Rules declared from the cache are judged by the listener before a notice is sent, so a vetoed focus costs no message; module code runs in the outpost after the read, as NVDA runs `event_gainFocus` after `doPreGainFocus` (`nvda/source/eventHandler.py` 349 to 357, 378 to 387). The Windows Terminal twin rule may not be needed (the history above).

### Menu openings, selections and notifications

Their senders are not the focus, so `GetFocusedElement` does not find them, and today the listener reads each from its sender.

- A menu opening, which NVDA handles as a focus on the menu (`nvda/source/UIAHandler/__init__.py`, 261): a menu that is a window is acquired by its handle. A windowless menu is looked for among the ancestors of the focused element, in the same remote operation as its read; found, the menu is reported as the focus with the chain above it; not found, the notice is dropped, and the menu is spoken as an entered container of the first focus inside it. Core judges the pending focus and the redirect as decided.
- A selection: judged against the followed focus as today's targeting does, the selected item found among its children by runtime id (one `FindFirstBuildCache`, `find_child_by_runtime_id`, as `selection_as_value` already does) or through the controller relation. A selection outside the followed focus is dropped before any call.
- A notification: its text comes with the event; its acceptance is judged on its sender's own window, or else on the focus window when the application serves it, or else on the desktop's handle, which is what NVDA substitutes when it finds no nearest window (`nvda/source/UIAHandler/__init__.py`, 1113 to 1120). A difference only when NVDA's walk would have found another window.

### The first focus of an application with no outpost

The notice starts the outpost as the marker does, normally by giving it a spare (`docs/design/focus-pipeline.md`, section 19); the supervisor holds the notice until `Ready`, under 12 ms with a spare, and the outpost then reads the application's focus as it is then. Nothing is lost: a focus that has moved meanwhile is read where it went. What is lost is the overlap: today the listener's read runs while the spare is assigned. The first window of an application also has its first raw probe on the outpost's worker rather than on a reading thread, 0.5 ms at the median and 211 ms at worst over 53 first sights (the listener design, section 8).

### Connecting to another application

The rule of `docs/design/listener-without-connections.md` (section 2) is that only an application's outpost connects to it. Acquiring keeps it as far as it can: a sender that is a window is looked up by its own handle, and a window never changes process; `GetFocusedElementBuildCache` is made only when the focus window is served by the application, which today's focus-now read already requires (`focused_control_in`, `crates/verbatim-outpost/src/outpost/read.rs`), and its answer is used only when its process is the application's. Two exposures remain. A focus moving to another application between the local check and the call connects the outpost there once: if that application is held, the worker waits up to the connection timeout, 2 seconds (E5); if another outpost's remote operation is queued there, this connection is the one that fails, and the proxy rule refuses its answer; whether such a connection can be one of the two of the collision's second form is not known. And a `GetFocusedElement` made while another process's remote operation is queued in the outpost's own application is "unsettled" (`docs/uia-bugs.md`); the proxy rule refuses a proxy answer, so the failure would be a notice with nothing spoken, not a wrong focus. Both are counted by the experiment. The alternative, a search by runtime id within the application's own focus window, avoids the first exposure but is a subtree `FindFirst` per focus, which a busy provider held for 13.2 seconds under a 1-second timeout (E-TT), and it misses elements in no tree; it is not proposed.

### Windows Terminal

- Tabs in no tree: whatever `GetFocusedElement` answers is read with its own ancestors; no search exists to find wrong ones. Which element it answers during a tab's focus is not known (the history above); `windows_terminal_tabs` decides what is said.
- The second identity: probably dropped as a repeat (the history above), which would be better than today, where the scenarios accept one repeated "terminal".
- The launch, and Windows Terminal's busy worker: its outpost's worker reads terminal output, so a focus notice can wait behind a read in progress. The intake already puts a focus first in its batch; a call under way is not overtaken. How long notices wait for the worker in the `windows_terminal_` scenarios is measured.

### The marker and ordering

The notice takes the marker's place and route, so an application's events are in the same order as today: MSAA events from the outpost's hook in raise order, UIA changes from its own subscriptions as they arrive, and each UIA focus at its notice's place. Since the outpost reads at that place, nothing behind it waits for a message from elsewhere, so the marker's wait, its release on the end of the listener's reads and the marker news go. The stale-focus race of `docs/design/focus-pipeline.md`, section 13, is unchanged, since the notice arrives when the marker does; the focus-following group moves sooner, on the read rather than after a search, which narrows the time in which a change on the new focus is missed. The old focus's state changes are still moved ahead of a focus inside it.

### Costs, against the agreed design

Per steady UIA focus, a windowless sender, from `docs/performance.md`'s figures for today's code, which the agreed design does not change on this path:

- Calls: today 5 UIA calls in the listener (the nearest window, `CompareElements`, the sender's keyboard focus, the refreshed cache, one parent step) and 2 in the outpost with 1 connection (its search for its own copy); here 2 calls and 1 connection, all the outpost's. A sender that is a window: 4 and 2 against 2. A repeat: 2 or 3 in the listener against 1. A text focus: 9 calls, 1 window message and 1 connection remotely, against about 4 and 1 connection.
- Wake-ups and processor time: the listener's reading thread goes. In Notepad's menu bar it was woken 4,487 to 4,754 times in 7 seconds at about 150 focuses, about 30 a focus, with 345 to 379 ms of processor time, about 2.4 ms a focus (decision 12 of the listener design). The outpost's worker makes two calls where today it makes two for its search, so its wake-ups are about the same. The listener's callback and writer do what they do for a marker today. Measured before it is trusted.
- Messages: a notice relayed through the app and a report, where today a marker and a read are relayed and the report follows: two pipe hops fewer per focus. The idle barrier no longer waits on markers.
- Latency, steady state: today the read runs on the listener's thread while the marker is relayed; here the read starts after the relay, 0.05 to 0.15 ms at the median, and after the worker is free. `GetFocusedElement` took 1.5 ms alone in mockapp, 2 to 4 ms in File Explorer and up to 10 ms in the Start menu (the 2026-10-05 investigation), against the listener's read's 1.4 ms at the median in File Explorer (listener design, section 8); expected about equal while the worker is idle, worse when it is busy.
- Latency, new windows: the connection of risk 11 before every first report in a window File Explorer is still building, up to about 2.5 seconds in some new windows, against no connection today. This is the cost most likely to decide against this version.
- Latency, first focus of an application: plus the spare's assignment, under 12 ms, which today overlaps the read.
- Memory: the listener's reading threads, each with a UIA client and a thread stack, their kept elements and abandoned threads, go. The outpost holds one kept element, as today.

### Removed and added

Removed, against the agreed design: the listener's reading threads, `FocusReader`'s judgement and read, its watchdog, `READ_BUDGET`, `READ_DEADLINE`, `MOVED_ON_GRACE` and `ABANDONED_LIMIT` in the listener, `WatchedRead`, the listener's out-of-time paths, its raw probe, verdict cache and console check from a held sender, its kept read and currency stamp, its chain reuse, its selection and notification checks, its menu-opening read; the read, drop and drop-evidence messages; the marker's wait and news; the unknown verdict's listener drop and the outpost's read after it and its drop of a listener report in an MSAA window; the outpost's search for its own copy (`crates/verbatim-outpost/src/outpost/focus_path.rs`, `element_by_path`), the splicing of a chain another process read, and the window-wide follow of an element not found.

Added: the notice and its bit; the outpost's handling of a focus notice (checks, repeat test, acquiring, matching, the read), which is today's focus-now read with a runtime id to match; the mismatch rule with the dropping of older notices it overtook; the windowless menu found among the focus's ancestors; the selection and notification judgements in the outpost.

### NVDA fidelity

Differences from NVDA that the agreed design does not have:

- A focus that has moved on when the outpost reaches it is not spoken; NVDA judges it on its callback thread, a few milliseconds after the event, speaks it and culls it. The outpost speaks where the focus is instead, as if the later focus event had come.
- A sender's keyboard focus is judged by the focused element's runtime id, not read on the sender; elements in no tree and second identities differ from NVDA either way (above).
- A windowless sender is judged first on the focus window rather than its nearest window.
- A windowless notification is judged on the focus window where NVDA reads its nearest window.
- A windowless menu not yet holding the focus is not spoken as a focus, only as the container of the first focus inside it.
- A stand-in answer or a timed-out acquisition speaks nothing for that event, where NVDA reads the sender.

Shared with the agreed design: everything else, including decision 11's recovery and the deliberate differences already decided.

## The experiment that would decide

Measurement only, in a scratch build of today's code, so both designs are seen on the same events. The shadow read: when the outpost's worker takes up a UIA focus marker, it first does what this version's outpost would do with the notice (steps 1 to 5, with the notice's runtime id and cached window taken from the listener's marker), logs its outcome, timing and calls, and reports nothing from it; then it handles the listener's read as today. Each shadow read is logged with the listener's verdict on the same event, whether the listener found the sender focused, and how long the marker waited for the worker. The shadow read delays the real path by its own time, which the logs show and the comparison discounts. Before the NVDA captures this needs, the NVDA pin is checked against the installed build.

What it counts, and the runs:

- Outcomes per focus event: match, mismatch with the listener's read accepted (a focus this version would not speak), mismatch with the listener's read dropped, answer from another process, proxy refused, acquisition timed out, and focus window differing from the read's nearest window. Scenarios: every `windows_terminal_` and `conhost_` scenario once and `windows_terminal_tabs` and `windows_terminal_close_tab` twenty times each, `explorer_folder_window` and `conhost_two_windows` twenty times each, `settings_system_page`, `rapid_tabbing_in_settings`, `menu_and_settings_dialog`, `second_application_and_verbatim_menu`, `notepad_and_verbatim_menu`, every `notepad_` scenario ten times, and `measure_focus_explorer` and `measure_repeat_explorer` five times each.
- Windows Terminal's identities: `measure_terminal_identities` for 150 rounds with the identity judge (`experiments/windows-terminal-raises-focus-from-a-second-runtime-identity/`), logging what the shadow read finds for each second-identity event, and what it finds for each tab focus in `windows_terminal_tabs`, with its parent chain.
- New windows: in `measure_focus_explorer`, the shadow read's acquisition time for each new folder window's first focus, against the listener's read and against risk 11's 2,003 to 2,516 ms.
- Latency: event to shadow report against event to the listener's read reaching the outpost, P50, P95 and worst, in the three latency runs of the listener design (File Explorer's list of 120 files, Settings' System list, Notepad's menu bar) and for a new application's first focus.
- Wake-ups and processor time: WPR traces (`cargo xtask trace`) of Notepad's menu bar, six of each, the listener's reading thread against the outpost worker's shadow reads.
- Calls and provider hits: `crates/mockapp/tests/call_counts.rs` with a scratch case running the shadow read on mockapp's cold, steady, list and list-item focuses.
- Isolation, in mockapp: two mockapps, the focus moved between them every 50 ms while the second is held (`hold`) or stalled (`stall` at 3 and 10 seconds), counting shadow reads answered by the other process and how long each waited; and a mockapp under `slow` with another process's remote operation queued, counting `GetFocusedElement` answers refused by the proxy rule.
- Stand-ins: fifty Notepad launches, logging the shadow read's answer for the text area's first focus by handle and by `GetFocusedElement`.
- Menus: the share of menu-opening senders that are windows, and for the rest whether the focus was inside the menu when the shadow read ran, in Notepad's menu bar, File Explorer's context menu, Windows Terminal's menu and Verbatim's menu.

What would decide: this version is worth building if the focuses it would not speak are rare and limited to ones NVDA culls, if no shadow read is answered by another process in ordinary use, if new windows' acquisitions do not wait as risk 11's connections did, and if steady latency is unchanged; Dickson sets the limits. Otherwise the agreed design stands.

## Questions for Dickson

- On a mismatch, report the focus where it is now (recommended, since it removes the moved-on patches and keeps the gap in the listener simple) or drop the notice as NVDA drops a sender without the keyboard focus, which needs the gap to learn the outpost's outcome again.
- A read stuck in acquiring at the bound: left to the handling deadline (recommended until measured), or published from the notice's cache with plain windows, a deliberate difference.
- Whether this version is worth the experiment at all, given the risk 11 connection, which is measured already.

## Comparison with the agreed design

This version makes the listener a router with no calls, removes its reading threads, budgets, verdicts and every mechanism the listener's read needs (about a dozen of the agreed design's), and reads each focus with about two calls instead of seven, in the process that holds the application's other events and keeps the element it reads. It brings back what the agreed design was chosen to avoid: a focus judged when the outpost's worker reaches it rather than when the event arrives, so moved-on focuses are lost where NVDA speaks them; a connection for every focus, which is measured to hold the worker for seconds in new File Explorer windows; a `GetFocusedElement` that can still land in another application; and senders the outpost can only guess at, Windows Terminal's tabs and windowless menus among them. It cannot do better than the agreed design on any measured case of the history except the second identity, gone senders, the listener's cost and the two verdicts, and it does worse on new windows by a measured figure. It can work; whether it should is what the experiment decides.
