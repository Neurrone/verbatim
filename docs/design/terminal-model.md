# How Verbatim reads terminals

Status: accepted by Dickson on 2026-10-25, under five principles he agreed on 2026-10-24: one model of rows and one alignment; one read rule; a real reason for every rule; one flood policy, Core's; and an oracle that only judges. On 2026-10-25 he decided that the reading may relax its requirements where that noticeably simplifies it: the memory holds only what the last read showed, with no inferred history and no inferred rotation; floods still respect the configured groups, but the count in "skipped N lines" need not be exact; once the history is full, a flood faster than a single read may say "skipped about N lines" and then its newest lines, its first lines lost; and the review cursor moves reliably up through the whole buffer, exactly while the program is not writing, and by its line's text near its place while output arrives with a full history. Every other decision is stated once, with its date, where it applies.

## The model

The screen is rows. Every operation a program can perform leaves each old row kept, rewritten or gone, and each new row an old row or new. So an alignment of old rows to new rows describes any change completely, and the alignment that keeps the most rows, moved in the fewest blocks, is the explanation that assumes the program did the least. That one alignment decides what is new, where each old row went, where the review cursor goes, and what a key did. Where two explanations fit every read, the rules take the one the alignment prefers; the cases where that can be wrong are under "Limits". A mistake lasts for one read, since the next read is aligned against what this read showed and nothing older is kept.

### The memory

For each terminal, kept in Core while the terminal exists, across focus changes:

- The last read's rows, its history block and its screen: each row's text without padding, a 64-bit hash of it, whether it continues onto the next row, its colour runs when last read, whether a program has rewritten it, and its history: what it last said, when it last changed and the change before, and whether it is volatile.
- Lingering rows, with their history, for 2 seconds.
- Anchors: the review position and the command marks, each a place in the buffer, a column, and the hash of its line.
- What waits for the quiet period: unfinished words, volatile rows, rows held for keys, and a command entered whose line no read has yet shown marked.
- The aside screen, while one is held (rule 8).

Nothing older than the last read is kept but the aside screen, so the memory does not grow however long the terminal runs or however it is flooded.

### The read

A read is one remote operation returning the text from one screen above the top of the last read's screen to the document's end, lines whole and padding kept; the screen's text; the caret's row, column and line; a provider range at the top of this read's screen, placed by counting up from the document's end, which the outpost keeps as the next read's start; whether the start was refused and whether the read reached the document's start; and, in a key's window, the screen's colour runs. The screen above holds the last read's history block for rule 4, and keeps the last read's screen inside the read while a full history moves up by less than two screens. A terminal's first read knows no screen's height and takes only the screen; when the document goes on above it, it is read again at once with the screen's worth of rows above (Dickson, 2026-10-26). The whole document is read only for a lost read, at most once per group of spoken output, and never with "report new output" off.

## Where it runs

The memory, the alignment and the rules run in Core, in the reducer (Dickson, 2026-10-24). Core's state holds each terminal's rules behind an `Arc`, serialized with the state, so a flight recorder's dump replays a terminal session (Dickson, 2026-10-26). A read crosses to Core without the spaces that pad its lines, each line's padded length kept, and whole by itself, naming nothing of an earlier read (Dickson, 2026-10-25). The outpost makes the accessibility calls only: it reads what Core asks for and sends the text back. Keys reach the rules from the keyboard hook through Core, in the order they reached the program, so there is one caret and one record of keys, Core's.

The outpost keeps the provider range where the next read starts, the screen's size as Core last told it, the latest end of a key's window that takes the colours, the merging of change signals and the reading-on-demand state machine (so a flood does not wake Core per line), and the noted caret. Every read it takes crosses to Core, those that say nothing included, since only Core can judge a read; it drops only a live read identical to the last one sent in every field but its times and caret report, and never a read that waited for Core's speech queue or the first after the focus arrives (Dickson, 2026-10-26).

The memory and alignment are in `crates/verbatim-text/src/terminal_rows.rs`, the rules in `crates/verbatim-text/src/terminal_reading.rs`, both run by `crates/verbatim-core/src/terminal_model.rs`; the flood policy is in `crates/verbatim-core/src/terminal.rs`, and the outpost's reads in `crates/verbatim-outpost/src/terminal.rs`.

## The rules

Terms used in the rules:

- A row is one line of the terminal's grid. A line is the text between two line breaks; a long line wraps over several rows.
- A row's place is where it is in the terminal's buffer. Rows keep their places until the history is full; then each new line moves every row up one place. A program that erases the history and prints again (Pi's regular mode on Control+O and on a resize) gives the rows it prints new places, lower or higher.
- A read is one snapshot of the terminal's text, taken in one remote operation. The last read is the one the memory holds; its screen is the screen as that read found it, and its history block is the screen's worth of rows above that screen, which every read includes.
- The alignment pairs the last read's rows (the old rows) with the rows of a read. Each old row's outcome is kept (the same text, wherever it moved), grown (its text extended where it was), rewritten (paired with a new row like it) or gone. A new row paired with nothing is new.
- A key's window is the reads taken, as of their end, within 300 milliseconds after the key reached the program. Within it the keys own a read's changes, but for a row that changed with no key in the 2 seconds before the first of them; the program owns every other change (Dickson, 2026-10-26).
- The quiet period is defined under "Volatile rows".

Each rule is followed by its reason. "Recording" means a recording of that program in the conformance corpus; a name with a star, such as `*_typing`, is an end-to-end scenario run in both terminals.

### Reading rules

These decide what changed and what is said of it.

1. **When to read.** One read follows any number of Windows Terminal's text-changed and caret events and the console host's four console update WinEvents, with no delay; while Core's speech queue is full nothing is read until Core asks, at a group's last line, a caret event is only noted, and a held key is read before it is passed on and again after the terminal answers. Reason: Windows Terminal moves its caret with no text change, the console host lost UIA text changes in 2 of 14 large writes, and a flood once took 2,800 reads (Dickson, 2026-10-07 and 2026-10-14); key holding (`docs/design/key-holding.md`).
2. **The read.** Each read is one remote operation from one screen above the top of the last read's screen to the document's end, with the screen, the caret and its line, starting at the provider range the last read placed by counting up from the document's end, never from the view; a refused start reads from one screen above the screen instead. Reason: one `GetText` is atomic, the user can scroll the view, and Windows Terminal's clear shrinks the document, refusing the start.
3. **Rows.** A read's lines are cut into rows by the screen's width, and a row's padding, the spaces after its line's last character, is never part of it. Reason: both terminals pad every row and give a wrapped line whole (Dickson, 2026-10-06).
4. **Positions.** When the read's rows above the last read's screen read exactly as the last read's history block did in the same places, and at least one of them has text, the last read's rows are where they were and every row below the end of the last read is new; otherwise the last read's rows are found by their text. Reason: rows keep their places until the history is full, Pi's Control+O prints other text there (pi-changed-above recording), and blank rows read the same after the buffer moved (Dickson, 2026-10-25).
5. **The alignment.** The last read's rows are aligned with the read's so that the most are kept, in the fewest blocks, moving the fewest rows from their places; growth in place counts as kept, a row the subsequence leaves gone is kept at the nearest new row with its text, whether or not that text is unique (Dickson, 2026-10-25), leftover rows between kept rows (or a kept row and the read's edge) are paired as rewritten when they share half the longer row's characters in order, and everything attached to a row moves with it, except that a row rewritten alone starts its change history afresh; found by text, a row of the last read's history block is found at its place or higher, or lower by the one shift the last read's screen rows with text took when they went lower, and nowhere else (Dickson, 2026-10-25); rows above where the last read's first row went are history, silent, in every read from the kept start (Dickson, 2026-10-25); the caret's line is that line rewritten where it started, unless it only lost text while the caret moved forward over text both reads show unchanged (Dickson, 2026-10-25). Reason: a prompt paired with a copy of itself (the first build); Pi's repainted transcript and "Working..." row (recordings); Claude Code's input box, its equal borders drawn again lower (claude-code-reply recording); growth (`*_long_lines`); "Model catalogs refreshed." (pi-regular recording; Dickson, 2026-10-24); the same output printed twice against Pi's Control+O (pi-changed-above recording); Escape on a two-row line, and `cls` in Windows Terminal (`windows_terminal_typing`).
6. **A lost read.** A read that keeps and pairs nothing of the last read and is no new screen is lost, positions trusted or not; so is a read whose positions are not trusted, whose start was not refused, and that keeps no row with text that the last read had at or above the caret, or keeps them equally well at more than one place. The whole document is then read once (with "report new output" off the memory starts again instead); when the aside screen is found in it, the read is a new screen, and otherwise it is aligned the same way: the rows below the last read's rows are new and counted as "about"; when the last read's rows are nowhere, every row is new, counted as "more than", or as "about" when the start of the read that asked for the whole document was refused, the document having shrunk under a clear; when they fit at more than one place, "skipped lines" is said with no number and only the visible screen is aligned. Reason: `clear; dir` (`windows_terminal_cleared_flood`); `*_scrollback_overflow`; a footer below the caret stays while a flood passes it (`conhost_footer_overflow`); a fresh or cleared screen trusts positions while a write larger than the buffer moved every row (`conhost_fresh_flood`, `windows_terminal_clear_flood`); Dickson, 2026-10-25.
7. **Screens.** A read that keeps and pairs nothing of the last read is a new screen when its own screen starts at the document's start, or when the aside screen's rows with text are found in it at their places or higher; its visible rows are new and spoken, the rows above them are silent, and the review cursor goes to the caret. Reason: vim, less and Pi's fullscreen mode (recordings); `cls` saying the prompt (NVDA capture, `*_typing`); NVDA speaks the shell's screen when a pager closes (`nv-con-pager.txt`); no text or event tells reliably when a full-screen program opens or closes (Dickson, 2026-10-24 and 2026-10-25).
8. **The aside screen.** When a read is judged a new screen, the row hashes of the screen it replaced, its screen and history block, are kept aside, each with its distance from the document's end, replacing any earlier aside screen; a read that keeps something of the last read and whose own screen does not start at the document's start drops it. It is the one exception to the memory holding only what the last read showed: recognition only, never spoken, nothing inferred. Reason: a full-screen program closing over a long history (`*_pager_history`) must be told from a flood after a clear (`windows_terminal_clear_flood`; Dickson, 2026-10-25).
9. **Lingering.** A row gone where it was, that a program had rewritten before or that was at or below the caret, is remembered for 2 seconds, and a new row with its text, the nearest first, is that row coming back. Reason: the console host redraws a footer a row lower, and a read can land inside Ink's erase and redraw (Claude Code; Dickson, 2026-10-24).
10. **A read with no text.** A read whose screen shows no text where the last read's had text changes nothing but the caret, and the next read is aligned against the memory as it was. Reason: a read can land between a program's clear and its reprint.
11. **Starting again.** A changed width or height, and a lost read with "report new output" off, start the memory again from the read with nothing aligned; each anchor is found again by its line's text nearest its old place, keeping its character within its line. Reason: a resize rewraps every row, and with output off a whole read would come every few hundred lines of a flood (Dickson, 2026-10-07 and 2026-10-24).
12. **New text.** New rows are output, their lines spoken in order, one utterance each, whole however long, through Core's flood policy; kept rows are silent wherever they moved; a blank line is never spoken but counts, and a blank row is a line only once a row with text is below it; a line or row that only lost text, or gained only white space, says nothing. Reason: NVDA speaks only inserted text (Dickson, 2026-10-06 to 2026-10-09); a list redrawn in two writes waits for its marker (the first build).
13. **Growing lines.** A line that grew speaks what it gained beyond what was said of it, without leading spaces, holding its unfinished last word (the caret at its end, no space after it) until the line grows past it, the caret leaves the line, or the quiet period passes. Reason: NVDA captures in `*_long_lines` and `*_full_screen`; streamed replies (Dickson, 2026-10-23).
14. **Reprinted input.** The input line a shell reprints at the caret below new rows is not spoken again. Reason: readline and PSReadLine below a completion list (recordings; Dickson, 2026-10-23).
15. **The focus.** Taking the focus subscribes and then reads, that read says only "terminal" and the caret's line ("blank" when empty), output written while the focus was elsewhere is never heard, and the memory lasts until the terminal closes. Reason: NVDA's capture of PowerShell's start-up notice (Dickson, 2026-10-09); `*_leave_flood`, `*_two_windows`, `windows_terminal_tabs`.
16. **Changed rows.** A rewritten row the program owns, and did not only lose text, is silent when the one character that changed is neither a letter nor a digit (a spinner), held when volatile, and otherwise spoken from the start of the first word that changed, against what it last said. Reason: Pi's and Claude Code's spinners (progress recording); vim's ruler and tig's count (Dickson, 2026-10-07 and 2026-10-08).
17. **Volatile rows.** A rewritten row that changed twice within 2 seconds, each a change the program owns, or at two reads in a row of which the second waited for speech, is volatile: its first change is heard, and then it is silent until it has been still for the quiet period (1 second, or 1.5 times the time between its last two changes when that is longer, the reading's one timer), when it is spoken once. Reason: once-a-second timers (Pi, Claude Code), htop's meters, cargo's bar during a flood, and fzf (Dickson, 2026-10-23).
18. **Keys and their window.** Keys reach the rules through Core in the order they reached the program, each with that time, and a read is taken as of its end. Each read is compared once with the last read; a change it finds is the keys' when the read lies within 300 milliseconds after the latest key, unless it is on a row away from the caret that changed with no key in the 2 seconds before the first of them, and the program's otherwise; keys inside each other's windows share one window, and the caret before the first is where they started; a read's speech counts as after every key whose window holds it (Dickson, 2026-10-26). Reason: NVDA's caret wait in Windows Terminal is 3 times 100 milliseconds; Up Arrow and a character at once (`*_up_typing`); typing next to a prompt's clock is echoed (Dickson, 2026-10-23 and 2026-10-24).
19. **The caret's line.** When the keys own a read, the caret's line is answered from its comparison: the caret back where the keys started, on its line unchanged, says nothing; after Enter, nothing, its answer being only new output; on a new line, the line is output; on another line already there, that line is spoken, or the character or word at the caret for a character or word key; on its line, typing shown is echoed, a line key not followed by typing speaks the line, text gained is spoken, text lost next to the caret is spoken (Delete speaks what it leaves at the caret), any other change by its changed words, and with no text changed a move speaks the key's unit, or the character or word the caret landed at. A caret move the program owns is never spoken (Dickson, 2026-10-26). Reason: NVDA's capture of "> banana" (`*_marker_list`); the editing keys of bash, PSReadLine and Pi (recordings); NVDA has no new-line announcement in terminals (`docs/parity/terminals.md`, "Typing"); `cls` homes the caret before it erases (`windows_terminal_typing`); Dickson, 2026-10-08, 2026-10-09 and 2026-10-25.
20. **Typing echo.** Typed characters are echoed when the terminal shows them and never spoken again as output, while output that is not the typing is output however short; a line changed some other way drops the held typing and speaks what it shows, typing the terminal cannot show yet is echoed when the caret passes over it, held typing is forgotten on Enter, Tab, Escape, Control+C, Control+D and Control+Break, and a character not shown within 300 milliseconds of reaching the program is dropped unspoken. Reason: NVDA's "probably typed" rule drops real output (`*_short_output`); a slow connection's echo (Dickson, 2026-10-07 to 2026-10-23); `*_spoken_password`.
21. **Rows the keys own.** A row away from the caret that the keys own and that gained text (compared without spaces, its new text contains the old and adds more than at its end) or gained emphasis (of the rows whose colours changed while their text did not, the one whose colours now differ from both its neighbours') is spoken whole at once; one that only lost text is silent; any other is held while keys keep coming and spoken once, by its changed words, when no key has been pressed for the quiet period (Dickson, 2026-10-26). Reason: tig, Microsoft Edit, Pi and Claude Code's lists (recordings, `*_redrawn_list`); htop, tig and PSReadLine's MenuComplete select by colour alone; fzf's count and vim's ruler (Dickson, 2026-10-23 and 2026-10-24).
22. **Suggestions.** Text after the caret on its row, in colours other than the typing's and not typed, is a suggestion, spoken when it appears and when it becomes other than the last suggestion less what was typed. Reason: PSReadLine's prediction, fish and zsh (Dickson, 2026-10-07 and 2026-10-23).
23. **Colours.** The whole screen's colours are read with the text in every read that begins within a key's window once Core's request for that key has reached the outpost, and in one read at once when a read ended in the window without them. The suggestion, gained emphasis and untyped text after the caret wait for a read with colours in the window, and are spoken as gained text if the window ends without one. Colours are read at no other time (Dickson, 2026-10-26). Reason: a read without colours cannot tell a suggestion from text gained, and colours in every read would cost 6 to 12 percent of a core while a program streams ("Costs"; Dickson, 2026-10-24).
24. **The review anchor.** The review position is a place in the buffer, the hash of its line and a column: within the last read it moves with its row's outcome and follows the caret only with "review follows caret" on when a key moved the caret within its window or the focus arrived; above the last read, a review command reads by place, in one remote operation, the rows from one screen above its place to the document's end and takes the nearest row with its line's text from a screen above its place to a screen below it; when no row has that text, it keeps its place and reads the row there now; with the read's start refused, an anchor above the read is found by its line's text within the read, or goes to the caret. Reason: the place is exact while nothing is written, a full history moves rows up, Pi's Control+O moved every row 17 lower, and a refused start means the document shrank (pi-changed-above recording; `*_review_output`; Dickson, 2026-10-23 and 2026-10-25).

### Features and settings

These are not reading rules: they decide how what the reading rules found is spoken, or offer commands.

- **Core's flood policy**, the only one; the reading rules hand it every new line. The first "Lines spoken in full" (30) lines of a burst are spoken whole, and once heard, if more than that wait, all but the newest "Last lines to speak" (30) become "skipped N lines", repeated for each group, either limit settable up to 10,000; every line counts, blank lines included, a line and its growth counting and dropping as one. A count taken from text after a lost read says "skipped about N lines"; lines that went by past a full history with nothing of the last read found make "skipped more than N lines"; and a lost read whose rows fit at more than one place says "skipped lines" with no count. A key other than Shift cuts speech and drops waiting output, output read before the cut is never spoken after it while output read after it is, and a cut takes the read owed at that moment, using its output only to echo typing and answer keys; Shift pauses and resumes. Waiting output is bounded at 10 MB, a larger single line cut on a grapheme boundary with "line cut"; Verbatim+5 turns "report new output" off and on, saying which, and off drops waiting output. Reason: NVDA has no flood control (Dickson, 2026-10-06 to 2026-10-17, and 2026-10-25 for "about"); `*_flood`, `*_shift_flood`.
- **Speak passwords.** With it on, typing is echoed as it is typed. Reason: NVDA; `*_spoken_password`.
- **Keyboard layout.** The console host's keys are translated with its own keyboard layout. Reason: NVDA.
- **Notifications.** Every UIA notification from a terminal is ignored. Reason: they carry no positions, so cannot tell output from a redraw, and NVDA's overlays block them (Dickson, 2026-10-06).
- **Text as it is.** Lines are spoken as they are, symbols included, in one language for the terminal. Reason: Dickson, 2026-10-07 and 2026-10-08, until symbol processing (M8).
- **Review line ends.** A review line ends at its last character. Reason: Dickson, 2026-10-06; `*_review_padding`.
- **Moving by command.** Enter on a line a key changed since it appeared sets a mark on that line's first row, unless it has one; when the terminal prints the input elsewhere within the quiet period, as Pi and Claude Code do, the new row starting a line with its text, nearest the caret, is marked instead. Verbatim+Alt+Up Arrow and Verbatim+Alt+Down Arrow take the fresh read, then try the marks strictly above or below the review position, nearest first, each found by its line's text: near its place within the rows Core keeps, and above them by the outpost's `FindText` search for the line's first row, outward from the mark's place, each match checked by its line's hash, at most 20 matches over at most 100 calls. A mark not found is dropped and the next tried, silently; a search that never ran abandons the move, dropping nothing; a press makes at most three searches, the marks not yet tried kept once they are spent. A search's answer names the read it counted from, and one counted from a read Core did not take ends the move, the mark kept. The review cursor goes to the mark's row at its column and speaks the row; past the oldest or newest mark, and outside a terminal, nothing is said. Within the last read a mark moves with its row; above it, it keeps its place, and is dropped once a read starting at the document's start shows its place above that start; after a new screen it is set aside with that screen and comes back with it, so marks set in the shell survive a full-screen program; after the memory starts again it is found by its line's text or keeps its place. At most 1,000 marks are kept, the oldest dropped first. There is no exit status, so no success or failure sound. Reason: Dickson, 2026-10-23 and 2026-10-26; Windows Terminal's `autoMarkPrompts` uses the same signal.
- **Report status bar.** Verbatim+End in the desktop layout and Verbatim+Shift+End in the laptop layout read the footer once the command's fresh read is aligned: the lines below the caret's line; otherwise the run of rows at the screen's bottom that a program has rewritten, trailing blank rows skipped; otherwise the last line with text. Wrapped rows are joined, blank lines left out, and the footer is one utterance of one segment per line. A second press spells it, its lines joined by a space, and a third copies it to the clipboard; the review cursor does not move; a screen with no text says "no status bar information", and outside a terminal Core says "No status line found" until M5's general status bar. It is the way to hear a row that never stops changing. Reason: NVDA's gestures; vim's and less's footers (Dickson, 2026-10-23 and 2026-10-26).

## The rules in detail

Decisions and mechanisms the rules leave implicit.

- **Positions.** A read whose start is the document's start compares the rows it has; with none above the last read's screen, positions are trusted while the document did not shrink, since with no history nothing moved (Dickson, 2026-10-26).
- **The alignment.** It is a longest common subsequence of row hashes, ties broken by fewest blocks and then fewest rows moved, so a screen cleared into the history over repeated text pairs each copy with the copy in the same place (Dickson, 2026-10-24). The history block's one admitted lower shift is the commonest in a vote over the screen rows' hashes. The caret's line is identified by its first row. Rows that leave by scrolling never linger, so a pager scrolled back speaks the line it brings back.
- **The aside screen.** It is found when a row with text of it is no nearer the document's end than it was, since rows only move up and the document's end only down; a lost read's whole document is searched for it too.
- **Starting again.** After a resize only the caret's line is spoken, if it changed. The review position not found goes to the caret; a mark not found keeps its place (Dickson, 2026-10-26).
- **New output.** A line counted in a flood's summary counts as said. A volatile row stops being volatile once spoken after settling, and a change already in Core's queue is not replaced by the row's next change (Dickson, 2026-10-24).

### Keys

Keys carry the time each reached the program on the clock every process shares (`crates/verbatim-process/src/clock.rs`), and reads carry when they began and ended. Before a read is given to the rules, Core gives them every key that reached the program at or before the read's end, since the terminal may answer at any moment of the read (Dickson, 2026-10-26: ordering by the start silenced an echo with its own key's fence); whether output was read before a key cut speech is judged by the read's start. A read request carries no key, since every key reaches Core before the program does (Dickson, 2026-10-26). The keys only tag changes: the diff speaks. Keys sharing a window answer once, so Up Arrow followed at once by "x" speaks the recalled line "echo onex" without the character's own echo (Dickson, 2026-10-09). A read whose caret is past typing its line does not show yet changes nothing, and the typing is echoed at the read that shows it (`conhost_line_key_flood`).

### Lists and colours

Core sends the outpost one small request a key, naming the key's window; the outpost keeps the latest end it was asked for and takes the colours in every read that begins by it, and when the last read ended at or after the key without colours it reads once at once with them (Dickson, 2026-10-26). The echo, a move to another line, lost text and the landing rule never wait for colours. Colours are never read before a key, so a held key reaches the program no later than otherwise. The read program checks each row's colours whole, a row of several colours in 16-cell chunks, and a chunk of several cell by cell.

### The review cursor

Within the last read, a kept row carries the review position to its new place, a rewritten row keeps it, and a gone row moves it to the nearest surviving row above, or to the caret. A review command first takes a read and then moves and speaks within that snapshot, never on a live provider range. Above the last read, its read starts two screens above the anchor's place, the second covering output that scrolls meanwhile (Dickson, 2026-10-26), and of two rows equally near takes the higher (Dickson, 2026-10-25); the answer names the read whose start it counted from, and Core places its rows only when its memory last took that read, otherwise ending the command silently.

### Every time limit

- 300 milliseconds: a key's window and a typed character's echo, NVDA's wait for the caret in Windows Terminal, judged at reads.
- 2 seconds: a row that keeps changing, a row that changed alone before the first of the keys, and a lingering row, taking in a once-a-second timer and htop's 1.5-second refresh, judged at reads.
- The quiet period, the reading's one timer, armed only while something waits for it.
- Key holding's limits are its own (`docs/design/key-holding.md`).

## Evidence

The facts the rules rest on, measured in both terminals (`docs/performance.md`) or read from NVDA's pinned source.

### The terminals

- One `GetText` is atomic with respect to the terminal's writes but not the program's, so a line written in two calls can be read half written; the terminal's writer waits while a read copies.
- Rows keep their places until the history is full; then each new line moves the whole buffer up under fixed places. Both terminals keep 9,001 rows by default.
- Both pad every row to the width and give a wrapped line whole; Windows Terminal's range for the buffer's last row ends one cell short.
- The document's range ends where the document ended when the range was taken, so a read whose text is taken after output moved the end lower stops at the old end; during a scroll region's flood this cut 186 of 200 console host reads and 130 of 200 Windows Terminal reads, and none with no output arriving (`experiments/a-terminal-read-ends-at-the-document-end-it-started-with`).
- The alternate screen is one screen tall, with no history; a range kept at its top is accepted on the main screen after it closes.
- The console host's `cls` pushes the screen into the history; Windows Terminal's clear erases the screen and the history, refusing a kept start. Windows PowerShell 5.1's `cls` in Windows Terminal homes the caret in one write and erases in the next.
- Reverse video covers only the cells written in it, so telling a selected row needs each row's colour runs, and Windows Terminal does not implement `FindAttribute`.
- Windows Terminal raises no text-changed event for writes made only of blank lines.
- The console host's four console WinEvents are its change signals; its scroll update counts rows moved in its window, not rotations, so the reading does not use it (Dickson, 2026-10-25).

### NVDA

NVDA reads the whole document on every change, diffs it by character, speaks only inserted text, and has no flood limit. Its "probably typed" rules drop real short output, and its caret wait is 100 milliseconds, times 3 in Windows Terminal. It has nothing for full-screen programs, footers, lists or moving by command.

### The programs

- Shells reprint the input below completion lists; PSReadLine rewrites the input line on every key, and its prediction and fish's and zsh's suggestions write grey text after the caret.
- Ink programs (Claude Code) erase and rewrite a region up to 30 times a second.
- Pi 1.4.0's regular mode rewrites its bottom rows a row lower for each streamed line, and clears the history and reprints everything on a resize or Control+O; its cursor is hidden and parked in its editor.
- Full-screen programs (vim, less, htop, fzf) put the caret anywhere and keep status lines at the top or bottom.
- Progress is a line rewritten after a carriage return, rows rewritten above the caret (docker pull, npm), or a bar below a build's output (cargo).

## Limits

Cases no reader can resolve from the text, and cases decided as not handled:

- With a full history, a read over repeated rows may miss or repeat one line, because the last read's rows found by text can fit where repeated text sits (Dickson, 2026-10-25).
- After a lost read, "skipped about N lines" can be a little off over repeated text, and a flood of identical lines says "skipped lines" and not its newest copies, which look like the screen before (Dickson, 2026-10-25).
- With a full history, a history block whose rows with text all repeat at the distance the buffer moved reads as unmoved.
- A page of a full-screen program that keeps no row of the page before it replaces the shell's screen as the aside screen, so the program's close is a lost read; less, vim, htop and man keep a status row (Dickson, 2026-10-25).
- A full-screen program already open when Verbatim first reads the terminal has no shell's screen aside, so its close is a lost read; otherwise a fresh shell's flood would be silenced (Dickson, 2026-10-25).
- A write that repeats a row of the aside screen no nearer the document's end is taken for the aside screen back.
- A program that erases the history and prints it again is heard only within the last read's reach, as Pi's Control+O is heard as "Tool output: expanded" without the 20 lines it adds above, since a whole read would speak sixty reprinted lines on every toggle; output repeating the last read's text lower after the first copy left the buffer reads the same (Dickson, 2026-10-25).
- "Skipped about N lines" after a clear counts the document's rows, so output that also overflowed the buffer is undercounted (Dickson, 2026-10-25).
- A review position whose line output carried more than a screen further up reads the newer line at its place (Dickson, 2026-10-25).
- A count the keys only shrink, such as fzf's, is silent, as the rule that keeps a list's old selected row silent requires (Dickson, 2026-10-24).
- A blank row a line feed wrote and one the cursor jumped over look the same.
- Output written and erased between two reads, or written in the same read as a resize, is not heard.
- A line read half written, and a line a program wraps itself (Pi), are spoken in pieces.
- Lines scrolled out of a scroll region between reads are seen only if the terminal kept them in its history.
- A program that clears and reprints the same screen is silent, as is text erased and written back within 2 seconds, since it was heard before (Dickson, 2026-10-24).
- What an overflow pushes out while held unspoken, an unfinished word or a volatile row's latest value, is not heard (Dickson, 2026-10-24).
- `cls` on a prompt on the screen's first row, with no read between Windows Terminal's two writes, reads exactly as Control+W, so the prompt is not said (Dickson, 2026-10-25).
- Windows Terminal's clear is not a new screen when the last read had a row with exactly the text the clear leaves, such as a bare prompt.
- A screen a program really left blank is not noticed until text appears, since rule 10 takes it for a reprint in progress.
- Rows a program reprints that no read showed, such as Pi's earlier conversation, are spoken as new.
- A character typed just after a recalled line is spoken as output when a read lands between them, since no text tells recalled text from typed (Dickson, 2026-10-26).
- Colours that change with no key and no text change are not heard (Dickson, 2026-10-23).
- A hidden cursor parked away from the user's attention gives the caret nothing useful to say.
- Panes side by side share rows, so a change is not attributed to its pane (Dickson, 2026-10-23).
- A row below a scroll region that a read during output leaves out is taken as gone, and is spoken whole when it next changes, such as "status: done" rather than "done", because the read's text ends where the document ended when its range was taken (Dickson, 2026-10-26).

## Costs

Each figure is detailed in `docs/performance.md` under the section named:

- Latency: a typing echo is queued for speech at a median of 4.1 milliseconds after the key in the console host and 21.4 in Windows Terminal, one frame ("A terminal's reads, live").
- An ordinary read: 0.45 to 1.06 milliseconds of snapshot in the console host ("A terminal's rotation"), 1.6 to 3.3 KB crossing to Core, and 101 to 116 microseconds of the reducer at the median ("A terminal's reads, live").
- A whole read, the worst case, after a lost read or a full-screen program's exit over a full history: 1.1 million UTF-16 units, 25 to 31 milliseconds of `GetText` in the console host and 11 to 12 in Windows Terminal while the terminal's writer waits, accepted by Dickson on 2026-10-24 and kept for a program's exit on 2026-10-25, since a lower start would miscount a fresh screen's output ("A full-screen program's exit"), 72 to 160 KB crossing to Core, and 1.1 to 1.9 milliseconds of the reducer at the median, within its 2-millisecond budget, optimized to stay on the reducer (Dickson, 2026-10-26; "A terminal's reads in Core").
- Memory: 20 to 27 KB per terminal however long it ran, rising by up to 5.6 MB while a whole read is aligned ("The terminal memory's cost, estimated").
- Wake-ups: 2.5 to 2.6 percent more for all of Verbatim's processes over a flood, every read crossing to Core (Dickson, 2026-10-26), none more for a once-a-second clock, and beyond them only the quiet-period timer ("A terminal's reads, live").
- Colours: 0.90 to 2.09 coloured reads a key, each 1 to 3 milliseconds more on an ordinary screen, 8 on Pi's and 72 in the worst case; read in every read, they would cost an estimated 6 to 12 percent of a core while Pi or Claude Code streams, 2 to 4 milliseconds a read at up to 30 reads a second (the per-key figures are in "A terminal's colours" in `docs/performance.md`).

## Testing

- The simulated terminal (`verbatim-term-sim`, in tests only) is an emulator whose rows carry a hidden identity, with adapters that answer as the two terminals' providers do; `cargo xtask regenerate-terminal-conformance-expectations` records what the real terminals answer to the corpus's streams, and a unit test replays them in the simulator.
- The oracle judges and never drives a rule. Over the corpus, random streams and every stream of up to four operations on a tiny terminal, it checks that every line no earlier read showed is reported or withheld with a reason the reader states (Dickson, 2026-10-23); that a reason holds under some explanation consistent with the reads; that every spoken line is printed text or a summary; and that the alignment and review position follow every row whose text is unique.
- A failure the oracle finds is accepted when two explanations fit, or through a listed limit's own reason, whose precondition it checks; otherwise it is a defect fixed in the code (Dickson, 2026-10-24). A new rule needs the failure in a real program, recording or scenario, never only in a random stream. The random streams, on a 12 by 5 terminal with 6 rows of history, accept three limits: repeated text with a full history (Dickson, 2026-10-26), a lost read, and a rewritten history (Dickson, 2026-10-25); of the corpus only `pi-changed-above` needs a limit, the last.
- What is said is decided speech, tested by unit tests and scenarios with exact expectations (`docs/testing.md`), each test file's module documentation listing the rules it covers; an expectation changes only with an NVDA capture or a decision recorded here. The recordings and scenarios still to add are in `docs/roadmap.md`, "The terminal redesign".
