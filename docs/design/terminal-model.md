# How Verbatim reads terminals

Status: accepted by Dickson on 2026-10-24, replacing the design of 2026-10-23, under five principles he agreed: one model of rows and one alignment; one read rule; a real reason for every rule; one flood policy, Core's; and an oracle that only judges. Decisions keep their dates. The code still follows the earlier design until the order of work below is done; until then, code comments that cite this document by section number refer to the earlier design, in git history.

## The rules

Terms used in the rules:

- A row is one line of the terminal's grid. A line is the text between two line breaks; a long line wraps over several rows.
- A read is one snapshot of the terminal's text, taken in one remote operation. The last read is the one the memory holds; its screen is the screen as that read found it.
- The alignment pairs the rows Verbatim remembers (the old rows) with the rows of a read. Each old row's outcome is kept (the same text, wherever it moved), grown (its text extended where it was), rewritten (paired with a new row like it) or gone. A new row paired with nothing is new.
- The rotation is how many rows a full history moved up between two reads.
- A key's window is the reads that begin within 300 milliseconds after the key reached the program.
- The quiet period is defined under "Volatile rows".

Each rule is followed by its reason: the real program, the measured terminal fact, or the NVDA capture or decision that needs it. "Recording" means a recording of that program in the conformance corpus; a name with a star, such as `*_typing`, is an end-to-end scenario run in both terminals.

### Reading rules

These decide what changed and what is said of it.

- **When to read.** The terminal is read after Windows Terminal's text-changed and caret events and the console host's four console update WinEvents, exactly one read following any number of them, with no delay. While Core's speech queue is full nothing is read until Core asks, at a group's last line, and a caret event is only noted, to be read when nothing else waits; a held key is read before it is passed on and again after the terminal answers. Reason: measured: Windows Terminal moves its caret with no text change, and the console host's UIA text changes were lost in 2 of 14 large writes (2026-10-13); one console-host flood took 2,800 reads and 3,000 caret reads before these limits (Dickson, 2026-10-07 and 2026-10-14); NVDA's monitor; key holding (`docs/design/key-holding.md`).
- **The read.** Each read is one remote operation from one screen above the top of the last read's screen to the document's end, with the screen, the caret and its line, and the document's first row; it starts at the provider range the last read kept, which that read placed by counting up from the document's end, never from the view. When it keeps no row with text that the last read had at or above the caret, or its start is refused, the whole document is read once, except with "report new output" off, when the memory starts again instead. Reason: principle 2; measured: one `GetText` is atomic, a full history rotates under fixed coordinates, the user can scroll the view, Windows Terminal's clear shrinks the document, a footer below a flood stays where it is (`conhost_footer_overflow`), and with output off whole reads would come every few hundred lines of a Windows Terminal flood at 25 to 38 milliseconds each while its writer waits (reads go on for typing echo, Dickson, 2026-10-07).
- **Rows.** A read's lines are cut into rows by the screen's width, and a row's padding, the spaces after its line's last character, is never part of it. Reason: measured: both terminals pad every row and give a wrapped line whole; Dickson, 2026-10-06.
- **The alignment.** The old rows, the remembered history above the last read and then the last read, are aligned with the read's rows so that the most are kept, in the fewest blocks, moving the fewest rows; a row whose text now starts with its old text where it was has grown and counts as kept, rows above the screen move only by the rotation (those it carries above the read count as kept), and a row whose text is once in the old rows and once in the read is kept where it went. Ties go to the rotation that brings the remembered history's row to the document's first row, then to the smallest; old and new rows left between two kept rows, or a kept row and the screen's edge, are paired as rewritten when they share half the longer row's characters in order, and the rest are gone or new. Everything attached to an old row (what it last said, its change times, anchors on it, its colours) moves with its outcome. Reason: a prompt paired with the wrong copy of itself (the first build); Pi's fullscreen transcript repainted a row higher, and Pi's regular mode clearing and reprinting (recording; Pi 1.4.0's source); growth (NVDA capture in `*_long_lines`); measured: a full history rotates under fixed coordinates and shows it in the document's first row; Claude Code's slash-command list (recording); Pi's "Working..." row redrawn a row lower and a carriage-return progress bar (recordings); vim's ruler; the history moving with the pairing (Dickson, 2026-10-24).
- **Lingering.** A row gone where it was, that a program had rewritten before or that was at or below the caret, is remembered for 2 seconds, and a new row with its text, the nearest first, is that row coming back. Reason: measured: the console host writes over a footer and draws it a row lower, and a read can land inside Ink's erase and redraw (Claude Code); rows scrolled back in are not gone where they were, so they are heard (`*_full_screen`, `*_pager`); no same-line condition (Dickson, 2026-10-24).
- **A read with no text.** A read whose screen shows no text where the last read's had text changes nothing but the caret, and the next read is aligned against the memory as it was. Reason: measured: a read can land between a program's clear and its reprint; a script that clears by printing blank lines.
- **Screens.** When even the whole document keeps no row with text that the last read had at or above the caret, the read returns to the screen set aside if it keeps rows of it, aligned against both that screen and the last read, so only rows in neither are new. Otherwise, if the document is one screen tall, it is a new screen and the last read's screen is set aside with its anchors unless one is aside already; if it is longer than one screen and no shorter than before, the history overflowed ("Starting again"); and otherwise it is a new screen and what is aside is dropped; on a new screen every row is new. Reason: vim, less and Pi's fullscreen mode (recordings); measured: the alternate screen is one screen tall and Windows Terminal's clear shrinks the document; `cls` says the prompt (NVDA capture, `*_typing`); closing a full-screen program says only what changed (Dickson, 2026-10-09; `*_full_screen`, `*_pager`); Pi's last frame printed as it leaves (recording; Dickson, 2026-10-23); `*_scrollback_overflow`, `conhost_footer_overflow`.
- **Starting again.** An overflow, a changed width or height (read with no alignment), and a read that keeps nothing with output off start the memory again from the read: after an overflow Core counts the read's lines as more than the history holds, after a resize only the caret's line is spoken if it changed, and with output off nothing is. Each anchor is then found by its line's text nearest its old place, or else the review position goes to the caret and a mark is dropped. Reason: Dickson, 2026-10-07; `*_scrollback_overflow`; measured: a resize rewraps every row; Pi's regular mode reprints on a resize.
- **New text.** New rows are output, their lines spoken in order, one utterance each, whole however long, through Core's flood policy; kept rows are silent wherever they moved; a blank line is never spoken but counts, and a blank row is a line only once a row with text is below it. A line or row that only lost text, or gained only white space, says nothing. Reason: NVDA and its diff; Dickson, 2026-10-06, 2026-10-07, 2026-10-08 and 2026-10-09; the first build's footer and marker-list scenarios; a list redrawn in two writes waits for its marker.
- **Growing lines.** A line that grew speaks what it gained beyond what was said of it, without leading spaces, holding its unfinished last word (the caret at its end, no space after it) until the line grows past it, the caret leaves the line, or the quiet period passes. Reason: NVDA captures in `*_long_lines` and `*_full_screen`; the held word, Dickson, 2026-10-23, for streamed replies.
- **Reprinted input.** The input line a shell reprints at the caret below new rows is not spoken again. Reason: readline and PSReadLine below a completion list (bash and psreadline recordings); Dickson, 2026-10-23.
- **The focus.** Taking the focus subscribes and then reads, that read says only "terminal" and the caret's line ("blank" when empty), output written while the focus was elsewhere is never heard, and the memory lasts until the terminal closes. Reason: NVDA, including its capture of PowerShell's start-up notice; Dickson, 2026-10-09; `*_leave_flood`, `*_two_windows`, `windows_terminal_tabs`.
- **Changed rows.** A rewritten row that is no key's answer, and did not only lose text is silent when the one character that changed is neither a letter nor a digit (a spinner), held when volatile, and otherwise spoken from the start of the first word that changed, against what it last said. Reason: Pi's and Claude Code's spinners (progress recording; Dickson, 2026-10-07); vim's ruler and tig's count (Dickson, 2026-10-07 and 2026-10-08).
- **Volatile rows.** A rewritten row that changed twice within 2 seconds, other than as a key's answer, or at two reads in a row of which the second waited for speech, is volatile: its first change is heard, and then it is silent until it has been still for the quiet period, when it is spoken once. The quiet period is 1 second, or 1.5 times the time between the row's last two changes when that is longer, and it is the reading's one timer. Reason: Dickson, 2026-10-23; once-a-second timers that must not seem settled between ticks (the progress recording's "Elapsed", Pi, Claude Code); htop's meters; a build's progress bar during a flood (cargo); keys pausing for a second (fzf).
- **Keys and their window.** Keys reach the rules through Core in the order they reached the program, each with that time; a key is credited with what reads in its window show, keys inside each other's windows share one window judged against the screen before the first, and a read's speech counts as after every key whose window holds it. Reason: Dickson, 2026-10-23 and 2026-10-24; NVDA's caret wait in Windows Terminal, 3 times 100 milliseconds; an echo taken for growth (first build); Up Arrow and a character at once, and "echo onex" cut off by its own key (`*_up_typing`).
- **The caret's line.** After keys, when the caret ends on another line that was already there, that line is spoken whatever changed on it; when it stayed on its line, text the line gained that was not typed is spoken (typing in it included, not echoed again), text it lost next to the caret is spoken (Delete speaks what it leaves at the caret), and a move with no text change speaks the unit of a caret key Verbatim knows or the character or word the caret landed at. A caret move with no key is never spoken. Reason: NVDA, and its capture of "> banana" (`*_marker_list`); tab completion; NVDA captures "o" and "tw"; Dickson, 2026-10-08 and 2026-10-09; the editing keys of bash, PSReadLine and Pi (recordings).
- **Typing echo.** Typed characters are echoed when the terminal shows them and never spoken again as output, while output that is not the typing is output however short; a line changed some other way drops the held typing and speaks what it shows, and typing the terminal cannot show yet is echoed when the caret passes over it. Held typing is forgotten on Enter, Tab, Escape, Control+C, Control+D and Control+Break, and a character not shown within 300 milliseconds of reaching the program is dropped unspoken. Reason: NVDA, whose "probably typed" rule drops real output (`*_short_output`); Dickson, 2026-10-07, 2026-10-08, 2026-10-09 (Escape) and 2026-10-23 (a slow connection's echo); `*_typing`, `*_commands`, `*_spoken_password`.
- **A key's answer.** A row away from the caret that, within a key's window, gained text (compared without spaces, its new text contains the old and adds more than at its end) or gained emphasis (of the rows whose colours changed while their text did not, the one whose colours now differ from both its neighbours') is the key's answer, spoken whole at once, unless it changed with no key in the 2 seconds before the key. Reason: tig, Microsoft Edit, Pi's "→" and Claude Code's list (recordings), `*_redrawn_list` (Dickson, 2026-10-23); htop, tig and PSReadLine's MenuComplete show the selection by colour alone; htop's meters refresh on their own every 1.5 seconds.
- **Held for keys.** Every other row the keys changed is held while keys keep coming and spoken once, by its changed words, when no key has been pressed for the quiet period, unless it only lost text, which is silent as in "New text". Reason: fzf's count, vim's ruler and relative line numbers (Dickson, 2026-10-23); the lost-text silence keeps a list's old selected row silent when its marker moves (Dickson, 2026-10-24).
- **Suggestions.** Text after the caret on its row, in colours other than the typing's and not typed, is a suggestion, spoken when it appears and when it becomes other than the last suggestion less what was typed. Reason: PSReadLine's prediction, fish and zsh; Dickson, 2026-10-07 and 2026-10-23.
- **Colours.** The whole screen's colours are read with the text in the first read after each key, the key's echo waits for that read, and colours are read at no other time. Reason: Dickson, 2026-10-24; the measured costs under "Costs".
- **The review anchor and following.** The review position moves with its row's outcome (kept, to its new place; rewritten, it stays with its column clamped; gone, to the nearest surviving row above, or else the caret), it follows the caret only with "review follows caret" on and only when a key moved the caret within its window or the focus arrived, and a review command first takes a read and acts on the memory, reading the history rows it needs by their place in that read. Reason: Dickson, 2026-10-23; `*_review_output`; measured: a range kept in a full history reads newer text once it rotates.

### Features and settings

These are not reading rules: they decide how what the reading rules found is spoken, or offer commands.

- **Core's flood policy**, the only one; the reading rules hand it every new line. The first "Lines spoken in full" (30) lines of a burst are spoken whole, and once heard, if more than that wait, all but the newest "Last lines to speak" (30) become "skipped N lines", repeated for each group, either limit settable up to 10,000; every line counts, blank lines included, a line and its growth counting and dropping as one; lines that left a full history make "skipped more than N lines", N the history's rows less the lines about to be spoken, or "skipped lines" with no count. A key other than Shift cuts speech and drops waiting output, output read before the cut is never spoken after it while output read after it is, and a cut takes the read owed at that moment, if any, using its output only to echo typing and answer keys; Shift pauses and resumes. Waiting output is bounded at 10 MB, a larger single line cut on a grapheme boundary with "line cut"; Verbatim+5 turns "report new output" off and on, saying which, and off drops waiting output. Reason: Dickson, 2026-10-06, 2026-10-07, 2026-10-09, 2026-10-10, 2026-10-14 and 2026-10-17; NVDA; the flood, history-flood, scrollback-overflow, control-flood and shift-flood scenarios, and NVDA's captures in `*_flood` and `*_full_screen`.
- **Speak passwords.** With it on, typing is echoed as it is typed. Reason: NVDA; `*_spoken_password`.
- **Keyboard layout.** The console host's keys are translated with its own keyboard layout. Reason: NVDA.
- **Notifications.** Every UIA notification from a terminal is ignored. Reason: NVDA's overlays block them; Dickson, 2026-10-06.
- **Text as it is.** Lines are spoken as they are, symbols included, in one language for the terminal. Reason: Dickson, 2026-10-07 and 2026-10-08, until symbol processing (M8).
- **Review line ends.** A review line ends at its last character. Reason: Dickson, 2026-10-06; `*_review_padding`.
- **Moving by command.** Enter on a line a key changed sets a mark on that line once the terminal answers, and Verbatim+Alt+Up Arrow and Verbatim+Alt+Down Arrow move the review cursor to the previous and next mark. Reason: Dickson, 2026-10-23; Windows Terminal's `autoMarkPrompts` uses the same signal.
- **Report status bar.** NVDA's "report status bar" gestures read the footer: the rows below the caret, or the rows at the bottom of the screen a program has rewritten, or with neither the last row with text. Reason: Dickson, 2026-10-23.

That is 22 reading rules and 8 features, against 128 rules in the design they replace.

## Where it runs

Decided by Dickson on 2026-10-24 and not reopened here: the memory, the alignment and the rules run in Core, in the reducer, beside the rest of what Verbatim decides. The terminal's outpost makes the accessibility calls only: it reads what Core asks for and sends the text back. Keys reach the rules from the keyboard hook through Core, in the order they reached the program. So there is one caret, Core's, and one record of keys, Core's; a caret any read or caret event reports is the caret the rules judge the next key against.

What stays in the outpost: the provider range where the next read starts, the screen's last height and width, the merging of change signals and the reading-on-demand state machine (so a flood does not wake Core per line), and the noted caret.

## Evidence

The facts the rules rest on. "Measured" means the measurements of 2026-10-06 to 2026-10-24 recorded in `docs/performance.md` and the conformance runs; NVDA's files are under `nvda/source/` at the pinned commit.

### The terminals

- One `GetText` is atomic with respect to the terminal's writes, not the program's: a line the program writes in two calls, or ConPTY delivers in two chunks, can end a read half written. Calls of one remote operation run together in the terminal's process. The terminal's writer waits while a read copies.
- The document ends with the lower of the last row with text and the caret's row: rows an insertion moved down stay in it, and a row erased at the end leaves it.
- Rows keep their coordinates until the history is full; then the whole buffer rotates under fixed coordinates, so a kept range reads newer text, and the rotation shows in the document's first row.
- Both terminals pad every row to the width and give a wrapped line whole. The console host's ranges end before a row's line break; Windows Terminal's end after it, except on the buffer's last row, which ends one cell short.
- The console host keeps 9,001 rows in all, Windows Terminal 9,001 rows of history above its screen, by default.
- The alternate screen is one screen tall, with no history. A range kept on the main screen reads the alternate screen silently when its row is within the alternate screen's height, and is refused beyond it.
- The console host's `cls` pushes the screen into the history; Windows Terminal's clear erases the screen and the history, so the document shrinks.
- A scroll region from the screen's top with a footer below it scrolls into the history in both terminals. The console host was seen writing a line over the footer's row and drawing the footer again a row lower.
- Reverse video covers only the cells written in it, so a selected row reads as several colours; telling a selected row needs each row's colour runs. A stretch of cells answers its first cell's colour when every cell but its last has it, and "mixed" otherwise; Windows Terminal does not implement `FindAttribute`.
- Windows Terminal serves UI Automation on its UI thread; with software rendering, a call that arrives during a heavy frame waits for it (10 to 36 milliseconds), while a read made on the text-changed event, which comes once the frame is done, did not wait. It raises no text-changed event for writes made only of blank lines.
- The console host's four console WinEvents are its change signals: a region update for each write of a row's cells, a simple update for one cell (each typed character's echo) and for a whole-buffer clear, a scroll update for text scrolled up, and a layout event for the view moving, a resize and the alternate screen opening or closing. UIA's text changes stopped reaching Verbatim in the middle of 12,000-line writes in 2 of 14 runs, so since 2026-10-13 the WinEvents are the only signal taken there (`docs/design/wake-ups.md`, item 15).
- Windows Terminal's notifications carry printed characters with no positions, and the console host's will report only the span the cursor travelled, so neither tells new output from a redraw. The events are signals to read, not content (decided).
- Only the console host tells its buffer's size through UI Automation; the text pattern says nothing of rows past the document's end in either.

### NVDA

- It reads the whole document on every change, diffs it by character, speaks only inserted text, and has no flood limit. On 2026-10-06 the document after 5,000 lines in a 120-column Windows Terminal was 610,244 characters and took 6 milliseconds to read before any diff.
- Monitoring starts on the focus with a baseline read; output written just after the focus is spoken (captured: "terminal blank" and then PowerShell's start-up notice).
- Events are coalesced: UIA's own coalescing, NVDA's rate limiter, and a monitor flag that turns any number of events between two reads into one more read.
- It hides typed text with "probably typed" rules that also drop real short output, holds typed characters until any text change, and forgets them on Enter, Tab, Control+C, Control+D and Control+Pause.
- Its wait for the caret after a caret key is 100 milliseconds, times 3 in Windows Terminal; Backspace speaks what was before the caret only if the caret moved within the wait, and Delete speaks the unit at the caret.
- Its cancel shares the queue with its line reports, so lines queued before a key are cut off and lines from a read that ends after the key are still spoken.
- It speaks nothing for keys it has no script for, has nothing for full-screen programs, footers, lists or moving by command, and its review cursor is a live range that follows every caret event.
- Its captured weaknesses: fragments from the character diff, typed commands and recalled lines spoken twice, queued password characters spoken on another change, and no flood control.

### The programs

- Shells (readline, PSReadLine) edit the input line in place, move the caret without writing, print completion lists below the prompt and reprint the input below them, and reprint the input below output that arrives while the user types. PSReadLine without its screen-reader mode rewrites the input line on every key to recolour it. Its prediction, and fish's and zsh's suggestions, write grey text after the caret.
- Ink programs (Claude Code) write finished output above a region they erase and rewrite each frame, up to 30 a second.
- Pi 1.4.0: fullscreen mode on the alternate screen, repainting its transcript to scroll and printing its last frame on the main screen as it leaves; regular mode on the main screen, rewriting its bottom rows a row lower for each streamed line, and clearing and reprinting everything on a resize or a change above the screen. Its cursor is hidden and parked in its editor after each frame; its spinner turns every 80 milliseconds and its "Elapsed" line ticks every second; a tool's state is shown by background colour.
- Full-screen programs (vim, less, htop, fzf) put the caret anywhere, keep status lines at the top or bottom, and scroll by rewriting rows or by scroll regions; htop refreshes its meters every 1.5 seconds by default.
- Progress: one line rewritten after a carriage return, or several rows rewritten in place above the caret (docker pull, npm), or a bar on the last row below the lines a build prints (cargo).

## The model

The screen is rows. Every operation a program can perform (write, line feed, carriage return, cursor moves, erase, insert or delete rows and characters, scroll regions, switching screens, resizing, colour changes) leaves each old row kept, rewritten or gone, and each new row an old row or new. So an alignment of old rows to new rows describes any change completely, and the alignment that keeps the most rows, moved in the fewest blocks, is the explanation that assumes the program did the least. That one alignment decides what is new, where each old row went, where the review cursor goes, and what a key did. Which operations happened between two reads cannot be observed; where two explanations fit every read, the rules take the one the alignment prefers, and the cases where that can be wrong are listed under "Limits".

### The memory

For each terminal, kept in Core while the terminal exists, across focus changes:

- The last read's rows: each row's text without padding, a 64-bit hash of it, whether it continues onto the next row, its coordinate, its colour runs when last read, whether a program has rewritten it, and its history: what it last said, when it last changed and the change before, and whether it is volatile.
- Lingering rows, with their history, for 2 seconds.
- The remembered history: the hash of every row reads have shown that the buffer still holds above the last read, by coordinate, a rotation dropping the oldest. A coordinate no read has shown is unknown. It holds at most the terminal's history, about 9,000 hashes, 72 kilobytes.
- Anchors: the review position and the command marks, each a coordinate, a column, and the hash of its line.
- At most one screen set aside, with its rows, its remembered history and its anchors.
- What waits for the quiet period: unfinished words, volatile rows, rows held for keys, marks waiting for their line.

## The read

A read is one remote operation that returns:

- the text from one screen above the top of the last read's screen to the document's end, lines whole and padding kept;
- the screen's text, for its width and height;
- the document's first row;
- the caret's row and column and its line;
- a provider range at the top of this read's screen, placed by counting up from the document's end by the screen's height, which the outpost keeps as the next read's start;
- whether the start was refused, and whether the read reached the document's start;
- after a key, the screen's colour runs (see "Colours").

The read starts a screen above the top of the last read's screen for two reasons. With a full history the rows move up by the rotation between reads; reading a screen higher keeps the last read's screen inside the read for any rotation up to two screens, so the alignment finds it in the one atomic snapshot, with no second read. And it gives the alignment a screen of history rows that can only have moved by the rotation, which settles the rotation in most cases on its own.

The whole document is read only when the read keeps no row with text that the last read had at or above the caret, or when its start is refused. Rows below the caret are left out of that test because a footer drawn below a scroll region stays where it is while a flood scrolls past it; if the footer counted, a flood larger than the history would never be read whole and "skipped more than N lines" would be missed. A read that reached the document's start is already whole. So a change costs at most two reads, the second only when more than two screens went by on a full history, after a clear, or on switching screens; and since reads wait while Core's speech queue is full, at most one whole read happens per group of spoken output. With "report new output" off nothing waits, so whole reads could follow every few hundred lines of a flood; they are not taken, and a read that keeps nothing starts the memory again.

A user scrolling the view does not move the read: its start was placed from the document's end, so scrolling neither moves it nor makes each read as long as the distance scrolled.

## The rules in detail

### Rows and the width

Lines are split into rows by the width and rebuilt from rows for speech; a read's first row may continue a line from above the read, and that line keeps its start. The width is the length of the caret's row, which the read gives as one row (one cell more on the row Windows Terminal cuts short), when that length fits every line on the screen; when two lengths fit, the one that gives the screen the height it had; otherwise the narrowest line on the screen but its last, which is wrong only when every one of those lines wraps. Padding is only what follows a line's last character, so spaces at the end of a wrapped line's earlier rows, and spaces a program writes inside a line (Pi aligning its model's name to the right), are text.

### The alignment

The alignment is a longest common subsequence of row hashes. Among alignments that keep equally many rows, the one whose kept rows move in the fewest blocks wins (a block is a run of kept rows moved by the same number of rows), and then the one that moves the fewest rows. So a repeated row (a prompt, a blank, a rule line) is never paired with a copy of itself elsewhere, a program's bottom rows that stay at their coordinates while the history above them rotates are kept, and a transcript repainted a row higher is one block. A subsequence keeps rows in order, so a screen cleared into the history over repeated text pairs each copy with the copy in the same place (Dickson's decision of 2026-10-24 holds by construction). A row whose text appears once among the old rows and once in the read is kept where it went, which a subsequence alone cannot do when it moved past others. A row whose new text starts with its old text, at its place, has grown, and counts as kept.

The old rows are the remembered history followed by the last read. In an ordinary read only the last read's rows can match, since the read reaches only a screen above them; the remembered history matters when the whole document is read, as after Pi's regular mode clears and reprints everything: the reprinted rows above the last read's screen repeat the remembered history in order and are kept, and only what changed is new. Over a whole document the alignment uses a histogram diff over the hashes (each match extended while rows agree, the rarest row anchoring each part), close to the rows times their logarithm. "Screens" is decided before any of this: when no row of the last read at or above the caret is kept, rows that match older history are not kept, so output repeated after Windows Terminal's clear is new.

Rows of the history move only by the rotation, because no program writes into the history. So the rotation is the distance the read's history rows moved, and an old row that the rotation carries above the read's start is kept, not gone. When the read started at the document's start (the alternate screen, or a main screen with no history) nothing can be above it, and a row scrolled off the top is gone. When several rotations explain the rows equally well, as with a history of one repeated line, the document's first row decides: the rotation r is right only if the remembered history held the first row's text r rows below the document's start. Coordinates the remembered history does not hold rule nothing out. What is still tied takes the smallest rotation; that is a limit.

Between two kept rows, or a kept row and the screen's edge, the old and new rows left over are paired as rewritten when two rows share at least half the characters of the longer, in order; among such pairings the one that moves rows by the same amount as the kept row beside them wins. A read with no kept row pairs nothing, which is how Windows Terminal's clear leaves its prompt new rather than a shortened copy of the old prompt line. So Pi's status row "⠋ Working..." that moved down a row, as a streamed line was written above it, pairs with "⠙ Working...", and the streamed line is new.

The alignment maps every old row to its outcome, and everything attached to the row moves with it: the review position and the marks, the caret before a key, what the row last said, its change times and volatility, its colours. A row rewritten into a row elsewhere keeps its history like any other (Dickson, 2026-10-24), so a progress bar on the last row, below a build's output, stays volatile as it moves down.

### Lingering

A row a read finds gone where it was (erased or written over, not moved away by a scroll) that a program had rewritten before, or that was at or below the caret before or after the read, is kept for 2 seconds with its history. A new row with its text, the nearest first, takes it back, history and all (no same-line condition: Dickson, 2026-10-24), so a paragraph an Ink region regrows and rewraps after a read caught it erased is not spoken again. Rows that leave by scrolling never linger, so a pager scrolled back a line speaks the line it brings back (`*_full_screen`, `*_pager`). The 2 seconds are the same limit that defines a row that keeps changing; every redraw seen, Ink's at 30 frames a second and the console host's footer, completes within one frame.

### A read with no text

A read whose screen shows no text where the last read's screen had text is taken for what it most likely is, a read landing between a program's clear and its reprint: the memory stays as it was, only the caret is taken from the read, and the next read is aligned against the memory. So a reprint is silent where it repeats what was there, and a script that clears by printing blank lines does not make the next whole read speak the history again. A screen that is still blank at the next read is read the same way; the first read with text decides what happened.

### Screens

When even the whole document keeps no row with text that the last read had at or above the caret, these are tried in order:

- If the read keeps rows of the screen set aside, it returns to that screen: the read is aligned against the screen set aside and the last read together, so the rows of the main screen as it was, and a full-screen program's last frame printed on the main screen as it leaves (Pi), are kept and silent, and only what neither shows is new (closing vim says only the prompt, Dickson, 2026-10-09). A program that clears the screen and reprints exactly the earlier screen is therefore silent too (decided by Dickson, 2026-10-24).
- If the document is one screen tall, as the alternate screen always is, it is a new screen, and the last read's screen is set aside with its anchors unless a screen is aside already: so less's second page keeps the shell's screen aside, not its first page. This comes before the overflow test so that entering the alternate screen from a fresh shell, whose document may be as long as before, is never taken for an overflow.
- If the document is longer than one screen and no shorter than before, the history overflowed ("Starting again").
- Otherwise it is a new screen, and what is aside is dropped: Windows Terminal's clear leaving a prompt is one, and the next full-screen program then sets the screen after the clear aside rather than the one from before it.

On a new screen every row is new, and the review position goes to the caret, since nothing it was on survived. Command marks set while a screen is current belong to it and go aside and come back with it.

### Starting again

Three cases start the memory again from the read: an overflow, a changed width or height, and a read that keeps nothing while output reporting is off. In each, every row's history begins afresh and nothing is aligned. After an overflow, lines left a full history between two reads: Core counts the read's lines as more than the history holds ("skipped more than N lines"), the last 30 being spoken by its flood policy; what was held unspoken (an unfinished word, a volatile row's latest value) is not heard, a limit (Dickson, 2026-10-24). After a resize only the caret's line is spoken, if it changed. With output off nothing is spoken. Each anchor is then looked for by its line's hash, the nearest occurrence to its old place; the review position not found goes to the caret, and a mark not found is dropped.

### New output

New rows are output, joined into lines where they wrap, and handed in order to Core's flood policy. A line seen for the first time is spoken whole at once, so a prompt that ends without a space is heard without waiting. A line that grew speaks what it gained beyond what was said of it: what was said of a line is remembered with its rows, and a line counted in a flood's summary counts as said, so a line that lost text and later gained it back says only the new part, and spaces gained alone wait for the word after them. Once a line has grown, its last word is held while it is unfinished (the caret at its end, no space after it) and spoken when the line grows past it, when the caret leaves the line (including when the line scrolls away), or after the quiet period.

A new blank row is a line once a row with text is written below it; blank rows the caret rests after, with nothing below, are not lines yet. A line feed makes a line; a cursor move does not.

The input reprinted: when after a read the caret is on a different row whose line equals the caret's line as last read, with any characters typed since, and that line held input (a key changed it since it appeared) and new rows lie between the two, the shell has reprinted the input below a completion list or below output that arrived while the user typed, and that row is not spoken; characters typed since are echoed as usual. A fresh prompt after Enter is not this, and is spoken.

### Changed rows

A rewritten row is judged in this order: a key's answer (see "Lists and colours"); lost text or white space only, silent; held for keys; a spinner, silent; volatile, silent and held; otherwise its changed words are spoken, from the start of the first word where it differs from what it last said (Unicode word rules, whole graphemes). A row is volatile when it changed at two reads within 2 seconds, other than as a key's answer, or at two reads in a row of which the second had waited for Core's speech queue, when the time between them says nothing about how often the row changes. So the first change of a timer is heard ("Working... 1s"), the user knows the row exists, and "Working... 34s" is heard once the work ends; a clock that never stops is heard once, at its first tick. A volatile row stops being volatile once it has been spoken after settling. A change already waiting in Core's queue is not replaced by the row's next change (Dickson, 2026-10-24); a row that changes faster than the queue drains is volatile and held instead.

### Keys

Keys reach the rules through Core with the time each reached the program, taken on the clock every process of a run shares (`crates/verbatim-process/src/clock.rs`). Each read request carries the last key Core knew of when it asked, and each read its start time, so a read is judged against every key that reached the program before it began, never by when a message arrived. A read's speech counts as after the newest key whose window holds it, so the cut a later key makes does not drop it: a key deferred behind a held key does not silence the held key's answer.

A key's effects are what reads beginning within its window show; later changes are output. Keys that arrive within each other's windows share one window, and the screen before the first is what they are judged against: Up Arrow followed at once by "x" speaks the recalled line with the "x" in it once, "echo onex", without the character's own echo (Dickson, 2026-10-09).

The caret's line is identified by its first row, so a key that empties a wrapped line's second row (Escape on a two-row line) is judged on that line. After the keys, the caret's line before them is followed through the alignment, and:

- when the caret now rests on another line that was already there, that line is spoken whatever changed on it: a list whose caret follows its ">" marker says "> banana" (NVDA capture, `*_marker_list`), and Up Arrow in a pager says the line it moved to;
- when the caret rests on a new line, that line is output, spoken by "New text";
- when the caret stayed on its line and the line gained text the user did not type (a tab completion, Control+R's match, a paste, a recalled line), the gain is spoken, typing in it included;
- when it stayed and the line lost text next to the caret, what it lost is spoken, whether the program erased it in one write or over several reads; Delete instead speaks what it leaves at the caret;
- when it stayed and the line did not change but the caret moved along it, a caret key Verbatim knows speaks its unit, and any other key the landing rule: one character along, that character; at the start or end of the line or a word, the character or word there. A line a read found gone and that came back counts as changed. A caret that a program moved while it drew and parked back where the keys found it did not move.

Typed characters follow `docs/parity/terminals.md`: echoed when the terminal shows them; never spoken again as output; a line changed some other way, such as a password prompt's asterisks, drops the held typing and speaks what it shows; a clock on a password prompt's line never speaks the password; typing the terminal cannot show yet (a space at a line's end, a character typed over a suggestion that showed it already) is echoed when the caret moves over it; typing past the right margin is echoed, not spoken as a new line. A character not shown within 300 milliseconds of reaching the program is dropped unspoken, judged at the next read with no timer.

### Lists and colours

One rule for every key, with no knowledge of list markers. A row away from the caret that gained text within the key's window is the key's answer and is spoken whole at once: compared without spaces, its new text contains the old and adds more than at its end (a ">" or "→" before an entry, "[x]" for "[ ]"). A row that gained emphasis is the answer too: of the rows whose colours changed while their text did not, the one whose colours now differ from both its neighbours'. A row that changed with no key in the 2 seconds before the key, such as a meter, is not its answer. Every other row the keys changed (fzf's count, vim's ruler) is held while keys keep coming and spoken once, by its changed words, when no key has been pressed for the quiet period; a row that only lost text stays silent, as everywhere, so a list's old selected row is silent when its marker moves, and fzf's count is heard when it grows but not when it shrinks (Dickson, 2026-10-24). So when a list is filtered as the user types, the entries that survive are kept rows and silent, the row that gained the pointer is spoken after the echo, and the count once typing pauses.

On the caret's row, text after the caret in colours other than the typed text's, which the user did not type, is a suggestion: spoken when it first appears and when it becomes something other than the previous suggestion less the character typed, so typing along it does not repeat it; accepting it (Right Arrow, End) speaks the key's unit.

Colours are read for the whole screen in the first read after each key, in the same remote operation as the text, and compared with the colours kept from the last read that read them. The key's echo waits for that read. Colours are never read before a key, so a held key reaches the program no later than it would otherwise, and never at other reads, so a stream costs nothing for them. The read program checks each row whole, a row of several colours in 16-cell chunks, and a chunk of several colours cell by cell, 16 cells having measured fastest; on the buffer's last row, which Windows Terminal cuts a cell short, the row is read cell by cell.

### The review cursor

The review position is an anchor: a row and column of the memory and the hash of its line. Each read's alignment maps it: a kept row carries it to the row's new place, so it moves with its text when output scrolls, into the history when the history rotates; a rewritten row keeps it, the column clamped to the row's text, and so does a blank row written over in place; a gone row moves it to the nearest surviving row above, or to the caret when nothing survived. A redraw elsewhere (a footer, a spinner, a timer) never moves it. With "review follows caret" on, it follows the caret when a key moved the caret within the key's window, judged from the caret before the keys to the caret after, and when the focus arrives; never when a program moves its cursor while it draws.

Review commands never act on a live provider range. A review command first takes a read, so its alignment maps the anchor onto the text as it is, then moves and speaks within that snapshot. The history rows the command needs, above the memory, are read by their place, their coordinate kept current by each read's rotation, in the same remote operation as that read; this is the one use of reading rows by their place, and `verbatim_uia_rops::terminal_rows` stays for it. A review line ends at its last character.

Moving by command: when Enter is pressed on a line a key changed since it appeared (so a bare Enter sets no mark and a recalled command does), Verbatim notes the line and sets a mark on the row that holds it once the terminal has answered: the same row in a shell; in Pi's and Claude Code's regular modes, where the input is cleared and printed into the transcript, the new row whose line equals it, looked for until the quiet period passes. A mark is an anchor on its line's first row with the hash of the whole line, moved by the alignment like the review position. Commands entered before Verbatim watched the terminal have no mark; moving past the oldest says nothing more. The exit status is unknown, so there is no success or failure sound.

"Report status bar" (NVDA+End in the desktop layout, NVDA+Shift+End in the laptop layout) reads the footer as it is now, top to bottom: the rows below the caret's row, or, when there are none, the rows at the bottom of the screen a program has rewritten; with neither, the last row with text. It is the way to hear a row that never stops changing.

### Every time limit

- A key's window, and the limit on a typed character's echo: 300 milliseconds after the key reached the program, NVDA's wait for the caret in Windows Terminal. Both are judged at reads, with no timer.
- A row that keeps changing, a row that changed alone before a key, and a lingering row: 2 seconds, which takes in a once-a-second timer's ticks and htop's 1.5-second refresh. Judged at reads, with no timer.
- The quiet period: 1 second, or 1.5 times the time between the row's last two changes when that is longer, so a once-a-second timer is not judged settled between ticks. It is the reading's one timer, armed only while something waits for it, with one wake-up when it ends.
- From key holding (`docs/design/key-holding.md`), unchanged: a held caret key waits at most 150 milliseconds for the read before it; a key pressed behind a held key waits at most 100 milliseconds after that key was passed on; a held key's watch ends with its evidence, at the next key or focus change, or after 10 seconds.

## Limits

Cases no reader can resolve from the text, and cases decided as not handled:

- A count the keys change that only shrinks, such as fzf's "12/340" becoming "2/340", is silent, because a row that only lost text is silent everywhere; that same rule keeps a list's old selected row silent when its marker moves, which no rule could tell from a shrinking count without a special case (Dickson, 2026-10-24).
- Identical lines that left a full history between two reads cannot be counted, and a rotation that neither the rows nor the document's first row settles, as with a history of one repeated line or a remembered history that does not reach the document's start, is taken as the smallest. No reader can count them from text, NVDA included; the console host's scroll event cannot count them either, and Windows Terminal raises none.
- When the last read showed no history and the next finds the buffer filled and rotated, a row a flood wrote again with the same text in the same place is taken as kept, so an unfinished word or a volatile row on it is carried by the line that replaced it.
- A blank row a line feed wrote and one the cursor jumped over look the same; the blank-lines rule judges by where the cursor rests.
- Output written and erased between two reads is never seen.
- A line read half written (a word split across the first two reads of a streamed line, or a line written in two chunks) is spoken in two pieces.
- Output written in the same read as a resize is not heard.
- Lines that scrolled out of a scroll region between reads are seen only if the terminal kept them in its history.
- Programs that wrap their own text with line breaks (Pi) give separate lines, spoken in pieces.
- A program that clears the screen and reprints exactly the earlier screen is silent (Dickson, 2026-10-24); output repeated after a clear, when it leaves the document as moving or erasing rows would, is silent too, as with Windows Terminal's clear on a screen with no history followed at once by the same output.
- Text erased and written back within 2 seconds is silent, wherever it comes back on the screen, so a wrapped line's last row printed again as a line of its own in that time is silent; it is text heard before.
- What an overflow pushes out of a full history while held unspoken, an unfinished word or a volatile row's latest value, is not heard (Dickson, 2026-10-24).
- Windows Terminal's clear is not taken for a new screen when the last read had, at or above the caret, a row with exactly the text the clear leaves, such as a bare prompt from an earlier Enter on an empty line: that row is kept, and the prompt is not spoken.
- A screen that shows no text is taken for a program between its clear and its reprint, so a screen a program really left blank is not noticed until text appears on it.
- Rows a program reprints that no read ever showed, such as Pi's earlier conversation when Verbatim began watching mid-way, are spoken as new; rows above the read that a reprint of the same length leaves unchanged in length are not read, and nothing is said of them.
- Colours that change with no key and no text change are not heard (Dickson, 2026-10-23), so Pi's tool state is heard only through its text.
- A hidden cursor parked away from the user's attention gives the caret nothing useful to say.
- Panes drawn side by side by one program share rows, so a change is not attributed to its pane (Dickson, 2026-10-23).
- Windows Terminal raises no text-changed event for writes made only of blank lines, so such a scroll is seen at the next read.
- Read in the console host's source, not measured: it may raise no event for a write that leaves the cursor where it was, as when a full history rotates under a cursor on the bottom row. NVDA has the same exposure. Whether build 26100 does this is open.

## Costs

Measured on 2026-10-23 and 2026-10-24, 120 columns by 30 rows, both terminals, unless stated:

- A read of the screen's text alone, as one remote operation: 0.19 milliseconds in the console host, 0.27 in Windows Terminal. A 30-row read 0.12 milliseconds; 1,000 rows 1.3 to 3.4; a full history of 9,001 rows 9.4 to 29 (the snapshot alone 25 to 26 milliseconds in the console host through the outpost, 1.1 million UTF-16 units, 31 to 38 milliseconds for the whole read). The terminal's writer waits while a read copies.
- The new read rule costs one screen of rows more per read: about 30 rows, about 0.1 milliseconds, the cost of a 30-row read. In exchange a rotation of up to two screens is settled in the one snapshot: the second remote operation that read history rows by their place (0.19 to 0.23 milliseconds of a 1.0 to 1.3 millisecond read, and the re-reads after it) is gone, and so is the case that read the whole document on every read, a history of one repeated line or a blank first row, 31 to 51 milliseconds a read live. A whole read now happens only when more than two screens went by on a full history, after a clear, or on switching screens: at most once per group of spoken output, never with output reporting off. Leaving a full-screen program over a full history reads the main document whole once.
- Colours, in the first read after a key only, added to the time from that key to its speech: a plain shell screen 2.6 milliseconds more in the console host and 1.6 in Windows Terminal; PSReadLine's line 1.9 and 1.2; Claude Code's screen 1.0 and 0.7; Pi's screen 8.0 and 4.9; the worst case, every cell a different colour, 72 and 31 (six programs, none over 4,200 instructions). Read with separate calls instead, the runs of a colourful screen cost 56 and 118 milliseconds; read with every read, colours would cost 6 to 12 percent of a core while Pi or Claude Code streams.
- The alignment: an ordinary read compares the last read's rows with the new read's, microseconds. A whole document is aligned by the histogram diff: a clear and reprint of 9,000 rows took 4.3 to 4.8 milliseconds, and a whole-document read about 9 milliseconds of the rules' time. This now runs on Core's reducer thread, where it delays every other input for that long; it is measured there in the order of work, and moved off the reducer as an effect if it exceeds the reducer's budget.
- Memory: about 0.1 MB per terminal in its steady state (125 KB after 100,000 lines, measured with a counting allocator), however long it ran and however it was flooded. A whole-document read raises the rules' peak by about 4.5 MB while it is handled, and its text, 1.1 MB as UTF-8, now crosses the pipe from the outpost to Core once per such read.
- The quiet-period timer: one wake-up for each thing that waits for it, when it ends.
- The terminals' own cost of being watched, unchanged by any design: the console host raises about 13,600 events in a 10,000-line flood, about 40 microseconds each to a listening client; with Verbatim a console-host flood took 2.9 to 3.7 seconds against 1.6 to 1.9 with no screen reader, and a Windows Terminal flood 1.5 to 1.7 seconds against 1.4 to 1.6 (2026-10-07, debug build).

The budget for the build: on the typing path no rise but the colours of the read after each key; for output, no rise in wake-ups beyond the quiet-period timer; processor time, wake-ups and change-to-speech time measured against the baseline taken before the redesign, for typing, a 20,000-line flood, a Pi stream at its recorded pace, a clock ticking once a second, and a full-screen program refreshing rows (`measure_` scenarios, `docs/performance.md`).

## Testing

- The simulated terminal (`verbatim-term-sim`, in tests only): an emulator on a VT parser with its own grid, every row carrying a hidden identity through scrolls, rotation and clears, adapters that answer as the two terminals' providers do, and a virtual clock. It is checked against the real terminals by `cargo xtask regenerate-terminal-conformance-expectations`, run on demand on this machine or in the VM (it opens real windows), which writes each stream of the corpus into both terminals chunk by chunk and saves what they answered; a unit test replays the streams in the simulator and compares. Nothing in this design changes those expectations: they record the terminals, not the reader.
- The oracle judges and never drives a rule. It checks invariants over the simulator's ground truth for the corpus, random streams with random read points, and every stream of up to four operations on a tiny terminal:
  - Every silence is accounted for, judged by text (Dickson, 2026-10-23): every line whose text no earlier read showed, on either screen (Dickson, 2026-10-23), while the terminal had the focus and output was reported, is reported (a line, its growth, a rewritten row's change, or a flood's summary) or withheld with a reason the reader states.
  - A reason is accepted when any explanation consistent with what the reads showed makes it true (principle 5): a volatile row changed at an earlier read and changes again under some consistent pairing of rows; an unfinished word is the end of a line that grows; a row that only lost text shows a part of what an earlier read showed there; a spinner's change replaces one symbol. The oracle never consults the hidden identity of the row a program wrote to, which no read reveals.
  - A held line is reported, or its text replaced while unreported, before the reader is asked once more after the stream with time passed.
  - Every spoken line is text the stream printed, or a summary; a line is reported twice only as a fault when its text stayed on the screen between.
  - For every row whose text is unique in both reads and on the screen in both, the alignment maps it where that text went; with no key pressed, following off and no switch of screens, the review position stays on its text while it is unique on the screen; padding is never spoken.
  A failure the oracle finds is one of three things (Dickson, 2026-10-24). When two explanations fit everything the reads showed, the consistent-explanation rule above already accepts it. When it is a case listed under "Limits", the oracle accepts it only through that limit's own named reason, whose precondition it checks against the ground truth (a silence accepted as a shrinking count only when the row really is a count the keys changed that only lost text), so a limit never covers a different fault; each limit has its smallest stream as a fixed test. Otherwise it is a defect in the code, fixed in the code. A failure from random or tiny streams is never the reason for a new rule; a rule needs the same failure in a real program, recording or scenario. The recordings of real programs pass with no violation and no limit's reason; a recording that needs one is the reason to write a rule. Adding a limit is a change to this design, reviewed like any other. There are no pinned cases numbered by random case.
- What rewritten rows, keys, lists and colours say is decided speech, not a property of the stream, so it is tested by unit tests that state a stream and the exact speech, one or a few per rule, never by the oracle (`docs/testing.md`). An expectation changes only with an NVDA capture or a decision recorded here, and a commit that changes one says which.

## Order of work

Each part is one step in the sense of `REVIEW.md`: built with its tests and documents, its related scenarios run, then reviewed once in full. Nothing is pushed until the last. The current code has the memory and alignment in `crates/verbatim-text/src/terminal_rows.rs` and `terminal_rows/align.rs`, the rules in `crates/verbatim-text/src/terminal_reading.rs`, both run by the outpost (`crates/verbatim-outpost/src/terminal.rs`), and the flood policy in `crates/verbatim-core/src/terminal.rs`. The simplification is done first, in the pure crate, because it removes most of the round trips the move into Core would otherwise have to carry.

1. The oracle under principle 5: reasons accepted when any explanation consistent with the reads makes them true; the hidden-identity premises and the `RotationWithoutBlock` pins removed; the random and tiny streams expected to show no violation.
2. The read: one screen above the top of the last read's screen; the history block, the candidate rotations, the reading rules' read of rows by their place (`verbatim_uia_rops::terminal_rows` stays, for the review's history rows), the read from further above, and the outpost's loop of up to 12 snapshots removed; the whole document read only by the rule above; ties settled by the document's first row against the remembered history.
3. The alignment: prefix likeness removed, so rows pair only by half their characters, and only between kept rows or a kept row and an edge; the remembered history as old rows for a whole-document read, replacing the separate reprint step; a read with no text, new screens, setting aside, returning and overflow (one screen tall tried before overflow) replacing the switch rules (the switch by the document's shape, the switch on every row replaced, the refusal to restore while rows read since are shown, the main screen back without a restore, the erase told from a clear); growth counted as kept; a row's history moving with every pairing; lingering without the same-line condition.
4. The rules: the reader's own flood split removed, every new line handed to Core; emphasis by the one test of differing from both neighbours; a suggestion no longer required to reach the row's end; the unused withheld reasons removed; the caret's line spoken whatever changed when the caret ends on another line; held rows no longer spoken before an overflow's count. Each change run against the corpus and the oracle.
5. Core's flood policy: a line and its growth counted and dropped as one (the kept tail never starts with a bare growth).
6. The move into Core, as decided: the memory, the alignment and the rules in the reducer, the outpost reading what Core asks; keys reaching the rules through Core, with the hook's separate report to the outpost and all that carries it removed; a read's speech counted after every key whose window holds it, so a deferred key does not cut a held key's answer; one caret, so a console-host caret move with no text reaches the rules; the review position and the review's rows as one anchor in the memory, found again after a resize. The whole document's transfer and the reducer's time for a whole-document alignment measured, and moved off the reducer as an effect if over budget.
7. "Report status bar"; then moving by command, with their scenarios in both terminals, in a shell and in Pi's regular mode.
8. The recordings listed under "Testing" and their conformance expectations, after checking that the NVDA pin equals the installed build for any capture.
9. End-to-end scenarios: the existing terminal scenarios brought back to passing, then the ones listed under "Testing", then the streaming program's.
10. Measurements after, against the baseline, recorded in `docs/performance.md`.
11. Documents: this design replaces `docs/design/terminal-model.md`; `docs/parity/terminals.md`, the crates' documents and the roadmap's M4 entries follow it.
12. The whole terminal suite, `cargo xtask ci`, and the push.
