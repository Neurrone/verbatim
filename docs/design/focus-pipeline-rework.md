# The focus pipeline rework

Status: designed, reviewed and agreed by Dickson on 2026-10-29; the next step is the first step of the order of work, the measurements and captures. The scope is every reconciliation between Verbatim's processes that the study below found and every difference from NVDA in [the focus pipeline audit](focus-pipeline-audit.md) (`docs/roadmap.md`, M4, "The focus pipeline rework"). The process and thread model it starts from is `docs/architecture.md`, section 1.

## What the study found

The pipeline's shape is forced: three measured facts about UI Automation (an element cannot leave the process that received its event; a focus registration is desktop-wide; a hung window named in a focus WinEvent holds every UIA event of a process registered for focus), decision D9, and Dickson's refusal of a one-process host on 2026-10-20 require a focus listener that reads every UIA focus, one outpost per application that holds everything else, and a Core that decides. What had grown is the machinery that reconciles the two routes and the copies of "the focus" they leave: of about ninety mechanisms, about half port NVDA or answer a constraint and about half make Verbatim's processes agree, and six of those were each patched three to seven times between 2026-10-20 and 2026-10-25, each round tuning a disagreement between two copies of one fact. The rework removes those reconciliations inside the present shape. The study's inventory of the ninety mechanisms, with their commits and the patch chains, is kept in git: it last appears in full in this document at 5b1e3d5a.

## Decisions (Dickson)

The aim (2026-10-29): NVDA's focus logic wherever the multi-process model allows, with one owner for each fact and as few calls into applications as possible.

- Where calls and judgements are made (2026-10-29). Core makes no call into Windows or any application; the app thread of `verbatim.exe` reads only Windows' own state, such as the foreground window, which never waits on an application. The listener and the outposts make every accessibility call. They drop an event only on what they observe of it at that moment, with no information from Core (the window is hung, the element no longer has the keyboard focus, the window is not related to the foreground, the window is UIA), as NVDA does before its read, and use their own last read only to skip a call, still sending the fact to its owner. Core alone judges what depends on the state it holds: the focus, repeats, the foreground and staleness. The one named exception is change and selection targeting: the outpost reads a change only on its followed focus or that focus's ancestors and sends nothing for other objects, as NVDA's focus gate, since sending every change unread would add a message and a wake-up of Core per change event.
- Repeats are judged in Core (2026-10-25; amended 2026-10-29). A reader makes NVDA's duplicate test only while its kept read is current, and sends a repeat unread: the listener a UIA focus whose sender `CompareElements` equates with its kept element while that element still has the keyboard focus, read live; the outpost an MSAA focus at its kept read's event address, and a foreground change its own last report says repeats. A kept read that was an MSAA simple child is never sent unread and never taken as a repeat, as NVDA never treats its id as one (`NVDAObjects/IAccessible/__init__.py` 863 to 872). The unread fact carries only what the event carries; Core judges it and, when it is no repeat, asks the reader that sent it to read it. Kept facts are not resent, since the listener's focus registration caches no value and no states beyond the keyboard focus, as NVDA's base cache request (`UIAHandler/__init__.py` 61 to 74). This removes `CoreFocus` and everything that reconciled with it, and closes the hole where a focus returning to an element while Core's notice is in flight is never spoken.
- NVDA's two foreground tests are Core's (2026-10-29), made on the unread foreground change above; a foreground change the outpost's own report says is no repeat is read at once. A focus is judged against the foreground once, before its read, as NVDA does: Core's second test goes.
- Backend verdicts (2026-10-29). The listener and the outposts each judge a window's backend with the same code (the class lists, the raw probe, the post-probe class checks) and no verdict message between them; the listener probes before it reads, in NVDA's order; a timed-out probe is unknown. The outpost's verdict decides, for both routes, which backend's focus counts in each of its windows. The second probe this makes per focus change in an MSAA window not on the class lists, where NVDA makes one, is a deliberate difference.
- A window in the focus's ancestry is named by NVDA's rule (2026-10-29): a plain window named by `InternalGetWindowText` for the desktop, a ghost window or a hung application, otherwise the window's UIA or MSAA object chosen as NVDA chooses it; when that read has not answered within Verbatim's existing bounds (`MOVED_ON_GRACE` when the focus has moved to a new window, the read's budget otherwise), by `InternalGetWindowText`, a deliberate difference. The plain windows of a walk cut by its bound start at its outermost element's nearest window, included, and a walk cut at the depth limit of 64 is completed the same way, both deliberate differences from NVDA's fallback, which skips that window and jumps to the desktop after 100 objects. The reason for the bounds is reliability (2026-10-26): Windows Terminal raises its focus event before it has finished showing its window, and its one UI thread then blocks in `DwmExtendFrameIntoClientArea`, 0.3 to 1.5 seconds on the test VM's software compositor, so a parent step past the read's budget left only "<title> terminal"; every call into a busy application stalls alike, so the rule is not specific to Terminal.
- NVDA's meeting of chains (2026-10-29): every report carries a chain complete to the desktop, and Core joins it to the previous chain where they meet, as `api.setFocusObject` does (`api.py` 111 to 147). This replaces keeping the previous chain for ancestors unknown (2026-10-21).
- The gap (decision 11 of the listener design, 2026-10-18; amended 2026-10-21, 2026-10-25 and 2026-10-29). The outpost's own read of a focus UIA did not deliver stays. The wait for it is in the listener, whose desktop-wide hook receives every focus `WinEvent` beside the UIA focus, on one clock; a drop for no window above the sender answers it at once, a drop for no keyboard focus or for being replaced does not (2026-10-21); at its one-second bound the listener sends focus-missing, and the outpost reads, in its ordered stream, only when its own verdict for the window is UIA.
- A UIA menu opening is read in order by the listener, as the focus it is in NVDA (`UIAHandler/__init__.py` 261), and Core judges NVDA's pending focus and redirect (2026-10-29).
- The outpost's followed focus (2026-10-29): it follows its newest focus report at once; Core sends a refusal notice only when it refuses a report while holding another node of that application; no notice is sent when Core's focus leaves an application. The caret rework's baseline lives while Core holds its node (`NodesHeld`), Core's choice between a new and a repeated focus deciding what is spoken.
- The hand-over to a new outpost holds the outpost's own hook copies until forwarding's end is known, instead of matching the listener's copies by counting (2026-10-25).
- Hooks in (2026-10-29): `HookInstalled` and `HookRemoved` alone, as today, with no keying, since the supervisor's one writer sends an outpost's `HookRemoved` before any replacement's `HookInstalled`.
- The marker that holds an application's later events until the listener's read arrives stays (2026-10-25).
- One time unit (2026-10-25; amended 2026-10-29): every observation is stamped in microseconds from one clock read, in every process, so the order of focuses is a total order; the millisecond field leaves the wire.
- Extensions (2026-10-29): a veto declared as a rule is judged by the listener from the event's cache; a module's code veto or redirect runs in the outpost after the listener's read, as NVDA runs `event_gainFocus` after its walk; no general read request is kept for M5.
- Deliberate differences (2026-10-29): a UIA dialog's own text bounded by the read's budget, 2 seconds, rather than NVDA's wait (audit difference 9); the virtual desktop's rename unspoken if no process-scoped name-change hook is possible (difference 23); Excel's UIA cells, whose duplicate focuses NVDA allows (`NVDAObjects/UIA/excel.py` 114), left to M5's application modules. The synthesizer stopping everything it was handed when any of it expired is not deliberate but a bug, fixed outside this rework.
- Call cancellation is out of scope (2026-10-29; `docs/roadmap.md`, M6.1): every bound here is one Verbatim has today, and abandoned threads and `READ_DEADLINE` stay.
- The alternative in which the listener makes no call and each outpost reads its own UIA focus was rejected (2026-10-29; "Why no smaller design").

## Terms

- The listener is the one permanent `verbatim-outpost.exe --listener` process: it holds the desktop-wide UIA focus registration and desktop-wide `WinEvent` hooks, and reads each UIA focus on a thread per application.
- An outpost is the process that serves one application: its own process-scoped `WinEvent` hook, its UIA property and text registrations, one worker thread, a watchdog.
- Core is the reducer in `verbatim-core`, the only decider; the app is `verbatim.exe`'s thread that feeds it and routes its answers.
- A route is the path one of an application's events takes to its outpost: the listener's (a UIA focus, read in the listener and relayed through the app) or the outpost's own (its hook and registrations). The two-route structure is that one application's events arrive by both.
- A reader is a process that reads an event: the listener for a UIA focus, an outpost for everything else.
- The marker is the message the listener's UIA focus callback sends an outpost the moment a focus event arrives; the outpost holds every later entry behind it until the listener's read or drop takes its place.
- The gap is the wait, after a `WinEvent` focus in a UIA window, for the matching UIA focus, after which the outpost reads its application's focus itself.
- The hand-over is the protocol by which the listener stops forwarding an application's `WinEvent`s once its outpost's hook is in.
- `CoreFocus` is the notice Core sends today after every focus event it judges and every change of its focus, so the listener and the outposts judge repeats and change targets against the focus Core holds. The rework removes it.
- A verdict is a window's backend decision, UIA or MSAA, from NVDA's class lists or a probe.
- A plain window is what NVDA makes for a window when it makes no UIA or MSAA object for it (`NVDAObjects/window/__init__.py` 85 to 97 choose it for the desktop, a ghost or a hung window): role window, named by `InternalGetWindowText` (190 to 194), invisible when not visible and unavailable when disabled by its style, and focused when it is its thread's focus window (`GetGUIThreadInfo`). Read from Windows' own state, with no call into any application.
- A kept read is the last focus a reader read in full, with its chain: the listener's per application, holding the element, and the outpost's, holding the MSAA event address and whether it was a simple child. A cache that saves calls: the reader makes NVDA's duplicate test against it, while current, only to skip a read, and Core judges the unread fact.
- A kept read is current while its reader has observed no focus or foreground event in another top-level window since the event it was read for. The event being judged is not counted; in the listener, another application's UIA sender with no window of its own counts as elsewhere, and its own application's are placed by its reading thread, which finds each one's nearest window in order before the next event.
- The followed focus is the node whose text, caret and terminal output an outpost reads and on which its focus-following subscription sits.
- A read request is Core asking the reader that sent an event unread to read it.
- The bound of a walk is `MOVED_ON_GRACE` (500 ms) when the focus's top-level window is not that of the previous focus its reader observed, and the read's budget otherwise, both measured from the event's observation on the shared clock.

## The constraints that force the shape

Each is measured or decided, with its record.

- A UIA element cannot leave the process that received its event. `CoMarshalInterface` succeeds and `CoUnmarshalInterface` fails in the other process, by every route (E-marshal, focus pipeline section 11; `docs/uia-bugs.md`, "Elements cannot be passed to another process"). So whoever receives a UIA focus event must judge and read it; that is why the pre-October design, in which the outpost found the element again by runtime id, name and position, grew the moved-on rules and failed (section 1 of the focus pipeline).
- A UIA focus registration is desktop-wide. The scoped form is undocumented, refused by the direct call, and misses every proxied Win32 window (`docs/uia-bugs.md`, "Focus events cannot be limited to one application"). So one process receives every application's UIA focus events, or every outpost receives all of them at 47 to 90 provider calls each per focus change (E-cost), which Dickson ruled out.
- A hung window named in a focus `WinEvent` holds every UIA event delivered to a process that holds a focus registration, for twice the connection timeout per event (`docs/uia-bugs.md`, "A hung window named in a system focus event"). So the process holding the focus registration must hold nothing whose stall would be heard; Dickson declined one UIA host process on 2026-10-20 for this reason (D13 as amended that day).
- A thread blocked in a cross-process call cannot be cancelled; only process exit reclaims it (D9). So one outpost per application, abandonable workers and reading threads, and the kill-and-replace ladder.
- UI Automation delivers a newly started process's focus events late or never, and sometimes after their senders are gone (risks 2 and 13 of the listener design; `docs/uia-bugs.md`, "A new process's focus events reach the desktop-wide handler late"). NVDA loses those focuses by its source; Dickson decided to recover them (decision 11, 2026-10-18 and 2026-10-21), which is Verbatim's one deliberate departure from NVDA on the focus path.
- `WinEvent`s and UIA callbacks arrive with no common order; NVDA restores one by passing both through one process's threads and one queue. Verbatim has no one process, so every ordering it needs it must build.
- Windows names a console window's owner as the console's client while the console host serves it, so one application's events arrive from two processes' windows.
- Two Verbatim processes connecting to one application collide inside UIA (`docs/uia-bugs.md`, the first entry), so only an application's outpost connects to it and the listener reads with calls on held elements only.
- NVDA parity for everything spoken, from captures and the pinned source: the acceptance test, the limiter, the duplicate rule, the foreground tests, presentability, the shell's and the switcher's rules.
- Verbatim's own GUI lives in a watched process, so its hidden frame must never be announced.

From the first four, the listener must receive and read every UIA focus and each outpost must hold everything else; Core, the only process that sees every application, must decide. The two-route structure is therefore forced, given Dickson's two decisions (outposts kept, no one-process host). Nothing below proposes undoing it.

## Where state is duplicated

The study found eleven facts each held in two or three processes with no single owner; the design is organised by them. Each with how its copies disagree:

- The focus: Core's `FocusContext`, the listener's held elements marked by `CoreFocus`, the outpost's `Held` (Core's focus, the reports Core has not judged, another application's observation time) and the outpost's older `Tracking`. A focus returning to an element while Core's notice is in flight is dropped as a repeat and never spoken; an outpost follows and reads the caret of a node Core refused; a focus-now answer's entry waits in the unjudged queue until a later judged trace drains it.
- The verdicts: the listener's, one arbitrator per reading thread, and the outpost's, which copies only the listener's "yes". A probe that times out in one process and answers UIA in the other leaves a focus a second late through the gap; negative verdicts expire on two clocks.
- Which applications have hooks in: the listener's map and the supervisor's records. Until `HookRemoved` reaches the listener after an outpost dies, neither route takes the application's events.
- The gap's evidence: the outpost matched the listener's drops to its own copies by time across two processes' stamps, so a drop in another window could close a gap with nothing read.
- The foreground: Core's attention, foreground node, latest focus's top level and the keyboard hook's view; the supervisor's attention; the listener's test before a read and the outpost's tests when an event is handled and again when it is reported, so a focus the listener accepted could be refused by the second test after Alt+Tab, where NVDA's one test would have spoken it.
- The hand-over: the outpost's counts of unmatched copies against the listener's tick, never trimmed when forwarding's end does not arrive.
- The last reported focus the intake reorders by, which lags a read taken in but not handled.
- The event thread's narrowing pair against the worker's tracked window: a destroyed focus window forgotten in one but not the other.
- The states last read by the outpost against Core's, when the outbound merge replaces a waiting state change.
- Readiness, known by the owner as it reads `Ready`, by the app when the frame reaches the reducer, and by the control plane.
- The listener's per-thread last focus against Core's: the next walk stops under a focus Core refused, so a container can be reported or omitted differently from Core's own chain.

## The design

### Where calls and judgements are made

By the decision of 2026-10-29, per process:

- The listener holds the UIA focus registration and its global group, the global `WinEvent` hooks with the desktop switch added (difference 22), one reading thread per application with its kept read and its newest unread repeat, each application's gap record (below), its own backend verdicts, the applications whose outposts have their hooks in with each one's forwarding tick, and the time of the newest change of top-level window among the focus and foreground events it observed. It decides from observation only: NVDA's checks before a read (the hung window, the native check, `isNativeUIAElement` then `isUIAWindow`, by the class lists, its own verdict or the raw probe and the post-probe class checks, NVDA's duplicate test against its kept element, the acceptance test against the real foreground window, the console window's and the hidden frame's refusals, the sender's keyboard focus), the rules M5 declares from the event's cache, the watchdog's publishing and abandonment, the gap's bound, and how far its walk may run. It makes no connection. A UIA menu opening it reads in order, as the focus it is. It sends markers; reads, unread repeats and drops; reads Core asks for; focus-missing; forwarded `WinEvent`s until an outpost's hook is in; forwarding's end; selections, notifications, menu and switcher ends; the foreground window for the keyboard hook; and the desktop switch.
- An outpost holds its hook, registrations, worker and watchdog; its own backend verdicts; its followed focus as one record (node, role, window, chain, the states last read, the MSAA event address and simple-child mark, the dialog memo); the per-node last reads of the caret rework; its held nodes; its intake with the marker wait and the hand-over's hold. It decides from observation: the acceptance test, once, for every event but a UIA focus; the window's readability, ghost and hung state; each window's backend with the listener's code; and, from what it receives, a disagreement with the listener's verdict, reading a focus the listener dropped as not UIA or unknown in a window it judges UIA, and dropping a listener's report in a window it judges MSAA; NVDA's focused-state test and child redirect for an MSAA focus; M5's node and event rules and its modules' code vetoes and redirects, after the read, on every report it emits; and, as the named exception, change and selection targeting. It sends focus reports with complete chains, an MSAA repeat or a foreground change it judged a repeat unread, and everything else as today; it answers read requests in its queue's order.
- The app, `verbatim.exe`'s thread and its supervisor, holds the single input channel, the held facts for starting outposts, the spares and the outposts' records. It decides nothing about a focus: the in-ignored-window drop moves to Core. It reads only Windows' state (the foreground window to route a focus-now query), stamps each input's arrival, and runs Core's timers.
- Core holds the one focus, one foreground record (below), the newest focus's stamps, and speech validity. It judges repeats, staleness, application refusals with the ignored processes among them, NVDA's two foreground tests, a menu opening's pending focus and redirect, a fake focus's duplicate test, whether a focus is new or repeated for the caret rework, where a new chain meets the previous one, the speech cut, and presentability. It sends refusal notices, read requests to the reader that sent an unread fact, focus-now queries, text requests and `NodesHeld`.

### Who owns each duplicated fact

Each of the eleven facts of "Where state is duplicated" goes or is left as the only mechanism of its kind.

- The focus. Core's `FocusContext` is the one copy. The listener's held elements and `CoreFocus` go: each reading thread keeps only its kept read, against which it makes NVDA's duplicate test and sends a repeat unread (below), and whose chain it reuses while current. The outpost's `Held` goes with its unjudged queue, its other-application time and the trace handshake. The outpost's `Tracking`, weighed three ways: adopting nothing until Core says it took a focus, a message per focus and Core's round trip before the subscription moves and the caret is followed; adopting at the report with no word from Core, which leaves the outpost following a refused node and targeting changes for a focus Core left; and the one decided, adopting at the report, corrected by the refusal notice. Core sends a refusal notice when it does not take a focus the outpost reported while it holds another node of that application, naming the report's trace and that node; the outpost follows the named node only when the trace is its newest report. No departure notice is sent: the acceptance test drops a background application's changes before any read, and text, caret and terminal following stay on the node as today. One message per refusal, none per focus taken. The followed focus is the only record of its kind in the outpost: the intake's `focused()` copy becomes a reading of it, and the worker's `is_focus` asks it.
- The verdicts. The listener and each outpost judge a window's backend independently, with the same code: the class lists, then the raw probe, then the post-probe class checks, each process keeping its own verdicts as now (UIA for the window's life, D15, a deliberate difference from NVDA's half-second for both answers in `isUIAWindow`, `UIAHandler/__init__.py` 1368 to 1380; not UIA for 500 ms). No verdict message goes either way; `record_probe`'s copy of the listener's verdict into the outpost goes. The listener probes before it reads, in NVDA's order, and never reads a focus whose window it has not judged. A probe that runs out of time is unknown, not "not UIA". The listener keeps nothing of it and drops the focus as unknown. The outpost handles that entry through MSAA, as today's timed-out probe does, and keeps the window as "not UIA" for 500 ms from the probe's end, NVDA's cache period, which NVDA's one cache holds for a cancelled probe too (`UIAHandler/__init__.py` 1368 to 1380): within it, a listener's UIA report for that window and focus-missing for it are settled by that kept verdict, so a re-probe cannot take a UIA report beside the MSAA focus already handled; after it, the outpost probes again. The outpost settles a disagreement from what it already receives. A drop of the listener's for not UIA or unknown names its nearest window and its reason, and an outpost that judges that window UIA reads its application's focus at once, stamped with the event's observation. The outpost's verdict decides, for both routes, which backend's focus counts in each of its windows, as NVDA's one verdict does: in a window it judges UIA, the listener's UIA report counts and the outpost drops its own MSAA copy, as today; in a window it judges MSAA, it handles its MSAA focus and drops any UIA report from the listener for that window, by window handle; with its own probe unknown, MSAA counts, kept so for 500 ms as above, as NVDA takes a cancelled probe as not UIA. Nothing is paired and nothing depends on time; the listener's verdict only decides whether it spends calls reading. So a disagreement costs a read, never a lost or doubled focus. The probe has one bound in both processes, `UiaHasServerSideProvider`'s own wait once measured (difference 15). A deliberate difference: in an MSAA window not on the class lists, each focus change more than 500 ms after the last makes two raw probes, the listener's and the outpost's, where NVDA makes one. The first step's experiment on the cached provider description may later let the listener skip its probe for such a window; nothing here depends on it.
- Which applications have hooks in. As today: the listener learns that a hook is in from `HookInstalled` and that it is gone from `HookRemoved`, which ends its forwarding pause and the application's reading thread. The supervisor sends `HookRemoved` when it removes a ready outpost's record: at the failure decision, a crash included, which it learns from the outpost's pipe closing, and at the retirement decision, before the retiring process has ended (`supervisor/owner.rs`, `take_record`). Its one writer, with hand-over priority, sends it before any replacement's `HookInstalled`, so the listener hears the two in order and needs no keying. A retiring outpost's hook can still be in while the listener forwards again, until it ends, within `SHUTDOWN_LIMIT`; its output is refused by the live-incarnation gate, so nothing is handled twice, and `docs/roadmap.md`, M6.2, which ends the old outpost before its replacement starts, removes that overlap. A crash's window in which neither route takes the application's events (difference 25) is one relay hop, 0.05 to 0.15 ms at the median.
- The gap's evidence. In the listener, as decided, on one clock and with no call and no verdict; whether it stays as designed is an open item. The `WinEvent` callback keeps one record per application whose outpost has its hook in, the oldest focus copy no UIA focus has answered, in the readers' shared state beside today's backlog drop. A UIA focus event of that application observed within 100 ms before the copy or after it, whose cached window's top-level window is the copy's, answers it once its read or unread repeat is reported, not when the callback observes it (a UIA focus can reach the listener up to 25.5 ms before its `WinEvent`, 5 of 1,680 measured, `gap.rs`); a windowless sender, which the callback cannot place, answers it when its read finds its nearest window, under the same readers' lock; so do a focus or foreground `WinEvent` observed later in another window of the application or in another application; the listener giving up on the application (a timed-out nearest-window lookup included, difference 14); a verdict drop of NVDA's checks (hung, not related to the foreground, the console window's own focus, the hidden frame); and a drop for no window above the sender, or for not UIA or unknown, after which the outpost reads the application's focus at once in its place when its own verdict is UIA. A drop because the element no longer has the keyboard focus, or because a newer event of its element replaced it, leaves the record open, as decided on 2026-10-21 (`focus_read.rs` 451 to 470, 525 to 540), since in fast navigation such a drop says nothing of the copy's focus. The record's one-second bound is armed by the `WinEvent` callback when the application has no read running or waiting, as for a new process whose UIA focus never comes, and otherwise by the reading thread when the application's reads finish with the record still open, and timed by the readers' watchdog, so no reading thread waits on it and a record answered first costs no wake-up. Unanswered at the bound, the listener sends focus-missing with the window and the copy's time; the outpost reads its focus, stamped with the copy's time, when its own verdict for that window is UIA, and otherwise does nothing, having handled its MSAA copy; a read that finds the focus Core holds is dropped by Core's duplicate rule. Removed: `gap.rs`, `MarkerNews`, the wake of `next_with_gap`, `DropEvidence` and its three classes, `Held.elsewhere`, the look-back across two clocks, and any matching of the two processes' copies.
- The foreground. Core keeps one record, set at one point of `reduce_event`: the attention, the real foreground window, and the foreground object, the entry of the focus's chain whose window is the foreground window read with the focus, else the chain's top below the desktop, as NVDA takes `objectInForeground()` and falls back to the ancestors (`eventHandler.py` 402 to 411; the first item recorded but undecided). A foreground report for the window already holding the focus then changes nothing. Attention following a focus in the system's foreground window with no foreground report stays inside the record, as the only way Core learns a foreground Windows announced with no event. The keyboard hook's foreground stays Windows' own window, from the listener's report, and judges nothing. The test when an event is handled, the outpost's, or before a read, the listener's, is the one test; the test again when the outpost reports (`in_foreground` judged by `classify`, and `report_foreground`'s second look) goes (difference 12). `in_foreground` stays on the wire for attention. The windowless focus adopting the attention window goes, since every report now has window facts.
- The hand-over. The outpost holds its hook's whole stream until `ForwardingEnded` arrives, while the listener's forwarded copies are handled as they come; then it drops its copies of the forwarded kinds raised at or before the tick named and queues the rest held, in raise order. The tick is the listener's `WinEvent` clock when `HookInstalled` reached it, as now (`listener.rs` 1086 to 1088), and the listener forwards exactly the copies raised at or before it, whenever they are delivered, so each event is handled once; a listener copy delivered after the end is handled after held copies raised later, a stated limit. If the listener ends first, `UiaFocusReadsEnded` releases the hold, dropping hook copies raised at or before the newest listener copy handled; copies the dying listener held unforwarded are lost, a limit of the listener's death only. Holding the whole stream keeps a state change raised after a focus behind it. Removed: the two multisets, `TWIN_BOUND`, `ListenerBeforeHook`, `in_raised_order`, the raise-time half of the foreground change's removal of a waiting focus, `focus_raised_first`.
- The intake's reference for moving the old focus's state changes becomes the newest focus the intake has taken in, from the read in hand, which removes the stated limit. Core's `reported_focused`, which drops a state change of a focus that has reported itself no longer focused, stays as this reorder's companion and the only mechanism of its kind, and goes with the reorder if the marker's measurement removes it.
- The narrowing pair. The event thread forgets a window from the pair on the same destroy event that clears its window cache. One owner, the event thread.
- The states last read move into the followed focus's record; Core's copy is the reported one. The outbound merge's effect is checked in the order of work.
- Readiness stays: one event, `Ready`, observed at three points along one ordered route, each acting on what it has seen, and no rule compares two of them.
- The listener's per-thread last focus against Core's. The kept read is reused only while current, and Core joins chains itself.

Also kept, each the only one of its kind: the stale rule, the one order across outposts, with its same-top-level exception until its open item is decided; and the background drop at a foreground change, the one stand-in for NVDA's queue cancelling a background event queued before the change, now in microseconds.

### A window's name, and the one fallback

The decision of 2026-10-29, as built here. A window in the focus's ancestry is the object a walk reaches for it: the listener's UIA walk, the outpost's MSAA walk, or the outpost's continuation, which goes on from a window by its object chosen as NVDA chooses it, UIA when the outpost's verdict says so and MSAA otherwise, and through MSAA above the process boundary (decision 7 of the listener design). A plain window is taken instead, with no call, in two cases only: the desktop, a ghost window or a window of a hung application, by NVDA's rule; and the windows a walk has not reached by its bound.

Where a walk ends by failure rather than by time, it goes on as NVDA's does: a failed or empty MSAA `accParent`, a boundary window that cannot be acquired, and a failed UIA parent step continue from the parent window's object (`Window._get_parent`), within the bound. The listener, which may not connect to a window, ends its read there and names the window to continue from; the outpost continues from it, as it continues a chain at the process boundary today. So after a failed `accParent` in a "Save As" dialog, the dialog's own object is reached and "Save As dialog" is said (difference 2). The depth limit of 64 is a walk's end by count, completed by plain windows.

Meeting the bound when a call is stuck. A call under way cannot be ended, so the bound is met by a publisher other than the reader, and only for a read that has passed every check NVDA makes before queueing a focus and is stuck in its walk: a read still in its checks at the bound (the nearest-window lookup, the sender's keyboard focus, the outpost's focused-state test) is left to the moved-on rule and the deadline, as today, so a focus NVDA would drop is never published early. The bound is the one of the Terms, measured from the event's observation. In the listener, the reading thread shares its progress (the event's cached facts, the facts read so far, the ancestors read and the nearest window) with the watchdog under `WatchedRead`'s claim; at the bound the watchdog publishes the focus from that progress, completed by plain windows read on its own thread, and takes the claim, so the reader's late result is discarded when it returns. The thread is not abandoned for this: it reads the application's next event when its call returns, is abandoned only at `READ_DEADLINE` or by the moved-on rule as now, and so counts against `ABANDONED_LIMIT` only then. The publication is one function of the reader's shared state, so that if M6.1 finds `CoCancelCall` ends a UIA call, the watchdog cancels the stuck call and the reader itself completes with plain windows through that function, and `WatchedRead`'s claim, the late-result discard, `READ_DEADLINE`, `ABANDONED_LIMIT` and abandoned threads go together, as M6.1 lists. The outpost's worker and watchdog do the same for its walks, under the generation claim; an entry whose focus object itself has not been acquired has nothing to publish and is left to the deadline. Speech: the Windows Terminal launch says its window by its text 500 ms after its focus event was observed, whatever its parent step is doing.

Core's use. Every report's chain is complete to the desktop, so `ancestors_unknown` leaves the wire. A plain window carries its handle in the node's details, as do UIA window elements and MSAA window and client objects, and no other node does; a nearest-window handle is never put there. Core walks the new chain from the focus outward and stops at the first entry equal to one in the previous chain, by node id, or by window handle when both entries are windows (a plain window, a UIA window element, or an MSAA window or client object), so that one window reported by two outposts, such as ApplicationFrameHost's frame around Settings' content, is one entry; the result is the previous chain to that entry and the new entries below it, as `api.setFocusObject` builds the focus line. Entered containers are those below the meeting point. Speech is cut when the chains differ just below the desktop (difference 21). A focus whose walk reached only its nearest window in a new top-level window says "Windows PowerShell window" and then the focus.

Also served by the fallback: the MSAA focused-state test past a failed `accParent` continues along parent windows, a plain window being focused when it is its thread's focus window (difference 19); and the focus-now answer onto a hung window is the plain window, as NVDA's (pending its capture).

Costs: nothing on the steady path. On a fallback, about four local calls per plain window and one `GetGUIThreadInfo`, and about a hundred bytes per window in the message; a continuation after a failure makes the calls NVDA makes. Removed: Core's unknown-ancestor handling (13dcd2db, 2b13487b), the windowless-focus adoption and `ancestors_unknown` in the protocol, the outpost's focus path and the focus-now answer.

### Repeats, stamps and the hold

Repeats, one mechanism. A reader makes NVDA's duplicate test, and sends a repeat unread, only while its kept read is current, since NVDA tests against `lastQueuedFocusObject` (`UIAHandler/__init__.py` 902 to 914; `IAccessibleHandler/__init__.py` 772 to 776), which a visit elsewhere replaces; otherwise it reads in full. So a return to an application onto the element it left is read at once, as NVDA reads it. Sent unread: the listener for a UIA focus whose sender `CompareElements` equates with its kept element while that element still has the keyboard focus, read live (`UIAHandler/__init__.py` 906 to 914); the outpost for an MSAA focus at the event address of its kept read, never one that was a simple child, and for a foreground change its own last report says repeats (NVDA's two foreground tests, `IAccessibleHandler/__init__.py` 837 to 864). The unread fact carries the event's identity (the runtime id, the MSAA event address, or the foreground window and the event's address) and only what the event itself carries: for UIA the cached name and keyboard focus, for MSAA and the foreground nothing. Core takes it as a duplicate of the node it holds, updating only what the fact carries, and drops it; when it is not a repeat in Core, it sends a read request to the reader that sent it, which reads in its queue's order, after anything it has already queued: the listener its kept element, with chain reuse while current, the outpost by reacquiring from the event address or reading the foreground window. Each reader keeps, per application, only its newest unread item, the listener's being its kept element, and answers a request for an older one gone, with no time bound. Core keeps two things per focus: the reading it holds, which a duplicate updates only with what it carries, for review; and what it last spoke of the focus, which only speech updates, and against which name, value, description and state changes are compared, as NVDA compares with the properties it last spoke (`speech/speech.py` 768 to 781). A name change carried in by a repeat is then spoken when its event comes (difference 20). A focus whose report marks it a simple child is never a repeat in Core of a held focus that was one, so a reused child id is announced as NVDA announces it. A repeated text focus brings no caret read; the caret rework's repeated-focus case is said by the key's answer, which still finds the change.

Currency. In the listener it is one stamp: the time of the newest change of top-level window among the focus and foreground events either source observed, written by the callbacks with one `GetAncestor` on the event's window, from the `WinEvent` or the UIA event's cached window, never by the nearest-window lookup, with the exact rule of the Terms for senders with no window of their own. In the outpost, a kept chain is current while its hook has delivered no foreground change since it was read. This fixes stale reused ancestors (difference 3): after Alt+Tab back to Windows Terminal, whose title a program changed meanwhile, the first focus reads the whole chain and says the new title, at the cost NVDA pays, the chain's calls once per return.

The time unit, first. Before anything else that compares stamps from two processes is built, every observation is stamped in microseconds from one clock read, in the listener's two callbacks, the outposts' hook and subscription callbacks, and the focus-now answer; Core compares only microseconds, in the stale rule, the background drop at a foreground change (`foreground_changed_at`, in milliseconds today), the fake focus's guard and the menu opening's pending focus. A report made for a read request, focus-missing or a listener's drop carries the observation stamp of the event it answers, never the time of its read, so the stale rule drops a late report of a window the user has left (the outpost's gap read today stamps its read, `worker.rs` 1399). The millisecond field leaves the wire; a log or the latency timeline derives milliseconds where it prints them. A `WinEvent`'s own tick stays only as the hand-over's identity of an event.

The hand-over's hold, as above; its cost is the relay's latency once per outpost start, on the hook's copies only.

The idle barrier. A read request counts as in progress in Core until its report or its gone answer has been reduced, and a refusal notice until written, so the harness's idle round, and a key's evidence under `docs/testing.md`, wait for what Core began after a reader answered idle.

### Edge cases, limitations and what must be measured

- Verdicts. A window that answers one process's probe and times out the other's, or gains a provider between them, is judged differently; the outpost reads after the listener's drop, or drops the listener's report in a window it judges MSAA, so the focus is spoken once, late by a read at worst. Measured: probes per focus in `call_counts` against mockapp, and `conhost_two_windows`, `windows_terminal_two_windows` and `explorer_folder_window` ten times each with no focus lost or doubled.
- Hooks in. An outpost stuck without exiting is covered by `HookRemoved` at the failure decision; its stuck worker's output is refused by the live-incarnation gate. Events raised in the relay hop after a crash, and those raised before it and not handled, are lost, as now. Checked by `outpost_crash_recovery` with a context menu opened during the replacement.
- The fallback. A popup owned by another window is placed under the desktop by plain windows, as NVDA's fallback places it, where UIA's raw view may put it under its owner. A thread whose call returns after the watchdog published goes on to the application's next event, so a second slow window can still reach the abandoned limit only through the deadline, as now. Measured: a mockapp provider stalling only its parent navigation for 15 seconds, with the focus arriving from another application and from within, giving "title window" at 500 ms, compared with NVDA's capture; a mockapp MSAA dialog whose child's `accParent` fails, giving its dialog; the Windows Terminal launch scenarios ten times.
- Core's meeting of chains. A plain window matched by handle to a UIA or MSAA window may differ in name; Core keeps the previous chain's entry, as NVDA keeps its old focus line's. Unit tests in Core per case.
- Repeats and currency. A focus in another top-level window raised with no event at all is not observed, so a kept read can be judged current across it. A read request that finds a newer unread item in its reader is answered gone and nothing is spoken for it, a newer event having come. Measured: the repeats per scenario, the kept reads found not current, and a Windows Terminal return after its title changed.
- A read request's read. The reader makes the read as asked, without NVDA's acceptance and keyboard-focus tests again, which it made on the event; an element gone answers gone, and nothing is spoken. Between Core's request and the read the focus may move on; for MSAA the focused-state test then drops a focus no longer focused, which NVDA, reading at once, would have spoken and cut. A foreground read answered after a focus the outpost had queued changes nothing, the window having been spoken as the focus's entered container. Measured: the round trip and the words of a return to Notepad by Alt+Tab in `second_application_and_verbatim_menu` and `return_after_retirement`.
- The refusal notice lags by one message, during which the outpost follows the refused node. With no departure notice, a background application's topmost window can have its focus's changes read and dropped by Core. An outpost unit test checks an older report's refusal is ignored.
- The menu opening. A focus observed before it but arriving after it, from another outpost or as a requested read's report, cannot count as pending, a limit: the menu is spoken and then the focus, where NVDA drops the menu; current-only repeats make the requested case rare. Unit tests in Core for the duplicate-then-menu case and the redirect.
- The gap in the listener, the hold and the marker: measured as the order of work says.
- The delayed pump, the speech cut and the desktop's name are built only after their captures and probes.

### Room for extensions

Extensions arrive in M5 ([extensions](extensions.md)), whose host runs in the outposts and Core and never in the listener, and whose window and event rules compile into tables the listener and the outposts both consult. This rework builds none of it, but keeps these things M5 needs, so that a module's veto or redirect of a focus never costs a read NVDA would not make:

- The listener's checks before a read stay data-driven tables in NVDA's order, with a place for M5's window, event and node rules judged from the event's cache alone. NVDA's base cache request, which the listener's registration copies, already carries the framework, automation id, class name, control type, name and process id (`UIAHandler/__init__.py` 61 to 74), so a veto declared as a rule drops the focus before any read.
- Hooks run in the outpost after the listener's read, as NVDA runs a module's `event_gainFocus` after `doPreGainFocus` has walked the ancestors (`eventHandler.py` 349 to 357, 378 to 387), so a code veto or redirect makes no read NVDA would not; NVDA's own UIA vetoes before the walk are UIA's default `shouldAllowUIAFocusEvent`, the keyboard-focus read the listener already makes, and in its application modules a class constant and a container override on the Alt key's state (`appModules/explorer.py` 35 to 48), expressible as rules from the cache. No general read request is kept for M5; a later module whose pre-walk veto is code adds it with its use.
- Kept verdicts can be dropped: each process drops its verdicts when it installs a new version of the rule tables, since a reloaded module can change a window's backend.
- Repeats judged in Core change what the Windows Terminal second-identity hook ([design](windows-terminal-twin-focus.md)) assumes, the listener's comparison before the read and `focus()` as Core's focus; M5 restates it against the unread repeat and the followed focus, and says which element `focus()` means when a hook drops a focus the listener's kept read is on.
- M5's node and event rules apply at one point, the outpost's emission, to every kind of report: listener reads, the requested read's report of an unread repeat (the unread fact itself carries only an identity), plain windows published at a bound, menu openings, and the outpost's own recovery reads (focus-missing, the read after a listener's drop, focus-now), which find a focus with no judgement of the listener's and so must meet the same vetoes, or a vetoed focus would come back through the gap.

### Why no smaller design

The study's first recommendation, on 2026-10-25, removed four reconciliations and left the copies of the focus, the two verdicts, the hooks-in window, the foreground copies and the audit's fallbacks; this design replaces it. A one-process host and outposts holding the focus registration stay ruled out for the reasons in the constraints section. The two routes are forced; given them, an application's events need an order (the marker), a new outpost needs its first events (the hold), a missed UIA focus needs a recovery (the gap in the listener), several outposts need a common order at Core (one time unit), two independent verdicts need settling (by the outpost, from what it receives), and the outpost needs to know when it follows the wrong node (the refusal notice). Each is kept once, in the process that holds its evidence.

The alternative in which the listener makes no call and each outpost finds and reads its application's UIA focus itself, with `GetFocusedElementBuildCache` and a comparison of runtime ids, was written and reviewed on 2026-10-29 and rejected by Dickson the same day; it is the outpost redesign of 2026-10-01 that option (b) replaced, and git keeps its record (e2c883a8). It would return to dropping a focus whose read of a starting application fails, which made the Notepad scenario fail in 1 of 5 to 25 runs (13dcd2db); `GetFocusedElement` does not always name the sender, as Start's search results raise focus while it stays on the search box (018e62d5), so the comparison would take such a focus for a repeat and say nothing; the reads that fail report nothing, so they would close the gap that should recover them; NVDA's refusals would be judged on the event rather than on the element found, which can be the console window; every new window's first focus would need a connection by handle, which held the worker 2.0 to 2.5 seconds in 1 to 6 of 10 new File Explorer windows (decision 11 of `docs/design/listener-without-connections.md`); and the window's name would wait on that read, against the decision of 2026-10-29. Its gain, a listener that makes no call, does not outweigh silences that NVDA does not have.

## Order of work

Each step is one step in the sense of `REVIEW.md` and leaves every mechanism it does not replace working. A builder step is one subagent's, ending at unit tests and `cargo xtask ci`; the parent then runs the scenarios named, one batch from one background script. The measurements of the first step get no adversarial review; the mockapp commands it commits are reviewed with the step that first relies on them.

1. Measure and capture. Results go to a new folder under `experiments/` named focus-pipeline-rework-measurements, with a readme in the form `experiments/readme.md` asks and a line in that index.
