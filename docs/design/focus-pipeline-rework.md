# The focus pipeline rework

Status: scope and order of work agreed by Dickson on 2026-10-25, to be built in a session of its own (`docs/roadmap.md`, M4, "The focus pipeline rework"). The study of the present pipeline follows them, with file and line references into the code as of 2026-10-25; the process and thread model it starts from is `docs/architecture.md`, section 1. The scope was widened on 2026-10-29 to every reconciliation below and every difference in [the NVDA audit](focus-pipeline-audit.md).

## What was found

The pipeline's shape is forced: three measured facts about UI Automation (an element cannot leave the process that received its event; a focus registration is desktop-wide; a hung window named in a focus WinEvent holds every UIA event of a process registered for focus), decision D9, and Dickson's refusal of a one-process host on 2026-10-20 require a focus listener that reads every UIA focus, one outpost per application that holds everything else, and a Core that decides. What has grown is the machinery that reconciles the two routes and the copies of "the focus" they leave: of about ninety mechanisms, about half port NVDA or answer a constraint and about half make Verbatim's processes agree, and six of those were each patched three to seven times between 2026-10-20 and 2026-10-25, each round tuning a disagreement between two copies of one fact. The rework removes reconciliations inside the present shape; no smaller shape meets the requirements.

## Decisions (Dickson, 2026-10-25)

- Repeats are judged in Core. The listener keeps the last focus each application's reading thread read. A focus event on that element, judged by NVDA's own checks, `CompareElements` against the kept element and a live `CurrentHasKeyboardFocus` on it, never inferred from a cache, is not read again: the listener sends the kept facts, with the event's cached states, as an ordinary focus fact, and Core's duplicate rule drops it or takes it. The outpost does the same for a repeated MSAA focus on the object it read last. There is no protocol change. This removes `CoreFocus` and its recipients, the listener's held elements, the outpost's queue of unjudged focuses, the trace handshake, and the follow-up on reads a watchdog abandons with the fix approved for it, and it closes the hole where a focus returning to an element while Core's notice is in flight is never spoken. It replaces the judging before the read of the D14 rework of 2026-10-25.
- The wait for a missing UIA focus (the gap) moves into the listener, whose desktop-wide hook already receives every focus WinEvent beside the UIA focus, on one clock. At its one-second bound the listener tells the application's outpost the focus is missing, and the outpost reads it in its ordered stream, as now, so the order of the application's events stays the outpost's. This replaces the placement of 2026-10-21.
- The outpost's own read of a focus UIA did not deliver stays (decision 11).
- The hand-over to a new outpost holds the outpost's own hook copies until the moment forwarding ended is known, instead of matching the listener's copies by counting.
- Every observation is stamped in microseconds from one clock read, in every process, so the order of focuses is a total order.
- The marker that holds an application's later events until the listener's read arrives stays.

Added by Dickson on 2026-10-29, with the scope widened to every reconciliation and every difference in [the NVDA audit](focus-pipeline-audit.md). The aim is NVDA's focus logic wherever the multi-process model allows, with one owner for each fact and as few calls as possible:

- A window in the focus's ancestry is named by NVDA's rule: a plain window named by `InternalGetWindowText` for the desktop, a ghost window or a hung application, otherwise the window's UIA or MSAA object chosen as NVDA chooses it. When that read has not answered within Verbatim's existing bounds (`MOVED_ON_GRACE` when the focus has moved to a new window, the read's budget otherwise), the window is named by `InternalGetWindowText`, a deliberate difference.
- Core's second test of an accepted focus against the foreground goes: a focus is judged against the foreground once, as NVDA does.
- Where calls and judgements are made. Core makes no call into Windows or any application; the app thread of `verbatim.exe` may read only Windows' own state, such as the foreground window, which never waits on an application. The listener and the outposts make every accessibility call. They may drop an event only on what they observe of it at that moment, with no information from Core (the window is hung, the element no longer has the keyboard focus, the window is not related to the foreground, the window is UIA), as NVDA does before its read. They may use their own last read only to skip a call, and then still send Core the fact. Core alone judges anything that depends on the state it holds: the focus, repeats, the foreground and staleness.
- NVDA's two foreground tests (the focus already in the window; the focus's own event) are Core's. An outpost whose own last report says a foreground change repeats its focus sends it unread, with the window and the event's identity, and Core judges it against its focus, asking the outpost to read the window only when it is not a repeat, after any focus the outpost has already queued; an outpost whose own report says it is no repeat reads the window at once, as now.

## Terms

- The listener is the one permanent `verbatim-outpost.exe --listener` process: it holds the desktop-wide UIA focus registration and desktop-wide `WinEvent` hooks, and reads each UIA focus on a thread per application.
- An outpost is the process that serves one application: its own process-scoped `WinEvent` hook, its UIA property and text registrations, one worker thread, a watchdog.
- Core is the reducer in `verbatim-core`, the only decider; the app is `verbatim.exe`'s thread that feeds it and routes its answers.
- A route is the path one of an application's events takes to its outpost: the listener's (a UIA focus, read in the listener and relayed through the app) or the outpost's own (its hook and registrations). The two-route structure is that one application's events arrive by both.
- A judge is a process that applies a focus rule before an element is read: the listener or an outpost. Core judges after the read.
- The marker is the message the listener's UIA focus callback sends an outpost the moment a focus event arrives; the outpost holds every later entry behind it until the listener's read or drop takes its place.
- The gap is an outpost's wait of one second after a `WinEvent` focus in a UIA window for the matching UIA focus, after which it reads its application's focus itself.
- The hand-over is the protocol by which the listener stops forwarding an application's `WinEvent`s once its outpost's hook is in, and the outpost drops the second copy of an event both hooks took.
- `CoreFocus` is the notice Core sends the judges after every focus event it judges and every change of its focus, so they judge repeats and change targets against the focus Core holds rather than a copy of what they last reported.
- A verdict is a window's backend decision, UIA or MSAA, from NVDA's class lists or a probe; each process keeps its own verdicts.

## The constraints that force the shape

Each is measured or decided, with its record.

- A UIA element cannot leave the process that received its event. `CoMarshalInterface` succeeds and `CoUnmarshalInterface` fails in the other process, by every route (E-marshal, focus pipeline section 11; `docs/uia-bugs.md`, "Elements cannot be passed to another process"). So whoever receives a UIA focus event must judge and read it; that is why the pre-October design, in which the outpost found the element again by runtime id, name and position, grew the moved-on rules and failed (section 1 of the focus pipeline).
- A UIA focus registration is desktop-wide. The scoped form is undocumented, refused by the direct call, and misses every proxied Win32 window (`docs/uia-bugs.md`, "Focus events cannot be limited to one application"). So one process receives every application's UIA focus events, or every outpost receives all of them at 47 to 90 provider calls each per focus change (E-cost), which Dickson ruled out.
- A hung window named in a focus `WinEvent` holds every UIA event delivered to a process that holds a focus registration, for twice the connection timeout per event (`docs/uia-bugs.md`, "A hung window named in a system focus event"). So the process holding the focus registration must hold nothing whose stall would be heard; Dickson declined one UIA host process on 2026-10-20 for this reason (D13 as amended that day).
- A thread blocked in a cross-process call cannot be cancelled; only process exit reclaims it (D9). So one outpost per application, abandonable workers and reading threads, and the kill-and-replace ladder.
- UI Automation delivers a newly started process's focus events late or never, and sometimes after their senders are gone (risks 2 and 13 of the listener design; `docs/uia-bugs.md`, "A new process's focus events reach the desktop-wide handler late"). NVDA loses those focuses by its source; Dickson decided to recover them (decision 11, 2026-10-18 and 2026-10-21), which is Verbatim's one deliberate departure from NVDA on the focus path.
- `WinEvent`s and UIA callbacks arrive with no common order; NVDA restores one by passing both through one process's threads and one queue. Verbatim has no one process, so every ordering it needs it must build.
- Windows names a console window's owner as the console's client while the console host serves it, so one application's events arrive from two processes' windows.
- Two Verbatim processes connecting to one application collide inside UIA (`docs/uia-bugs.md`, the first entry), so only an application's outpost connects to it and the listener reads with calls on held elements only.
- NVDA parity for everything spoken, from captures and the pinned source: the acceptance test, the limiter, the duplicate rule, the foreground tests, presentability, the shell's and the switcher's rules.
- Verbatim's own GUI lives in a watched process, so its hidden frame must never be announced.

From the first four, the listener must receive and read every UIA focus and each outpost must hold everything else; Core, the only process that sees every application, must decide. The two-route structure is therefore forced, given Dickson's two decisions (outposts kept, no one-process host). Nothing below proposes undoing it.

## Where state is duplicated, and how the copies disagree

Each item names the copies and gives one sequence from the code in which they differ.

- The focus: Core's `FocusContext` (`state.rs` 17 to 68); the listener's held elements marked waiting, held or done by `CoreFocus` (`focus_read.rs` 571 to 700); the outpost's `Held` with Core's focus, the unjudged reports and another application's observation time (`held.rs` 70 to 200); and the outpost's older `Tracking` (`worker.rs` 279 to 379). Sequence one, a correctness hole: Core holds E from a listener read; an MSAA focus in another application is applied and the notice that E is done is written; before it reaches the listener, E regains the focus and raises a UIA event; the reading thread finds E held and still focused and drops it as a repeat (`focus_read.rs` 1236 to 1323), so Core never hears the focus return. NVDA has no such window because its last queued focus is set synchronously. Sequence two, conservative by design: an outpost reads a state change for a report Core has meanwhile judged stale, and Core drops it; the cost is a read, not speech. Sequence three: `adopt_focus` runs as the report is published, before Core judges it, so an outpost follows and reads the caret of a node Core refused (`worker.rs` 1470 to 1479, 2372). Sequence four: a focus-now answer is pushed to the unjudged queue under the query's trace, and unless Core's notice names that trace it stays until a later judged trace drains past it (`held.rs` 104 to 108; `worker.rs` 4247 to 4257).
- The verdicts: the listener's arbitrator, one per reading thread and started empty (`focus_read.rs` 790), and the outpost's, which copies only the listener's yes (`worker.rs` 3861). Sequence: the listener's probe of a new File Explorer window times out and its focus is dropped as not UIA, which reaches the outpost as inconclusive; the outpost's own probe of the same window says UIA and is kept for life; the outpost drops its `WinEvent` copy and waits a second for a UIA focus the listener has already refused (`focus_read.rs` 455 to 464 names this). The negative verdicts also expire on two clocks, so one process can say MSAA and the other UIA within one event.
- Which applications have hooks in: the listener's hooked map and the supervisor's records (`owner.rs` 1419 to 1425). Sequence: a ready outpost dies; until `HookRemoved` reaches the listener, it forwards none of that application's `WinEvent`s and no hook holds them, so a menu or alert raised then is lost to both routes; the focus is recovered by the replacement's focus-now, the menu is not.
- The gap's "a UIA focus answered it" and the listener's knowledge: matched by observation time within 100 ms across two processes' stamps, and by top-level window for a read but by time alone for a drop (`gap.rs` 27 to 29). Sequence: a `WinEvent` focus in window A opens a gap; the listener's read of a focus in window B of the same application times out and is dropped with focus evidence; the news closes A's gap and nothing is read, though nothing is known of A (`gap.rs` 144 to 152).
- The foreground: Core's attention window, foreground node, latest focus's top level and the hook's foreground view; the supervisor's attention by message; the app's live read for the fake focus; the listener's test at read time; the outpost's test when handled and again when reported. Sequence: a UIA focus the listener accepted with its window in front is handled after Alt+Tab and reported `in_foreground: false`, and Core drops it, where NVDA's one earlier test would have spoken it. A foreground report for the window already holding the focus "changes nothing" yet moves the latest-focus stamp and its outpost (`reduce.rs` 655 to 664 against 856 to 861).
- The hand-over: the outpost's `hook_from` and `forwarded_through` against the listener's tick. If `ForwardingEnded` never arrives, `may_have_twin` is true for the outpost's life and the two maps are never trimmed (`handover.rs` 241 to 243); a listener backlog that replaced a waiting fact leaves a hook copy unmatched and misorders that tick.
- The last reported focus the intake reorders by, which lags a read taken in but not handled (`intake.rs` 136 to 139, stated as a limit).
- The event thread's narrowing pair against the worker's tracked window: a destroyed focus window is forgotten in the window cache but not in the pair (`narrowing.rs` 134 to 141).
- The states last read by the outpost against Core's, when the outbound merge replaces a waiting state change (`outbound.rs` 148 to 163; `held.rs` 197 to 207).
- Readiness known by the owner as it reads `Ready`, by the app when the frame reaches the reducer, and by the control plane.

Eleven of these exist because one fact is held in two or three processes with no single owner; the gap's look-back, the marker news, the copied verdict, the hand-over's counting and the unjudged queue are each a patch on one of them.

## Which mechanisms exist only because of earlier design choices

The two-route structure itself is forced, as the constraints section says. Within it, these follow from choices rather than constraints:

- The gap's placement in the outpost's worker (decision 11 as amended 2026-10-21). The reason given, that only the worker sees both halves, is not so: the listener's desktop-wide hook receives every focus `WinEvent` and drops a served application's in its backlog (`listener.rs` 227 to 231, `Waiting.hooked`), and its UIA callback receives every UIA focus. The listener is the one process that holds both halves with one clock.
- The hand-over's matching by counting rather than a hold. Counting was chosen so no copy waits; its price is the seven ordering commits, because the two sources' copies arrive interleaved.
- Judging repeats before the read in the judges, which needs Core's focus there (`CoreFocus`, the held elements, the unjudged queue, the trace handshake). The repeat is dropped by Core either way; the pre-read drop saves two to three calls per repeat and costs the notice machinery and the hole above.
- The listener making several calls where one remote operation was one transaction, hence the budget, the deadline's derivation and the out-of-time paths. This is the price of the no-connection rule (2026-10-19 and 2026-10-20), which removed the lock; it is a decided trade and not revisited here.
- The reading threads ended by `HookRemoved` rather than by the application's exit.
- Stamps in two units.
- Core's four notions of the foreground and two of the latest focus, updated at different points of `reduce_event`, with three patches reconciling them.
- The in-ignored-window judgement in the app.

## The design

Status: proposed on 2026-10-29 for Dickson's review, replacing the recommendation of 2026-10-25, revised the same day after an adversarial review, and simplified the same day after a simplification pass whose suggestions Dickson accepted. It keeps the shape the constraints force and every decision above, settles each of the eleven duplicated facts and each difference in [the audit](focus-pipeline-audit.md), and names what each change costs. Call cancellation stays out (`docs/roadmap.md`, M6.1): every bound below is one Verbatim has today, abandoned threads and `READ_DEADLINE` stay, and nothing here depends on whether a stuck call can be ended, so cancelling one later only frees its thread.

Terms used in this section:

- A plain window: what NVDA makes for a window when it makes no UIA or MSAA object for it (`NVDAObjects/window/__init__.py` 85 to 97 choose it for the desktop, a ghost or a hung window): role window, named by `InternalGetWindowText` (190 to 194), invisible when not visible and unavailable when disabled by its style, and focused when it is its thread's focus window (`GetGUIThreadInfo`). Read from Windows' own state, with no call into any application.
- A kept read: the last focus a reader read in full, with its chain: the listener's per application, holding the element, and the outpost's, holding the MSAA event address and whether it was a simple child. A cache that saves calls; nothing is judged against it.
- A kept read is current while its reader has observed no focus or foreground event in another top-level window since the event it was read for. The event being judged is not counted; in the listener, another application's UIA sender with no window of its own counts as elsewhere, and its own application's are placed by its reading thread, which finds each one's nearest window in order before the next event.
- The followed focus: the node whose text, caret and terminal output an outpost reads and on which its focus-following subscription sits.
- A read request: Core asking the reader that sent an event unread, the listener or an outpost, to read it.
- The bound of a walk: `MOVED_ON_GRACE` (500 ms) when the focus's top-level window is not that of the previous focus its reader observed, and the read's budget otherwise (the decision of 2026-10-29), both measured from the event's observation on the shared clock.

### Where calls and judgements are made

The rule of 2026-10-29: Core makes no call into Windows or any application; the app thread reads only Windows' own state; the listener and the outposts make every accessibility call, drop an event only on what they observe of it at that moment, and use their own last read only to skip a call, still sending the fact to the fact's owner; Core alone judges what depends on the state it holds. Per process:

- The listener holds the UIA focus registration and its global group, the global `WinEvent` hooks with the desktop switch added (difference 22), one reading thread per application with its kept read and its newest unread repeat, each application's gap record (below), its own backend verdicts, the applications whose outposts have their hooks in with each one's forwarding tick, and the time of the newest change of top-level window among the focus and foreground events it observed. It decides from observation only: NVDA's checks before a read (the hung window, the native check, `isNativeUIAElement` then `isUIAWindow`, by the class lists, its own verdict or the raw probe and the post-probe class checks, NVDA's duplicate test against its kept element, the acceptance test against the real foreground window, the console window's and the hidden frame's refusals, the sender's keyboard focus), the rules M5 declares from the event's cache, the watchdog's publishing and abandonment, the gap's bound, and how far its walk may run. It makes no connection. A UIA menu opening it reads in order, as the focus it is. It sends markers; reads, unread repeats and drops; reads Core asks for; focus-missing; forwarded `WinEvent`s until an outpost's hook is in; forwarding's end; selections, notifications, menu and switcher ends; the foreground window for the keyboard hook; and the desktop switch.
- An outpost holds its hook, registrations, worker and watchdog; its own backend verdicts; its followed focus as one record (node, role, window, chain, the states last read, the MSAA event address and simple-child mark, the dialog memo); the per-node last reads of the caret rework; its held nodes; its intake with the marker wait and the hand-over's hold. It decides from observation: the acceptance test, once, for every event but a UIA focus; the window's readability, ghost and hung state; each window's backend with the listener's code; and, from what it receives, a disagreement with the listener's verdict, reading a focus the listener dropped as not UIA or unknown in a window it judges UIA, and dropping a listener's report in a window it judges MSAA; NVDA's focused-state test and child redirect for an MSAA focus; M5's node and event rules and its modules' code vetoes and redirects, after the read, on every report it emits; and, as the named exception, change and selection targeting. It sends focus reports with complete chains, an MSAA repeat or a foreground change it judged a repeat unread, and everything else as today; it answers read requests in its queue's order.
- The app, `verbatim.exe`'s thread and its supervisor, holds the single input channel, the held facts for starting outposts, the spares and the outposts' records. It decides nothing about a focus: the in-ignored-window drop moves to Core. It reads only Windows' state (the foreground window to route a focus-now query), stamps each input's arrival, and runs Core's timers.
- Core holds the one focus, one foreground record (below), the newest focus's stamps, and speech validity. It judges repeats, staleness, application refusals with the ignored processes among them, NVDA's two foreground tests, a menu opening's pending focus and redirect, a fake focus's duplicate test, whether a focus is new or repeated for the caret rework, where a new chain meets the previous one, the speech cut, and presentability. It sends refusal notices, read requests to the reader that sent an unread fact, focus-now queries, text requests and `NodesHeld`.

### A window's name, and the one fallback

The decision of 2026-10-29, as built here. A window in the focus's ancestry is the object a walk reaches for it: the listener's UIA walk, the outpost's MSAA walk, or the outpost's continuation, which goes on from a window by its object chosen as NVDA chooses it, UIA when the outpost's verdict says so and MSAA otherwise, and through MSAA above the process boundary (decision 7 of the listener design). A plain window is taken instead, with no call, in two cases only: the desktop, a ghost window or a window of a hung application, by NVDA's rule; and the windows a walk has not reached by its bound.

Where a walk ends by failure rather than by time, it goes on as NVDA's does: a failed or empty MSAA `accParent`, a boundary window that cannot be acquired, and a failed UIA parent step continue from the parent window's object (`Window._get_parent`), within the bound. The listener, which may not connect to a window, ends its read there and names the window to continue from; the outpost continues from it, as it continues a chain at the process boundary today. So after a failed `accParent` in a "Save As" dialog, the dialog's own object is reached and "Save As dialog" is said (difference 2). The depth limit of 64 is a walk's end by count, completed by plain windows.

Meeting the bound when a call is stuck. A call under way cannot be ended, so the bound is met by a publisher other than the reader, and only for a read that has passed every check NVDA makes before queueing a focus and is stuck in its walk: a read still in its checks at the bound (the nearest-window lookup, the sender's keyboard focus, the outpost's focused-state test) is left to the moved-on rule and the deadline, as today, so a focus NVDA would drop is never published early. The bound is the one of the Terms, measured from the event's observation. In the listener, the reading thread shares its progress (the event's cached facts, the facts read so far, the ancestors read and the nearest window) with the watchdog under `WatchedRead`'s claim; at the bound the watchdog publishes the focus from that progress, completed by plain windows read on its own thread, and takes the claim, so the reader's late result is discarded when it returns. The thread is not abandoned for this: it reads the application's next event when its call returns, is abandoned only at `READ_DEADLINE` or by the moved-on rule as now, and so counts against `ABANDONED_LIMIT` only then. The publication is one function of the reader's shared state, so that if M6.1 finds `CoCancelCall` ends a UIA call, the watchdog cancels the stuck call and the reader itself completes with plain windows through that function, and `WatchedRead`'s claim, the late-result discard, `READ_DEADLINE`, `ABANDONED_LIMIT` and abandoned threads go together, as M6.1 lists. The outpost's worker and watchdog do the same for its walks, under the generation claim; an entry whose focus object itself has not been acquired has nothing to publish and is left to the deadline. Speech: the Windows Terminal launch says its window by its text 500 ms after its focus event was observed, whatever its parent step is doing.

Core's use. Every report's chain is complete to the desktop, so `ancestors_unknown` leaves the wire. A plain window carries its handle in the node's details, as do UIA window elements and MSAA window and client objects, and no other node does; a nearest-window handle is never put there. Core walks the new chain from the focus outward and stops at the first entry equal to one in the previous chain, by node id, or by window handle when both entries are windows (a plain window, a UIA window element, or an MSAA window or client object), so that one window reported by two outposts, such as ApplicationFrameHost's frame around Settings' content, is one entry; the result is the previous chain to that entry and the new entries below it, as `api.setFocusObject` builds the focus line. Entered containers are those below the meeting point. Speech is cut when the chains differ just below the desktop (difference 21). A focus whose walk reached only its nearest window in a new top-level window says "Windows PowerShell window" and then the focus.

Also served by the fallback: the MSAA focused-state test past a failed `accParent` continues along parent windows, a plain window being focused when it is its thread's focus window (difference 19); and the focus-now answer onto a hung window is the plain window, as NVDA's (pending its capture).

Costs: nothing on the steady path. On a fallback, about four local calls per plain window and one `GetGUIThreadInfo`, and about a hundred bytes per window in the message; a continuation after a failure makes the calls NVDA makes. Removed: Core's unknown-ancestor handling (13dcd2db, 2b13487b), the windowless-focus adoption and `ancestors_unknown` in the protocol, the outpost's focus path and the focus-now answer.

### Repeats, stamps and the hold

Repeats, one mechanism (decided). A reader makes NVDA's duplicate test, and sends a repeat unread, only while its kept read is current, since NVDA tests against `lastQueuedFocusObject` (`UIAHandler/__init__.py` 902 to 914; `IAccessibleHandler/__init__.py` 772 to 776), which a visit elsewhere replaces; otherwise it reads in full. So a return to an application onto the element it left is read at once, as NVDA reads it. Sent unread: the listener for a UIA focus whose sender `CompareElements` equates with its kept element while that element still has the keyboard focus, read live (`UIAHandler/__init__.py` 906 to 914); the outpost for an MSAA focus at the event address of its kept read, never one that was a simple child, and for a foreground change its own last report says repeats (NVDA's two foreground tests, `IAccessibleHandler/__init__.py` 837 to 864). The unread fact carries the event's identity (the runtime id, the MSAA event address, or the foreground window and the event's address) and only what the event itself carries: for UIA the cached name and keyboard focus, for MSAA and the foreground nothing. Core takes it as a duplicate of the node it holds, updating only what the fact carries, and drops it; when it is not a repeat in Core, it sends a read request to the reader that sent it, which reads in its queue's order, after anything it has already queued: the listener its kept element, with chain reuse while current, the outpost by reacquiring from the event address or reading the foreground window. Each reader keeps, per application, only its newest unread item, the listener's being its kept element, and answers a request for an older one gone, with no time bound. Core keeps two things per focus: the reading it holds, which a duplicate updates only with what it carries, for review; and what it last spoke of the focus, which only speech updates, and against which name, value, description and state changes are compared, as NVDA compares with the properties it last spoke (`speech/speech.py` 768 to 781). A name change carried in by a repeat is then spoken when its event comes (difference 20). A focus whose report marks it a simple child is never a repeat in Core of a held focus that was one, so a reused child id is announced as NVDA announces it. A repeated text focus brings no caret read; the caret rework's repeated-focus case is said by the key's answer, which still finds the change.

Currency. In the listener it is one stamp: the time of the newest change of top-level window among the focus and foreground events either source observed, written by the callbacks with one `GetAncestor` on the event's window, from the `WinEvent` or the UIA event's cached window, never by the nearest-window lookup, with the exact rule of the Terms for senders with no window of their own. In the outpost, a kept chain is current while its hook has delivered no foreground change since it was read. This fixes stale reused ancestors (difference 3): after Alt+Tab back to Windows Terminal, whose title a program changed meanwhile, the first focus reads the whole chain and says the new title, at the cost NVDA pays, the chain's calls once per return.

The time unit, first. Before anything else that compares stamps from two processes is built, every observation is stamped in microseconds from one clock read, in the listener's two callbacks, the outposts' hook and subscription callbacks, and the focus-now answer; Core compares only microseconds, in the stale rule, the background drop at a foreground change (`foreground_changed_at`, in milliseconds today), the fake focus's guard and the menu opening's pending focus. A report made for a read request, focus-missing or a listener's drop carries the observation stamp of the event it answers, never the time of its read, so the stale rule drops a late report of a window the user has left (the outpost's gap read today stamps its read, `worker.rs` 1399). The millisecond field leaves the wire (decided); a log or the latency timeline derives milliseconds where it prints them. A `WinEvent`'s own tick stays only as the hand-over's identity of an event.

The hand-over's hold, as above; its cost is the relay's latency once per outpost start, on the hook's copies only.

The idle barrier. A read request counts as in progress in Core until its report or its gone answer has been reduced, and a refusal notice until written, so the harness's idle round, and a key's evidence under `docs/testing.md`, wait for what Core began after a reader answered idle.

### Mechanisms removed and added, with their costs

Removed: `CoreFocus` and its builder in the app; the listener's `HeldElements`; the outpost's `Held`; the "no repeat while unjudged" rule; `Reading::abandoned`'s keeping for Core and the follow-up on abandoned reads; the outpost's gap with `MarkerNews`, `DropEvidence` and the drop classes; the hand-over's multisets, `TWIN_BOUND`, `ListenerBeforeHook` and run ordering by raise time; `record_probe`; the listener's judgement of a menu opening before its turn; the resend of kept facts; the millisecond field on the wire; Core's second acceptance test, `report_foreground`'s second look and the intake's second hung test; `ancestors_unknown` with Core's kept chain and the windowless-focus adoption; the app's in-ignored-window judgement (to Core, with the top-level window's process in the window facts); Core's four notions of the foreground.

Added: the unknown verdict, the outpost's read after a listener's drop in a window it judges UIA and its drop of a listener's report in a window it judges MSAA; the unread fact for every repeat with Core's read request to the reader that sent it, each reader keeping its newest unread item; the continuation from a parent window's object, plain windows at the bound, the watchdogs publishing at the bound through one function, and Core's meeting of chains; the window handle in node details; the listener's currency stamp; refusal notices; Core's spoken record; the menu opening read in order and judged in Core; focus-missing; the hand-over's hold; the desktop switch and the desktop's name; the delayed pump, if its capture agrees.

Per focus on the steady path: two or three fewer messages, the `CoreFocus` notices, and as many fewer wake-ups of the listener's and outposts' pipe threads; no call added; one local `GetAncestor` and one atomic store per focus and foreground event in the listener; memory down by the unjudged queues and held elements. A repeat Core holds costs NVDA's test (two calls for UIA, none for MSAA and the foreground) and one small message. Since a reader sends a repeat unread only while its kept read is current, a repeat Core does not hold is rare: for UIA and MSAA it needs Core's focus to have moved without the reader seeing it, an MSAA focus elsewhere in the same top-level window or a refusal, which the first step counts; it then costs a read request's round trip before the read, expected under a millisecond and measured before it is trusted, and the application's events raised meanwhile are handled before the requested read's report. The foreground's repeat test is NVDA's two foreground tests against the outpost's last report, which the 2026-10-29 decision fixes, so a return by Alt+Tab whose last report is in that window costs the round trip. The first focus after a return to an application reads its whole chain, as NVDA. The listener probes before it reads, as now: in an MSAA window not on the class lists, two raw probes per focus change more than 500 ms after the last, the deliberate difference above. A menu opening Core drops costs the listener one read NVDA does not make. A gap record costs no wake-up when answered before its application's reads go idle, and one at its bound otherwise.

Per outpost start: the hook's copies wait for the relay's latency until forwarding ends, measured at 0.05 to 0.15 ms at the median, 36 ms at the 90th percentile and 146 ms at worst before communication step 6; `TWIN_BOUND`'s timer goes.

Fixed costs: one more global `WinEvent` kind and possibly one process-scoped hook in the listener; the delayed pump's up to 10 ms on a batch beginning with a popup start or foreground change, and one timer, which NVDA has too, only if its capture agrees.

### Edge cases, limitations and what must be measured

- Verdicts. A window that answers one process's probe and times out the other's, or gains a provider between them, is judged differently; the outpost reads after the listener's drop, or drops the listener's report in a window it judges MSAA, so the focus is spoken once, late by a read at worst. Measured: probes per focus in `call_counts` against mockapp, and `conhost_two_windows`, `windows_terminal_two_windows` and `explorer_folder_window` ten times each with no focus lost or doubled.
- Hooks in. An outpost stuck without exiting is covered by `HookRemoved` at the failure decision; its stuck worker's output is refused by the live-incarnation gate. Events raised in the relay hop after a crash, and those raised before it and not handled, are lost, as now. Checked by `outpost_crash_recovery` with a context menu opened during the replacement.
- The fallback. A popup owned by another window is placed under the desktop by plain windows, as NVDA's fallback places it, where UIA's raw view may put it under its owner. A thread whose call returns after the watchdog published goes on to the application's next event, so a second slow window can still reach the abandoned limit only through the deadline, as now. Measured: a mockapp provider stalling only its parent navigation for 15 seconds, with the focus arriving from another application and from within, giving "title window" at 500 ms, compared with NVDA's capture; a mockapp MSAA dialog whose child's `accParent` fails, giving its dialog; the Windows Terminal launch scenarios ten times.
- Core's meeting of chains. A plain window matched by handle to a UIA or MSAA window may differ in name; Core keeps the previous chain's entry, as NVDA keeps its old focus line's. Unit tests in Core per case.
- Repeats and currency. A focus in another top-level window raised with no event at all is not observed, so a kept read can be judged current across it. A read request that finds a newer unread item in its reader is answered gone and nothing is spoken for it, a newer event having come. Measured: the repeats per scenario, the kept reads found not current, and a Windows Terminal return after its title changed.
- A read request's read. The reader makes the read as asked, without NVDA's acceptance and keyboard-focus tests again, which it made on the event; an element gone answers gone, and nothing is spoken. Between Core's request and the read the focus may move on; for MSAA the focused-state test then drops a focus no longer focused, which NVDA, reading at once, would have spoken and cut. A foreground read answered after a focus the outpost had queued changes nothing, the window having been spoken as the focus's entered container. Measured: the round trip and the words of a return to Notepad by Alt+Tab in `second_application_and_verbatim_menu` and `return_after_retirement`.
- The refusal notice lags by one message, during which the outpost follows the refused node. With no departure notice, a background application's topmost window can have its focus's changes read and dropped by Core. An outpost unit test checks an older report's refusal is ignored.
- The menu opening. A focus observed before it but arriving after it, from another outpost or as a requested read's report, cannot count as pending, a limit: the menu is spoken and then the focus, where NVDA drops the menu; current-only repeats make the requested case rare. Unit tests in Core for the duplicate-then-menu case and the redirect.
- The gap in the listener, the hold and the marker: measured as the order of work says.
- The delayed pump, the speech cut and the desktop's name are built only after their captures and probes.

### Room for extensions

Extensions arrive in M5 ([extensions](extensions.md)), whose host runs in the outposts and Core and never in the listener, and whose window and event rules compile into tables the listener and the outposts both consult. This rework builds none of it, but keeps these things M5 needs, so that a module's veto or redirect of a focus never costs a read NVDA would not make (Dickson, 2026-10-29):

- The listener's checks before a read stay data-driven tables in NVDA's order, with a place for M5's window, event and node rules judged from the event's cache alone. NVDA's base cache request, which the listener's registration copies, already carries the framework, automation id, class name, control type, name and process id (`UIAHandler/__init__.py` 61 to 74), so a veto declared as a rule drops the focus before any read.
- Hooks run in the outpost after the listener's read, as NVDA runs a module's `event_gainFocus` after `doPreGainFocus` has walked the ancestors (`eventHandler.py` 349 to 357, 378 to 387), so a code veto or redirect makes no read NVDA would not; NVDA's own UIA vetoes before the walk are UIA's default `shouldAllowUIAFocusEvent`, the keyboard-focus read the listener already makes, and in its application modules a class constant and a container override on the Alt key's state (`appModules/explorer.py` 35 to 48), expressible as rules from the cache. No general read request is kept for M5; a later module whose pre-walk veto is code adds it with its use.
- Kept verdicts can be dropped: each process drops its verdicts when it installs a new version of the rule tables, since a reloaded module can change a window's backend.
- Repeats judged in Core change what the Windows Terminal second-identity hook ([design](windows-terminal-twin-focus.md)) assumes, the listener's comparison before the read and `focus()` as Core's focus; M5 restates it against the unread repeat and the followed focus, and says which element `focus()` means when a hook drops a focus the listener's kept read is on.
- M5's node and event rules apply at one point, the outpost's emission, to every kind of report: listener reads, the requested read's report of an unread repeat (the unread fact itself carries only an identity), plain windows published at a bound, menu openings, and the outpost's own recovery reads (focus-missing, the read after a listener's drop, focus-now), which find a focus with no judgement of the listener's and so must meet the same vetoes, or a vetoed focus would come back through the gap.

### Why no smaller design

The recommendation of 2026-10-25 removed four reconciliations and left the copies of the focus, the two verdicts, the hooks-in window, the foreground copies and the audit's fallbacks; the design above replaces it. A one-process host and outposts holding the focus registration stay ruled out for the reasons in the constraints section. The two routes are forced; given them, an application's events need an order (the marker), a new outpost needs its first events (the hold), a missed UIA focus needs a recovery (the gap in the listener), several outposts need a common order at Core (one time unit), two independent verdicts need settling (by the outpost, from what it receives), and the outpost needs to know when it follows the wrong node (the refusal notice). Each is kept once, in the process that holds its evidence.

The alternative in which the listener makes no call and each outpost finds and reads its application's UIA focus itself, with `GetFocusedElementBuildCache` and a comparison of runtime ids, was written and reviewed on 2026-10-29 and rejected by Dickson the same day; it is the outpost redesign of 2026-10-01 that option (b) replaced, and git keeps its record (e2c883a8). It would return to dropping a focus whose read of a starting application fails, which made the Notepad scenario fail in 1 of 5 to 25 runs (13dcd2db); `GetFocusedElement` does not always name the sender, as Start's search results raise focus while it stays on the search box (018e62d5), so the comparison would take such a focus for a repeat and say nothing; the reads that fail report nothing, so they would close the gap that should recover them; NVDA's refusals would be judged on the event rather than on the element found, which can be the console window; every new window's first focus would need a connection by handle, which held the worker 2.0 to 2.5 seconds in 1 to 6 of 10 new File Explorer windows (decision 11 of `docs/design/listener-without-connections.md`); and the window's name would wait on that read, against the decision of 2026-10-29. Its gain, a listener that makes no call, does not outweigh silences that NVDA does not have.
