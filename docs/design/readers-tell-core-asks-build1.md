## Terms

The ADR's terms (reader, tell, ask, Core's inbox, the event queue, the committed focus, the readers' last focus, due time, stop waiting, the ancestors Core already knows, held object) are used as it defines them. This design adds:

- Entry: one item of the event queue. It is waiting (no request out) or asked (its function paused on exactly one request). Only the front entry is asked.
- Request in Core: Core's record of one request, with its due time; it is waiting for its outpost, out, no longer awaited or answered.
- Outcome: one of the ADR's five ways an answer ends (a result; refused, with a reason; not there; not responding; the reader ended or stopped), and, inside Core, a sixth that only Core gives: no longer awaited.
- Withdrawn: Core ends a request because its entry no longer needs it (a focus became pending under a caret key, a later key marked it, say-all stopped). It behaves as a stop for the hang or the due time: a request not started is dropped, a running call is left alone, its answer dropped by number. It plays no sound.
- Run: the ADR's and the build notes' run, MSAA focus and foreground tells merged into one entry and tried newest first.
- Menu slot: the one waiting entry for MSAA menu start, menu end, popup start, popup end and switch end.
- A focus is pending: at least one focus-kind entry stands behind the entry being judged and counts as pending: judged at that moment with no read, from the facts its tell carries, its acceptance passes, its verdict (in force, or carried from the check thread's probe) does not drop it, an override does not refuse it, a UI Automation focus's keyboard-focus answer let it through, and it is not a duplicate of the readers' last focus (an MSAA one by ids, a UI Automation one by the earlier element's keyboard-focus answer its tell carries). NVDA's `isPendingEvents("gainFocus")` (`eventHandler.py` 90 to 106) counts only focuses queued after those judgements (`IAccessibleHandler/__init__.py` 577 to 582, 760 to 782, 1036 to 1044; `UIAHandler/__init__.py` 885 to 950), and its caret loop pumps them before testing (`editableText.py` 95). Every judgement is made on the tell's facts, so this is exact.
- Tell window: the window Core judges a tell by. For a UI Automation focus, the nearest window the listener's check thread found (the sender's own window when it has one); for other tells, the event's window.
- Check thread: the listener's thread, one per application whose UI Automation events the listener hears, that makes, at delivery and before the tell is sent, every call NVDA's handler for that event makes (Table 11).
- Verdict: the backend cache's answer for one window, read through UI Automation or not. Probe: the outpost's one raw `WM_GETOBJECT` for `UiaRootObjectId`, waiting at most 3 seconds (`docs/parity/backends.md`, "The UIA provider probe").
- Starting read: the caret read a held caret key asks at its turn, before Core sends the key on (in a terminal, build 3's full read, naming the key's unit). Its answer mints the starting point.
- Starting point: a held anchor (an object the outpost keeps behind an id Core names) holding the caret and selection ends the starting read found, with the key's unit, the word at the caret (for Delete) and the line beside it.
- Pass: the moment Core sends a held key's stroke to the application, stamped on the run's shared clock.
- Watch: the outpost's waiting request that looks for a key's effect by comparing the application's caret with the starting point. Check: one such comparison, a short program on the outpost's worker. Final read: the one full read that ends a watch.
- Bound: how long a watch looks for an effect, counted from the pass.
- Marked: a caret key entry with a key, command, braille gesture or key Core sends standing behind it in the event queue. It is judged from the queue whenever Core needs it, so it is not stored.
- Selection baseline: the held anchor of the selection Core last spoke from, with that selection's text (up to 513 UTF-16 units) beside it.
- Text-changed flag: Core's fact, for the committed focus, that its text changed since the selection was last compared (NVDA's `hasContentChangedSinceLastSelection`).
- Stroke line: Core's list of the key transitions the hook held or deferred and Core has not yet sent, in the hook's order.
- Text provider: how the outpost reads a node's text: UI Automation, an edit control's window messages (with its edit API version), IAccessible2 text (M7), or none. Core names it in each text request.
- Details: what a text read fetches beyond the text (formatting attributes, spelling errors, links), named in each request.
- Release: the hook's held key sent to the application 150 ms after its press.
- Recovery set: Core's set of windows it stopped waiting on as hung, watched until they answer again.
- Kept element: a UI Automation element the listener keeps behind a token for a tell, until Core asks about it or it is swept.
- Generation record: Core's one record of an application's outpost generation (M6.2's single record).

## The decisions this design honours

Quoted from the ADR; each part of the design below was checked against them.

- "Every call into an application is made for a request from Core; the request carries what it needs and gets one answer, with one of five outcomes."
- "Core holds every rule that decides what is spoken, written to read like NVDA's, and its thread never blocks on an application."
- "Only the front entry may have a request out."
- "Only Core stops waiting. It keeps one due time per request, or one for a command's whole chain of requests: 11 seconds, 13 for a focus read, counted from the moment Core decides to ask, so time spent waiting for an outpost to start counts."
- "The readers keep no deadline of their own and no rule of their own for the user having moved on."
- "Core keeps the committed focus and the readers' last focus as separate facts."
- "Core's logic is written as async functions run on Core's thread ... under five rules: only a request to a reader can be awaited; each request names the type of its answer, which the queue decodes once; every request gets exactly one outcome, so no paused function outlives its entry; the recorder's checkpoint is the state at the front entry's start plus the inputs since, so replay stays exact; and a state dump shows each entry, the answers it has had and the request out."
- "The listener holds every desktop-wide registration ... An outpost holds no WinEvent hook, except a console host's outpost, which keeps the console's five events."
- Its "Limits accepted", taken as stated.

The rulings of 2026-11-15 (Dickson), honoured here: keys and commands join the event queue in this build, caret keys first ruled to keep the outpost's note and poll for one build, a ruling replaced on 2026-11-16 by building the keys-and-text design's caret key here, and a focus judged while a caret key starts or watches making the key silent, as NVDA; Core's reducer owns the single record of an outpost generation, the owner thread reporting process facts as inputs; requests outside the event queue keep their due time and hung check but Core does not stop waiting for them on a foreground change; the backend cache lands in this build, its class lists applied by Core from `docs/parity/backends.md`. What remained of the changes-and-announcements build merges into this build, so that nothing is silent between builds and no interim mechanism is written (Dickson, 2026-11-15); live regions stay later work, as today. His answers to this design's questions, the same day: MSAA change requests, window destruction routed to the outpost and `Follow` named by Core move from the changes-and-announcements build into this build; no below-the-lock-screen test while Verbatim lacks UIAccess, until M8.7, as NVDA; report focus is one request that reads the committed focus node's properties live, as NVDA's `getObjectSpeech` does (`globalCommands.py` 2956 to 2979), a hung window's refusal or stop playing the sound and saying nothing.

Dickson's rulings of 2026-11-16, written into the rules they decide: a caret key whose press-bound field is no longer the focus at its turn runs on that field and speaks its unit after the new focus; Backspace and Control+Backspace with a focus pending speak the deleted text, then the focus, amending the ADR's line for these two keys; a selection compared against its old range as it now is, as NVDA, retiring the replaced-text rule; a UI Automation caret or text-change event within 60 ms of the pass counted as the key's effect, as NVDA; the text box's Delete over a selection kept, its declaration removed after a recapture; the 2026-10-22 wait for the key ahead removed, the next key read at its turn as NVDA; the late-answer rule made uniform; this build's caret key built in this design, which then has no interim caret key; and the decisions of record retired ("Found against ADR 0003 or the build notes"). Rulings of 2026-11-15 honoured: speak exactly what NVDA speaks, no more and no fewer; no feature silent between builds; no interim mechanism written only to be removed; this design's check thread and registering thread exist. The uniform late-answer rule (the goals audit, Dickson, 2026-11-16): every late answer is dropped by number, and a window Core stopped waiting on as hung is re-asked when it answers again.

## The model

Everything a reader hears reaches Core as a tell, in one shape, through Core's inbox in arrival order. The inbox handles at once what NVDA handles before its queue or outside it: answers, due timers, the listener's foreground report, a desktop switch, a change of the lock state, progress facts, readers starting and ending, window destruction, and the speech side's cut and failures. Every other tell, every key and command, index marks and say-all's reads, and the entries Core makes itself, join the event queue at its back.

The event queue is NVDA's one queue (`queueHandler.py` 61 to 69). Its front entry is judged by an async function on Core's thread that reads top to bottom like NVDA's handler for that kind. When the function needs the application, it awaits a typed request to a reader; Core's request table gives the request a due time, Core's shell checks the request's window live for a hang and sends it, and the function resumes with exactly one outcome. Nothing else in the queue is asked meanwhile. When the function ends, the entry is executed or dropped and the next one is taken.

A focus is read only when Core asks. An MSAA focus or foreground tell is read by the application's outpost in one request; a UI Automation focus is read in two requests chained under one due time: the listener reads the element it kept and answers a snapshot and the element's route, then the application's outpost completes the read from the route. The walk up the ancestor chain stops at an ancestor Core already knows, which Core names in the request: the committed focus's ancestors, sent only while the readers' last focus is set. Core judges acceptance, the backend verdict, the duplicate tests, the run's refusals, the menu rules and execution itself, from facts the tells carry and the answers return.

Only Core stops waiting: at the due time, on its shell's live hang check, or when the foreground leaves the request's window. A stop resumes the paused function with "no longer awaited" and tells the reader to cancel, with the reason; only a foreground stop abandons a call in progress. Every late answer is dropped by number; a window Core stopped waiting on as hung is watched, and when it answers again Core re-asks its application's current focus.

Keys and commands are entries too. A key's action is chosen at the press against the hook's published view of the committed focus. Held caret keys are released 150 ms after the press whatever waits ahead of them.

A caret key's life is in three places. The hook holds its stroke and defers later transitions behind it, as today. Core holds the stroke in its stroke line, decides at the key's turn what to ask, sends the stroke, and decides what the key says. The outpost reads the caret, holds the starting point, and watches.

At its turn a held caret key asks one starting read of the node its press was bound to. The answer mints the starting point; Core keeps a copy of what it found (unit, word, line, selection, the text Backspace would delete) and sends the stroke. Unless the key is marked or a focus is pending, Core then sends one watch request naming the starting point, the key's effect test, the poll interval, whether the node's UI Automation events may shortcut the poll, the bound, and what the final read fetches. The outpost checks at once and then about every 10 ms (5 ms in the console host), and in a UI Automation text field other than a terminal a caret (text-selection) or text-change event of the watched node within 60 ms of the pass counts as the key's effect, as NVDA's events do (Dickson, 2026-11-16), and a later one queues a check at once. On the first check or event that shows the key's effect, or at the bound, it makes one final read and answers once: how the watch ended and what the final read found (through UI Automation the check that shows the effect goes on to read the final read's fields in the same program). The final read compares no selection. Core speaks by NVDA's caret scripts: an effect speaks the unit, the line or the deleted text; at the bound movement keys and Delete speak the unit at the caret and Backspace speaks nothing. In a terminal the key says nothing and the final read is a terminal read, handed to the terminal's reading rules. A sentence key whose text has a sentence unit ends its watch at the bound with no final read, and Core sends the sentence move.

A later key, command or braille gesture cancels a watch, and the key says nothing (the ADR); a sentence key in text with a sentence unit still moves by sentence, silently, as NVDA's script does. The key behind it takes its starting read at its own turn, with no wait for the key ahead's effect, as NVDA's next script does (`editableText.py` 94 to 95); typed characters behind are echoed at once. A pending focus cancels a watch too.

Selection keys pass at once and say nothing for themselves. Only a caret tell's read and a focus read compare selections, as only NVDA's caret event and focus do: each names Core's selection baseline, the outpost reports the difference and mints the next baseline, and Core speaks the difference, in general terms when the text-changed flag is set or a value change of the node waits in the queue, and otherwise naming each part as the baseline's range now holds it, as NVDA's caret event compares its old range (Dickson, 2026-11-16). A key's starting read and final read compare none, as NVDA's caret scripts compare only the caret (`editableText.py` 70 to 192); the key's own caret tell, which the ruling of 2026-11-12 already pays one read for, speaks its selection change after the key's words, and its value-change tell reaches Core on the same pipe in Windows' order, so general terms are decided in NVDA's order.

A move by sentence is one request: from the starting point, the outpost reads the paragraph, finds the sentence by Unicode's rules, moves the caret and answers the sentence, or "unsupported" for text with no sentence unit.

The text provider and the details are chosen as today until build 2 ("What build 2 builds").

Changes on objects are judged in Core too: an MSAA name, value, state, description or selection change is told by the listener and, when its window is in the committed focus's ancestry, read by the application's outpost at Core's request; UI Automation property changes come from the `Follow` subscription Core names after each commit; a window's destruction is passed to the outpost of the raising thread's process.

Core owns the outpost generation record; the supervisor's owner thread reports process facts (started, failed, ready, pipe closed or exit, pong) and carries out Core's effects (start, end). The listener's own record stays on the owner thread, with `ListenerReady` and the new `ListenerEnded` sent to Core.

## Rules, each with its reason

### Readers' local drops (the only judging a reader does)

The listener drops, in its WinEvent callback, by NVDA's checks that cannot hang (NVDA: `IAccessibleHandler/internalWinEventHandler.py` 84 to 187; `IAccessibleHandler/__init__.py` 556 to 576; `UIAHandler/utils.py` 438 to 459):

- Object ids at or below the alert object's; location changes but the caret's; the window object read as its client; `EXCEL7` children; the input method candidate window's menu events; a focus on the menu bar or system menu with child id 0 (`orderedWinEventLimiter.py` 60 to 62). Today (`verbatim-ia2/src/hook.rs` 820 to 948).
- A window of 0 becomes the desktop window for every event kind; a non-zero invalid window becomes the desktop window for switch start, switch end, menu end and popup end, and any other event with one is dropped; `MSNHiddenWindowClass` is dropped. NVDA: `internalWinEventHandler.py` 112 to 136, 183 to 187 (corrected from the build notes' wording against NVDA's source; `docs/parity/focus-events.md`, "A WinEvent with no window or an invalid one"). Reason: Core's acceptance rule 8 then accepts the desktop window as NVDA does.
- Show events only from NVDA's six classes (`Frame Notification Bar`, `tooltips_class32`, `mscandui21.candidate`, `mscandui40.candidate`, `MSCandUIWindow_Candidate`, `TTrayAlert`), with a show of `OBJID_CARET` passed for Core's caret rule and only `OBJID_CLIENT` or a positive object id kept. NVDA: `eventHandler.py` 506 to 515; `IAccessibleHandler/__init__.py` 905, 1039 to 1055.
- A ghosted or hung window, for WinEvents and UI Automation senders, live as each arrives; for a UI Automation sender only by its own cached window, so a windowless sender is never dropped as hung at arrival (NVDA: `UIAHandler/utils.py` 446 to 450). NVDA: the same three places.
- A destroy of anything but a window object. Verbatim-only: Verbatim has no object table to clean.
- On the event's own cached class and automation id, with no call and no tell, as today: a terminal text area's UI Automation notifications (`verbatim-listener/src/listener.rs` 1883 to 1888; `verbatim-uia/src/map.rs` 385 to 396) and window-opened events that are not toast candidates (`listener.rs` 1929 to 1936). Verbatim-only (Dickson, 2026-11-16): it judges nothing of Core's and gives the outcome Core's rule would give, without a walk per event on the check thread; amends the ADR's "a reader drops an event only by NVDA's local checks".
- The foreground events of `Progman` and `Shell_TrayWnd` are told as `ShellForeground`, which updates Core's foreground record in the inbox with no foreground entry. NVDA drops these foreground events (`internalWinEventHandler.py` 164 to 171); Core still needs the record so that Windows+D or a taskbar click stops waiting for the old application's requests (Verbatim-only in form).

The listener's limiter merges only: one waiting event per object, kind and raising thread on its pipe, the newest keeping its place. NVDA: `orderedWinEventLimiter.py` 63, 79. Reason: a merge needs no knowledge of the focus; the 2026-11-14 measurement found Core kept up at every load, so no count caps (ruled).

An outpost makes no drop of its own and no hang check before a call; it keeps a limiter for what it still hears (its UI Automation `Follow` events, and a console host's five events).

### The inbox, handled at once

- Answers are routed to their request by number; an answer for no live request is dropped and logged, except the late focus answer below. Reason: one answer path per request.
- Timers: Core keeps every due time on its own clock (request due times, the half-second hang round while a request is out, the 50, 200 and 250 ms delays, held keys' 150 ms releases, the key's 100 ms bound, generation liveness and backoff), and the shell keeps one OS timer for the earliest. Reason: the reducer is pure; one timer source.
- The listener's foreground report updates Core's foreground record, stops waiting at once for every request in the queue whose window is outside the new foreground window's tree or owner chain, resets the application's outpost backoff, and puts a foreground marker at the back of the queue. At the marker's turn the readers' last focus is emptied when the report's window is a top-level window unrelated to the committed focus then. ADR, "A frozen window" (the stop at once) and "The ancestors Core already knows and leaving a window" (the emptying in arrival order), so a waiting duplicate that arrived before the report is still judged against the last focus.
- A desktop switch and the lock state: see "The secure desktop and the lock state". NVDA: `IAccessibleHandler/__init__.py` 1076 to 1077; `core.py` 1026 to 1027.
- Readers starting and ending; window destruction (see "Changes on objects"); a terminal's "changed" tell (handled at once in the inbox; build 3); progress facts; the speech side's cut and utterance failure.
- A mark reached or done speaking joins the queue. NVDA: `speech/manager.py` 594 to 595, 721 to 722.

### The event queue

- One queue; only the front entry is asked. NVDA: `queueHandler.py` 61 to 69.
- Merge: a waiting entry of the same object, kind and raising thread, with no focus-kind entry between it and the arrival, is replaced, the newest keeping its place, so a change is never moved past a focus that arrived between (NVDA merges within one pump, which Core does not have); for UI Automation the key is the element (runtime id) and kind, plus the property id for property changes, and the notification kind, processing and activity id for notifications. NVDA: `orderedWinEventLimiter.py` 63, 79; `nvdaHelper/local/UIAEventLimiter/eventRecord.h` 45 to 50, 62 to 83.
- NVDA's whole limiter runs on the waiting MSAA entries: a foreground tell removes a waiting focus with its window, object, child and thread; the newest four focus-cache entries (foreground tells counted among them) are kept; the newest ten other entries per raising thread are kept, the readers' last focus's own ids exempt but counted; one menu slot for the four menu kinds across threads; a show removes a waiting hide of the same key and the reverse. NVDA: `orderedWinEventLimiter.py` 59 to 128; the exemption follows NVDA's last queued focus (`IAccessibleHandler/__init__.py` 1025 to 1031), so Core judges it on the readers' last focus, not the committed one (corrected from the build notes against NVDA's source). NVDA applies its caps per pump; Core applies them each time an MSAA entry joins, a difference in form only (Verbatim-only: Core has no pump).
- A foreground change ends waiting entries and stops waiting for asked ones whose request names a window outside the new foreground window's tree or owner chain, judged by window, at once. Verbatim-only in form (NVDA's watchdog waits half a second, `watchdog.py` 206 to 232): a switch frees the keys at once. Exempt: entries accepted by something other than the foreground relation, namely toasts, show classes (help balloons and tooltips), MSAA alerts accepted as topmost, and desktop-window events; their hang check and due time still bound them, so a toast waiting behind a slow focus read is spoken after an Alt+Tab, as NVDA speaks it (Dickson, 2026-11-16; amends the ADR's "A frozen window").
- Due time from the decision to ask: 11 seconds, 13 for a focus read, one per chained command, the UI Automation focus's two requests included. Verbatim-only (Core's stop); NVDA bounds a queue item by its watchdog, `queueHandler.py` 65, `watchdog.py` 133 to 162.
- Typed characters behind a stuck entry are echoed at the stop, each as its own entry. Behind a slow window, what is heard matches NVDA's speech in a capture the parent makes (Dickson, 2026-11-15), and no test asserts it until that capture exists; behind a hung window it is Verbatim-only (Dickson, 2026-11-16), asserted as designed. If NVDA is heard saying every character, the echoes are stamped so the fence keeps them; if only the last, the fence as it stands gives that.
- Index marks and say-all's reads are entries; stopping say-all withdraws its queued and running requests; say-all's speech carries its starting key's number. NVDA: `speech/sayAll.py` 364; the stamp Verbatim-only.
- The speech fence: every entry's speech carries the newest key number at the entry's arrival, 0 before the first key, so the speech manager's fence drops speech of entries that arrived before a cancelling key (`verbatim-speech/src/manager.rs` 963 to 967, 993 to 998, 1102 to 1118, read for this design; the manager needs no change; Core today stamps only key speech, `verbatim-core/src/keys.rs` 86 to 105). Verbatim-only: the cut stays on the hook thread at the press, where NVDA queues it (`inputCore.py` 583 to 605); the stamp gives NVDA's outcome, that speech queued before the key is not heard after it.

### Requests in Core

- Every node an answer mints carries its nearest window, which a request on that node names. A queue entry has no window field; only a request an entry makes into an application must name its window, and a command that makes no request, such as report time and date, carries none. Every request that holds the event queue names a window that Core's shell can check live for a hang and the foreground rule can test: the tell window (a run's application's newest candidate's; a UI Automation focus's nearest window from its check), the node's window, the foreground record's for "read the current focus", `Shell_TrayWnd` for both taskbar reads, the target's main window for a tree dump. Reason: a frozen application must not hold the user's keys (ADR, "A frozen window"), and the test is by window, so a hung window of one application does not stop requests to its other windows. The queue's request type takes a window handle, not an option, and acceptance takes a found window, parsed at the tell's boundary into one of found (with its facts), none, or failed, so a request that holds the event queue cannot be built without a window (the goals audit).
- The shell maps a ghost window to its hung window (`HungWindowFromGhostWindow`) and asks `IsHungAppWindow` before sending; a foreground report naming a ghost is mapped to its hung window before the foreground test, so a request to the hung window is stopped as hung, with the sound if attended, and its window, not the ghost, joins the recovery set; a request to a hung window answers "not responding" unsent, as the ADR first wrote, and its window joins the recovery set. While any request is out, the shell asks again every half second for each request out. NVDA: `UIAHandler/utils.py` 438 to 459; `IAccessibleHandler/__init__.py` 556 to 576; `NVDAObjects/window/__init__.py` 34 to 40, 97. A send the shell refuses enters the inbox as that request's answer, so no reducer step re-enters itself.
- The not-responding sound plays once for each request Core refuses, or stops waiting for, because its window is hung, while its application holds attention, with no record of having played. Verbatim-only: today's sound (`verbatim-core/src/shell.rs` 156 to 170).
- Cancel carries one of four reasons: foreground, hung, due time, withdrawn. The reader drops a request not yet started, whatever the reason. Only for "foreground" does a reader abandon a thread still inside the call and start a fresh one; for the other three it leaves the thread alone, so a call's answer still arrives when the window answers again. ADR, "A frozen window"; "withdrawn" is this design's (its reason: an entry ending for a rule of Core's must not cost a thread). The reason in the Cancel also classes a parked worker for `parked_on_hung` (the outpost's own check, its former source, goes).
- The uniform late-answer rule (goals audit, section 4; Dickson, 2026-11-16): every late answer, of every kind, is dropped by number. A window whose request Core stopped waiting for as hung, or refused unsent as hung, joins the recovery set (Table 18): while its application holds attention and the window lives, Core's half-second live check continues on it, and when Windows no longer reports it hung, Core appends one entry that asks that application's outpost for its current focus, naming the recovered window. Its answer is judged as the re-take after a reader's replacement is: compared whole with the committed focus by `reads_the_same`, the same taken silently, a different focus executed and spoken; for a UI Automation answer, a runtime id equal to the readers' last focus's is the duplicate test's answer, since the read is of the current keyboard focus (NVDA: `UIAHandler/__init__.py` 902 to 923; nothing is replayed after a hang). When the focused terminal is in that window, Core also sends its `Follow` again, and build 3's Table 1, column J, reads it: a terminal waiting for its window, or baselining with no baseline out, is sent its baseline; a modelled one's reading takes its Table 2, column K. So a terminal whose `Follow` or read was stopped as hung is read again without a new commit, which a re-ask finding the same focus does not make. So a focus is spoken when the hang ends, up to about half a second plus one read later than the call would have answered, and it is the current focus, as NVDA's handler finds it (NVDA reads the focus live once its call returns; nothing is replayed, `docs/nvda/main-loop-and-watchdog.md`, "When an application stops responding"). Reason: one path in place of three special send paths and per-kind late policies, which drew nine review findings.
- Requests outside the event queue (Verbatim's dialogs, the control plane, the tree dump, the taskbar list's two reads, a terminal's output reads (build 3); later an extension host's reads and M4.3's spelling check) have the same due time and live hang check, hold no key, and and Core does not stop waiting for them when the foreground changes (ruled 2026-11-15). Reason: the notification-area list sends its click-position read as its dialog closes and Windows then activates another window (`verbatim-gui/src/tray_list.rs` 142 to 168), so a foreground stop would always stop the click. They are answered through the inbox to their responders by number and never awaited by an entry's function, so the async rules' "no paused function outlives its entry" and the checkpoint are untouched.
- A paused function always ends through its own code: a stop resumes it with "no longer awaited"; an answer that does not decode resumes it with "refused, undecodable", logged as the reader's fault, and does not replace the reader (ruled 2026-11-14).

### The narrow ordering rule, and what the Settings combo box recording shows

When the answer that completes a focus read arrives (for a UI Automation focus, the outpost's completion, just before execution) and its ancestors include the committed focus by runtime id, Core first judges the committed focus's waiting UI Automation state tells, in their order, then takes the focus; name and value changes are not moved. Verbatim-only (ADR, "The narrow ordering rule"): the listener's and an outpost's events come from two processes with no order between them.

The `verbatim-event-record` recording of the Settings "Show additional calendars in the taskbar" combo box, opened with Alt+Down Arrow and closed with Escape (two rounds, Settings' Date and time page, process 5548) gives the order the rule works on:

- Opening (Alt+Down Arrow): an MSAA focus on the `Windows.UI.Core.CoreWindow` (object 6, then 35) comes 6 to 12 ms first; then UI Automation `ExpandCollapseState` 1 on the combo box and the UI Automation focus on the list item, 0 to 2 ms apart, the expanded change first both times; then a Name change on the list item (second round only, to an empty name, 1 ms before its focus) and structure changes.
- Closing (Escape): the MSAA focus and the UI Automation focus on the combo box in the same millisecond; a Name change on the list item 3 ms later (first round); `ExpandCollapseState` 0 on the combo box 20 to 21 ms after the focus (3.053 then 3.073; 5.593 then 5.614).

Under this design:

- The MSAA focus on `Windows.UI.Core.CoreWindow`: that class is on neither of NVDA's lists (`docs/parity/backends.md`, "The class lists the per-window verdict reads"), so the verdict comes from the probe, not the class. With no verdict in force (the last probe began more than half a second earlier, which holds between the recording's rounds 1.5 seconds apart), the run's request to the outpost probes first, finds a provider and answers "read through UI Automation", which Core treats as the drop. The UI Automation focus that follows is judged by the verdict now in force and read. NVDA probes at the same point (`IAccessibleHandler/__init__.py` 577 to 582, `isUIAWindow` with its half-second cache, `UIAHandler/__init__.py` 1368 to 1381). Cost: one request and one probe before each Settings focus change whose window's verdict has lapsed, while the 6 to 12 ms gap usually hides it; measured in this build.
- Opening: the expanded change on the committed combo box is told by the outpost's `Follow` (the combo box is the followed committed focus), the list item's focus by the listener. - One generic read replaces the event-referenced kinds (goals audit, section 5): "properties of the object an event names, by property set, optionally reading up its ancestors until it reaches an ancestor Core already knows". Its fields: the object (a kept token, MSAA window, object and child ids, or a held node); the property set, which can name a relation to named nodes (the committed focus or one of its ancestors, or inside an object the focus controls) and an alert's descendants; whether it reads up to the ancestors Core already knows; its purpose, focus or other, a focus read naming the readers' last focus's token to keep (Table 6) and making its element "read, not yet named"; and the window it names. It replaces the listener's reads of a focus event's kept element and of a menu opening, the desktop's name, a toast's or alert's text and a UI Automation selection's item, and the outpost's MSAA menu opening, "is this event's object one of these nodes, read these properties", a tree item's child count, a selection's item with its relation, and an alert, help balloon or tooltip as a snapshot with descendants. The completion of a UI Automation read from the listener's route (a focus's, adding its `Follow` registration first, or a selection's item, minting a node with its relation to the focus), the MSAA run, the current focus, the caret reads, the watch, the sentence move and the terminal reads keep their own kinds, each for the reason the audit gives.

### The focus answers

The focus requests and what each answer carries, from the build notes' list of what Core keeps with the committed focus and the rules above (`verbatim-model`'s `request` module):

- The listener's focus read is the generic read with purpose focus; its answer adds the element's route: the element's nearest window, the element and each ancestor it read, nearest first, each with its runtime id, its own window when it is a window's element and whether it is a control and content element, and where the chain goes on (at the top, at an ancestor Core already knows or the process boundary; on from a window's own object; or by plain windows from a window).
- The completion of a UI Automation read names the route, what the listener read of each element on it, the property set, the ancestors Core already knows and what it completes: a focus, whose `Follow` registration comes before its states are read, or a selection's item, with the committed focus whose controller-for relation it reads live.
- An MSAA run names one application's candidates newest first, each by its event's ids, whether it is a foreground candidate and its window's verdict, with the property set and the ancestors Core already knows; its answer lists each candidate tried, in order: skipped (read through UI Automation), refused with its reason, not there, or the valid focus, which ends the list.
- The current focus names the property set and the ancestors Core already knows.
- A focus answer, for the completion, a run's valid focus and the current focus, carries: the focus node (its node id, nearest window and properties by the set, its rectangle, states, name and value among them, and its runtime id when it is a UI Automation node); the MSAA ids it was read by with the held child id; the focused child's ids when a redirect reached it; its ancestors nearest first up to the ancestor met, each a node with whether it is a simple child and its dialog text when it is a dialog the walk read; which known ancestor the walk met; the foreground window it entered under, when it could be read; whether its value comes from its selection; its class verdict (only "plain" until a class with rules of its own is read); and whether its runtime id named another element before.
- Every request carries its window's verdict: UI Automation, MSAA, or "probe first" when none is in force (Table 4, column D); every answer carries the probes the request made, each with its window, the window's owning thread, whether a provider answered and when the probe began, and Core records them. A completion refuses "read through MSAA", and an MSAA read "read through UI Automation", when the probe finds the other backend.

### The test harness's idle

Every reader idle by its own definition; the event queue empty; no request out or waiting for its outpost; no key held by the hook or waiting in Core; no lock key announcement to come; no terminal quiet-period timer armed; no 50, 200 or 250 ms timer due; and, from build 3, the focused terminal quiet (not baselining, waiting for its window, or reading), no speech entry waiting and no colours owed. The live hang check counts only while a request is out, and the recovery set must be empty.

## How the code is organised

Each feature's code sits together in its own module; the queue holds only what crosses features (ruled 2026-11-14). In `verbatim-core`:

- `event_queue/`: `mod.rs` (entries, waiting and asked, the front, the merge), `limiter.rs` (NVDA's limiter on MSAA entries, runs, the menu slot), `driver.rs` (the async driver on Core's thread: `ask`, the run-time check that only an ask pauses, checkpoints at the front entry's start, the dump of each entry's answers and request out), `request.rs` (the typed request trait and `Outcome`).
- The queue's place in the reducer: ADR 0003 decides it ("the recorder's checkpoint is the state at the front entry's start plus the inputs since, so replay stays exact; and a state dump shows each entry, the answers it has had and the request out"). `SrState` holds only plain, copyable and serializable data: the queue's entries, and the front entry's checkpoint, the state at its start with the answers it has had. The live paused function sits in a runtime part beside it that is never cloned or serialized; a clone, a restored dump or a replay rebuilds it by running the front entry's function again from the checkpoint's state with each recorded ending, and checks that it asks the recorded requests. The paused function shares Core's state by reference, so it is not part of `SrState`: it sits in a `Runtime` beside it, owned by whoever runs the reducer (the reducer thread's loop in `verbatim-app`, the replay, the tests), and passed in by `reduce(&mut SrState, &mut Runtime, &Input)`; a runtime without the function, after a clone or a restored dump, rebuilds it from the checkpoint before the next input. Core keeps no hidden state and uses no thread. `entries.rs` holds the queue's entries over `SrState` and which feature's function runs each.
- `requests.rs`: Core's request table, due times, stops, late answers, requests outside the queue (replacing `queries.rs` and the shell's table).
- `inbox.rs`: everything handled at once.
- `announcements/`: one module per kind (`notification.rs`, `toast.rs`, `selection.rs`, `alert.rs`, `show.rs`), each an async function on its entry.
- `changes.rs`: MSAA change entries, their request, the state, name and value rules; `follow.rs`: `Follow` named after each commit; window destruction in `inbox.rs`.
- `focus/`: `mod.rs` (the two versions and what Core keeps with the committed focus), `acceptance.rs`, `backend.rs` (the cache and class lists, with the class-name normalization), `duplicate.rs`, `msaa_run.rs`, `uia_focus.rs` (the two chained requests), `menus.rs` (the slot, the check after an end, the UI Automation menu opening), `execute.rs` (commit order, ancestors, foreground object, desktop name), `narrow.rs`, `retake.rs`, `pending.rs` (the pending-focus tests).
- `keys/`: `entry.rs` (choice at the press, marks, release timers, the fence's numbers), and the keys-and-text modules:
  - `verbatim-core/src/keys/`: `strokes.rs` (the stroke line, its send and exit effects, M4.8's reader), `caret_key.rs` (Table 7, one async function per key: starting read, pass, watch, words), `sentence.rs` (the request and its words), `words.rs` (each key's script words, from today's `editing.rs`).

  - `verbatim-outpost/src/text/`: `check.rs` (a check per provider), `caret_read.rs` (the starting, caret-tell and final reads), `sentence.rs`; `text_reads.rs` loses the note; the waiting table's high-resolution timer beside the worker.

## Limits

The ADR's "Limits accepted" hold as stated. Added or sized here:

- In a window whose verdict has lapsed, an MSAA focus copy that arrives before its UI Automation focus costs one outpost request and one probe before the UI Automation focus is judged; the 6 to 12 ms gap in Settings usually hides it.
- A walk that fails drops the focus: for a hang of 10 to 20 seconds NVDA, whose walk waits UI Automation's default 20 seconds (`docs/nvda/main-loop-and-watchdog.md` 120 to 122), speaks the focus when the application answers, and Verbatim, with its 10-second transaction timeout, does not (Dickson, 2026-11-15).
- Closing the Settings combo box when the check takes longer than the 20 ms before its "collapsed": "collapsed", then the combo box's announcement with "collapsed" again; in general an old focus's change raised after a new focus event can be spoken before the new focus, since the focus's tell waits for its check. Accepted, matching NVDA's own race (Dickson, 2026-11-15); revisited if the measured checks there exceed about 20 ms.
- The check thread and the reading thread can both be inside one application, as NVDA's handler and main threads can: a second exception to the ADR's one caller, beside the registering thread.
- A hung application stalls its own later UI Automation events, up to UI Automation's 10-second transaction timeout per call; other applications and keys are unaffected.
- The tell is delayed by its check, and a key pressed meanwhile acts on the previous focus, as in NVDA.
- One more thread per application whose UI Automation events the listener hears, let go when idle.
- A check thread's record is keyed by process generation at the callback; an event from a new process reusing a process id, arriving before the old process's exit is known, goes to the old record and is dropped untold when that generation ends.
- Report focus while the committed focus's reader has ended, before the re-take answers: the node is not there, so nothing is said, where NVDA speaks its object.
- With the listener not holding the earlier element, a UI Automation focus is not a duplicate.
- After any stop of a run's request (hung, due time or foreground), its older candidates are not tried, so a responsive application's older candidate behind a hung one is lost.
- A window whose foreground lags more than 20 ms behind its event: its focus is judged against the old foreground and refused, as NVDA after its two cycles. Every tell is held up to 20 ms behind a lagging foreground.
- A state change of the old focus that reaches Core after the completion's answer is spoken after the new focus ("Don't show additional calendars 1 of 3", "expanded").
- A request from outside the queue already running on an outpost's worker is not preempted by the queue's request.
- A waiting MSAA entry named by ids can be read in a reused window handle after its window was destroyed; NVDA shares this.
- On Windows 11 21H2 property changes are followed on the focus and its ancestors only, where NVDA registers them desktop-wide.
- A held key whose entry ends at a foreground stop reaches, in press order, the window now in front, not the one it was pressed in.
- A Settings combo box's collapse raised after its focus is unsaid because "collapsed" was already spoken; if the focus read ran before the provider collapsed, "expanded" then "collapsed" (as in NVDA).
- The generation's replacement may start while the old process retires (today's; M6.2 bounds it).
- A classic edit control's key is found by the poll alone, since no outpost hears its caret events, where NVDA ends on the system caret's event: its speech can come up to about 10 ms later than today's, measured below, and a key whose caret event comes with no move speaks at its bound, 100 ms later than NVDA, with the same words.
- In a UI Automation field, an event raised within 60 ms by something other than the key ends the key as its effect, as in NVDA, so the key speaks the unit at the caret then.
- A held key read at its turn behind a key the application has not yet handled starts from the caret before that key's move, and may speak a unit that follows from neither, as NVDA's does; only for keys pressed faster than a person types, measured below.
- An unheld selection key just before a held key can still be read late by the held key's starting read; that changes only the held key's starting point, not any selection word, as in NVDA.
- A watch cancelled while its final read runs costs that read, dropped.
- A key run on an earlier field holds the event queue's front for its whole bound, since that field's caret never moves (ruled 2026-11-16).
- A request from outside the event queue running on the worker (a tree dump, a dialog's read) delays a watch's checks; it is not preempted.
- Selection keys in a burst are reported as one change when their caret tells merge, as NVDA.
- A selection change waiting while a focus becomes pending is not said, as NVDA.
- Checks per key that moves nothing: 10 in a text field, 20 in the console host, 30 in an older console host and in Windows Terminal.
- A Windows Terminal key that moves nothing delays output told behind it by up to 200 ms more than today.
- Enter's new-line text is not announced (NVDA's `script_caret_newLine`), a gap this build does not change.
- Until M8.7 caret keys in an elevated window are unheld and say nothing.
- The uniform late-answer rule: a recovered focus is spoken up to about half a second later than its call would have answered; a read to a window slow but never reported hung, past its due time, is dropped and not re-asked.
- Until M8.7: a secure-desktop switch says nothing beyond the cut; no lock-screen gate on scripts and no below-the-lock-screen test.

## What build 2 builds

The keys-and-text design's caret key, stroke line, watch, held anchors, selection baseline and text-changed flag, sentence move, recordings, rulings, speech, tests and removals are in this design. What remains, none of it needed for this build to work, is build 2 (`docs/design/readers-tell-core-asks-build2.md`): text requests naming the provider and the details per request, with `CoreToOutpost::Fetches`, the theme broadcast and `fetches_sent` removed; the formatting last spoken and the kind of line break kept on each focus record a key or entry names; and control fields compared by the provider's identity, when built. Until build 2 the outpost chooses the provider by window class and reads the details `Fetches` names, as today, and Core sends `Fetches` as an effect ("The outpost generation record").
