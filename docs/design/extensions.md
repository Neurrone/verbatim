# Extensions: the design

The design of Verbatim's extension system, the equivalent of NVDA's app modules, add-ons and synth drivers, settled on 2026-10-22 and restated with Dickson on 2026-11-09. It is implemented by M5 ([work plan](m5-extensions-work.md)) and, for native speech engines, M6 ([work plan](m6-native-synth-work.md)). D6 in the architecture is the decision of record; this document is its detail. Where a sentence carries a name and a date, it is a decision Dickson took and is not reopened without new evidence.

The surface as extension authors see it, every manifest key, matcher form, rule action, hook, event kind, import and install dialog line, is the Extensions guide's reference (`books/extensions/src/reference/readme.md`), and the WIT files in `verbatim-ext-api` once they exist, from which that reference is generated. This document does not restate it: it records how the surface is implemented and why.

## 1. Terminology

- An **extension** is the installable unit: one `.vext` file, a zip its author makes by hand holding an extension manifest, locale files and one or more module folders. NVDA's add-on.
- A **module** is one contribution inside an extension, of a **kind**: an **app module**, bound to one or more applications and active while such an application has an outpost; a **global module**, bound to none, one instance for the session, reading only the applications its manifest's `reads` names; or a **synthesizer**. Speech-text stages, recognisers and braille drivers are later kinds.
- A **built-in** is a module folder that ships with Verbatim under `extensions/builtin/` (planned). The built-ins together are one internal extension, loaded and run as an installed one is, but never listed, installed or disabled by the user.
- A **rule** is a matcher and an action Verbatim applies itself, without calling the module; a **hook** is a function a module exports and Verbatim calls, with a deadline.
- A **capability** is a WIT interface a component imports, derived from its imports and never declared.
- The **host** is the process running one extension's modules, `--extension <id>`; a **lane** is one thread in it, one per outpost it serves and one per global module.
- The **loader** is a thread of Core's that reads, validates and compiles extensions and reports each result to the reducer.
- A **generation** is one publication by Core's reducer of the merged rule tables, hook registrations and gesture map of every active extension; every judgement a reader makes names the generation it was made under.
- A **hook call** is one call of one hook in one layer, named by an id the outpost or Core mints; a read the hook makes names its call.

## 2. Extensions, modules and built-ins

### 2.1 One folder layout

A module is always a folder containing `module.toml` and, unless the module is rules only, a component named in it. A built-in is that folder under `extensions/builtin/` (planned) with no extension manifest of its own, its strings in Verbatim's own Fluent resources. An installed extension is a `.vext` zip with `manifest.toml` at its root, a `locale/` folder and its module folders; there is no packaging tool, and the guide documents the zip (Dickson, 2026-11-09). Install extracts it to `extensions/<extension id>/` under the configuration root, the user's profile for an installed copy and beside the executable for a portable one, first into a hidden staging folder beside its destination, renamed into place only once every file is written and checked ([security model](security-model.md), X13). The loader has one code path for a module folder wherever it finds it.

### 2.2 Loading, the developer folder and hot reload

The loader thread does all file and processor work: it reads folders and `.vext` files, parses and validates manifests and rules with `verbatim-ext-api`, reads each component's imports to derive its capabilities, and compiles the merged rule tables with `verbatim-reader-rules`, then has the extension's host compile and pre-link its components. The supervisor starts the host for that compile when it is not running and ends it after, and a host that ends during the compile answers the loader "failed: host ended". For each extension the loader reports two results, each final and never a step in between: its rules, validated and compiled into tables, and then its code, compiled and pre-linked; either can instead be failed with its reason. The rules come first because compiling the built-ins on a cold cache takes seconds, and no application may be read without its rules meanwhile. Conflicts are decided by the loader from the whole set of manifests a scan found, never by the order results arrive: of two installed extensions claiming one application (a folder copied by hand) or two developer-folder modules claiming one, the later in ordinal order of their ids fails; a module found once Verbatim is running fails when it conflicts with one already loaded.

The reducer owns each extension's lifecycle as one state value, in the table below. Its inputs are the loader's results, the user's enable and disable, the breaker's verdicts and the supervisor's reports of a host's end. From every extension's state it publishes a generation: rule tables and hook registrations to the listener and the outposts, and the gesture map to the keyboard hook thread. A host is sent no version, since each call names the version it runs (below). The supervisor's owner thread writes every configuration a child process receives, its first and each later one, so each child's configuration has one writer (`m5-build-a.md` section 9). A spare outpost's assignment carries the current generation, so its first event is judged under the tables. Each reader takes a new generation at a boundary in its intake, and every judgement names its generation. One focus can pass the listener's veto under one generation and the outpost's rules and hooks under the next; each judgement stands under its own, and Core acts on a judgement from a generation it has moved past by its kind: a veto's drop stands, since a dropped event cannot be read again; an effect of a module whose extension is now `Disabled` or `Failed`, or of a built-in module now turned off, is dropped; anything else is used. During a reload the code version travels only on the call: an outpost's call names the version its event's generation registered the hook under, and a call Core makes names the extension's version in Core's record. A lane runs a call on an instance of the version the call names, or on its own instance when that is newer, so a lane never goes back; when that newer instance's module no longer exports the hook or no longer registers it for the call's subject, the lane answers the call `pass` or no change without calling into the guest, and the breaker counts nothing, since the newer version did not fail. It drops an instance of an older version at the first call naming a newer one, which needs no acknowledgement since a lane serves one outpost. The host keeps in memory each version a lane holds an instance of and the newest it compiled; a lane's first call naming any other version loads that version's pre-linked code again from the compiled-code cache, where the loader's compile left it, so no call is refused for its version. A reload that fails at any step leaves the previous version everywhere.

| State | Data | Published | Left by |
|---|---|---|---|
| `Loading` | none | nothing of this extension | its rules result, to `RulesReady` or `Failed` |
| `RulesReady` | version, tables, hook registrations | its tables, and its hook registrations marked code pending | its code result, to `Active` or `Failed` |
| `Active` | version, tables, hook registrations; for the built-in extension, the set of its modules the breaker turned off | its tables, and the hook registrations of every module not turned off, marked ready | a reload, which keeps both new results until both arrive and then publishes them together, or keeps this version if either failed; the user's disable or the breaker, to `Disabled` |
| `Failed` | reason | nothing of this extension | a reload in developer mode, to `Loading` |
| `Disabled` | by the user or by the breaker | nothing of this extension | the user's enable, to `Loading` |

The rules that read it: the supervisor's relay holds the listener's `Ready`, which does not reach Core's reducer, and so input, until the built-in extension has left `Loading`, so the first focus is judged with the built-ins' rules; hook registrations are declared in the manifests, so they are published with the rules and marked code pending until the code result, which marks them ready or, failed, removes them; newer rules that replace those held in `RulesReady` remove the older version's pending registrations, publishing the newer version's as code pending; and an event matching a pending registration waits for its code as it waits for a host not yet ready (section 4), so the first focus of a cold start waits for its hook; the breaker turns off a built-in module by adding it to `Active`'s set and an installed extension or developer-folder module by `Disabled`; an effect is judged against the state of its module's extension as above; `RulesReady` is reached only at a first load, since a reload publishes rules and hooks of one version together.

The developer folder is watched, with the built-in folder, only in developer mode, and works as one extension, as the built-ins do (Dickson, 2026-11-09): its module folders, with a `locale/` folder for their strings and no extension manifest, are loaded as one internal extension, run in one host of its own, and counted by the breaker per module, as built-ins are. Its modules claim applications as an installed extension's do, so no two of them claim one application. A developer-folder module that claims an application an installed extension claims replaces that extension's module for that application only, while it is there, as NVDA's scratchpad does (`addonHandler/packaging.py`, `addDirsToPythonPackagePath`), so an author can work on the next version of an installed extension (Dickson, 2026-11-09). A developer-folder DLL is loaded from a copy in the compiled-code cache, named by its content, never from the folder, so a build can overwrite it; since a DLL cannot be unloaded safely, a changed DLL restarts the developer folder's host with the new copy (Dickson, 2026-11-09). Speech says "Loaded <module>" for a module that appears, "Reloaded <module>" for one that changed, or "Reload of <module> failed" with the first line of the reason (Dickson, 2026-11-09).

A built-in failing to load is a defect or a damaged install, logged and spoken at once, unscheduled, as "Built-in module <folder name> failed to load", or "Built-in modules failed to load" when the built-in folder cannot be read; installed extensions' failures are one sentence, "<n> extensions failed to load", with each marked failed in the Extensions dialog. These sentences become Windows toasts with M8.6 (Dickson, 2026-11-09).

The Extensions dialog, in the Verbatim menu before Preferences (Dickson, 2026-11-09), has, in tab order: a list view of the installed extensions with the columns Name, Version, Author and Status (Enabled; Disabled; Turned off after repeated failures; Failed to load; Partly loaded; Overridden for <application> by the developer folder); the selected extension's description; its Applications, Commands and warnings lists, as the install dialog shows them; and the buttons Install from file, Enable or Disable as the selection's state needs, Uninstall, and Close. Enable, Disable and Uninstall take effect at once, Uninstall after the question "Uninstall <extension name>?". In developer mode the list also shows the developer folder's modules, read only, with their rules, hooks and imports; built-ins are never listed.

### 2.3 Secure mode

Secure mode (M8.7) loads only a machine-wide copy of the extensions the user allowlisted for secure screens, an allowlist of plain data, made by an elevated step into a folder the installer made readable for the hosts' containers, as NVDA copies selected add-ons into its system configuration (`config/__init__.py`, `_setSystemConfig`); installation, the developer folder and the console are disabled there. Allowlisting is the user's consent, and the allowlist dialog shows the extension's warnings as the install dialog does (Dickson, 2026-11-06). An extension on a secure screen writes only a scratch folder, deleted when Verbatim exits.

## 3. Binding a module to an application

Application identity comes from a fixed core table: the executable name; for a console window, the console client's executable; for `wwahost.exe`, the hosted application's name from its application user model id; for `msedgewebview2.exe`, the parent process's executable. The listener resolves it once per process, with one image-name query from a process handle it holds, so window and event rules apply before any outpost exists, and sends it with the first fact for that process; the supervisor uses that identity rather than resolving its own (section 14). The listener's cache is keyed by the process id with the process's creation time, and an entry is dropped when its process exits, so a reused process id never carries another executable's identity. From the listener the identity travels one path (`m5-build-a.md` section 4.2): the listener sends `Process { pid, identity }` ahead of the first message naming a process; the supervisor keeps it in its record of the application and writes it, with that identity's slice of the rules, in the outpost's first command (`Configure` for an outpost launched for the application, `Assign` for a spare) and in `Started`, from which Core's reducer keeps it in its record of the outpost; an outpost wanted for a process no message has named first waits while the supervisor asks the listener (`Identify`). Core's reducer knows the focus's application as the process and identity of the outpost that reported its committed focus, and publishes it to the keyboard hook thread (section 4, "Commands"). Verbatim's own process is the one exception: Core states its identity, `verbatim`, and the listener records it rather than resolving it. So an outpost holds only its own identity's rules and looks nothing up by identity, and the listener looks up its slice by the identity in its record of the event's process. A module's `applications` list is NVDA's alias table in the module's own manifest.

At most one installed extension claims an application, above the built-in, and no two modules of one extension claim the same one; a second is refused at install, so installed extensions need no order among themselves (Dickson, 2026-11-09). A host runs one instance per process of a claimed application, on the lane of that process's outpost, as NVDA keeps one `AppModule` per process; the instance's memory is its state, lost on reload or fault. When an outpost is replaced for the same process, the instance moves to the new outpost's lane with its lane record, and the nodes it held come back `gone`, since they were the old outpost's. A global module has one instance on a lane of its own, and its reads reach only the applications in `reads`; a read that only Core can route goes through Core's reducer (section 14).

## 4. The surface, as implemented

The surface is the guide's reference. These are the implementation rules behind it.

- **One matcher grammar,** one type, parser and evaluator in `verbatim-ext-api`, serving rules, hook registrations and the find reads; legality per use is a check at load. Window and event rules need a property named directly at the top level, so they compile to hash tables and stay one probe per event.
- **Rules are placed by the loader from the properties they name:** a focus veto naming only what the listener's event shape (`ListenerEvent`) caches runs in the listener before its read, and also in the outpost on every focus the outpost reads itself (the read after a menu or the task switcher ends, a replacement outpost's current focus, the read after the listener is replaced); any other focus veto runs in the outpost on the read node. An event drop runs in the first reader that has its properties, and otherwise in Core; node rules and redirects run in the outpost's worker as it emits a snapshot; window `backend` where a reader first reads the window; `normalize-class` in every reader that evaluates `window-class`, the listener included, so a rule naming a normalized class matches wherever it is placed; `silent` in Core's reducer, and `accept` in the outpost's worker before Core, as it tests each event it takes.
- **Hooks are called by the outpost's reducer, and no worker waits on a host.** The outpost reads the host pipe as it reads Core's, and every message on it, a host's readiness, a verdict, a read or an effect, is a reducer input naming its hook call. `on-node` runs as the outpost emits a batch, after the node rules; `on-focus` after the listener's read, the node rules and `on-node`; `on-event` after the rules. Each read is an ordinary program for the worker in charge, named by its call; when the call ends, a read of it not yet started is withdrawn and answered `deadline`, and one already running finishes and its answer, naming an ended call, is dropped by the host; reads are dispatched in arrival order whichever call they name, since holding another call's read behind a pending hook deadlocks a click made from a list dialog's answer against a hook queued on the same lane. Core's queries are dispatched meanwhile too. The chain's resolution between layers is a pure function in `verbatim-outpost-logic`, called by the reducer on each verdict. `status-bar` and an app module's `on-command` are resolved by Core's reducer and run through the outpost in key order; a global module's `on-command` and every `on-list-dialog` go from Core's reducer straight to the host, which bounds them by the same one clock.
- **A hook call has one clock, its host's.** The call carries its deadline as a duration, and the host's lane counts it from when it starts the call: past it, the epoch callback traps guest code, and a read the guest waits on is given up; the lane then answers the call `deadline`, which counts as `pass` or no change. So every call is answered, and its caller, the outpost's reducer or Core's, keeps no timer for it and waits for the answer or the end of the host's pipe. Reason: timed on both sides, a call the outpost had given up still ran on its lane, and the next event's call waited behind it with its own deadline already running, so one overrun timed out the next event's hook too.
- **A stalled host is ended, by one liveness bound its caller keeps.** The host's clock cannot stop a lane stuck where epoch interruption does not reach, in a native library called through the narrow import or in the host's own code, and the host's other lanes keep its pipe open, so without a bound the stuck lane's outpost would wait for ever. So the caller of each call, the outpost's reducer for the calls it makes and Core's reducer for a global module's `on-command` and every `on-list-dialog`, keeps one alarm while it awaits a call, `stalled_at`: the call's sending plus the handling deadline plus the liveness grace. The alarm never answers the call: it reports the host stalled, the outpost by `OutpostToCore::HostStalled { host, call }` and Core from its own alarm, and Core's reducer has the supervisor end that host's process (its generation named, so a report about a host already replaced is dropped); the end of its pipe then answers every call in flight on it, by the rules for a broken pipe. Because the bound lies the grace past the host's own clock, a host that keeps its clock always answers first, so the two never judge one call. The breaker (security model, A9) counts an end at this bound as a failure to respond against the module whose call stalled, a built-in module included, since unlike a crash the stalled call names it; the host is restarted with the outposts' backoff. The grace's figure is Dickson's to set (proposed: 2 seconds, so a stalled hook leaves its application silent for at most 13 seconds).
- **Reads** are bindings over the outpost's own readers, so a module sees what its outpost sees; every navigation stops at the application's boundary, checked by the node's process in one place, and the outpost judges each request by the pipe it arrived on, so the extension is the unit whose reach is enforced. For `on-focus`, `properties()` and the ancestor reads are answered from the chain the listener's read carried, and the outpost finds its own element by the chain's runtime ids only at the first read that needs a live call, so a hook that reads nothing more adds no re-find before the report.
- **Effects** made during a hook the outpost called (speech, `speak-node`, `cancel-speech`, tones and browseable messages) travel back with its verdict on the host pipe, and the outpost forwards them to Core inside the event's report, in call order, so a module's speech and the event it was spoken for reach Core in one message, in NVDA's order; Core judges them by attention. Effects of a hook Core called, a global module's `on-command` and every `on-list-dialog`, go from the host to Core, their only sender, and so do logs. Every `on-command` call carries its press's key number (`KeySeq`), and every effect of the call is stamped with it, so Core's fence on expired gesture speech drops the speech of a press a later key superseded; during `on-command`, `cancel-speech` acts while its press is the newest key, for a global module as for an app module. `speak-node` carries the snapshot of the node the host holds, so a later release cannot empty it. A list dialog is recorded by Core's reducer, which sees every press in key order and every command's answer, and shown by the GUI thread. For a click, the host reads the node's place from its outpost, a read like any other, and sends Core the click with the rectangle read; Core moves the pointer and clicks from a shell thread, as the tray list does today, and never queries an outpost on a module's behalf.
- **Commands:** a binding names a number of presses, and every press fires at once. The keyboard hook thread alone judges whether the same keys are bound to a higher count, from the gesture map it resolved the press with, and only then stamps the raised gesture with `hold_until`, when its multi-press window closes. An app module's commands follow the focus, as NVDA's do: its scope is active while Core's committed focus is in one of its applications, as NVDA looks up the focus's app module after the global plugins (`scriptHandler.py`, `_yieldObjectsForFindScript`, 178 to 185; Dickson, 2026-11-10). The focus's application is the process and identity of the outpost that reported Core's committed focus, or, when Core accepts a foreground change into another application's window after it, that window's process and identity from the `Foreground` report, until the next committed focus, as NVDA maps the foreground event to `gainFocus` (`IAccessibleHandler/internalWinEventHandler.py` 36) and so moves its focus object, and with it the app module, at once; so moving to a window Verbatim cannot read, such as an elevated one before M8.7, ends the bindings of the application left at once. The hook thread reads it from Core's lock-free view with the key's one load, whatever window is in front, and names it on the gesture; Core routes an app module's `on-command` to that process's outpost without judging the focus again. Between the focus moving to another application and Core's committing it or accepting its foreground change, a press resolves against the application of the focus Core committed last, as NVDA's resolves against its focus object until its main thread has handled the new focus, so a gesture bound only by the new application's module reaches that application then, as in NVDA (Dickson, 2026-11-11: match NVDA unless that is proven impossible or too costly). A press bound in an active scope is resolved before the caret table is consulted, so a module that binds a caret key takes its hold away: the press is raised as the module's command and never held, with no before read and no caret speech of Verbatim's, as NVDA runs the app module's script in place of the caret script it would have found later on the focus. Passing it through, by `pass-through = true` or `pass-through()`, sends the key on unheld and does nothing more, so only the module's own reads and speech follow it (`m5-build-a.md` section 10). Core starts a module's `on-command` only once every held key ahead of its press has been passed on and has its result, as it runs its own commands ([holding caret keys](../../books/dev/src/explanation/design/key-holding.md), "Keys behind a held key"), so a module's command, a caret key's included, never reads before a held key ahead of it has reached the application and been read after. A list dialog a command opens is `Held` in Core's reducer's record until the later of `hold_until` and the answer of every later press of the same keys raised before then, so a double press never shows the first dialog, however slow the first command (Dickson, 2026-11-09; its record moved from the lane to Core's reducer, 2026-11-11). `trigger.declared` names the binding a press resolved to, which a user's change of gesture keeps.
- **Node handles** are component-model resources owned by the instance; the host reports the nodes it holds, so the outpost keeps their elements alive, and an outpost is not retired as idle while a host holds any of its nodes.
- **Gesture conflicts** are listed in the install dialog, not refused (Dickson, 2026-11-09).
- Accepted: a module may remove the protected state, where an application sets it wrongly; the provenance names the module that did.

The outpost's reducer holds, for each host it serves, the host's pipe as `Waiting` until the host reports that its lane and the instance are ready, then `Ready`, and the hook state as one value: `NoHook`; `AwaitingHost { lane, layer, until }`, a hook due whose host's pipe is `Waiting` or whose registration is marked code pending; or `AwaitingHook { lane, call, layer, stalled_at }`. No state holds a call's deadline, which only the host counts; `stalled_at` is the liveness bound above, which ends the host rather than the call. Each cell says what the rule does in that state.

| Rule | `NoHook` | `AwaitingHost` | `AwaitingHook` |
|---|---|---|---|
| An event from the intake | judged; a registered hook whose host's pipe is `Ready` and whose registration is ready starts a call, to `AwaitingHook`; one whose pipe is `Waiting` or whose registration is code pending, to `AwaitingHost`. For a pipe `Waiting`, `until` is the host's measured start-up time within the event's deadline (Dickson, 2026-11-09). For a registration code pending, the wait ends at the code result, which every load gets (section 2.2), and `until` is the code-pending bound, its figure Dickson's to set (proposed: the handling deadline, 11 seconds), because the first start has no measured start-up time and compiling the built-ins on a cold cache takes seconds; when both hold, the later of the two | held, as behind a marker | held, as behind a marker |
| The hook's host reports ready, or a configuration marks its registration ready | the pipe to `Ready`, or the configuration applied | when the pipe is `Ready` and the registration ready, the call starts, to `AwaitingHook` | the pipe to `Ready`, or the configuration applied between two inputs; the call in flight goes on |
| A configuration that no longer registers the hook (its code failed, newer rules replaced its pending registration, or its extension was disabled) | applied | the chain goes on without that hook: the next layer's hook, or the outcome reported, to `NoHook` | applied; the call in flight goes on, and its verdict is judged by section 2.2's rule for an older generation |
| The alarm at `until` | no alarm | the hook counts as `pass`, which is logged (Dickson, 2026-11-09), and the chain goes on | no alarm |
| The alarm at `stalled_at` | no alarm | no alarm | `HostStalled` reported to Core, once; the state stays, and the pipe's end that follows answers the call |
| A verdict naming the current call, `deadline` included | none can arrive | none can arrive | the call ends; the chain function gives the next layer's hook, which starts or waits as an event's does, or the outcome, reported with the calls' effects in call order, to `NoHook` |
| The call ends | none is current | none is current | every read of it not yet started is withdrawn and answered `deadline` |
| A verdict naming an ended call | dropped as late | dropped as late | dropped as late |
| A read naming a call of this outpost's that has ended | answered `deadline` | answered `deadline` | answered `deadline` |
| Any other read, of this outpost's call or of one Core made | dispatched as a program named by the call | dispatched as a program named by the call | dispatched as a program named by the call |
| Core's query | dispatched | dispatched | dispatched |
| The host's pipe breaks | its pipe returns to `Waiting` until the restarted host reports ready | its pipe returns to `Waiting`; the wait goes on until `until` | the current call, when it is that host's, ends and counts as `pass` or no change, and the chain goes on; its pipe returns to `Waiting` |

Core's reducer keeps a list dialog record for each instance that showed one, keyed by its extension, module and version and, for an app module, its process: `None`, `Held { id, spec, until, presses waited on }` or `Open { id }`. Core holds it, not the lane, because only Core's reducer sees every press in key order, a press that runs another module's command or Core's own included, and every command's answer, from the outpost's report or the host.

| Rule | `None` | `Held` | `Open` |
|---|---|---|---|
| `show-list-dialog` during an `on-command` whose press carries `hold_until` | to `Held`, waiting on no press | spec replaced, stays `Held` | replaced in place and brought to the front |
| `show-list-dialog` during an `on-command` with no `hold_until` | shown, to `Open` | spec replaced, stays `Held` | replaced in place and brought to the front |
| A later press of the same keys raised before `until`, resolved to a command of this instance | nothing | added to the presses waited on | nothing |
| A later press of the same keys raised before `until`, resolved to anything else: another module's command, another process's instance of this module, or Core's own command | nothing | settled at once, as it is raised: the held dialog is withdrawn unseen, `on-list-dialog(cancelled)` to its instance, to `None`, since the later press ran another command (Dickson, 2026-11-09) and no answer of this instance's can follow it | nothing |
| A waited press's `on-command` answers, by its call's answer, the end of its host's pipe, or Core's dropping the command because its outpost has ended | nothing | removed from the presses waited on; when none is left and `until` has passed, shown, to `Open` | nothing |
| The alarm at `until`, a deadline of the reducer's | no alarm | when no press is waited on, shown, to `Open` | no alarm |
| The user answers | none can arrive | none can arrive | `on-list-dialog` to the instance, its one answer, to `None` |
| The instance ends: Core publishes another version of its extension, the supervisor reports the host's end, the breaker turns it off, or its application process ends | nothing | discarded with no answer, to `None` | closed with no answer, to `None` |

## 5. Where modules run

- **Every extension's host,** the built-ins' included, runs that extension's modules on its lanes and makes no call into any application. It runs in an AppContainer, with a memory cap, and a processor rate cap unless it holds a synthesizer ([security model](security-model.md), X4, A7). The built-in host is started with Verbatim and always runs, since the taskbar and global modules need it (Dickson, 2026-11-09); when it ends, the supervisor restarts it with the outposts' backoff, and its memory cap is set from a measurement taken with many outposts open, since it runs one instance per outpost per module.
- **The outposts** apply node rules, call hooks from their reducer and answer hosts' reads on their worker; they load no runtime.
- **The listener** applies window rules, focus vetoes and event drops as data, and runs no module code.
- **Core** owns the extension lifecycle, publishes the tables and the gesture map, judges and performs effects, and shows dialogs; it runs no module code and links no Wasm runtime.
- **eSpeak NG and OneCore** are built-in extensions of their own, each a native synthesizer module in its own host behind `verbatim_synth_v1` (Dickson, 2026-11-09; section 12).

Core's reducer stays pure: a module's speech is an ordinary effect, and a module command and a dialog's answer are recorded inputs, so the flight recorder's replay needs no module.

## 6. Ordering, provenance and conflicts

For one application there are at most three layers: a developer-folder module or the one installed extension, then the built-in, then core behaviour. Within one event, every layer's rules apply first, lowest layer first, so the highest layer's action wins a contested property; then hooks run from the highest layer down, each seeing the node as the rules and the hooks above left it: `pass` and `rewrite` continue the chain, `drop` and `replace` end it, and `on-node` and `rewrite` changes accumulate in that order, so a drop is never undone by a later layer (Dickson, 2026-10-22 and 2026-10-28). On a focus, the `on-node` chain runs as the batch is emitted, before the `on-focus` chain. For commands, the highest layer that binds a gesture gets it; the user's own gesture map sits above every layer once it exists. The outpost records for each overridden field which layer and rule set it, and the focus report shows it.

## 7. Performance

A rules-only module costs what the constant tables cost today: rules are merged once at load into the tables the listener and the outposts consult, the listener's looked up by the identity of the event's process, an outpost's holding only its own identity's (section 3). A hook costs a round trip between processes and two wake-ups on the event's path, and each read two more, accepted for built-ins as for installed extensions (Dickson, 2026-11-09), measured in step 4 against D15. Per event, the time inside module code, split into guest and host-call time, is a stage of the latency timeline, and the call ledger carries two rows ratcheted against `mockapp`: a rules-only module leaves every count unchanged, and a module with one descendant read adds exactly one UIA call.

Wasmtime's epoch interruption bounds a hook's own execution; since the epoch is the engine's and one host runs many lanes, each store's deadline callback checks its own hook's time before it traps. The compute bound is loose until step 8 sets it from the built-ins' measured guest time; the total bound is the handling deadline (`verbatim_model::HANDLING_DEADLINE`, 11 seconds: UIA's 10-second transaction timeout and a margin), counted by the host's lane from when it starts the call, the call's one clock (section 4), so a call's time does not depend on how long its event waited behind an earlier call. A trap counts as `pass` or no change, the instance is re-created, and the breaker (A9) counts it. A store limit counts as a trap does. The host's end counts against an installed extension or a developer-folder module with a call in flight, which is exact since each has a host of its own, and against no built-in module, since a process-wide fault or the host's memory cap names none; every outpost counts a hook in flight on the broken pipe as `pass` or no change. Limits of the one clock: a module whose hooks each run to the deadline delays its application's events by that much each, until the breaker (A9) disables it; and a lane stuck where its clock cannot reach, in a native call or the host's own code, holds its application's events until the liveness bound ends the host (section 4), the handling deadline and the grace after the call was sent. `on-node` is called once per emitted batch, so its round trip under an event flood is measured in step 4.

## 8. Capabilities

Capabilities are derived from the component's imports for built-ins and installed extensions alike, and the install and Extensions dialogs are built from them, as the guide's capabilities page lays out and words them (Dickson, 2026-11-09). An install request reaches the running Verbatim through the user endpoint from a small helper executable registered for `.vext` by the installer (M8.6), which shows a message box that Verbatim must be running when nothing answers, as NVDA's `nvda_slave.pyw` does; the Extensions dialog's Install from file button needs no association, and is how a portable copy installs.

## 9. The runtime and the guest workflow

The runtime is wasmtime with the component model (Dickson, 2026-10-22), chosen by a requirements comparison: Windows x64 and ARM64, the component model and WIT, interruption of running code, memory limits, precompiled artifacts; wasmer dropped its Windows native compilers, wasmi and WAMR have no component model, WasmEdge is x64 only. Cranelift compiles on both architectures; Pulley is switched on for ARM64 only if `ci-arm64` ratification or a Cranelift fault requires it; Winch is excluded because it cannot be epoch-interrupted. `verbatim-ext` is the only crate that names the runtime.

The WIT files in `verbatim-ext-api` are the single source (Dickson, 2026-11-09): `wasmtime::component::bindgen!` generates the host's traits, `wit-bindgen` the guests' bindings, and an xtask step parsing them with `wit-parser` generates the guide's API reference pages, which `cargo xtask ci` checks are current; the manifest reference and a JSON Schema are generated from the manifests' `serde` types with `schemars`, with the same check. The conversions between Verbatim's internal types and the WIT types are exhaustive matches, so a new internal variant fails to compile until someone decides how modules see it. Guests build for `wasm32-unknown-unknown` with no WASI adapter, in a workspace separate from the host's; the guide's examples are crates there, included into the book, so its code is compiled and tested.

## 10. Versioning

A WIT package carries a semantic version, and every interface a component imports is named with it in the binary; the linker resolves an import by exact name first and otherwise by track, several tracks living side by side for a deprecation period, and `wasm-tools component semver-check` proves each new version compatible. The manifest's `api` names the version an extension was built against and must agree with the binary's imports, which are the authority. There is no `verbatim-minimum` or `verbatim-tested`: NVDA needs its version fields because its API breaks each year, and the API's tracks already say what an extension needs (Dickson, 2026-11-09).

## 11. The console

In M5, `verbatim-inspect call` invokes any function of the world by name with WAVE-encoded arguments through a host's dynamic call path, relayed by Core's developer endpoint. The interpreter console and scripted modules are M10's; with no runtime in Core, the console runs in a host of its own, and its design, settled in M10, starts from that.

## 12. Synthesizers and native code

Native code comes in two forms (Dickson, 2026-11-09): a library a Wasm module of any kind calls through a narrow import that passes bytes to a named function in a DLL its extension ships, in the extension's host, which covers NVDA add-ons calling a vendor SDK; and a whole native module for a kind with a small interface, implementing that kind's C ABI, first the synthesizer's, `verbatim_synth_v1`, the `SynthDriver` trait as C exports (version, create, destroy, describe, set a setting, speak a sequence through PCM, mark and is-cancelled callbacks, cancel). A native module's manifest lists its DLLs, and Verbatim reads each one's architecture from its file header rather than from a declaration, choosing the best build the machine can run: its own architecture, then x64, then x86; an extension with none is refused at install. ARM64 installations run x86 engines through the 32-bit host and are to run x64 ones through a full x64 host under emulation, built later (Dickson, 2026-11-09). An engine's files that may not be distributed, such as Eloquence's, are added by the user to the extension's folder before zipping it; there is no `user-files` list (Dickson, 2026-11-09). The x86 host for 32-bit engines carries no Wasm runtime, so an extension whose native code is built only for x86 holds no other module. Native code runs in its extension's host, contained as section 5 says, and the install dialog warns that it "Contains native code that runs outside Verbatim's extension sandbox", the extension sandbox being the Wasm boundary.

eSpeak NG and OneCore are built-in extensions, each one native synthesizer module behind `verbatim_synth_v1`, in a host of its own, so that every host process is one extension's host and `verbatim-synth-host` loses its engine mode (Dickson, 2026-11-09, built in M6). They stay separate processes because an engine's crash must not stop the other, which the fallback to the other engine needs (A3).

## 13. Porting NVDA's app modules

The porting track runs from M5 onward. In M5, every Windows inbox application: Explorer, Windows Terminal (a focus veto dropping every `TermControl` focus whose runtime id starts 14, with no hook; Dickson, 2026-11-09), Notepad, Calculator, Task Manager (proven by `mockapp` until UIAccess), Settings, Start and search, Quick Settings and Open With, and the tray list, taskbar list and time as global modules. Sleep mode becomes a core per-application list seeded with the five executables NVDA's sleep-only modules name. A module is done when its NVDA behaviours are captured on the VM with the pinned build, one end-to-end scenario per behaviour asserts the captured utterance, its own tests pass, and the parity ledger lists each behaviour with the scenario that pins it. After M5 the order of the track is appendix A's tiers.

## 14. Routing and identity

- **Gesture order** (Dickson, 2026-11-09): a gesture bound by a global module and by the focused application's app module runs the global module's command, as NVDA checks global plugins before the application's module (`scriptHandler.py`, `_yieldObjectsForFindScript`); the install dialog lists the conflict.
- **Reads only Core can route** (Dickson, 2026-11-09): a global module's `find-window` when an application has several processes, a read of an application with no outpost, and `focus()` and `foreground()`, which are Core's facts, go from the host to Core's reducer, which answers or names the outpost whose pipe the supervisor then makes; Core owns which outposts exist, so the route has one owner.
- **Application identity has one resolver** (Dickson, 2026-11-09): the listener resolves a process's identity once, from a process handle it holds, and sends it with the first fact for that process; the supervisor uses it, so the fact has one owner. Section 3 gives its path to the outposts, Core's reducer and the keyboard hook thread.
