# The one judge build

Status: built on 2026-10-30. Designed against main at e4fecc9b, rebuilt the same day around one rule for what an outpost reads, after reviews showed that every mechanism in which an outpost guessed Core's verdict needed a patch per sequence, and revised after the rule's own review, which judged the goal achievable, with Dickson's decisions of the same day. It applies [the ownership model](ownership.md) to Core's judgement of focuses, the focus listener and the outposts' copy of Core's focus. The refactor preserves what is heard, except the three changes the model keeps and the two Dickson accepted below. The mechanism is in the crate guides of `verbatim-core` ("Focus, events and objects"), `verbatim-outpost` (the listener, "What to read", "Window destruction and held objects") and `verbatim-uia` (`docs/crates/`); this document keeps the problems, the choices and the limits.

## The problem

Core judged each focus report, and the listener and the outposts each kept a copy of Core's focus (`CoreFocus`, `HeldElements`, `Held`'s copy) to guess that verdict and skip work. Each copy was one message old, so a focus that returned while Core's notice was in flight was never spoken (the repeat hole), and every mechanism that guessed Core's verdict needed a patch per sequence (43de3932, c0bbf19b, 094a8dc8 and later). Core's refusal paths are the application rule, the duplicate rule, the stale rule, a foreground report of the window already holding Core's focus, the second foreground test and the app's ignored-window drop; an outpost that predicts any of them can disagree with Core.

## The rule

An outpost reads changes for every node it has not released, and Core's targeting decides what is spoken (Dickson, 2026-10-30). Core's focus line is always a set of nodes the outpost carried and Core still holds, so it is always inside the set; while a `NodesHeld` is in flight the outpost has released only what Core released at an acknowledged position, so the set can be larger than Core's, never smaller. A lag costs reads, never a word. `NodesHeld` is a release message about node lifetime and carries no judgement. Queued nodes must be in the set: a change of W judged while the report that carries W still waits in the outbound queue is read and queued behind that report.

Name, value and description changes are read only for unreleased nodes that were the focus of a report, state changes for every unreleased node, since Core speaks the first kind only on its focus and the second on the focus or an ancestor. The outpost's own exclusions stay: a tree item's logical ancestors, the foreground window's own object, `is_foreground_window`.

What Core holds in an outpost is its focus line plus a few single nodes (the last announced selection, the navigator object, the caret's node, a pending request's node, a held key's read, say-all's node), so the set is one or two focus lines for one release round trip and nothing grows with time. `NodesHeld` is written after Core handles a focus report or any message that changed the nodes it holds there, and a change of held anchors or a bare move of the acknowledged position rides on the next message to that outpost (Dickson, 2026-10-30).

## What was chosen, and why

- The back-channel is removed: `CoreFocus` and every function that builds or reads it, `HeldFocus`, the listener's `HeldElements` and the outposts' copy. Repeats are judged only in Core, from full facts, and the listener reads every UIA focus that passes its own checks. Cost: a UIA repeat reads about 5 calls where the drop made 3, and an MSAA repeat or a foreground change into a report's window reads in full (about 20 and 5 to 10 MSAA calls); `docs/performance.md` has the figures.
- Core keeps one foreground record, `Foreground` (`crates/verbatim-core/src/foreground.rs`), with one writer function and one fact per writer, replacing five scattered notions. The focus stamp splits into an ordering stamp, which the stale rule reads and every attended observation writes, and an applied stamp, which `menu_or_switch_ended` reads and only a focus taken writes. Two speech changes follow, accepted by Dickson: with Core's check box in W, W's foreground change at 2,000 refused and another application's focus observed at 1,900 arriving after it, the 1,900 focus is stale and silent; with A's repeat (1,200) arriving before another application's B (1,100), B is stale and silent and Core ends on A, closing the repeat hole in that order too. The pinned NVDA source was to confirm this before building (`docs/parity/focus-events.md`, "Stale focus events").
- Focus groups: the outpost tries a group's entries newest first, as NVDA's `pumpAll` does, and the stop moves into Core. Every report of a group carries the group's number and rank, and Core takes a report only when it took no newer report of the same group. The outpost reads an older entry after a reported foreground change only when the change's window holds an unreleased node of a report's focus line. Groups are keyed by the generation of the report's node, since group numbers restart with each generation.
- UIA property, text and caret changes reach an outpost only through its focus-following group, so the group stays on the element of every report whose focus node is unreleased and is removed when the store releases that node, not when the next focus is followed. An event is attributed to its node by its cached runtime id. This also avoids re-adding a group to an element the focus returns to within a round trip.
- The listener's menu-opening comparison is with the reading thread's own last read while that read is current, and a reading thread clears its last read when the scheduler answers that the read was abandoned. This is the third kept change. The read scheduler is a pure transition under the lock it already had, `Schedule` in `read_schedule.rs`, with the menu end's grace as `GraceState`, and the first ownership check (`xtask/src/ownership.rs`) holds it to an allow-list.
- Dialog text is carried with each report: a dialog counts as entered against every report's line, a superset, and Core speaks it only when its own line enters the dialog. The ignored-window drop moves into the outpost, from the ignore list it inherits; the app's check stays. Every focus report carries window facts.
- Every carried node is recorded as carried. The splice of a walk and the `existing_id` lookups put nodes in a message without a record, so an older acknowledgement could free a node a newer message still carried, Core then held it, and its next change resolved to a new id that Core dropped: a lost word. A walk now splices only from entries the store still holds. The alternative weighed, identity that outlives the object, fails because UIA runtime ids are reused after their element dies (5797c075), most MSAA nodes have no stable key, and a key-to-id map grows for the outpost's life; it is a redesign of identity, left to the reducer build and the focus pipeline rework.
- Text anchors are released by message position like nodes: an anchor is forgotten only when a `NodesHeld` acknowledges a position at or after the last message that carried it and does not list it. Before, an outpost forgot any anchor once 64 newer existed, so typing more than 64 caret reports with follow-caret off before Core's next list lost the review cursor's anchor and say-all stopped silently. A change of Core's anchor list does not write `NodesHeld` on its own, since the caret's anchor changes with every key; it rides on the next message or the relay's 3-second ping, which bounds how long an outpost keeps an anchor Core dropped (Dickson, 2026-10-30).
- A terminal's new output is read for every unreleased terminal node with a follow entry, since Core speaks output only for its focus; the extra reads cost calls during one round trip and add no word.
- The stale rule compares generations, not applications, so a replacement outpost's report is judged against its predecessor's newest focus as another outpost's; that is safe because its first report, the focus-now answer, carries the time its read began.

As built, Core never speaks a state change of its foreground object as an ancestor's, and a refused foreground report still writes the foreground object, so a window's own client, which the outpost reads as that report's focus, says nothing when it is disabled (2cd08d08).

## Limitations

- Reads the outpost makes for a node Core no longer targets cost calls until the release arrives: the NodesHeld round trip, or the 3-second ping for anchors.
- The extra costs of reading unreleased nodes, which `docs/performance.md` records: `nearest_window_handle`'s normalize call for an event of an old XAML element, `caret_of`'s text calls for a selection event of an old element, the refresh for a help-text or controller-for change of an old element, and the second focus-following group for one round trip.
- `NodesHeld` after each focus report costs about what `CoreFocus` to the focus's outpost cost: one pipe write and the reader's wake. The saving is the notices to the listener and to the other outposts, and the supervisor owner-thread wake each caused.
- The identity redesign above is not done: a reused UIA runtime id can still name a dead node on the focus, where the reader's `earlier` evidence corrects it.

## Dickson's decisions (2026-10-30)

- The rule: an outpost reads changes for every unreleased node.
- `NodesHeld` is written on its own only when the held set changes or after a focus report.
- The ordering and applied stamps split, with the two speech changes above.
- UIA's focus-following group per unreleased report, attributed by cached runtime id.
- Focus groups' stop in Core; every carried node recorded as carried, the splice included; text anchors released by message position.
- The dialog text carried; menu currentness lost only on another top-level window; the menu end's grace as a pure transition; the ignored-window drop in the outpost; every focus report carrying window facts.
