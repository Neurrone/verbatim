## The second build: Core's foreground record and the gap

A choice marked "(Claude, 2026-11-02)" was taken in this restatement and is checked by the build's adversarial review; every claim about UIA's behaviour cites [UI Automation](../explainers/uia.md), the explainer.

Terms used below:

- A foreground change is the listener's `ListenerToCore::Foreground`: a window came to the system's foreground, with when the listener observed it.
- A whole-window focus is a `FocusChanged` whose node is a top-level window standing for the application's focus in it, no control in it read: an outpost's report of a foreground change into a window it reads through MSAA, and the held UIA application's title.
- The entered window is the top-level window the user's focus line was last in, a field of Core's foreground record.
- Core's focus is left when a foreground change into another top-level window was observed after every report Core has judged since it took that focus, the window being neither the entered window nor one sharing the root owner of Core's focus's top-level window.

The commits, each leaving `cargo xtask ci` passing: the foreground tests on the reducer's thread and Core's one test; the listener's foreground change and the left focus; the whole-window focus and the title rule; the gap and the held application's title; the keep-id evidence's order. Wake-ups and processor time are measured before and after the build; expected: unchanged at idle; per foreground change, no message or wake-up added, since the listener's message is already sent, and one gap timer armed on the outpost's reducer thread for a window judged UIA, cancelled when its focus is reported; per MSAA focus, the acceptance test's local calls moved from the worker to the reducer's thread.

### The outpost's foreground tests, on its reducer's thread

Today. The worker tests a foreground change when it handles it (`Worker::foreground`: `accepts` and `in_front`), reads the window, and looks again (`report_foreground`: a second `in_front`), stamping the report with the time after the read. It tests an MSAA focus (`accepts`) when it handles it. A focus is tested again by Core on the window facts read when the outpost publishes it (`classify`, `ForegroundRelation::of_facts`), so a focus its reader accepted, published after the user switched away, is dropped unheard.

What NVDA does. It tests a focus once, before it queues it: a UIA focus in its focus handler (`UIAHandler/__init__.py` 925, before `queueEvent` at 958), an MSAA focus in its pump (`IAccessibleHandler/__init__.py` 1056 to 1059), and a foreground event once against `getForegroundWindow` (835), with no test after its object is made; `doPreGainFocus` makes none (`eventHandler.py` 378 to 413). The ledger's entry is `docs/parity/focus-events.md`, "Event acceptance", which the build updates.

The rules:

- Every test the outpost makes against the foreground is made on its reducer's thread from Windows' state, never on the worker (Dickson, 2026-11-02): the acceptance test of an MSAA focus and the in-front test of a foreground change, as the reducer takes the entry from the mailbox, the shell making the local calls (`GetForegroundWindow`, `GetAncestor`, the class and thread reads `acceptance::accepts_event` makes) and the result carried on the item to the worker; and the in-front test at the gap record's bound (below). Reason: the worker can wait behind a call into a held application for up to `HANDLING_DEADLINE`, since every call into an application waits behind a stuck one in its one request reader (explainer, "Inside the provider process: the one request reader"), so a test made there can be made seconds after the event. NVDA tests in its pump, as the event is handled; Verbatim tests as the event is taken in, nearer the event.
- That test is the one test. `report_foreground`'s second look goes, and a whole-window focus is stamped with the time the test found its window in front. Reason: NVDA tests once, and that time is still after the window came in front, since the foreground event Windows raises for a switch reaches an out-of-context hook only once `GetForegroundWindow` names its window (an event an application raises itself earlier, as File Explorer does for its folder window, is not in front at the test and is dropped there, below), so the old window's focuses raised before the switch stay older (b1917eed's sequence).
- Core judges every focus report that has window facts against its own record's front, not against the facts read at publication (`classify`); `ForegroundRelation::of_facts` goes (Claude, 2026-11-02). A focus is dropped when the front was observed after it and is a window it is unrelated to: neither its top-level window nor its root owner is the front window or the front's root owner, so a popup, an owned dialog and a focus in an owned window pass. Otherwise it is attended. A focus with no window facts keeps today's test by application. Reason: Core judged a copy of the reader's test on facts read later, while a reader's test at the event cannot see a foreground change after it; NVDA tests when it handles the event, so a focus whose read was held past a switch to an unrelated window is refused there, and the record says the same from the listener's one report. Without it a held application's late focus, released after the user's return, would be spoken in the window returned to and take the title from the return.
- The listener's acceptance test of a UIA focus stays where it is, when the read starts: it needs the sender's nearest window, a call into the application the callback must not make (D13), and a read that starts late is judged again by Core's front.
- `in_foreground` stays on the wire for the attendance of events other than focuses (`window_is_attended`), and the title rule's `foreground_window` is read with it.

Edge cases. A slow focus published after Alt+Tab into an unrelated window is dropped by the front, where NVDA speaks it and then cuts it when its slowness came after its own test: a deliberate difference, recorded in `docs/parity/focus-events.md`, "Event acceptance", by the build's records commit (Dickson, 2026-11-02: accepted). A focus of form M observed before its owned dialog D came in front is related through D's root owner and taken, as NVDA takes it. Within one outpost reports leave in observation order. A foreground change whose window leaves the front during its read is reported and then judged by Core's record.

Speech. Unchanged on the steady path. The slow focus is heard as NVDA's source says it is; no capture exists. Cost: one local `GetForegroundWindow` fewer per foreground change; the other local calls move from the worker to the reducer's thread, which keeps its rule of no call into an application. Lifecycle states: none added.

### One foreground change, from the listener

Today. Found on 2026-11-01, 4 of 4 runs by hand: with Notepad's edit as Core's focus, switching to an application whose UIA calls are held, then back to the same place in Notepad, says nothing. The busy application's outpost drops the foreground change of a window it judges UIA (`Worker::foreground`, "foreground dropped: UIA owns the window"), and its UIA focus read never answers, so Core hears nothing of the switch: on the return it refuses Notepad's foreground report as the window holding its focus (`reduce_focus_changed`) and drops the edit's focus as a duplicate (`is_duplicate_focus`). NVDA is silent there too, its last queued focus still Notepad's edit: the foreground event is a descendant of it (`IAccessibleHandler/__init__.py` 845) and the UIA focus a duplicate (`UIAHandler/__init__.py` 902 to 914). The listener already sends `ListenerToCore::ForegroundWindow` for every foreground `WinEvent`, for the keyboard hook alone, with only the newest waiting; attention moves on an outpost's foreground report (`ForegroundFact::Reported`) and on a focus in the foreground window unrelated to attention (`follow_an_unreported_foreground`).

The return (Dickson, 2026-11-02): silence while in the busy application is accepted; the return is always read, and spoken exactly as the same switch is spoken without a stall, so no NVDA capture is needed. A deliberate difference from NVDA, recorded in `docs/parity/focus-events.md`, "Duplicate focus suppression".

The message (Dickson, 2026-11-02): `ListenerToCore::ForegroundWindow` is renamed `ListenerToCore::Foreground` and gains `observed_at_us`, when the listener's callback observed the event, on the run's shared clock that orders facts across outposts. It is the only source of the fact that a window came to the foreground; Core uses it for the keyboard hook, for attention, and for the foreground record. Reason: one fact, one sender; the listener sees every foreground change from its global hook with no call into any application. It also carries the process its facts go to, the console host's for a console window, which the callback already resolves, and the window's root owner (`GetAncestor` with `GA_ROOTOWNER`, local), the two facts attention is judged by (`window_is_attended`) (Claude, 2026-11-02).

The rules (the listener's `WinEvent` thread; Core's thread):

- The listener sends one for each foreground `WinEvent` whose window is in front, Program Manager's and the taskbar's (`WinEventKind::ShellForeground`) and ignored processes' included, and none replaces another (Claude, 2026-11-02, after the review). It tests on its `WinEvent` thread, with local calls only, that `GetForegroundWindow` names the event's window. A window not in front is kept as the watch's pending window, replacing any kept before, and is sent once a later focus or foreground `WinEvent` the thread receives finds `GetForegroundWindow` naming it, with that event's observation; a newer foreground event replaces it. Reason: an event for a window not in front is stale (the Alt+Tab staging window's, already passed), raised by the application before the switch (File Explorer's folder window, 140 to 400 ms early, and with no later event when opened in front), or refused by Windows' foreground lock (`docs/parity/focus-events.md`, "Event acceptance"); sent unfiltered, a background application's change would drop the focus the user is in by the front rule and mark it left. The pending window keeps the early event of File Explorer's folder window and of a console, which come in front with no event of their own, since their first focus follows. A console in front when the listener starts is sent by the watch's start with its thread unknown, and again when one of its events names it (`ForegroundWatch::console_event`), as today. Core's hidden frame is sent too, since the keyboard hook needs every window in front; Core takes a change whose process is its own for the hook alone, never for attention, the front or the left mark, as the outposts drop the hidden frame today. Events reach Core in the order the listener's one thread sent them; a refused one while the writer is behind is not sent at all, and a return replacing the busy window's change cannot happen, since none replaces another.
- Core applies it at one point of `reduce_input`: the keyboard hook's view, as today; attention, which becomes its process and window (D14: attention moves only on a foreground change); and the record's front, its window and stamp. When its window is neither the top-level window of Core's focus nor the entered window, its root owner is not the root owner of Core's focus's top-level window (an owned dialog, a progress or find window, a popup of the same window), and it was observed after the ordering stamp, the newest observation of a focus Core has judged (taken, a duplicate, or a whole-window focus refused as inside Core's focus's window), Core's focus is marked left (Dickson, 2026-11-02, option A). Reason: one rule, needing no event from the held application's thread; judged by that stamp, a change that reaches Core after the reports of the user's return cannot mark the focus the user is back in. It speaks nothing, cuts nothing (the line cut, `ForegroundFact::LineCut` and `changed_at`, still moves only with a focus Core takes, as today), sets no ordering stamp (`ForegroundFact::Observed`), and changes no node, focus group or navigator. Reason: the stamp orders focuses, and with a foreground change among them a focus of the same application observed before its own dialog came in front would be stale, where NVDA speaks it; nothing is heard in the busy application.
- A left focus reported again is taken as a focus from another top-level window is: it is no duplicate (`is_duplicate_focus`); a whole-window focus of its window is not refused (`reduce_focus_changed`); a replacement outpost's report of it is not taken silently (`reads_the_same`); its line meets the previous line only at the desktop, with speech cut (`focus_line`); its spoken record comes from its reading (`spoken_record`); and its caret is forgotten (`end_text_activity`). Every state Core keys on the focus's node is reset as when the focus moves to another node: the terminal's speech state and its queries (`terminal::focus_moved`, called from `end_text_activity` with the node, which today resets only for another node), the terminal model's blur and focus (`terminal_model::focus_moved`, called from `reduce` only when the focus's node changes), the reported formatting (`reported_format`), the navigator and the review position, the selection last spoken (`last_selection`) and the menu item of the focus (`menu_item_of_focus`). Reason: that is the state the same switch leaves when the busy application's focus is taken, so the return says the same words and Core's state after it is the same.
- Removed: `ForegroundFact::Reported` and `follow_an_unreported_foreground`; `ForegroundFact::Window` becomes the front; `ForegroundFact::Unreported` becomes a write of the foreground object alone, made by the focus that enters a window (the title rule), so `FocusNow`'s foreground still names the window in front after a switch to a UIA window, as NVDA's `doPreGainFocus` moves its foreground object from the focus's ancestry.

Edge cases, with the order of the two pipes:

- A held application's focus F_H, observed before the user returned to M and released after: the front, M, was observed after F_H and is unrelated to it, so it is dropped, and M's own focus says the title.
- An owned window of a held application: the user in M's edit, M's owned dialog D comes in front and M is held. D shares M's root owner, so the focus is not left, and a return within the second is a duplicate and silent; past the second, D's window text is taken as Core's focus and the return is spoken: a stated limit.

- Windows+D and the taskbar: Program Manager's and the taskbar's changes move attention and leave the focus. NVDA takes no foreground event from them but moves its foreground with the next focus (`doPreGainFocus`), so attention matches NVDA's once that focus comes.
- A console window's early foreground event moves attention to it at once, where today its first focus does.
- Two applications visited before the return: the focus stays left until a focus is taken. The busy application's late focus is dropped by the front, as above.
- A splash or tray window that takes the foreground and reports no focus leaves the focus like any window, so the return after it is spoken as the same switch with no stall (Dickson, 2026-11-02). A deliberate difference from NVDA, which drops a native UIA window's `WinEvent`s (`IAccessibleHandler/__init__.py` 576 to 581) and so is silent after a UIA splash window and after a held application alike; the two cannot be told apart from outside the application for the first five seconds, before `IsHungAppWindow` says hung, so the always-spoken return applies to both. ### The whole-window focus

The rule (Dickson, 2026-11-02): the outpost's report of a foreground change is a `FocusChanged` whose node is the window, following NVDA, whose `processForegroundWinEvent` queues a `gainFocus` on the window's object. Its flag `foreground: bool` becomes `whole_window: bool`, which says the node stands for the application's focus in that window. Core cannot tell such a focus from its node (Claude, 2026-11-02): an MSAA focus event on a window's client object with no focused child (`OBJID_CLIENT`, `CHILDID_SELF`) reads as the same node, and NVDA ignores only the foreground event when its focus is in a descendant window (`IAccessibleHandler/__init__.py` 844 to 848), never such a focus event, so a rule on the node would drop a focus NVDA speaks.

The rules (Core's thread):

- A whole-window focus never moves attention. It is judged by the front as every focus is: taken when the record's front is its window, or was observed no later than it; dropped when the front is another, unrelated window observed after it. Reason: the listener sends every foreground event, so its change for the same switch always comes, and a whole-window focus reaching Core first over its own pipe is the one that change would take. No pending slot is kept for it.
- It is then refused, as today, when Core's focus is in its window and not left, and taken silently when it has no name. A whole-window focus Core drops or refuses lets its group's older entry be taken, by the focus group rule.
- The outpost reports one only for a window it reads through MSAA, as today, and for the held UIA application's title; a UIA window's title comes with its UIA focus (the title rule).

Edge cases. The listener's change for W arrives after W's whole-window focus: the front was X, observed before it, so the focus is taken, and the change, observed before the focus, leaves nothing. A later switch to X observed after W's report and reaching Core before it: W's is dropped. A whole-window focus of the window holding Core's focus, after Core's focus was left: taken and spoken.

Speech. Unchanged for a window read through MSAA: Settings' frame "Settings", then "Settings window" and "Region button" (`settings_combo_box_expanded`); the Windows Forms window "second-application". Cost: one compare per whole-window focus. Lifecycle states: none.

Tests. Core: `a_whole_window_focus_arriving_before_its_foreground_change_is_taken`, `a_whole_window_focus_of_a_window_left_since_is_dropped`, `a_whole_window_focus_never_moves_attention`, `a_whole_window_focus_in_the_window_holding_the_focus_is_refused`, and `a_focus_on_a_windows_client_is_not_refused_as_a_whole_window_focus`.

### The title rule

Decided by Dickson on 2026-10-30, wording confirmed: the window's title is always said when the focus enters a top-level window it was not in, decided in Core from the focus's chain. It supersedes the batch rules of `experiments/ownership-study/foreground-batch-stress.md`. The decision of the same day that a focus never drops a foreground change into another top-level window from its batch is superseded too and is not built: the outpost's batches stay NVDA's newest first.

Today. Core says a top-level window only as an entered container: when the new line differs from the previous just below the desktop (`focus_line`'s cut), the window's chain entry is spoken if it is presentable (`is_presentable_container`). When a foreground change and the focus after it share an outpost batch, tried newest first as NVDA's `pumpAll` tries them (`IAccessibleHandler/__init__.py` 1019 to 1110), the foreground change is never tried; a Windows Forms edit's walk reaches the form's client through `accParent` with no identity string, so the entry is a quiet pane and the title is lost (`text_box_editing`, 2 of 3 runs). NVDA loses it in that timing too: its capture of `text_box_review_cursor` says the title in 3 of 5 launches.

The rules (Core; the outpost reads one handle more per report):

- The window is the system's foreground window when the focus was published, not merely the focus's top-level window, since popup menus, combo box lists and Windows Forms drop-downs are top-level windows that take the focus without becoming the foreground. `WindowFacts` gains `foreground_window`, the handle of the `GetForegroundWindow` already called for `in_foreground` (`window::window_facts`), so no call is added. It is a fact of that report, used for this rule only; the record's front is not used, since the listener's change can reach Core after the focus it brought, and a title cannot be said after its focus.
- The entered window changes on a whole-window focus Core takes, to its window, and on a focus Core takes whose own top-level window is its `foreground_window`, to that window; that focus also makes its chain's outermost entry the foreground object (`ForegroundFact::Object`), as `Unreported` did. A foreground change never sets either. Reason: `foreground_window` is read when a report is published, so a report read in M while dialog D came in front carries D, and setting the entered window from it would lose D's title when D's foreground change and its focus then share a batch.
- When Core takes a focus whose top-level window is its `foreground_window`, and that window is not the entered window or Core's focus before it was left, Core finds the window's own entry: the chain entry with that window handle that stands for the window (its UIA element, MSAA window or client object, or plain window). If the line already speaks it as an entered container, nothing is added; otherwise Core speaks it with the words of a whole-window focus of that window, after the top-level cut and before the other entered containers.
- Program Manager and the taskbar are entered with no title (`WindowFacts::foreground_is_shell`, read with `foreground_window`), as NVDA takes no foreground event for them. A foreground change into one of Verbatim's own windows clears the entered window, so the return from its menu, a popup that enters nothing, says the title even when the application's focus is the return's only report.
- An entry with no name adds nothing, and a chain with no entry for the window adds nothing (a stated limit). A focus in a popup says no title. A whole-window focus taken first sets the entered window, so the focus after it says nothing more. The rule never moves attention.

Reason: the title then does not depend on whether a foreground change and its focus shared a batch, which NVDA's own result does by pump timing (`experiments/ownership-study/foreground-batch-stress.md`).

Edge cases. The return from a busy application: Core's focus was left, so the next focus in the foreground window says its title unless its line already does, as the switch without a stall does. A focus read in M and published after D came in front is taken with the entered window unchanged. The roadmap's follow-up from the one judge build, a top-level window without a system menu not said after an ancestor walk, is covered whenever the chain carries that window's entry.

Speech. `text_box_editing` and `second_application_and_verbatim_menu` say the window's title in every run, as "second-application" before "Note edit multi line". Cost: one compare per focus taken and one look for the handle along its chain, which `focus_line` already walks; 8 bytes per report. No call, wake-up or timer.

### The held UIA application's title

The rule (Dickson, 2026-11-02): at the gap record's bound, the existing second from its first copy, when no focus of that window has come, the outpost sends the window's text from Windows' state as a whole-window focus, whatever is in flight, and keeps the gap's read going beside it. So a slow application that reports its focus later is heard as its window text at one second, then its focus. A deliberate difference from NVDA, which says nothing until the focus comes. Reason (Dickson): a second is the silence budget, and a test of whether the application is answering (a call in flight, a marker waiting, a give-up, a hung window) missed cases the gap read must still speak. When the application answers within the second, its focus closes the record first, and the title is the UIA name said with the focus, as today.

Where it runs: the outpost's reducer decides at the bound's timer; its shell makes the local calls and builds the node, with the store's lock for the node id, a short hold its rule allows.

The rules:

- At the bound, the shell reads the foreground window (`GetForegroundWindow`, local) and the record's top-level window's relation to it by the acceptance test (`acceptance::foreground_relation`: the same top-level window or root owner, topmost, or a `Windows.UI.Core` window under the active window), the in-front test of "The outpost's foreground tests" above. Unrelated: the record closes and nothing is sent or read. Reason: a UIA popup's record, a combo box's drop-down or a context menu in a top-level window of its own, is still read when its owner is in front.
- Related: the bound's entry is queued, so the worker makes the gap's read as today when it is free, for a record whose window is read through UIA; the record stays open until a report closes it, and a later copy in its window arms a new bound a second from the copy, since a gap read the worker could not finish leaves no other timer (review of the build). The window text is sent as a whole-window focus, stamped with the record's stamp, only when the record's top-level window is the foreground window itself, so a popup's record says no title.
- A window read through MSAA whose foreground report has not been sent by the bound, because the worker is blocked reading it (`read::foreground_window`, called from `Worker::report_foreground`), says its window text the same way (Claude, 2026-11-02, from Dickson's rule that a held application says its title; he can override): the record also opens on a foreground change into a window read through MSAA, waiting for its title, and any report in its top-level window, its whole-window focus included, closes it; no gap read is made for it, since the worker's own report is still owed. A record opened by a copy or by a change into a UIA window waits for the focus, and a whole-window focus does not close it (defect B).
- A foreground change the listener forwards before the outpost's hook is in (`hook_installed`) is taken into the outpost's mailbox as its hook's would be, and arms the record the same way; held for an outpost still starting, it arms the record when released, stamped with its event's observation, so an application held right after its launch says its window text at once if the second has passed.
- The node is the plain window read from local window data (`plain_window`, `Nodes::window`, MSAA key `(hwnd, OBJID_WINDOW, 0)`): backend MSAA, role window, named by `InternalGetWindowText`, so it is said as the responsive switch says the window, "held-application window", as Notepad's would be "Untitled - Notepad window" (Dickson, 2026-11-02: the words of the responsive switch). Reason: the store already serves that node with no object, so no UIA node without an element is made and no assumption is made about a provider's runtime id for its window; and the window key, not the client's, keeps one role per node, since an MSAA report of the window's client stays a pane under its own key. It is minted under a request tag the reducer takes for the send and claims when the message is recorded, so the store's release rule applies unchanged.
- The title is said once. A focus Core takes after a whole-window focus of its own top-level window, not left since, meets the previous line at that window: the new chain's entry with the window's handle that stands for the window (the title rule's "own entry") is not spoken again, though its node differs, since a UIA chain's window element is another node than the plain window the text was read into (`focus_line`). An MSAA focus meets an MSAA whole-window focus by the client's own node today; the held title's plain window is met by this rule in either backend.

Edge cases, re-derived under this rule:

- The application answers after the title: the gap's read, or the listener's late read, reports the focus, and Core says the control alone, and its containers below the window.
- Settings, a slow page whose focus never comes: the frame's whole-window focus was taken at the switch, so the text at the bound is refused as a window holding Core's focus, and the gap read speaks the page's focus a second late, as today.
- File Explorer, a slow folder window whose list's focus never comes: the frame's whole-window focus says the title at the switch when its foreground event comes in front, and the bound's text is refused likewise; otherwise the bound's text says it. The gap read speaks the list and item when explorer answers.
- The second visit to a held application: the foreground change re-arms the record's bound, so the title is said again a second after each visit, and the gap read, behind the held call, speaks the focus if the application answers within `HANDLING_DEADLINE`. An application already hung when entered is the same: its record opens on the foreground change.
- The user returns to N between the bound's in-front test and Core applying the listener's change into N: the title, stamped with the record's stamp, observed before that change, is dropped by Core's front rule once the change is applied, and spoken and then cut by N's focus if it reaches Core first.
- The user returns before the bound: the in-front test closes the record with nothing; the return is spoken ("One foreground change").
- A nameless window: taken silently.
- The listener's marker reaching the outpost before the hook's copy, which happens only when the UIA focus reaches the listener first (5 of 1,680 `WinEvent` focuses in UIA windows, before its two pipe crossings), holds the copy behind the marker, so the record opens only once the listener's read resolves, at most `READ_DEADLINE` (8 s) later: a stated limit. A window with no verdict yet whose probe waits on the held application opens no record until the probe ends: a stated limit.

### The gap, closed by the outpost's own reports

Today. The record opens when the worker drops an MSAA focus copy because it judges the copy's window UIA (`Worker::copy_dropped_for_uia`), restamps on a later copy or an accepted foreground change in its top-level window, and waits a second (`BOUND_US`) before the gap's read (`Worker::gap_read`). It is closed by what the listener computes from each UIA focus outcome (`GapAnswer`, from `gap_answer` in `crates/verbatim-listener-logic/src/focus.rs`): a read, and a drop that is a verdict of NVDA's checks (`VERDICTS`), close a record in their top-level window; a give-up (`GAVE_UP`) closes one in any window; a drop for no window has the record read at once; any other drop, the moved-on rule's `MOVED_ON` among them, leaves it open. A read is placed as the mailbox takes it in, with one `GetAncestor` (`read_answer` in `crates/verbatim-outpost/src/outpost/mod.rs`), before the worker judges it, so a read the worker then drops still closes the record. An MSAA copy handled through MSAA, or an accepted foreground change, in another top-level window closes it too (`GapRecord::accepted`).

What NVDA does. Its fake focus reads the focus 50 ms after a menu or switch event only when its own focus object has not changed since (`IAccessibleHandler/__init__.py`, `processFakeFocusWinEvent` and `_fakeFocus`, 976 to 1003), so what an event it dropped says closes nothing. The gap itself is Verbatim's own (`docs/design/listener-without-connections.md`, decision 11).

The rules (the outpost's reducer, in its commits; the listener's reading threads for a drop's fact):

- A report closes the record: every focus the outpost sends Core in a commit but a whole-window focus in the record's own top-level window, whichever program made it (a listener read the worker reports, an MSAA focus, a publication at the bound, the gap's read, a focus-now answer's focus). The reducer applies it where it records the commit's report (`Change::report`), with the observation and top-level window of the commit's message. It closes a record in its own top-level window when observed no earlier than `ANSWERED_BEFORE_US` (100 ms) before the record's stamp, and a record in another top-level window, or when it has no window facts, only when observed after the stamp. Reason: the record waits for the application's focus to be told to Core, and only the outpost knows what it told; a whole-window focus says only that the window is in front, as a foreground event does in NVDA, and the focus in it is still owed.
- A report is placed by its window facts' top-level window (`window::window_facts`, `GetAncestor` with `GA_ROOT`), the rule its copy is placed by (`top_level_of`), so no call is added, and a popup whose accessibility parent is its owner, such as a combo box's drop-down, is placed in its own top-level window as its copy is (the earlier review's finding 6). The newest report per top-level window is kept for the look-back, so a copy judged after a report of its own focus opens nothing; a whole-window focus is never kept for its own window, so File Explorer's frame's report does not stand for the list's copy that follows it (the earlier review's finding, which brought defect B back). It is pruned on the window's destroy, as answers are today.
- A foreground change into a window of the application (the record waits for its focus when the outpost judges the window UIA by a kept verdict or the class lists, local and with no probe, and for its title otherwise, above) opens the record, or restamps an open one, as the reducer takes it from the outpost's own hook, on its thread, in front by the test made there; it does not wait for a focus copy, which an application whose thread is held or hung may never raise. Its restamp also arms a new bound, a second from the change, and clears the bound's queued mark (`GapRecord::copy_dropped` and `accepted` keep `due_us` today), so every visit says the held title at one second; a copy still restamps without moving the bound. A bound's entry already queued stays the record's one entry: handled before the new bound, it waits for it again, as today (`bound_reached`). A foreground change no longer closes a record of another window, which the in-front test at the bound covers. Reason: the second visit, and an application already hung when entered, raise no focus copy (Claude, 2026-11-02).
- A drop carries no answer, but one fact the listener observed, in place of `UiaFocusDropped`'s `answer`: whether the sender had no window above it. Then the record is read at once, as today (decided on 2026-10-21 for the burst of gone senders). Every other drop, a give-up included, and a read the worker drops (by its verdict, as Core's hidden frame, as another process's window), leaves the record to its bound (Claude, 2026-11-02). Reason: Dickson's rule for the window text says it at the bound whatever is in flight, and a give-up that closed the record unread would leave a slow application silent; the gap read beside it speaks a focus the application gives later. So the earlier review's finding 4, a give-up of File Explorer's first folder window closing the second's record, cannot arise.
- A give-up's own read says nothing more, as NVDA says nothing for a call its watchdog cancels; the gap read at the bound reads the application's focus anew.
- Removed: `GapAnswer`, `gap_answer` and `GAVE_UP`; the listener's placement of every outcome; `read_answer` and its `GetAncestor` per read; `Intake::apply_gap_outcome`'s answers; `GapRecord::accepted`'s closing.

Speech. `settings_combo_box_expanded` keeps "Settings", "Settings window", "Region button", Settings' lookup failing fast leaving the record to its bound. A read the outpost drops in a window it judges not UIA, under a copy it judged UIA, is followed at the bound by the gap's read of the application's focus, spoken a second late when it is new and dropped by Core as a duplicate otherwise; NVDA's fake focus reads in the same case. A focus whose listener read was given up is spoken by the gap read when the application answers it.

### The keep-id evidence, read in NVDA's order

Found in run 41414227699 (2026-11-02), six Windows Terminal scenarios: at launch Windows Terminal raises its terminal's focus twice and then minimizes itself. For the second event the listener read the sender's keyboard focus (step 6 of its checks, `crates/verbatim-listener/src/focus_read.rs`), which answered true, and about a millisecond later, inside the walk (`focus_ancestry_classic` in `crates/verbatim-uia-rops/src/focus.rs`, `FocusQuery::previous`), the earlier element's, which answered false as the window minimized. Core took "sender focused, earlier element not focused" as a new element under the runtime id and said "<title> terminal", "blank" again. NVDA reads the other way round: once `compareElements` matches the last queued focus, it reads that object's `currentHasKeyboardFocus` first (`UIAHandler/__init__.py` 902 to 917 and 948), and the sender's only after (`shouldAllowUIAFocusEvent`, `NVDAObjects/UIA/__init__.py` 1632), so a focus that is only being lost is dropped whichever read sees the loss.

The rule (Dickson, 2026-11-02): the earlier element's keyboard focus is read before the sender's. The sender's plain read moves from the listener's checks (step 6 of `judge_before_reading`) into the walk as its `require_focus` read, and in the remote program and the classic walk (`crates/verbatim-uia-rops/src/focus.rs`, the program's order and `focus_ancestry_classic`) the earlier element's read (`FocusQuery::previous`) comes first, then the sender's, which stops the walk when false (Claude, 2026-11-02: the place). So no call or round trip is added: in the remote program both reads are in its one round trip, and in the classic walk they are the same two calls. Core's duplicate rule is unchanged. Reason: NVDA's order, so a focus only being lost can no longer read as a new element. The walk does not stop when the earlier element reads focused, though NVDA drops the event there: the listener holds its own last focus, not Core's, and Core judges a repeat, so a return to the same element after another application must still reach Core.

Speech. Windows Terminal's launch says "<title> window", "<title> terminal", "blank" once, and nothing on the restore. This fixes `docs/flaky-tests.md`, "Windows Terminal's terminal said again as it minimizes at launch". Cost: no call added; the sender's read joins the remote program's round trip, one round trip fewer where the walk is a remote program, and the same two calls in the classic walk; and a focus dropped for lacking the keyboard focus now costs the walk's start, its one round trip, where step 6 dropped it before the walk. Lifecycle states: none.

### Defect B

Found by the ownership study in `explorer_folder_window` (`experiments/ownership-study/architecture-study.md`, item 5): the outpost dropped the listener's read of the folder window's frame because its probe judged the read's window MSAA, while the list in its `DirectUIHWND`, judged UIA, had its MSAA copy dropped for UIA and no UIA focus came; "Items View list" was never said.

Established from today's code: the outpost is the one owner of a window's verdict (`read::own_window_verdict`, by which `Worker::uia_focus` judges a listener read at the read's nearest window), and the listener's only skip is the class-list verdict, made by the function the outpost's verdict starts from (`verbatim_reader_rules::class::class_verdict`), so the two can differ only while a backend override is in flight, which the version rule covers in M5. The window judged is NVDA's: NVDA judges a UIA focus by its sender's nearest window (`isNativeUIAElement`, `UIAHandler/__init__.py` 1516 to 1543, called at 887). What remains is the listener's answer: the frame's read closes the list's record as it is pushed (`read_answer`), before the worker drops it, so the record closes with nothing told to Core.

The fix is the gap's rule above, with one owner: the record is closed only by what the outpost reported, and the frame's whole-window focus neither closes the list's record nor stands for it in the look-back. The dropped frame read leaves the record open, and at its bound the gap's read reads the application's focus, so Core says "Items View list" and the item, up to a second late. Scenario: `explorer_folder_window`; a local failure is matched to its entry of 2026-10-31 in `docs/flaky-tests.md` before it is rerun. Limitation: should the frame's own MSAA focus, not its whole-window focus, be reported no earlier than 100 ms before the list's copy, its report closes the record and the list is still not said; the scenario's logs under this build give that order.

### A spliced ancestor released by `NodesHeld` (the first possible defect)

Built by the ownership refactor's reducer build, through its release rule; not built here.

The sequence that makes it real. Core's focus is in application B and Core holds no node of application A. A's focus F1, in container C of window W, is observed before B's newest focus but reaches Core after it, so Core drops it as stale and sends no notice, holding nothing of A. A follows F1. Before Core's `NodesHeld` that acknowledges F1 reaches A's worker, A's next focus F2 in C is handled. Its walk meets the followed chain at C, which is still registered, and splices W from it (`read.rs`, `splice`). A splice copies snapshots without looking them up, so W is not recorded as reported by F2 (`Outbound::publish`'s `touched`). The `NodesHeld` then releases W, since W was last recorded at F1's position. Core takes F2 and holds W, which A no longer serves: object navigation up from the focus answers gone at W, and a change on W is matched against an id the registry no longer gives. NVDA has no such hole.

Where it runs: the outpost's reader and its release.

The rules:

- Every spliced entry is recorded as reported by the report that carries it, as a looked-up node is. Reason: a node is released only when Core has seen every message that may carry it.
- A walk meets the followed chain only at an entry that is still in its registry, and only when every entry it would splice is too. Otherwise it walks on and reads those ancestors live. Reason: an entry released before the walk cannot be served again.

Speech: unchanged; the defect is in object navigation and change targeting. Cost: per spliced report, one registry lookup per spliced entry, local, with no call. Tests. Added: mockapp's `an_ancestor_spliced_into_a_later_report_is_not_released_by_an_older_acknowledgement` and `a_walk_does_not_meet_the_followed_chain_above_a_released_ancestor`, with `NodesHeld` sent by the test. Scenarios: `explorer_folder_window`, `settings_system_page`.

### The outbound merge (the second possible defect)

Still this build's: the refactor's merges reproduce today's, and these evidence fixes are built here (Dickson, 2026-10-30), without the clause on `answers`, since read requests are not built.

The states themselves cannot differ: a state change carries the complete set, and the newer replaces the older. What a merge loses is what the older message carried about its own change:

- A tree view item expanded by Right Arrow raises two state changes. The first is newly expanded and carries the child count; the second, read after the record says expanded, carries none. Merged while a write is in flight, the report says "expanded" without "52 items" (`docs/nvda/speech.md`, "How many items an expanded tree view item holds").
- A focus report whose `earlier` says `NotFocused` or `Gone` merged under a newer report of the same node that says `Focused`: Core takes the merged report as a duplicate, so the new element is never announced and a gone element's caret and terminal state are never reset.
- A requested read's report, carrying `answers`, merged under a newer report of the same node: the request is never answered and the idle barrier waits until the outpost ends.

Where it runs: the outpost's outbound queue, `merged`.

The rules: a report carrying `answers` is never merged, as no answer to Core's request is. A merged state change keeps the older's child count when the newer has none and its states still include expanded. A merged focus report keeps the stronger `earlier`, in the order `Gone`, `NotFocused`, `Focused`, none. Reason: the merged message must say what Core would have concluded from both in order.

Speech: "expanded", "52 items" in every run. Cost: a compare per merge, no call. Tests. Added: the outbound queue's `a_merged_expansion_keeps_its_child_count`, `a_merged_focus_report_keeps_the_older_evidence_of_another_element` and `a_report_answering_a_read_request_is_never_merged`. Scenarios: `system_information_tree`.
