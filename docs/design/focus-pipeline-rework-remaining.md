## The title rule

Decided by Dickson on 2026-10-30: the window's title is always said when the focus enters a top-level window it was not in, decided in Core from the focus's chain. On the same day he decided that it belongs to the focus pipeline rework, not to the ownership refactor, because it changes what is heard and the refactor preserves behaviour (`docs/design/ownership.md`). It is built after the refactor, in the focus pipeline rework's resumed second build, with its own design and adversarial review against the code then. It supersedes the batch rules of `experiments/ownership-study/foreground-batch-stress.md` and the batch decision in the second build below. Its wording below is as it stood after the ownership design's second review, which Dickson confirmed as what he meant; it uses the one foreground record, which the refactor's one judge build makes.

### The rule

The window's title is always said when the focus enters a top-level window it was not in, decided in Core from the focus's chain. Dickson confirmed this form as his decision.

- The window is the system's foreground window, not merely the focus's top-level window, because popup menus, combo box lists and Windows Forms drop-downs are top-level windows that take the focus without becoming the foreground. Each report's `WindowFacts` gains `foreground_window`, the handle of the `GetForegroundWindow` already called for `in_foreground`, so no call is added.
- The foreground record keeps the entered window. It changes only on a foreground report Core takes, to that report's own window, or on a focus Core takes whose own top-level window equals its `foreground_window`. Reason: `foreground_window` is read when a report is published, not when it is read, so a report read in M while dialog D came in front would carry D, and setting the entered window from it would lose D's title when D's foreground change and its focus then share a batch.
- When Core takes a focus whose top-level window equals its `foreground_window` and differs from the entered window, it finds the window's own entry: the chain entry with that window handle that stands for the window (its UIA element, MSAA window or client object, or plain window). If the line already speaks it as an entered container, nothing is added; otherwise Core speaks it with the words of a foreground report of that window, after the top-level cut and before the other entered containers; then the entered window becomes that window.
- An entry with no name adds nothing; a chain with no entry for the window adds nothing (a stated limit). A focus in a popup or owned popup, whose top-level window is not the foreground window, says no title and does not change the entered window. A foreground report taken first sets the entered window, so the focus after it says nothing more. The rule never moves attention, which moves only on a foreground report (D14).

Reason: the title then does not depend on whether a foreground change and its focus shared an outpost batch, which NVDA's own result does by pump timing (`experiments/ownership-study/foreground-batch-stress.md`); `text_box_editing` lost it in 2 of 3 runs. The outpost's batches stay NVDA's newest-first handling. Cost: one compare per focus and one handle on the wire.

### Tests

One Core test each, the first from the ownership design's second review:

- A Windows Forms button b in form M has the focus; Enter opens dialog D. The MSAA read of b is served by M's UI thread, busy in `ShowDialog`, and finishes after D is in front, so b is published with top-level window M and `foreground_window` D. Core takes b. Then D's foreground change and D's first focus share a batch, and newest first drops the foreground change. D's title is said with its focus.
- A Windows Forms form's focus with its foreground change dropped from the batch: the title is said.
- The foreground report taken first: the title is said once.
- The focus before the foreground report, in two batches: the title with the focus, and the report then ignored.
- Shift+F10 then Escape in the form: no title on the return.
- A combo box list opening and closing: no title.
- A named Windows Forms drop-down entered: spoken only as the presentability rule says.
- An owned dialog opening and closing: its title, then the main window's.
- A return from Verbatim's menu: the title.
- A nameless foreground window, and a chain with no entry for it: nothing added.
- The chain entry's words equal to the foreground report's for the same window, within one backend only, since a UIA entry and an MSAA window read can differ in name.
- Attention unchanged by the rule.

Scenarios: `text_box_editing` and `second_application_and_verbatim_menu` expect the title in every run; `menu_and_settings_dialog`.

### Departures from NVDA, for the parity ledger

- A Windows Forms form or dialog brought to the front with its focus within NVDA's 10 ms pump says its title, where NVDA says none (`two-same-named-dialogs.txt` and `classic-context-menu.txt` in `experiments/focus-pipeline-rework-measurements/captures/`). So does a Windows Forms main window when a dialog closes.
- A focus reported before its window's foreground change arrives, its window already in front, says the title with the focus, where NVDA drops the later foreground change as a repeat.
- A focus raised before its window's foreground change within one pump says the title and then the focus, where NVDA says the window and loses the focus.
- The return to the user's desktop after the secure desktop says the title, where NVDA normally says the focus alone (untestable until M8.1).
- Known difference: on the first Escape from Windows 11 Notepad's WinUI context menu, NVDA says "Untitled - Notepad" (`keyboard-opened-context-menu.txt` in the same folder). The menu is a popup in Notepad's foreground, so the title rule adds nothing; Verbatim says the title only when Notepad's foreground report is not dropped from its batch.

Repeats come before the followed focus because the unread facts replace what `CoreFocus` told the readers, and the gap comes last because it closes on unread repeats as reports. ### Read requests and Core's foreground

Reversed by Dickson's decisions of 2026-10-30 (`docs/design/ownership.md`): kept only as a record of what was designed; not to be built.

Today. Core never asks a reader to read: the listener and the outposts drop a repeat against the focus Core holds, which Core tells them after every judgement (`CoreFocus`). The outpost drops a foreground change as a repeat against `Held`, NVDA's two foreground tests (`IAccessibleHandler/__init__.py`, `processForegroundWinEvent`, 816 to 864), and after reading the window looks again whether it is still in front (`report_foreground`). Core tests a focus against the foreground a second time on the facts read at report (`classify`, `ForegroundRelation::related`). Core keeps four notions of the foreground: the attention record, `foreground` (an `ObjectKey`), `foreground_changed_at` and the newest focus's top-level window. The app drops a focus in an ignored process's top-level window (`in_ignored_window`), a judgement outside Core.

The read request, defined once (Core, the app, every reader):

- Core asks for a read only of an unread fact it does not take as a repeat, naming the fact's trace, its reader (the listener or one outpost incarnation) and its application (`Effect::ReadRequest`). The app routes it as a command (`SupervisorToOutpost::ReadRequest`). Reason: only Core holds the focus every repeat is judged against, and it is the only process that can tell a repeat from a return.
- Core first judges the unread fact as it judges a report: a fact the stale rule or an application refusal would drop is dropped with no request (`docs/parity/focus-events.md`, "Stale focus events"), so no round trip is spent on a focus that could not be taken. Core sends no refusal notice for an unread fact it drops, since an unread fact is not a report and moves nothing the outpost follows.
- A fact's stamp is its event's observation, but a foreground change's, unread or read at once, is the time the outpost's front test confirmed its window in front, as `report_foreground` stamps it today (`worker.rs`, `confirmed_at_us`), so Notepad's foreground change raised before the desktop list's last focuses is not stale against them (b1917eed; Core's `notepads_foreground_report_after_the_desktops_last_focuses_is_spoken`, kept).
- An answer is judged stale within its application too: Core drops a requested read's report when it has applied, since the unread fact's stamp, a newer focus or foreground of that application from either reader, and the outpost then gets the refusal notice of the next rules if it holds a node there. Reason: NVDA reads at once, so a focus that came after the event is always handled after it; Verbatim's answer can arrive after it, and within one outpost Core otherwise orders by arrival. One compare per answer, against the newest stamp Core keeps per application.
- A reader keeps, per application, only its newest unread item, and an item stops being newest when the reader handles any later focus or foreground event of that application, read or unread; a request for anything else is answered gone, which saves the read when the reader has seen the newer event.
- The reader makes the read in its queue's order, after everything queued before the request: the listener on the application's reading thread, sending the outpost a marker first so the outpost holds what follows behind the read, as for any UIA focus; the outpost as an intake entry (`Item::ReadRequest`). The read skips NVDA's acceptance and keyboard-focus tests, made on the event.
- Every request has exactly one answer: the report, carrying `answers` (the request's trace) and the fact's stamp, or `ReadGone`, also when the reader drops the read for any reason (an element gone, a verdict, a hung window). The listener's gone answer travels as its read would, a drop resolving the request's marker in the outpost, which relays it to Core, so it never reaches Core ahead of what the outpost holds behind the marker. Reason: the idle barrier needs an end for every request.
- Core counts a request in progress until its answer is reduced, and the harness's idle round waits on it. The app answers gone every request still open when its route ends: at `Input::OutpostEnded` every request of that application, the listener's included, since the listener's answers pass through that outpost; at the listener's replacement, when the supervisor sends `UiaFocusReadsEnded`, every request to the listener.

The foreground (outpost worker, Core):

- The outpost's foreground test is the one test, made when the event is handled (`accepts`, `in_front`), as NVDA makes it once in its pump (`docs/nvda/events.md`, "Foreground windows"). `report_foreground`'s second look and Core's second acceptance test of a focus (`classify`'s `ForegroundRelation::of_facts`) go (audit difference 12). `in_foreground` stays on the wire, for attention.
- Right after the front test, in NVDA's order, the outpost judges a foreground change by its own last report, the followed focus's record: its window is the change's window or a child of it (`IsChild`, local), or the record came from the change's event address. Such a change is sent unread (`Input::ForegroundRepeat`: the window, the event address and the window facts the acceptance test already read, so no call is added); any other is read at once. A repeat restamps no gap record.
- Core drops an unread foreground change when its focus's top-level window is the change's window, which stands for both of NVDA's tests: a foreground window is a top-level window, so a focus in it or at its event address has it as its top-level window. Dropped or not, it refreshes attention from its window facts, as a foreground report does today (`reduce.rs` 896). Otherwise Core sends a read request; the outpost reads the window (`read::foreground_window`) and reports it.
- Core keeps one foreground record, set at one point of `reduce_event`: the attention (application and window facts), the real foreground window, and the foreground object, the chain entry whose window handle is the real foreground window, else the chain's top below the desktop, as `docs/nvda/events.md`, "What a focus event actually does (doPreGainFocus)", takes the object in the foreground and falls back to the ancestors. The real foreground window comes with each report (`WindowFacts::foreground_window`, the `GetForegroundWindow` the outpost already reads for `in_foreground`). The record replaces `foreground`, `foreground_changed_at` (the background drop's stamp, now a field of it) and the four notions; the keyboard hook's `foreground_window` stays apart and judges nothing. The foreground object is never spoken.
- The ignored-window rule moves into Core: a focus report's `WindowFacts` carries the top-level window's process (`top_level_pid`, one local `GetWindowThreadProcessId` in the outpost per focus report, the call the app makes today, moved rather than removed; other events carry none), and Core refuses a focus whose top-level window belongs to an ignored process, from the ignored list the app gives it at start (`Input::IgnoredProcesses`), as data. Reason: the app decides nothing about a focus.

A foreground change and a focus in one batch (the title lost on return). In `text_box_editing` (2 of 3) and `second_application_and_verbatim_menu` (1 of 3, `rework-runs/group1`), Escape closing Verbatim's menu back to the Windows Forms window put the outpost's foreground change and the edit's MSAA focus in one batch, the worker waking 12 ms after the push; tried newest first, as NVDA's `pumpAll` does (`IAccessibleHandler/__init__.py` 1060 to 1068), only the focus was handled. ### Repeats end to end

Reversed by Dickson's decisions of 2026-10-30 (`docs/design/ownership.md`): kept only as a record of what was designed; not to be built.

Today. The listener drops a UIA focus whose sender `CompareElements` equates with Core's focus element while that element reads `HasKeyboardFocus` true (`HeldElements`, `CoreFocus`), and compares nothing while a focus awaits Core's judgement; the outpost drops an MSAA focus at the address of Core's focus (`Held`). A focus returning to an element while `CoreFocus` is in flight is dropped and never spoken (audit difference 10).

The rules (listener reading thread, outpost worker, Core):

- A reader makes NVDA's duplicate test only against its own kept read, and only while that read is current, since NVDA tests against the last focus it queued (`UIAHandler/__init__.py`, `IUIAutomationFocusChangedEventHandler_HandleFocusChangedEvent`, 902 to 914; `IAccessibleHandler/__init__.py`, `processFocusNVDAEvent`, 772 to 776), which a visit elsewhere replaces. So a return onto the element left is read in full, as NVDA reads it.
- Currency in the listener is one stamp, the time of the newest change of top-level window among the focus and foreground events either of its sources observed, written by the callbacks with one `GetAncestor` of the event's window (the `WinEvent`'s, or the UIA event's cached window). The `WinEvent` and UIA callbacks run on different threads, so the last top-level window and the stamp are kept together under one small lock, taken once per event and never across a call, and the stamp only moves forward; a UIA sender with no cached window is placed by its reading thread after its nearest-window lookup, in order before the next event, as the Terms say. A kept read is current while its event's observation is no earlier than the stamp. In the outpost, a kept read is current while it has handled no focus or foreground event in another top-level window since, the listener's reads of its application included, since they pass through it, and its hook has delivered no foreground change (Dickson, 2026-10-29), which turned the five MSAA repeats Core did not hold in the measurements into full reads. The two readers judge currency each on what it observed, and may disagree for one application read by both backends; a disagreement costs at most a round trip, since Core judges every unread fact.
- The listener sends a UIA repeat unread (`DeliveredFact::UiaFocusRepeat`: marker, runtime id, the cached name and keyboard focus, the kept read's nearest window and top-level window); the outpost judges its window by its verdict as it judges a read, gives it the node its runtime id has, or none, and sends it in a commit that changes no follow state (`Input::FocusRepeat`, reader the listener). An unread fact never moves the followed focus: only a report does, the requested read's included, so a gone answer leaves the outpost following what it followed, as NVDA's duplicate leaves its focus where it was. The outpost sends an MSAA focus at its kept read's event address unread, never one whose kept read was a simple child (`NVDAObjects/IAccessible/__init__.py`, `isDuplicateIAccessibleEvent`, 863 to 872). An unread repeat ends a focus group's tries, as a duplicate counts as a valid focus in NVDA's `pumpAll` (`IAccessibleHandler/__init__.py` 1019 to 1110).
- Core takes an unread fact as a duplicate when its node is the live focus Core holds, updating the reading only with what the fact carries, never the spoken record (`docs/parity/focus-events.md`, "Duplicate focus suppression"); otherwise it asks its reader. Kept facts are not resent with it, since the listener's registration caches no value and no states beyond the keyboard focus.
- A report marks an MSAA simple child (`simple_child`, one byte), and Core never takes such a report as a repeat of a held focus that was one, so a reused child id is announced as NVDA announces it.
- The listener's newest unread item is its kept element; a request reads it, reusing the kept chain while current. The outpost's is the event address, reacquired on request.

Speech: unchanged on the steady path, as the measurements found every current UIA repeat held by Core (0 of 178 unheld at arrival) and, with the outpost's currency rule, every MSAA one. A name change a repeat carried in is spoken when its event comes (already built). A return to Windows Terminal after a program changed its title reads the whole chain and says the new title.

Cost. A repeat Core holds: NVDA's test (two UIA calls; none for MSAA). For UIA, where today the listener's drop already crosses to the outpost behind its marker, the unread fact takes the drop's place and the outpost sends one message more to Core: one pipe crossing and one wake-up of Core's thread, beside the outpost's pipe thread and worker that the drop already woke. For MSAA, one message to Core and its wake-up. One Core does not hold: the request's round trip, then the read. Per focus and foreground event in the listener: one local `GetAncestor` and one uncontended lock. The first focus after a return reads its whole chain, as NVDA's does.

Tests. Removed: the listener's `the_element_compared_with_is_the_one_behind_the_focus_core_holds` and `a_read_returning_after_it_was_abandoned_accepts_no_focus`. Updated: mockapp's `a_repeated_focus_on_the_still_focused_element_is_dropped_before_any_read`, which becomes `a_repeated_focus_on_the_still_focused_element_is_sent_unread`; `a_repeated_msaa_focus_is_a_duplicate_only_of_a_full_object`, to the simple-child rule. Added: the listener's `a_kept_read_is_not_current_after_a_focus_in_another_top_level_window`; mockapp's `a_return_onto_the_element_left_is_read_in_full`, `an_msaa_kept_read_is_not_current_after_a_foreground_change` and `a_repeat_answered_gone_leaves_the_followed_focus_where_it_was`; Core's `an_unread_repeat_of_the_focus_core_holds_is_dropped`, `an_unread_repeat_of_another_node_asks_its_reader_to_read_it`, `a_simple_child_focus_is_never_a_repeat`. Scenarios: `notepad_editing`, `rapid_tabbing_in_settings`, `explorer_folder_window`, `windows_terminal_tabs`.

Limitations. A focus in another top-level window raised with no event at all is not observed, so a kept read can be judged current across it, and its repeat costs a round trip. A request that finds a newer item is answered gone and nothing is spoken for it, a newer event having come.

### The followed focus, with `CoreFocus` removed

Reversed by Dickson's decisions of 2026-10-30 (`docs/design/ownership.md`): kept only as a record of what was designed; not to be built.

Today. Core tells the listener and the outposts its focus after every judgement (`CoreFocus`); the outpost keeps it with its unjudged reports (`Held`) and judges repeats, targets changes, gathers dialog text and finds MSAA equality's candidates against them, while it follows its newest report (`Tracking`). The focus-following subscription adds the new focus's group before removing the old one's in one move (`verbatim-uia`, `subscribe.rs`, `move_to`), but removes it in the same move, and in 2 of 10 runs of `settings_combo_box_expanded` the combo box's expand state change, raised 72 µs before the item's focus read reached the outpost, was delivered after the removal and lost.

The rules (Core, outpost pipe thread and worker, the registering thread):

- The outpost follows its newest report at once, in the report's commit, as today. Its followed focus is the one record of its kind: node, role, window, chain, the states last read, the MSAA event address and simple-child mark, the dialog memo. Every use of `Held` reads it: the changes it targets (its node and chain, the named exception of the 2026-10-29 decision), whether a state change newly expanded the focus, the dialog text's entered test, the walk's previous top-level window, and the foreground test above. The kept read (the last full read, for repeats) stays apart from it, so a repeat of a refused report still goes unread and Core asks.
- Core sends a refusal notice when it does not take a report of an outpost while it holds a node of that same outpost incarnation, a foreground report of the window holding the focus included: the report's trace and the node Core holds with its line, `HeldFocus::for_outpost`, the value `CoreFocus` carried. The notice carries the line because MSAA equality takes its candidates from the line Core holds (first build, "MSAA object equality"); with the followed focus always Core's line or the newest report, the candidates become the followed focus's chain alone. No notice is sent when Core's focus leaves an application.
- The notice is an intake entry, and the worker applies it in a commit only when its trace is the outpost's newest report, making the named node followed; an older report's notice is ignored. Reason: follow state changes only in a commit, and a newer report is judged by Core in its own turn. A requested read's report that Core drops as older than a newer focus of its application is a report Core did not take, so it brings the notice like any other.
- Moving the followed focus back to Core's node moves the subscription back: the refused report's element is removed and Core's node's added again, unless the refused focus was inside it, which the keep rule below leaves registered. A refusal therefore costs up to two moves, each one `AddEventHandlerGroup` and one `RemoveEventHandlerGroup` into the application on the registering thread, off the event path.
- The subscription keeps an old focus that the new focus is inside: on each move its scope is the new focus and every previously followed element that is in the new focus's chain by node id, each with its group, and an element is removed at the first move whose focus is no longer inside it. Reason: the old focus's events travel on the outpost's own route and the new focus on the listener's, so a removal made when the new focus arrives can discard what was raised just before it, while NVDA, receiving both on one route, removes the old group only when it handles the new focus (`api.py`, `setFocusObject`, 94; `NVDAObjects/UIA/__init__.py`, `event_gainFocus` and `event_loseFocus`, 1623 to 1630). It keeps only ancestors because a late change of an old focus outside the new one would reach Core after the new focus and be dropped as no longer the focus, as NVDA's speech for it is cancelled as expired.
- A reused UIA runtime id with "not focused" evidence drops the node's text caches as "gone" does (the keep-id build, 5797c075, keeps them, a stated limit): the element now under the runtime id is another one, as NVDA's new object for it reads its own text pattern, so a cached pattern would read the old element's text. ### The hand-over's hold

Moved into the ownership refactor's reducer build (Dickson's decisions of 2026-10-30), with released events tried as today's batch; this section is that build's draft.

Today. Two places hold an application's events and release them at once. The supervisor holds the facts for a starting outpost, merged by key, and releases them on `Ready` (`HeldFacts`); the outpost then matches its hook's copies with the listener's by counting (`outpost::handover`). Either way the released events reach the intake together, which plans them as one batch, so a run of focus and foreground events is tried newest first and the foreground change is never tried. In `second_application_and_verbatim_menu` run 1 (`rework-runs/chains`) the listener observed the window's foreground change, then the edit's focus 7.6 ms later, then the form's and the edit's focus; released together, the edit's focus was reported and the window's title never said.

What NVDA does. Its pump runs at once for a focus event and within 10 ms for any other (`IAccessibleHandler/internalWinEventHandler.py`, `winEventCallback`, 193; `core.py`, `CorePump`, 990 to 1052, and `requestPump`, 1180 to 1199), so events that come one at a time are pumped one at a time, and its limiter merges only within one pump (`orderedWinEventLimiter.py`). It holds nothing at an application's start, having one hook. Its capture of `text_box_review_cursor` (`rework-runs/nvda-textbox`) says the new window's title in 3 of 5 launches, so whether a foreground change and the focus after it share a pump depends on their timing and on its foreground defer.

The rules (the supervisor, the outpost's pipe thread and intake):

- The outpost holds its hook's whole stream until `ForwardingEnded` arrives, handling the listener's forwarded copies as they come; then it drops its copies raised at or before the tick named and releases the rest, in raise order, ahead of anything the hook delivers later. The listener forwards exactly the copies raised at or before its tick (`listener.rs`, `HookInstalled`), so each event is handled once. If the listener ends first, `UiaFocusReadsEnded` releases the hold, dropping hook copies raised at or before the newest listener copy handled.
- `HeldFacts` keeps the facts in arrival order unmerged, up to 64, the writer's queue length, beyond which a fact replaces an older one of its key as today, or, with none, the oldest fact makes room, as the writer's queue does. Reason: a merge across what would have been several pumps moves a fact behind facts raised after it.
- Every released event, from either hold, is planned in a batch of its own (`DeliveredFact`'s `released` mark; the planner ends a batch before a released MSAA entry). Reason: each event would have been delivered alone, so a held event is handled as Verbatim's intake handles one delivered when it happened, which for a focus event is NVDA's immediate pump. A released non-focus event is not held for NVDA's delayed pump, which Verbatim's intake does not build (difference 17), so the hold changes nothing heard.
- The narrowing pair: the event thread forgets a window from it on the destroy event that clears its window cache.
- Removed: the two multisets, `TWIN_BOUND`, `ListenerBeforeHook`, `in_raised_order`, the raise-time half of the foreground change's removal of a waiting focus, `focus_raised_first`, and `HeldFacts`' merge below its bound.

Speech. `second_application_and_verbatim_menu` says "second-application", "Note edit multi line" and the line in every run, at the start and on the return: released one batch each, the foreground change is reported, the edit's focus enters the window, the form's focus is dropped by the focused-state test, and the edit's second focus is an unread repeat Core holds. NVDA says the title in 3 of 5 such launches; Verbatim saying it in every run is the recorded difference of NVDA's delayed pump and defer, which change no meaning.

Cost. Per outpost start, the hook's copies wait from hook-in to `ForwardingEnded`: a median of 20.6 ms, 68.2 ms at the 90th percentile and 591.3 ms at most over 126 starts, the maximum at Verbatim's start while the listener installed its UIA registrations (the step 1 measurements; the design's earlier figure was the relay's latency alone). No timer, `TWIN_BOUND`'s going. A released batch per event: one plan per event, no wake-up, since the entries are already waiting; but each released focus and foreground event is now judged and read, with calls into the starting application, where today's one batch is tried newest first and stops at the first report. That is what NVDA does with events that came one at a time, so it is kept, and the cost is stated: per released MSAA focus, its acquisition and focused-state test, and when focused its walk (the ledger's "A focus change, MSAA, cold"); per released foreground change, the window's read. In run 1 that is four events, one caret event, one foreground read, the form's focus acquired and dropped by the focused-state test (about three MSAA calls), and the edit's read, its second focus being an unread repeat with no call; at most 64 reads from `HeldFacts` and as many as were raised from the hook's hold, each bounded by the worker's deadline. Memory: up to 64 unmerged facts per starting application.

Tests. Removed: `handover.rs`'s ten tests, and the intake's `a_listener_copy_raised_before_the_hook_goes_ahead_of_the_hooks_copies_of_its_tick`, `a_listener_copy_ahead_of_one_raised_before_the_hook_goes_ahead_with_it` and `a_foreground_change_keeps_a_focus_raised_after_it_that_arrived_first`. Updated: the supervisor's `held_facts_release_in_arrival_order_and_a_repeat_moves_to_the_back`, which becomes `held_facts_release_unmerged_in_arrival_order_below_their_bound`. Added: the intake's `hook_copies_wait_for_forwardings_end_and_those_at_its_tick_are_dropped`, `a_listener_copy_delivered_after_the_end_is_handled_once`, `the_end_of_the_listeners_reads_releases_the_hold` and `each_released_event_is_planned_in_a_batch_of_its_own`; mockapp's `a_starting_outposts_foreground_change_and_focus_are_both_reported`, with run 1's order; the event thread's `a_destroyed_window_leaves_the_narrowing_pair`. Scenarios: `outpost_crash_recovery`, `return_after_retirement`, `explorer_folder_window`, `second_application_and_verbatim_menu`.

Limitations. A listener copy delivered after the end is handled after held copies raised later. Copies a dying listener held unforwarded are lost. A hold whose `ForwardingEnded` never comes lasts until the supervisor replaces the listener, nine seconds without a pong.

### The gap, closed by the outpost's own reports

Today. The record is closed by the answer the listener computes from each UIA focus outcome (`GapAnswer`, from `focus_read::gap_answer`): a read, a class-list skip or a verdict of NVDA's checks answers it, a drop for no keyboard focus or one replaced leaves it open, a drop for no window reads at once, a give-up answers it in any window. A read is placed by `GetAncestor` of its window as the intake takes it in (`intake.rs`, `read_answer`), and a window destroyed by then answers 0, so the read answers a record open in any top-level window, closing a copy of another window with nothing read. A read is final whatever the worker then does with it.

What NVDA does. Its fake focus reads the focus 50 ms after a menu or switch event only when its own focus object has not changed since (`IAccessibleHandler/__init__.py`, `processFakeFocusWinEvent` and `_fakeFocus`, 976 to 1003): what an event it dropped says closes nothing. The gap itself is Verbatim's own (decision 11), so only that closing rule is NVDA's.

The rules (outpost worker and watchdog, in commits; the intake's lock):

- A report closes the record: a read the outpost reports, its MSAA focus report, a focus published at its bound, the gap's read, a focus-now answer, or an unread repeat it sends. It closes it when observed no earlier than 100 ms before the record's stamp in the record's top-level window, or after the stamp in another. A foreground report in the record's own top-level window restamps it and never closes it, as the accepted foreground change does today, so a return whose UIA focus never comes is still read. Reason: the record waits for the application's focus to be told to Core, and only the outpost knows what it told.
- A report is placed by its own window facts' top-level window, which every focus report already carries (`window::window_facts`, `GetAncestor` with `GA_ROOT`, the rule the record's copy is placed by), so no call is added and a popup whose accessibility parent is its owner, such as a combo box's drop-down, is placed in its own top-level window as its copy is. A report with no window facts counts as in another top-level window, closing only a record it is newer than. This is the destroyed-window fix: today's `read_answer` takes a destroyed window's 0 as "any window" and closes a record of another window whose copy came first; now a report closes a record in another window only when its focus was observed after the copy, when NVDA's focus too has moved on. The newest report per top-level window is kept for the look-back, pruned on the window's destroy, as answers are today.
- The commit applies it under the intake's lock, nested in the commit's order, so a publication at the bound closes the record as a worker's report does.
- A drop carries no answer. It carries two facts the listener observed: that the sender had no window above it (`no_window`), and that the listener gave up on the application (`gave_up`: the read abandoned at `READ_DEADLINE` or by the moved-on rule, dropped by `ABANDONED_LIMIT`'s limit, or a nearest-window lookup that waited a second or more). On `no_window` the outpost reads at once in the drop's place, before or after the copy, as decided on 2026-10-21 for the burst of gone senders. A `gave_up` drop also carries its event's top-level window, placed by the listener as drops are today (one local `GetAncestor` of the cached or nearest window, made only for these drops), and the drop entry's observation is its event's; it closes the record unread only when the record is in that top-level window, or the drop is unplaced, and the record's stamp is no later than 100 ms after the event's observation, so it closes the record its own event's copy opened and never a record a later copy opened or restamped. This is the default taken pending Dickson's acceptance (Fable, 2026-10-30): NVDA says nothing for a focus whose call its watchdog cancels or that it cannot place. In the moved-on case the user's new window, of another thread, keeps its own record, which a give-up of the old window's read does not touch. Every other drop, and a read the worker drops (its verdict, Core's hidden frame, another process's window), leaves the record to its bound, whose read's local checks refuse the cases those drops refused.
- An accepted copy or foreground change in another top-level window no longer closes it unless it is reported. Removed: `GapAnswer`, `gap_answer`, the drop's placement `GetAncestor` but for a give-up, `read_answer`, `Intake::apply_gap_outcome`'s answers, and the accepted-elsewhere answer of `GapRecord::accepted`.

Speech. `settings_combo_box_expanded` keeps "Settings", "Settings window", "Region button", Settings' lookup failing in 1.1 ms and leaving the record to its bound. A focus whose listener read was given up is silent, as NVDA is by its source and its stall captures (`experiments/focus-pipeline-rework-measurements/captures/`); no capture exists of NVDA under a timed-out nearest-window lookup. A read the outpost drops in a window it judges not UIA, under a copy it judged UIA in another window, is followed at the bound by a gap read of the application's focus, which Core drops as a duplicate or, if the focus is new, speaks a second late; NVDA's fake focus reads in the same case.

Cost. Per UIA read taken in: one local `GetAncestor` fewer; per drop but a give-up: one fewer in the listener. Per report: a compare and two stores under the intake's lock the commit already takes, the placement coming from window facts already read. Per record: unchanged, two threadpool timer calls when answered and one wake-up at its bound. Added: at most one gap read per record no report closes, local checks first: a record whose UIA outcome the outpost drops, whose UIA focus was dropped by NVDA's checks (hung, not related to the foreground, Core's hidden frame, the console window's own focus) with no later report, or whose give-up is placed in another window. Today the listener's answer closed those; the read's local checks refuse the hung, background and hidden-frame cases with no call into the application, and the rest cost the gap read the ledger gives (`docs/performance.md`, "A WinEvent focus no UIA focus answers, and the gap's read"), which Core drops as a duplicate.

Tests. Removed: the listener's `a_drop_carries_its_answer_and_its_top_level_window`; the intake's `a_drops_answer_is_applied_as_its_marker_resolves`. Updated: `a_focus_events_drop_answers_its_gap_record_or_leaves_it_open`, which becomes `a_focus_events_drop_carries_whether_its_sender_had_no_window_and_whether_the_listener_gave_up`; the gap record's `an_answer_resolved_before_its_copy_is_judged_opens_no_record`, `an_answer_in_another_top_level_window_leaves_a_copys_own_answer_standing`, `an_accepted_focus_in_another_top_level_window_answers_the_record` and `a_destroyed_windows_answer_is_pruned`, to reports; `a_windowless_senders_read_answers_the_record_in_its_nearest_windows_top_level_window`, which becomes `a_report_is_placed_by_its_window_facts_top_level_window`; mockapp's eight `a_winevent_focus_` tests, to closing by reports. ### Facts owned by two processes

- The focus: Core's, and each outpost's followed focus, which follows its newest report, never an unread fact, and is corrected by the refusal notice, a requested read's dropped answer included.
- Repeats: each reader's kept read and its currency, judged by each on what it observed, against Core's focus, which judges the unread fact; a disagreement between the two readers of one application costs a round trip.
- The newest unread item: the reader's, named by Core's read request and answered gone when no longer newest.
- A requested read's order against later focuses of its application: Core's newest stamp per application, against which the answer is dropped.
- Read requests in progress: Core's count, ended by the reader's report or gone answer, or by the app at the end of the reader or of the outpost a listener answer passes through.
- Attention: Core's, refreshed from the window facts of every foreground fact, unread or read.
- The gap record: the outpost's, closed by its own reports placed by their window facts, with the listener's `no_window` and placed `gave_up` facts on a drop.
- The hand-over's tick: the listener's `WinEvent` clock when `HookInstalled` reached it, against the outpost's held hook copies.
- The held facts of a starting outpost: the supervisor's, released into the outpost's intake.
- The foreground: Core's one record, from the readers' one test and the real foreground window each report carries; the keyboard hook's window from the listener's report.
- The ignored processes: the supervisor's list, given to Core at start.
- The subscription's registered elements: the registering thread's, moved from the followed focus's commits, a refusal notice's included.

Decision (Dickson, 2026-10-30): a foreground change and a focus in one batch. Out-of-date focus events stay dropped, newest first, but a focus never drops a foreground change into a different top-level window: that foreground change is handled before the focus, so the window's title is said. A deliberate difference from NVDA's pumpAll, which drops it too; a burst within one window costs nothing extra. This replaces the optional-utterance default.


### Adversarial review of the second build: 8 Important

Reversed by Dickson's decisions of 2026-10-30 (`docs/design/ownership.md`): kept only as a record of what was designed; not to be built.

1. Read requests: a stale requested read can replace a newer focus. The reader keeps its newest unread item, but Core orders by arrival per outpost. F6 raises UIA focus on A; listener judges a repeat and sends it unread; Core holds D so it requests a read. Same with the gap read, a focus-now answer or a foreground report standing in for D. Possible fixes: Core drops an answer when it has taken a newer fact from that outpost incarnation since the unread fact, or the outpost answers gone for both readers.

2. Read requests and the foreground: the stamp change undoes the Notepad fix. The request or the gone answer must restore the followed focus.

6. The gap: placing a report by its chain changes which record it closes. Placing by the chain's outermost entry differs from the record's GetAncestor placement for popups whose accessibility parent is their owner (example: WPF combo box popup, a separate top-level window whose UIA chain runs through the combo box to the main window; needs a live check). The item's UIA report, observed before its copy, lands "in another window" and closes only if observed after the stamp, which it was not; the record runs to its 1 s bound and the outpost makes a gap read on every such item. Today's read_answer places by the nearest window and closes it. The cost section counts gap reads only "whose UIA outcome the outpost drops".

7. The hold: the cost of reading each released event is not stated. Each released event is planned alone, so every held focus is read, with calls into the starting application, up to the 64 kept facts; today a batch is tried newest first and stops at the first report. ### A spliced ancestor released by `NodesHeld` (the first possible defect)

Built by the ownership refactor's reducer build, through its release rule; not built here.

The sequence that makes it real. Core's focus is in application B and Core holds no node of application A. A's focus F1, in container C of window W, is observed before B's newest focus but reaches Core after it, so Core drops it as stale and sends no notice, holding nothing of A. A follows F1. ### The outbound merge (the second possible defect)

Still this build's: the refactor's merges reproduce today's, and these evidence fixes are built here (Dickson, 2026-10-30), without the clause on `answers`, since read requests are not built.

The states themselves cannot differ: a state change carries the complete set, and the newer replaces the older. What a merge loses is what the older message carried about its own change:

Where it runs: the outpost's outbound queue, `merged`.

The rules: a report carrying `answers` is never merged, as no answer to Core's request is. A merged state change keeps the older's child count when the newer has none and its states still include expanded.
