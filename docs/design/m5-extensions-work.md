# M5 work plan: Extensions v1

The order of work for M5, the tests that prove each step, and what each step leaves behind. The design it implements is `extensions.md`, whose section 4 is the pinned surface and section 5 an example of the manifest's shape. The roadmap's M5 entry points here; this file is the detail, the roadmap keeps the exit criteria.

Vocabulary used below, defined in the design: a module is one unit of behaviour for an application (app module) or a speech engine (synthesizer module); an extension is an installed bundle of modules; a built-in is a module folder shipped with Verbatim under `extensions/builtin/`; a rule is a matcher plus an action applied by the host as data; a hook is a function a module exports and the host calls; a capability is a group of host functions a module imports, derived from the component's imports and never declared; only the sentences naming something of the user's or code outside Verbatim's control are shown at install.

Each step is reviewed as `REVIEW.md` says: one adversarial review of the step's whole implementation, fixes in one commit, one re-review, stop. The end-to-end scenarios named under each step run before the step is called done; the full suite runs once at the end of the loader step and once at the end of the install step, because those two change how Verbatim starts.

## Order of work

### Step 0: M4.4, the precondition

The roadmap places M4.4 (message types in their final home) before M5 because the extension API exposes events and commands. It is not done: `crates/verbatim-outpost/src/protocol.rs` still reads `verbatim_core::SNAP_RESULTS_ACTIVITY` and the outpost crate depends on `verbatim-core`. M5 starts when M4.4's exit criteria hold, so the WIT event types and the rule tables are defined against the types in their final home.

### Step 1: snapshot properties and application identity

What: `NodeDetails` gains the UIA class name, automation id and framework, which the outposts already cache, the window class of the node's window from the window cache, and for MSAA nodes the control id, which is one new `GetDlgCtrlID` call per MSAA snapshot and is recorded in the performance ledger as such. The supervisor resolves each outpost's application identity at launch: the executable name, replaced by the console client's for a console window, the hosted application's name from the application user model id for `wwahost.exe`, and the parent process's executable for `msedgewebview2.exe`. Core keeps the identity per outpost beside the attention record. The listener learns a process's identity the same way, with one local image-name query per process id, cached, so window and event rules can be scoped before any outpost exists.

Why first: every rule and every module binding keys on these, and `verbatim-inspect` shows them for diagnosis whether or not a module exists.

Tests: unit tests in `verbatim-uia` and `verbatim-ia2` that the mapping fills each field from a cached element and leaves it empty when the backend lacks it; a `mockapp` scenario asserting the exact five values cross-process for one scripted provider; the `verbatim-inspect` focus dump shows them; the performance ledger records the added bytes per snapshot and the one new MSAA call, and the latency scenario is unchanged for UIA.

### Step 2: rules

First, `verbatim-model`'s `StateSet` keeps only independent states: checked and mixed become one optional check state (unchecked, checked or mixed) and expanded and collapsed one optional expansion state, so neither a backend nor a rule can make a node both checked and mixed or both expanded and collapsed (Dickson, 2026-10-28). What a provider that reports both maps to, and so what is spoken, is taken from NVDA's pinned source and a capture before this is built.

What: `verbatim-ext-api`, a platform-neutral crate added to xtask's neutral list, holds the WIT files, the manifest and rule types (`module.toml`, rules with a subject of `window`, `event` or `node`, the matcher properties and actions of the design's section 4.2) and their validation. Every rule is scoped to the sender's application identity, which must be one the module claims; a window or event rule is consulted only for windows and events of those identities, which is NVDA's per-process scope for `isGoodUIAWindow`, and is what the install sentence "changes how Verbatim reads the named applications" promises. Compilation of rules into the tables the code consults today, keyed by identity: window rules into the arbitration and ignored-window tables used by the listener and the outposts, event rules into the acceptance filter with acceptance implying an outpost start, node rules into a matcher list applied where the outpost emits a snapshot, writing each change with its provenance. Every rule carries a required `id`, unique within its module, and the log and provenance name a rule as `<module>/<rule id>`. The four Explorer constants and Task Manager's list are this step's fixtures and become a built-in manifest in the next step.

Tests: one unit test per refusal in validation (a property of the wrong backend, a pattern in a window rule, an unknown action for a subject, a missing backend on a node rule, an identity not claimed by the module, a missing or duplicate rule id, two window or event rules of one module naming the same class with different actions); matcher evaluation over a snapshot for every property and combinator; table compilation producing exactly the tables the constants produce today, asserted against the current constants so behaviour cannot drift; a `mockapp` scenario where a node rule sets a role and the focus dump shows the new role and its provenance; a rule for an identity other than the sender's does not apply; two node rules of one module contesting one property log the warning once and the later wins; provenance for a value no rule touched names the backend.

### Step 3: built-in module folders, the loader, and the log

What: `extensions/builtin/<module>/module.toml` in the repository; `cargo xtask build-extensions` places each module folder under `target/debug/extensions/builtin/`, beside the executable the end-to-end suite runs, and `cargo xtask ci` runs it, as do the end-to-end and `ci-arm64` jobs. Core loads every built-in at startup, each independently, and a failure is logged as an error and spoken once as "Built-in module <name> failed to load". Explorer and Task Manager land as rules-only modules, and the Explorer scenarios stay green with the constants deleted from the code. Task Manager auto-elevates on an administrator account and is unreadable end to end until UIAccess (M8.1), so its proof here is a `mockapp` scenario.

The log, pulled forward from M9 in its smallest form because extension warnings need somewhere to go: an in-memory ring behind the existing tracing subscriber plus the file it already writes; a log viewer window in the Verbatim menu, which is a new window kind in the GUI's C++ (today it has the settings dialog and the list dialog), with a new `GuiCommand` and a new `ScriptAction`, sized as D4 work; Verbatim+F1 (Dickson, 2026-10-22) writes the navigator object's developer information to the log (the snapshot with its details, provenance per field, outpost, application identity, the module instances active there) and opens the viewer, as NVDA's key does for its navigator object; the navigator is the focus until the review cursor exists. Module log lines carry the module id. The rest of M9 (levels, categories, the recent-error command) stays in M9, whose roadmap entry is amended.

Tests: a unit test that the loader skips one broken manifest and loads the others, with the exact error text; an end-to-end scenario launching Verbatim with a fixture extensions directory containing one broken built-in and asserting the one spoken sentence and the log line; `explorer_` scenarios unchanged; a `mockapp` scenario with a scripted `SysListView32` window and a `TmRowIcon` child proving Task Manager's two rules; a scenario pressing Verbatim+F1 in Notepad and asserting the viewer window's title is spoken and its text contains the focused edit's class name and application identity; a unit test that the ring keeps the newest lines when full.

### Step 4: the component host

What: `verbatim-ext` embeds wasmtime (the one crate that names the runtime, as D6 asks) and links the `verbatim:ext@0.1` world: the hooks and imports of the design's sections 4.3 and 4.4, with node reading as thin bindings over the outpost's own reading functions on the worker, never a second query implementation, so a module sees exactly what its outpost sees and the outpost's process-boundary stop (by the outpost's resolved identity) is the only gate; readers lacking the stop gain it once here, output as effects to Core, commands resolved in Core by the ordering rule and run in the module's outpost (one Core-to-outpost-to-Core round trip per module command, counted in the communication design), process facts from the supervisor, settings read-only, log. Speech imports are enforced by attention: a module cancels speech only while its application holds attention, and a module whose application does not speaks at queued priority, as D14 treats background events. The extension world imports no WASI interface. Budgets: the outpost's alarm is re-armed at hook entry to the compute bound and restored at return, and extended by each read's duration, so interrupting a hook costs timer calls on the event path, which the ledger states; reads are refused once the worker's remaining handling deadline is spent; a trap counts as pass or no change, the instance is re-created from the pre-linked form, repeated faults unload the module for the outpost's lifetime with one report. Precompilation: Core compiles a component once into a content-named file in a cache directory and outposts map that file, never the source, so the source can be overwritten while modules run. Per-module hook counts and times in `verbatim-inspect`. Latency (Dickson, 2026-10-22): each event that passed through a hook carries a `LatencyStage` of a new module kind in its timeline, the worker's time inside module code split into guest time and host-call time, with the module's reads as its call counts, so `verbatim-inspect latency` attributes a slow event to the module per event; a rules-only module adds no stage. A module command adds the same stage kind for its outpost run on the hook-to-Core path. The call ledger gains two permanent rows ratcheted against mockapp: a rules-only module leaves every count unchanged, and a module with one descendant read adds exactly one UIA call and nothing else. The host-call overhead measured for ratification is recorded as a ledger entry in the same units. The call console: `verbatim-inspect call` invokes any function of the world by name with WAVE-encoded arguments through the host's dynamic call path. Ratification of the runtime: the host's tests run on `ci-arm64` under Cranelift and under Pulley, and host-call overhead is measured on both architectures against a provisional compute bound recorded in the ledger, replaced by the measured one in step 8.

Tests, all against the surface and none against application logic: a test component per import and export built in the extension tests workspace, round-tripping every type; a looping component interrupted within the bound with the worker still alive; a component that grows memory past its limit contained; the outpost's readers over a fake element source, a parent walk stopping at the process boundary and a descendant search skipping a foreign subtree, called through the module bindings; an end-to-end scenario with a test module claiming Settings whose `parent()` walk from the focused control logs none where ApplicationFrameHost's frame begins; a component importing a function outside the world, including any WASI interface, refused at load with the exact message; a background module's cancel refused and its speech queued; a reload of the same component id swapping between two events; the precompiled cache reused across two outposts; hook statistics visible in `verbatim-inspect`; the module stage present with its call counts in the timeline of an event a hook handled and absent for a rules-only module; the two ledger rows passing the ratchet; every interface of the world callable through `verbatim-inspect call`.

### Step 5: the guest workspace and the first Rust modules

What: an `extensions/` Cargo workspace, separate from the host workspace so the platform-neutral check and `workspace-hack` never see a Wasm target, holding the guest SDK crate under its own permissive licence, the test helper, and the module crates. Guests build for `wasm32-unknown-unknown` with `wit-bindgen` and are wrapped into components by `wasm-tools component new` without a WASI adapter, so they carry no WASI import; `cargo xtask build-extensions` builds, validates against the world and places `<module id>.wasm` beside each `module.toml`; the CI jobs add the target. The test helper loads a component against a fake tree and asserts verdicts and speech. Calculator (the hook reading the result element on the display-updated notification, which is where NVDA's spoken result comes from, and the result keys declared as pass-through commands) and Notepad (the status bar provider, the go-to-line role rule) as the first Rust built-ins, each through the `/port` protocol: captures first, scenarios from captures.

Tests: Calculator's and Notepad's own unit tests over the generated types and their integration tests through the helper, run by the xtask; end-to-end scenarios pinned from captures: Calculator's result after Enter, Notepad's status bar command and the go-to-line box.

### Step 6: hot reload

What: Core creates the developer folder if it is missing and watches it always, and watches the built-in directory when the developer setting is on; debounces; validates the new version fully (manifest, API version, rules, imports, compilation); rebuilds the merged tables; tells each hosting outpost to instantiate, run the load hook and swap between two events. Speech: "Reloaded <module>" or "Reload of <module> failed" with the first line of the reason, the previous version continuing. The developer folder's modules sit above installed ones in the ordering and a duplicate id fails the later one. The watch covers the whole module folder, so a `module.toml` change reloads the same way (rules rebuild the tables, hook registrations re-route, a changed applications list starts or ends instances, changed commands rebind, which is why module gestures are rebindable at run time with an open command id); one reload path reloads the module whole, and a folder appearing in the developer folder loads a new module while a folder removed unloads one, each spoken.

Tests: an end-to-end scenario with a fixture module in the developer folder in three versions: the first speaks one word on a notification, the second a different word, the third does not compile; the scenario copies each in turn with the agent's file verbs and asserts the reload sentence and the word heard afterwards, with the failed third leaving the second's word; the same for a built-in with the developer setting on; a unit test that a burst of writes produces one reload. A rules-only fixture whose manifest changes a role between two saves, asserting the new role on the next focus and no component involved; a fixture folder removed and the module unloaded.

### Step 7: installing extensions and the Extensions dialog

What: the `.vext` bundle, a zip with the extension `manifest.toml`, module folders and a `locale/` folder, read with the limits the theme packager already enforces, extracted to `extensions/<id>/` under the configuration root beside the executable, as the design says, so the suite's fresh stage per run isolates scenarios. Capabilities derived from each component's imports at install and again at load; an import outside the world refused with a message; an installed extension may not claim Verbatim's own executables as identities, since Verbatim reads its own dialogs through an outpost. Install is a request to the running instance, as NVDA does it: the `.vext` file type is registered (by the installer later; by hand now) to a small helper executable, not to `verbatim.exe`, exactly as NVDA registers `.nvda-addon` to `nvda_slave.exe addons_installAddonPackage` (`installer.py`, `nvda_slave.pyw`); the helper sends the path over the control plane to the running Verbatim, which shows the dialog, and exits, or shows a message box that Verbatim must be running when nothing answers, as NVDA's does. `verbatim.exe` gets no install flag, so its single-instance takeover (`single_instance.rs`) is never involved. The install dialog: name, version, author, description, the modules and the applications they claim, the shown capability sentences, the commands one per line with their default bindings, with Install and Cancel. Installed extensions load after built-ins, newest highest. The Verbatim menu gains Extensions: a list dialog, built on the existing list dialog, showing each extension's name, version and status (loaded, partly loaded, failed with reason), a details view with the description, the shown sentences, a "show everything" line for the silent ones, and the module's activity counts, and Uninstall with a confirmation that unloads the modules and removes the folder. No store, no updates, no reordering in this milestone. Startup failures of installed extensions are one spoken sentence and a status in this dialog.

Tests: unit tests for the package reader (size and count limits, a path escaping the bundle, a missing manifest, a module naming a file not in the bundle, a claim on Verbatim's executable); a unit test that a component importing an ungranted function is refused at install with the exact message, which is the roadmap's capability-denial criterion; end-to-end: install a fixture `.vext` through the control-plane request, hear the dialog's title and the first shown sentence, confirm, hear the module's effect, open the Extensions dialog, hear the name and status, uninstall, confirm, and the effect is gone, with the scenario's cleanup deleting the extension folder on failure too; a second fixture whose manifest claims a module file that is missing is refused and the reason is spoken.

Tests, the same for every module here and later, by the `/port` protocol: a capture series on the VM with the pinned NVDA build checked against the submodule first; one end-to-end scenario per ported behaviour asserting the exact utterance the capture gave; the module's unit tests over its decisions and integration tests through the helper; the parity ledger lists each behaviour with the scenario that pins it; the sleep-mode list has a scenario. A module is done when all of that is green.

### Step 9: the Windows Terminal twin rule

What (Dickson, 2026-10-22: a module, not core, since application-specific logic is not to be hard-coded in Verbatim): the twin rule as an `on-event` hook in a Terminal built-in, registered for UIA focus events on `TermControl` in Terminal's outpost, placed after the listener's read (the design's section 6). The surface grows by one property and one verdict for it: the UIA runtime id as a UIA-only node property, always filled from the cache and shown in the focus dump; and the `adopt` verdict, meaning this sender is the current focus's element, keep the node, say nothing new, and follow the sender, which the outpost implements by moving its focus-following subscription while keeping the node. No same-element import is needed, because the event reaches the module only after the listener's `CompareElements` judgement has found the two different. The other four twin conditions are already readable: class name, control type and framework from the node, the same process by the module living in Terminal's outpost, and `node.window()` against `focus().window()`. The evidence the roadmap asks for, that the runtime id's last part is never reused within a process, is collected first, with the identity judge in `experiments/windows-terminal-raises-focus-from-a-second-runtime-identity/`.

Tests: those of `windows-terminal-twin-focus.md`, "The judge", including that the terminal is followed afterwards and two panes in one window; the `windows_terminal_` scenarios without the optional repeated "terminal"; a unit test in the module over the runtime-id suffix comparison; a host surface test that `adopt` moves the following without a new announcement.

## Hot reload for built-ins, stated once

A developer edits a built-in's crate, runs `cargo xtask build-extensions`, which rebuilds the component and copies it over `target/debug/extensions/builtin/<module>/<module id>.wasm`. The running development Verbatim, with the developer setting on, sees the write, validates, swaps, and says "Reloaded <module>". Overwriting works because no process maps the source file: Core read it once to compile it into the cache, and the outposts map the cache file. Without the developer setting the change takes effect at the next start, which is the released behaviour.
