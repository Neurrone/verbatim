# M5 work plan: Extensions v1

The order of work for M5, the tests that prove each step, and what each step leaves behind. The design it implements is `extensions.md`; the surface as authors see it is the Extensions guide's reference (`books/extensions/src/reference/readme.md`), settled with Dickson on 2026-11-09. The roadmap's M5 entry points here; this file is the detail, the roadmap keeps the exit criteria.

Vocabulary used below, defined in the design: a module is an app module, a global module or a synthesizer; an extension is a bundle of modules, and Verbatim's built-ins are one internal extension; a rule is a matcher plus an action applied as data; a hook is a function a module exports and Verbatim calls; a host is the process running one extension; a lane is one thread in it, one per outpost it serves and one per global module; the loader is the Core thread that reads, validates and compiles extensions.

The steps are built as four builds: A, steps 1 to 3, designed in [m5-build-a.md](m5-build-a.md); B, steps 4 to 6; C, step 7; D, steps 8 and 9 (Dickson, 2026-11-09). Each step is reviewed as `REVIEW.md` says: one adversarial review of the step's whole implementation, fixes in one commit, one re-review, stop. The end-to-end scenarios named under each step run before the step is called done; the full suite runs once at the end of the loader step and once at the end of the install step, because those two change how Verbatim starts.

## Order of work

### Step 0: M4.4, the precondition

Done: the messages are `verbatim_model::protocol`'s ([the messages build](../../books/dev/src/explanation/design/ownership.md)), so the WIT event types and the rule tables are defined against the types in their final home.

### Step 0b: the design restated, and the host designed

The design was restated with Dickson on 2026-11-09 against the outpost's reducer and the decisions of that session. Before step 1, this step writes what the restatement leaves to design, each lifecycle with its table of states and the rules that read them, and gives it one adversarial review:

- The host: one program, `--extension <id>`, one process per extension, the built-ins' started with Verbatim and always running; one lane per outpost served and per global module; each store's deadline callback checking its own hook's time, since the epoch is the engine's; the pipes between a host and an outpost made by the supervisor, read by the outpost as it reads Core's, and the outpost judging requests by the pipe; the built-in host restarted with the outposts' backoff when it ends; the host's memory and start-up time measured, and the built-in host's memory cap set from them, measured with many outposts open.
- The extension lifecycle in Core's reducer, as `extensions.md` section 2.2 tables it: `Loading`, `RulesReady`, `Active` with the built-in's set of modules turned off, `Failed` and `Disabled`; the loader's two results per extension, the user's enable and disable, the breaker and a host's end as its inputs; the published generation, which a spare outpost's assignment carries; the listener's `Ready` held until the built-in extension has left `Loading`; the outposts' and the listener's swap at an intake boundary; each kind of stale judgement's one action; a lane dropping an old instance at the first call naming a newer version.
- The hook state in the outpost's reducer, as `extensions.md` section 4 tables it: each host's pipe `Waiting` or `Ready`, and `NoHook` or `AwaitingHook` holding the event intake, every host message a reducer input naming its call, each read a program named by its call; the hook chain's resolution as a pure function in `verbatim-outpost-logic`, called by the reducer on each verdict, `pass` and `rewrite` continuing the chain and `drop` and `replace` ending it.
- A module command, a status-bar request and a list dialog as entries in Core's request table or the owning lane's record, each with exactly one answer path across an unload, an outpost's end, a host's end and an abandonment; a list dialog's `None`, `Held` and `Open` states keyed by the instance, its alarm, and the instance's end closing it with no answer.
- The breaker as a pure rule over failures to respond and their times: per module for built-ins, per extension otherwise.

Each later step adds its invariants and model checks to M4.6's generated tests: no hook runs on an unloaded instance, a failed reload leaves the previous version everywhere, two quick saves end with every outpost on the newest valid version, a list dialog has one answer. The rules' layering and validation, the matcher grammar, the capabilities derived from imports and the package reader get generated tests: the highest layer wins a contested property, `rewrite` and `on-node` changes accumulate down the chain, and a drop is never undone; every import maps to an install dialog row or is silent; no archive writes outside its folder.

### Step 1: snapshot properties and application identity

What: `NodeDetails` gains the UIA class name, automation id, framework and runtime id, which the outposts already cache, the window class of the node's window from the window cache, and for MSAA nodes the control id, one new `GetDlgCtrlID` call per MSAA snapshot recorded in the performance ledger. The supervisor resolves each outpost's application identity at launch, and the listener each process's, as `extensions.md` section 3 says; Core keeps it per outpost beside the attention record.

Tests: unit tests that each field is filled from a cached element and empty where the backend lacks it; a `mockapp` scenario asserting the values cross-process; the focus dump shows them; the ledger records the added bytes and the one MSAA call, and the latency scenario is unchanged for UIA.

### Step 2: the manifests, the matcher grammar and rules

First, `StateSet` keeps only independent states: one optional check state and one optional expansion state (Dickson, 2026-10-28), with what a provider that reports both maps to taken from NVDA's pinned source and a capture before this is built.

What: `verbatim-ext-api`, platform neutral, holds the WIT files, which are the single source of the host's and the guests' bindings, the manifest types for `manifest.toml` and `module.toml` with their validation, the one matcher grammar (exact, lists, several keys, `all`, `any`, `not`, `prefix`, `regex`, `at-least`, `below`) with its parser and evaluator, and the rule types for the three subjects. Its WIT files and manifest schema are written first and approved by Dickson interface by interface before anything implements them. `verbatim-reader-rules` compiles rules into the tables the listener and the outposts consult today, keyed by identity, and the loader places each rule from the properties it names: a focus veto naming only the listener's `ListenerEvent` properties in the listener and in the outpost for the focuses it reads itself, otherwise in the outpost; `normalize-class` in every reader that evaluates `window-class`, the listener included; an event drop in the first reader that has its properties, otherwise in Core. The Windows build and revision are matcher properties compiled at load. The four Explorer constants and Task Manager's list are this step's fixtures. Before the File Explorer constants are deleted, one of them, the Alt+Tab switcher items' dropped containers, is checked on Windows 11 with `verbatim-inspect dump-tree` in the Alt+Tab switcher and in Task View: if their windows differ in structure (window class, root class, the list's automation id or the item's framework), it becomes a rule matching that difference with `parent-automation-id` and a new node action that drops the focus's containers; if they do not, the choice of a general `modifiers-held` property returns to Dickson, and the rule stays in Core until he decides (Dickson, 2026-11-09).

Tests: one unit test per refusal (an unknown key, property, action or event kind; a property of the wrong backend; a window or event rule with no property at its top level; a missing or duplicate rule id; a rule in a global module); generated tests of the matcher grammar over arbitrary properties; table compilation producing exactly the tables the constants produce today; each rule's placement from its properties, with a listener veto applied to the outpost's read after a menu ends and a `normalize-class` rule seen by a listener veto; a `mockapp` scenario where a node rule sets a role and the focus dump shows the role and its provenance; a rule for an identity other than the sender's does not apply.

### Step 3: built-in module folders, the loader, the log and gestures at a version

What: `extensions/builtin/<module>/module.toml` in the repository, placed by `cargo xtask build-extensions` under `target/debug/extensions/builtin/`. The loader thread reads, validates and compiles every extension at startup, each independently, deciding conflicts from the whole set it found, and reports each extension's rules and then its code to the reducer, which owns the extension lifecycle, publishes the rule tables and hook registrations to the listener and the outposts at a generation, and holds the listener's `Ready` until the built-in extension's rules are published; a failure is logged and spoken once, "Built-in module <name> failed to load". Explorer and Task Manager land as rules-only modules, and the Explorer scenarios stay green with the constants deleted. The keyboard hook thread's gesture map becomes published at a version, so module commands follow install, enable and reload; a binding names a number of presses, and the hook thread stamps a raised gesture with `hold_until` only when its map binds the same keys to a higher count, and names the application whose binding it resolved. Authoring tools, on demand rather than in every report (Dickson, 2026-11-09): `verbatim-inspect matcher` prints a ready-made matcher for the focus or the navigator object in the manifest's TOML form; `verbatim-inspect dump-tree --properties` adds every matcher property, named as matchers name them; `verbatim-inspect match '<matcher>'` lists the nodes a matcher selects in the foreground application.

The log, pulled forward from M9 in its smallest form: an in-memory ring behind the tracing subscriber plus its file; a log viewer window in the Verbatim menu; Verbatim+F1 writes the navigator object's developer information to the log (the snapshot, provenance per field, outpost, application identity, active module instances) and opens the viewer, as NVDA's key does.

Tests: the loader skips one broken manifest and loads the others, with the exact error; an end-to-end scenario with one broken built-in asserting the spoken sentence and the log line; `explorer_` scenarios unchanged; a `mockapp` scenario proving Task Manager's two rules; Verbatim+F1 in Notepad opening the viewer with the edit's class name and identity; the ring keeping its newest lines; a gesture bound to two presses running its command on the second press, `hold_until` stamped only where a higher count is bound in the press's own map, and the published map's version; a cold cache's start judging the first focus with the built-ins' rules.

### Step 4: the host

What: `verbatim-ext` embeds wasmtime and links the `verbatim:ext@0.1` world in the host program only; no Wasm runtime is in Core, the listener or an outpost. Reads are requests from a lane to the claiming outpost, answered by the outpost's own readers on its worker, never a second query implementation, each stopping at the module's applications. Hooks are called by the outpost's reducer, which holds its intake while it waits for the host's answer or the end of its pipe, keeping no deadline of its own, since a hook call has one clock, its host's, and only a liveness bound that ends a stalled host ([extensions](extensions.md), section 4): `on-focus`, `on-event`, `on-node` once per emitted batch, `status-bar`; `on-command(command, trigger)` and `on-list-dialog` come from Core's reducer. Effects of a hook the outpost called travel back with its verdict and reach Core inside the event's report; effects of a hook Core called go from the host to Core; every `on-command` effect carries its press's key number. Speech is judged by attention, `speak-node` carries its node's snapshot and is built as a focus announcement is, list dialogs are shown by the GUI thread, and a click is the host's read of the node's place followed by Core's pointer move and click. Budgets: each store's own deadline for the module's execution, extended by each read's duration; the handling deadline for the whole call, counted by the host's lane from the call's start, after which the lane answers `deadline`; a trap counts as pass or no change, the instance is re-created, and the breaker counts it. Compiled code is mapped only by the extension's own host. Per-module hook counts and times in `verbatim-inspect`; a module stage in the latency timeline split into guest and host-call time; the call ledger's two rows ratcheted against `mockapp`. `verbatim-inspect call` invokes any function of the world by name through a host's dynamic call path. The host's tests run on `ci-arm64` under Cranelift and Pulley, and the round trip and host-call overhead are measured on both architectures, with the outpost's re-find of the focus's element, which a hooked focus now waits for on the first read needing a live call, measured against D15, and `on-node`'s round trip under an event flood.

Tests, all against the surface: a test component per import and export round-tripping every type; a looping component interrupted within its bound while other lanes' hooks run on; a component growing memory past its limit contained; reads stopping at the application's boundary through the bindings, and a global module's read of an application not in `reads` refused; a component importing a function outside the world, any WASI interface included, refused with the exact message; a background module's cancel refused and its speech queued; a reload swapping between two events; a list dialog replaced in place and held across a double press whose first command is slower than the multi-press window; a module's speech from `on-focus` spoken before the focus it was spoken for; a superseded press's speech dropped; a click from a list dialog's answer while a hook of the same lane is queued; a hook call answered `deadline` by its host, its reads not yet started withdrawn and each read answered once; a lane stuck in a native call ending its host at the liveness bound, every call in flight answered by the pipe's end and the stalled module counted by the breaker; the module stage present with its call counts for a hooked event and absent for a rules-only module; every interface callable through `verbatim-inspect call`.

### Step 5: the guest workspace and the first modules

What: a guest workspace separate from the host's, with the guest SDK under its own permissive licence and the test helper; `cargo xtask build-extensions` builds each module for `wasm32-unknown-unknown`, wraps it into a component with no WASI adapter, validates it against the world and places it beside its `module.toml`. Calculator and Notepad first, each through the `/port` protocol, and the Extensions guide's tutorial modules as compiled examples included into the book. An xtask step generates the guide's API reference from the WIT and its manifest reference and a JSON Schema from the manifest types, and `cargo xtask ci` checks both are current. Authoring tools: `verbatim-inspect watch-events --explain` adds, per event, the rule that matched, the layer that dropped it, each hook's verdict and the generation it was judged under; a template that creates a module folder with its `module.toml` and, for code, a crate wired to the SDK; and `dump-tree` output saved as a fixture the test helper loads.

Tests: each module's unit tests and its integration tests through the helper; end-to-end scenarios pinned from captures: Calculator's result after Enter and after a paste, Notepad's status bar and go-to-line box; the tutorial examples built and tested.

### Step 6: hot reload and the developer folder

What: Core creates the developer folder and, only in developer mode, watches it and the built-in folder; debounces; the loader validates the new version fully; the reducer publishes it and the host swaps between two events. The developer folder works as one extension, as the built-ins do: its module folders and a `locale/` folder for their strings, no extension manifest, loaded as one internal extension in one host of its own, the breaker counting each module (Dickson, 2026-11-09). A developer-folder module claiming an application an installed extension claims replaces that extension's module for that application while it is there (Dickson, 2026-11-09); two developer-folder modules claiming one application are refused, as two modules of one extension are. Speech: "Loaded <module>", "Reloaded <module>", or "Reload of <module> failed" with the first line of the reason (Dickson, 2026-11-09). A developer-folder DLL is never loaded from the developer folder: the loader copies it into the compiled-code cache under a name derived from its content and the host loads the copy, so a build can overwrite the original; a change is checked without loading it, its architecture from its header and its required exports from its export table, and, since a DLL cannot be unloaded safely from a running process, the developer folder's host is restarted with the new copy, its Wasm modules reloading with it; a failed check or start keeps the old copy running.

Tests: an end-to-end scenario with a fixture module in three versions, the third failing to compile and leaving the second's behaviour; the same for a built-in; a burst of writes producing one reload; a rules-only change taking effect on the next focus; a folder removed and the module unloaded; a developer module overriding and then restoring an installed one; two developer modules claiming one application refused with the reason spoken.

### Step 7: installing extensions and the Extensions dialog

What: the `.vext` zip, which its author makes by hand, extracted through a staging folder to `extensions/<id>/` under the configuration root from the one resolver M5 adds ([security model](security-model.md), X13). Capabilities derived from each component's imports at install and again at load. A second installed extension claiming an application, or two modules of one extension claiming one, refused. The helper registered for `.vext` sends the path to the running Verbatim over the user endpoint, or shows a message box that Verbatim must be running when nothing answers; the Extensions dialog's Install from file button needs no association. The install dialog as the guide's capabilities page lays it out and words it: the trust line, read-only name, version and author, the description, the Applications and Commands lists with their conflicts, Before you install when it has items, Install and Cancel; a refusal shown as one message with Close. The Extensions dialog lists each extension with its version and status, its details with the same lists, enable and disable for the whole extension, and Uninstall with a confirmation.

Tests: unit tests for the package reader (a path escaping the folder, a missing manifest, a module naming a file not in the folder); a component importing an ungranted function refused at install with the exact message; end-to-end: install a fixture `.vext` through the user endpoint, hear the dialog's first lines, confirm, hear the module's effect, open the Extensions dialog, uninstall, and the effect is gone, the cleanup deleting the folder on failure too; a second extension claiming the same application refused with the sentence spoken; a second install request refused while the dialog is open.

### Step 8: the remaining Windows inbox modules and the global modules

What: Explorer completed, Settings, Start and search, Quick Settings and Open With, by the `/port` protocol; the tray list, taskbar list and time as global modules, reading Explorer through `find-window` and MSAA as `ruifontes/systrayList` does, with the list dialog and the click; sleep mode as a core per-application list. With these running, the compute bound is set from the measured guest-time distribution.

Tests, by the `/port` protocol: a capture series on the VM with the pinned NVDA build checked against the submodule first; one end-to-end scenario per ported behaviour asserting the captured utterance; `tray_list_and_task_bar` listing Verbatim's own tray icon and opening its menu, then the taskbar on a double press with no tray dialog heard; the parity ledger lists each behaviour with its scenario.

### Step 9: the Windows Terminal second identity

What (Dickson, 2026-11-09): a focus veto rule in the Terminal built-in dropping every focus from a `TermControl` whose UIA runtime id starts 14, judged in the listener, with no hook. First, the experiment's judge is rerun with the order and the gap between the two identities recorded, since where the 14 comes first "terminal" is said only when the 42 arrives.

Tests: the terminal announced once and followed afterwards for each order of the two identities, and with two panes in one window; the `windows_terminal_` scenarios without the optional repeated "terminal".

### Step 10: documents

What: the Extensions guide's reference generated as step 5 says, its tutorials compiled, and its how-to guides written as their tooling lands; crate documents for `verbatim-ext` and `verbatim-ext-api`; glossary entries; D6 amended with the ratification measurements; CLAUDE.md's coding standards amended for the named targets (`wasm32-unknown-unknown` for guests, `i686-pc-windows-msvc` for the x86 host in M6); the M9 entry reduced by the viewer, and the M5 entry closed into `roadmap-done.md`.
