# Ownership: one owner for every fact

Status: the model, decided with Dickson on 2026-10-30, and built by five builds: the one judge, the input, the messages, the outpost's reducer and the output. This document keeps, for the model and for each build, the problem, the alternatives weighed, the reasons for the choice and the limits; the mechanism is in the crate guides (`docs/crates/`), which each area links. The rules each planned milestone follows are in [the milestone rules](ownership-milestone-rules.md); the evidence (the study, four audits, the three reviews and the decisions) is in `experiments/ownership-study/`.

## The problem

Most defects of the focus pipeline rework had one cause: a fact about one application was decided in two or three processes, and a decision waited on a message from another process arriving first. Two kinds of message let the class grow back after each fix: a message carrying Core's state to a reader for it to judge against (`CoreFocus`), and a reader skipping work on a judgement only Core can make. Inside an outpost, the same class between threads cost four review rounds on the publication at the bound. The aim is a model under which such races are impossible by construction where they can be, and confined to one named owner where they cannot, for all of Verbatim and its planned milestones. A change is in scope only when it points to a concrete past defect, or shows a sequence that would go wrong in today's code or in a planned milestone; everything else stays as it is.

The processes stay split as they are, for measured reasons: a UIA client call cannot be cancelled (`experiments/cocancelcall-does-not-end-a-uia-client-call/`), so only process exit reclaims a stuck thread (D9); a UIA element cannot leave the process that received its event, so the listener reads every UIA focus; the desktop-wide focus registration is costly and stalls with hung windows, so only the listener holds it; two Verbatim processes connecting to one application collide inside UIA.

## The scope rule

- Core decides every word, and every fact that spans applications: speech, attention, the foreground, repeats, the order of focuses, chains, text and terminals.
- Each outpost decides, for its own application only, which calls to make: the order of its two routes, verdicts, the gap, node identity and the caret watch. These decisions sit between two calls; each moved to Core would cost a round trip. Which changes it reads is not a judgement: it reads changes for every node it has not released, a superset of what Core holds, and Core's targeting decides what is spoken.
- The listener observes and reads. Before a read it makes NVDA's checks on its own observations of the event (hung, the console's element, acceptance against the foreground, keyboard focus) and applies NVDA's limiter to its own queue; it judges nothing against another process's state.
- Whether a UIA focus is read or skipped by its window's backend has one owner, the outpost's verdict rule. The listener applies only its probe-free part, NVDA's MSAA class list and the override, through the outpost's own code and tables, whose skips the outpost's verdict always also judges MSAA; every other window's focus is read, and the outpost's verdict decides whether it counts. This is NVDA's order, a class check before the read and one verdict per window (Dickson, 2026-10-30).
- The application rules stay where they are until M5 moves them into modules (D6).

D14 keeps its rules that attention moves only on a foreground change, the foreground is announced and never a gate, and focuses are ordered by when they happened. Only its clause on where the rules run is replaced, by: "each event rule is defined once; words and every fact across applications are judged in Core; what to read for one application is judged by its reader, from its own observations of the event, and by its outpost's verdict rule, which the listener applies only in its probe-free part; no state of Core is sent back for a reader to judge against."

## The rules

- **One owner per fact.** Every fact has one writer (the single-writer principle, [prior art](../../experiments/ownership-study/prior-art.md), "One owner per fact"), one thread or one state machine run by one thread; others learn it from one-way reports or from a view. A view inside one process is allowed only when it is ordered with what it judges, keyed by a fact its reader observes, or, for lifecycle only, a lagging copy whose staleness costs no word. A monitor, one module whose every operation runs under its own private lock that is never held across a call, never exposes its guard and never runs a caller's code, is one owner too. Reason: every reconciliation between two writers in the history was patched three to seven times. Evidence: the gap record moved between the listener and the outpost four times (01cba97e to e02c7854); defect B in `explorer_folder_window`, the listener's read-or-skip and the outpost's count-or-drop decided apart. Enforcement: the owner's fields private to its module, with one mutating function, by Rust's privacy.
- **Pure reducers, with calls as effects.** Every owner whose decisions depend on order is a pure state machine: inputs in, effects out, no clock, no call, no blocking. Calls, timers and messages are effects; local reads of Windows' own state come through an injected query trait. Reason: a pure owner's orderings are enumerated by replay tests, an impure one's are found by review. Evidence: the publication at the bound took four rounds (c47d57ae, 6dbcca25, 2bd69a85, 8a087fe7). Enforcement: an ownership check in `cargo xtask ci` reads the reducer modules against an allow-list of paths, with no binding, clock, thread, channel or lock; it reads text, so its limit is a review rule. Replay tests are the real check.
- **Queries have exactly one answer.** Across processes, the asking side's request table gives every query its one outcome: the answer, or "gone" when the outpost generation asked ends or backs off, or "unanswered" at its deadline, since a killed process runs no code to answer. Within a process, the side that answers holds a responder, consumed by answering, whose `Drop` answers "gone", held only in a thread's shell, never in a pure reducer's state. Reason: an idle round or a dialog otherwise waits for ever. Evidence: 886d8e73, a shell-items request never answered when its outpost ended. Enforcement: the in-process responder by Rust (`#[must_use]` and `Drop`); the table's endings, a review rule held by a unit test of each ending; a debug assertion that a reducer transition ending a request emitted its answer.
- **Messages are of declared kinds.** Every message between processes is a query, a one-way report, a release, a lifecycle message from one ordered path per generation, a routed report, or configuration. A message carrying Core's state for a child to judge against fits none. Reason: `CoreFocus` was added as an untyped variant and no type asked what it was. Evidence: c0bbf19b. Enforcement: enums split by role and direction, so a message a role may not send cannot be decoded; an exhaustive `kind()` per enum; a unit test listing every variant with its kind, so a new one changes a reviewed file. Whether a variant carries Core's state is a review rule.
- **Nodes are released by message position.** This is distributed garbage collection by reference listing ([prior art](../../experiments/ownership-study/prior-art.md), "The release protocol"), with Core as the holder sending its list. A node leaves an outpost only through its object store, which records the position of the message that carried it, and is freed only when Core's `NodesHeld` acknowledges a later position and does not hold it; a node never carried is freed only when the request that minted it can no longer publish. Reason: a node must outlive every message Core may still read it from. Evidence: the splice sequence in [the focus pipeline rework's remaining builds](focus-pipeline-rework-remaining.md). Enforcement: a sendable snapshot type whose constructor is private to the store's module.
- **A fact carries the version of the state it depends on.** Every fact that depends on state another owner can change carries that state's version, and the receiver recognises a fact made under a version it has moved past. This one rule unifies instances already built: the worker generation, by which an abandoned worker's late result is discarded; the outpost generation in every node id, so an id from a replaced outpost never names a node of its successor (the generation is the standard epoch or term, [prior art](../../experiments/ownership-study/prior-art.md), "The generation"); node release by message position; and the walk's mint tag (worker generation and request) that the release rule needs. The new instance is configuration: the fetch configuration today, M5's rule tables later, which Core changes while the listener and the outposts judge events under them. It is built in M5 (Dickson, 2026-10-30), a rule M5 must follow; its only production use today is the fetch configuration, with no recorded defect. Event order is not this rule: across applications it is Core's stale rule on observation stamps, and within an application the marker and the intake's order. Reason: two owners acting on one changed state at different times otherwise disagree silently. Evidence: the fetch configuration's push to an outpost is refused on a full queue and retried after the next input, so the outpost reads under the old value while Core already reads under the new (design review 2, finding 2). Enforcement: the version a required field of each such fact, by the compiler; that the receiver compares it, a review rule held by unit tests.
- **No back-channel.** No message tells a reader what Core holds; a reader skips a read only on its own observations of the event. Reason: a reader's copy of Core's state is always one message old. Evidence: the repeat hole, where a focus returning while Core's notice is in flight is never spoken; 43de3932. Enforcement: the functions that export Core's focus to a reader are deleted, so no API offers it.
- **No state lent across a call into an application.** A thread works on a copy and only its result's transition records the change. Reason: a thread abandoned inside the call keeps what it holds, and its replacement blocks on it. Evidence: d0ec3a89. Enforcement: the outpost's workers never see the reducer's state, and the object store's API has no guard or closure, by Rust's privacy; inside the store, a review rule.
- **One route and one sequence for user input.** Every user input enters Core by one route and gets its key number where it enters that route, from one minter, the keyboard hook's thread, in the order it posts. The hook thread takes only keys: a test's gestures are pressed as keys, M5's module commands are bound gestures and M12's remote input is real keys, and how M15's braille gestures are numbered is M15's design (`docs/design/ownership.md`, "The hook takes only keys"). Reason: speech is fenced by key order, and a command must run in key order with held keys. Evidence: ba7064e5 and its reversal e180f14a; and the race of a second minter, in which the control plane took number n and was pre-empted, the hook took n+1, cancelled speech through it and posted, and the control plane then posted n, whose speech was fenced and silent. Enforcement: the key number a required field of each input and of speech, by the compiler; the one minter, a review rule, and the hook thread taking only keys, by the ownership check's hook rule.
- **Merging only for kinds that declare it.** A queue may merge judged messages only of a type implementing `Merge`, whose test shows Core concludes the same; barriers are declared on the type. NVDA's own limiter is not a merge and stays. Reason: a merge is a judgement made outside Core. Evidence: dd363ecc, a caret report merged across a reply and spoken twice. Enforcement: merge functions generic over `Merge`, by the compiler.
- **Lifecycles as typestates.** A lifecycle is an enum whose transitions consume the old state, the consuming half of the typestate pattern ([prior art](../../experiments/ownership-study/prior-art.md), "Lifecycles as typestates"), checked by `match` at run time unless each state is its own type. Reason: impossible combinations of flags get written. Evidence: df4c15d9. Enforcement: by Rust.
- **Who may block on whom.** Core never blocks on a reader, nor a reader on Core; the hook takes no lock; the audio thread waits on no lock held across a blocking call, does no I/O but the device's and allocates nothing per pass. The threads that call into applications are named. Evidence: the hook takes the `KEY_ORIGINS` lock on every key, a priority inversion. Enforcement: the ownership check on the hook's and the mixer loop's modules, and an allocation-counting test; the rest a review rule.

## The refactor preserves behaviour

The refactor changes who owns each fact, not what is heard. A change in speech during it is a defect, except the three Dickson kept (2026-10-30): review commands queued behind held keys, so a command pressed while a caret key is held reads the moved line; the repeat hole closed, so a focus returning while another is judged is spoken; and the listener's menu-opening comparison with its own current last read rather than Core's focus. Each is pinned by a test. He moved three to the focus pipeline rework: removing Core's second foreground test (audit difference 12), one node per window (defect A), and the merges' evidence fixes (a tree item's child count, a focus report's `earlier`); the refactor keeps today's behaviour for each. Behaviour changes found while designing it belong to the focus pipeline rework or a milestone: the title rule went there (Dickson, 2026-10-30; [the focus pipeline rework's remaining builds](focus-pipeline-rework-remaining.md)).

## What the rules do not cover

The order across applications, confined to Core's stale rule; the two routes of one application, confined to the outpost's reducer; the applications themselves, bounded by deadlines, abandonment and kill-and-replace; the application rules until M5; version skew and untrusted peers, validated at their boundaries; a second instance in M8.1, sharing no writable fact; the supervisor's wall-clock decisions; thread-affine backends, recovered by kill-and-replace only.

## Tests

Each build removes tests or makes them cheaper where its changes allow: tests of mechanisms it removes, such as those of `CoreFocus`, `HeldElements` and the back-channel, and end-to-end or mockapp tests whose ordering cases become replayed unit tests of a reducer, or whose real waits become injected timers. Dickson's rule: a test is removed only once the cheaper test covering the same behaviour exists and passes, and the replacements meet `docs/testing.md`.


## The builds, by area

Each area gives its problem, the choice with the alternatives weighed, and its limits. The refactor preserves what is heard in every area, except where stated.

### One judge: focuses, repeats and the listener

Crate guides: [verbatim-core](../crates/verbatim-core.md) ("Focus, events and objects"), [verbatim-listener](../crates/verbatim-listener.md), [verbatim-outpost](../crates/verbatim-outpost.md) ("What to read") and [verbatim-uia](../crates/verbatim-uia.md).

The problem: Core judged each focus report, and the listener and the outposts each kept a copy of Core's focus (`CoreFocus`, `HeldElements`, `Held`'s copy) to guess that verdict and skip work. Each copy was one message old, so a focus that returned while Core's notice was in flight was never spoken (the repeat hole), and every guess needed a patch per sequence (43de3932, c0bbf19b, 094a8dc8).

The choices:

- The back-channel is removed. Repeats are judged only in Core, from full facts, and every UIA focus that passes the listener's own checks is read in full. Cost: a UIA repeat reads about 5 calls where the drop made 3; an MSAA repeat or a foreground change reads in full (`docs/performance.md`).
- An outpost reads changes for every node it has not released, and Core's targeting decides what is spoken. Reason: Core's focus line is always inside the outpost's set, because a node is released only when Core's `NodesHeld` acknowledges a later position and omits it, so a lag costs reads, never a word. Rejected: every mechanism in which an outpost predicts Core's verdict, which reviews showed needed a patch per sequence.
- Core keeps one foreground record with one writer, replacing five scattered notions, and its focus stamp splits into an ordering stamp (the stale rule) and an applied stamp (the menu end). Two speech changes follow: in two orderings of cross-application focuses, the later-arriving but older focus is stale and silent, which also closes the repeat hole in that order.
- Focus groups keep NVDA's newest-first order in the outpost, and the stop moves into Core, which takes a report only when it took no newer report of the same group.
- UIA property, text and caret changes reach an outpost only through its focus-following group, so the group stays on every unreleased report's element until the store releases it, attributed by cached runtime id.
- Every carried node is recorded as carried, including those a walk splices in, and text anchors are released by message position like nodes. Reason: an older acknowledgement could free a node a newer message still carried, and an outpost forgot any anchor once 64 newer existed, so say-all stopped silently. Rejected: identity that outlives the object, because UIA runtime ids are reused after their element dies (5797c075), most MSAA nodes have no stable key, and a key map grows for the outpost's life.
- The listener's read scheduler is a pure transition under the lock it already had, held by the first ownership check. Its menu-opening comparison is with its own last read (the third kept change). The ignored-window drop moves into the outpost; dialog text and window facts are carried with each report.

Limits: reads for a node Core no longer targets cost calls until the release (the `NodesHeld` round trip, or the 3-second ping for anchors, which does not write `NodesHeld` on its own); the extra reads `docs/performance.md` records for old elements; a reused UIA runtime id can still name a dead node on the focus, where the reader's `earlier` evidence corrects it. As built, a window's own client says nothing when disabled (2cd08d08).

### Input: one route, one minter

Crate guides: [verbatim-input-windows](../crates/verbatim-input-windows.md), [verbatim-app](../crates/verbatim-app.md), [verbatim-core](../crates/verbatim-core.md), [verbatim-speech](../crates/verbatim-speech.md) and [verbatim-model](../crates/verbatim-model.md).

The problem: two minters of the key number (the hook and the control plane's gesture injection) raced, so a gesture's speech could be fenced and silent. A global side table of trace to key number was taken on the hook thread for every key, a priority inversion; the hook's cancel took a channel's waker mutex; key reports and bound gestures entered Core by two routes with no common order (ba7064e5, e180f14a), so a review command pressed while a caret key was held read the old line; and any thread holding the speech manager could speak.

The choices:

- The hook thread is the one minter, and takes nothing from another thread but the message that stops it. Reason: speech is fenced by key order, and only numbers minted in the order the hook handles keys agree with the order inputs reach Core. Gestures are real keys: a test presses a gesture's keys, so the hook numbers it as a person's, and the same gesture twice within 500 ms is a double press. Rejected: numbering gestures in Core while the hook numbers keys (two minters again), and the hand-written lock-free inbox this build first had to inject gestures into the hook thread (removed as hand-written concurrency that keys alone make unnecessary).
- One route: the hook reports everything through one callback to the reducer's port in decided order, and the router thread is gone. An idle waiter goes straight to the port and waits for the hook's `Handled(n)` mark. Rejected: a barrier key the harness injects and swallows, because `SendInput` fails silently under UIPI and a hook that overruns its timeout is silently removed; and a standard channel with `MsgWaitForMultipleObjectsEx` on the hook thread, which keeps a cross-thread hand-off and a second wait.
- Core owns the trace-to-key table and stamps every `Speak` with the key that caused it. The speech queue's inbox is a completion port, so the hook's cancel never waits and keeps the first-in, first-out order the fence needs.
- A review command or script pressed while a caret key is held waits in Core's held-key line behind that key's read and watch, at most 100 ms after the pass. This is the first kept change; NVDA runs scripts one at a time in queued order but reads the old line, where Verbatim reads the line the key moved to (`docs/parity/input.md`).
- The router's work became Core effects. A lock key's announcement is due 30 ms after the press and carries no key number, as in NVDA.
- `SpeechManager::new` returns a `SpeakToken` only the reducer thread holds, so "only the reducer speaks" is a type. A hook rule in the ownership check forbids locks, waits, logging, I/O and sent messages in the hook's modules.

Limits: each post to the port allocates a box; keys injected with `SendKeys` carry no harness number; speech of a key more than 1,024 keys old carries no number; a command behind a held key waits up to 150 ms for the read and 100 ms for the watch; a reducer stalled past 30 ms delays the lock-key announcement; the single minter is a review rule; how M15's braille gestures are numbered is M15's design.

### Messages: declared kinds, one answer, typestates

Crate guides: [verbatim-model](../crates/verbatim-model.md) ("The wire protocol"), [verbatim-process](../crates/verbatim-process.md) (the message layer), [verbatim-supervisor](../crates/verbatim-supervisor.md), [verbatim-app](../crates/verbatim-app.md) and [verbatim-gui](../crates/verbatim-gui.md). This is roadmap milestone M4.4.

The problem: one enum per direction served both kinds of child, so receivers dropped what was not theirs with a wildcard arm and `CoreFocus` was added with nothing asking what kind of message it was. `carries_nodes` was a `matches!`, so a new node-carrying variant went uncounted and a node could be released while Core read it. The outbound queue's merge had no declared barriers or equivalence test. Wanted requests had no owner, so one never ended when its application exited during a backoff and every later idle round timed out (886d8e73), and the GUI's shell-items request had no answer on drop (76180512). The supervisor's record encoded a generation's life in booleans and a sentinel id (df4c15d9).

The choices:

- The wire types live in `verbatim_model::protocol`, split by role and direction, so a message a receiver may not take cannot be decoded, and every dispatch is an exhaustive match. Each enum has an exhaustive `kind()` into six kinds, and a test lists every variant with its kind, so a new variant changes a reviewed file. Whether a variant carries Core's state is a review rule. `#[non_exhaustive]` was removed from the moved enums, since the processes are one build.
- `Merge` is a trait with a key, a declared barrier and `may_merge`; only the outpost's outbound messages implement it, and an equivalence test per kind checks that Core's state and the others' speech are unchanged. The merged report's own speech is dropped on purpose, as NVDA's limiter does, so the test cannot assert identical speech. NVDA's limiter is not a merge and stays in the intake and listener.
- Across processes the asking side's request table gives every query one outcome (reply, "gone" at its generation's end, or "failed" at its deadline), because a killed process runs no `Drop`. Within a process a `Responder` answers "gone" on drop and lives only in a thread's shell. One module owns the wanted requests and ends each exactly once.
- The supervisor's generation is an enum whose transitions consume the state, and lifecycle messages carry a `Sealed` only the supervisor makes. The owner thread itself stays impure.

Limits: a merge reorders an event of the merged report's node queued between the two ahead of it, which is NVDA's limiter's own effect and is pinned by a test per kind; a wanted request ended at a retirement just before a new start is answered "nothing"; `kind()` exists for the wire enums only; the backend override and fetch configuration are sent unversioned until M5; a reply bars only a caret report with selection changes from merging across it, and the caret rework generalises that.

### Output: one saver, one audio owner

Crate guides: [verbatim-config](../crates/verbatim-config.md), [verbatim-speech](../crates/verbatim-speech.md), [verbatim-audio](../crates/verbatim-audio.md), [verbatim-audio-wasapi](../crates/verbatim-audio-wasapi.md) and [verbatim-app](../crates/verbatim-app.md).

The problem: the settings file had three writers under the store's lock, so a slow disk in the GUI's write stalled the reducer and every later key's speech (`docs/design/communication.md`, section 6.6). The dialog's mirror of the synthesizer kept a value the driver refused, and a commit before the answer saved it, where NVDA saves the driver's own values. The audio thread at MMCSS priority held the mixer's lock across WASAPI calls that other threads also took, so a pre-empted holder made it miss its period and a blocked device call stalled all speech; cancel, pause and fail blocked their callers; the thread allocated every pass. The synthesizer's display name came from the host, which never loads the user's locale.

The choices:

- One saver thread owns `settings.toml`, with one non-`Clone` writer per section. A writer posts to a completion port and never waits; the saver writes the newest of each section per batch. The synth thread owns the speech section, the reducer the reader section and the GUI the theme.
- The synth thread alone writes the mirror, reads every value back from the driver after each change and answers with all of them; a commit and a revert run on the synth thread in order behind every change, and a commit saves what the driver has. Rejected: updating the mirror from the answer alone, which does not stop a commit made before the answer from saving the refused value; and keeping the settings host's owed commit and revert (0d791a13), which this replaces with the same outcome.
- The audio thread owns the mixer with no lock. Each producer has a bounded single-producer lane, cancel is a generation and pause a flag, and records leaving the audio thread go through a ring to a delivery thread that runs listeners, logs and frees. Per-pass buffers are allocated when the device opens. Reason: a lock on the audio thread is a priority inversion on every producer, and a request that waits couples a producer to the device. Rejected: a hand-written park handshake or flags with fences for waking the synth and audio threads, which the review found racy with two writers of the wanted room; wakes are plain events, with a level-set room event waited on in a loop so no wake is lost.
- The display name comes from Core's registry by the driver's id.

As built: a push wakes the audio thread only when its lane was empty, and the room event is set when a pass took any record and left the lane at most half full; a format change fails an utterance whose registration was still in its lane, with the reason written by the delivery thread; a device format beyond the stores' reserve is muted until the device reopens; a device that cannot make an event refuses to open; the exit save has its own bound, `EXIT_SAVE_TIMEOUT`.

Limits: the audio thread's wake-ups rose under key load (`measure_keys_notepad`: 5,832 before, 11,420 after the wake change, the cause of the rest unknown; `docs/performance.md`, `docs/roadmap.md`), and the delivery thread adds about three wakes per utterance. A change is on disk a write after it is made, a commit waits up to 10 seconds on a host that stopped answering, and a commit unwritten after the 2-second exit bound is lost and logged. Earcons beyond 256 in a lane are dropped and logged. Formats beyond 8 channels at 192 kHz are muted. The wake and cancel-ordering races cannot be produced by a test; the crate guides state the rules for a reviewer. The ownership check reads text, so an allocating method inside an allowed type is a review rule held by the allocation test. After a driver refuses or clamps a value the control snaps back at once, where NVDA leaves it as set; NVDA's refresh of other controls after a voice change is a roadmap follow-up. Verbatim writes the file on every change; NVDA writes on exit or its save command.

### The outpost's store and reducer

Crate guides: [verbatim-outpost](../crates/verbatim-outpost.md) ("The outpost", "Text and caret", "The arbitrator", "Who calls into an application"), [verbatim-uia](../crates/verbatim-uia.md) ("The node registry") and [verbatim-ia2](../crates/verbatim-ia2.md); the costs are in `docs/performance.md`. It undid two recent mechanisms by design: the commit point and its lock order (`docs/design/focus-pipeline-rework.md`), and the hand-over's counting, which the hold decided on 2026-10-25 replaced.

The problem: one worker thread planned, judged and called, sharing state with the watchdog and the intake under the watch lock, with the judgement list, intake, outbound queue and both registries nested inside it. The publication at the bound took four review rounds (c47d57ae, 6dbcca25, 2bd69a85, 8a087fe7). Guards were held across application calls and text objects dropped under locks, so an abandoned worker's replacement blocked (d0ec3a89, 5797c075). A query was answered by whichever of three threads came first. Node identity and its release were not one owner's.

The choices:

- The work split in two along the object store's API: the store first, then the reducer. The reverse order would have built programs against registries that then changed.
- The object store is a monitor owning both node registries, the text objects and each node's mint tag (worker generation and request). Its API returns owned clones and removed objects, never a guard or closure, so no lock is held across a call. A message carrying nodes is built from a `Recorded` only the store makes, and `Store::release` frees a node only when no live request can name it and Core acknowledged a position at or after its last carrier without holding it. Text calls work on clones of anchors.
- The reducer holds every remembered fact of the application with no Windows type: inputs from a mailbox that producers only append to, effects out, local reads through an injected trait. It runs on a thread of its own because UIA calls cannot be cancelled (Dickson, 2026-10-30). Workers run whole call programs on copies with exactly today's calls, and the reducer applies a program's commits only while its request is live. Abandonment is the reducer's transition on the deadline; late results of a dead generation are discarded, so none of the four publication rounds can recur.
- The shell waits on the mailbox's alarm, a high-resolution timer set to the earliest timer, so the watchdog thread and the gap record's threadpool timer are gone and each timer costs one wake where the watchdog took two. Rejected: keeping a watchdog that posts timer inputs. This is sound because every lock the reducer's thread takes is a short hold with no call.
- Each re-read of the console caret poll is a program of its own, timed by the reducer's wake for the watch, so a program that arrives during the poll waits for at most one read and the worker keeps nothing between programs (amended 2026-10-31). An edit control's caret read is two programs, because the reducer owns the waiting entries.
- The hand-over's hold: the reducer holds the hook's whole stream from install until `ForwardingEnded`, drops the copies the listener forwarded, and releases the rest in the hook's order. Reason: holding only the forwarded kinds would let a caret or value change pass a focus raised before it.
- Every query gets one answer from a reply token in the shell's request table, whose `Drop` answers `Failed` since the outpost's process lives.

As built: parked event objects and an active text range are parked as pushed, after the push-time drops; plain windows mint by window handle, with no separate map; owed work and the gap's read are programs of their own, dispatched first; a generation's charge holds the walk's progress and its abandoned flag under one lock; what the shell lets go of is dropped by the worker before its next program; a focus walk's object is its event address or runtime id; text facts are reducer state while ranges and patterns stay in the store.

Limits: at an outpost's start the hook's stream waits for `ForwardingEnded` (median 20.6 ms, at most 591.3 ms over 126 starts), and without it until the listener's reads end; a dead generation's mints wait for the next `NodesHeld`, at most 3 seconds; an event with a commit usually costs four wakes where the worker alone woke once; the fetch configuration and backend override are still written by the I/O thread, versioned in M5; the purity check reads text.

## Dickson's decisions

On 2026-10-30:

- A repeat focus is read in full and judged in Core; no reader holds a copy of Core's focus. The application rules stay where they are until M5.
- The reducer runs on a thread of its own; its cost is in `docs/performance.md`.
- The refactor includes the settings saver, real-time audio, the synthesizer's display name, the key number on the input and review commands on the key reports' route. The message types live in `verbatim_model::protocol`.
- The gap record is kept as built, and the supervisor's owner thread becomes a pure state machine in M6.2, after the refactor (`docs/roadmap.md`). Amended on 2026-10-31.
- The title rule belongs to the focus pipeline rework; the refactor preserves behaviour except the kept speech changes.

- `NodesHeld` is written on its own only when the held set changes or after a focus report.
