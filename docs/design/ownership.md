# Ownership: one owner for every fact

Status: the model, decided with Dickson on 2026-10-30. Nothing in it is built. The refactor that applies it is built in a few builds; each gets its own design, written against the code as it stands just before that build and given its own adversarial review. Their starting drafts, with the traps two reviews found, are in [the ownership builds](ownership-builds.md); the evidence (the study, four audits, the three reviews and the decisions) is in `experiments/ownership-study/`.

## The problem

Most defects of the focus pipeline rework had one cause: a fact about one application was decided in two or three processes, and a decision waited on a message from another process arriving first. Two kinds of message let the class grow back after each fix: a message carrying Core's state to a reader for it to judge against (`CoreFocus`), and a reader skipping work on a judgement only Core can make. Inside an outpost, the same class between threads cost four review rounds on the publication at the bound. The aim is a model under which such races are impossible by construction where they can be, and confined to one named owner where they cannot, for all of Verbatim and its planned milestones. A change is in scope only when it points to a concrete past defect, or shows a sequence that would go wrong in today's code or in a planned milestone; everything else stays as it is.

The processes stay split as they are, for measured reasons: a UIA client call cannot be cancelled (`experiments/cocancelcall-does-not-end-a-uia-client-call/`), so only process exit reclaims a stuck thread (D9); a UIA element cannot leave the process that received its event, so the listener reads every UIA focus; the desktop-wide focus registration is costly and stalls with hung windows, so only the listener holds it; two Verbatim processes connecting to one application collide inside UIA.

## The scope rule

- Core decides every word, and every fact that spans applications: speech, attention, the foreground, repeats, the order of focuses, chains, text and terminals.
- Each outpost decides, for its own application only, which calls to make: the order of its two routes, verdicts, the gap, node identity, the followed focus, change targeting and the caret watch. These decisions sit between two calls; each moved to Core would cost a round trip.
- The listener observes and reads. Before a read it makes NVDA's checks on its own observations of the event (hung, the console's element, acceptance against the foreground, keyboard focus) and applies NVDA's limiter to its own queue; it judges nothing against another process's state.
- Whether a UIA focus is read or skipped by its window's backend has one owner, the outpost's verdict rule. The listener applies only its probe-free part, NVDA's MSAA class list and the override, through the outpost's own code and tables, whose skips the outpost's verdict always also judges MSAA; every other window's focus is read, and the outpost's verdict decides whether it counts. This is NVDA's order, a class check before the read and one verdict per window (Dickson, 2026-10-30).
- The application rules stay where they are until M5 moves them into modules (D6).

D14 keeps its rules that attention moves only on a foreground change, the foreground is announced and never a gate, and focuses are ordered by when they happened. Only its clause on where the rules run is replaced, by: "each event rule is defined once; words and every fact across applications are judged in Core; what to read for one application is judged by its reader, from its own observations of the event, and by its outpost's verdict rule, which the listener applies only in its probe-free part; no state of Core is sent back for a reader to judge against."

## The rules

- **One owner per fact.** Every fact has one writer, one thread or one state machine run by one thread; others learn it from one-way reports or from a view. A view inside one process is allowed only when it is ordered with what it judges, keyed by a fact its reader observes, or, for lifecycle only, a lagging copy whose staleness costs no word. A monitor, one module whose every operation runs under its own private lock that is never held across a call, never exposes its guard and never runs a caller's code, is one owner too. Reason: every reconciliation between two writers in the history was patched three to seven times. Evidence: the gap record moved between the listener and the outpost four times (01cba97e to e02c7854); defect B in `explorer_folder_window`, the listener's read-or-skip and the outpost's count-or-drop decided apart. Enforcement: the owner's fields private to its module, with one mutating function, by Rust's privacy.
- **Pure reducers, with calls as effects.** Every owner whose decisions depend on order is a pure state machine: inputs in, effects out, no clock, no call, no blocking. Calls, timers and messages are effects; local reads of Windows' own state come through an injected query trait. Reason: a pure owner's orderings are enumerated by replay tests, an impure one's are found by review. Evidence: the publication at the bound took four rounds (c47d57ae, 6dbcca25, 2bd69a85, 8a087fe7). Enforcement: an ownership check in `cargo xtask ci` reads the reducer modules against an allow-list of paths, with no binding, clock, thread, channel or lock; it reads text, so its limit is a review rule. Replay tests are the real check.
- **Queries have exactly one answer.** Across processes, the asking side's request table gives every query its one outcome: the answer, or "gone" when the incarnation asked ends or backs off, or "unanswered" at its deadline, since a killed process runs no code to answer. Within a process, the side that answers holds a responder, consumed by answering, whose `Drop` answers "gone", held only in a thread's shell, never in a pure reducer's state. Reason: an idle round or a dialog otherwise waits for ever. Evidence: 886d8e73, a shell-items request never answered when its outpost ended. Enforcement: the in-process responder by Rust (`#[must_use]` and `Drop`); the table's endings, a review rule held by a unit test of each ending; a debug assertion that a reducer transition ending a request emitted its answer.
- **Messages are of declared kinds.** Every message between processes is a query, a one-way report, a release, a lifecycle message from one ordered path per incarnation, a routed report, or configuration. A message carrying Core's state for a child to judge against fits none. Reason: `CoreFocus` was added as an untyped variant and no type asked what it was. Evidence: c0bbf19b. Enforcement: enums split by role and direction, so a message a role may not send cannot be decoded; an exhaustive `kind()` per enum; a unit test listing every variant with its kind, so a new one changes a reviewed file. Whether a variant carries Core's state is a review rule.
- **Nodes are released by message position.** A node leaves an outpost only through its object store, which records the position of the message that carried it, and is freed only when Core's `NodesHeld` acknowledges a later position and does not hold it; a node never carried is freed only when the request that minted it can no longer publish. Reason: a node must outlive every message Core may still read it from. Evidence: the splice sequence in [the focus pipeline rework's remaining builds](focus-pipeline-rework-remaining.md). Enforcement: a sendable snapshot type whose constructor is private to the store's module.
- **A fact carries the version of the state it depends on.** Every fact that depends on state another owner can change carries that state's version, and the receiver recognises a fact made under a version it has moved past. This one rule unifies instances already built: the worker generation, by which an abandoned worker's late result is discarded; the outpost incarnation in every node id, so an id from a replaced outpost never names a node of its successor; node release by message position; and the walk's mint tag (worker generation and request) that the release rule needs. The new instance is configuration: the fetch configuration today, M5's rule tables later, which Core changes while the listener and the outposts judge events under them. It is built in M5 (Dickson, 2026-10-30), a rule M5 must follow; its only production use today is the fetch configuration, with no recorded defect. Event order is not this rule: across applications it is Core's stale rule on observation stamps, and within an application the marker and the intake's order. Reason: two owners acting on one changed state at different times otherwise disagree silently. Evidence: the fetch configuration's push to an outpost is refused on a full queue and retried after the next input, so the outpost reads under the old value while Core already reads under the new (design review 2, finding 2). Enforcement: the version a required field of each such fact, by the compiler; that the receiver compares it, a review rule held by unit tests.
- **No back-channel.** No message tells a reader what Core holds; a reader skips a read only on its own observations of the event. Reason: a reader's copy of Core's state is always one message old. Evidence: the repeat hole, where a focus returning while Core's notice is in flight is never spoken; 43de3932. Enforcement: the functions that export Core's focus to a reader are deleted, so no API offers it.
- **No state lent across a call into an application.** A thread works on a copy and only its result's transition records the change. Reason: a thread abandoned inside the call keeps what it holds, and its replacement blocks on it. Evidence: d0ec3a89. Enforcement: the outpost's workers never see the reducer's state, and the object store's API has no guard or closure, by Rust's privacy; inside the store, a review rule.
- **One route and one sequence for user input.** Every user input enters Core by one route and gets its key number where it enters that route, from one minter, the keyboard hook's thread, in the order it posts: the control plane's injected gestures, and later M5's module commands, M12's remote input and M15's braille keys, are posted to the hook thread, which numbers and forwards them in order with the keys. Reason: speech is fenced by key order, and a command must run in key order with held keys. Evidence: ba7064e5 and its reversal e180f14a; and today's race, in which the control plane takes number n and is pre-empted, the hook takes n+1, cancels speech through it and posts, and the control plane then posts n, whose speech is fenced and silent. Enforcement: the key number a required field of each input and of speech, by the compiler; the one minter, a review rule; the race as a test.
- **Merging only for kinds that declare it.** A queue may merge judged messages only of a type implementing `Merge`, whose test shows Core concludes the same; barriers are declared on the type. NVDA's own limiter is not a merge and stays. Reason: a merge is a judgement made outside Core. Evidence: dd363ecc, a caret report merged across a reply and spoken twice. Enforcement: merge functions generic over `Merge`, by the compiler.
- **Lifecycles as typestates.** A lifecycle is an enum whose transitions consume the old state. Reason: impossible combinations of flags get written. Evidence: df4c15d9. Enforcement: by Rust.
- **Who may block on whom.** Core never blocks on a reader, nor a reader on Core; the hook takes no lock; the audio thread waits on no lock held across a blocking call, does no I/O but the device's and allocates nothing per pass. The threads that call into applications are named. Evidence: the hook takes the `KEY_ORIGINS` lock on every key, a priority inversion. Enforcement: the ownership check on the hook's and the mixer loop's modules, and an allocation-counting test; the rest a review rule.

## The refactor preserves behaviour

The refactor changes who owns each fact, not what is heard. A change in speech during it is a defect, except the three Dickson kept (2026-10-30): review commands queued behind held keys, so a command pressed while a caret key is held reads the moved line; the repeat hole closed, so a focus returning while another is judged is spoken; and the listener's menu-opening comparison with its own current last read rather than Core's focus. Each is pinned by a test. He moved three to the focus pipeline rework: removing Core's second foreground test (audit difference 12), one node per window (defect A), and the merges' evidence fixes (a tree item's child count, a focus report's `earlier`); the refactor keeps today's behaviour for each. Behaviour changes found while designing it belong to the focus pipeline rework or a milestone: the title rule went there (Dickson, 2026-10-30; [the focus pipeline rework's remaining builds](focus-pipeline-rework-remaining.md)).

## Each part of Verbatim

- **Core.** Remove `CoreFocus` and everything that feeds it or exports Core's focus to a reader. Repeats are judged only in Core, from full facts. The five notions of the foreground become one record with one writer, which keeps today's second foreground test as a function of it. Stays: the reducer, the request table, the held-key line, text, terminals, review, the stale rule, `FocusNow`.
- **Input and the hook.** Remove the `KEY_ORIGINS` side table; the key number travels on the input. Review commands take the key reports' route into Core, so they queue behind held keys. Only the reducer thread can speak, a decision of record (architecture section 2, Dickson, 2026-10-24), now enforced by a token. Stays: the decision machine, the held-key records, the hook's keyed views.
- **The listener.** Remove `HeldElements`, its copy of Core's focus; every UIA focus that passes its own checks is read in full, a UIA repeat costing 5 calls where the drop made 3. Its read scheduler becomes a pure transition under the lock it already has. Stays: the reading threads, the publication at the bound, the moved-on rule, the hand-over map, its limiter, its checks.
- **The outposts.** Remove `Held`'s copy of Core's focus; its record of the states each node was read with (`states_read`), which decides "newly expanded" and a tree item's child count, stays as the outpost's own. Every MSAA repeat and every foreground change `Held` dropped is then read in full, about 20 calls and 5 to 10 calls each; the repeat is Dickson's decision, the foreground change follows from removing the copy. The followed focus is the outpost's own newest report, except a report that a rule the outpost applies itself through Core's one definition refuses (the application rules' refusal, such as its own read of the Alt+Tab switcher's pane), and a foreground report of the window holding its followed focus, which Core ignores. The outpost's MSAA hand-over (`handover.rs`) is outpost state, and moves into the reducer once, as the hold Dickson decided on 2026-10-25, with released events tried as today's batch. All remembered state of the application moves into one pure state machine on a thread of its own, the outpost's reducer: workers run whole call programs on copies and post results, the watchdog only posts timer inputs, and objects the reducer releases are handed to a worker. One object store owns node identity and its release. Stays: the walks and their call counts, terminals' split with Core, verdicts as the outpost's, the event thread's narrowing.
- **The supervisor and the app.** Lifecycle records and the supervisor's hook records become typestates; requests wanted but not yet sent get responders. Stays: the relay, `HeldFacts`, the idle round, process identity, the backoff.
- **Messaging and the control tools.** The message types move into `verbatim_model::protocol`, beside Core's `Input`, as M4.4 and communication decision 13 ask, split by role and direction with declared kinds; the framing stays in `verbatim-outpost`. Stays: the transport, the overflow policies, the control plane.
- **Speech.** Stays as is, except that the synthesizer's display name comes from Core's registry, since the host never loads the user's locale.
- **Audio.** The mixer's state is owned by the audio thread with no lock, other threads sending requests it never waits on; the WAV recorder's tap, which copies and sends its samples on every pass (`crates/verbatim-audio/src/wav.rs`) in every recorded run (D16), moves to a preallocated ring.
- **The synthesizer host.** Stays as is until M6.
- **The GUI and settings.** One saver owns the settings file, one writer per section, off the reducer's path; the dialog's mirror follows the synthesizer's answer. Stays: the GUI thread token, the hidden frame mark.

Each planned milestone's rules under this model are listed in [the ownership builds](ownership-builds.md), to be moved into the roadmap by the documents commit.

## What the rules do not cover

The order across applications, confined to Core's stale rule; the two routes of one application, confined to the outpost's reducer; the applications themselves, bounded by deadlines, abandonment and kill-and-replace; the application rules until M5; version skew and untrusted peers, validated at their boundaries; a second instance in M8.1, sharing no writable fact; the supervisor's wall-clock decisions; thread-affine backends, recovered by kill-and-replace only.

## Tests

Each build removes tests or makes them cheaper where its changes allow: tests of mechanisms it removes, such as those of `CoreFocus`, `HeldElements` and the back-channel, and end-to-end or mockapp tests whose ordering cases become replayed unit tests of a reducer, or whose real waits become injected timers. Dickson's rule: a test is removed only once the cheaper test covering the same behaviour exists and passes, and the replacements meet `docs/testing.md`.

## The order of the builds

Each build gets its own design against the code just before it, its own adversarial review, one implementation review, and its related scenarios; the drafts give each a starting point.

- The one judge build: `CoreFocus`, `HeldElements` and `Held`'s copy removed; repeats in Core; the one foreground record; the followed focus; the listener's scheduler as a pure transition; the first ownership check, on that scheduler.
- The input build, beside the messages build: the one input route, the one minter, the key number, the speaking token, the ownership check on the hook.
- The messages build: `verbatim_model::protocol`, the kinds, the request table's endings and every responder (the listener's marker included), `Merge` reproducing today's merges, the supervisor's typestates.
- The outpost's reducer build: the reducer, call programs, the hand-over's hold, the object store and the release rule, the ownership check on the reducer.
- The output build, beside the reducer build: the settings saver and mirror, audio, the synthesizer's display name.
- A documents commit: D14, the architecture's sections 1 and 2, the communication design, the glossary, the roadmap.

Afterwards the focus pipeline rework resumes with the paused keep-id fix in the worktree `verbatim-wt-fix2`, then its reduced second build (the gap closed by the outpost's own reports, defect B, the title rule, Core's second foreground test removed) and third build (with one node per window and the merges' evidence) ([the focus pipeline rework's remaining builds](focus-pipeline-rework-remaining.md)).

## Dickson's decisions (2026-10-30)

- A repeat focus is read in full and judged in Core; no reader holds a copy of Core's focus.
- The application rules stay where they are until M5.
- The outpost's reducer runs on a thread of its own, as above; its cost, one hop each way per call program and one more wake-up per event and per result, is stated in `docs/performance.md`.
- In the refactor: the settings saver, real-time audio, the synthesizer's display name, the key number on the input, and review commands on the key reports' route.
- The message types live in `verbatim_model::protocol`, and M4.4 is folded into the messages build.
- The gap record is kept as built; the supervisor's owner thread is not made a pure state machine now.
- The title rule belongs to the focus pipeline rework, not the refactor; the refactor preserves behaviour.
- The speech changes kept in, and moved out of, the refactor, as listed above.
- The configuration instance of the version rule is built in M5, not in the refactor: M5 must give the rule tables and the fetch configuration a version, published by Core alone, named by every judgement made under them, and recognised by its receiver when it has moved past it.
- The listener skips a UIA focus whose window's class is on NVDA's MSAA list before any read, as NVDA does, through the outpost's code and tables; the outpost's verdict owns every other window.
