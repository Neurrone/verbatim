# Holding caret keys as NVDA does

Status: adopted and built on 2026-10-22 (Dickson, 2026-10-22), the one mechanism for caret keys in text fields and terminals. The prototype was measured against main at 11c0718a; those figures are this design's measurements, with the evidence in `target/e2e-evidence/m42-key-holding-2026-10-22/` (its `readme.md` says what each folder holds; `analysis.txt` has every figure). The merge added the order of keys behind a held key and the guard for elevated windows, and measured the other two stale caret cases, with the evidence in `target/e2e-evidence/m42-key-holding-merge-2026-10-22/`. The review's fixes bounded a held key's wait for the key ahead and let the lock keys pass at once, with the evidence in `target/e2e-evidence/m42-key-holding-fixes-2026-10-22/`.

Terms used here:

- A held key is a caret-table key that the keyboard hook swallows and Verbatim sends to the application again once it has read the caret, as NVDA's caret scripts do.
- The before read is that read of the caret, made by the focus's outpost (the per-application process that reads it through UIA or MSAA) before the key is passed on.
- A watch is what Core asks the outpost for after a caret key: wait, without blocking, for evidence of what the key did, then answer with the caret. Its baseline is the caret it compares with.
- A key's effect is misjudged when its answer is read from a caret that does not follow from the key: read before the application handled the key, or compared with a caret older than the one the key started from.

## Decisions

- Holding is Verbatim's one mechanism for caret keys, replacing the per-case fixes of the caret problems that share one cause, at the cost measured below: up to about 3 ms more from key to first sound at the median, and 8 to 13 wake-ups and 0.7 to 1.5 ms of processor time per held key in a debug build (Dickson, 2026-10-22).
- Keys that are not held never overtake a held key (Dickson, 2026-10-22): see "Keys behind a held key". This goes one step beyond NVDA, which has the same race: there a typed character pressed while a held Backspace's caret is read reaches the application first, so "ab", Backspace, "c" typed fast leaves "ab", the "c" deleted instead of the "b".
- Nothing is held while an elevated window is in front, a temporary guard until Verbatim has uiAccess (Dickson, 2026-10-22): see "Elevated windows".
- The foreground changing between a key's press and its pass-on is an accepted limitation, too small a window to matter in practice (Dickson, 2026-10-22).
- A held key waits for the key ahead of it to be answered no longer than 100 ms after that key was sent on (Dickson, 2026-10-22): see "Core".
- The lock keys are never held back behind a held key (Dickson, 2026-10-26): see "Keys behind a held key".
- In the console host only, a caret key's watch that finds no move on its first check re-reads the caret every 5 ms until a check finds the evidence or 50 ms after the key was passed on, whichever is first, a documented workaround to waiting only for evidence (Dickson, 2026-10-26): see "The console host's caret poll".

## The design as built

### The hook

The keys held are Verbatim's whole caret table (`verbatim_input::caret_bindings`): the arrows and their Control forms, Home, End, Page Up and Down, Control+Home and Control+End, each also with Shift, Backspace and Delete (the numpad's Delete too) each alone and with Control or Shift, Alt with Up and Down Arrow, and Control+A. NVDA holds the Shift forms and Control+A only in controls that do not report their own selection changes; Verbatim holds them everywhere, keeping one rule. The clearing keys (Escape, Control+C, Control+D, Control+Break), typed characters, Enter, Control+X and Control+V and every other key pass as before, as NVDA never holds them.

How the hook knows the focus is holdable: a `KeyHolding` switch, an atomic flag the reducer's thread sets after every input from Core's focus (`SrState::holds_caret_keys`: the focus is alive and has text, or has a role that may have it, the same test that decides whether a caret key's evidence is watched). The hook reads it with one relaxed load, so it never waits. A key held for a focus that turns out to have no text is passed on at once by Core.

A held key's press is swallowed and reported as `KeyReport::Held` with the hook's press time and the stroke it came from (virtual key, scan code, extended flag); its release is swallowed too, so the application never sees a release without its press. Its effect on speech (the cancel at the press) is unchanged.

Keys sent on carry `PASSED_ON_TAG` in the high half of the injected input's extra information and their place in line in the low half (below); the hook passes them, and the modifiers sent with them, straight on, deciding and reporting nothing. Keys the end-to-end harness injects carry their stroke numbers there instead, so they are held like the user's (a unit test checks both).

### Keys behind a held key

While any key held back has not yet reached the application, the hook holds back every later key transition it would pass, typed characters, Enter, the clearing keys, modifiers and releases included, and reports each as `KeyReport::Deferred`, besides what it reports for the key as before (a typed character is still reported as typed, translated with the deferred modifiers ahead of it taken as made, since Windows' own key state has not seen them). A later caret key is held in its own turn. A deferred key is never read: it is held only for its place in line, and reaches the application right after the keys ahead of it. Verbatim's own keys, the guard for elevated windows and the lock keys are the only exceptions. Caps Lock, Num Lock and Scroll Lock pass at once, press and release, even while keys are held back: the router announces a lock key's new state from Windows' own state 30 ms after the press, which a deferred key would not yet have changed, and Windows turns a numpad key into an arrow or a digit by Num Lock's state before the hook sees it, so numpad 4 pressed behind a deferred Num Lock would arrive as Left Arrow. The consequence is in "Limitations".

The hook knows a key has reached the application when it comes back through the hook: every key held or deferred gets the next place in line, which the shell puts on the key it sends, and a key coming back clears its place and every place before it, since keys are sent in order; a key Windows dropped is therefore waited for only until a later one comes back. The shell keeps one line in the order the hook reported: a held key waits at its front until Core passes it on, a deferred key goes as soon as it reaches the front, and whatever may go is sent with one `SendInput`, which Windows never interleaves with other input. A key the user presses while that input is still on its way to the hook comes after it and is deferred too, so nothing overtakes.

Core keeps the same order: a caret key the hook passed, text typed, or a clearing key that arrives while a held key waits is queued behind it, and handled once the keys ahead were passed on, as the input it came as, a caret key taken as pressed no earlier than the key ahead was passed on. The watch of the key just passed on is marked as having a later key, as that key's press would have marked it without holding had the watch existed, so its answer keeps the caret current and says its selection's change but not its words, as NVDA's caret script says nothing while another script waits. Each queued key's effects carry its own trace (`Effect::ForKey`), so its answers and speech are its own and a later key's cancel treats them as that key's. In a terminal, Core also gives every key, held, deferred or passed by the hook, to the terminal's reading rules itself, with the time it reached the program, a deferred key's being no earlier than the held key ahead of it was passed on; nothing tells the terminal's outpost of keys (`docs/design/terminal-model.md`, "Keys").

Unit tests: the hook defers a typed letter and its release behind a held Right Arrow, holds a second Right Arrow in its turn, and passes keys again once the last one comes back, a later one clearing those before it, and passes the lock keys at once behind a held key (`verbatim-input-windows`; before the lock keys were exempt, every lock key transition there was swallowed and deferred); Core echoes a typed "c" only after a held Backspace was passed on, on the letter's own trace, and reads the caret before a held Right Arrow once Backspace's watch is answered (`crates/verbatim-core/tests/text.rs`, `keys_pressed_behind_a_held_key_are_handled_after_it_in_order`).

### Elevated windows

Verbatim runs without the uiAccess privilege, and Windows drops input it sends to a window of higher integrity without an error, so a key held for such a window would be lost. While the foreground window's process has higher integrity than Verbatim's, or its integrity cannot be read, the hook therefore holds and defers nothing; a held key's release is still swallowed, its press having been sent with its own release. The focus listener reads the integrity of each window that comes to the front, from every process, Verbatim's own included, and once when it starts; Core decides from it whether keys may be held there (`SrState::hook_foreground`) and publishes the answer in the hook's lock-free `ForegroundView`, which the hook applies only while the window it names is still in front, holding nothing until Core has caught up (architecture section 5; `docs/crates/verbatim-input-windows.md`, "Holding caret keys"). This is a temporary guard, removed when uiAccess is built (`docs/roadmap.md`, M8.1). Unit tests check Core's decision for integrity levels above, equal to and below Verbatim's or unknown (`crates/verbatim-core/tests/shell.rs`) and drive the hook's decision with a view that forbids holding, a view of another window, and none; the live case was not checked, since no elevated window can be opened without a UAC prompt.

### Core

`Input::HeldKey` asks the focus's outpost for `TextOp::ReadCaret`. On the answer, Core takes the caret read as the focus's caret, as it takes a caret event's report, handles the key exactly as a caret key the hook passed itself, pressed one millisecond after the read ended, and passes it on (`Effect::PassHeldKey`). The key's existing watch therefore runs unchanged, with the read as its baseline in Core and in the outpost, since each takes the newest caret report from before the key's time. Nothing polls, except the watch in the console host ("The console host's caret poll"). The watch is asked for before the key is passed on, so it reaches the outpost before the key reaches the application, as a key the hook passes is reported before it is passed; with the key passed on first, the console host's output after Up Arrow and a character typed at once was read before the character arrived in 4 of 10 runs of `conhost_up_typing`, where the outpost, busy with the watch, had always read both at once.

A key is never lost while Verbatim runs: a read that fails, or does not answer within the bound, passes the key on with the hook's time, and its watch runs as without holding.

A held key pressed while another's read is in flight, or while the watch of the held key passed on ahead of it is unanswered, waits behind it ("Keys behind a held key"). The waiting key gets its own before read once the watch of the key ahead has been answered, whether with its evidence or by ending without it, or once 100 milliseconds have passed since the key ahead was passed on (`KEY_AHEAD_BOUND_MS` in `verbatim-core`), whichever comes first; past the bound it is read as if the watch had been answered, and that watch is left to end as it would, the waiting key's own watch replacing it in the outpost. A key pressed later than the bound is read at once. When a key handled in between starts a newer watch, the waiting key waits for that one instead. The read is made on the waiting key's own trace (`Effect::ForKey`), so that its answer and speech belong to that key; without that, the prototype's first judge pass found the speech of Right after Control+Home cancelled as Control+Home's.

This wait is Verbatim's own. NVDA does not wait: its caret script stops waiting for evidence the moment another script is queued and then says nothing, and the next script reads the caret at once (`_hasCaretMoved` returns when `isScriptWaiting()`, and `_caretScriptPostMovedHelper` returns before speaking, `nvda/source/editableText.py` 94 to 95 and 166 to 167). Verbatim waits so that the next read sees the application after the key ahead: reading the waiting key as soon as the key ahead was passed on, as the prototype did, let the read and the waiting key reach the application before the key ahead was handled, and with the watch asked for before the key is passed on, Shift+Right followed at once by Right was then misjudged in 10 of 60 rounds, 6 of 30 in Notepad and 4 of 30 in the text box (`merged-watch-first-no-wait/` in the merge's evidence, judged in its `analysis-no-wait.txt`), where waiting for the answer misjudged none. The bound is NVDA's default wait for a caret to move (`caretMoveTimeoutMs`, 100 by default, `nvda/source/config/configSpec.py` 364), which NVDA multiplies by 3 in Windows Terminal (`_caretMovementTimeoutMultiplier`, `nvda/source/NVDAObjects/UIA/winConsoleUIA.py` 470 and 486), so 300 ms there; Verbatim's bound is 100 ms everywhere. Without it, a key that moved nothing, such as Control+Home at the top, Right at the end of a field, Up on the first line or Backspace at the start, got no answer until the watch's own bound of 10 seconds, and the next held key, with every key deferred behind it, waited that long: in `text_box_editing`, Right Arrow after Control+Home at the top was held 10,020 ms.

How the bound is kept: when a held key starts waiting for the key ahead's watch, Core asks the shell to end the wait at the bound (`Effect::BoundHeldKeyWait`, with the time left), once per waiting key. The shell keeps that one time beside its other deadlines and wakes the reducer thread for it in the same wait that ends the before read at `HELD_KEY_BOUND` and every other request with a deadline (`next_deadline`), so it adds no wake-up source; the thread wakes for it only when a held key has started waiting, at most once per waiting key, and then enters `Input::HeldKeyWaitEnded`, which reads the waiting key's caret if it still waits and does nothing otherwise.

No branch on trusted caret events. NVDA's one branch is whether a control's caret events are trusted (`caretMovementDetectionUsesEvents`, false for terminals): with it, NVDA waits for an event, without it, it polls the caret. Verbatim's "after" is always the outpost's evidence read, prompted by the application's events and checked against the caret, so text fields and terminals take one path and holding needs no branch. The one exception is the console host, whose caret events come only on its blink timer and so are no prompt evidence; its watch also re-reads the caret for a short time ("The console host's caret poll").

### The outpost

`ReadCaret` is the read a caret event's report makes, with no formatting: one remote-operations round trip through UIA where the window's provider runs them (the existing caret read program in `verbatim-uia-rops`, which already reads the caret, the selection, the caret's line and the line the selection starts in, so it needed no extension), the classic UIA reads otherwise, and the edit control's messages for a classic edit control. It joins the node's remembered caret reports, so the watch takes it as its baseline, and leaves the selection kept for comparison as it was, so the key's answer compares with the same selection as without holding. Backspace's character before the caret or the selection's start comes from the line it reads, as Core already worked it out. In a focused terminal it is instead a read of the terminal, sent to Core as a snapshot whose caret answers it, so the reading rules compare the key's effect with the screen just before the key.

Remote operations audit (CLAUDE.md): the before read is one round trip through UIA, the same program as a caret report; nothing reads the caret twice in one place. A possible reduction left for later: the watch's first check, which follows the before read by a few milliseconds and finds no evidence when the application has not yet handled the key, could be skipped when the before read is that recent.

### The console host's caret poll

A documented workaround to the rule that a watch waits only for evidence (Dickson, 2026-10-26). In the console host, a caret key's watch that finds no evidence on its first check re-reads the caret every 5 ms until a check finds the evidence, its own re-read or the check an event makes, the console's caret event (`EVENT_CONSOLE_CARET`) included, or 50 ms after the key was passed on, whichever is first; a watch whose last re-read, at that bound, finds no evidence ends as a watch ends at its own bound, answered `WatchEnded`, and nothing is said for it.

Why: the console host raises its caret events only on its cursor's 530 ms blink timer, one tick covering every move since the last, and nothing earlier follows a caret move: no text change, console update, property change or focus change (`experiments/the-console-host-raises-its-caret-events-on-its-blink-timer/`, 120 Left and Right Arrow presses each in cmd and Windows PowerShell). The caret's signals came 257 to 278 ms after the key at the median, about 500 at the 95th percentile and at most 540, while the cursor itself had moved at the median within 1 ms, at the 95th percentile within 5 ms in PowerShell and 33 ms in cmd, and at most 54 ms after the key. The watch's first check, asked for before the key is passed on, always comes before the console host has handled the key, so without the poll every key that moved only the caret waited for the next tick of the blink timer. The bound is half NVDA's: NVDA does not use caret events in consoles (`_get_caretMovementDetectionUsesEvents` returns false, `nvda/source/NVDAObjects/behaviors.py` 527 to 530) and polls the caret every 10 ms until its 100 ms timeout (`_hasCaretMoved`'s `retryInterval`, `nvda/source/editableText.py` 70 and 150 to 160). A key whose caret moves later than the bound is still spoken: the console's caret event that follows reads the terminal, as any caret event of a focused terminal does, and the reading rules say what moved.

How: the poll belongs to the open watch (`OpenWatch::poll`, `outpost/caret_poll.rs`), set when the first check leaves the watch open and the node is the focused console host's text area (`text_reads::console_focus`); Windows Terminal, whose caret events are timely, and every other text field take no poll. Each re-read is the watch's own check, one remote operation through UIA, made by the worker on `Item::Wake`: the worker asks the intake to wake it at the next read (`caret_poll::wake_for`, `Intake::wake_at`), and the intake's wait for work ends then on a high-resolution waitable timer, since a wait at the system's timer resolution, 15.6 ms by default, would miss most reads. Only the worker asks for its wakes, so none can be taken back by another thread's write. The poll stops with the watch, answered, replaced by the next key's or ended by a focus on another node. A console caret event for the watched node does not stop it: the event's check answers the key when it finds the evidence, and otherwise the poll goes on, since a blink tick left over from an earlier cursor set, such as `PSReadLine`'s set that moves nothing, can come after the key and before its move. A worker the watchdog abandoned during a re-read leaves alone the watch open when its read returns, which is its replacement's: the re-read is matched to its watch by the request, not the node. A watch answered by a re-read has the terminal read after it, as a first check that answers does. The key's time is the watch's `pressed_at_ms`, which for a held key is when Core passed it on; a watch without it is bounded 50 ms after it opened.

Costs, per caret key the first check finds unmoved: at most 10 more remote operations and 10 more wake-ups, the worker's, one per re-read, fewer when the caret moves sooner. A key that moves nothing, such as Left Arrow at the start of the line, now pays all 10; its watch is answered after 50 ms rather than left open, so the next held key waits for it at most that long instead of 100 ms.

Measured on 2026-10-26 on Dickson's x64 machine, release builds of main at 0dbec69b (before) and of the poll (after), one run of each scenario, the compositor below 130 percent of a processor before each, each build with a temporary debug log, not committed, of every watch and every check. Announcements of one character, a space or "blank", by the latency line's time from the last key to speech, minimum, P50, P95, P99 and maximum in milliseconds, before then after:

- `measure_keys_conhost`, caret keys and Backspace (108 and 123 announcements): 2.7, 3.4, 44.0, 146.8, 233.1, then 2.9, 3.5, 9.0, 9.4, 9.4. The typing echo (724 each): 1.6, 3.9, 5.4, 11.0, 17.4, then 1.6, 3.8, 5.2, 7.4, 15.6.
- Of its 141 watches, 45 and 48 stayed open after the first check. Before, they were answered 84 ms after opening at the median and 434 at most; after, all 48 polled and were answered within 5 ms, 1 at the median, and none reached the bound. Caret reads by watches: 186 before and 189 after, 1.32 and 1.34 per key, since one re-read, or the console update's check that comes as soon, found each move.
- `measure_keys_windows_terminal`: no watch polled. Its caret key tail differed between the runs (P95 61.1 then 125.8, maximum 150.6 then 512.9, over 76 and 57 announcements), with no code path changed there; the backlog behind held keys there varies from run to run ("Keys behind a held key"; `docs/performance.md`, "Live, against the build before").

The poll's ticks were then moved from a thread of their own to the intake's wait, which only the worker sets, since the ticker thread's write of the intake's one wake time could be overwritten by the worker's and the tick lost. Measured on 2026-10-26 on the same machine, release builds of d8cfe4f1 (before) and of the change (after), three runs of `measure_keys_conhost` each, the three after first and then the three before, the compositor below 130 percent of a processor: caret keys and Backspace (132 announcements a run), P99 16.2, 14.3 and 14.0 and maximum 22.9, 16.4 and 16.8 before, then P99 10.7, 10.0 and 10.0 and maximum 13.3, 11.6 and 13.0 after; P50 3.5 or 3.6 in every run. ### The shell

The app keeps a held key's stroke in its line until Core passes it on, then sends it with `SendInput`: the gesture's Shift, Control or Alt that Windows does not have down are pressed before it and released after, and the key is released first if Windows still has it down, as NVDA's `KeyboardInputGesture.send` does. Since every transition after a held key is deferred behind it, the modifiers are as they were when it was pressed, so this sends extra modifiers only for a key whose modifiers went down before the hook could see them. Each pass-on logs how long the key was held (`verbatim::held_key`, `held_us`). Verbatim is not idle while any key waits in the line, since that key has not reached its application (the idle barrier's own conditions, `docs/design/communication.md`, section 6.7).

The bound: the before read is a request with a deadline of 150 milliseconds (`HELD_KEY_BOUND`). Past it the request ends as unanswered and Core passes the key on without the read. The value: above the slowest before read seen in every run here (the longest hold of a key that waited behind no other was 65.5 ms, in a trace of Windows Terminal, and 25.8 ms in the merge's stale caret runs), and short enough that a key the outpost cannot read for still reaches the application before it feels lost; NVDA's default wait for a caret move is 100 ms. It is a bound on a request, not a sleep: nothing waits on it unless a read is outstanding.

## Costs

Measured on the prototype, before the merge added the order of keys behind a held key and the wait for the key ahead's answer. A key now also waits for the key ahead of it when it is pressed during that key's hold, or within 100 ms after that key was passed on while its watch is unanswered; that wait is measured in "A key held with auto-repeat".

- Latency added per held key, from the hook's press to the re-sent key's injection (minimum, P50, P95, P99, maximum, in ms): text box 0.9, 1.4, 4.9, 12.4, 44.3 (1,305 keys); Notepad 1.5, 2.0, 9.0, 12.7, 44.8 (1,305); console host 1.2, 1.6, 3.9, 5.7, 12.7 (396); Windows Terminal 1.3, 1.9, 3.6, 32.7, 62.8 (396).
- Calls: one round trip through UIA per held key (the before read), or the edit control's window messages for a classic edit control, on top of the watch's checks, which are unchanged.
- Wake-ups and processor time (`cargo xtask trace scenario`, debug build, info logging): in the console host's window (13 to 18 s, typing and arrows) holding added 6 percent of wake-ups (3,434 to 3,651) and 3 percent of processor time (578 to 596 ms); in Windows Terminal's, 7 percent (3,496 to 3,734) and 4 percent (610 to 634 ms). The reducer thread took 36 and 44 percent more wake-ups, the outpost's worker 24 and 15 percent more, and the hook thread 20 and 10 percent more, from the injected press and release. An earlier pair of branch traces, before two bug fixes that do not touch this path, gave 17 and 13 percent more wake-ups. From the hook's extra wake-ups, two per held key, these come to roughly 8 to 13 wake-ups and 0.7 to 1.5 ms of processor time per held key. The text box and Notepad traces are not compared: their fixed windows (46 to 54 s) caught different stretches of the workload in the two builds (the base caught the drains between steps, the branch the keys), so their totals measure the windows, not holding.
- Code: about 1,270 lines added on the branch: about 800 in the crates' sources (the hook's in-file unit tests among them), 380 of tests and measurement workload, and 90 of crate documentation.

## A key held with auto-repeat

The one case where the wait for the key ahead repeats is a key that moves nothing, held with auto-repeat: every repeat waits for the one ahead of it. `measure_held_repeat_text_box` measures it: three times, Control+End in the Windows Forms text box, then Right Arrow held about a second, as Windows' default auto-repeat sends it (the press, then 15 repeats from 500 ms, 33 ms apart, and the release at 995 ms), with the time the release was sent. The figures come from Verbatim's log (`verbatim::held_key`) against that time, with the evidence in `target/e2e-evidence/m42-key-holding-fixes-2026-10-22/`.

- Fixed: the last repeat reached the application 1,064, 1,047 and 1,055 ms after the release in the three rounds; from the first repeat on, each was passed on about 110 ms after the one ahead of it (the 100 ms bound, then the read), so the backlog grew by about 77 ms per repeat. Nothing was said after the release in any round: Right Arrow at the end of the text moves nothing, its watch gets no answer, and a watch that ends without evidence says nothing.
- Before the fix (main at fd1b92a5, whose holding is as at 8a9c66c5, built and named with `--verbatim-exe`): the last repeat reached the application 149,164, 149,151 and 149,200 ms after the release, each repeat waiting out the watch of the one ahead, 10 seconds; nothing was said either.
- The press itself and the first repeat, 500 ms later and so past the bound, waited for nothing (held 1 to 2 ms).

## Limitations

- A stalled reducer thread delays caret keys in text fields, and every key pressed after one, until it recovers, where before holding keys reached the application at once whatever Verbatim was doing; the bound covers only the outpost's read. If Verbatim exits while keys are held, those keys are lost.
- The foreground changing between a key's press and its pass-on sends the key, and the keys deferred behind it, to the new foreground window, as NVDA's would; accepted (Dickson, 2026-10-22). If the new window is elevated, Windows drops them.
- A key auto-repeating is held press by press, so the application receives separate presses rather than repeats.
- Verbatim's own commands (a review command, select then copy) are not deferred: one pressed while a held key waits runs before the held key reaches the application.
- The before read's bound (`HELD_KEY_BOUND`) was never reached in these runs, so the path that passes a key on without its read ran only in the unit test.
- A held key waiting behind another waits for that key's watch to be answered, at most 100 ms after that key was passed on, where before holding it reached the application at once; a key that moves nothing, held with auto-repeat, therefore reaches the application about once every 110 ms, behind the repeats (see "A key held with auto-repeat").
- The lock keys pass at once while keys are held back, so a letter typed before Caps Lock and deferred behind a held key reaches the application after Caps Lock and is typed in the other case; a numpad key pressed behind a held key and before Num Lock likewise arrives as Windows translated it when it was pressed.
- No release-build figures; all are debug, as the measuring guide's key workloads are.
- The text field traces are not comparable (above); a hand-made trace over a fixed number of keys would settle their cost.
- NVDA's settings on this machine have delayed character descriptions on, contrary to its defaults, so its captures say "Alfa" after "a"; the expectations leave that out, as the comparison guide requires NVDA's defaults.
