# NVDA handler layer inventory: UI Automation, MSAA and IAccessible2, Java Access Bridge, and their native side

Scope: `nvda/source/UIAHandler/` (all), `nvda/source/IAccessibleHandler/` (all), `nvda/source/JABHandler.py`, `nvda/source/oleacc.py`, `nvda/source/winVersion.py` where it changes behaviour, `nvda/source/comInterfaces` generation, and the native code they call in `nvda/nvdaHelper/local/UIAEventLimiter/`, `nvda/nvdaHelper/UIARemote/`, `nvda/nvdaHelper/local/UIAUtils.cpp` and `nvda/nvdaHelper/remote/` (IA2 support, live regions, injection). Every line range below was read at the pin. Where a decision depends on another area (`eventHandler.shouldAcceptEvent`, `isPendingEvents`, `lastQueuedFocusObject`, NVDAObjects' own properties), it is named as a dependency and not inventoried here.

Replay classes, as briefed: R1 runs as-is with the harness's existing stand-ins; R2 needs a named new stand-in; R3 needs a clock or thread-order seam; R4 depends on Windows reacting to NVDA's own actions; R5 is native or in-process code; R6 is not needed.

## What the harness already stands in (read from `nvda-oracle/uia/boot.py`, `standins.py`, `run.py`)

- A real in-process `IUIAutomation6` (comtypes `COMObject`) over a recorded tree: property reads current and cached (with `NS` for not-supported), `GetRuntimeId`, `BuildUpdatedCache`, patterns answered only as "absent" (a pattern object is logged as a miss), conditions (property, not, bool, and/or classes exist but no `Create*ConditionFromArray` member), raw, control and custom tree walkers, `CompareElements`, focus handler and handler-group registration (recorded, not used to filter delivery), `ProxyFactoryMapping` with `count = 0`, `IntSafeArrayToNativeArray` returning a zero count.
- `winUser` and `winKernel`: every function replaced; 15 `winUser` functions implemented, the rest raise. Every `ctypes` function pointer in `winBindings.user32` is replaced by a raiser except five calls about NVDA's own desktop, which pass through to the real system.
- `UiaHasServerSideProvider`, `watchdog.cancellableSendMessage` (WM_GETTEXT and WM_GETTEXTLENGTH only), `appModuleHandler.getAppNameFromProcessID` and `getProcessHandleFromProcessId`.
- `UIAHandler.CoCreateInstance` returns the stand-in; `UIARemote.initialize` is skipped; `enhancedEventProcessing` is set to disabled.
- Stubbed wholesale: `wx`, GUI, braille, and `comInterfaces.IAccessible2Lib`, `tom`, `SpeechLib`. `NVDAObjects.IAccessible` is replaced by a module with two empty classes.
- Events are injected by calling `UIAHandler.handler.IUIAutomationFocusChangedEventHandler_HandleFocusChangedEvent` on the main thread, then `queueHandler.pumpAll`, a drain of the MTA queue, and `pumpAll` again. `IAccessibleHandler.pumpAll` and `JABHandler.pumpAll` (both in `core.py` 1025 to 1026, the real pump order) are not called.

## Native: enhanced event processing (nvdaHelper/local/UIAEventLimiter/, 608 lines)

- Default on: `enhancedEventProcessing = featureFlag(..., behaviorOfDefault="enabled")`, `configSpec.py` 310. The harness turns it off, so it does not reproduce a default NVDA.
- Entry points: `rateLimitedUIAEventHandler_create(IUnknown* existingHandler, out)` and `rateLimitedUIAEventHandler_terminate` (`api.cpp`). The object implements all five handler interfaces and is what NVDA registers with UIA (`__init__.py` 558 to 568).
- Behaviour (`rateLimitedEventHandler.cpp` 30 to 63, 245 to 261; keys in `eventRecord.h`): each event is appended to one list; an event whose key matches a waiting one replaces it, the old entry is erased and the new one sits at the end (newest position). Keys: runtime id plus event id; plus property id for property changes; plus kind, processing and every character of the activity id for notifications; focus and active text position by runtime id alone. The first event into an empty list wakes a flusher thread, which swaps out the whole list and calls NVDA's Python handler for each entry on that thread.
- Needs from the element: only `GetRuntimeId` (`utils.cpp`), which the stand-in implements; NVDA's handler is reached by `QueryInterface` on the Python `COMObject`. So the DLL can be loaded and driven in the test process with stand-ins (R5, drivable).
- What it decides that a user hears: two focus events on one element in one batch become one; two name changes become one, at the later position; notifications of one kind and activity id from one element collapse to the last.
- Seam needed (R3): which events share a batch depends on when the flusher thread swaps the list relative to arrivals, a race between UIA's callback threads and the flusher. A deterministic replay must either declare batch boundaries in the world (recorded as delivered) and use a Python port of the same keying, or drive the native object and wait for each flush; driving it natively alone cannot fix the boundaries.

## The core cycle as a seam (R3)

NVDA's pump (`core.py` 1015 to 1048) runs `JABHandler.pumpAll`, `IAccessibleHandler.pumpAll`, `queueHandler.pumpAll` in that order, then invalidates property caches. A focus winEvent requests an immediate pump, others a delayed one of `PUMP_MAX_DELAY = 10` ms (`core.py` 55). UIA events reach `eventHandler.queueEvent` from UIA's callback threads (or the limiter's flusher) at any time. The harness's `core_cycle` runs only `queueHandler.pumpAll`. A complete oracle needs a stated rule for which recorded events precede each pump, and must call `IAccessibleHandler.pumpAll` and `JABHandler.pumpAll` in the real order.

## Hardest items

1. Enhanced event processing, NVDA's default: a native limiter with its own flusher thread. It is loadable and drivable with stand-ins, but batch boundaries are a race, so replay needs declared batches and a matching port of its keying. The harness runs with it off.
2. The core cycle: which winEvents and UIA events precede each pump decides the limiter's output, `pumpAll`'s newest-first focus choice, the foreground defer and `isPendingEvents`. No seam exists yet, and the harness skips `IAccessibleHandler.pumpAll`.
3. Live reads at handling time: `currentHasKeyboardFocus` (duplicate rule and `shouldAllowUIAFocusEvent`), `GetFocusedElement` on the MTA thread, `GetForegroundWindow` in foreground handling and the defer. The world must answer as of the read, not as of the recording's single snapshot.
4. Delivery by registration: with selective registration, Windows sends property and caret events only for elements NVDA registered; the stand-in must filter by NVDA's registrations, and a recording must hold the events of unregistered elements too.
5. The in-process helper: its registration decides UIA versus object model in Word, Excel and Chromium, and IA2 live regions are computed inside the browser by code that cannot be loaded and driven here.
6. Remote operations: native work in Windows' UIA core; the local executor is a seam, but Word's extensions have no local form.
7. Timers on the stubbed `wx`: fake focus at 50 ms and the desktop re-read at 200 ms; and two 0.5 s `time.time()` windows (window answer cache, live region repeat).
