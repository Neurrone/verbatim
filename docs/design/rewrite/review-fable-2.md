# Adversarial review of design-v2, second pass (Fable, 2026-11-28)

Scope: the parts of `docs/design/rewrite/design.md` changed since `review-fable.md`: release by held views, the outcome-entry rule, the gated limiter, remote operations, the native code newly in the oracle, math, extensions replay and the coverage table, with sizes and the decisions list. Read against today's code at deaf7553, NVDA's pinned source, and the experiments under `experiments/nvda-oracle/`. Nothing was built or run. Line numbers are design-v2's unless a file is named. "The view" is the held view.

Assessment: held views work for ids that rest in a record, and the crossing cases (a late answer, a withdrawn batch, a restart) hold. The view breaks on the one place ids live outside a record, a running entry, which the change to async entries created. On the verification side, three claims go further than their experiments: the real UI Automation core as bulk executor, "one world served to both" for the native code, and the outcome-entry rule on generated worlds.

## Must-fix

### M1. A running entry's ids are in no record, so a view sent during its run releases them

Evidence.
- The view is "computed when the message is sent, from the records; no list of held ids is stored" (144), by `NamesIds` over ledger types that hold a `Named<Id>` (164).
- A running entry is `async fn run(self, cx)` (317): the entry value moves into a future the driver stores "beside `Core`, not inside it" (815). Entry types "are the entry's own data and may cross waits" (294). The front view carries kind, stage and stamps, no ids (54).
- The table at 152 to 162 gives two holders as "the key's entry" and "the entry built from the tell", and names no holder at all for a read's answer between its arrival and its commit.
- Today this works only because entries are data: `held_nodes` walks `self.queue.requests()` and `self.queue.entries()`, and `held_tokens` covers "its waiting entries, its front entry and the entries it appends later" (`crates/verbatim-core/src/state.rs` 957 to 1040).

Sequence, the ordinary focus path. A focus tell with listener token K is stepped at listener position p and waits. It reaches the front; `run(self)` takes K into the future. The entry asks the outpost for the walk. While it waits, Core sends the listener any message: credit rides "on every message Core sends" (95), or a `Watch` replacement, or a `Cancel(Late)`. That message's view has `handled` at or past p and is computed from records, none of which holds K. The listener releases K (145). The entry's next ask naming K is answered "not there", and the focus is not spoken.

The same holds for the outpost: the walk's answer arrives at position q with the line's ids; before the commit the entry waits again, and the per-focus `Cancel` of the old follow (134) goes to that outpost with `handled` at or past q. The line is released before it is committed. M5's loop (899) has it too: the ids a `Wants` read mints sit in the future until the lane record names them.

The build check cannot close it: `Entry: Send` (313) while "every ledger type in Core carries the `NotSend` marker" (824), so entries are not ledger types, and `Named<Id>` must be `Send` to be in an entry at all, so it can sit in any future's locals unseen. The simulator would find it, but the design claims completeness by construction (164). It needs a stated owner: for example the entry's slot in `Queue` holds every id the entry was given, the future holding only places in that slot, so answers land in a record and `cx.ask` never hands an id to the future.

### M2. The outcome-entry rule cannot be met on generated worlds, and does not cover the difference the design sends to it

- An entry pins "the world, the step" and a ruling, and the check fails if it is missing (730). Generated worlds exist to reach races (22, 760 to 768), which is where NVDA's set has several members, and "every seed is checked" (768). So each seed that reaches a race fails until a hand-written, Dickson-ruled entry exists for that world file and step. The rule needs a form keyed by decision and outcome class for generated worlds, or generated worlds cannot be compared at such points.
- The same per-world pinning now applies to a ruled, systematic difference: commit deaf7553 records in `docs/parity/backends.md` (376 to 381) that NVDA keeps the older of two coalesced events and Verbatim the newer, "kept (Dickson, 2026-11-28)". With the limiter on, every flood step with a duplicate differs, and the allowlist admits it only per world, step and count (747). The design still says the coalescing "is to be checked against this" (697) and "must match that or record it" (929), and the ruling is absent from the list at 1050.
- Line 649 says snapshot-against-sequential differences "are handled by outcome sets and outcome entries". An outcome entry requires Verbatim's outcome to be in NVDA's set (730). NVDA's set comes from its thread orders and batch boundaries, all of them sequential reads; a snapshot outcome is in none of them. Such a difference is an allowlist difference or a failure, never an outcome entry.
- "Verbatim gives one output" (728) holds for one order of arrivals at Core. The simulator varies delivery order between pipes (430). The design does not say which schedules a comparison run uses: with one, Verbatim's own order dependence is never set against NVDA's set; with several, a step where two schedules differ fails with no entry able to admit it. State that every explored schedule must give the entry's outcome.
- Whether the check fails when NVDA's explored set changes but still contains the chosen outcome is unstated; since the set is "bounded by the seed budget" (733), it will change with the budget.

### M3. The ordinary-call path is equivalent to a program only on a world that does not change, and the real-core alternative is recommended on a measurement that did not test it

Equivalence.
- The contract suite checks a program "against the same read made by ordinary calls over the same world" (642), a fixed world. In comparison runs "each read takes the latency the world recorded for it" (722). So a program run as ordinary calls spreads over simulated time and can read across a world change, which the design itself says a real program does not (649). The simulator then shows Verbatim behaviour the product cannot have, and hides the snapshot behaviour it does have. The path needs a rule that one program's calls are served at one simulated instant.
- The suite cannot name "a kind of program" as written. Programs are generated from any run of consecutive fusable steps, split at the declared instruction limit and after an act or a walk (`crates/verbatim-uia-rops/src/batch/mod.rs` 9 to 22; `batch/program.rs` 48, `LIMIT` 10,000), and bound through a program cache. One case per step proves no fused run, no split at the limit and no rerun by the fallback rule (`mod.rs` 24 to 28). The ordinary path never meets the limit, so the worst case Dickson asks to be measured is invisible in bulk runs.
- Line 391 has the executor in the GPL logic crates, generic over `Platform`, emitting programs through `verbatim-uia-rops`. That crate is Windows-specific and its builder imports `IUIAutomationElement` (`lib.rs` 37; `builder.rs` 307). A logic crate may not depend on it (389, CLAUDE.md's tiers). So either `Platform` is cut above the programs, and the bulk runs exercise none of the 7,087-line generator, only today's `run_calls`, or the generator moves; the design says neither.

The real core.
- `nvda-oracle/office/runcore.py` and `out_core.txt` show one program, run once, 2.7 ms for that single timed call. The provider is one element on a real, never-shown window, answering three properties, with no fragment navigation, no text provider and no pattern (`GetPatternProvider` returns none). The program calls `IsExtensionSupported` and `CallExtension` only; it reads no property, walks nothing and returns no element.
- Verbatim's programs walk the tree, fill caches, read text ranges and return elements. None of that was run. Line 645's "measured viable ... for all of Verbatim's remote programs" and line 1071 overstate it.
- The provider's `HostRawElementProvider` is the real window's (`runcore.py`, `UiaHostProviderFromHwnd`). Through the real core, a window-hosted element's process id, native window handle and runtime id come from the test process and its real window, not from the world. Core's records are keyed by process id (184), outposts are one per process, and fingerprints use "runtime id and window" (50), while NVDA is served the recorded values by the comtypes stand-in. The alternative needs a mapping, or the two readers see different identities for one world.
- Line 18 says Word's extensions "run ... in the real UI Automation core"; line 663 says the text provider and range provider, about 25 methods, remain. The core ran stand-in extension calls, not Word's sentence movement. Line 653 still says the experiment "is testing" the routes, and the coverage table (635) points at "the route the Office experiment settles", which nothing records as settled.

### M4. For the native code moved into the oracle, NVDA and Verbatim no longer read the same world

Line 628 requires each API "recorded once and served by the one world server to both". The native experiments serve NVDA from live components of the replaying machine instead.
- List views: a real comctl32 control rebuilt in the test process (603). `native/lv.out` shows NVDA's ancestry running through the real desktop window (`native/helper.py` 135 calls `GetDesktopWindow`) and NVDA trying to open live process 6364 ("Access is denied"), a breach of harness rule 4. NVDA's answers come from this machine's comctl32 (`6.0.26100.9818`) and oleacc; Verbatim's would come from the recorded `LVM_*` and `msaa` lines.
- Display model: "the replay redraws the recorded runs with real GDI" (606), so NVDA's rectangles, lines and word breaks come from the replaying machine's fonts and DPI. Excel's cropped state likewise "through real GDI measurement" (657).
- `browse/expB.out` has the same leak: "Process handle 0 for AppModule(... processID=6364) is invalid ... application chrome closed".

Needed: for each rebuilt control, a read-back check that the rebuilt control answers what the recording holds, failing the world otherwise; the font and DPI facts pinned from the header; and the live-machine reads closed.

Also, none of these has a copy check. Lines 18 and 600 say they "are in the oracle" and "moved into the oracle". Line 589's rule is that a world with a live NVDA capture must give the capture's speech; no list-view, display-model, IME, Word or Excel run was set against a live capture, and the Word and Excel object models were written by hand on a machine with no Office (660). They ran; they are not yet an oracle.

## Should-fix

- S1. `HeldView.handled` is `Position(NonZeroU64)` (79 to 83). The first `Ask` to a new generation (the `Watch`, or an outpost's first batch, whose `Ready` came relayed through the supervisor, 106) is sent before Core has stepped any message of that reader, so there is no valid value. It needs a variant for "none yet", by CLAUDE.md's rule against a valid-looking value for a miss.
- S2. `ReleasedAtAnswer` is not made unrepresentable. Its answer still carries ids; nothing in the types stops an entry storing one in a record (the navigator, for example), after which the view names an id the reader released at the answer. Only the simulator's invariant (448) catches it, on a world that reaches it. Give such a request a result type with no ids. The rule at 146 should also say "created by this request and sent in no other message".
- S3. The abandoned worker. With "lost" recommended (263 to 267), Core's records go on naming ids of the current generation that the reader no longer has, and Core is never told which. That contradicts the invariants at 448 and 449 as written, and line 147's release of a withdrawn request's ids is a `Release` job to a worker that is stuck (145, 255). State the exception, or have the outpost answer with the lost ids.
- S4. The limiter's gate (rule 11, 582) is described as "adds the batch's events and only then lets the flusher run". The experiment's only gate is inside the inner handler (`time/run_ratelimit.py` 30 to 35). The first event into an empty list wakes the flusher with no point the harness controls (`rateLimitedEventHandler.cpp` 37, 56 to 59, 90 to 97), so a first batch of several events needs a primer event held in the handler and swallowed by the harness. Say so. "Plausible" boundaries are undefined, and the measurement that would bound them is "optional"; until it is a rule computed from arrival times and measured handler time, the set is the harness author's choice, and line 727's "every member ... is reachable in a real NVDA" does not hold for boundaries. The ungated run delivered all five events in each of 20 bursts, so no coalescing at all at that timing.
- S5. The saved gated run still disagrees with the model and with "keeps the oldest": the burst holds `(window, 20014)` twice and the DLL delivered it not at all (`time/out_rl.txt`). The output is exactly what keeping the oldest gives if every sender's runtime id read failed, leaving the event id as the whole key (`eventRecord.h` 34 to 38), which fits the `GetRuntimeId` stand-in bug line 698 mentions. That is my inference, not verified. The parity ledger already records the finding as fact on the source reading alone.
- S6. List views: the design says the cause of the missing focused state "is unknown" (604); the experiment's own note gives it ("the hidden window is never foreground", `native/lv.py` 88). Delivering focus with `force=True` (85) bypasses NVDA's own focus checks, so list-view worlds cannot judge focus rules, the slice's subject. Any rebuilt hidden control has this limit.
- S7. IME: the recorder "records the boundary calls, or ... the composition string" (610). Boundary calls are the output of NVDA's `ime.cpp`, so recording them means running NVDA's GPL helper inside the recorded application, takes that native code out of the test, and gives the world two recordings of one fact with no check that they agree. The experiment already ran `ime.cpp` over stand-in IMM32 answers; record the raw state only and serve it to both. The replay pass matching the live pass (`native/ime.out`) proves nothing beyond the Python callbacks being deterministic.
- S8. "The recording answers every program Verbatim or NVDA can run" (647) contradicts "a world answers only what was recorded" (480) and the snapshot policy of one level of children (475). A program that walks further, or reads a property outside the recorded union, misses; and 483 then counts a Verbatim-only miss as a Verbatim failure when it is a world failure.
- S9. Calibration (651): the `element` line has `plain` and `ex` only (493). If classic and remote reads of an application disagree, neither executor can replay it: the ordinary-call path gives Verbatim the classic value, and one stand-in provider gives both readers one value. The format needs the value by access path, or the rule must say such applications are outside the replay.
- S10. Object models are both "outside the oracle" (622, 963, 25) and "moved into the oracle" for classic Word and Excel (657 to 660, 18). State the split once: the helper paths are in, fed by which recorder; the rest is out.
- S11. Extensions: a session "is recorded: its inputs (events, answers ...)" (679). That replays one transcript, the reason line 715 rejects recording at the helper's boundary. Run the host over a world, with its reads answered through Core, and keep transcripts as expectations only.
- S12. Tiers: the stand-in UI Automation provider is Windows COM code but is sized inside the world server (1019), which is "platform-neutral" (828). The real-core alternative also needs a Windows session, so the bulk runs would leave the Linux job.
- S13. Sizes. The tooling table has no line for the recorder's in-process hooks (GDI, IMM and TSF), the list-view rebuild, the display-model redraw, the Word and Excel models (about 745 lines measured, 658), the gate's driver and boundary exploration (1023 names only "limiter model"), or the real-core executor. Line 1028's "7,707 lines of Python across 49 files" predates `native/` and `office/`: the folders now hold 62 files and 10,241 lines. The product table has no line for the program generator's move (M3).
- S14. Decisions list. Missing: the keep-newer ruling (M2); which route serves NVDA's remote paths; the IME's "or"; the outcome-entry form for generated worlds. Line 24 states the ordinary-call path as settled while 645 and 1071 recommend the other. Line 704 says the text model "replaces the per-call `text` line above", but 504 is already the model.

## Checked and found sound

- A late answer, a `Cancel` crossing a `Final`, and a withdrawn batch: the ids are either never sent or left out of the next view at or past their position, so they are released.
- An id merged or dropped at arrival is in no record and goes at the next view.
- A reader's restart: ids carry their generation, and line 113's re-take covers the last focus's token.
- A `ReleasedAtAnswer` mint and release happen in one root step, so a follow's tell cannot interleave.
- Math: the three sources match the pinned source (`ia2Web.py` 388 to 420, `UIA/wordDocument.py` 1030 to 1035, `mathType.py` 28 to 45); `mathPres/MathCAT` exists and the install has `libmathcat_py.pyd`. One addition: Chromium's MathML is wrapped with the object's language (`ia2Web.py` 396), so the recorder needs it with the MathML.
- `_fixBridgeFuncs` is at `JABHandler.py` 337.
- The size tables add up to 12,550 and 15,600.

## Could not verify

- Whether the gated DLL and the model agree once rerun (S5).
- That the real core can serve a fragment tree, text ranges and returned elements from a Python or Rust stand-in provider at a cost near 2.7 ms; one sample of an extension call is all there is.
- That a virtual list or an owner-drawn list can be rebuilt from `LVM_*` reads; no run tried either.
- That `expandToLine` and the `Move` edge rules of the hand-written Word model match Word; no Office here.
- TSF, which was not tried (609).
- `out_word.txt` and the caret outputs line by line; I read `out_word2.txt`, `out_excel.txt`, `out_sentence.txt` and the heads of the rest.
