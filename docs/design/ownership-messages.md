# The messages build

Status: built on 2026-10-30; designed that day against main at 50370e74, with its adversarial review's findings (verdict: achievable) and Dickson's decision on merging. It applies [the ownership model](ownership.md)'s rules "Messages are of declared kinds", "Queries have exactly one answer", "Merging only for kinds that declare it" and "Lifecycles as typestates" to the protocol between verbatim.exe and its children, the supervisor and the app shell. It is roadmap milestone M4.4. It ran beside [the input build](ownership-input.md). The refactor preserves what is heard, and this build changed no speech. The mechanism is in the crate guides of `verbatim-model` ("The wire protocol"), `verbatim-outpost` ("The protocol", "The supervisor"), `verbatim-app` and `verbatim-gui` (`docs/crates/`); this document keeps the problems, the choices and the limits.

## The problems

- One enum per direction served both kinds of child, so each receiver dropped what was not its own with a wildcard arm, and a message variant could be added that no receiver handled. `CoreFocus` had been added without anything asking what kind of message it was (c0bbf19b).
- `carries_nodes`, which decides which messages the release position counts, was a `matches!`, so a new variant that carried node ids went uncounted unless someone remembered it. A node could then be released that Core still read. The outpost and verbatim.exe also counted the position at two sites with different filters, which agreed only because none of the filtered messages carried nodes.
- The outbound queue's merge was a set of free functions with no declared barriers or test that Core concludes the same.
- Wanted requests (focus-now, the shell's items) had no single owner, and a focus-now request was never ended when its application exited during a backoff, so `idle_conditions_clear` stayed false and every later `AwaitIdle` timed out (886d8e73). A GUI request for the shell's items was a callback with no answer on drop (76180512).
- The supervisor's `Record` encoded a generation's life in booleans, options and an `OutpostId(0)` sentinel (df4c15d9, difference 25), and any code could build an `Ended`.

## What was chosen, and why

- The wire types moved into `verbatim_model::protocol`, beside Core's `Input` (M4.4, communication decision 13). The framing, encode and decode, `now_us` and the `WinEventKind` conversion stayed in `verbatim-outpost`, since they use the Windows bindings. The serde representation is unchanged. `#[non_exhaustive]` was removed from the moved enums, since inside another crate it would force a wildcard in every match, and the listener, the outposts and verbatim.exe are one build of these types.
- The enums are split by role and direction: `CoreToOutpost`, `CoreToListener`, `OutpostToCore` and `ListenerToCore`. Reason: a message its receiver may not take cannot be decoded, and every receiver's dispatch is an exhaustive match under `clippy::wildcard_enum_match_arm`. A frame of the wrong direction fails to decode and its child is ended as failed. The writer is generic over the child's type, and the listener's cannot be given a routed fact.
- Each enum has an exhaustive `kind()` into six kinds (a query's ask and answer, report, release, lifecycle, routed, configuration), and a unit test lists every variant with its kind, so a new variant changes a reviewed file; it also asserts that Core sends no report, which is the back-channel's shape. That a variant carries no state of Core is a review rule made visible by the list. `carries_nodes` is an exhaustive match, and the outpost's urgent messages take an `Urgent` type that carries no node, so no message that carries nodes can skip numbering.
- `Merge` is a trait with a key, a declared barrier (`All`, `Reply` or `None`) and a `may_merge`, and one generic `merge_into` serves the outbound queue; only `OutpostToCore` implements it, reproducing today's merge exactly. An equivalence test per merged kind reduces every sequence of the older message, zero to two others and the newer against the merged result, and asserts the same Core state and the same utterances from the others, plus the merged report's own utterances as a fixed sequence. It cannot assert that Core says the same with and without the older message, because a merge drops the older report's speech on purpose, as NVDA's limiter does (a value change of "50" then "51" speaks "51" alone). NVDA's limiter is not a merge and stays in the intake, the listener's schedule, `HeldFacts` and the writers' fact replacement.
- Across processes the asking side's request table gives every query its one outcome (reply, "gone" at its generation's `Ended`, or "failed" at its deadline), because a killed process runs no `Drop`. Within a process the answering side holds a `Responder`, whose `Drop` answers "gone". It sits in a thread's shell, never in a pure reducer: the GUI's shell-items requests hold one, and the listener's readers keep the answer owed for each event's marker beside the schedule, with a debug assertion that the owed markers are exactly those the schedule holds.
- The wanted requests have one owner, `wanted.rs`, which ends each exactly once: at its outpost's `Ready`, at `NotWatched`, and for a shell-items request at its 6-second deadline. A request waits through a backoff for the replacement. The supervisor gives the app `NotWatched` after every `Ended` at a retirement or target exit, and `Ended` carries `follows`, set by the supervisor's transition, so "a generation follows" has one writer.
- The supervisor's record keeps what belongs to the application, and its generation is a `Generation` enum (launching, spare given, starting, ready, waiting for a backoff) whose transitions consume the state and return the next with the notices to send. Leaving `Ready` emits `HookRemoved` in the same step. The app's `Live` is `Starting` or `Ready`. The lifecycle variants of `OutpostMessage` carry a `Sealed` that only the supervisor makes, with a test constructor behind the feature `lifecycle-for-tests`. The owner thread itself stays impure, as Dickson decided.

## Limitations

- The merge's reordering: an event of the merged report's node or line queued between the two reaches Core before the merged report, so Core judges it against an older focus than without the merge. It is NVDA's limiter's own effect, and a test per kind pins it.
- A wanted request ended at a retirement just before a new start for the same process is answered "nothing"; the user's next request starts an outpost.
- `kind()` exists for the wire enums only; `OutpostMessage` and Core's effects to other threads have none.
- The backend override is sent as two messages to the outpost and the listener, and the fetch configuration is pushed through a writer that refuses it when full; both are configuration whose version Dickson put in M5.
- The focus-now, activation and dump queries have no deadline; that none waits for ever on a live outpost rests on the outpost's reply tokens, built in the reducer build ([the outpost's reducer](ownership-outpost-reducer.md), "Reply tokens").

## Dickson's decisions

- A reply bars only a caret report with selection changes from merging across it, as before (2026-10-30). A value, name or state change of one node keeps merging across a reply while the outpost's write is in flight; the caret rework generalises the barrier.
- The outposts' reply tokens are built in the outpost's reducer build, so no test is written against the intake, worker and watch that build replaced (accepted 2026-10-31).
