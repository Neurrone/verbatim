## Terms these notes use beyond the record

- Pending focus entry: a focus-kind entry waiting or asked in the event queue. "A focus is pending": at least one stands behind the entry being judged (NVDA's `isPendingEvents("gainFocus")`).
- Starting point: the text anchor a caret key's starting read mints, with the key's unit, word, line and selection report read beside it.
- Watch: the outpost's waiting request that looks for a caret key's effect. Check: one cheap comparison the watch makes.
- Run: MSAA focus and foreground tells merged into one entry and tried newest first.
- Menu slot: the one waiting entry for MSAA menu start, menu end, popup start, popup end and switch end.
- Told, not yet read: Core's fact, per terminal, that a change was told and no full read has begun since.
- Selection baseline: the anchor, held by the outpost, of the selection Core last spoke from, with that selection's text beside it.
- Property table: the one declaration of every property, with its name, its type and how each interface (UI Automation, MSAA, IAccessible2) reads it; an event-kind table beside it declares each event kind once with its teller. A read names a property set fixed at compile time; extensions name entries at run time.
- Shared request list: the one set of object and text requests that Core's own features and the extension surface both use.
- Outcome: one of the five ways an answer ends: a result; refused, with a reason; not there (gone, failed, not started); not responding; ended or stopped (cancelled, abandoned, the reader ended). The detail in brackets is diagnostic; Core's rules branch on the five.

## The builds, in order

One build that changes state at a time, each leaving the product working. Measurements in "Measurements" come first; the first one gates everything.

### Build 0: the fast speech-level tests

Scope: a test level with keys and scripted application events in and speech out, with the listener's, outposts' and Core's real logic, asserting speech only, so it survives the builds below (Dickson, 2026-11-11). Its design is not in the repository and must be written again. What was established for it:

- Today's pieces: `mockapp` is a real UI Automation and MSAA provider driven by standard-input commands (`mockapp/src/stdin.rs` 88 to 442); a real outpost already runs in a test's process (`Outpost::with_focused_element_reader`, `verbatim-outpost/src/outpost/mod.rs` 1033); the listener has no test entry (`run_listener`, `verbatim-listener/src/listener.rs` 2632, registers desktop-wide); `verbatim-app` is a binary only; speech can be read at `SpeechEvents` with `VERBATIM_TEST_AUDIO=null` (`verbatim-app/src/main.rs` 630 to 700); mockapp's `.heard(` waits for intake, it is not a speech check.
- On a desktop made for a test no window has keyboard focus, so a desktop-wide UI Automation handler hears no provider focus event.
- UI Automation's registering thread, its process-wide exit (`release_mta_usage`, `verbatim-uia/src/client.rs` 1154 to 1183) and its timeouts are one per process, so roles cannot simply become threads of one process; D9 records one process as weighed and rejected. The adversarial reading favoured the real executables under the real supervisor on the test's desktop, with the desktop facts supplied from one source every process reads, and an experiment before any build.
- Open for Dickson, from that design: the boundary; whether an experiment runs first; real time or one test clock; the supervisor in the loop; where expectations come from (a capture or an end-to-end scenario's expectation, no optional utterances); the rule texts that narrow tests and documents to behaviour; whether it joins `cargo xtask ci`.
- Decided (Dickson, 2026-11-14): the design weighs the new tests against the existing ones, and an existing test the new level makes duplicative is removed.

### Build 1: the event queue and focus

Scope: the listener takes every desktop-wide hook and a limiter that only merges; tells replace routed facts and carry acceptance's window facts; the property table and event-kind table, and the shared request list, introduced here because this build rewrites the tell's shape, the focus snapshot and the request kinds, so builds 2 and 3 only add entries; Core's inbox and event queue with every focus rule of "Core's rules" below; Core's clock, the live hang check with the ghost mapping, and the give-up with a Cancel that abandons a running call; the readers' deadlines and moved-on rule removed; the supervisor's three jobs and `ListenerEnded`; focus requests with stop points for both backends, a UI Automation focus read as two requests chained through Core; keys, commands, index marks and say-all join the event queue with the choice made at the press, the 150 ms release from the press, the mark on arrival and the speech fence; report focus's outcomes; the test harness's idle; the secure desktop switch and the lock state handled at once; M6.2's single record of an outpost generation in the supervisor's owner thread (ruled to come with this build). Removed: the marker, the hand-over, the live re-read, the readers' ancestry caches, narrowing, the outpost's intake as an event queue, the hang record, the left mark (folded into the readers' last focus), the outpost's own hang checks. It cannot be split without a second route living beside the first.

Open in this build's design: the record moves caret-key handling to build 3, yet this build puts keys in the event queue and removes the paths today's key line rides on; the interim caret-key path between the two builds is not designed anywhere. Likewise focus requests need the details to fetch, which build 3 moves into requests; today's listener reads every detail whatever the theme (`verbatim-listener/src/focus_read.rs` 761 to 763); the property table's sets make the details a choice of set.

Decided (Dickson, 2026-11-13): a cancel carries Core's reason for giving up. After a give-up because the window is hung or the due time passed, the reader only drops work not yet started and leaves a thread inside the call alone, so that call's answer still arrives when the window answers again and is the late answer the record keeps; an abandoned worker's commits stay refused (`verbatim-outpost/src/outpost/worker.rs` 20 to 27). After a give-up because the foreground moved away from the request's window, the reader abandons a thread still inside the call and starts a fresh one. The reason in the cancel is also the source for classing a parked worker as parked on a hung window.

Decided (Dickson, 2026-11-14): Core's reducer thread runs at `Highest` from this build, set where the shell starts it (`verbatim-app/src/main.rs`, the `verbatim-reducer` thread, 360 to 364), amending decision 14 of `docs/design/communication.md` and its section 6.1, which keep the reducer at normal priority. The fact that changed: the relay wakes the reducer by a post to its port, which gives no priority boost, while a pipe's completion gives two, so at normal priority Core waits behind any thread at 8 or above on the processor it is readied on, and under this model several crossings into Core sit on the way to every spoken event. Measured with the crossing benchmark (`verbatim-process/examples/crossing.rs`), release, two runs each: a message into Core through the relay at the 99th percentile fell from 1.8 to 2.1 ms to 0.22 to 0.26 ms during speech and from 2.0 to 2.2 ms to 0.08 to 0.11 ms under a console flood; Core's own request and answer stayed at 0.06 to 0.11 ms. Raised alone in today's product, the reducer starved neither the foreground application's UI thread nor the speech threads and left key-to-speech unchanged; the earlier measurement behind decision 14 raised every computing thread together. The relay stays (decision 3 of the communication design, kept): Core reading the readers' pipes itself, with its thread raised, kept the 99th percentile under 0.1 ms under both loads, and is weighed again only if the relay's 0.2 to 0.26 ms during speech proves too slow.

State: the event queue (one value per entry, waiting or asked).

| Input | Waiting entry | Asked entry |
| --- | --- | --- |
| Reaches the front | judged at once, or its request is sent and it becomes asked | not applicable |
| Its answer arrives with a result | cannot happen; a late answer finds no entry (see "A request in Core") | judged; a follow-up keeps it asked under the same due time; otherwise executed and the next taken |
| The foreground changes | ends if its request would name a window outside the new foreground window's tree or owner chain (another window of the same application included); an entry making no request is not ended | same test; failing it, ends with reason "foreground" |
| Its reader ends | dropped if the ended reader kept its element; an MSAA entry, read by ids, stays | ends with reason "reader ended" |
| An asked entry ends, with a reason | not applicable | ends unspoken; the next taken; the reason's effect below |
| Desktop switch, input desktop does not open | stays and runs as NVDA's (ruled); a focus among them replaces the sleeping focus | the sleeping focus is committed at once; the answer is judged against it |
| Desktop switch, input desktop opens | stays; 200 ms later the read after the return joins the back | same |
| Locked or unknown, and the entry's object is below the lock screen, at its turn | dropped whatever its kind; never committed focus or readers' last focus | its answer is not spoken and moves nothing |
| A non-modifier key, command, braille gesture with an action or key Core sends arrives | marks every caret key ahead silent; records its time in the focused terminal's model; joins the back | same |
| A focus-kind tell arrives | joins the back | joins the back; if the front is a caret key starting or watching, it is judged at once with a focus pending |
| Same object, kind and raising thread waits | merged, the newest keeping its place | not merged |
| An MSAA focus or foreground tell arrives while one waits with no accepted MSAA tell between | merged into its run at the newer place, newest four kept | not merged |
| Menu-slot entries wait together | only the newest kept; at the front, moved once behind the focus and foreground tells waiting behind it | not counted |
| An extension hook holds the front | waits | Core's bound runs from the call's send; past it Core runs the default, cancels, ignores a late answer |

The reasons an asked entry ends, and their effects beyond taking the next: an answer with an outcome other than a result (nothing more); Core's give-up on a hung report (Cancel sent, the sound if attended), at the due time (Cancel sent; a chained entry whose due time passes before its follow-up is sent sends none), or at a foreground change (Cancel sent); the send finding its window hung (nothing sent, the sound if attended); the reader ending (Core appends the read after a replacement). One row, so a new reason is a new item in this list, not a new state.

The focus kinds' rules that read the readers' last focus are under "The two versions of the focus" below; the event queue has no cell for a left mark.

State: a request in Core. Every request has exactly one answer path: its answer, the reader's end, or Core's give-up.

| Request | Its reader can take it | Half-second check finds its window hung | Due time passes | Answer arrives | Reader ends | Foreground changes |
| --- | --- | --- | --- | --- | --- | --- |
| Waiting for its outpost (due time running since Core decided to ask) | shell checks the window: hung, answered not responding unsent (the sound if attended); else sent, Out | not applicable | given up silently, entry ends | not applicable | an outpost failing while starting leaves it waiting for the next start | ends if its window is outside the new foreground window's tree or owner chain; never sent |
| Out | not applicable | given up, Cancel sent, the sound if attended | given up, Cancel sent, no sound | judged by its entry's rules, by outcome | answered "ended" | same window test; failing, given up, Cancel sent |
| Given up | not applicable | not checked again | not applicable | a focus answer, unless the user has switched away (its window outside the foreground window's tree or owner chain), joins the back as a fresh focus entry already answered (re-asked with current stop points if its ancestry no longer meets Core's line); any other answer dropped by request number | forgotten | nothing (the late-answer test reads the foreground on arrival) |
| Answered | nothing | nothing | nothing | cannot happen | nothing | nothing |

Cancel means stop, and carries Core's reason: the reader drops a request not yet started; it abandons a thread still inside the call and starts a fresh one only when the reason is that the foreground moved away from the request's window, and leaves the thread alone when the reason is a hung report or the due time. A reader keeps no deadline and no moved-on rule. A "cancelled" or "abandoned" answer that follows finds the request given up and is dropped by number; a result that follows a hung give-up is the late answer.

Rules on that table: the due time is 11 seconds, 13 for a focus read, the taskbar's reads included, counted from when Core decides to ask; one due time for a whole chained command, a UI Automation focus's two requests included. Every request names the window it calls into: the event's window (a run's newest candidate's), the node's window, the foreground record's for "read the current focus", the taskbar's window for the taskbar's reads, the dump's root for a tree dump (these last two not verified). A request with no window is judged by its due time only. A send the shell refuses enters the inbox as that request's answer, so no reducer step re-enters itself. The shell maps a ghost window to its hung window (`HungWindowFromGhostWindow`) before the check. Requests outside the event queue (an extension host's reads, Verbatim's dialogs, the control plane, later M4.3's spelling check) have the same due time and live check but hold no key; queries answered from a terminal's memory have no window, due time, check or Cancel.

State: the two versions of the focus. There is no left mark: its three effects are what an empty readers' last focus gives (Dickson, 2026-11-13).

| Fact | Set by | Cleared or replaced by | Read by |
| --- | --- | --- | --- |
| Committed focus (NVDA's `api.getFocusObject`) | executing any focus, a reader's or one Core commits itself | the next commit; marked ended but its data kept when its reader is replaced | the stop points' line, the check after a menu end, a UI Automation event on its runtime id, caret tells off the focus, the "text changed" flag, the narrow rule, typed echo's masking, the selection baseline, the key's choice at the press, navigator and review following |

| A focus Core commits itself | an entry's rule (now: the sleeping focus; later maths, a module's object, a recognition result, possibly a composition) | the next commit | its kind selects its gestures in the hook's view; its source node is held; stop points use its source's line, then the readers' last focus's (Verbatim-only, not verified that NVDA's walk meets an interaction object) |

While the readers' last focus is empty: no duplicate test, no whole-window refusal, no stop points sent; the ancestors spoken are compared with the empty fact, so the window's title and the focus are said; a system caret event has no target and is ignored; a replaced reader's re-taken focus is spoken (the two accepted corners).

What Core keeps with the committed focus, each carried in the focus answer: each UI Automation node's runtime id (Core holds none today); the MSAA event's window, object and child ids and the held child id; whether it was reached by a redirect to a focused child, with the child's ids; the foreground window it entered under; which ancestors are simple children; its last states, updated by every state change Core judges for it; whether its value comes from its selection; the dialog text of each dialog among its ancestors; its class verdict (for module rules and the MSAA duplicate test); its rectangle.

The property table, the event-kind table and the shared request list (Dickson, 2026-11-13), introduced in this build:

- Each property is declared once: its name, its type, and how each interface reads it (the UI Automation property id and conversion, the MSAA call, the IAccessible2 call or attribute), with its cost class for the bulk-read gate (`verbatim-outpost/src/gates.rs` 18 to 24). - A read names a property set fixed at compile time; the UI Automation cache request and the remote program are built from the set, so every field the read needs is cached and costs nothing extra; a rule takes a snapshot typed by its set, so the compiler checks that it uses only what its read asked for. - Each event kind is declared once with its teller (a listener hook, the listener's global group, an outpost's `Follow` group, the console host's five), replacing the hook table, the `Follow` group and the one-teller rule written in three places.
- The shared request list: properties of a node by set, navigation, find the first child or descendant by property, a node's children with a set, text reads, actions.
