# Repository audit, 2026-09-02

Transient and untracked; `handoff-2026-09-02.md` is the entry point that
names it. Written for Dickson on returning to the project after six weeks
away. It
records what was read, what was found, and a recommended order of work. Line
numbers refer to the tree at commit 2c383f3.

## Scope and method

Every Rust file in the workspace was read in full, about 42,700 lines. The
runtime crates were read by Claude directly: verbatim-model, verbatim-core,
verbatim-outpost, verbatim-uia, verbatim-ia2, verbatim-app, verbatim-control,
verbatim-speech, and verbatim-input. Two Opus subagents read the rest and
reported back: one covered verbatim-e2e, verbatim-agent, verbatim-inspect,
mockapp, and xtask; the other covered verbatim-gui, verbatim-config,
verbatim-i18n, verbatim-audio, the two synth crates, and the three stubs. The
crate guides under `docs/crates/` were checked against the code as part of
each read. The eight findings of the July 2026 review session (an untracked
note since deleted; all eight are now folded into this file) were
re-verified rather than taken on trust.

`cargo xtask ci` was run on this machine and passed: rustfmt, clippy pedantic
with warnings denied, 387 unit tests with none failing and three ignored, and
the ARM64 release cross-build. The end-to-end suite was not run; it needs a
VM or an interactive desktop.

## The verdict in one paragraph

The architecture is sound and the code is far better documented than most
codebases of any age. The model, reducer, control plane, input state machine,
speech pipeline, config, and i18n crates are in good shape and need at most
small fixes. The problems concentrate in three places. The outpost supervisor
and runtime have a cluster of concurrency defects that all trace to the same
two habits: doing blocking work while holding the outposts lock, and doing
blocking work on the command loop thread. The audio layer has two defects
that make Verbatim go silent or speak at the wrong pitch, which for a screen
reader are the worst class of bug. And the test harness has a handful of
operational defects that each cost a debugging session, most seriously a way
for a scenario that never ran to be reported as a pass. None of this argues
for a restart. It argues for a focused pass over the outpost crate and the
audio layer, and for fixing the harness before relying on it for the NVDA
transcript work.

## Findings, most serious first

Confirmed means the defect is visible in the code as read. Plausible means it
needs a timing or environmental trigger that could not be forced from
reading alone.

### Group one: silent failures a user would hit

1. Supervisor pipe writes under the global outposts lock can freeze all
   announcements, with no recovery. Confirmed. `supervisor.rs` writes to an
   outpost's synchronous anonymous pipe while holding the `outposts` mutex in
   `heartbeat_tick` (line 609), `route_fact` (494), `announce_foreground`
   (439), `on_ready` (522), and `send_to` (347). A pipe write blocks when the
   4 KB buffer is full. An outpost stops reading its command pipe for up to
   five seconds at a time on its own (see item 6), and forever if wedged.
   Once a write blocks under the lock, every other path needing the lock
   stops, including the heartbeat that would have killed the wedged outpost.
   The reducer thread in `verbatim-app` calls `send_to` directly from
   `apply_input` (main.rs line 715), so the reducer stalls too and all speech
   from events stops. The same functions also call `spawn`, a full
   `CreateProcessW`, under the same lock. Fix: never write to an outpost pipe
   under the map lock. Give each `Running` its own writer thread fed by a
   bounded channel whose full arm drops with a log line, since facts are
   newest-wins anyway.

2. The query pool's "parked" count never decreases, so a merely slow
   application gets its outpost killed after eight timeouts, for the rest of
   the outpost's life. Confirmed and not in the earlier review.
   `query_pool.rs` bumps `parked` on every timeout (lines 582 and 669) and
   spawns a replacement worker, but the timed-out worker is not parked at
   all: when its job eventually completes it goes back to pulling jobs from
   the shared receiver (line 630). So each timeout permanently adds one
   worker thread, and the counter measures "timeouts ever", not "threads
   currently stuck". The supervisor's `PARKED_THREAD_KILL_THRESHOLD` of 8
   then means "kill and respawn after any eight 300 ms deadline misses",
   which a loaded Explorer or a busy XAML app will produce in normal use.
   Each respawn loses the outpost's element cache and hooks. The crate guide
   (`docs/crates/verbatim-outpost.md` line 84) states the worker "stays
   parked", describing the intended design rather than the code. Fix:
   decrement when an abandoned job completes, or track abandoned workers by
   identity and retire them when they return.

3. The audio sink goes permanently silent after a device invalidation.
   Confirmed. `wasapi.rs` `begin` (lines 271 to 280) only rebuilds the stream
   when the PCM format changes. After `AUDCLNT_E_DEVICE_INVALIDATED`, which
   happens on unplugging a USB headset, switching the default device, or a
   driver restart, every later utterance at the same format reuses the dead
   client, `Start` fails, and nothing above the sink retries. Verbatim stays
   silent until restarted. The same permanent state follows a render-event
   timeout, which leaves `running` true so the next `Reset` and `Start` fail.
   Fix: drop `self.stream` on any stream error so the next `begin` rebuilds.
   Also close the render event handle on the failure paths of `open_stream`
   (line 180 onward), which currently leaks it.

4. The first utterance after startup, and after switching to a voice with a
   different sample rate, plays at the wrong speed and pitch. Confirmed.
   The speech manager reads `driver.pcm_format()` before calling `speak`
   (`manager.rs` line 431), but the OneCore driver only learns the real
   format from the synthesized WAV after synthesis (`lib.rs` line 336) and
   reports a hardcoded default until then (lines 62 and 244). The sink opens
   the stream declaring the stale rate and auto-conversion faithfully
   resamples the mismatch. Fix: let the driver report the format from inside
   `speak`, through the sink, rather than before it. This is a small change
   to the `SynthDriver` and `PipelineSink` contract.

5. Snapshot versions can be allocated and sent out of order, and the reducer
   then drops a genuine focus announcement as stale. Confirmed. `runtime.rs`
   `emit_at` (lines 179 to 194) takes a version from an atomic counter on the
   emitting thread and then sends on the outbound channel; concurrent
   emitters exist (the announce lane, pool workers, UIA callback threads,
   the background window retry). Thread A takes 5, thread B takes 6 and
   sends first; the reducer records 6, sees 5, drops it, and refetches the
   old focus. Fix: stamp the version in the single outbound writer thread,
   which is the only place with a total order.

6. Five-second query-pool calls run synchronously on the outpost command
   loop thread, so pongs and fact delivery stop while they run. Confirmed.
   `handle_dump_tree` (line 991), `handle_ancestor_chain` (1013),
   `handle_navigate` (1038), `handle_activate` (1058), and the navigation
   arm of `handle_fetch` (971) all call `pool.run` and wait. Two five-second
   dumps back to back exceed the nine-second wedge threshold, so a healthy
   outpost inspecting a hung application is killed mid-answer. This is also
   how the command pipe fills up and triggers item 1. Fix: reply from the
   pool worker, as `handle_fetch`'s snapshot arm already does.

7. In the settings dialog, pressing Enter while focused on Cancel commits
   and closes, and Enter on Apply closes the dialog. Confirmed.
   `dialog.rs` binds one handler that treats Enter as "activate OK" (lines
   327 to 332) to the dialog, OK, Cancel, and Apply alike (261 to 296). The
   guide says "Cancel reverts". Separately, the shortcuts Ctrl+Tab, Ctrl+S,
   and Enter are bound to four widgets only, so they are dead whenever focus
   is inside the Speech panel, which is where a user spends their time.
   Both bugs live in logic that will be rewritten in the GUI port; the
   routing table should be extracted into a pure, tested function first so
   the C++ layer cannot reintroduce them.

### Group two: defects that cost a debugging session each

8. Paced mode in the end-to-end suite silently discards utterances.
   Confirmed. `speech.rs` `wait_for_audio_finished` (lines 74 to 91) reads
   frames until `SpeechFinished` and pushes any speech frame it passes to the
   timeline, then drops it, so that utterance can never satisfy the next
   assertion. `--record` implies `--paced`, so every recorded run uses the
   path that can lose an announcement and then time out on the next step.

9. A scenario that never ran can be reported as a pass. Confirmed.
   `xtask/src/vm/test.rs` (lines 402 to 414) reads the scenario's summary
   file after the subprocess exits, but only the subprocess clears that
   directory, so a subprocess that dies before reaching the runner leaves
   the previous run's summary in place and it is read as this run's result.
   Fix: remove each selected scenario's artifact directory before spawning.

10. A deploy that fails mid-copy leaves the guest with its agent stopped.
    Confirmed. `deploy.rs` stops the agent task before copying (lines 238 to
    252) and only restarts it after every copy succeeds (270 to 277); the
    `?` at line 263 skips the restart. The next test run then fails at
    `wait_for_agent` after five minutes with no hint why.

11. The agent's control tunnel can leak a stuck thread and an open pipe
    handle per tunnel. Confirmed. `tunnel.rs` lines 62 to 79: the
    tcp-to-pipe thread calls `CancelIoEx` once after its loop ends; if the
    pipe-to-tcp thread is between reads at that moment, its next overlapped
    read blocks forever, the join never returns, and the handle and socket
    clones leak. Every scenario opens two tunnels. Also, `read` maps every
    pipe error to a clean end of stream (line 217), so the one diagnostic
    the module exists to produce cannot distinguish failure from close.

12. Video recordings can be attributed to the wrong scenario. Confirmed.
    `recording.rs` writes every capture to one fixed guest path (line 103)
    and never deletes it after pulling (line 346), so a scenario whose
    ffmpeg produced nothing pulls its predecessor's file under its own name.
    The recording client also has no connect or read timeouts (line 427),
    the lesson `verbatim-e2e`'s own agent client already learned.

13. The fixed flush order for facts queued across an outpost spawn can drop
    the menu announcement. Plausible. `PendingFacts::drain` (supervisor.rs
    lines 1021 to 1031) always flushes focus before menu-popup regardless of
    observation time. A menu observed before the focus on its first item
    flushes second, arrives at the reducer with an earlier timestamp, and is
    dropped by last-observation-wins, since a menu node is neither a window
    nor an ancestor. The item is still announced; the container name is
    lost. Fix: drain in observation order.

14. A respawn can briefly produce two outposts for one pid and lose the
    queued facts of one of them. Plausible, narrow window.
    `respawn_if_alive` and `kill_and_respawn` remove the map entry, drop the
    lock, spawn, then re-insert (lines 553 to 560 and 684 to 693). A fact
    routed in between finds the entry vacant and spawns its own outpost,
    which the re-insert then overwrites and kills through its job handle,
    together with anything queued on it.

15. A staleness refetch that reports the node gone clears focus but leaves
    the navigator on the dead node. Confirmed; this is finding 6 of the
    earlier review, `reduce.rs` lines 797 to 800.

16. A late window announcement is spoken at Interrupt priority and cuts off
    the control announcement it arrived after. Plausible. The reducer's
    carve-out for stale windows (`reduce.rs` lines 100 to 123) speaks the
    window with `SpeechPriority::Interrupt`, which cancels whatever is
    playing, so the user hears the control's name start and then the window
    name. `Next` or `Queued` priority is probably what is wanted for the
    late case.

17. OneCore synthesis adds up to about 30 ms of dead time per utterance by
    polling with one-millisecond sleeps (`lib.rs` lines 328 and 386), which
    Windows rounds up to the timer resolution, and cancellation is only
    observed between PCM chunks after the whole utterance has been
    synthesized, so interrupting a long paragraph waits out the synthesis.
    `apply_voice` also re-enumerates every installed voice on every
    utterance. All confirmed.

18. The outpost spawns a fresh OS thread per announce, per probe, and per
    late window retry (`runtime.rs` lines 215, 860, 1342) with no bound.
    Under focus churn this is a thread creation storm rather than a queue.
    Confirmed, and a structural cousin of item 2.

19. The node-id registries never forget. The UIA registry's forward and
    reverse maps (`registry.rs` in verbatim-uia) and the MSAA registry grow
    for the life of the outpost; only the live-element cache is capped, and
    that cap is the "clear everything at 2048" the handoff already calls
    crude. Long-lived outposts for Explorer or a browser will grow without
    bound. Small per entry, real over a day.

20. A unit test mutates the process environment concurrently with tests
    that read it (`verbatim-e2e/src/artifacts.rs` lines 302 to 310), the
    exact data race edition 2024 made `set_var` unsafe for.

21. The mock application under-reports MSAA fidelity: `accSelection` is
    stubbed to fail (`msaa.rs` lines 508 to 510) so the selection enrichment
    path the product relies on is never exercised cross-process, and absent
    names and values return empty strings where a real provider returns
    `S_FALSE`, with the tests compensating on their side.

### Group three: structure, duplication, and drift

22. Two generations of announcement machinery coexist in `runtime.rs`. The
    pre-D13 poll (`run_announce`, lines 1159 to 1261) and the D13 lane
    (`window_announce_job`, `background_window_retry`, `run_msaa_fact`,
    `run_uia_fact`) implement the same window-then-control logic twice with
    different retry budgets. The poll is documented as a fallback but it is
    a full second implementation.

23. Direct MSAA access is duplicated into the outpost
    (`msaa_window_snapshot`, `runtime.rs` line 1952) instead of living in
    verbatim-ia2, by its own admission.

24. `NavigateDirection` is defined three times (protocol, verbatim-uia,
    verbatim-ia2) with two mapping functions between them. The MSAA state
    bits are defined twice (verbatim-ia2 and mockapp) by hand when the
    `windows` crate exports them. `AGENT_PORT` and the stderr log path are
    each duplicated between crates with a comment that no longer holds since
    the dependency now exists. There are two hand-written agent clients.

25. Dead code: `Arbitrator::resolve_with` and `Resolution` in
    `arbitration.rs` are used only by their own tests and encode the
    opposite timeout policy from the live code (cache a timeout as non-UIA
    versus leave it unresolved); `DialogGuard` and `OpenAction` in
    `verbatim-gui/src/plan.rs` are exported and used by nothing;
    `SpeechCollector::transcript` in verbatim-e2e has no callers and its
    tests do not call it either; `acquire_ia2` is an empty function.

26. Doc drift, in each case the doc describes the intended design and the
    code does something else:
    - The outpost guide says an abandoned worker stays parked; it rejoins
      the pool (item 2).
    - The app guide and three comments in `main.rs` say multi-press counting
      is not wired yet and the router always passes zero; the input state
      machine implements it and the router passes `emitted.repeat` through.
    - `runtime.rs` line 774 and 804 say the reducer does not announce
      selection and notification events; it has since M3.
    - The verbatim-uia probe doc says the outpost treats a timeout as
      non-UIA; it deliberately leaves it unresolved.
    - The supervisor doc says the memory cap makes the kernel kill a leaking
      outpost; a job memory limit makes allocations fail, and the abort
      that follows is what ends the process.
    - The GUI guide claims dialog-level shortcut handling and "Cancel
      reverts" (item 7), and lists four planning functions as public API
      when the module is private.
    - The agent guide omits `KillProcessesByName` and describes a symmetric
      tunnel teardown that only one direction performs (item 11).
    - The xtask help text and two comments say "no filter runs every
      scenario"; the registry excludes the Diagnostic group by default.
    - `test.rs` lines 163 to 167 have two doc comments spliced together, and
      line 175 has a run of stray spaces inside a user-facing warning.

## Per-crate verdicts

- verbatim-model: keep as is. Small, pure, correct.
- verbatim-core: keep with two small fixes, items 15 and 16. The reducer is
  pure, readable, and has a 2,000-line test file that earns its keep.
- verbatim-outpost: keep the design, rewrite the concurrency. Items 1, 2, 5,
  6, 13, 14, 18, 22, 23 all live here. The right shape is one writer thread
  per outpost with a bounded channel, versions stamped in the writer, pool
  accounting that tracks abandoned workers by identity, replies sent from
  pool workers, and the legacy poll deleted once the D13 lane covers the
  startup target. This is a few hundred lines of change in two files, not a
  rewrite of the crate.
- verbatim-uia and verbatim-ia2: keep with targeted fixes, chiefly registry
  pruning (item 19) and moving the window snapshot back into ia2. The COM
  discipline is careful and the SAFEARRAY ownership is documented.
- verbatim-app: keep as is apart from the stale multi-press comments. The
  composition root is long but legible.
- verbatim-control: keep as is. The overlapped-pipe reasoning is correct and
  the dispatch loop is tested without a real pipe.
- verbatim-speech: keep with the format-negotiation change (item 4). The
  lane logic and cancellation are correct.
- verbatim-input: keep as is. The state machine is pure and well tested.
- verbatim-audio: keep with targeted fixes (item 3, the handle leak, and a
  prefill before the first event wait). Consider MMCSS registration later.
- verbatim-synth-onecore: keep with targeted fixes (items 4 and 17).
- verbatim-config, verbatim-i18n, verbatim-synth-capture, verbatim-inspect:
  keep as is. Minor notes only: `for_e2e` sits away from its type, the
  message accessors could be generated, the capture synth has an unused
  dependency and a misleading comment, and the inspect formatting functions
  have no tests.
- verbatim-gui: rewrite, which is already the plan. Salvage `plan.rs`,
  `hidden_frame.rs`, `foreground.rs`, `shell_items.rs` minus two call-after
  lines, and the tray click code; extract the shortcut table and the dialog
  lifecycle rules into pure functions before porting.
- verbatim-e2e: keep with targeted fixes (items 8 and 20, delete
  `transcript`). The guard struct, dedicated speech connection, and
  artifacts seam are the right design.
- verbatim-agent: keep with the tunnel fixed (item 11) and a bidirectional
  tunnel test added. Note the agent accepts unauthenticated connections on
  all interfaces by default; acceptable on a lab network, worth a documented
  decision.
- mockapp: keep with fidelity fixes (item 21). The lock-before-callback
  discipline is consistently right.
- xtask: keep with the four operational fixes (items 9, 10, 12 and the
  recording client timeouts). The `Host` trait has one implementation and
  no test double, which is the worst of both; the Proxmox backend will give
  it a second implementation, and a fake for tests should come with it.

## What this means for the restart question

Nothing here changes the earlier recommendation. The defects cluster in
verbatim-outpost, the audio layer, and the harness, and each cluster has a
clear, bounded fix. The crates that would be the most expensive to recreate
are the ones in the best shape. The one crate genuinely worth rewriting is
the GUI, and that rewrite is already planned for other reasons.

## Suggested order

1. Harness first, because everything after depends on trusting it: items 9,
   10, 12, 8, 20. A day.
2. Audio, because silence and wrong pitch are the two worst things a screen
   reader can do: items 3 and 4. A day, including the driver contract change.
3. Outpost concurrency as one change set: items 1, 5, 6, 2, then 13, 14, 18.
   Two to three days, verified against the end-to-end suite on fresh
   restores and the cold-start loop the handoff describes.
4. Proxmox backend, NVDA transcript tool, GUI port, in the order already agreed.
5. The reducer nits, registry pruning, dead code, and doc drift can ride
   along with whichever change touches the file.
